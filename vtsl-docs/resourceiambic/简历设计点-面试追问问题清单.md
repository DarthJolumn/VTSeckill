# 简历设计点 · 面试追问问题清单

> **用途**：针对简历中每个设计点，穷举面试官可能追问、以及设计中必须回答的问题，并给出答案方向（源自《电商系统实战》课程大纲 + 项目知识库）。
>
> **配套文档**：`简历项目与课程内容匹配分析.md`（设计点 ↔ 课程章节映射）
> **章节引用格式**：`第X章 §Y` 指向课程大纲标题。

## 〇、通用追问套路（先建立框架）

面试官的问题大多逃不出以下 7 个维度，回答任何设计点时都可以按这个框架自查：

| 维度 | 典型问法 |
|---|---|
| **用户感知** | 用户什么时候看到结果？失败/延迟时用户看到什么？体验如何兜底？ |
| **一致性** | 最终一致还是强一致？中间不一致窗口多大？谁兜底？ |
| **故障场景** | 中间件挂了怎么办？消息丢了/重复了/乱序了怎么办？ |
| **幂等** | 重复调用会不会出问题？幂等键是什么？ |
| **性能** | 压测数据口径？瓶颈在哪？为什么是这个数？ |
| **扩展性** | 多实例部署是否一致？新增策略/渠道/类型要改什么？ |
| **降级** | 系统扛不住时放弃什么？保留什么？如何切换？ |

> **原则**：每一个"异步"都必须回答"用户感知"和"最终一致性"；每一个"缓存"都必须回答"击穿/穿透/雪崩"；每一个"消息"都必须回答"不丢/不重/不乱序"。

## 一、秒杀系统

### 1. Kafka + 异步落库 —— 用户感知专题（你问的核心）

**问题 1：用户下单后，何时收到"成功"响应？**
- 答案方向：秒杀场景**不能等落库完成再返回**（延迟太高）。两种模式：
  - **先扣 Redis 即返回**（实时模式）：Redis Lua 扣减成功 → 立即返回"下单成功" → Kafka 异步落库；
  - **排队返回**（MQ 排队模式）：返回"排队中，请稍后查询结果"，**不承诺即时成功**。
- 课程依据：第6章 §5 商品秒杀「秒杀结果轮询——状态机驱动的用户体验」。

**问题 2：异步落库期间，用户如何查询结果？**
- 答案方向：**结果轮询**——秒杀结果状态机（成功/发放中/已售空）写入 Redis，前端定时轮询；**查不到默认降级为"已售空"**（第6章 §6 优惠券秒杀）。要能讲出**为什么选轮询而非 WebSocket**（轮询无状态、易水平扩展、WebSocket 需维护长连接与推送一致性）。
- 知识库提示：本项目另有 WebSocket 推送方案（Redis Pub/Sub 多实例广播），可两者对比。

**问题 3：Redis 扣减成功了，但 Kafka 消息丢了，用户以为抢到、实际订单没落库——怎么办？**
- 答案方向（三层兜底）：
  1. **发送可靠性**：本地消息表 + 事务提交后发送 + 定时补投（第8章 §1 MQ事务消息发送组件——先 DB 后内存、5 分钟缓冲）；
  2. **消费可靠性**：手动 ACK + 重试 + 死信 + 定时任务补偿（第8章 §3）；
  3. **对账兜底**：库存对账/订单对账扫描出"有扣减无订单"的差异，自动补单或回补（第5章 §2）。
- 核心话术："**宁可重复，不可丢失**"——用户感知靠轮询状态，正确性靠对账兜底。

**问题 4：用户显示"下单成功"，但查订单列表时查不到，怎么解释？**
- 答案方向：结果查询走**秒杀结果缓存**（Redis，TTL 管理生命周期）而非直接查订单表；订单落库是异步的，查询接口需要**先查结果缓存、未完成时返回"处理中"**，避免用户看到"成功但无订单"的矛盾。

**问题 5：异步落库的"成功"到底以什么为准？**
- 答案方向：以**DB 订单记录落库成功**为准；Redis 扣减只是"预占成功"。要明确讲出**预占（Redis）≠ 成交（DB）**，中间的差值就是"超卖未成交"的库存，最终要回补。

**问题 6：用户重复点击/重复提交怎么办？**
- 答案方向：幂等——Redis INCR 原子检查用户参与次数（第6章 §6）+ 唯一索引（订单号/用户+活动）兜底 + 前端按钮置灰 + 分布式锁。

### 2. Redis Lua 原子扣减

**问题 7：Lua 脚本的原子性由什么保证？**
- 答案方向：Redis 单线程执行 Lua，脚本执行期间不被其他命令打断（第6章 §5）。可以顺带讲"为什么不用 MULTI/EXEC 或普通 GET+DECR"（非原子，有并发窗口）。

**问题 8：Redis 返回 null（脚本异常/连接问题）时，如何区分"库存不足"和"系统故障"？**
- 答案方向（知识库 P1-5 修复记录）：**null 一律视为系统故障抛 503"系统繁忙"**，不能误报"库存不足"（400）；库存不足由 Lua 返回 -2 明确标识。**不要让用户把系统错误当成业务失败**。

**问题 9：扣减成功但 Kafka 发送失败，库存已减、订单没发——一致性怎么保证？**
- 答案方向：见问题 3 的三层兜底。补充一点：**不能先发消息再扣库存**（消息发出去了库存没减 → 超卖），顺序必须是"扣库存成功 → 可靠投递"。

**问题 10：Redis 集群/多实例部署，Lua 里的 key 怎么保证落在同一节点？**
- 答案方向（知识库）：**hash tag**（`{activityId}`）保证相关 key 在同一 slot；Cluster 模式配置 `read-from: MASTER` 避免 replica 延迟读到旧库存。

**问题 11：秒杀结束后，Redis 里的库存和 DB 库存怎么对齐？**
- 答案方向：最终以 DB 落库的订单数为准；Redis 预占库存与 DB 实际成交之间的差异由**对账任务**处理（第5章 §2 库存对账）。

### 3. 手动 ACK + Semaphore 背压

**问题 12：Semaphore 信号量耗尽时，消费者线程被阻塞，会发生什么？**
- 答案方向（知识库 Kafka 背压设计）：信号量耗尽 → 阻塞 Kafka listener 线程 → poll 暂停 → Broker 感知消费慢 → 降速。**从根源杜绝虚拟线程堆积引发的连接耗尽**。上限对齐 HikariCP 池大小（30）。

**问题 13：为什么不直接调大信号量？**
- 答案方向：信号量本质是**消费速率闸门**，调大只会让"待处理任务"在内存堆积（OOM 风险），DB 连接池只有 30 个，任务再多也落不了库。**限流上限必须对齐下游瓶颈资源**（第6章 §9 超时：连接池耗尽量化）。

**问题 14：消费失败怎么重试？重试几次？重试完还失败呢？**
- 答案方向：内存分级重试（TransactionException 重试 3 次）→ 超过后 ack 放弃 + **幂等兜底**（DuplicateKey 不会重复入库）→ 死信/告警/定时补偿（第8章 §3：18 级阶梯延迟、状态机 0/1/2、死信隔离）。

**问题 15：手动 ACK 下，重复消费如何防？**
- 答案方向：**唯一索引 + 幂等**（订单号唯一索引，DuplicateKeyException 捕获后视为已处理）；消费前查状态（status=1 直接返回）。

**问题 16：消息乱序怎么办？**
- 答案方向：同一用户/同一订单的消息**顺序消费**（第6章 §11 点赞：ORDERLY 顺序消费 + 乐观锁）；订单状态机保证状态只能按序流转（第3章 §2.1）。

### 4. 三策略引擎（策略模式）

**问题 17：三种策略如何"动态调整"？切换时机是什么？**
- 答案方向：配置中心（Nacos）下发秒杀模式 → 策略工厂按 `secKillMode` 路由（第6章 §5 双模式秒杀）；切换要考虑**存量请求**：已按旧策略扣减的请求不能因切换而回滚。

**问题 18：三种策略操作的是同一份库存还是各自独立？**
- 答案方向：必须**同一份库存源**（Redis 预占库存），只是"落库方式"不同；若各自独立会导致数据源混乱。要讲清楚策略差异在"落库路径"而非"库存本体"。

**问题 19：Redis+Kafka 同步落库"兼容高吞吐与强一致"——同步怎么会高吞吐？**
- 答案方向：吞吐取决于 Kafka 批量落库的吞吐（远高于逐条 DB 写）；"同步"指消费端同步落库而非异步攒批。面试官可能故意挖坑，要解释清楚"同步落库 vs 异步落库"指的是**消费端写 DB 的方式**。

**问题 20：DB 乐观锁直扣的性能上限？为什么只用于低并发？**
- 答案方向：乐观锁冲突重试在低并发下几乎无冲突；高并发下大量 version 冲突 → 重试风暴 → DB 压力大。课程第6章 §11 点赞给的是"MQ 顺序消费 + 乐观锁"，可引用。

### 5. 取消订单回补库存

**问题 21：回补库存的幂等怎么保证？**
- 答案方向：**flowNo/cancelFlowNo 唯一索引 + DuplicateKeyException 兜底**（第4章 §4 取消订单；第3章 §3.5 四步回滚：查流水 → 幂等校验 → 回滚 → 记流水）。

**问题 22：回补失败（Redis 挂了）怎么办？**
- 答案方向（知识库）：**DB 先（@Version CAS）、Redis 后（Lua EXISTS 幂等）**；Redis 回补失败由 **ReconciliationScheduler 每 5 分钟对账补偿**。注意顺序不能反：先回补 Redis 再写 DB，DB 失败会导致库存泄漏。

**问题 23：用户取消订单的同时，另一个用户在抢购，回补的库存何时可见？**
- 答案方向：回补完成即可见（即时恢复）；并发安全靠 Lua 原子回补 + 乐观锁。

### 6. JVM 延迟治理（G1 → ZGC）

**问题 24：压测口径是什么？856ms 和 3ms 分别是什么指标？**
- 答案方向：同口径对比（相同并发/相同数据量）；856ms 是 G1 同步 Evacuation 的 STW 峰值，3ms 是分代 ZGC 的 GC 停顿（Proactive 主动触发）。**要强调口径一致**，否则数据不可信。

**问题 25：STW 从 856ms→3ms，P99 到底改善了百分之多少？为什么？**
- 答案方向（知识库：G1→ZGC 对比压测）：同口径 450 并发，G1 GC 耗时 856ms → ZGC 3ms，P99 降 32%。GC 停顿消除后，尾部延迟不再被 GC 抖动污染。

**问题 26：ZGC 的 3ms 是平均值还是最大值？**
- 答案方向：ZGC 设计目标就是**停顿时间不随堆大小增长**（亚毫秒~毫秒级，分代后更低）；要能区分"平均停顿"与"P99 停顿"，面试官会测你是否真懂。

**问题 27：为什么不用 G1 调参（MaxGCPauseMillis）而直接换 ZGC？**
- 答案方向：G1 的停顿目标受堆大小/并发度限制，同步 Evacuation 阶段仍可能长停顿；ZGC 并发整理 + 染色指针 + 读屏障，停顿与堆大小解耦。

**问题 28：ZGC 的代价（CPU/吞吐）是什么？降级回 G1 的影响？**
- 答案方向：ZGC 并发阶段消耗额外 CPU 与内存（染色指针、额外堆开销），吞吐略降；降级预案就是"关闭 VT + 切 G1 回退 JDK17/21"——**高吞吐低延迟取舍**。

### 7. SkyWalking 瓶颈定位

**问题 29：控制变量测试怎么做的？怎么证明是"Kafka 同步阻塞 + Redis 跨 VM 网络"？**
- 答案方向：链路追踪定位最慢调用（SW 最长 3342ms）→ 逐项排除（本地化 Redis 测网络、改异步测 Kafka 阻塞）→ 单一变量验证。

**问题 30：异步化之后，Max RTT 从 3342ms 降到 379ms，为什么还有 379ms？**
- 答案方向：剩余延迟来自 Kafka 批处理/网络抖动等，属于可接受范围；**要讲清楚 P99 降 67%（264ms→92ms）是主指标**，Max RTT 是长尾参考。

**问题 31：异步化后如何保证原来的业务语义（如扣减后立即查询可见）？**
- 答案方向：异步只影响**非关键路径**（落库/通知），关键路径（扣减判定）保持同步；依赖最终一致 + 对账。

### 8. 降级预案（回退 JDK17/21）

**问题 32：运行时怎么切换回平台线程和 G1？需要重启吗？**
- 答案方向：若靠启动参数（`-XX:+UseZGC`、虚拟线程开关），切换需要**滚动重启**；降级预案的意义是"紧急回退手段"，配合网关摘流量 → 分批重启 → 恢复。

**问题 33：虚拟线程切回平台线程，吞吐会掉多少？有实测吗？**
- 答案方向（知识库 vt-vs-platform 压测）：有对比数据（见 `performance/01-vt-vs-platform.md`）；IO 密集型场景 VT 优势明显，切回平台线程吞吐下降是**预期内的降级代价**，换取兼容性/稳定性。

**问题 34：降级触发条件是什么？谁决策？**
- 答案方向：监控（P99 超阈值/错误率升高/GC 异常）→ 告警 → 人工或规则触发降级；纳入 L0~L4 降级体系（第6章 §10，你的预案属资源端腾挪）。

## 二、短链平台

### 9. KGS 预生成发号器

**问题 35：MongoDB 自增账本分段取号——账本怎么保证自增唯一？并发取号怎么办？**
- 答案方向：Mongo 自增 ID（`findAndModify` 原子递增）保证号段不重；**一次取一段**（如 1000 个），段内号在内存/Redis 分配，DB 压力小。

**问题 36：Redis List 里的号用完了（RPOP 返回空）怎么办？**
- 答案方向：**阈值异步补货**——低于阈值（如 20%）时后台触发补货；**极端耗尽时同步补货兜底**（宁可短暂阻塞取号，也不能发重复码）。

**问题 37：多个发号服务实例同时补货，会不会重复？**
- 答案方向：补货动作加**分布式锁**（Redisson tryLock），只有拿到锁的实例能取新号段（第8章 §2 动态分片"临时大脑"竞争模式）。

**问题 38：Base62 6 位容量≈568 亿怎么算的？短码耗尽后怎么办？**
- 答案方向：62⁶ ≈ 568 亿；耗尽策略：**扩位**（6→7 位，兼容旧码）或**回收复用**（过期短码入库重发）。要能现场算出来。

**问题 39：发号器挂了，短链跳转链路会怎样？**
- 答案方向：发号只在**创建短链**时调用；跳转链路不依赖发号器（只查缓存/DB）——**发号故障只影响新建，不影响存量跳转**，这是双服务架构的价值。

### 10. 二级缓存（Caffeine + Redis）

**问题 40：Caffeine 本地缓存和 Redis 分布式缓存的一致性怎么保证？**
- 答案方向：Caffeine 短 TTL（如 3s）自然过期同步，Redis 长 TTL（24h±10% 随机偏移）——**最终一致，接受短窗口**（第6章 §7；知识库 L1/L2 设计）。

**问题 41：缓存击穿/穿透/雪崩分别怎么防？**
- 答案方向（第4章 §1.1 缓存三板斧）：
  - 击穿：ConcurrentHashMap + CompletableFuture + putIfAbsent，同一 key 只有一个线程回源；
  - 穿透：缓存 NULL_VALUE + 兜底降级数据；
  - 雪崩：TTL 随机偏移。

**问题 42：短码跳转为什么能"缓存命中零 DB 查询"？缓存里存什么？**
- 答案方向：缓存存 **短码 → urlId/目标 URL** 的映射；命中直接重定向。要说明**缓存未命中的回源路径**和**缓存更新的触发方式**（删除重建 vs 事件驱动刷新，第6章 §7 的取舍）。

**问题 43：热门短码（营销活动）和冷门短码在缓存策略上有区别吗？**
- 答案方向：可区分——热点短码预热 + 更长 TTL；冷门短码走 Cache-Aside 懒加载。

### 11. 网关 Base62 格式校验

**问题 44：格式校验能防什么？不能防什么？**
- 答案方向：能防**无效请求打到底层**（格式垃圾流量）；不能防**合法格式的恶意刷量**（脚本批量请求真实短码）——需要叠加**限流 + 防重放 + 风控**（第7章 §3 接口签名）。

**问题 45：校验是网关做还是业务做？为什么放网关？**
- 答案方向：网关做（统一入口、提前拦截、不进后续链路）；代价是网关 CPU 多一次正则/解码，要用**纯内存正则**（微秒级）。

### 12. 软删除 + 归属校验

**问题 46：软删除后短码还能跳转吗？**
- 答案方向：设计决策——**软删除后跳转返回"链接已失效"**（查询时过滤 deleted 标记），而不是直接 404；要讲清软删除 vs 物理删除的取舍（可恢复、保留统计、异步清理）。

**问题 47：归属校验失败（用户访问/删除别人的短链）返回什么？**
- 答案方向：403/404（隐藏资源存在性，防枚举）；归属校验基于 user_id（C 端按 user_id 隔离，对照第7章 §1 多租户差异化设计）。

**问题 48：短码能否被枚举遍历？**
- 答案方向：Base62 短码空间大（568 亿）但**可枚举**；靠限流 + 匿名访问策略 + 统计异常检测。

### 13. 存储选型分离（Mongo 账本 + MySQL 业务表）

**问题 49：Mongo 账本和 MySQL 业务表的数据一致性？短码在两边的对应关系？**
- 答案方向：**短码字符串是解耦键**——发号阶段只写 Mongo 账本（唯一性），业务创建时写 MySQL（归属/统计/过期）；两者通过短码关联。要讲清"先发号后建业务记录，业务失败则号作废/回收"。

**问题 50：为什么不用单库？Mongo 换 MySQL 或反过来行不行？**
- 答案方向：Mongo 自增 ID 天然适配分段发号（高并发取号）；MySQL 适合业务属性查询（索引/事务）；**按数据特征选存储**（第1章 §1 混合存储）。

### 14. gRPC 契约通信

**问题 51：gRPC 调用超时/重试/负载均衡怎么配？发号器不可用时降级？**
- 答案方向：gRPC 配置超时 + 重试策略；发号器不可用时**降级为 DB 直取号段**（保留最终兜底），或熔断等待恢复（第6章 §8）。

**问题 52：为什么选 gRPC 而不是 HTTP/Feign？**
- 答案方向：强类型契约（protobuf）、性能（HTTP/2 多路复用）、代码生成；代价是调试成本与生态差异。**要能对比 gRPC vs REST**。

## 三、跨项目通用深水区（简历必被追问）

### 15. 分布式事务（TCC）

**问题 53：TCC 的空回滚、悬挂、幂等三大难题分别是什么？怎么解决？**
- 答案方向（第4章 §1.3）：tcc_operation 表 + bizKey 唯一索引（幂等）、interruptedFlag 中断标记（防悬挂）、状态判断防空回滚。

**问题 54：为什么不能在 Try 阶段直接扣减？**
- 答案方向：违背 TCC 语义（Try 是预留非消耗）、Cancel 需反向补偿+作废流水、流水变成无效凭证；冻结模式 Cancel 只需恢复冻结。

**问题 55：TCC vs 本地事务（@Transactional）vs 可靠消息，各自适用场景？**
- 答案方向：@Transactional 管单库 ACID；TCC 管跨服务强一致（金融/库存）；可靠消息管最终一致（异步链路）。**选型是面试核心考点**（第3章 §1 Hmily vs Seata-AT 对比）。

### 16. 对账

**问题 56：既然有 TCC/消息补偿，为什么还要对账？**
- 答案方向：分布式"必然"存在不一致（消息丢失/重复/延迟），对账是**最后一道防线**（第5章 §1：长款/短款/金额不一致/状态不一致）。

**问题 57：对账发现差异怎么处理？自动还是人工？**
- 答案方向：差异处理矩阵——部分可自动修复（如库存流水缺失、长库存），部分必须人工（资金类、需查 Bug）（第5章 §2 差异处理策略矩阵）。

### 17. 幂等设计（总原则）

**问题 58：幂等键怎么选？**
- 答案方向：业务唯一标识（订单号/用户+活动/flowNo）；**不用随机数**（无法定位业务）；bizKey 设计要兼顾幂等、回滚定位、线上排查可读性（第4章 §1.3）。

**问题 59：接口层幂等（前端重复提交）怎么做？**
- 答案方向：Redis SETNX + X-Idempotency-Key + TTL（知识库 IdempotencyService）；或唯一索引兜底。
