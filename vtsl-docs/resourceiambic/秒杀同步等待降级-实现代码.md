# REDIS_SYNC 同步等待降级为异步不等待 · 实现代码

> 完整可落地的 `RedisSyncStrategy` 改造代码，配套 `application.yml` 配置与可选管理接口。
> 设计依据见《秒杀同步等待降级为异步设计方案.md》。
>
> **⚠️ 落地修正（对照项目实际）**：
> 1. `vtsl-seckill/pom.xml` **没有 `spring-boot-starter-actuator`** → 无 `MeterRegistry` bean，构造注入会启动失败 → 指标改用 `AtomicLong` 计数器 + 日志，**不依赖 MeterRegistry**；
> 2. **复用现有 `SeckillMode` 枚举**（REDIS_SYNC ↔ REDIS_ASYNC）表达降级状态，不新增 `SendMode`——降级本质就是策略模式切换；
> 3. `@Value` 走**构造注入**（与 `StockService`/`SeckillOrderConsumer` 风格一致），不新建配置类；
> 4. **滑动窗口 + 采样恢复**（评审改进）：环形数组只统计最近 N 次（突发故障即时触发），降级后 5% 请求仍走同步采样感知恢复（快于固定冷却），**无探针 topic**。

## 一、改造后 `RedisSyncStrategy.java`（整体替换，已落盘）

**核心变化**（对照旧版）：
1. 旧版：超时/失败 → 抛异常 → `placeOrder` catch → `refundStock()` 回补 + 503（用户失败）
2. 新版：超时/失败 → **降级为异步重发，立即返回成功**（用户成功），可靠性交给消费端幂等 + 对账
3. **滑动窗口降级判定**：环形数组统计最近 window-size 次发送，平均耗时/超时率超阈值 → 切 REDIS_ASYNC
4. **采样恢复**：降级后 5% 请求仍走同步采样，连续 recover-threshold 次成功 → 恢复 REDIS_SYNC

```java
package com.jolumn.vtslseckill.biz.service.strategy;

import com.jolumn.vtslseckill.model.entity.SeckillActivity;
import com.jolumn.vtslseckill.biz.service.StockService;
import com.jolumn.vtslseckill.model.enums.SeckillMode;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Component;

import java.util.concurrent.ExecutionException;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicReference;

/**
 * Redis lua 原子扣库存 + Kafka get等待结果落库创建订单。
 * 强一致性，但在超高流量时 get 等待会成为瓶颈。
 *
 * <p>自适应降级：复用 {@link SeckillMode} 表达当前实际执行模式——
 * 正常为 REDIS_SYNC（同步等待 broker ack），用环形数组滑动窗口统计最近
 * window-size 次发送的平均耗时与超时率，超过阈值自动降级为 REDIS_ASYNC
 * （异步不等待，用户立即成功）；降级后保留 sample-rate 比例的请求仍走同步
 * 采样，连续 recover-threshold 次成功即恢复 REDIS_SYNC（快于固定冷却），
 * 采样失败不影响用户（异步兜底重发）。</p>
 *
 * <p>降级期间消息可能丢失/重复：丢失由本地消息表补投 + 对账兜底，
 * 重复由消费端 uk_activity_user 唯一索引幂等兜底（SeckillOrderConsumer）。</p>
 */
@Component
public class RedisSyncStrategy implements SeckillStrategy {

    private static final Logger log = LoggerFactory.getLogger(RedisSyncStrategy.class);
    private static final long SEND_TIMEOUT_SECONDS = 3;

    private final StockService stockService;
    private final KafkaTemplate<String, String> kafkaTemplate;

    // ====== 降级配置（yml: seckill.sync-degrade.*，构造注入与 StockService/SeckillOrderConsumer 风格一致） ======
    private final int windowSize;
    private final long maxAvgMs;
    private final double maxTimeoutRate;
    private final double sampleRate;            // 降级后采样同步比例（默认 5%）
    private final int recoverThreshold;         // 连续采样成功恢复阈值（默认 5 次）
    private final long minRecoverDelayMs;       // 降级后最短恢复延迟，防抖（默认 10s）

    // ====== 降级状态（复用 SeckillMode：REDIS_SYNC ↔ REDIS_ASYNC） ======
    /** 当前实际执行模式：正常 REDIS_SYNC（同步等待）/ 降级 REDIS_ASYNC（异步不等待） */
    private final AtomicReference<SeckillMode> effectiveMode = new AtomicReference<>(SeckillMode.REDIS_SYNC);
    private final AtomicInteger recoverStreak = new AtomicInteger();   // 连续采样成功次数
    private volatile long degradedAt;                                 // 降级时间戳（最短恢复延迟起点）

    // ====== 环形数组滑动窗口（记录最近 windowSize 次发送耗时/超时，避免累计统计对突发不敏感） ======
    private final Object windowLock = new Object();
    private final long[] windowElapsedMs;       // 耗时(ms)，与 timeout 数组同下标
    private final boolean[] windowTimeout;      // 是否超时/失败
    private final int windowCapacity;
    private int windowHead;                     // 环形写指针（覆盖最旧样本）
    private int windowFilled;                   // 已填样本数（< capacity 时递增）
    private long windowSum;                     // 窗口内总耗时
    private int windowTimeoutCount;             // 窗口内超时数

    public RedisSyncStrategy(StockService stockService,
                             KafkaTemplate<String, String> kafkaTemplate,
                             @Value("${seckill.sync-degrade.window-size:100}") int windowSize,
                             @Value("${seckill.sync-degrade.max-avg-ms:500}") long maxAvgMs,
                             @Value("${seckill.sync-degrade.max-timeout-rate:0.05}") double maxTimeoutRate,
                             @Value("${seckill.sync-degrade.sample-rate:0.05}") double sampleRate,
                             @Value("${seckill.sync-degrade.recover-threshold:5}") int recoverThreshold,
                             @Value("${seckill.sync-degrade.min-recover-delay-ms:10000}") long minRecoverDelayMs) {
        this.stockService = stockService;
        this.kafkaTemplate = kafkaTemplate;
        this.windowSize = windowSize;
        this.maxAvgMs = maxAvgMs;
        this.maxTimeoutRate = maxTimeoutRate;
        this.sampleRate = sampleRate;
        this.recoverThreshold = recoverThreshold;
        this.minRecoverDelayMs = minRecoverDelayMs;
        this.windowCapacity = windowSize;
        this.windowElapsedMs = new long[windowSize];
        this.windowTimeout = new boolean[windowSize];
    }

    @Override
    public int deductStock(Long activityId, Long userId) {
        return stockService.deduct(activityId, userId);
    }

    @Override
    public void createOrder(SeckillActivity activity, Long userId, String orderNo) {
        String msg = userId + ":" + activity.getId() + ":" + orderNo;
        if (effectiveMode.get() == SeckillMode.REDIS_SYNC) {
            if (trySendSync(msg, orderNo)) return;
            // 超时/失败：先判定是否整体降级，再异步兜底重发（用户成功）
            maybeDegrade();
            sendAsync(msg, orderNo);
        } else {
            // 已降级（REDIS_ASYNC）：5% 采样仍走同步以感知恢复，其余异步不等待
            if (shouldSample()) {
                if (trySendSync(msg, orderNo)) {
                    maybeRecover();
                } else {
                    recoverStreak.set(0);
                    sendAsync(msg, orderNo);   // 采样失败兜底，用户仍成功
                }
            } else {
                sendAsync(msg, orderNo);
            }
        }
    }

    /**
     * 同步发送：等待 broker 确认。成功返回 true；
     * 超时/失败返回 false，并记录到滑动窗口。
     */
    private boolean trySendSync(String msg, String orderNo) {
        long start = System.nanoTime();
        try {
            kafkaTemplate.send("seckill-order", msg).get(SEND_TIMEOUT_SECONDS, TimeUnit.SECONDS);
            recordSample((System.nanoTime() - start) / 1_000_000, false);
            log.info("RedisSync 同步发送 MQ 消息并确认: orderNo={}", orderNo);
            return true;
        } catch (TimeoutException e) {
            recordSample(SEND_TIMEOUT_SECONDS * 1000, true);
            log.warn("RedisSync 同步发送超时: orderNo={}", orderNo);
            return false;
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            recordSample(SEND_TIMEOUT_SECONDS * 1000, true);
            return false;
        } catch (ExecutionException e) {
            recordSample(SEND_TIMEOUT_SECONDS * 1000, true);
            log.warn("RedisSync 同步发送失败: orderNo={}, cause={}",
                    orderNo, e.getCause() == null ? e.getMessage() : e.getCause().getMessage());
            return false;
        }
    }

    /**
     * 异步发送：fire-and-forget，不等待 broker ack。
     * 仅当 send() 本身失败（如 producer 已关闭，Kafka 彻底不可用）才抛异常，
     * 由 placeOrder catch 后 refund + 503（Fail Fast）。
     */
    private void sendAsync(String msg, String orderNo) {
        try {
            kafkaTemplate.send("seckill-order", msg);
            log.info("RedisSync(降级) 异步发送 MQ 消息: orderNo={}", orderNo);
        } catch (Exception e) {
            throw new RuntimeException("RedisSync 异步发送 MQ 失败: " + orderNo, e);
        }
    }

    /**
     * 滑动窗口记录样本（环形数组，覆盖最旧样本）。线程安全。
     */
    private void recordSample(long elapsedMs, boolean timeout) {
        synchronized (windowLock) {
            if (windowFilled == windowCapacity) {
                // 覆盖最旧样本：先扣减其统计
                long oldest = windowElapsedMs[windowHead];
                windowSum -= oldest;
                if (windowTimeout[windowHead]) windowTimeoutCount--;
            } else {
                windowFilled++;
            }
            windowElapsedMs[windowHead] = elapsedMs;
            windowTimeout[windowHead] = timeout;
            windowHead = (windowHead + 1) % windowCapacity;
            windowSum += elapsedMs;
            if (timeout) windowTimeoutCount++;
        }
    }

    /**
     * 降级判定：滑动窗口填满后，平均耗时或超时率超阈值 → 切 REDIS_ASYNC。
     * 窗口只反映最近 N 次，突发故障能即时触发（对比累计统计的迟钝）。
     */
    private void maybeDegrade() {
        if (effectiveMode.get() != SeckillMode.REDIS_SYNC) return;
        synchronized (windowLock) {
            if (windowFilled < windowCapacity) return;             // 窗口未满不判定
            long avg = windowSum / windowFilled;
            double rate = windowTimeoutCount * 1.0 / windowFilled;
            if (avg > maxAvgMs || rate > maxTimeoutRate) {
                effectiveMode.set(SeckillMode.REDIS_ASYNC);
                degradedAt = System.currentTimeMillis();
                recoverStreak.set(0);
                log.warn("REDIS_SYNC 降级为 REDIS_ASYNC: avg={}ms, timeoutRate={}%, window={}",
                        avg, String.format("%.2f", rate * 100), windowFilled);
            }
        }
    }

    /**
     * 采样恢复：降级后连续 recover-threshold 次同步采样成功 → 恢复 REDIS_SYNC。
     * 受 min-recover-delay-ms 防抖约束（避免 Kafka 瞬时抖动导致刚降级又恢复）。
     */
    private void maybeRecover() {
        if (System.currentTimeMillis() - degradedAt < minRecoverDelayMs) return;
        if (recoverStreak.incrementAndGet() >= recoverThreshold) {
            effectiveMode.set(SeckillMode.REDIS_SYNC);
            resetWindow();
            recoverStreak.set(0);
            log.info("REDIS_ASYNC 采样连续 {} 次成功，恢复 REDIS_SYNC", recoverThreshold);
        }
    }

    /** 降级期间：按 sample-rate 概率决定本次请求是否走同步采样 */
    private boolean shouldSample() {
        return ThreadLocalRandom.current().nextDouble() < sampleRate;
    }

    private void resetWindow() {
        synchronized (windowLock) {
            windowHead = 0;
            windowFilled = 0;
            windowSum = 0;
            windowTimeoutCount = 0;
        }
    }

    @Override
    public void refundStock(Long activityId, Long userId) {
        stockService.refund(activityId, userId);
    }

    /** 供监控/管理接口查看当前执行模式 */
    public SeckillMode currentMode() {
        return effectiveMode.get();
    }
}
```

## 二、`application.yml` 新增配置段

在现有 `seckill:` 配置段下追加：

```yaml
seckill:
  # ====== REDIS_SYNC 自动降级为异步 ======
  sync-degrade:
    window-size: 100          # 滑动窗口样本数（环形数组，只统计最近 N 次）
    max-avg-ms: 500           # 窗口平均发送耗时阈值(ms)，超过则降级
    max-timeout-rate: 0.05    # 窗口超时率阈值(5%)，超过则降级
    sample-rate: 0.05         # 降级后同步采样比例(5%)，用于感知 Kafka 恢复
    recover-threshold: 5      # 连续采样成功次数，达到即恢复 REDIS_SYNC
    min-recover-delay-ms: 10000  # 降级后最短恢复延迟(防抖，避免瞬时抖动反复横跳)
```

> 所有配置均有默认值，不配也能启动。
> **无探针 topic**：恢复感知由"降级后 5% 请求仍走同步采样"替代（更快、无需独立 topic、不污染业务消息）。

## 三、与 `placeOrder` 的契约（已核验）

`SeckillService.placeOrder`（`SeckillService.java:133-144`）：

```java
if (result == 200) {
    try {
        strategy.createOrder(activity, userId, orderNo);
        return "ok";
    } catch (Exception e) {
        strategy.refundStock(activityId, userId);
        throw new BizException(503, "系统繁忙，请稍后重试");
    }
}
```

**契约匹配**：
- 同步成功 → 不抛 → `"ok"` ✅
- 同步超时/失败 → `trySendSync` 返回 false → `sendAsync` 兜底不抛 → `"ok"`（用户成功，降级语义）✅
- `send()` 本身失败（Kafka 彻底不可用）→ `sendAsync` 抛 RuntimeException → catch → `refundStock()` + 503（Fail Fast）✅

## 四、可选：管理接口（查看当前降级状态）

`SeckillController` 新增：

```java
@RestController
@RequestMapping("/seckill")
public class SeckillController {

    private final RedisSyncStrategy redisSyncStrategy;   // 构造注入

    /** 查看当前执行模式：REDIS_SYNC（同步等待）/ REDIS_ASYNC（已降级异步） */
    @GetMapping("/strategy/send-mode")
    public Result<String> currentSendMode() {
        return Result.ok(redisSyncStrategy.currentMode().name());
    }
}
```

> 无 actuator，暂无 Prometheus 指标暴露；降级/恢复均打 WARN/INFO 日志，`grep "降级为 REDIS_ASYNC|恢复 REDIS_SYNC"` 即可观测。
> 若后续引入 actuator，可在 `maybeDegrade()`/`maybeRecover()` 里补 `MeterRegistry` 计数（需先加 `spring-boot-starter-actuator` 依赖）。

## 五、评审隐患分析与改进

针对评审提出的 4 条隐患，结论如下：

| # | 隐患 | 判断 | 改进 |
|---|---|---|---|
| 1 | 统计周期无上限，`syncCount` 无限累加 | ✅ **成立，严重** | 改为**环形数组滑动窗口**（`windowElapsedMs[]` + `windowTimeout[]`），只统计最近 window-size(100) 次。累计统计下"健康 10000 次后突发 100 次超时"rate≈1% 检测不到；滑动窗口下窗口内 100 次全是超时 → rate=100% 即时降级 |
| 2 | 降级后感知恢复慢（干等冷却 60s） | ✅ **成立** | 改为**采样恢复**：降级后 5% 请求仍走同步 `trySendSync`，连续 5 次成功即恢复 REDIS_SYNC。Kafka 10s 恢复 → 平均 20 个请求内（约秒级）感知，无需等冷却。采样失败不伤用户（`sendAsync` 兜底） |
| 3 | 探针消息被业务消费者消费 | ⚠️ **已规避** | 恢复机制改为采样后**不再需要探针 topic**，该问题彻底消失（旧方案用独立 `seckill-order-probe` topic 已规避，但探针已删除） |
| 4 | 同步超时重发导致重复消息 | ⚠️ **已兜底** | 消费端 `uk_activity_user` 唯一索引 + `DuplicateKeyException` 幂等 ack（`SeckillOrderConsumer:95-97`）。**DB 唯一索引比 Redis orderNo 去重更强**（持久化、无 TTL 窗口），不建议再加 Redis 去重 |

## 六、行为变化对照（面试应答口径）

| 场景 | 旧版行为 | 新版行为 |
|---|---|---|
| 同步发送成功 | 返回成功 | 返回成功（不变） |
| 同步发送超时（Kafka 慢） | refund + 503，**用户失败** | **异步重发，用户成功**；滑动窗口记录超时 |
| 窗口超时率 > 5% 或平均耗时 > 500ms | 持续 refund + 503（雪崩） | 自动切 REDIS_ASYNC，全部异步不等待（吞吐保持） |
| Kafka 恢复（降级中） | — | 5% 请求仍走同步采样，连续 5 次成功 → 恢复 REDIS_SYNC（快于固定冷却） |
| Kafka 彻底不可用 | refund + 503 | `send()` 本身失败 → 仍 refund + 503（Fail Fast） |
| 重复消息（超时重发） | 靠消费端唯一索引幂等 | 同样靠 `uk_activity_user` 唯一索引幂等 ✅ |

**面试话术**：
> "同步模式下 `send().get(3s)` 在 Kafka 慢时会成为瓶颈，超时即回补库存 + 503，流量越大越雪崩。我加了两态执行模式：用环形数组滑动窗口统计最近 100 次同步发送的平均耗时与超时率，超过阈值（500ms / 5%）自动降级为异步不等待，用户立即成功；降级后保留 5% 请求仍走同步采样感知 Kafka 恢复，连续 5 次成功即切回同步（比固定冷却快，且采样失败不伤用户）。降级期间消息可能重复或丢失，重复由消费端唯一索引幂等兜底，丢失由本地消息表补投 + 对账扫描兜底。阈值锚定用户体验 SLA 而非 P99。"
