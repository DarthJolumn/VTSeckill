### 题4：G1 收集器

1. **G1 的核心思想**：把堆划分为大小相等的 **Region**（默认 2048 个，每个 1~32MB），每个 Region 可以动态充当 Eden、Survivor、Old 或 Humongous（大对象区）。不再物理隔离新生代和老年代，而是逻辑划分。

    - **Young GC**：只回收所有 Eden + Survivor Region
    - **Mixed GC**：回收所有年轻代 Region + **部分**老年代 Region（G1 会根据每个 Region 的回收价值和回收耗时来排序，优先回收"性价比最高"的 Region，这就是 G1 的 **Garbage First** 名字的由来）

### 题4 补充：G1 的 Region、Mixed GC、RSet、SATB

**补充打分：从 3/10 提升到 6.5/10**

**说对了的部分**：
- Region 默认 2048 个，大小根据堆大小动态计算 ✅
- 四种角色：Eden、Survivor、Old、Humongous ✅
- Young GC 回收 Eden + Survivor，存活对象复制到新 Survivor ✅
- Mixed GC 的初始标记伴随 Young GC 一起做 ✅
- CSet（Collection Set）的概念 ✅
- RSet 记录"谁引用了我" ✅
- RSet 基于 Card Table 实现 ✅
- Card Table 标脏——引用被修改时标记 ✅
- SATB（Snapshot At The Beginning）提到了 ✅

**需要纠正/补充的部分**：

1. **Mixed GC 触发条件**——不是"堆使用率到 45%"，标准说法是：当老年代占用超过 `InitiatingHeapOccupancyPercent`（默认 45%）时，G1 会启动并发标记周期。但 Mixed GC 的实际触发是在并发标记完成之后，G1 根据每个 Old Region 的**回收价值**（垃圾占比）和**回收耗时**来排序，选出"性价比最高"的 Region 加入 CSet 进行回收。

2. **并发标记阶段**你说"不是很懂"，帮你理清：
    - 并发标记是 G1 最核心的阶段，它和应用程序线程**同时运行**
    - 它从 GC Roots 出发，遍历整个堆，标记所有存活对象
    - 因为是并发的，标记过程中对象引用关系可能发生变化，所以需要 SATB 来保证正确性

3. **SATB 的原理**——你的理解方向对但不够精确：
    - SATB 的意思是：在并发标记**开始的那一刻**，拍一个"快照"，标记那一刻所有存活的对象
    - 具体实现：在并发标记期间，如果某个对象的引用被**删除或修改**（即旧引用即将"消失"），写屏障（Write Barrier）会把这个旧引用记录到 SATB 队列中
    - 标记结束后，G1 会重新扫描 SATB 队列中的引用，确保不会因为并发修改而漏标
    - 简单说：**SATB 解决的是"并发标记期间，正在被标记的对象突然不再被引用了，但它引用的对象可能被漏标"的问题**

4. **Card Table 标脏**——你说"引用被修改了"，更精确地说：当对象的引用字段被写入新值时，写屏障会把该对象所在的 Card（通常是 512 字节一块）标记为"脏"，这样在回收某个 Region 时，只需要扫描 RSet 中记录的脏 Card，而不需要扫描整个堆来找跨 Region 引用。

### 题5：CMS

**打分：2/10**

**说对了的部分**：
- 碎片化严重 ✅
- 碎片化严重到无法分配对象时触发 Full GC ✅
- Full GC 的 STW 时间特别长 ✅

**需要补充的标准答案**：

CMS 的四个阶段：
1. **初始标记（STW）**：标记 GC Roots 直接关联的对象，速度快
2. **并发标记**：和应用程序并发执行，从 GC Roots 出发遍历整个对象图
3. **重新标记（STW）**：修正并发标记期间因程序继续运行导致的标记变动（用三色标记法 + 增量更新）
4. **并发清除**：和应用程序并发执行，清除死亡对象

CMS 最大的缺点：
- **内存碎片**：基于标记清除算法，不做压缩，碎片积累到一定程度触发 Full GC（退化为 Serial Old，STW 时间极长）
- **CPU 敏感**：并发阶段占用 CPU 资源
- **浮动垃圾**：并发清除阶段新产生的垃圾无法在本次 GC 中清理

JDK 9 标记废弃的原因：G1 在几乎所有场景下都优于 CMS——无碎片、可预测停顿、整体吞吐量更高。

### 题6：双亲委派

**打分：4/10**

**说对了的部分**：
- 先交给父加载器加载 ✅
- 目的是安全性，防止核心类被篡改 ✅
- `loadClass` 源码流程：先查缓存 → 找 parent → 到 Bootstrap → 加载不了再回退 ✅

**需要纠正/补充的部分**：

1. **"缓存池"不是缓存池**——是 `findLoadedClass()`，检查这个类是否已经被当前类加载器加载过。

2. **为什么要打破双亲委派**——你提到了 JDBC Driver 的例子，方向是对的，我帮你把逻辑链补上：
    - JDBC 的 `DriverManager` 是由 **Bootstrap ClassLoader** 加载的（因为它在 `rt.jar` 里）
    - 但具体的数据库驱动（比如 `com.mysql.cj.jdbc.Driver`）是放在 classpath 下的，Bootstrap ClassLoader **找不到**它
    - 所以 JDK 设计了一个**线程上下文类加载器（Thread Context ClassLoader）**，让父加载器可以"反向"委托子加载器去加载实现类
    - 这就是打破双亲委派的典型场景：**父加载器需要加载子加载器才能看到的类**

3. **怎么打破**——你说"重写 loadClass 方法"，这个对了一半。标准做法有两种：
    - **重写 `loadClass()` 方法**：完全自定义加载逻辑（极端做法）
    - **重写 `findClass()` 方法**：更推荐，只在父加载器找不到时才介入
    - **线程上下文类加载器**：`Thread.setContextClassLoader()`，JDBC、Tomcat 都是这么用的

4. **SPI 机制**——本质就是"接口由父加载器加载，实现由子加载器加载"。JDBC 的 `java.sql.Driver` 接口在 `rt.jar` 里（Bootstrap 加载），但具体实现（MySQL Driver）在 classpath 下（AppClassLoader 加载）。JDK 通过 `ServiceLoader` + 线程上下文类加载器来实现这个机制。

### 题7：诊断工具 + CPU 100% 排查

**打分：2.5/10**

**说对了的部分**：
- `jps -l` 查看运行中的 Java 进程和 PID ✅
- `jstat -gc` 查看 GC 情况 ✅
- `jstack` 和虚拟机栈有关 ✅

**需要补充的标准答案**：

四个工具：
- **jps**：列出当前系统中所有 Java 进程及其 PID
- **jstat**：监控 GC 状态（`-gcutil` 看各代使用率和 GC 耗时百分比）
- **jmap**：导出堆内存快照（`jmap -dump:format=b,file=heap.hprof <pid>`），也可以用 `-heap` 查看堆的概要信息
- **jstack**：导出线程栈快照，查看每个线程当前在执行什么代码、是否死锁

**CPU 100% 排查思路**（标准六步）：
1. `top` 命令找到 CPU 占用最高的 Java 进程 PID
2. `top -Hp <pid>` 找到该进程下 CPU 占用最高的线程 TID
3. 将 TID 转换为十六进制：`printf "%x\n" <tid>`
4. `jstack <pid> | grep <十六进制tid> -A 30` 查看该线程的栈帧，定位到具体代码行
5. 常见原因：死循环、频繁 GC（`jstat -gcutil` 确认）、正则回溯、锁竞争
6. 如果是频繁 GC 导致的，用 `jmap -dump` 导出堆快照，用 MAT 分析大对象和内存泄漏
