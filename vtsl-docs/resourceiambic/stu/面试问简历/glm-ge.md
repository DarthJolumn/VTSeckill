### 一、 项目深挖：基于分代 ZGC 和虚拟线程的秒杀系统
这是你的核心亮点项目，面试官会花大量时间在这里，重点考察“数据真实性”和“细节落地”。
**1. 秒杀扣减策略引擎**
*   抽象策略接口 `SeckillStrategy` 是如何设计的？方法签名大概是什么样的？
*   `REDIS_ASYNC` 中使用 Kafka fire-and-forget 异步落库，如果 Kafka 宕机或者消息丢失，库存扣了但订单没落库怎么办？怎么保证最终一致性？
*   `REDIS_SYNC` 中等待 Broker ACK，如果网络超时，但 Broker 其实已经收到了，重试会导致重复落库吗？怎么解决幂等问题？
*   `DB_QUEUE` 中的乐观锁具体是怎么实现的（版本号机制还是 CAS）？MQ 顺序消费是如何保证的？如果消费失败怎么重试？会不会乱序？
    **2. 滑动窗口自适应机制**
*   环形数组滑动窗口的具体数据结构是怎么实现的？如何保证并发统计的线程安全？
*   “压测 1000 QPS 自动触发切换”，这个 1000 QPS 是怎么测出来的？为什么定在 1000？
*   在从 `REDIS_SYNC` 切换到 `REDIS_ASYNC` 的瞬间，如果有线程还在执行同步等待，怎么处理状态不一致的问题？
    **3. 数据一致性与回补机制**
*   Redis Lua 幂等回补的具体 Lua 脚本怎么写的？如何判断是超时未支付还是取消订单？
*   Semaphore 背压对齐 HikariCP 池大小，具体参数是多少？如果 HikariCP 满了，Semaphore 阻塞，上游请求会怎样？会不会导致 Tomcat 线程耗尽？
*   定时补投机制是怎么实现的？用的定时任务还是延迟队列？补投时如果发现订单已经落库了怎么处理？
    **4. GC与并发治理**
*   你怎么知道 STW 从 856ms 降到了 3ms？用的什么工具看的（GC 日志、JConsole、Arthas）？
*   为什么要在秒杀场景用分代 ZGC？G1 在这个场景下到底差在哪里？
*   引入虚拟线程重构 IO 密集型链路，具体是重构了哪段代码？是在 Controller 层还是 RPC 调用层？
*   “600 并发下 TPS 提升 7.6%”，虚拟线程号称能成倍提升，为什么这里只提升了 7.6%？是不是瓶颈根本不在线程数上？
    **5. 瓶颈精准定位**
*   SkyWalking 和 JMeter 具体是怎么配合使用的？怎么定位到 `send.get()` 是根因的？
*   `pending` 标记回调确认中，`SET pending TTL` 兜底，如果补投时发现这个 pending 还在，但 Kafka 其实已经消费成功了，怎么防止重复消费？
*   P99 从 264ms 降至 92ms，这 92ms 主要花在哪里了？（Redis 网络 IO？Kafka 发送？还是业务逻辑？）
