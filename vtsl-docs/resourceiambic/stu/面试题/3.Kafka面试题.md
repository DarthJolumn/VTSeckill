### 第1集：Kafka Producer 的消息发送流程

**💡 核心回答：**

Kafka Producer 的消息发送经过以下完整链路：拦截器（Interceptor）→ 序列化器（Serializer）→ 分区器（Partitioner）→ RecordAccumulator（消息累积器）→ Sender 线程 → Broker。

消息首先经过 ProducerInterceptor 链进行预处理（如添加元数据、过滤消息），然后由 Serializer 将 Key/Value 对象序列化为字节数组。Partitioner 根据 Key 决定消息发往哪个 Partition。随后消息被送入 RecordAccumulator 按批次（RecordBatch）缓存，当批次满（batch.size）或等待时间到达（linger.ms）时，Sender 线程将批次按 Broker 分组，通过 NetworkClient 以 Request 形式发送。

**📦 实际例子：**

悦茶奶茶平台的订单服务每秒产生数千条订单事件。Producer 的拦截器在消息头中注入 traceId 用于全链路追踪；序列化器将 OrderEvent 对象序列化为 Protobuf 字节流；分区器以 storeId 为 Key 保证同一门店的订单进入同一分区，确保门店维度的顺序性。RecordAccumulator 将消息攒到 16KB 批次后再发送，配合 linger.ms=5ms 显著提升吞吐。

**🔍 源码解析：**

核心入口类 `KafkaProducer`（`org.apache.kafka.clients.producer.KafkaProducer`）：

```java
// KafkaProducer.doSend() 核心流程
private Future<RecordMetadata> doSend(ProducerRecord<K, V> record, Callback callback) {
    // 1. 拦截器：onSend 链式调用
    ProducerRecord<K, V> interceptedRecord = interceptor.onSend(record);
    
    // 2. 序列化
    byte[] serializedKey = serializer.serialize(record.topic(), record.key());
    byte[] serializedValue = serializer.serialize(record.topic(), record.value());
    
    // 3. 获取分区
    int partition = partition(record, serializedKey, serializedValue, cluster);
    
    // 4. 确保 Topic 元数据已获取
    TopicPartition tp = new TopicPartition(record.topic(), partition);
    ResultedPartition rp = waiter.awaitMetadataUpdate(tp);
    
    // 5. 追加到 RecordAccumulator
    RecordAccumulator.RecordAppendResult result = accumulator.append(
        tp, timestamp, serializedKey, serializedValue, headers,
        interceptor, remainingWaitMs, time);
    
    // 6. 如果批次满了或创建了新的批次，唤醒 Sender 线程
    if (result.batchIsFull || result.newBatchCreated) {
        sender.wakeup();
    }
}
```

`RecordAccumulator`（`org.apache.kafka.clients.producer.internals.RecordAccumulator`）核心结构：

```java
// 按 TopicPartition 维护 Deque<ProducerBatch>
private final ConcurrentMap<TopicPartition, Deque<ProducerBatch>> batches;

public RecordAppendResult append(TopicPartition tp, long timestamp, 
        byte[] key, byte[] value, Header[] headers, 
        int maxTimeToBlock) throws InterruptedException {
    // 获取或创建新的 ProducerBatch
    Deque<ProducerBatch> deque = batches.get(tp);
    ProducerBatch last = deque.peekLast();
    if (last != null) {
        FutureRecordMetadata future = last.tryAppend(timestamp, key, value, headers, callback, time);
        if (future != null) {
            // 批次还有空间，直接追加
            return new RecordAppendResult(future, deque, false, false);
        }
    }
    // 批次满了，分配新的 MemorySegment
    ByteBuffer buffer = bufferPool.allocate(size, maxTimeToBlock);
    ProducerBatch batch = new ProducerBatch(tp, recordsBuilder, buffer);
    // ...
}
```

`Sender` 线程（`org.apache.kafka.clients.producer.internals.Sender`）核心循环：

```java
// Sender.run() 主循环
void run(long now) {
    // 1. 按 Broker 分组，找出每个 Broker 需要发送的 batches
    List<ClientRequest> requests = createProduceRequests(now);
    // 2. 通过 Selector 发送网络请求
    for (ClientRequest request : requests)
        client.send(request, now);
    // 3. poll 网络事件
    client.poll(pollTimeout, now);
}
```

**⚠️ 常见坑/加分回答：**

- `linger.ms=0` 时 Producer 立即发送，吞吐极低；悦茶生产环境设为 5~20ms 平衡延迟与吞吐。
- `buffer.memory` 默认 32MB，高峰期可能被耗尽导致 `send()` 阻塞甚至抛 `TimeoutException`。
- 拦截器中不要做重逻辑（如网络调用），否则会阻塞 Producer 主线程。
- 加分回答：`ProducerBatch` 内部使用 `MemoryRecordsBuilder` 写入消息，支持消息压缩后整体存储，这就是"Producer 端压缩"的源码实现。

### 第2集：分区策略——Key 哈希分区、轮询分区、自定义分区

**💡 核心回答：**

Kafka 提供三种分区策略：

1. **指定分区**：Producer 直接指定 partition 号，消息进入该 Partition。
2. **Key 哈希分区**：消息带 Key 时，对 Key 的字节数组做 MurmurHash2 哈希，再对分区数取模：`partition = Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions`。
3. **轮询分区**：消息不带 Key 时，Kafka 客户端使用 Sticky Partitioner（Kafka 2.4+），在批次未满时粘滞到同一分区，批次满后切换到下一个分区，既保证一定顺序性又分散负载。

要保证顺序性，必须使用相同的 Key 发送到同一 Partition，且 Consumer 端单线程消费该 Partition。

**📦 实际例子：**

悦茶平台的订单服务以 `storeId` 为 Key 发送订单事件，确保同一门店的订单按顺序进入同一分区，下游门店实时看板消费时能按时间顺序看到订单。而用户行为日志不带 Key，使用轮询策略均匀分散到所有分区。

悦茶还实现了自定义分区器，将 VIP 客户（消费金额 > 500 元/月）路由到独立的高优先级 Topic 分区，保证 VIP 相关的事件被优先处理。

**🔍 源码解析：**

默认分区器 `DefaultPartitioner`（`org.apache.kafka.clients.producer.internals.DefaultPartitioner`）：

```java
// DefaultPartitioner.partition()
public int partition(String topic, Object key, byte[] keyBytes,
                     Object value, byte[] valueBytes, Cluster cluster) {
    List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
    int numPartitions = partitions.size();
    
    if (keyBytes == null) {
        // 无 Key：使用 Sticky Partitioner（Kafka 2.4+）
        return stickyPartitioner.partition(topic, cluster);
    } else {
        // 有 Key：MurmurHash2 哈希取模
        return Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
    }
}
```

MurmurHash2 实现（`org.apache.kafka.common.utils.Utils`）：

```java
public static int murmur2(byte[] data) {
    int length = data.length;
    int seed = 0x9747b28c;
    // 'm' and 'r' are mixing constants generated offline
    final int m = 0x5bd1e995;
    final int r = 24;
    int h = seed ^ length;
    // ... 标准 MurmurHash2 实现
    return h;
}
```

自定义分区器实现 `org.apache.kafka.clients.producer.Partitioner` 接口：

```java
public class VipPriorityPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
        int numPartitions = partitions.size();
        
        // 解析 Key 格式: "storeId:userLevel"
        String keyStr = new String(keyBytes);
        String userLevel = keyStr.split(":")[1];
        
        // VIP 用户路由到前 1/3 的分区
        if ("VIP".equals(userLevel)) {
            return Utils.toPositive(Utils.murmur2(keyBytes)) % (numPartitions / 3);
        }
        // 普通用户路由到剩余分区
        return (numPartitions / 3) + 
               Utils.toPositive(Utils.murmur2(keyBytes)) % (numPartitions * 2 / 3);
    }
}
```

**⚠️ 常见坑/加分回答：**

- 增加分区数后，Key 哈希取模结果变化，消息会分散到不同 Partition，**破坏 Key 顺序性**。悦茶在扩容分区时需要同步评估对下游顺序消费的影响。
- Sticky Partitioner（KIP-480）解决了旧版轮询策略每次都切换分区导致小批量频繁发送的问题，大幅提升小消息场景的吞吐。
- 加分回答：Key 为 null 时如果用自定义 Partitioner 需要自行处理 Sticky 逻辑，否则消息全部路由到 partition 0。

### 第3集：生产者的高可用保障——acks 与 ISR 机制

**💡 核心回答：**

`acks` 参数控制 Producer 发送消息后需要等待多少副本确认：

- **acks=0**：Producer 不等任何确认，发完即忘（fire-and-forget），吞吐最高但可能丢消息。
- **acks=1**：只需 Leader 副本写入成功即返回，Leader 挂掉且未同步到 Follower 时会丢消息。
- **acks=all（-1）**：需要 ISR 中所有副本都写入成功才返回，安全性最高但延迟最大。

**ISR（In-Sync Replicas）** 是与 Leader 保持同步的副本集合。`min.insync.replicas` 定义 ISR 中最少必须有几个副本，当 ISR 中副本数低于该值时，`acks=all` 的写入会抛出 `NotEnoughReplicasException`。

典型配置：`acks=all` + `min.insync.replicas=2` + `replication.factor=3`，允许 1 个副本挂掉，写入至少需要 2 个副本确认。

**📦 实际例子：**

悦茶平台的订单事件（支付、退款等涉及资金的场景）配置 `acks=all`、`min.insync.replicas=2`，确保支付成功事件不丢失。而门店的设备心跳日志配置 `acks=1`，允许少量丢失以换取低延迟。

**🔍 源码解析：**

ISR 管理在 `Partition` 类中（`kafka.cluster.Partition`，Scala 实现）：

```scala
// kafka.cluster.Partition
class Partition(val topicPartition: TopicPartition, ...) {
  // ISR 状态存储在 volatile 变量中，保证读一致性
  @volatile private var isrState: IsrState = IsrState.CommittedIsr(...)
  
  def maybeExpandIsr(replicaId: Int): Unit = {
    val currentIsr = isrState.isr
    val replica = getReplica(replicaId).orNull
    // 判断 Follower 是否在 LAG 阈值内（replica.lag.time.max.ms）
    if (replica != null && !currentIsr.contains(replica) && 
        isFollowerAtLogEndOffset(replica)) {
      // 扩展 ISR
      val newIsr = currentIsr + replica
      updateIsr(newIsr)
    }
  }
  
  def maybeShrinkIsr(): Unit = {
    val currentIsr = isrState.isr
    // 检查每个 Follower 的 LEO 是否落后 Leader 超过 replica.lag.time.max.ms
    val newIsr = currentIsr.filter(replica => !isFollowerOutOfSync(replica))
    if (newIsr.size < currentIsr.size) {
      updateIsr(newIsr)  // 收缩 ISR
    }
  }
}
```

`ReplicaManager` 中处理 Produce 请求时对 acks 的校验：

**⚠️ 常见坑/加分回答：**

- `acks=all` 不等于"绝不丢消息"，如果所有 ISR 副本同时宕机（如机架级故障），仍可能丢数据。需要配合 `unclean.leader.election.enable=false` 防止非 ISR 副本当选 Leader。
- 悦茶遇到过 `min.insync.replicas=3` 但 `replication.factor=3` 的配置，导致任何 1 个副本维护时写入直接失败。正确做法是 `replication.factor` 至少比 `min.insync.replicas` 大 1。
- 加分回答：`NotLeaderOrFollowerException` 通常在 Leader 切换时出现，Producer 应该开启 `retries` 并配合 `retry.backoff.ms` 做退避重试。

### 第4集：幂等生产者与事务消息

**💡 核心回答：**

**幂等生产者（Idempotent Producer）** 通过 PID（Producer ID）+ Sequence Number 去重：

- 每个 Producer 实例在初始化时从 Broker 获取一个全局唯一的 PID（`ProducerId`）。
- 每个 `<PID, Partition>` 维护一个单调递增的 Sequence Number。
- Broker 端在 `<PID, Partition>` 维度缓存最新的 Sequence Number，收到消息时校验：
  - `seq == cachedSeq + 1`：正常消息，接受。
  - `seq <= cachedSeq`：重复消息，丢弃（实现幂等）。
  - `seq > cachedSeq + 1`：序列号不连续，返回 `OutOfOrderSequenceException`。

幂等生产者保证单分区、单会话内的消息不重复，但**不能跨分区保证 Exactly-Once**。

**事务消息（Transactional Producer）** 在幂等基础上增加了跨分区原子性：

- Producer 通过 `initTransactions()` 向 TransactionCoordinator 注册，获取 PID 和 ProducerEpoch。
- `beginTransaction()` 开启事务。
- `send()` 发送消息时，Broker 将消息标记为 uncommitted 状态。
- `commitTransaction()` 提交事务，Broker 将消息状态改为 committed。
- Consumer 端设置 `isolation.level=read_committed`，只读取已提交的消息。

**📦 实际例子：**

悦茶平台的支付回调处理：支付网关回调可能重试多次，如果不做幂等，同一笔支付会产生多条订单完成事件。开启 `enable.idempotence=true` 后，Broker 自动去重，下游不会出现重复的订单完成事件。

悦茶的库存扣减场景需要跨分区事务：一条消息扣减门店库存（按 storeId 分区），另一条消息记录流水（按流水号分区）。使用 Kafka 事务保证两条消息要么都成功、要么都失败，Consumer 设置 `isolation.level=read_committed` 只看到完整事务。

**🔍 源码解析：**

幂等写入的 Broker 端校验逻辑（`kafka.cluster.Partition`）：

```scala
// Partition.appendRecordsToFollowerOrLeaderReplica()
// 幂等检查在 ReplicaManager 层面完成
// kafka.server.ReplicaManager
def checkAndMaybeAssignProducerId(producerId: Long, producerEpoch: Short,
                                  seq: Int, topicPartition: TopicPartition): Unit = {
  // 从 ProducerStateManager 获取当前缓存的 last sequence
  val psm = producerStateManager(topicPartition)
  val lastSeq = psm.lastSeq(producerId)
  
  if (seq == lastSeq + 1) {
    // 正常，接受并更新 lastSeq
    psm.updateLastSeq(producerId, seq)
  } else if (seq <= lastSeq) {
    // 重复消息，幂等丢弃
    throw new DuplicateSequenceException()
  } else {
    // 序列号不连续，可能是数据丢失
    throw new OutOfOrderSequenceException()
  }
}
```

事务协调器 `TransactionCoordinator`（`kafka.coordinator.transaction.TransactionCoordinator`）：

```scala
class TransactionCoordinator(...) {
  // 事务状态机: Empty -> Ongoing -> PrepareCommit -> CompleteCommit
  def handleTxnCommit(producerId: Long, producerEpoch: Short,
                      transactionTimeoutMs: Int): Either[Errors, CommitMarker] = {
    // 1. 将事务状态改为 PrepareCommit
    // 2. 向所有涉及的 Partition Leader 发送 WriteTxnMarkers 请求
    // 3. 所有分区标记完成后，将事务状态改为 CompleteCommit
  }
}
```

Producer 端事务 API（`KafkaProducer`）：

```java
public class KafkaProducer {
    public void initTransactions() {
        // 向 TransactionCoordinator 发送 InitProducerIdRequest
        // 获取 PID + ProducerEpoch
    }
    
    public void beginTransaction() {
        // 本地状态标记事务开始
        transactionManager.beginTransaction();
    }
    
    public void commitTransaction() {
        // 1. flush 所有缓存的消息
        // 2. 向 TransactionCoordinator 发送 EndTxnRequest(COMMIT)
        // 3. Coordinator 向所有分区 Leader 写 COMMIT marker
        // 4. 标记本地事务完成
    }
    
    public void abortTransaction() {
        // 类似 commit，但发送 ABORT marker
    }
}
```

**⚠️ 常见坑/加分回答：**

- 幂等生产者只能保证**单分区**幂等，跨分区需要事务。悦茶在升级过程中踩过坑：以为开了幂等就万事大吉，结果跨分区消息还是重复了。
- 事务消息的性能代价：Kafka 事务的延迟开销主要来自 WriteTxnMarkers 的 RPC 调用，悦茶实测单次事务的额外延迟约 10~50ms。
- Consumer 端 `read_committed` 模式下，消费者会被阻塞在事务消息的 Offset 处直到事务提交或超时，要注意 `max.poll.interval.ms` 的设置。
- 加分回答：`ProducerFencedException` 表示 Producer 的 Epoch 已经过期（通常是新 Producer 实例使用了相同的 transactional.id），旧 Producer 应停止发送。

### 第5集：Kafka 的日志存储结构

**💡 核心回答：**

Kafka 的日志存储采用三层设计：

- **Topic**：逻辑概念，一个 Topic 可以有多个 Partition。
- **Partition**：物理分区，每个 Partition 是一个独立的、有序的、不可变的消息序列。每个 Partition 在磁盘上对应一个目录，目录命名格式为 `topicName-partitionIndex`。
- **LogSegment**：每个 Partition 由多个 LogSegment 组成，每个 LogSegment 包含三个文件：
  - `.log`：存储实际消息数据（MessageSet/RecordBatch）
  - `.index`：稀疏偏移量索引，记录 Offset → Position 的映射
  - `.timeindex`：稀疏时间索引，记录 Timestamp → Offset 的映射

LogSegment 默认大小 1GB（`log.segment.bytes`），滚动后生成新文件。文件命名使用起始 Offset（20位数字，左补零），如 `00000000000000368769.log`。

**📦 实际例子：**

悦茶平台的 `order-events` Topic，配置 12 个分区，每个分区对应磁盘上的一个目录：

```
/var/kafka-logs/
├── order-events-0/
│   ├── 00000000000000000000.log     (0~999999 的消息)
│   ├── 00000000000000000000.index
│   ├── 00000000000000000000.timeindex
│   ├── 00000000000001000000.log     (1000000~1999999 的消息)
│   ├── 00000000000001000000.index
│   └── 00000000000001000000.timeindex
├── order-events-1/
│   └── ...
```

悦茶运维每天监控各 Partition 目录的 `.log` 文件大小，用于判断磁盘使用趋势。

**🔍 源码解析：**

`LogManager`（`kafka.log.LogManager`）管理所有日志：

```scala
// LogManager 管理所有 Topic-Partition 的 Log 实例
class LogManager(...) {
  // ConcurrentHashMap[TpAndLogDir, Log]
  private val currentLogs = new Pool[TopicPartition, Log]()
  
  def getLog(topicPartition: TopicPartition): Option[Log] = {
    currentLogs.get(topicPartition)
  }
  
  // 创建或获取 Log
  def getOrCreateLog(tp: TopicPartition, config: TopicConfig): Log = {
    synchronized {
      currentLogs.get(tp) match {
        case Some(log) => log
        case None =>
          val logDir = selectLogDir(tp)
          val dir = new File(logDir, s"${tp.topic}-${tp.partition}")
          val log = Log(dir, config, logDirFailureChannel, time, ...)
          currentLogs.put(tp, log)
          log
      }
    }
  }
}
```

`Log`（`kafka.log.Log`）管理 Partition 的所有 LogSegment：

`LogSegment`（`kafka.log.LogSegment`）封装三个文件：

```scala
class LogSegment(val log: FileRecords,
                 val offsetIndex: LazyIndex[OffsetIndex],
                 val timeIndex: LazyIndex[TimeIndex],
                 val baseOffset: Long, ...) {
  // .log: FileRecords（基于 FileChannel 的消息文件）
  // .index: OffsetIndex（稀疏偏移量索引）
  // .timeindex: TimeIndex（稀疏时间索引）
}
```

**⚠️ 常见坑/加分回答：**

- `.log` 文件不能删除，否则该 Segment 的消息全部丢失且无法恢复（除非有多副本）。
- 悦茶遇到过磁盘满导致 Broker 停止接收消息的问题，解决方案是监控各 Partition 目录的磁盘使用率，设置 80% 告警阈值。
- 加分回答：`LazyIndex` 是 Kafka 的懒加载设计，只有真正需要读写索引时才将文件映射到内存（mmap），减少 Broker 启动时的文件句柄消耗。

### 第6集：稀疏索引的设计原理

**💡 核心回答：**

Kafka 使用**稀疏索引**而非稠密索引，原因是：

1. **空间效率**：每条消息都建索引的话，索引文件大小可能超过消息文件本身（Offset 8字节 + Position 4字节 = 12字节/条，而消息本身可能只有几十字节）。
2. **性能折中**：稀疏索引每写入约 4KB 消息记录一个索引条目，查找时先在稀疏索引中二分定位到近似位置，再顺序扫描 `.log` 文件找到目标消息。这个折中在空间和速度之间取得最佳平衡。

**Offset Index**：记录 Offset → 物理 Position（在 .log 文件中的字节偏移量），用于按 Offset 查找消息。

**Time Index**：记录 Timestamp → Offset 的映射，用于按时间查找消息。查找时先在 TimeIndex 中找到不超过目标时间的最大 Timestamp 对应的 Offset，再在 OffsetIndex 中定位。

**📦 实际例子：**

悦茶的实时分析系统需要按时间回溯消费数据："请给我昨天 10:00 到 12:00 的所有订单数据"。Consumer 调用 `offsetsForTimes()` 接口，Broker 端使用 TimeIndex 快速定位到 10:00 对应的 Offset，避免了逐条扫描整个 Log。

悦茶的日志查询系统中，`.index` 文件约为对应 `.log` 文件的 1/200，极大地节省了磁盘空间。

**🔍 源码解析：**

`OffsetIndex`（`kafka.log.OffsetIndex`）：

```scala
// 每个索引条目: Offset(8字节) -> Position(4字节) = 12字节
// 索引条目稀疏分布，约每 4KB 消息一个条目
class OffsetIndex(file: File, baseOffset: Long, maxIndexSize: Int) 
    extends AbstractIndex(file, baseOffset) {
  
  // 查找 <= targetOffset 的最大索引条目
  def lookup(targetOffset: Long): OffsetPosition = {
    // 二分查找
    val idx = binarySearch(targetOffset)
    if (idx < 0) {
      // 没找到精确匹配，返回前一个条目
      val pos = -idx - 2
      if (pos < 0) OffsetPosition(baseOffset, 0)
      else entry(pos)
    } else {
      entry(idx)
    }
  }
  
  // 追加索引条目
  def append(offset: Long, position: Int): Unit = {
    // 确保 offset 单调递增
    require(offset > lastOffset)
    mmap.putInt(offset - baseOffset)  // 存相对偏移，节省空间
    mmap.putInt(position)
  }
}
```

`TimeIndex`（`kafka.log.TimeIndex`）：

```scala

    extends AbstractIndex(file, baseOffset) {

  // 查找不超过 targetTimestamp 的最大条目

    val idx = binarySearch(targetTimestamp)

```

按时间查找消息的完整流程（`Log.lookUpBoundingOffsets()`）：

```scala

  // 1. 在 TimeIndex 中查找目标时间对应的 Offset
  val segment = segments.lastSegmentBefore(timestamp)
  val offset = segment.timeIndex.lookup(targetTimestamp).offset
  
  // 2. 在 OffsetIndex 中查找该 Offset 的物理位置

```

**⚠️ 常见坑/加分回答：**

- 索引文件损坏（如 Broker 异常宕机）时，Kafka 会在启动时重建索引（从 `.log` 文件重新扫描生成），不会丢消息但启动变慢。
- `log.index.size.max.bytes`（默认 10MB）控制单个索引文件的最大大小。
- 加分回答：稀疏索引的查找复杂度为 O(log N)（二分）+ O(K)（顺序扫描 K 条消息），K 的值取决于稀疏程度，通常在百级别，对性能影响可忽略。悦茶通过压测验证，索引查找平均耗时 < 1ms。

### 第7集：零拷贝（Zero-Copy）技术

**💡 核心回答：**

传统 I/O 读取文件并发送到网络需要 4 次数据拷贝和 4 次上下文切换：

1. 磁盘 → 内核缓冲区（DMA Copy）
2. 内核缓冲区 → 用户空间缓冲区（CPU Copy）
3. 用户空间缓冲区 → Socket 缓冲区（CPU Copy）
4. Socket 缓冲区 → 网卡（DMA Copy）

**零拷贝**使用 `sendfile` 系统调用，将步骤 2 和 3 合并为一次拷贝（内核缓冲区直接到 Socket 缓冲区），甚至在使用 Scatter/Gather DMA 时减少到 0 次 CPU 拷贝：

1. 磁盘 → 内核缓冲区（DMA Copy）
2. 内核缓冲区 → 网卡（DMA Copy，由 DMA 引擎完成）

Kafka 的 Broker 在将消息发送给 Consumer 时大量使用零拷贝：Producer 写入消息后，消息已经通过 PageCache 在内存中了。Consumer 消费时，Broker 调用 `FileChannel.transferTo()` 直接将 PageCache 中的数据发送给 Consumer，无需拷贝到用户空间。

**📦 实际例子：**

悦茶平台的订单数据消费高峰期，每秒有数十万条消息被 Consumer 拉取。如果没有零拷贝，每条消息需要额外的 CPU 拷贝开销；使用零拷贝后，Broker 的 CPU 使用率降低约 30%，网络吞吐量提升约 50%。

悦茶压测对比：关闭零拷贝（`sendfile.zerocopy=false` 模拟）后，Broker 的吞吐量从 600MB/s 降到 200MB/s，降幅达 67%。

**🔍 源码解析：**

Kafka 使用 `FileChannel.transferTo()` 实现零拷贝：

```java

    private final FileChannel channel;
    
    // 将数据写入通道（网络 Socket）

        // 底层调用 FileChannel.transferTo()，即 sendfile 系统调用
        return channel.transferTo(position, count, target);
    }
}
```

`Network send` 层面（`org.apache.kafka.common.network.KafkaChannel`）：

```java

    // 对于 Fetch 响应，send 是 MultiSend
    // 底层使用 FileRecords.writeTo() 实现零拷贝
    this.transportLayer.transferFrom(send);
}

// DefaultTransportLayer.transferFrom()

    // 调用 FileChannel.transferTo() -> sendfile 系统调用
    return send.writeTo(this);

```

Linux 内核层面的 sendfile 实现：

```
// 传统 read + write 路径:
// Disk -> Kernel Buffer -> User Buffer -> Socket Buffer -> NIC
// 4次拷贝（2次CPU拷贝），4次上下文切换

// sendfile 路径:
// Disk -> Kernel Buffer -> Socket Buffer -> NIC
// 2次拷贝（0次CPU拷贝，都是DMA），2次上下文切换

// sendfile + Scatter/Gather DMA:
// Disk -> Kernel Buffer -> NIC
// 2次拷贝（0次CPU拷贝），2次上下文切换
```

**⚠️ 常见坑/加分回答：**

- 零拷贝只在消息大小合适时效果最好。如果消息太大（超过 PageCache 大小），可能导致频繁的磁盘 IO。Kafka 通过 `socket.request.max.bytes`（默认 100MB）控制单次请求大小。
- 悦茶遇到过零拷贝在加密传输场景下失效的问题：启用 SSL 后，消息需要先读到用户空间进行加密，无法使用 sendfile。解决方案是对延迟不敏感的 Topic 启用 SSL，实时 Topic 使用 SASL 明文认证。
- 加分回答：Kafka 的零拷贝与 PageCache 配合形成"黄金组合"——Producer 写入的消息先进入 PageCache，Consumer 读取时直接命中 PageCache 并通过零拷贝发送，全程无用户空间拷贝。

### 第8集：日志清理策略——删除 vs 压缩

**💡 核心回答：**

Kafka 提供两种日志清理策略：

**日志删除（Delete）**：默认策略。超过 `log.retention.hours`（默认 168 小时 = 7天）的消息会被删除。实际删除粒度是 LogSegment，Kafka 后台线程 `LogCleaner` 定期检查是否有 Segment 的所有消息都过期，如果则直接删除整个 Segment 文件。

**日志压缩（Compact）**：对于同一 Key 的多条消息，只保留最后一条。适用于需要"最新状态"的场景（如用户资料、库存快照）。压缩后：
- 旧版本的消息被删除
- 每个 Key 至少保留一条消息（即"墓碑消息"之前的最后一条）
- 删除标记（Tombstone，value 为 null）用于标识 Key 已被删除，保留一段时间后才清理

配置方式：`log.cleanup.policy=delete`（默认）、`log.cleanup.policy=compact`、`log.cleanup.policy=delete,compact`（两者结合）。

**📦 实际例子：**

悦茶平台使用两种策略的组合：

- **用户行为日志**（`user-behavior-log`）：使用 `delete` 策略，保留 3 天，因为行为日志只需要短期分析。
- **门店配置数据**（`store-config`）：使用 `compact` 策略，Key 为 storeId，Consumer 消费后始终拿到门店的最新配置。
- **用户积分余额**（`user-points`）：使用 `delete,compact` 组合策略，7天内的数据完整保留，超过 7 天的只保留每个用户的最新余额。

**🔍 源码解析：**

日志清理的核心类 `LogCleaner`（`kafka.log.LogCleaner`）：

```scala

    new CleanerThread(i, ...)

  // 2. 扫描 .log 文件，构建 Key -> LastPosition 的映射表（CleanedPoint）
  // 3. 从后往前扫描，只保留每个 Key 最后一次出现的消息
  // 4. 写入新的 Segment 文件，替换旧文件
```


**⚠️ 常见坑/加分回答：**

- 日志压缩需要开启 `LogCleaner` 线程，默认只有 1 个线程。悦茶在门店配置数据量增大后，将 `log.cleaner.threads` 调到 4，清理速度提升 4 倍。
- 压缩后的 Topic 中，Consumer 不能依赖 Offset 顺序性（同一 Key 的旧消息被删除后，Offset 不再连续）。
- 墓碑消息（Tombstone）的保留时间由 `log.cleaner.delete.retention.ms` 控制（默认 24 小时），要给 Consumer 足够时间消费到删除标记。
- 加分回答：Compact 后的 Log 有一个"cleaner point"概念，标记已经清理到的位置。Consumer 的 Offset 如果指向已被清理删除的消息，会自动回退到最近的存活消息。

### 第9集：Consumer Group 的消费模型与分区分配策略

**💡 核心回答：**

Kafka Consumer Group 中，同一个 Group 内的 Consumer 共同消费 Topic 的所有 Partition，每个 Partition 只能被 Group 内的一个 Consumer 消费。

三种分区分配策略：

1. **Range（默认）**：按 Topic 维度，将每个 Topic 的 Partition 按序号范围分配给 Consumer。如果一个 Consumer 订阅了多个 Topic，可能导致部分 Consumer 分配不均。
2. **RoundRobin**：将所有 Topic 的所有 Partition 按轮询方式分配给 Consumer，保证全局均匀。但要求所有 Consumer 订阅相同的 Topic 集合。
3. **Sticky（Kafka 2.4+ 默认）**：在均匀分配的基础上，尽量减少 Rebalance 时的分区迁移。Consumer 挂掉后，只有其原来的分区会被重新分配，其他 Consumer 的分区不变。

**📦 实际例子：**

悦茶平台的订单分析系统有 3 个 Consumer 实例消费 `order-events` Topic（12 个分区）：

- Range 策略：Consumer-A 分配 Partition 0~3，Consumer-B 分配 4~7，Consumer-C 分配 8~11。如果 Topic 有 2 个，Range 可能导致分配不均。
- Sticky 策略：悦茶选择 Sticky，因为当某个 Consumer 实例重启时（如部署更新），只有该实例原来负责的分区会被重新分配，其他实例的消费不中断，减少了实时分析的波动。

**🔍 源码解析：**

```java
public class RangeAssignor extends AbstractPartitionAssignor {
    public Map<String, Assignment> assign(
            ClusterMetadata metadata, 
            Map<String, Subscription> subscriptions) {
        
        // 按 Topic 维度分配
        Map<String, List<MemberInfo>> topicToMembers = getTopicToMembers(subscriptions);
        
        Map<String, Assignment> assignment = new HashMap<>();
        for (Map.Entry<String, List<MemberInfo>> entry : topicToMembers.entrySet()) {
            String topic = entry.getKey();
            List<PartitionInfo> partitions = metadata.partitionsForTopic(topic);
            List<String> members = entry.getValue();
            
            // 按范围分配: 每个 Consumer 分配 numPartitions/numMembers 个分区
            int numPartitionsPerMember = partitions.size() / members.size();
            int extra = partitions.size() % members.size();
            int start = 0;
            for (int i = 0; i < members.size(); i++) {
                int length = numPartitionsPerMember + (i < extra ? 1 : 0);
                assignment.get(members.get(i)).addPartitions(
                    partitions.subList(start, start + length));
                start += length;
            }
        }
        return assignment;
    }
}
```

```java
            ClusterMetadata metadata, 
            Map<String, Subscription> subscriptions) {

            recoverPreviousAssignment(subscriptions);
```

**⚠️ 常见坑/加分回答：**

- Range 策略在订阅多个 Topic 时可能导致分配不均：悦茶有 Consumer 同时订阅 `order-events` 和 `payment-events`，Range 下某个 Consumer 可能在两个 Topic 都被分配到更多分区，导致负载不均。
- Sticky 策略要求 Consumer 在 Heartbeat 请求中携带上一次的 Assignment 信息（`userData`），如果新旧版本不兼容会导致 Sticky 失效退化为均匀分配。
- 加分回答：Kafka 2.4 引入了 `CooperativeStickyAssignor`，支持增量式 Rebalance，在 Rebalance 期间只有受影响的分区暂停消费，其他分区继续消费，大幅减少消费停顿时间。

### 第10集：Consumer Rebalance 的完整流程

**💡 核心回答：**

Consumer Rebalance 是 Kafka Consumer Group 重新分配分区的过程，触发条件包括：

1. Consumer 加入或离开 Group
2. Consumer 订阅的 Topic 发生变化
3. Topic 的 Partition 数量发生变化

**Rebalance 流程（Consumer Protocol）**：

1. **加入组（JoinGroup）**：Consumer 向 GroupCoordinator 发送 JoinGroupRequest，Coordinator 选举一个 Consumer 为 Leader。
2. **同步（SyncGroup）**：Leader Consumer 根据分配的分区策略计算分区分配方案，发送给 Coordinator。Coordinator 将分配结果分发给所有 Consumer。
3. **心跳维持**：Consumer 定期发送 Heartbeat 请求维持会话。如果超过 `session.timeout.ms`（默认 45 秒）没有心跳，Coordinator 认为该 Consumer 已死亡，触发 Rebalance。
4. **处理超时**：如果 `poll()` 的间隔超过 `max.poll.interval.ms`（默认 5 分钟），Coordinator 认为 Consumer 处理卡死，将其踢出 Group。

**📦 实际例子：**

悦茶平台的实时分析服务在高峰期部署更新时，Consumer 实例会短暂停止心跳。悦茶将 `session.timeout.ms` 设为 30 秒、`heartbeat.interval.ms` 设为 10 秒（建议为 session.timeout 的 1/3），`max.poll.interval.ms` 设为 10 分钟（因为某些复杂聚合任务单次处理可能需要 5 分钟）。这样正常部署更新不会触发 Rebalance。

悦茶还配置了 `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor`，使 Rebalance 时只有受影响的分区暂停消费。

**🔍 源码解析：**

`GroupCoordinator`（`kafka.coordinator.group.GroupCoordinator`）管理消费组状态：

```scala
// GroupCoordinator 管理所有 Consumer Group
class GroupCoordinator(...) {
  // 消费组状态机: Empty -> PreparingRebalance -> CompletingRebalance -> Stable -> Dead
  // GroupMetadata 维护消费组状态和成员信息
  private val groupManager = new GroupMetadataManager(...)
  
  // 处理 JoinGroup 请求
  def handleJoinGroup(groupId: String, memberId: String,
                      protocols: List[JoinGroupProtocol]): JoinGroupResult = {
    val group = groupManager.getGroup(groupId)
    
    if (group.is(Empty)) {
      // 第一个 Consumer 加入，成为 Leader
      group.add(member)
      group.transitionTo(PreparingRebalance)
      // 等待其他成员加入（rebalance.timeout.ms）
    } else if (group.is(Stable)) {
      // 已有稳定组，新成员加入触发 Rebalance
      group.transitionTo(PreparingRebalance)
    }
    
    // 等待所有成员加入后，选举 Leader
    val leaderId = electLeader(group)
    JoinGroupResult(memberId, leaderId, group.protocol, group.generationId)
  }
  
  // 处理 SyncGroup 请求
  def handleSyncGroup(groupId: String, generationId: Int,
                      memberId: String, assignments: Map[String, Array[Byte]]): Array[Byte] = {
    val group = groupManager.getGroup(groupId)
    
    if (memberId == group.leaderId) {
      // Leader 发送完整的分配方案
      group.setAssignment(assignments)
      group.transitionTo(Stable)
    }
    
    // 返回该 Consumer 的分配结果
    group.getAssignment(memberId)
  }
  
  // 处理心跳
  def handleHeartbeat(groupId: String, memberId: String,
                      generationId: Int): Errors = {
    val group = groupManager.getGroup(groupId)
    if (generationId != group.generationId) {
      REBALANCE_IN_PROGRESS  // 通知 Consumer 需要重新加入
    } else {
      group.updateMember(memberId)
      NONE
    }
  }
}
```

Consumer 端心跳线程（`HeartbeatThread`）：

```java
// AbstractCoordinator.HeartbeatThread
class HeartbeatThread extends Thread {
    public void run() {
        try {
            while (!closed) {
                if (heartbeat.sessionTimeoutExpired(now)) {
                    // 超过 session.timeout.ms，标记需要 Rebalance
                    coordinator.markRejoinNeeded();
                }
                if (heartbeat.shouldHeartbeat(now)) {
                    // 发送心跳
                    client.send(new HeartbeatRequest.Builder(...).build());
                    heartbeat.sentHeartbeat(now);
                }
                // 等待下次心跳
                Thread.sleep(heartbeat.timeToNextHeartbeat());
            }
        } catch (Exception e) {

        }
    }
}
```

**⚠️ 常见坑/加分回答：**

- `heartbeat.interval.ms` 应设为 `session.timeout.ms` 的 1/3，确保在超时前至少发送 3 次心跳。
- 悦茶遇到过 `max.poll.interval.ms` 超时导致的 Rebalance 风暴：Consumer 处理一批消息太慢，被 Coordinator 踢出 Group，然后重新加入又触发 Rebalance，其他 Consumer 也被踢出...解决方案是增大 `max.poll.interval.ms` 并减小 `max.poll.records`。
- 加分回答：`REBALANCE_IN_PROGRESS` 错误码在 Consumer 端会触发 `ConsumerRebalanceListener.onPartitionsRevoked()` 回调，悦茶在此回调中提交当前 Offset，避免重复消费。

### 第11集：消费进度（Offset）的管理

**💡 核心回答：**

Kafka Consumer 的消费进度通过 Offset 管理，有两种提交方式：

**自动提交**：`enable.auto.commit=true`（默认），每隔 `auto.commit.interval.ms`（默认 5 秒）自动提交 `poll()` 返回的最大 Offset。简单但有风险——如果在两次提交之间 Consumer 崩溃，会重复消费。

**手动提交**：`enable.auto.commit=false`，由开发者控制提交时机：
- `commitSync()`：同步提交，等待 Broker 确认，确保 Offset 已持久化。
- `commitAsync()`：异步提交，不阻塞业务线程，通过回调处理失败。
- `commitSync(Map<TopicPartition, OffsetAndMetadata>)`：精确提交指定分区的 Offset。

**__consumer_offsets Topic**：Kafka 内部 Topic，存储所有 Consumer Group 的 Offset 信息。
- 默认 50 个 Partition（`offsets.topic.num.partitions`）
- 副本因子 3（`offsets.topic.replication.factor`）
- 清理策略为 compact（只保留最新 Offset）
- Key 格式：`groupId + topic + partition`
- Value：`offset + metadata + commitTimestamp`

**📦 实际例子：**

悦茶的订单处理 Consumer 使用手动提交：先处理消息（扣减库存、生成物流单），处理成功后调用 `commitSync()` 提交 Offset。如果处理过程中 Consumer 崩溃，重启后从上次提交的 Offset 重新消费，配合业务幂等保证不重复。

悦茶在监控中发现 `__consumer_offsets` Topic 的磁盘占用持续增长，排查发现是因为 `group.id` 动态生成（包含时间戳），导致产生了大量废弃的消费组。修复后统一使用固定的 `group.id`，并手动清理了过期组。

**🔍 源码解析：**

**⚠️ 常见坑/加分回答：**

- 自动提交 + 业务处理失败 = 消息丢失。悦茶早期使用自动提交，某次消费逻辑抛异常但 Offset 已自动提交，导致数据不一致。之后全部切换为手动提交。
- `__consumer_offsets` 是内部 Topic，不要手动修改或删除，否则所有消费组的进度丢失。
- 加分回答：`committed offset` 和 `consumed offset` 可能不一致——Consumer 已经消费到 Offset 100，但只提交了 Offset 95。重启后从 95 开始重新消费 5 条消息，需要业务幂等保证。

### 第12集：消费者如何保证消息不丢不重

**💡 核心回答：**

**消息不丢失**：Consumer 端使用手动提交 Offset，在业务处理成功后才提交：

```java
while (true) {
    ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord record : records) {
        processMessage(record);       // 先处理业务
        // 处理成功后手动提交
        consumer.commitSync();        // 同步提交保证可靠性
    }
}
```

**消息不重复**：Kafka 本身不保证消费端幂等，需要业务层配合：

1. **数据库唯一键**：将消息中的业务 ID（如订单号）作为数据库唯一键，重复插入自动报错。
2. **Redis 幂等校验**：处理前检查 `SETNX order:processed:{orderId} 1`，已处理则跳过。
3. **数据库乐观锁**：使用版本号控制，如 `UPDATE orders SET status='PAID' WHERE id=? AND status='UNPAID'`。
4. **状态机**：消息携带状态变更，重复消费同一状态变更时直接忽略。

**完整方案**：手动提交 Offset + 业务幂等 = 不丢不重。

**📦 实际例子：**

悦茶平台的订单支付回调消费：

```java
public void consume() {
    while (true) {
        ConsumerRecords<String, byte[]> records = consumer.poll(Duration.ofMillis(200));
        for (ConsumerRecord<String, byte[]> record : records) {
            PaymentEvent event = deserialize(record.value());
            
            // 1. Redis 幂等检查
            String lockKey = "payment:processed:" + event.getOrderId();
            boolean isNew = redis.set(lockKey, "1", "NX", "EX", 86400);
            if (!isNew) {
                log.info("重复消息，跳过: orderId={}", event.getOrderId());
                continue;  // 幂等跳过
            }
            
            // 2. 处理业务逻辑
            try {
                orderService.handlePayment(event);
            } catch (Exception e) {
                redis.del(lockKey);  // 处理失败，清除幂等标记，允许重试
                throw e;
            }
            
            // 3. 业务成功后提交 Offset
            consumer.commitSync();
        }
    }
}
```

**🔍 源码解析：**

Consumer 端 `KafkaConsumer` 的 `poll()` 内部流程（`org.apache.kafka.clients.consumer.KafkaConsumer`）：

```java
public ConsumerRecords<K, V> poll(final Duration timeout) {
    // 1. 检查是否需要 Rebalance
    coordinator.poll(time.timer(timeout));
    
    // 2. 发送 FetchRequest 拉取消息
    fetcher.sendFetches();
    client.poll(fetchDeadline);
    
    // 3. 解析响应，获取消息
    Map<TopicPartition, List<ConsumerRecord<K, V>>> records = 
        fetcher.fetchedRecords();
    
    // 4. 更新消费位值（position）
    // 注意：position 在 poll 后就更新，但 committed offset 需要手动提交
    for (Map.Entry<TopicPartition, List<ConsumerRecord<K, V>>> entry : records) {
        TopicPartition tp = entry.getKey();
        List<ConsumerRecord<K, V>> partitionRecords = entry.getValue();
        // 更新 position 到最后一条消息的下一个 Offset
        long lastOffset = partitionRecords.get(partitionRecords.size() - 1).offset();
        subscriptions.position(tp, new OffsetAndMetadata(lastOffset + 1));
    }
    
    // 5. 自动提交（如果 enable.auto.commit=true）
    if (autoCommitEnabled) {
        coordinator.commitOffsetsAsync(subscriptions.allConsumed());
    }
    
    return new ConsumerRecords<>(records);
}
```

消费位值的两个关键概念：


`FetchSession` 中的增量拉取优化（`org.apache.kafka.clients.consumer.internals.FetchSessionHandler`）：

**⚠️ 常见坑/加分回答：**

- 先提交 Offset 再处理业务 = 消息丢失的风险。悦茶遇到过 `commitAsync()` 成功后业务处理失败，消息被跳过。必须**先处理再提交**。
- `commitAsync()` 不保证顺序：如果提交 A 失败但提交 B 成功，重试 A 时 B 的提交可能被覆盖。悦茶的关键场景使用 `commitSync()`。
- 加分回答：`ConsumerRebalanceListener` 的 `onPartitionsRevoked()` 回调是提交 Offset 的最后机会——悦茶在此回调中执行最后一次 `commitSync()`，防止分区被重新分配前丢失进度。

### 第13集：Kafka Controller 的选主机制

**💡 核心回答：**

**Kafka Controller** 是整个 Kafka 集群的核心管理者，负责管理 Partition 的 Leader 选举、ISR 管理、Topic 创建/删除等元数据操作。一个集群只有一个 Controller。

**基于 Zookeeper 的选主（传统模式）**：
- 所有 Broker 启动时在 ZK 的 `/controller` 节点上竞争创建临时节点。
- 第一个成功创建的 Broker 成为 Controller。
- Controller 与 ZK 保持 Session，如果 Session 断开（Broker 宕机），临时节点自动删除，触发新一轮选举。
- Controller 注册 ZK Watch 监听 Broker 上下线、Topic 变更等事件。

**KRaft 模式（Kafka 3.0+ 去 ZK）**：
- 引入 Raft 共识算法，Controller Quorum 由多个 Controller 节点组成。
- 通过 Raft 选主选出 Leader Controller，其余为 Follower。
- 元数据存储在内部 `__cluster_metadata` Topic 中，不再依赖 ZK。
- 优势：消除 ZK 单点瓶颈、元数据操作延迟从秒级降到毫秒级、支持更大规模的集群。

**📦 实际例子：**

悦茶平台从 Kafka 2.8 升级到 3.3 后，将架构从 ZK 模式切换到 KRaft 模式。升级后：
- 创建 Topic 的延迟从 2~3 秒降到 50ms 以内。
- 去掉了 3 个 ZK 节点的运维负担。
- Controller 故障切换从 30 秒（ZK Session Timeout）降到 3 秒（Raft 心跳）。

**🔍 源码解析：**

ZK 模式下 Controller 选举（`kafka.controller.KafkaController`）：

```scala
    // 成为 Controller 后注册各种 Watch

  }
  
  private def registerZkCallbacks(): Unit = {
    // 监听 Broker 上下线
    zkClient.registerBrokerChangeHandler(BrokerChangeHandler(this))
    // 监听 Topic 变更
    zkClient.registerTopicChangeHandler(TopicChangeHandler(this))
    // 监听 Partition 状态变化
    zkClient.registerIsrChangeHandler(IsrChangeHandler(this))

    zkClient.registerControllerChangeHandler(ControllerChangeHandler(this))

        .filter(_.brokerId != deadBrokerId)
        .headOption
      partition.leaderId = newLeader.map(_.brokerId).getOrElse(-1)

  }
```

- 加分回答：ZK 模式下 Controller 切换需要 30~60 秒（ZK Session Timeout），KRaft 模式下只需几秒。这是 KRaft 最大的优势之一。

### 第14集：Partition 的 Leader 选举和 ISR 机制

**💡 核心回答：**

每个 Partition 有一个 Leader 副本和零到多个 Follower 副本。所有读写请求都由 Leader 处理，Follower 只从 Leader 拉取数据进行同步。

**Leader 选举条件**：
- 只有 ISR 中的副本才有资格被选为 Leader。
- 当 Leader 宕机时，Controller 从 ISR 中选举第一个存活的副本作为新 Leader。
- 如果 ISR 为空（所有副本都挂了）：
  - `unclean.leader.election.enable=false`（默认）：Partition 不可用，等待 ISR 中副本恢复。
  - `unclean.leader.election.enable=true`：从非 ISR 副本中选择 Leader，可能导致数据丢失（该副本的数据不是最新的）。

**ISR 扩缩容**：
- **扩容**：Follower 的 LEO（Log End Offset）追上 Leader 的 LEO，且延迟在 `replica.lag.time.max.ms`（默认 30 秒）内，加入 ISR。
- **缩容**：Follower 落后 Leader 超过 `replica.lag.time.max.ms`，或 Follower 长时间未发送 Fetch 请求，从 ISR 中移除。

**📦 实际例子：**

悦茶的 `order-events` Topic 配置 `replication.factor=3`、`min.insync.replicas=2`。当某台 Broker 进行磁盘维护时，该 Broker 上的 Follower 副本脱离 ISR（ISR 从 3 缩减为 2），但写入不受影响（ISR 中仍有 2 个副本满足 `min.insync.replicas=2`）。维护完成后 Follower 追上 Leader，重新加入 ISR。

悦茶严格配置 `unclean.leader.election.enable=false`，因为订单数据不能有任何丢失风险。

**🔍 源码解析：**

Leader 选举逻辑（`kafka.controller.KafkaController.electLeaderForPartition`）：

```scala
// KafkaController
def electLeaderForPartition(tp: TopicPartition, 
                            isUnclean: Boolean = false): Option[Int] = {
  val partition = partitionStates(tp)
  val isr = partition.isr
  
  if (isr.nonEmpty) {
    // 从 ISR 中选举第一个存活的副本
    val newLeader = isr.head  // ISR 有序列表，第一个是最佳候选
    partition.leader = newLeader
    
    // 发送 LeaderAndIsr 请求通知相关 Broker
    sendLeaderAndIsrRequest(newLeader, partition)
    Some(newLeader)
  } else if (isUnclean && uncleanLeaderElectionEnabled) {
    // ISR 为空，允许 Unclean 选举
    // 从 OOS（Out-Of-Sync）副本中选择 LEO 最大的
    val candidates = partition.replicas.filter(_.isAlive).sortBy(-_.leo)
    candidates.headOption.map { replica =>
      partition.leader = replica.brokerId
      sendLeaderAndIsrRequest(replica.brokerId, partition)
      replica.brokerId
    }
  } else {
    // ISR 为空且不允许 Unclean，Partition 不可用
    None
  }
}
```

ISR 缩容检查（`kafka.server.ReplicaManager`）：

```scala
// ReplicaManager.maybeShrinkIsr()
def maybeShrinkIsr(): Unit = {
  val lagTimeMax = config.replicaLagTimeMaxMs  // 默认 30000ms
  
  replicaStates.foreach { case (tp, partition) =>
    val leader = partition.leaderReplicaIfLocal
    
    leader.foreach { leaderReplica =>
      // 检查每个 Follower 的 LAG
      val newIsr = partition.isr.filter { replicaId =>
        val replica = partition.getReplica(replicaId).get
        val lag = leaderReplica.logEndOffset - replica.logEndOffset
        val lastFetchTime = replica.lastFetchTimeMs
        
        // 条件1: LEO 差距不超过阈值
        // 条件2: 最后一次 Fetch 时间在 lagTimeMax 内
        val isCaughtUp = lag <= replicaMaxLagBytes && 
                         (time.milliseconds - lastFetchTime) < lagTimeMax
        isCaughtUp
      }
      
      if (newIsr.size < partition.isr.size) {
        // ISR 缩容
        partition.inSyncReplicas = newIsr
        // 写入 ZK 或 Raft 元数据
        updateIsr(tp, newIsr)
      }
    }
  }
}
```

**⚠️ 常见坑/加分回答：**

- `replica.lag.time.max.ms` 设得太小会导致 ISR 频繁抖动（Flapping），设得太大则故障检测延迟。悦茶建议设为 10~30 秒。
- Unclean Leader Election 是数据丢失的最大风险之一。悦茶通过多机房部署 + `replication.factor=3` + `unclean.leader.election.enable=false` 的组合来保障数据不丢失。
- 加分回答：ISR 的顺序很重要——Controller 选举新 Leader 时从 ISR 列表的第一个元素开始选。ISR 列表按 LEO 排序，LEO 最大的排在前面，这意味着选举出的 Leader 数据最新。

### 第15集：数据一致性保障——HW 与 LEO

**💡 核心回答：**

**LEO（Log End Offset）**：每个副本（Leader 和 Follower）都有一个 LEO，表示该副本最后一条消息的下一个 Offset。即该副本已写入的所有消息的总量。

**HW（High Watermark）**：所有 ISR 副本中 LEO 的最小值。Consumer 只能读取 HW 之前的消息，保证消费者读到的数据在所有 ISR 副本中都已存在。

**工作流程**：
1. Producer 发送消息到 Leader 副本，Leader 的 LEO 增加。
2. Follower 通过 Fetch 请求拉取消息，Follower 的 LEO 逐渐增加。
3. HW = min(所有 ISR 副本的 LEO)，随 Follower 追赶 Leader 而增加。
4. Consumer 只能读取 HW 之前的消息，保证一致性。

Leader 切换时，新 Leader 会截断（Truncate）超过旧 HW 的消息（这些消息可能未完全同步到所有 Follower），保证数据一致性。

**📦 实际例子：**

悦茶平台在 Leader 切换后验证数据一致性：某次 Broker 宕机触发 Leader 切换，新 Leader 的 HW 为 999，而旧 Leader 的 LEO 为 1005。新 Leader 将 1000~1004 的 5 条消息截断（这些消息旧 Leader 写入了但 Follower 未完全同步）。Consumer 在切换前后都只读到了 999 之前的消息，不会读到不一致的数据。

**🔍 源码解析：**

HW 的更新逻辑（`kafka.cluster.Partition`）：

```scala
class Partition(...) {
  @volatile var leaderReplica: Option[Replica] = None
  
  // 更新 HW：取所有 ISR 副本 LEO 的最小值
  def maybeIncrementLeaderHW(leaderReplica: Replica, 
                             currentTimeMs: Long): Boolean = {
    val allLeo = for {
      replicaId <- inSyncReplicas  // ISR 中所有副本
      replica <- getReplica(replicaId)
    } yield replica.logEndOffset
    
    val minLeo = allLeo.min
    val newHW = minLeo
    
    if (newHW > leaderReplica.highWatermark) {
      leaderReplica.highWatermark = newHW
      true
    } else {
      false
    }
  }
}
```

Leader 追加消息后更新 HW（`ReplicaManager`）：

```scala
// ReplicaManager.appendRecords()
def appendRecords(records: Map[TopicPartition, MemoryRecords]): Map[TopicPartition, PartitionResponse] = {
  // 1. Leader 追加消息，LEO 增加
  val appendResults = localLog.append(records)
  
  // 2. 尝试更新 HW（如果 Follower 已经追上来）
  appendResults.foreach { case (tp, result) =>
    val partition = getPartition(tp)
    partition.maybeIncrementLeaderHW(partition.leaderReplica.get)
  }
  
  // 3. 返回结果
  appendResults.map { case (tp, result) =>
    tp -> PartitionResponse(result.error, 
                            baseOffset = result.baseOffset,
                            logAppendTime = result.timestamp)
  }
}
```

Follower Fetch 请求处理中更新 HW（`KafkaApis.handleFetchRequest`）：

```scala
// KafkaApis.handleFetchRequest()
def handleFetchRequest(request: RequestChannel.Request): Unit = {
  val fetchRequest = request.body[FetchRequest]
  
  // 读取消息，但不能超过 HW
  val data = replicaManager.fetchMessages(
    fetchRequest.maxWait,
    fetchRequest.minBytes,
    fetchRequest.isolationLevel,  // read_uncommitted 或 read_committed
    fetchRequest.partitions
  )
  
  // 在 FetchResponse 中返回 HW，让 Follower 更新自己的 HW
  sendResponse(request, new FetchResponse(data, throttledTime))
}
```

Leader 切换时的截断逻辑（`Replica.fetcher`）：

```scala
// ReplicaFetcherThread 在 Leader 切换后
override def doTruncate(tp: TopicPartition, leader: LogOffsetMetadata): Unit = {
  val localReplica = replicaManager.getReplicaOrException(tp)
  
  // 截断到 Leader 的 HW
  // 丢弃本地 LEO > HW 的所有消息
  localReplica.truncateTo(leader.messageOffset)
  
  // 重新同步
  localReplica.logEndOffset = leader.messageOffset
}
```

**⚠️ 常见坑/加分回答：**

- HW 的更新不是实时的——需要等待所有 ISR 副本的 LEO 都跟上，因此在 `acks=1` 下 Consumer 可能短暂读到 Leader 已写入但 Follower 未同步的数据（因为 HW 在 Follower Fetch 时才更新）。
- 悦茶遇到过 Leader 切换后数据截断导致 Consumer 重复消费的问题：被截断的消息在旧 Leader 恢复后重新同步，Consumer 会再次消费。配合业务幂等解决。
- 加分回答：`read_committed` 模式下，HW 还要考虑事务消息——HW 不能超过最后一个事务的起始 Offset（防止消费者读到未提交事务的中间状态）。

### 第16集：副本同步机制

**💡 核心回答：**

Follower 副本通过定期向 Leader 发送 Fetch 请求来同步数据，流程如下：

1. Follower 的 `ReplicaFetcherThread` 向 Leader 发送 Fetch 请求，携带当前 LEO（即上次同步到的位置）。
2. Leader 返回从 Follower LEO 开始的新消息。
3. Follower 将收到的消息追加到本地日志，更新本地 LEO。
4. Leader 收到 Fetch 请求后更新 Follower 的"最后 Fetch 时间"和 LEO，用于判断是否在 ISR 中。

**关键参数**：
- `replica.fetch.max.bytes`（默认 1MB）：单次 Fetch 最大数据量。
- `replica.fetch.wait.max.ms`（默认 500ms）：Leader 等待新消息的最大时间。
- `replica.lag.time.max.ms`（默认 30 秒）：Follower 超过此时间未跟上 Leader 则从 ISR 移除。

**延迟优化**：Kafka 引入了 Fetch 请求的"延迟响应"机制——Leader 不会立即返回 Fetch 响应，而是等到有新数据或等待超时才返回，减少空轮询。

**📦 实际例子：**

悦茶平台的跨机房复制场景：主集群在北京，备集群在上海。上海集群的 Follower 需要跨 1500 公里从北京 Leader 拉取数据，网络延迟约 30ms。悦茶将 `replica.fetch.max.bytes` 调到 10MB，减少 Fetch 次数，并通过 `replica.fetch.wait.max.ms=100` 让 Leader 尽快返回新数据，将副本同步延迟控制在 1 秒以内。

**🔍 源码解析：**

`ReplicaFetcherThread`（`kafka.server.ReplicaFetcherThread`）核心逻辑：

```scala
class ReplicaFetcherThread(name: String, 
                           sourceBroker: BrokerEndPoint,
                           replicaManager: ReplicaManager) 
    extends AbstractFetcherThread(...) {
  
  override def doWork(): Unit = {
    // 1. 构建 FetchRequest
    val fetchRequest = buildFetchRequest()
    
    // 2. 发送 Fetch 请求到 Leader
    val response = sendRequest(fetchRequest)
    
    // 3. 处理响应，追加消息到本地日志
    response.partitionData.foreach { case (tp, data) =>
      val replica = replicaManager.getReplica(tp).get
      
      // 将消息追加到本地 Log
      val appendInfo = replicaManager.appendToLocalLog(
        tp, data.records, isFromFollower = true)
      
      // 更新本地 LEO
      replica.logEndOffset = appendInfo.lastOffset + 1
    }
  }
  
  private def buildFetchRequest(): FetchRequest = {
    // 收集所有需要 Fetch 的 Partition
    val fetchPartitionData = partitions.keys().map { tp =>
      val replica = replicaManager.getReplica(tp).get
      // 携带当前 LEO 作为 Fetch 起始位置
      tp -> new FetchRequest.PartitionData(
        replica.logEndOffset,  // 从 LEO 位置开始拉取
        0,  // fetchOffset
        replicaManager.config.replicaFetchMaxBytes,
        None  // logStartOffset
      )
    }
    new FetchRequest.Builder(
      -1,  // replicaId（Follower 的 BrokerId）
      replicaManager.config.replicaFetchWaitMaxMs,
      replicaManager.config.replicaFetchMinBytes,
      fetchPartitionData.toMap
    ).build()
  }
}
```

Leader 处理 Follower 的 Fetch 请求（`ReplicaManager.fetchMessages`）：

```scala
// ReplicaManager.fetchMessages()
def fetchMessages(timeout: Long, minBytes: Int,
                  replicaId: Int,
                  fetchInfos: Seq[(TopicPartition, PartitionData)]): Map[TopicPartition, FetchData] = {
  
  // 更新 Follower 的状态（最后 Fetch 时间、LEO）
  if (replicaId >= 0) {
    fetchInfos.foreach { case (tp, data) =>
      val partition = getPartition(tp)
      partition.updateFollowerLogEndOffset(replicaId, data.fetchOffset)
      partition.updateFollowerFetchTime(replicaId, currentTimeMs)
    }
  }
  
  // 读取消息
  val fetchData = fetchInfos.map { case (tp, data) =>
    val partition = getPartition(tp)
    val hw = partition.leaderReplica.get.highWatermark
    
    // Follower 可以读到 Leader 的 LEO（不限制 HW）
    // Consumer 只能读到 HW
    val maxOffset = if (replicaId >= 0) 
      partition.leaderReplica.get.logEndOffset 
    else 
      hw
    
    val records = readRecords(tp, data.fetchOffset, maxOffset, data.maxBytes)
    tp -> FetchData(records)
  }
  
  // 延迟响应：如果数据量不足 minBytes，等待新消息或超时
  if (fetchData.values.map(_.size).sum < minBytes && timeout > 0) {
    // 放入延迟队列，等有新消息时唤醒
    delayedFetch.add(fetchData)
  }
  
  fetchData
}
```

**DelayedFetch** 延迟响应机制（`kafka.server.DelayedFetch`）：

```scala
// 延迟 Fetch 响应：减少空轮询，提升吞吐
class DelayedFetch(timeoutMs: Long, 
                   minBytes: Int,
                   fetchPartitionData: Seq[(TopicPartition, FetchData)],
                   replicaManager: ReplicaManager,
                   callback: () => Unit)
    extends DelayedRequest(timeoutMs) {
  
  // 当 Leader 收到新的 Producer 消息时，检查延迟 Fetch 是否可以满足
  override def tryComplete(): Boolean = {
    val currentBytes = fetchPartitionData.map(_._2.size).sum
    currentBytes >= minBytes  // 数据量够了，完成响应
  }
  
  override def onExpiration(): Unit = {
    // 超时，返回当前已有的数据
    callback()
  }
}
```

**⚠️ 常见坑/加分回答：**

- 跨机房复制时，如果网络延迟高且 `replica.fetch.max.bytes` 较小，会导致 Fetch 次数增多、同步延迟加大。悦茶建议跨机房场景将 `replica.fetch.max.bytes` 设为 5~10MB。
- 悦茶监控副本同步延迟（`kafka.server:ReplicaFetcherManager:MaxLag`），当 Lag > 10000 条消息时触发告警。
- 加分回答：Kafka 2.7+ 引入了 `fetch.max.wait.ms` 的改进——当有新消息到达时，Leader 会主动唤醒延迟 Fetch 响应，而不是等到超时。这使得低延迟场景下 Consumer 也能及时获取新消息。

#### 二、多副本机制全景解析

**0. 核心概念：AR / ISR / OSR / LEO / HW**

Kafka 多副本体系中，有几个关键概念必须清晰区分：

**AR（Assigned Replicas，分配副本）**
- 创建 Topic 时，Controller 为该 Partition 分配的所有副本集合。
- 大小由 `replication.factor` 决定。例如 `replication.factor=3`，则 AR = [Broker-0, Broker-1, Broker-2]。
- AR 是静态的，除非手动 reassign，否则不会变化。

**ISR（In-Sync Replicas，同步副本）**
- AR 的子集，由与 Leader 保持同步的副本组成。
- "同步"的判定标准：Follower 的最后一次 Fetch 请求距 Leader 的时间差 < `replica.lag.time.max.ms`（默认 30s）。
- ISR 是动态的：Follower 追赶上来就加入，落后太多就被踢出。
- **只有 ISR 中的副本有资格被选为新 Leader**（除非开启 unclean leader election）。
- 初始化时 ISR 只包含 Leader 自己，Follower 追平后逐步加入。

**OSR（Out-of-Sync Replicas，非同步副本）**
- AR 中不在 ISR 里的副本，即 `OSR = AR - ISR`。
- 原因通常是：Follower 所在 Broker 宕机、网络延迟、磁盘 IO 瓶颈等。
- OSR 副本**不能**参与 Leader 选举（默认配置下），即使它上面有部分数据。

**三者关系：AR = ISR + OSR**

```
┌─────────────────────────────────────────────────────────────┐
│  AR（Assigned Replicas）= [B0, B1, B2]   replication.factor=3 │
│                                                               │
│  ┌─────────────────────────┐  ┌──────────────────────┐        │
│  │  ISR (同步副本)          │  │  OSR (非同步副本)     │        │
│  │  [B0, B1]               │  │  [B2]                │        │
│  │  · B0 = Leader          │  │  · B2 落后超过 30s   │        │
│  │  · B1 = Follower，已追平 │  │  · 暂不可用于选举    │        │
│  │  · 可参与 Leader 选举    │  │  · 追平后可重新加入ISR│        │
│  └─────────────────────────┘  └──────────────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

**LEO（Log End Offset，日志末端偏移量）**
- 每个副本（Leader 和每个 Follower）各自维护一个 LEO。
- 表示该副本本地日志文件中最后一条消息的下一个 Offset。
- Leader 的 LEO 代表已写入的最新位置；Follower 的 LEO 代表已同步到的位置。

**HW（High Watermark，高水位）**
- `HW = min(所有 ISR 副本的 LEO)`
- Consumer 只能消费 HW 之前的消息。这保证了消费者读到的数据在所有 ISR 副本中都已存在，不会因为 Leader 切换而丢失已读消息。
- HW 只在 ISR 中所有副本的 LEO 都推进时才会推进。

**几个关键数值关系：**
```
对于任意 ISR 中的副本 R：
  HW ≤ R.LEO ≤ Leader.LEO

对于任意 OSR 中的副本 R：
  R.LEO < HW（已落后于高水位）

Consumer 可见范围：offset ∈ [0, HW)
Leader 可写范围：  offset ≥ Leader.LEO
Follower 追赶目标：R.LEO → Leader.LEO
```

**悦茶场景理解：**
悦茶的 `order-events` Topic 配置 `replication.factor=3`，则：
- AR = [Broker-0, Broker-1, Broker-2] — 三个 Broker 各持有一份副本
- 正常状态下 ISR = [Broker-0, Broker-1, Broker-2] = AR — 三个都同步
- Broker-2 磁盘 IO 抖动，LEO 落后超过 30s → ISR 缩为 [Broker-0, Broker-1]，Broker-2 进入 OSR
- 此时 `acks=all` + `min.insync.replicas=2` 仍然满足，写入不中断
- Broker-2 恢复正常、LEO 追平 Leader → 重新加入 ISR → ISR 恢复为 [Broker-0, Broker-1, Broker-2]
- 如果 Broker-0（Leader）此时宕机 → Controller 从 ISR 中选 Broker-1 作为新 Leader → 0 数据丢失

### 第17集：Kafka 为什么这么快？

**💡 核心回答：**

Kafka 的高性能来自五大核心设计：

1. **顺序写磁盘**：Kafka 将消息追加写入日志文件（顺序 IO），而非随机写入。顺序写磁盘的速度接近内存随机写（600MB/s vs 内存 100MB/s 随机写），远高于随机磁盘 IO（~100KB/s）。
2. **零拷贝（Zero-Copy）**：使用 `sendfile` 系统调用，消息从 PageCache 直接发送到网卡，无需经过用户空间，减少 2 次数据拷贝和 2 次上下文切换。
3. **页缓存（PageCache）**：Kafka 不做内存管理，而是依赖 OS 的 PageCache。消息写入后自然缓存在 PageCache 中，Consumer 读取时直接命中缓存。即使 Broker 重启，PageCache 仍被 OS 保留。
4. **批量发送**：Producer 将消息攒到 `batch.size`（默认 16KB）后批量发送，减少网络请求次数。配合 `linger.ms` 控制等待时间，用少量延迟换取大量吞吐。
5. **压缩**：Producer 端支持 Snappy/LZ4/Zstd 压缩，将多个消息一起压缩后发送，减少网络传输量和磁盘 IO。

**📦 实际例子：**

悦茶平台的性能压测结果（单 Broker、3 个 Partition）：

| 配置 | 吞吐量 | 延迟 P99 |
|------|--------|----------|
| 基础配置（batch.size=16KB, linger.ms=0） | 200MB/s | 5ms |
| 开启批量（batch.size=64KB, linger.ms=10ms） | 450MB/s | 15ms |
| 批量 + LZ4 压缩 | 520MB/s | 12ms |
| 批量 + 压缩 + 增大 buffer.memory | 580MB/s | 10ms |

悦茶生产环境最终配置：`batch.size=32KB`、`linger.ms=5ms`、`compression.type=lz4`、`buffer.memory=64MB`。

**🔍 源码解析：**

顺序写实现（`kafka.log.FileRecords`）：

```java
// FileRecords 基于 FileChannel 的追加写
public class FileRecords implements Iterable<RecordBatch> {
    private final FileChannel channel;
    private final File file;
    
    // 追加消息到日志文件
    public int append(MemoryRecords records) throws IOException {
        int written = channel.write(records.buffer());
        // 底层是 FileChannel.write()，顺序追加
        // OS 会将数据写入 PageCache，异步刷盘
        return written;
    }
}
```

批量压缩实现（`MemoryRecordsBuilder`）：

```java
// org.apache.kafka.common.record.MemoryRecordsBuilder

    private final ByteBuffer buffer;
    private final CompressionType compressionType;
    private int numberOfRecords = 0;
    
    // 追加单条消息到 RecordBatch
    public void append(long timestamp, byte[] key, byte[] value) {
        // 消息先写入 buffer，在 commit 时统一压缩
        buffer.put(recordBytes);
        numberOfRecords++;
    }
    
    // 构建最终的 MemoryRecords
    public MemoryRecords build() {
        if (compressionType != CompressionType.NONE) {
            // 将整个 buffer 压缩
            byte[] compressed = compressionType.compress(buffer.array());

```

PageCache 的工作机制（操作系统层面）：

```
// Kafka 不直接管理内存，依赖 OS PageCache
// 消息写入流程:
// Producer -> Broker -> FileChannel.write() -> PageCache -> (异步) Disk Flush

// Consumer 读取流程:
// Consumer <- Broker <- FileChannel.transferTo() <- PageCache <- (可能) Disk Read

// PageCache 优势:
// 1. JVM 不需要管理内存，避免 GC 问题
// 2. 即使 Broker 重启，OS PageCache 保留
// 3. 读热数据（最近的消息）几乎全在 PageCache 中

// Kafka 不主动调用 fsync()（除非配置 log.flush.interval.messages）
// 而是依赖 OS 的刷盘策略（通常每 30 秒或 PageCache 满时刷盘）
```

**⚠️ 常见坑/加分回答：**

- `log.flush.interval.messages` 设为较小值会强制 fsync，严重降低吞吐量。悦茶不建议设置此参数，而是依赖多副本保证数据安全。
- JVM 堆内存不要设太大（悦茶设为 6GB），留给 OS PageCache 更多内存。Kafka 的性能瓶颈通常在磁盘 IO 而非 JVM。
- 加分回答：Kafka 的"快"不是单一优化，而是多个设计协同的结果。顺序写 + PageCache 使得写性能接近内存速度；零拷贝 + PageCache 使得读性能也接近内存速度；批量 + 压缩减少了网络开销。

### 第18集：Kafka vs RocketMQ 对比

**💡 核心回答：**

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| **架构** | Broker + ZK/KRaft | NameServer + Broker |
| **元数据管理** | ZK 或 KRaft Raft | NameServer（无状态，简单） |
| **消息模型** | Pull 模型 | Pull + Push（长轮询） |
| **事务消息** | 基于 PID + Sequence + 事务 Coordinator | 半消息 + 回查机制 |
| **延迟消息** | 原生不支持 | 原生支持（18 个级别） |
| **消息回溯** | 按时间/Offset 回溯 | 按时间回溯 |
| **协议** | 自定义二进制协议 | 自定义二进制协议 |
| **吞吐量** | 百万级 TPS | 十万级 TPS |
| **适用场景** | 日志收集、大数据管道、流处理 | 电商交易、金融场景 |
| **语言** | Java + Scala | Java |

**核心差异**：
1. **吞吐量**：Kafka 通过顺序写 + 零拷贝 + 批量 + 压缩达到百万级 TPS；RocketMQ 更注重功能丰富性和业务场景适配。
2. **事务消息**：Kafka 使用 PID + 事务 Coordinator 实现分布式事务；RocketMQ 使用半消息 + 回查的两阶段提交，对业务侵入更小。
3. **延迟消息**：RocketMQ 原生支持，Kafka 需要外部方案。

**📦 实际例子：**

悦茶平台同时使用 Kafka 和 RocketMQ：
- **Kafka**：用户行为日志、门店数据采集、实时数据分析管道——这些场景吞吐量大、对延迟消息无需求。
- **RocketMQ**：订单超时取消（30分钟延迟消息）、支付回调重试（延迟消息）、分布式事务——这些场景需要延迟消息和事务消息的原生支持。

悦茶的选择：大数据管道用 Kafka，业务消息用 RocketMQ。

- 加分回答：两者社区生态不同——Kafka 背后是 Confluent 和 Apache 社区，围绕大数据生态（Flink、Spark、Connect、Streams）；RocketMQ 是阿里开源，更贴合 Java 业务开发场景。

### 第19集：Kafka 的多租户设计

**💡 核心回答：**

Kafka 从 2.0 开始提供完整的多租户能力，主要包括三个方面：

**1. Quota 限流**：
- **Producer Quota**：限制单个 Client ID 的字节生产速率（bytes/sec）。
- **Consumer Quota**：限制单个 Client ID 的字节消费速率（bytes/sec）。
- **Request Quota**：限制单个 Client ID 的 CPU 配额（百分比）。
- 超限时请求不会报错，而是被延迟（Throttled），在响应中携带 `throttle_time_ms`。

**2. ACL 权限控制**：
- 基于 Kafka 内置的 Authorizer 或外部系统（如 Confluent RBAC）。
- 支持 Topic 级别的 Produce/Consume/Describe/Create/Delete 权限。
- 支持 Consumer Group 级别的 Read 权限。
- 支持 Cluster 级别的 Alter/Describe/ClusterAction 权限。

**3. Topic 隔离**：
- 通过 ACL 限制不同租户只能访问自己的 Topic。
- 通过 Quota 限制不同租户的资源使用量。
- 物理隔离方案：不同租户使用不同的 Broker 集群。

**📦 实际例子：**

悦茶平台的 `order-events` Topic 需要被多个团队消费：
- 订单团队（`order-service`）：拥有 Produce + Consume 权限，Quota 不限。
- 风控团队（`risk-analysis`）：只有 Consume 权限，Quota 限制 50MB/s。
- 外部合作方（`partner-api`）：只有 Describe + Consume 权限，Quota 限制 10MB/s。

```bash

kafka-acls.sh --add --allow-principal User:order-service   --operation Write --topic order-events

kafka-acls.sh --add --allow-principal User:risk-analysis   --operation Read --topic order-events --group risk-group

# 设置 Quota
kafka-configs.sh --alter --add-config 'producer_byte_rate=52428800'   --entity-type clients --entity-name risk-analysis
```

**🔍 源码解析：**

Quota 限流实现（`kafka.server.ClientQuotaManager`）：

```scala
class ClientQuotaManager(config: ClientQuotaManagerConfig, ...) {
  // 基于令牌桶算法的限流
  private val throttleTimeMs = new AtomicLong(0)
  
  def recordAndMaybeThrottle(clientId: String, 
                              value: Double, 
                              timeMs: Long): QuotaResult = {
    // 获取该 Client 的 Quota 配置
    val quota = getQuotaForClient(clientId)
    
    // 令牌桶计算
    val currentRate = quota.update(value, timeMs)
    
    if (currentRate > quota.bound) {
      // 超限，计算延迟时间
      val delayMs = ((currentRate - quota.bound) / quota.bound * 1000).toLong
      QuotaResult(throttleTimeMs = delayMs, isThrottled = true)
    } else {
      QuotaResult(throttleTimeMs = 0, isThrottled = false)
    }
  }
}
```

ACL 权限检查（`kafka.security.authorizer.AclAuthorizer`）：

```scala
class AclAuthorizer extends Authorizer {
  // ACL 存储在 ZK 的 /kafka-acls 路径下（或内部 Topic __acl）
  
  override def authorize(requestContext: AuthorizableRequestContext,
                         actions: util.List[Action]): util.List[AuthorizationResult] = {
    val principal = requestContext.principal
    val resource = actions.get(0).resourcePattern()
    
    // 1. 查找匹配的 ACL 规则
    val acls = getAcls(resource)
    
    // 2. 检查 ALLOW 和 DENY 规则
    val denied = acls.exists { acl =>
      acl.accessControlEntry().operation() == ANY &&
      acl.accessControlEntry().permissionType() == DENY &&
      acl.accessControlEntry().principal() == principal.toString
    }
    
    if (denied) {
      return List(AuthorizationResult.DENIED)
    }
    
    val allowed = acls.exists { acl =>
      acl.accessControlEntry().principal() == principal.toString &&
      acl.accessControlEntry().operation().matches(actions.get(0).operation())
    }
    
    if (allowed) List(AuthorizationResult.ALLOWED)

  }
}
```

**💡 核心回答：**

### 第21集：Kafka 的消息保留与回溯

**💡 核心回答：**

Kafka 支持按时间和 Offset 回溯消费：

**按时间回溯**：Consumer 调用 `offsetsForTimes(Map<TopicPartition, Long>)` 传入目标时间戳，Broker 返回每个 Partition 中第一个 ≥ 目标时间的 Offset。Consumer 再 `seek()` 到该 Offset 开始消费。

**按 Offset 回溯**：Consumer 调用 `seek(TopicPartition, long)` 直接跳转到指定 Offset。

**按位置回溯**：
- `seekToBeginning(Collection<TopicPartition>)`：跳到每个 Partition 的起始位置。
- `seekToEnd(Collection<TopicPartition>)`：跳到每个 Partition 的末尾。

**日志压缩后的回溯**：对于 `compact` Topic，旧消息可能已被清理。回溯到某个时间点时，只能读到该时间点之后仍然存活的最新消息（即每个 Key 的最后一条）。

**时间精度**：Broker 使用 TimeIndex 定位，精度取决于索引密度（每写入约 4KB 消息记录一个索引条目）。时间定位后在 `.log` 文件中顺序扫描找到精确消息。

**📦 实际例子：**

悦茶平台的运营系统需要"重播"昨天的订单数据重新计算报表：

```java

    .toInstant().toEpochMilli();

}

    if (entry.getValue() != null) {
        consumer.seek(entry.getKey(), entry.getValue().offset());
    }
}
```

悦茶的门店配置 Topic 使用 `compact` 策略，运维人员发现某门店配置被误改后，无法通过时间回溯恢复旧配置——因为旧配置已被压缩清理。解决方案是额外维护一个 `compact` + `delete` 组合策略的审计 Topic。

**🔍 源码解析：**

`offsetsForTimes` 的 Broker 端实现（`KafkaApis.handleOffsetRequest`）：

```scala
// KafkaApis 处理 OffsetForTimes 请求
def handleOffsetRequest(request: RequestChannel.Request): Unit = {
  val offsetRequest = request.body[OffsetsRequest]
  
  val responsePartitions = offsetRequest.topics.flatMap { topic =>
    topic.partitions.map { partition =>
      val tp = new TopicPartition(topic.name, partition.partition)
      
      partition.timestamp match {
        case EARLIEST_TIMESTAMP =>
          // 返回最早可用 Offset
          val logStartOffset = replicaManager.getLog(tp).get.logStartOffset
          new OffsetsResponse.PartitionOffsets(tp, Errors.NONE, 
            List(logStartOffset).asJava)
        
        case LATEST_TIMESTAMP =>
          // 返回最新 Offset（HW）
          val hw = replicaManager.getLog(tp).get.highWatermark
          new OffsetsResponse.PartitionOffsets(tp, Errors.NONE, 
            List(hw).asJava)
        
        case timestamp =>
          // 按时间查找：使用 TimeIndex
          val log = replicaManager.getLog(tp).get
          val segment = log.segments.lastSegmentBefore(timestamp)
          
          // 在 TimeIndex 中二分查找
          val timestampOffset = segment.timeIndex.lookup(timestamp)
          val offset = timestampOffset.offset
          
          // 在 OffsetIndex 中精确定位
          val position = segment.offsetIndex.lookup(offset)
          
          // 在 .log 文件中顺序扫描找到第一条 >= timestamp 的消息
          val records = segment.log.read(position.position, maxBytes)
          val resultOffset = records.batches.asScala
            .flatMap(_.records.asScala)
            .find(_.timestamp >= timestamp)
            .map(_.offset)
            .getOrElse(segment.baseOffset + segment.size)
          
          new OffsetsResponse.PartitionOffsets(tp, Errors.NONE,
            List(resultOffset).asJava)
      }
    }
  }
}
```

### 第22集：Exactly-Once 语义（EOS）的完整链路

**💡 核心回答：**

Kafka 的端到端 Exactly-Once 语义由三个组件配合实现：

1. **幂等 Producer**：`enable.idempotence=true`，通过 PID + Sequence Number 保证单分区内消息不重复。
2. **事务 Producer**：`transactional.id=xxx`，保证跨分区、跨 Topic 的原子写入。
3. **Consumer read_committed**：`isolation.level=read_committed`，只读取已提交事务的消息，忽略未提交和已中止事务的消息。

**完整链路**：
```
Producer.beginTransaction()
  → send(msg1)  [标记为 uncommitted]
  → send(msg2)  [标记为 uncommitted]
Producer.commitTransaction()
  → 写入 COMMIT Marker
  → Consumer (read_committed) 可以读到 msg1, msg2
```

如果事务 Abort：
```
Producer.beginTransaction()
  → send(msg1)  [标记为 uncommitted]
Producer.abortTransaction()
  → 写入 ABORT Marker
  → Consumer (read_committed) 看不到 msg1
```

**📦 实际例子：**

悦茶平台的库存扣减事务流程：

```java
Properties props = new Properties();

props.put("transactional.id", "inventory-service-tx");
props.put("enable.idempotence", "true");

producer.initTransactions();

try {
    producer.beginTransaction();
    
    // 扣减门店库存（store-inventory Topic，按 storeId 分区）
    producer.send(new ProducerRecord<>("store-inventory", 
        storeId, serializeInventoryDecrease(skuId, quantity)));
    
    // 记录流水（inventory-ledger Topic，按流水号分区）
    producer.send(new ProducerRecord<>("inventory-ledger",
        ledgerId, serializeLedgerRecord(skuId, quantity, orderId)));
    
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
    throw e;
}
```

Consumer 端设置 `isolation.level=read_committed`，确保只看到完整事务：

```scala

// Empty -> Ongoing -> PrepareCommit -> CompleteCommit
//                  -> PrepareAbort -> CompleteAbort
// Empty -> Dead (超时)
class TransactionStateManager(...) {
  
  def validateTransactionTimeout(producerId: Long): Boolean = {
    val metadata = getTransactionMetadata(producerId)
    val now = time.milliseconds
    
    // 检查事务是否超时
    if (metadata.state == Ongoing && 
        now - metadata.txnStartTimestamp > transactionTimeoutMs) {
      // 超时，触发 Abort
      transitionTo(PrepareAbort)
      false
    } else {
      true
    }
  }
}
```

Consumer 端 `read_committed` 的过滤逻辑（`Fetcher`）：

```java
// Fetcher.fetchedRecords() 中的事务过滤
private List<ConsumerRecord<K, V>> filterAbortedTransactions(
        List<ConsumerRecord<K, V>> records) {
    if (isolationLevel == READ_UNCOMMITTED) {
        return records;  // 不过滤
    }
    
    // READ_COMMITTED: 过滤未提交和已中止的事务
    return records.stream()
        .filter(record -> {
            // 检查消息所属的事务是否已提交
            // 如果遇到 ABORT Marker，丢弃该事务的所有消息
            // 如果遇到 COMMIT Marker，保留该事务的所有消息
            return transactionState.isCommitted(record.producerId());
        })
        .collect(Collectors.toList());
}
```

**⚠️ 常见坑/加分回答：**

- `read_committed` 模式下 Consumer 可能被阻塞：如果一个长事务一直不提交，Consumer 在该事务的 Offset 处等待，导致后续消息的消费延迟。悦茶监控 `currentTxnBeginOffset` 指标检测此类问题。
- 加分回答：Kafka 事务的 Control Batch（控制批次）与普通数据批次格式不同，包含 `isTransactional=true` 和 `isControl=true` 标记。Consumer 在解析时会跳过 Control Batch 的内容，只读取其状态信息。

### 第23集：Kafka 的压缩机制

**💡 核心回答：**

Kafka 的压缩分两层：

**Producer 端压缩**（推荐）：
- Producer 在发送前将一个 RecordBatch 中的所有消息一起压缩。
- 支持的算法：Snappy（默认）、LZ4、Zstd、Gzip。
- 压缩后的数据通过网络传输，Broker 原样存储。
- Consumer 读取后自行解压。
- **优点**：一次压缩、全程使用，减少网络带宽和磁盘 IO。

**Broker 端压缩**（不推荐）：
- 如果 Producer 的消息有不同的压缩类型，Broker 在追加到日志时可能需要重新压缩（Decompression + Recompression）。
- 这发生在 Producer 的压缩类型与 Broker 配置不一致时。
- **优点**：可以统一压缩格式。
- **缺点**：Broker 端压缩消耗 CPU，影响吞吐量。

**压缩算法对比**：

| 算法 | 压缩比 | 速度 | 适用场景 |
|------|--------|------|----------|
| Gzip | 最高 | 最慢 | 磁盘空间紧张，网络带宽有限 |
| Snappy | 中等 | 快 | 通用场景，平衡压缩比和速度 |
| LZ4 | 中等 | 最快 | 低延迟场景 |
| Zstd | 最高 | 较快 | Kafka 2.1+ 新增，压缩比接近 Gzip 但速度更快 |

**📦 实际例子：**

悦茶平台的压缩策略：
- **用户行为日志**（`user-behavior`）：使用 Zstd 压缩，压缩比约 5:1，每天节省约 60% 磁盘空间。
- **订单事件**（`order-events`）：使用 LZ4 压缩，追求低延迟（实时分析需要快速消费）。
- **门店监控数据**（`store-metrics`）：使用 Snappy 压缩，平衡压缩比和 CPU 消耗。

悦茶压测对比（100 万条订单消息，单条 500 字节）：

| 压缩算法 | 磁盘占用 | 压缩耗时 | 解压耗时 | 端到端吞吐 |
|----------|----------|----------|----------|------------|
| 不压缩 | 500MB | 0ms | 0ms | 300MB/s |
| Snappy | 200MB | 15ms | 5ms | 420MB/s |
| LZ4 | 180MB | 10ms | 3ms | 450MB/s |
| Zstd | 120MB | 25ms | 8ms | 380MB/s |
| Gzip | 100MB | 80ms | 20ms | 250MB/s |

**🔍 源码解析：**

RecordBatch 压缩格式（`org.apache.kafka.common.record.RecordBatch`）：

```java
    // Bit 0-2: compression type (0=none, 1=gzip, 2=snappy, 3=lz4, 4=zstd)
    // Bit 3:   timestamp type (0=CreateTime, 1=LogAppendTime)
    // Bit 4:   isTransactional (0=false, 1=true)
    // Bit 5:   isControlBatch (0=false, 1=true)
    // Bit 6:   deleteHorizon (0=false, 1=true)
```

```scala
  records.batches.forEach { batch =>
    if (batch.compressionType != CompressionType.NONE) {
      // 检查是否需要重压缩
      val targetCompression = logConfig.compressionType
      if (targetCompression != batch.compressionType) {
        // 需要重压缩: 先解压，再用目标压缩算法重新压缩
        val decompressed = batch.decompress()
        val recompressed = recompress(decompressed, targetCompression)

        segment.append(batch)
      }
    }
  }
}
```

**⚠️ 常见坑/加分回答：**

- 悦茶遇到过 Producer 用 Gzip 压缩但 Broker 配置的 `compression.type=producer`（默认值，保持 Producer 的压缩格式），导致 Broker 存储了混合压缩格式的消息。Consumer 端需要支持所有格式的解压。
- Zstd 在 Kafka 2.1+ 才支持，升级前确认客户端和 Broker 版本。
- 加分回答：`compression.type=producer` 是 Broker 的默认配置，表示保持 Producer 发送时的压缩格式。建议统一 Producer 和 Broker 的压缩类型，避免重压缩开销。

### 第24集：延迟消息和定时任务的实现

**💡 核心回答：**

Kafka 原生不支持延迟消息。常见实现方案：

**方案一：时间轮（DelayedQueue）**
- 在应用层维护一个延迟队列（如 Java 的 `DelayedQueue` 或 Kafka 内部的时间轮）。
- 消息到达后不立即发送，而是放入延迟队列。
- 到达延迟时间后，从延迟队列取出并发送到 Kafka。
- **优点**：精确控制。
- **缺点**：延迟消息存储在应用内存中，应用重启丢失。

**方案二：多 Topic 时间分桶**
- 按延迟时间创建多个 Topic：`delay-1s`、`delay-5s`、`delay-30s`、`delay-1m`、`delay-5m` 等。
- Producer 将消息发送到对应延迟级别的 Topic。
- Consumer 消费后判断是否到达目标时间，未到则重新发送到下一级 Topic。
- **优点**：消息持久化在 Kafka 中，不丢失。
- **缺点**：Topic 数量多，精度有限。

**方案三：Kafka + 外部组件**
- 使用 Redis、RocketMQ 等支持延迟消息的中间件作为延迟层，到期后再写入 Kafka。
- 或使用定时任务框架（如 XXL-JOB）触发消息发送。

**方案四：Kafka 内部时间轮（Kafka 自身的 DelayedOperation）**
- Kafka Broker 内部使用 `DelayedOperationPurgatory` 实现延迟操作（如延迟 Fetch、延迟 Producer 确认）。
- 可以利用此机制构建延迟消息，但需要自定义开发。

**📦 实际例子：**

悦茶平台的延迟场景实现：

**订单超时取消**（30分钟未支付自动取消）：
- 方案：Producer 发送订单创建事件时，同时发送一条延迟消息到延迟服务（Redis DelayedQueue），30 分钟后触发检查。
- Consumer 收到延迟消息后查询订单状态，如果未支付则发送取消事件到 `order-cancel-events` Topic。

**定时数据同步**：
- 方案：使用 XXL-JOB 定时任务，每分钟触发一次数据同步 Job，将结果发送到 Kafka。

**促销倒计时提醒**：
- 方案：用户设置促销提醒后，将提醒事件写入 Redis Sorted Set（score = 提醒时间），定时任务扫描到期事件，写入 `promotion-reminders` Topic。

```scala
// 使用分层时间轮（Hierarchical Timing Wheel）
class DelayedOperationPurgatory[T <: DelayedOperation](
    purgatoryName: String,
    timeoutTimer: Timer,
    serverId: Int) {
  
  // 分层时间轮
  // 第1层: 20个槽，每槽 1ms → 覆盖 0~20ms
  // 第2层: 20个槽，每槽 20ms → 覆盖 20~400ms
  // 第3层: 20个槽，每槽 400ms → 覆盖 400~8000ms
  // ...以此类推
  
  def tryComplete(operation: T): Unit = {
    // 尝试完成延迟操作（如 Fetch 请求等到了足够的数据）
    if (operation.tryComplete()) {
      operation.onComplete()
    }
  }
  
  def watch(operation: T): Unit = {
    // 将延迟操作放入时间轮
    val timeoutMs = operation.delayMs
    timeoutTimer.add(new TimerTask(timeoutMs) {
      def run(): Unit = {
        // 时间到了，执行操作
        operation.onExpiration()
      }
    })
  }
}

class TimerTaskList {
  private val root = new TimerTaskEntry(null, -1)
  
  def add(timerTaskEntry: TimerTaskEntry): Unit = {
    // 将任务添加到链表
  }
  
  def flush(f: TimerTaskEntry => Unit): Unit = {
    // 触发所有到期任务
  }
}

class TimingWheel(tickMs: Long, wheelSize: Int, startMs: Long) {
  private val buckets = Array.fill(wheelSize)(new TimerTaskList())
  private var interval = tickMs * wheelSize
  private var overflowWheel: TimingWheel = null  // 上一层时间轮
  
  def add(timerTaskEntry: TimerTaskEntry): Boolean = {
    val expirationMs = timerTaskEntry.expirationMs
    if (expirationMs < startMs + interval) {
      // 在当前轮中
      val virtualId = (expirationMs / tickMs) % wheelSize
      val bucket = buckets(virtualId.toInt)
      bucket.add(timerTaskEntry)
      true
    } else {
      // 溢出到上一层
      if (overflowWheel == null) {
        overflowWheel = new TimingWheel(interval, wheelSize, startMs)
      }
      overflowWheel.add(timerTaskEntry)
    }
  }
}
```

```java
// 延迟消息生产者
public class DelayedMessageProducer {
    private final KafkaProducer<String, byte[]> kafkaProducer;
    private final DelayQueue<DelayedMessage> delayQueue;
    
    public DelayedMessageProducer(KafkaProducer<String, byte[]> producer) {
        this.kafkaProducer = producer;
        this.delayQueue = new DelayQueue<>();
        // 启动延迟消息发送线程
        new Thread(this::processDelayedMessages).start();
    }
    
    public void sendDelayed(String topic, String key, byte[] value, 
                            long delayMs) {
        delayQueue.put(new DelayedMessage(topic, key, value, 
            System.currentTimeMillis() + delayMs));
    }
    
    private void processDelayedMessages() {
        while (true) {
            try {
                DelayedMessage msg = delayQueue.take();  // 阻塞直到到期
                kafkaProducer.send(new ProducerRecord<>(
                    msg.getTopic(), msg.getKey(), msg.getValue()));
            } catch (InterruptedException e) {
                break;
            }
        }
    }
}

class DelayedMessage implements Delayed {
    private final String topic;
    private final String key;
    private final byte[] value;
    private final long executeTime;
    
    @Override
    public long getDelay(TimeUnit unit) {
        return unit.convert(executeTime - System.currentTimeMillis(), 
            TimeUnit.MILLISECONDS);
    }
    
    @Override
    public int compareTo(Delayed o) {
        return Long.compare(this.executeTime, 
            ((DelayedMessage) o).executeTime);
    }
}
```

### 第25集：消息积压的排查与解决

**💡 核心回答：**

消息积压（Consumer Lag）是指 Producer 发送消息的速度 > Consumer 消费的速度，导致未消费消息堆积。

**排查步骤**：

1. **确认积压量**：使用 `kafka-consumer-groups.sh --describe --group xxx` 查看 Lag 值。
2. **定位瓶颈**：
   - Consumer 端：单条消息处理太慢？频繁 GC？锁竞争？
   - Broker 端：磁盘 IO 瓶颈？网络带宽不足？
   - Rebalance 问题：频繁 Rebalance 导致消费中断？
3. **分区数匹配**：Consumer 数量 > Partition 数量时，多余的 Consumer 闲置。需要增加 Partition 数量。

**解决方案**：

1. **增加 Consumer 实例**：水平扩容，Consumer 数 ≤ Partition 数。
2. **优化消费逻辑**：减少单条消息处理时间，异步化非关键操作。
3. **批量消费**：增大 `max.poll.records`，减少 poll 次数。
4. **增加 Partition**：如果 Partition 不够，扩容 Topic 的 Partition 数（注意：不能减少，且 Key 哈希会变化）。
5. **临时中转 Topic**：紧急情况下，创建临时 Topic（Partition 数 = 原 Topic × N），Consumer 从原 Topic 消费后快速写入临时 Topic，再用更多 Consumer 消费临时 Topic。

**📦 实际例子：**

悦茶平台在"双11"促销期间，`order-events` Topic 的消息量暴增 5 倍，Consumer Lag 持续增长。

**排查过程**：
1. 查看 Lag：从正常的 1000 条增长到 50 万条。
2. 查看 Consumer 处理耗时：单条消息处理 20ms（正常 5ms），原因是下游数据库连接池被打满。
3. 查看 Partition 分配：12 个 Partition，8 个 Consumer，所有 Consumer 都在满负荷工作。

**解决措施**：
1. 紧急扩容数据库连接池（从 50 调到 200）。
2. 临时创建 36 个 Partition 的中转 Topic `order-events-temp`。
3. 原有 8 个 Consumer 消费原 Topic 后快速写入临时 Topic。
4. 新启动 28 个 Consumer 消费临时 Topic。
5. 积压在 2 小时内清理完毕。

### 第26集：Rebalance 频繁的根因和解决

**💡 核心回答：**

Rebalance 频繁会导致 Consumer 长时间无法消费（Stop-The-World），严重影响吞吐和延迟。

**常见根因**：

1. **心跳超时**：Consumer 网络不稳定或 Broker 负载过高，导致心跳包无法在 `session.timeout.ms` 内到达 Coordinator。
2. **处理超时**：Consumer 处理消息太慢，两次 `poll()` 的间隔超过 `max.poll.interval.ms`，Coordinator 认为 Consumer 已死。
3. **订阅不一致**：同一个 Group 内的 Consumer 订阅了不同的 Topic 集合，导致每次 Rebalance 后都因为元数据变化再次触发。
4. **Consumer 频繁启动/停止**：如容器化部署中 Pod 频繁重启。

**解决方案**：

1. **调大 session.timeout.ms**：从默认 45 秒调到 60~120 秒（同时调大 heartbeat.interval.ms）。
2. **调大 max.poll.interval.ms**：根据最慢的消息处理时间设置。
3. **减小 max.poll.records**：减少单次 poll 的消息量，加快处理速度。
4. **使用 CooperativeStickyAssignor**：增量式 Rebalance，减少消费停顿。
5. **统一订阅**：确保所有 Consumer 订阅相同的 Topic 集合。

**📦 实际例子：**

悦茶平台的 Consumer 在一次发版后出现 Rebalance 风暴：

**现象**：每 5 分钟 Rebalance 一次，每次停顿 30 秒，导致实时销售数据延迟 30 秒以上。

**排查**：
1. 查看 Broker 日志：发现 `Member xxx has failed` 频繁出现。
2. 查看 Consumer 日志：发现 `Poll timeout exceeded max.poll.interval.ms` 错误。
3. 分析代码：新版本增加了一个数据库查询操作，导致单条消息处理时间从 5ms 增加到 200ms。
4. 计算：`max.poll.records=500` × 200ms = 100 秒 > `max.poll.interval.ms=60 秒`（默认 300000ms，但悦茶之前设为了 60 秒）。

**修复**：
1. 将 `max.poll.interval.ms` 从 60 秒调到 600 秒。
2. 将 `max.poll.records` 从 500 减到 200。
3. 数据库查询添加连接池和缓存，处理时间降到 50ms。
4. 切换到 `CooperativeStickyAssignor`。

### 第27集：数据倾斜（Data Skew）问题

**💡 核心回答：**

数据倾斜是指某些 Partition 的数据量远大于其他 Partition，导致：
- 部分 Consumer 负载过重，处理延迟增大。
- 部分 Broker 磁盘/网络使用率不均衡。
- 整体吞吐受限于最慢的 Partition。

**根因分析**：

1. **Key 分布不均**：使用 Key 哈希分区时，如果某些 Key 的消息量远大于其他 Key（如"热门门店"），导致热点 Partition。
2. **Producer 指定分区**：所有消息被路由到同一 Partition。
3. **Consumer Group Rebalance 后分区分配不均**：某个 Consumer 被分配到数据量最大的几个 Partition。

**解决方案**：

1. **优化 Key 设计**：
   - 将热点 Key 拆分：`storeId` → `storeId + random(0~9)`，分散到 10 个 Partition。
   - 使用组合 Key：`storeId:timestamp_bucket`，按时间分桶。
2. **自定义分区器**：识别热点 Key，将其打散到多个 Partition。
3. **增加 Partition 数**：更多 Partition 分散数据。
4. **消费端扩容**：针对热点 Partition 增加专门的 Consumer 实例。

**📦 实际例子：**

悦茶平台的"旗舰店"问题：

某旗舰店（storeId=STORE_001）的订单量是普通门店的 100 倍。以 storeId 为 Key 分区后，该门店的所有订单都进入同一个 Partition（假设是 Partition 3），导致：
- Partition 3 的数据量是其他 Partition 的 50 倍。
- 负责 Partition 3 的 Consumer 处理延迟是其他 Consumer 的 30 倍。
- 该 Broker 的磁盘使用率远高于其他 Broker。

**解决方案**：
1. **Key 改造**：将 `storeId` 改为 `storeId:hash_bucket`，其中 `hash_bucket = hash(orderId) % 10`。旗舰店的订单分散到 10 个 Partition。
2. **自定义分区器**：对 TOP 10 门店使用打散策略，其他门店正常哈希。
3. **监控**：悦茶监控每个 Partition 的消息速率（messages-in per sec），当某个 Partition 的速率 > 平均值的 3 倍时触发告警。

```java
public class SkewAwarePartitioner implements Partitioner {
    private static final Set<String> HOT_KEYS = Set.of("STORE_001", "STORE_002", "STORE_005");
    
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionsForTopic(topic).size();
        String keyStr = new String(keyBytes);
        
        if (HOT_KEYS.contains(keyStr)) {
            // 热点 Key：用 value 中的 orderId 做二次哈希
            // 将同一门店的消息分散到多个 Partition
            // 注意：这会牺牲该门店的顺序性
            int orderIdHash = extractOrderId(valueBytes).hashCode();
            return Utils.toPositive(orderIdHash) % numPartitions;
        }
        
        // 非热点 Key：正常哈希
        return Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
    }
}
```

`batch.size` 和 `linger.ms` 的协同（`RecordAccumulator`）：

```java
// RecordAccumulator.append()
public RecordAppendResult append(TopicPartition tp, long timestamp,
        byte[] key, byte[] value, Header[] headers,
        Callback callback, long maxTimeToBlock) {
    
    // 1. 尝试追加到当前批次
    Deque<ProducerBatch> deque = batches.get(tp);
    ProducerBatch last = deque.peekLast();
    
    if (last != null) {
        FutureRecordMetadata future = last.tryAppend(timestamp, key, value, headers, callback, time);
        if (future != null) {
            // 追加成功，检查是否需要唤醒 Sender
            boolean batchFull = last.isFull();  // 达到 batch.size
            return new RecordAppendResult(future, deque, batchFull, false);
        }
    }
    
    // 2. 当前批次满了或不存在，创建新批次
    ByteBuffer buffer = bufferPool.allocate(batchSize, maxTimeToBlock);
    ProducerBatch batch = new ProducerBatch(tp, recordsBuilder, buffer);
    FutureRecordMetadata future = batch.tryAppend(timestamp, key, value, headers, callback, time);
    deque.addLast(batch);
    
    // 3. 检查 linger.ms
    // Sender 线程会在 linger.ms 到期后发送该批次（即使未满）
    return new RecordAppendResult(future, deque, false, true);
}

// Sender.run() 中检查 linger.ms
void run(long now) {
    List<ProducerBatch> expiredBatches = accumulator.drain(
        cluster, readyNodes, batchSize, now);
    // drain() 返回所有已满或已到 linger.ms 的批次
    for (ProducerBatch batch : expiredBatches) {
        send(batch);
    }
}
```

`linger.ms` 的等待逻辑（`RecordAccumulator.drain`）：

```java
// RecordAccumulator.drain()
public List<ProducerBatch> drain(Cluster cluster, Set<Node> nodes,
                                  int batchSize, long now) {
    List<ProducerBatch> results = new ArrayList<>();
    
    for (Node node : nodes) {
        List<TopicPartition> partitions = partitionsForNode(node, cluster);
        
        for (TopicPartition tp : partitions) {
            Deque<ProducerBatch> deque = batches.get(tp);
            if (deque == null) continue;
            
            synchronized (deque) {
                ProducerBatch batch = deque.peekFirst();
                if (batch == null) continue;
                
                // 检查是否到了 linger.ms 的等待时间
                long waitedTime = now - batch.createdMs;
                if (waitedTime >= lingerMs || batch.isFull()) {
                    // 已到等待时间或已满，可以发送
                    deque.pollFirst();
                    results.add(batch);
                }
                // 否则继续等待
            }
        }
    }
    return results;
}
```

**⚠️ 常见坑/加分回答：**

- 悦茶在调优时踩过一个坑：将 `batch.size` 设为 1MB，但 `buffer.memory` 还是 32MB，导致只能缓存 32 个批次，高峰期内存不足。正确做法是 `buffer.memory` 至少是 `batch.size × 预期并发批次数`。
- `max.in.flight.requests.per.connection=1` 会严重降低吞吐（每个请求必须等确认后才能发下一个），但能保证消息顺序。悦茶在需要顺序性的分区使用此配置。
- 加分回答：Kafka 的 `delivery.timeout.ms` = `linger.ms` + `request.timeout.ms` + `retry.backoff.ms × retries`，调优时需要理解这个公式的关系。

### 第29集：容量规划

**💡 核心回答：**

Kafka 容量规划需要综合考虑以下维度：

**1. 磁盘容量估算**：

```
磁盘总量 = 消息TPS × 单条消息大小 × 保留天数 × 副本因子 × 1.2(冗余)
```

示例：悦茶每天 1 亿条消息，单条 500 字节，保留 7 天，3 副本：
- 原始数据：1 亿 × 500B × 7 天 = 3.5TB
- 副本后：3.5TB × 3 = 10.5TB
- 加冗余：10.5TB × 1.2 = 12.6TB

**2. Broker 数量估算**：

```
Broker 数量 = ceil(总TPS / 单Broker吞吐上限)
```

单 Broker 吞吐上限取决于磁盘 IO、网络带宽、CPU。经验值：
- 普通磁盘（HDD）：单 Broker 约 100~200MB/s
- SSD：单 Broker 约 500~800MB/s
- NVMe：单 Broker 约 1~2GB/s

**3. Partition 数量估算**：

```
Partition 数量 = max(
    目标TPS / 单Partition吞吐上限,
    Consumer数量需求
)
```

单 Partition 吞吐上限经验值：
- 单 Partition Producer 约 10~50MB/s（取决于消息大小）
- 单 Partition Consumer 约 50~100MB/s

**4. 网络带宽估算**：

```
网络带宽 = TPS × 消息大小 × 副本因子 × 1.5(冗余)
```

**📦 实际例子：**

悦茶平台的容量规划（3000+ 门店）：

**业务需求**：
- 订单事件：5000 TPS，单条 1KB
- 用户行为：50000 TPS，单条 200B
- 门店监控：10000 TPS，单条 500B
- 总入口流量：5000×1000 + 50000×200 + 10000×500 = 20MB/s

**磁盘规划**：
- 每天数据量：20MB/s × 86400s = 1.7TB
- 保留 7 天 + 3 副本：1.7TB × 7 × 3 = 35.7TB
- 加 20% 冗余：42.8TB
- 5 台 Broker，每台 10TB 磁盘

**Broker 规划**：
- 总入口流量 20MB/s + 副本流量 40MB/s = 60MB/s
- 单 Broker 吞吐（SSD）约 500MB/s
- 5 台 Broker 足够（5 × 500 = 2500MB/s >> 60MB/s）

**Partition 规划**：
- 订单事件：12 个分区（6 个 Consumer × 2）
- 用户行为：24 个分区
- 门店监控：12 个分区
- 总计 48 个分区，平均每 Broker 约 10 个分区

**最终方案**：
- 5 台 Broker（8 核 32GB，SSD 10TB × 2）
- ZK/KRaft Controller 3 台
- 总计 48 个分区

```python
# 容量规划计算工具
def calculate_capacity(tps, msg_size_bytes, retention_days, 
                       replication_factor, num_brokers):
    # 总入口流量 (bytes/s)
    ingress_bytes = tps * msg_size_bytes
    
    # 总副本流量 (bytes/s) 
    total_replication = ingress_bytes * replication_factor
    
    # 每天数据量 (bytes)
    daily_bytes = ingress_bytes * 86400
    
    # 总磁盘需求 (bytes)
    total_disk = daily_bytes * retention_days * replication_factor
    total_disk_gb = total_disk / (1024**3)
    
    # 每 Broker 磁盘 (bytes)
    per_broker_disk = total_disk / num_brokers
    per_broker_disk_gb = per_broker_disk / (1024**3)
    
    # 每 Broker 网络流量 (bytes/s)
    per_broker_network = total_replication / num_brokers
    
    # 建议 Partition 数 (假设单 Partition 20MB/s)
    recommended_partitions = int(ingress_bytes / (20 * 1024 * 1024))
    
    return {
        'total_disk_gb': total_disk_gb,
        'per_broker_disk_gb': per_broker_disk_gb,
        'per_broker_network_mbps': per_broker_network * 8 / (1024 * 1024),
        'recommended_partitions': recommended_partitions
    }

# 悦茶的规划
result = calculate_capacity(
    tps=65000,           # 5000+50000+10000
    msg_size_bytes=500,  # 加权平均
    retention_days=7,
    replication_factor=3,
    num_brokers=5
)
# 结果:

```

- 磁盘使用率超过 80% 后性能急剧下降，悦茶告警阈值设为 70%。
- 加分回答：Kafka 的容量不是线性扩展的——增加 Broker 后，Partition 需要重新分配，且 Controller 的管理压力增大。建议 Broker 数量不超过 50 台（KRaft 模式下可支持到几百台）。

**Kafka Streams 实时聚合示例**：

```java
// 实时销售看板
StreamsBuilder builder = new StreamsBuilder();

KStream<String, OrderEvent> orders = builder.stream("order-events");

// 按门店聚合（1分钟滚动窗口）
KTable<Windowed<String>, SalesSummary> salesByStore = orders
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
    .aggregate(
        SalesSummary::new,
        (storeId, order, summary) -> summary.add(order),
        Materialized.with(Serdes.String(), salesSummarySerde)
    );

salesByStore.toStream().to("realtime-sales");

// 按品类聚合（5分钟滚动窗口）
KTable<Windowed<String>, Long> salesByCategory = orders
    .groupBy((key, order) -> order.getCategory())
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
    .count();

salesByCategory.toStream().to("category-sales");
```

**⚠️ 常见坑/加分回答：**

- 悦茶在架构设计初期 Partition 数量设得太少（每个 Topic 3 个分区），后来扩容导致 Key 哈希变化。建议**一开始就按峰值预留分区数**。
- Kafka Streams 的 State Store（RocksDB）在数据量大时内存占用很高。悦茶通过 `statestore.cache.max.bytes=10485760`（10MB）控制缓存，并监控 RocksDB 的 Block Cache 使用率。
- 悦茶的全链路压测：在生产环境模拟 5 倍流量，验证 Kafka 集群的承压能力。关键指标：Consumer Lag 增长率、Broker CPU 使用率、磁盘写入速率。
- 加分回答：悦茶在 KRaft 模式下使用 Kraft 的 Metadata Quorum 监控 API 来检测 Controller 的健康状态，替代了传统的 ZK 监控。
