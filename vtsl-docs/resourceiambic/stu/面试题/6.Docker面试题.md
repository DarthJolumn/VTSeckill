# Docker面试题·带实例源码版（30集完整内容）

## 第1系列：容器基础与Linux内核原理

### 第1集：容器的本质是什么？和虚拟机有什么区别？Namespace 的六种隔离机制

**💡 核心回答：**

容器的本质是**被 Namespace 和 Cgroups 限制的 Linux 进程**。容器并不是一套独立的操作系统，而是一个（或一组）运行在宿主机上、被 Linux 内核的 Namespace 机制隔离了视野、被 Cgroups 限制了资源用量的普通进程。

容器与虚拟机的核心区别：

| 维度 | 容器 | 虚拟机 |
|------|------|--------|
| 隔离级别 | 进程级（共享宿主机内核） | 硬件级（独立内核） |
| 启动速度 | 毫秒级 | 秒~分钟级 |
| 资源占用 | MB 级 | GB 级 |
| 性能损耗 | 近乎零 | 5%~30% |
| 隔离强度 | 较弱（共享内核，存在逃逸风险） | 较强（Hypervisor 隔离） |
| 密度 | 单机可跑数百容器 | 单机通常几十个 VM |

**Linux Namespace 的六种隔离机制：**

| Namespace | 系统调用标志 | 隔离内容 |
|-----------|-------------|---------|
| PID | `CLONE_NEWPID` | 进程 ID 命名空间，容器内进程 PID 从 1 开始 |
| Network | `CLONE_NEWNET` | 网络设备、IP 地址、端口、iptables 规则 |
| Mount | `CLONE_NEWNS` | 文件系统挂载点，容器看到独立的文件系统视图 |
| UTS | `CLONE_NEWUTS` | 主机名和域名 |
| IPC | `CLONE_NEWIPC` | 进程间通信（消息队列、信号量、共享内存） |
| User | `CLONE_NEWUSER` | 用户和组 ID 映射（容器内 root ≠ 宿主机 root） |

此外还有 Cgroup Namespace（`CLONE_NEWCGROUP`），隔离 Cgroup 视图。

**📦 实际例子：**

悦茶奶茶平台的订单服务（order-service）部署在容器中。当运维人员进入容器执行 `ps aux` 时，只能看到容器内的进程（Java 进程 PID 为 1），看不到宿主机上的其他几百个进程——这就是 PID Namespace 的隔离效果。

```bash
# 在宿主机上，订单服务容器的 Java 进程实际 PID 是 28394
$ ps aux | grep order-service
root  28394  3.2  12.5  java -jar order-service.jar

# 进入容器后，看到的是 PID 1
$ docker exec -it order-service ps aux
PID   USER     TIME  COMMAND
1     app      0:45  java -jar order-service.jar
```

悦茶的监控服务容器和订单服务容器各自拥有独立的 Network Namespace，所以两边都可以监听 8080 端口而不冲突——因为它们在不同的网络命名空间中。

**🔍 源码解析：**

容器创建的核心系统调用是 `clone()`。在 Linux 内核中，`clone()` 系统调用通过标志位决定共享哪些资源：

```go
// runtime 层（runc）调用 clone 的简化伪代码
// 源码参考：github.com/opencontainers/runc/libcontainer/system/linux.go
func CloneFlags() uintptr {
    return syscall.CLONE_NEWPID |    // PID Namespace
           syscall.CLONE_NEWNS |     // Mount Namespace
           syscall.CLONE_NEWNET |    // Network Namespace
           syscall.CLONE_NEWIPC |    // IPC Namespace
           syscall.CLONE_NEWUTS      // UTS Namespace
}
```

在内核层面，`kernel/fork.c` 中的 `copy_namespaces()` 函数负责为新进程创建独立的命名空间：

```c
// Linux 内核 kernel/fork.c（简化）
int copy_namespaces(unsigned long flags, struct task_struct *tsk)
{
    struct nsproxy *old_ns, *new_ns;
    
    old_ns = tsk->nsproxy;
    new_ns = create_new_namespaces(flags, tsk, old_ns);
    // 为每个 namespace 类型调用对应的 create 函数：
    // - copy_mnt_ns()     -> Mount Namespace
    // - copy_pid_ns()     -> PID Namespace
    // - copy_net_ns()     -> Network Namespace
    // - copy_ipc_ns()     -> IPC Namespace
    // - copy_uts_ns()     -> UTS Namespace
    // - copy_user_ns()    -> User Namespace
    
    tsk->nsproxy = new_ns;
    return 0;
}
```

PID Namespace 的实现在 `kernel/pid.c` 中，每个 PID Namespace 维护一棵独立的 PID 树（`struct pid_namespace`），容器内的 PID 1 对应宿主机上的一个真实 PID，形成了嵌套的 PID 映射关系：

```c
// kernel/pid_namespace.h
struct pid_namespace {
    struct kref kref;           // 引用计数
    struct idr idr;             // PID 分配器
    struct rcu_head rcu;        // RCU 回收
    unsigned int pid_allocated; // 已分配 PID 数
    int last_pid;               // 最后分配的 PID
    unsigned int level;         // 嵌套层级（0=初始命名空间）
    struct pid_namespace *parent; // 父命名空间
};
```

**⚠️ 常见坑/加分回答：**

1. **PID 1 问题**：容器内的 PID 1 进程必须能处理 `SIGTERM` 和 `SIGCHLD` 信号。很多应用默认不处理这些信号，导致容器无法正常关闭。悦茶的 Java 服务在 Dockerfile 中使用了 `exec` 形式而非 shell 形式来启动，确保 Java 进程成为 PID 1：
   ```dockerfile
   # 正确方式：Java 进程直接成为 PID 1
   CMD ["java", "-jar", "order-service.jar"]
   
   # 错误方式：shell 作为 PID 1，Java 进程是 shell 的子进程
   CMD java -jar order-service.jar
   ```

2. **User Namespace 的坑**：启用 User Namespace 后，容器内的 root（UID 0）会映射到宿主机的非特权用户（如 UID 100000），这提高了安全性，但会导致文件权限问题——容器内创建的文件在宿主机上看是 100000 拥有的。

3. **加分回答**：可以提到 Linux 5.6+ 引入的 `pidfd`（PID 文件描述符），解决了 PID 复用导致的竞态条件问题。在容器密集调度场景中，`pidfd` 可以安全地引用容器进程而不担心 PID 被回收后重新分配。

### 第2集：Cgroups 资源限制的原理：CPU、Memory、IO 的限制方式和参数

**💡 核心回答：**

Cgroups（Control Groups）是 Linux 内核提供的资源限制、优先级控制和用量统计机制。它通过将进程分组（cgroup），对每组进程施加 CPU、内存、IO 等资源的限制。

**三大核心限制能力：**

| 资源类型 | 主要控制参数 | 效果 |
|---------|-------------|------|
| CPU | `cpu.shares`、`cpu.cfs_quota_us`/`cpu.cfs_period_us`、`cpuset.cpus` | 限制 CPU 使用比例、硬性配额、绑核 |
| 内存 | `memory.limit_in_bytes`、`memory.soft_limit_in_bytes`、`memory.swap.max` | 硬限制、软限制、Swap 控制 |
| IO | `blkio.throttle.read_bps_device`、`blkio.throttle.write_bps_device` | 限制读写速率和 IOPS |

**Cgroup v1 vs Cgroup v2：**

| 特性 | Cgroup v1 | Cgroup v2（统一层级） |
|------|----------|---------------------|
| 层级结构 | 每个子系统独立层级 | 所有子系统共享统一层级 |
| 接口 | 多文件、每控制器一个目录 | 统一文件（如 `cpu.max`、`memory.max`） |
| 压力监控 | 无 | 内建 PSI（Pressure Stall Information） |
| Linux 版本 | 2.6.24+ | 4.5+，5.0+ 成熟 |

**📦 实际例子：**

悦茶奶茶平台的订单服务在高峰时段（如新品上线秒杀）CPU 和内存消耗激增。为了防止某个容器吃掉整台机器资源，运维为每个容器设置了资源限制：

```bash
# 订单服务：限制 2 核 CPU、4GB 内存
docker run -d \
  --name order-service \
  --cpus=2 \                    # 等价于 cpu.cfs_quota=200000, cpu.cfs_period=100000
  --memory=4g \                 # 内存硬限制 4GB
  --memory-swap=4g \            # 禁用 Swap（防止 OOM 后性能骤降）
  --cpu-shares=1024 \           # CPU 权重（默认值）
  --restart=on-failure:3 \
  yuecha/order-service:latest
```

悦茶的 Redis 缓存服务对 IO 敏感，设置了 IO 限制防止日志写入抢占磁盘带宽：

```bash
# 获取磁盘设备号
$ stat -c "%t:%T" /dev/sda
08:00  # 主设备号:次设备号 = 8:0

# 限制 Redis 容器磁盘读取速率为 50MB/s
docker run -d \
  --name redis-cache \
  --device-read-bps=/dev/sda:50mb \
  --device-write-bps=/dev/sda:30mb \
  redis:7-alpine
```

**🔍 源码解析：**

Cgroups 在 Docker 中的集成路径是 `libcontainer`。当 runc 创建容器时，调用 `libcontainer/cgroups` 包写入 Cgroup 文件系统：

```go
// 源码参考：github.com/opencontainers/runc/libcontainer/cgroups/fs/cpu.go
// Cgroup v1 CPU 配额设置
func (s *CpuGroup) Set(path string, cgroup *configs.Cgroup) error {
    // 设置 CPU 硬限制（CFS 调度器）
    // cpu.cfs_period_us 默认 100000 微秒（100ms）
    // cpu.cfs_quota_us = cpus * 100000
    if cgroup.Resources.CpuQuota != 0 {
        if err := writeFile(path, "cpu.cfs_quota_us", 
            strconv.FormatInt(cgroup.Resources.CpuQuota, 10)); err != nil {
            return err
        }
    }
    
    // 设置 CPU 权重（shares），影响 CPU 竞争时的优先级
    if cgroup.Resources.CpuShares != 0 {
        if err := writeFile(path, "cpu.shares",
            strconv.FormatInt(cgroup.Resources.CpuShares, 10)); err != nil {
            return err
        }
    }
    return nil
}
```

Cgroup v2 的内存限制实现（`memory.max` 文件）：

```go
// 源码参考：github.com/opencontainers/runc/libcontainer/cgroups/fs2/memory.go
func (m *Manager) setMemory(path string, cgroup *configs.Cgroup) error {
    // Cgroup v2: 统一接口 memory.max
    if cgroup.Resources.Memory != 0 {
        val := strconv.FormatInt(cgroup.Resources.Memory, 10)
        if val == "0" || val == "-1" {
            val = "max"  // v2 中用 "max" 表示无限制
        }
        if err := os.WriteFile(filepath.Join(path, "memory.max"), 
            []byte(val+"\n"), 0644); err != nil {
            return err
        }
    }
    return nil
}
```

Linux 内核中内存 Cgroup 的核心数据结构（`mm/memcontrol.c`）：

```c
// Linux 内核 mm/memcontrol.c（简化）

    struct cgroup_subsys_state css;  // Cgroup 子系统状态
    struct page_counter memory;      // 内存用量计数器

    struct page_counter kmem;        // 内核内存计数器
    /* OOM 相关 */
    struct mem_cgroup_thresholds thresholds;
    bool oom_group;                  // 是否为 OOM 组（触发时杀整个组）
    /* 统计 */

// 当进程申请内存时，内核在 page fault 路径中检查限制
// 源码：mm/memcontrol.c -> mem_cgroup_charge()
int mem_cgroup_charge(struct folio *folio, struct mm_struct *mm, gfp_t gfp)
{
    // 1. 找到当前进程所属的 mem_cgroup
    // 2. 尝试增加内存计数器
    // 3. 如果超过 memory.max，触发直接回收（direct reclaim）
    // 4. 如果回收后仍超限，触发 OOM Killer
}
```

**⚠️ 常见坑/加分回答：**

1. **OOM Killed 排查**：悦茶的商品搜索服务曾因 Elasticsearch 堆内存设置不当，被 Cgroup 的内存限制触发 OOM Killer。排查命令：
   ```bash
   # 查看容器 OOM 事件
   docker inspect --format='{{.State.OOMKilled}}' product-search
   # 查看 dmesg 中的 OOM 日志
   dmesg | grep -i "oom\|killed process"
   ```

2. **CPU 节流（Throttling）陷阱**：设置 `--cpus=2` 后，即使用宿主机 CPU 利用率很低，容器也最多用 2 核。`cpu.shares` 只影响竞争时的权重分配，空闲时容器可以用更多 CPU。悦茶的批处理任务用 `--cpus` 限制，实时服务用 `--cpu-shares` 保证优先级。

3. **Cgroup v2 的 `memory.low` 保护**：悦茶生产环境使用 `memory.low`（软保护）而非 `memory.high`（硬节流），避免突发流量时被过早节流：
   ```bash
   # memory.low = 2G（保证至少能用 2G）
   # memory.high = 6G（超过后节流但不杀进程）
   # memory.max = 8G（绝对上限）
   ```

4. **加分回答**：提到 PSI（Pressure Stall Information）——Cgroup v2 内建的性能指标，可以直接观测 CPU/Memory/IO 的等待时间，比传统指标更精确地反映容器压力。

### 第3集：UnionFS 联合文件系统：Overlay2 驱动的分层原理，镜像层和容器层的关系

**💡 核心回答：**

UnionFS（联合文件系统）是 Docker 镜像分层的核心技术。Overlay2 是 Docker 当前默认的存储驱动，它将多个目录（层）叠加挂载到一个统一的文件系统视图中。

**核心概念：**

- **镜像层（Image Layers）**：只读层，每个 Dockerfile 指令生成一层
- **容器层（Container Layer）**：可写层，位于最顶部，容器的文件修改都发生在这里
- **Copy-on-Write（CoW）机制**：读取文件时从底层往上查找；写入文件时，如果文件在只读层，先复制到可写层再修改
- **Whiteout 文件**：删除底层文件时，在可写层创建一个 `.wh.filename` 标记文件来"遮住"原文件

**Overlay2 的目录结构：**

```
/var/lib/docker/overlay2/
├── <layer-id>/          # 每一层一个目录
│   ├── diff/            # 该层的实际文件内容（差异数据）
│   ├── link/            # 层的短名称链接
│   ├── lower/           # 指向 lowerdir 的挂载点
│   ├── lower-id         # 下一层的 ID
│   ├── merged/          # 合并后的完整视图（容器看到的）
│   └── work/            # OverlayFS 内部工作目录
```

**📦 实际例子：**

悦茶奶茶平台的商品服务镜像有 5 层：

```dockerfile
# 第1层：基础 OS（ubuntu:22.04）— 约 77MB
FROM ubuntu:22.04

# 第2层：安装 JDK — 约 300MB
RUN apt-get update && apt-get install -y openjdk-17-jdk

# 第3层：创建应用目录和用户
RUN groupadd -r yuecha && useradd -r -g yuecha app

# 第4层：COPY 应用 jar 包 — 约 85MB
COPY target/product-service.jar /app/product-service.jar

# 第5层：设置启动命令
CMD ["java", "-jar", "/app/product-service.jar"]
```

当悦茶的 10 个微服务都基于同一个 JDK 基础镜像时，第 1、2、3 层在磁盘上只存储一份（通过层 ID 共享），只有第 4、5 层每个服务不同。这大大节省了磁盘空间。

```bash
# 查看镜像的分层
$ docker history yuecha/product-service:latest
IMAGE          CREATED       SIZE      COMMENT
abc123         2 hours ago   85MB      COPY target/product-service.jar ...
def456         2 hours ago   0B        CMD ["java" ...]
ghi789         2 hours ago   0B        RUN groupadd ...
jkl012         2 hours ago   300MB     RUN apt-get install ...
mno345         3 days ago    77MB      ubuntu:22.04 base
```

容器启动后，悦茶的商品服务在运行时缓存了热点数据到 `/tmp/cache/`，这些文件只存在于容器的可写层（最顶层），不会影响底层镜像。

**🔍 源码解析：**

Overlay2 的挂载参数在内核中由 `fs/overlayfs/` 目录实现：

```c
// Linux 内核 fs/overlayfs/super.c（简化）
// OverlayFS 的挂载函数
static int ovl_fill_super(struct super_block *sb, void *data, int silent)
{
    // 解析挂载参数：lowerdir, upperdir, workdir
    // lowerdir: 只读层列表（冒号分隔，可以是多层）
    // upperdir: 可写层（容器的 diff 目录）
    // workdir:  工作目录（必须在同一文件系统上）
    
    struct ovl_config config;
    config.lowerdir = ...;  // 如 "layer3:layer2:layer1"
    config.upperdir = ...;  // 如 "/var/lib/docker/overlay2/xxx/diff"
    config.workdir = ...;   // 如 "/var/lib/docker/overlay2/xxx/work"
    
    // 创建根 dentry，设置 overlay 文件系统操作
    sb->s_root = d_make_root(ovl_dentry);
    sb->s_op = &ovl_super_operations;
    // 设置 dentry 操作（lookup, open, readdir 等）
    // 这些操作决定了如何跨层查找文件
}
```

Overlay2 的文件查找流程（`fs/overlayfs/inode.c`）：

```c
// 文件查找：从顶层到底层逐层搜索
// 源码参考：fs/overlayfs/dir.c -> ovl_lookup()
static struct dentry *ovl_lookup(struct inode *dir, struct dentry *dentry,
                                  unsigned int flags)
{
    // 1. 先在 upperdir（可写层）查找
    struct dentry *upper = lookup_one_len(upperdir, name);
    if (upper && d_is_positive(upper)) {
        // 找到了，同时检查是否有 whiteout 标记
        return ovl_dentry;
    }
    
    // 2. 检查 whiteout：upper 层有 .wh.filename 表示底层文件已被删除
    if (ovl_is_whiteout(upper)) {
        return ERR_PTR(-ENOENT);  // 文件不存在
    }
    
    // 3. 在 lowerdir（只读层，从新到旧逐层查找）
    for (i = 0; i < numlower; i++) {
        struct dentry *lower = lookup_one_len(lowerdirs[i], name);
        if (lower && d_is_positive(lower)) {
            // 找到后创建 overlay inode，关联到实际的下层 inode
            return ovl_dentry;
        }
    }
    
    return ERR_PTR(-ENOENT);
}
```

Copy-on-Write 的实现（`fs/overlayfs/copy_up.c`）：

```c
// 当容器要修改只读层文件时触发 copy-up
// 源码：fs/overlayfs/copy_up.c -> ovl_copy_up()
int ovl_copy_up(struct dentry *dentry)
{
    // 1. 打开下层文件（只读）
    struct file *lower_file = ovl_path_open(lower_path, O_RDONLY);
    
    // 2. 在上层创建新文件（可写）
    struct file *upper_file = ovl_path_open(upper_path, O_WRONLY|O_CREAT);
    
    // 3. 拷贝数据（通过 sendfile 或循环读写）
    // 4. 拷贝元数据（权限、时间戳、xattr）
    ovl_copy_xattr(lower, upper);
    
    // 5. 替换 dentry 的关联，后续访问指向上层文件
}
```

Docker daemon 层管理（`daemon/graphdriver/overlay2/overlay2.go`）：

```go
// 源码参考：github.com/moby/moby/daemon/graphdriver/overlay2/overlay2.go
func (d *Driver) CreateReadWrite(id, parent string, opts ...) error {
    // 1. 创建容器层的目录结构
    dir := d.dir(id)
    // /var/lib/docker/overlay2/<id>/
    //   ├── diff/    (可写层)
    //   ├── link/
    //   ├── merged/  (挂载点)
    //   └── work/
    
    // 2. 构建 lowerdir 参数（所有只读层，从新到旧）
    lowerDirs := d.getLowerDirs(parent)
    
    // 3. 执行 mount 系统调用
    // mount -t overlay overlay \
    //   -o lowerdir=<layer3>:<layer2>:<layer1>,upperdir=<id>/diff,workdir=<id>/work \
    //   <id>/merged
    mountLabel := label.FormatMountLabel("", mountOpts)
    return mount.Mount("overlay", mergedDir, "overlay", mountLabel)
}
```

**⚠️ 常见坑/加分回答：**

1. **层数限制**：Overlay2 最多支持 128 个 lowerdir（Linux 4.x 之前是 5000 个字符的路径长度限制）。悦茶的基础镜像团队控制镜像层数在 10 层以内。

2. **Copy-Up 性能问题**：大文件即使只修改一个字节，也会完整复制到上层。悦茶的视频素材文件（产品宣传图）不应放在只读层然后修改，而应直接挂载 Volume。

3. **磁盘空间排查**：
   ```bash
   # 查看每层占用的空间
   docker system df -v
   # 清理悬空镜像和停止的容器
   docker system prune -a --volumes
   ```

4. **加分回答**：提到 Overlay2 的 `metacopy` 特性（Linux 4.19+），只修改元数据（如 chmod）时不需要 copy-up 整个文件，只复制元数据到上层，大幅减少 I/O。

### 第4集：容器网络模型：Bridge、Host、None、Overlay 四种模式的原理和适用场景

**💡 核心回答：**

Docker 提供四种核心网络模式，通过 `--network` 参数指定：

| 模式 | 原理 | 适用场景 |
|------|------|---------|
| Bridge | 容器连接到 Docker 虚拟网桥 `docker0`，通过 NAT 访问外网 | 默认模式，单机多容器通信 |
| Host | 容器共享宿主机网络命名空间，直接使用宿主机端口 | 高性能场景，如监控 Agent |
| None | 容器没有网络接口（只有 lo），完全网络隔离 | 高安全要求场景，如离线计算 |
| Overlay | 跨主机容器通信，基于 VXLAN 隧道封装 | Docker Swarm 多机部署 |

**Bridge 模式详解：**

创建容器时，Docker daemon 会：
1. 创建一对 veth 设备（虚拟网线）
2. 一端（`eth0`）放入容器的 Network Namespace
3. 另一端（`vethXXXX`）连接到 `docker0` 网桥
4. 为容器分配 IP（如 `172.17.0.2/16`）
5. 配置 iptables NAT 规则，实现端口映射和外网访问

**📦 实际例子：**

悦茶奶茶平台的微服务在单机部署时采用自定义 Bridge 网络。订单服务、商品服务、用户服务放在同一个 `yuecha-net` 网络中，通过服务名互相访问：

```bash
# 创建自定义网络（DNS 解析支持容器名）
docker network create --driver bridge --subnet 10.10.0.0/16 yuecha-net

# 启动各服务
docker run -d --name order-service --network yuecha-net \
  --ip 10.10.0.2 -p 8080:8080 yuecha/order-service

docker run -d --name product-service --network yuecha-net \
  --ip 10.10.0.3 -p 8081:8080 yuecha/product-service

docker run -d --name redis --network yuecha-net \
  --ip 10.10.0.10 redis:7

# 容器内通过服务名访问（Docker 内建 DNS 解析）
# order-service 中访问 redis://redis:6379
# order-service 中访问 http://product-service:8080/api/products
```

悦茶的主机上运行了 node-exporter（Prometheus 监控采集器），使用 Host 模式以避免网络开销：

```bash

  prom/node-exporter:latest
# 直接通过宿主机 9100 端口访问，无需端口映射
```

```go
func (d *driver) CreateNetwork(id string, options map[string]interface{}) error {

    bridgeName := config.BridgeName  // 默认 "docker0" 或自定义名

    addr, _ := netlink.ParseAddr(config.FixedCIDR)
    netlink.AddrAdd(link, addr)
    
    // 4. 启动 bridge 设备
    netlink.LinkSetUp(link)
    
    // 5. 配置 iptables NAT 规则（MASQUERADE）
    // iptables -t nat -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
```

```go
    // 创建 veth pair
    vethPair := &netlink.Veth{
        LinkAttrs: netlink.LinkAttrs{Name: "veth" + id[:5]},
```

```go
func setupIPTables(config *networkConfiguration) error {
    // 1. SNAT（容器访问外网）
    // iptables -t nat -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
    
    // 2. DNAT（外部访问容器映射端口）
    // 假设 -p 8080:80 的端口映射
    // iptables -t nat -A DOCKER -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
    
    // 3. FORWARD 规则（允许容器间通信）
    // iptables -A FORWARD -i docker0 -o docker0 -j ACCEPT
    
    // 4. 容器隔离（不同 network 间的隔离）
    // iptables -A DOCKER-USER -i docker0 ! -o docker0 -j ACCEPT
    // iptables -A FORWARD -j DOCKER-USER
}
```

**⚠️ 常见坑/加分回答：**

1. **Bridge 模式的 DNS 坑**：默认 `docker0` 网桥不支持容器名 DNS 解析，必须创建自定义 Bridge 网络。悦茶早期踩了这个坑，订单服务通过 IP 访问 Redis，IP 变化后服务中断。改用自定义网络后，通过服务名访问解决了问题。

2. **Host 模式端口冲突**：使用 Host 模式的容器直接占用宿主机端口，多个容器不能监听同一端口。悦茶的监控 Agent 统一使用 Host 模式，端口规划在 9000-9999 段。

3. **iptables 规则冲突**：Docker 会修改宿主机的 iptables 规则，可能与其他防火墙工具（如 firewalld、ufw）冲突。生产环境建议将 Docker 相关规则链（DOCKER、DOCKER-USER）放在自定义规则之前。

4. **加分回答**：提到 Cilium（基于 eBPF 的 CNI 插件），它绕过了 iptables，用 eBPF 程序在内核层面处理网络策略和负载均衡，性能更高、可观测性更强。悦茶正在评估从 Docker 原生网络迁移到 Cilium。

## 第2系列：镜像与Dockerfile

### 第5集：Docker 镜像的分层结构：每一层是什么、怎么共享、COPY vs ADD 的区别

**💡 核心回答：**

Docker 镜像由多个**只读层**（Layer）堆叠而成，每一层对应 Dockerfile 中的一条指令（`FROM`、`RUN`、`COPY`、`ADD`、`ENV`、`EXPOSE` 等会生成层；`CMD`、`ENTRYPOINT` 等元数据指令不生成层）。

**分层的核心机制：**

1. **每层是一个 diff**：只记录该层相对于上一层的文件变化（新增、修改、删除）
2. **层通过 ChainID 关联**：每层的 ID 是基于其内容和父层 ID 计算出的 SHA256 哈希
3. **层共享**：多个镜像可以共享相同的底层。如果悦茶的订单服务和商品服务都基于同一个 JDK 基础镜像，基础镜像的层在磁盘上只存一份
4. **引用计数**：每层被多个镜像引用时，通过引用计数管理，只有引用归零才会被清理

**COPY vs ADD 的区别：**

| 特性 | COPY | ADD |
|------|------|-----|
| 基本功能 | 复制本地文件到镜像 | 同 COPY，但额外支持自动解压 tar、远程 URL |
| URL 下载 | ❌ 不支持 | ✅ 支持从 URL 下载文件（但不会解压） |
| Tar 解压 | ❌ 原样复制 | ✅ 自动解压 tar/tar.gz 到目标路径 |
| 安全性 | 更安全（行为可预测） | 可能引入意外（URL 内容不可控） |
| 最佳实践 | **推荐使用** | 仅在需要自动解压时使用 |

**📦 实际例子：**

悦茶的商品服务 Dockerfile，展示了分层的实际效果：


镜像层的构建过程在 Docker daemon 的 `builder` 模块中：

```go
// 源码参考：github.com/moby/moby/builder/dockerfile/dispatchers.go
// COPY 指令的实现
func dispatchCopy(d *dispatchOptions, cfg *instructions.CopyCommand) error {
    // 1. 解析源路径和目标路径
    sources := cfg.SourcesAndDest()
    
    // 2. 构建上下文 tar 流
    // 每个 RUN/COPY 指令会创建一个新的容器（临时），
    // 在该容器中执行操作，然后将文件系统变化提交为新层
    imgMountID, err := d.builder.storage.CreateRWLayer("")
    
    // 3. COPY 操作：从构建上下文复制文件到容器的挂载点
    for _, src := range sources.Sources() {
        srcPath := filepath.Join(d.builder.context, src)
        // 支持通配符匹配
        matches, _ := filepath.Glob(srcPath)
        for _, match := range matches {
            // 复制文件到 rw layer 的挂载点
            copyFile(match, filepath.Join(imgMountID, dest))
        }
    }
    
    // 4. ADD 额外处理：检查是否为 tar 或 URL
    if cfg.IsAdd() {
        for _, src := range sources.Sources() {
            if isURL(src) {
                // 下载文件
                downloadFile(src, dest)
            } else if isArchive(src) {
                // 自动解压 tar
                extractTar(src, dest)
            }
        }
    }
    
    // 5. 提交为新层
    layerID, err := d.builder.storage.CommitRWLayer(imgMountID)
    return nil
}
```

层的 ChainID 计算（`layer/mounted_layer.go`）：

```go
// 源码参考：github.com/moby/moby/layer/layer_store.go
// ChainID = SHA256(parentChainID + ":" + diffID)
func (ls *layerStore) Register(ts io.Reader, parent ChainID) (Layer, error) {
    // diffID 是层内容的 SHA256（解压后的 tar 内容的哈希）
    digester := canonical.NewDigester()
    tr := io.TeeReader(ts, digester.Hash())
    
    diffID := ChainID(digester.Digest())
    
    var chainID ChainID
    if parent == "" {
        // 顶层：ChainID = DiffID
        chainID = diffID
    } else {
        // 非顶层：ChainID = SHA256(parentChainID + ":" + diffID)
        hash := sha256.New()
        hash.Write([]byte(parent))
        hash.Write([]byte(":"))
        hash.Write([]byte(diffID))
        chainID = ChainID(hex.EncodeToString(hash.Sum(nil)))
    }
    
    // 检查是否已存在相同 ChainID 的层（层共享）
    if existing, ok := ls.layerMap[chainID]; ok {
        existing.references++
        return existing, nil
    }
    
    // 存储层数据
    layer := &roLayer{
        chainID: chainID,
        diffID:  diffID,
        parent:  parent,
        size:    size,
    }
    ls.layerMap[chainID] = layer
    return layer, nil
}
```

**⚠️ 常见坑/加分回答：**

1. **层缓存失效**：Dockerfile 中任何一层变化，后续所有层都要重新构建。悦茶将不常变动的层（安装依赖）放在前面，频繁变动的层（COPY 源码）放在后面，最大化利用构建缓存。

2. **COPY 上下文过大**：`COPY . /app` 会把整个项目目录（包括 `node_modules/`、`.git/`、日志文件等）都发送为构建上下文。悦茶通过 `.dockerignore` 排除不必要的文件：
   ```
   # .dockerignore
   .git
   node_modules
   target/*.log
   *.md
   .env*
   ```

3. **ADD 的安全风险**：`ADD` 下载远程 URL 时不会验证 TLS 证书，也不会缓存（每次构建都重新下载）。生产环境悦茶统一使用 COPY + 预下载的方式。

4. **加分回答**：Docker 17.05+ 支持多阶段构建后，层的概念从"镜像层"扩展为"构建阶段"。每个 `FROM` 开启新阶段，只有最终阶段的层会出现在最终镜像中。

### 第6集：Dockerfile 最佳实践：多阶段构建、层缓存优化、安全扫描、镜像瘦身

**💡 核心回答：**

Dockerfile 最佳实践的核心目标是：**镜像小、构建快、安全、可维护**。

**四大核心实践：**

| 实践 | 目标 | 关键手段 |

多阶段构建的实现在 Docker BuildKit 中：

```go
// 源码参考：github.com/moby/buildkit/frontend/dockerfile/builder/build.go
// BuildKit 的构建流程
func Build(ctx context.Context, opt backend.BuildConfig) error {
    // 1. 解析 Dockerfile，识别所有 FROM 指令
    stages, err := dispatchers.Parse(dockerfile)
    
    // 2. 构建依赖图（DAG）
    // 每个阶段可能依赖其他阶段的产物（COPY --from=xxx）
    dag := buildStageGraph(stages)
    
    // 3. 并行执行无依赖的阶段（BuildKit 支持并发构建）
    for _, stage := range dag.ParallelStages() {
        go func(s *stage) {
            // 为每个阶段创建临时容器
            containerID := createContainer(s.BaseImage)
            // 执行该阶段的所有指令
            for _, cmd := range s.Commands {
                executeInContainer(containerID, cmd)
            }
        }(stage)
    }
    
    // 4. 最终阶段：只导出最终阶段的文件系统
    // COPY --from=builder 只会从指定阶段提取需要的文件
    exportLayer(finalStage, outputPath)
}
```

BuildKit 的缓存机制（`cache` 包）：

```go
// 源码参考：github.com/moby/buildkit/solver/llbsolver/ops/exec.go
// BuildKit 使用内容寻址缓存
func (e *execOp) CacheMap(ctx context.Context, g session.Group, index int) (*digest.Digest, error) {
    // 缓存键 = hash(指令内容 + 输入文件内容 + 环境变量)
    h := sha256.New()
    h.Write([]byte(e.op.GetExec().GetMount()))  // 挂载配置
    h.Write([]byte(e.op.GetExec().GetMeta().GetArgs())) // 命令参数
    
    // 如果输入文件内容没变，缓存键不变，直接使用缓存
    for _, input := range e.inputs {
        inputDigest := input.CacheKey()
        h.Write(inputDigest)
    }
    
    digest := digest.NewDigest(h)
    
    // 检查缓存是否存在
    if cached, ok := e.cacheManager.Lookup(digest); ok {
        return cached, nil  // 使用缓存，跳过执行
    }
    
    return &digest, nil  // 无缓存，需要执行
}
```

### 第7集：镜像仓库（Registry）的工作原理：Pull/Push 流程、镜像签名与内容寻址

**💡 核心回答：**

Docker Registry 是存储和分发 Docker 镜像的服务。Docker Hub 是默认的公共 Registry，企业内部通常搭建私有 Registry（如 Harbor）。

**核心概念：**

| 概念 | 说明 |
|------|------|
| Repository | 同名镜像的集合（如 `yuecha/order-service`），不同 Tag 指向不同 manifest |
| Tag | 人类可读的版本标签（如 `v1.2.3`、`latest`），指向一个 manifest |
| Manifest | 描述镜像元数据和层列表的 JSON 文档 |
| Digest | 镜像内容的 SHA256 哈希（内容寻址），如 `sha256:abc123...` |
| Blob | 镜像层的实际数据（压缩的 tar 包） |

**Pull 流程：**

1. Docker 客户端向 Registry 请求 manifest：`GET /v2/<name>/manifests/<reference>`
2. Registry 返回 manifest JSON（包含各层的 digest 和大小）
3. 客户端对比本地已有层，只下载缺失的层：`GET /v2/<name>/blobs/<digest>`
4. 层数据下载完成后，组合成完整的镜像

**Push 流程：**

1. 客户端上传每一层 blob：`POST /v2/<name>/blobs/uploads/` → `PUT`
2. 上传 manifest：`PUT /v2/<name>/manifests/<tag>`
3. Registry 验证 manifest 中引用的所有 blob 都存在

**内容寻址（Content-Addressable）：**

镜像的 Digest 是基于内容的哈希。只要镜像内容不变，Digest 就不变。这意味着：
- 同一个镜像不可能被篡改（改了内容 Digest 就变了）
- 可以用 Digest 精确引用镜像版本（比 Tag 更可靠）

**📦 实际例子：**

```go
func (im *imageManifests) Get(ctx context.Context, dgst digest.Digest) (*manifest.Descriptor, error) {
    // 1. 从存储后端加载 manifest
    // 存储后端可以是文件系统、S3、OSS 等
    manifestContent, err := im.blobStore.Get(dgst)
    
    // 2. 解析 manifest
    m, desc, err := manifest.UnmarshalManifest(manifestContent)
    
    // 3. 返回 manifest 描述符
    return desc, nil
}

// Push 流程的 Blob 上传
func (bs *blobStore) Create(ctx context.Context) (BlobWriter, error) {
    // 1. 生成 upload UUID
    uploadID := uuid.New().String()
    
    // 2. 创建临时写入器（先写到临时目录）
    writer := &blobWriter{
        uploadID: uploadID,
        file:     os.CreateTemp(bs.tmpDir, "upload-"),
    }
    
    // 3. 客户端分块上传数据
    // 每块数据写入临时文件
    
    return writer, nil
}

func (bw *blobWriter) Commit(ctx context.Context, desc distribution.Descriptor) (distribution.BlobDescriptor, error) {
    // 1. 计算上传内容的 Digest
    actualDigest := sha256.Sum256(bw.buf.Bytes())
    
    // 2. 验证 Digest 匹配（内容寻址）
    if actualDigest != desc.Digest {
        return BlobDescriptor{}, ErrDigestMismatch
    }
    
    // 3. 将数据从临时目录移动到正式存储
    // 存储路径：/blobs/sha256/ab/abcdef1234567890...
    finalPath := path.Join(bw.store.blobDir, 
        string(actualDigest[:6]),  // 前6位作为目录
        string(actualDigest))
    os.Rename(bw.file.Name(), finalPath)
    
    return BlobDescriptor{Digest: actualDigest, Size: bw.written}, nil
}
```

```go
// Docker Content Trust 使用 Notary 进行镜像签名
func SignImage(imageRef string, signer *Signer) error {
    // 1. 计算镜像 manifest 的 Digest
    manifest, _ := getManifest(imageRef)
    digest := manifest.Digest()
    
    // 2. 用私钥签名
    signature, err := signer.Sign(digest)
    
    // 3. 将签名上传到 Notary Server
    // 签名存储在 TUF（The Update Framework）格式中
    notaryClient.PublishTarget(imageRef, Target{
        Digest: digest,
        Signature: signature,
        Signer: signer.Name(),
    })
}

// 客户端拉取时验证签名
func PullWithVerification(imageRef string, trust bool) error {
    if trust {
        // DOCKER_CONTENT_TRUST=1 时
        // 1. 从 Notary Server 获取签名
        sig, err := notaryClient.GetTarget(imageRef)
        // 2. 用公钥验证签名
        verified := signer.Verify(digest, sig)
        if !verified {
            return ErrUntrustedImage  // 拒绝拉取未签名的镜像
        }
    }
    // 3. 验证通过，正常拉取
    return pullImage(imageRef)
}
```

## 第3系列：容器运行时

### 第9集：Docker 架构演进：Docker Engine → containerd → runc 的分层设计

**💡 核心回答：**

Docker 的架构经历了从单体到分层解耦的演进过程：

| 阶段 | 架构 | 特点 |
|------|------|------|
| Docker Engine（早期） | 单体守护进程（dockerd） | 所有功能在一个进程中，耦合严重 |
| Docker Engine（libcontainer） | dockerd + libcontainer | 容器运行逻辑抽离为库，但仍嵌入在 dockerd 中 |
| Docker 1.11+（containerd） | dockerd → containerd → runc | 三层分离：API/编排/运行时 |
| Docker 20.10+ | dockerd → containerd → runc + shim | 增加 containerd-shim 实现容器生命周期独立于 daemon |

**三层架构的职责：**

| 层级 | 组件 | 职责 |
|------|------|------|
| API/编排层 | Docker Daemon (dockerd) | REST API、镜像构建、网络配置、Volume 管理、插件 |
| 容器管理层 | containerd | 容器生命周期管理、事件通知、镜像分发、网络分配 |
| 运行时层 | runc | 创建和运行容器进程（调用 Namespace/Cgroups） |

**containerd-shim 的作用：**

每个容器对应一个 `containerd-shim` 进程，它是容器和 containerd 之间的中间层：
- 即使 containerd 崩溃重启，容器进程依然运行（shim 保持对容器的父进程关系）
- 收集容器的退出状态和输出，转发给 containerd
- 减少 containerd 的文件描述符占用（shim 持有 FIFO 日志文件句柄）

**📦 实际例子：**

containerd-shim 的实现（关键：为什么容器不随 containerd 崩溃而停止）：

```go
// 源码参考：github.com/containerd/containerd/runtime/v2/shim/shim.go
// shim 的核心设计：双 fork（subreaper）
func serve(ctx context.Context, manager Manager, config Config) error {
    // 1. shim 作为中间层，是容器进程的父进程
    // containerd -> shim -> runc -> 容器进程
    
    // 2. shim 使用 PR_SET_CHILD_SUBREAPER 捕获子进程
    // 即使 containerd 崩溃，shim 仍然是容器的父进程
    syscall.Prctl(syscall.PR_SET_CHILD_SUBREAPER, 1, 0, 0, 0)
    
    // 3. shim 通过 FIFO（命名管道）与 containerd 通信
    // containerd 崩溃后，shim 检测到管道断开
    // 但容器进程不受影响，继续运行
    
    // 4. containerd 重启后，重新连接到已有的 shim
    // shim 通过 /run/containerd/<id>/address 文件暴露自己的地址
    address := filepath.Join("/run/containerd", id, "address")
    
    // 5. shim 持有容器的 stdio FIFO 文件描述符
    // 容器输出不会丢失
    stdout, _ := os.OpenFile("stdout", os.O_WRONLY, 0)
    stderr, _ := os.OpenFile("stderr", os.O_WRONLY, 0)
}
```

runc 的启动流程（最底层的容器创建）：

```go

func (c *Container) start(process *Process) error {
    // 1. 创建 Linux Namespace（通过 clone 系统调用）
    cmd := c.commandTemplate(process, c.initProcess)

    // a. 设置 Hostname（UTS Namespace）
    // b. 配置网络接口（Network Namespace）
    // c. 挂载文件系统（Mount Namespace）
    // d. 设置 Cgroups
    // e. 切换用户（User Namespace，如果启用）
    // f. exec 执行用户指定的命令

    return nil
}
```

**⚠️ 常见坑/加分回答：**

1. **containerd-shim 内存泄漏**：每个容器对应一个 shim 进程（约 10-15MB）。悦茶曾在一台机器上运行 200+ 容器，shim 进程的总内存占用达到 3GB。解决方案是合理控制单机容器数量。

2. **Docker daemon 重启导致 API 短暂不可用**：悦茶的 CI/CD 在构建时如果遇到 daemon 重启，会重试 3 次。

3. **加分回答**：containerd 可以独立于 Docker 使用。悦茶后来迁移到 Kubernetes，K8s 直接使用 containerd 作为运行时（`containerd://1.7.x`），跳过了 Docker daemon 这一层，减少了资源消耗和故障点。

### 第10集：OCI 标准是什么？Runtime Spec 和 Image Spec 的关系

**💡 核心回答：**

OCI（Open Container Initiative）是 Linux 基金会下的开源治理组织，负责制定容器技术的开放标准。OCI 定义了三个核心规范：

| 规范 | 全称 | 定义内容 |
|------|------|---------|
| Runtime Spec | Runtime Specification | 定义如何运行一个容器（运行时配置） |
| Image Spec | Image Specification | 定义容器镜像的格式和内容 |
| Distribution Spec | Distribution Specification | 定义镜像仓库的 API 协议 |

**OCI Runtime Spec（`config.json`）：**

描述容器的运行配置，包括：
- 进程参数（`process.args`、`process.env`、`process.cwd`）
- 资源限制（`linux.resources`：CPU、Memory、PIDs 等）
- Namespace 配置（`linux.namespaces`）
- 设备访问（`linux.devices`）
- Mount 配置（`mounts`）
- Hook（`hooks`：prestart、poststart、prestop）

**OCI Image Spec（`manifest.json` + `config.json`）：**

定义镜像的分发格式：
- Manifest：描述镜像包含哪些层
- Image Config：描述层的应用方式（Entrypoint、Cmd、Env、ExposedPorts 等）
- Layer：每一层的文件系统 tar 包（压缩格式为 gzip/estargz/zstd）

**两者的关系：**

```
Image Spec（描述镜像"是什么"）
    ↓ 解压后
Runtime Spec（描述容器"怎么运行"）
```

镜像的 Image Config 会被转换为 Runtime Spec 的一部分。Docker/containerd 从 Image Spec 提取配置，生成 Runtime Spec，然后交给 runc 执行。

```go
// 源码参考：github.com/containerd/containerd/oci/spec.go
// 从镜像配置生成 OCI Runtime Spec
func GenerateSpec(ctx context.Context, client *Client, container *containers.Container) (*specs.Spec, error) {
    // 1. 加载默认的 OCI Runtime Spec 模板
    s := defaultSpec()
    
    // 2. 从 Image Config 提取配置
    imgConfig := container.Image.Config
    if imgConfig.Env != nil {
        s.Process.Env = imgConfig.Env
    }
    if imgConfig.Entrypoint != nil {
        s.Process.Args = append(imgConfig.Entrypoint, imgConfig.Cmd...)
    }
    if imgConfig.WorkingDir != "" {
        s.Process.Cwd = imgConfig.WorkingDir
    }
    if imgConfig.User != "" {
        uid, gid := parseUser(imgConfig.User)
        s.Process.User.UID = uid
        s.Process.User.GID = gid
    }
    
    // 3. 设置默认 Namespace
    s.Linux.Namespaces = []specs.LinuxNamespace{
        {Type: specs.PIDNamespace},
        {Type: specs.NetworkNamespace},
        {Type: specs.MountNamespace},
        {Type: specs.IPCNamespace},
        {Type: specs.UTSNamespace},
    }
    
    // 4. 设置默认 Mount（/proc, /dev, /dev/pts 等）
    s.Mounts = defaultMounts()
    
    // 5. 应用用户自定义选项（如资源限制、Volume 挂载等）
    for _, opt := range container.Options {
        opt(ctx, client, container, s)
    }
    
    return s, nil
}
```

```go
func CreateLibcontainerConfig(spec *specs.Spec) (*configs.Config, error) {
    config := &configs.Config{
        Rootfs: spec.Root.Path,
    }
    
    // 转换 Namespace 配置

        config.Namespaces.Add(ns.Type, ns.Path)
    }
    
    // 转换资源限制
    if spec.Linux.Resources != nil {
        config.Cgroups.Resources.Memory = spec.Linux.Resources.Memory.Limit
        config.Cgroups.Resources.CpuQuota = spec.Linux.Resources.CPU.Quota
        config.Cgroups.Resources.CpuPeriod = spec.Linux.Resources.CPU.Period
        config.Cgroups.Resources.PidsLimit = spec.Linux.Resources.Pids.Limit

            Device:      m.Type,
            Source:      m.Source,

            Flags:       parseMountOptions(m.Options),
        })
    }

}
```

### 第11集：容器启动的完整流程：docker run → containerd → runc → exec 的调用链

**💡 核心回答：**

执行 `docker run` 时，经过的完整调用链：

```
用户执行 docker run
    ↓
Docker CLI → Docker Daemon（HTTP/REST API）
    ↓
Docker Daemon → containerd（gRPC）
    ↓
containerd → containerd-shim（fork 子进程）
    ↓
containerd-shim → runc（调用 OCI runtime）
    ↓
runc → Linux 内核（clone/fork/exec 系统调用）
    ↓
容器内进程启动（PID 1）
```

**每一步的详细说明：**

| 步骤 | 操作 | 关键行为 |
|------|------|---------|
| 1 | CLI → Daemon | HTTP POST /containers/create + /containers/start |
| 2 | Daemon 准备 | 创建容器元数据、分配 IP、准备 Volume |
| 3 | Daemon → containerd | gRPC：Create container + New task |
| 4 | containerd → shim | fork containerd-shim 进程 |
| 5 | shim → runc | 调用 `runc create`（创建容器但不启动） |
| 6 | runc 配置环境 | 设置 Namespace、Cgroups、Mount、Network |
| 7 | shim 调用 `runc start` | 启动容器内进程 |
| 8 | 容器进程运行 | PID 1 进程开始执行 |

runc create 的内部实现（容器环境初始化）：

```go
// 源码参考：github.com/opencontainers/runc/libcontainer/process_linux.go
func (p *InitProcess) start() error {
    // 1. 创建 pipe 用于父子进程同步
    parentPipe, childPipe, err := newPipe()
    
    // 2. 构建 clone 命令
    cmd := p.cmdTemplate()
    cmd.ExtraFiles = append(cmd.ExtraFiles, childPipe)
    
    // 3. 使用 CLONE_NEW* 标志启动子进程
    // 子进程在 init_linux.go 中的 containerInit() 执行
    cmd.Start()
    
    // 4. 父进程等待子进程完成初始化
    // 子进程会：
    // a. 创建新的 Namespace（clone 系统调用）
    // b. 设置 Cgroups（写入 /sys/fs/cgroup/...）
    // c. 配置根文件系统（pivot_root）
    // d. 设置 hostname、网络接口
    // e. 发送 "ready" 信号给父进程
    
    // 5. 父进程收到 ready 后，将子进程加入 Cgroup
    // （必须先加入 Cgroup，再解除 freeze，防止资源逃逸）
    cgroupManager.Apply(cmd.Process.Pid)
    
    // 6. 解除 freeze（容器进程开始执行）
    cmd.Process.Signal(syscall.SIGCONT)
    
    return nil
}
```

1. **启动慢排查**：悦茶的 Java 服务启动慢，80% 的时间花在 JVM 初始化和 Spring Boot 自动配置上。通过 `-XX:+UseZGC -Xlog:gc*:time` 和 `--spring.lazy-initialization=true` 优化。

2. **PID Namespace 嵌套**：`docker exec` 进入容器时，exec 进程在容器的 PID Namespace 内不是 PID 1。悦茶曾遇到 `docker exec` 进程被误杀导致连接中断的问题。

3. **containerd-shim 调试**：悦茶运维通过 `ctr tasks ls` 和 `ctr events` 直接查看 containerd 的任务状态，比 `docker ps` 更快。

4. **加分回答**：提到 `runc` 的两种模式——`create`（只创建不启动，用于调试）和 `run`（创建并启动）。高级调试时可以先 `runc create` 检查容器环境，再 `runc start`。

### 第12集：容器的生命周期管理：状态机（created/running/paused/stopped）、钩子（Hooks）、健康检查

**💡 核心回答：**

容器有一个明确的状态机模型，包含以下状态及转换：

```
created → running → paused → running → stopped → deleted
              ↓                              ↑
           oom/exited ──────────────────────┘
```

| 状态 | 含义 | 触发方式 |
|------|------|---------|
| `created` | 容器已创建但进程未启动 | `docker create` 或 `runc create` |
| `running` | 容器进程正在运行 | `docker start` 或 `runc start` |
| `paused` | 容器进程被冻结（Cgroup freezer） | `docker pause` |
| `restarting` | 容器正在重启（restart policy 触发） | 自动（退出后重启策略） |
| `exited/stopped` | 容器进程已退出 | 进程退出或 `docker stop` |
| `dead` | 容器已删除但资源未完全清理 | `docker rm` 后清理中 |

**容器的三种停止信号流程：**

```
docker stop → SIGTERM（等待 grace period）→ SIGKILL（强制杀死）
docker kill -s SIGINT → 直接发送指定信号
docker kill -s SIGKILL → 直接杀死
```

```go
// 源码参考：github.com/opencontainers/runc/libcontainer/container_linux.go
// 容器的状态定义
const (
    Created  = "created"
    Running  = "running"
    Paused   = "paused"
    Stopped  = "stopped"
)

// 状态转换
func (c *Container) Status() (Status, error) {
    c.mu.Lock()
    defer c.mu.Unlock()
    
    // 检查 init 进程是否还活着
    pid, err := c.initProcess.pid()
    if err != nil {
        return Stopped, nil
    }
    
    // 检查进程是否存在
    if !processExists(pid) {
        return Stopped, nil
    }
    
    // 检查是否被 Cgroup freezer 冻结
    if c.isFrozen() {
        return Paused, nil
    }
    
    // 检查是否已经 start
    if c.initProcess.started {
        return Running, nil
    }
    
    return Created, nil
}

// 暂停容器（使用 Cgroup freezer）
func (c *Container) Pause() error {
    // 写入 cgroup freezer：FROZEN
    // Cgroup v1: echo FROZEN > /sys/fs/cgroup/freezer/docker/<id>/freezer.state
    // Cgroup v2: echo 1 > /sys/fs/cgroup/docker/<id>/cgroup.freeze
    c.cgroupManager.Freeze(configs.Frozen)
    return nil
}

// 恢复容器
func (c *Container) Resume() error {
    // 写入 cgroup freezer：THAWED
    c.cgroupManager.Freeze(configs.Thawed)
    return nil
}
```

**⚠️ 常见坑/加分回答：**

1. **`health-start-period` 设置不当**：悦茶的 Java 服务启动需要 45 秒，但健康检查的 `start-period` 只设了 10 秒，导致容器被反复重启。正确设置：`--health-start-period=60s`。

2. **`docker stop` 超时**：悦茶的订单服务在 `SIGTERM` 后需要 15 秒处理在途请求（connection draining），默认的 10 秒超时不够。设置 `docker stop --time=30` 或在 docker-compose.yml 中设置 `stop_grace_period: 30s`。

3. **Paused 容器的 Cgroup 内存泄漏**：Paused 状态的容器进程被冻结，但 Cgroup 内存计数器不会释放。如果大量容器长期 Paused，可能导致可用内存减少。悦茶运维监控 Paused 容器数量，超过阈值自动告警。

4. **加分回答**：提到 containerd 的 `restart policy` 是通过 containerd-shim 实现的，而不是 Docker daemon。这意味着即使 Docker daemon 崩溃，容器的 `restart: on-failure` 策略依然生效。

### 第13集：Docker Volume vs Bind Mount vs tmpfs 的区别和选择

**💡 核心回答：**

Docker 提供三种数据持久化方式：

| 方式 | 存储位置 | 管理方式 | 适用场景 |
|------|---------|---------|---------|
| Volume | `/var/lib/docker/volumes/` | Docker 管理 | **推荐**：数据库、持久数据 |
| Bind Mount | 宿主机任意路径 | 用户管理 | 开发环境、配置文件挂载 |
| tmpfs | 宿主机内存 | Docker 管理 | 敏感信息临时存储、临时文件 |

**核心区别：**

| 特性 | Volume | Bind Mount | tmpfs |
|------|--------|-----------|-------|
| 性能 | 接近原生 | 接近原生 | 内存级别（最快） |
| 持久性 | ✅ 持久化到磁盘 | ✅ 持久化到磁盘 | ❌ 重启丢失 |
| 跨平台 | ✅ 由 Docker 管理路径 | ❌ 依赖宿主机路径 | ❌ 不持久化 |
| 共享 | ✅ 多容器安全共享 | ⚠️ 需手动管理权限 | ❌ 容器独享 |
| 备份 | `docker volume` 命令 | 直接复制文件 | 不支持 |
| 权限控制 | Docker 管理 | 用户自行控制 | 内存权限 |

```go
func All(mounts []Mount, target string) error {
    for _, m := range mounts {
        // 1. 创建目标目录
        os.MkdirAll(target, 0755)
        
        // 2. 执行 mount 系统调用
        // 对于 Volume：mount -o bind /var/lib/docker/volumes/xxx/_data /container/path
        // 对于 Bind Mount：mount -o bind /host/path /container/path
        // 对于 tmpfs：mount -t tmpfs -o size=10m tmpfs /container/path

            return fmt.Errorf("failed to mount %v: %w", m, err)
        }
    }

}

    var flags uintptr = syscall.MS_BIND
    if m.Type == "tmpfs" {
        flags = 0
    }
    
    // 执行 mount 系统调用
```

**⚠️ 常见坑/加分回答：**

1. **Volume 权限问题**：MySQL 容器以 `mysql` 用户（UID 999）运行，但 Volume 目录默认属于 root。悦茶的解决方案：`docker run -v mysql-data:/var/lib/mysql --user "999:999"`，或在初始化脚本中 `chown`。

### 第14集：容器网络实现原理：veth pair、bridge、iptables NAT 规则是怎么配置的

**💡 核心回答：**

Docker Bridge 网络的底层实现依赖三个核心 Linux 网络组件：

| 组件 | 作用 | 类比 |
|------|------|------|
| **veth pair** | 虚拟以太网设备对，一端在容器内（eth0），一端在宿主机（vethXXX） | 一根虚拟网线 |
| **Linux Bridge** | 虚拟交换机（docker0），连接多个 veth 对 | 一个物理交换机 |
| **iptables NAT** | 网络地址转换，实现端口映射和容器上网 | NAT 路由器 |

**数据包从容器到外网的路径：**

```
容器内进程 → eth0 → veth pair → docker0(bridge) → iptables POSTROUTING(MASQUERADE) → 物理网卡 → 外网
```

**数据包从外网到容器的路径（端口映射 -p 8080:8080）：**

```
外网请求 → 物理网卡:8080 → iptables PREROUTING(DNAT) → docker0 → veth pair → eth0:8080 → 容器内进程
```

```go
// 源码参考：github.com/moby/libnetwork/drivers/bridge/bridge.go

// 1. 创建 Linux Bridge 设备
func (d *driver) createBridge(config *networkConfiguration) error {
    // 创建 bridge 设备（类似 brctl addbr docker0）
    bridge := &netlink.Bridge{
        LinkAttrs: netlink.LinkAttrs{
            Name:         config.BridgeName,
            MTU:          config.MTU,  // 默认 1500
            TxQLen:       -1,
        },
    }
    netlink.LinkAdd(bridge)
    
    // 配置 IP 地址
    ipAddr, ipNet, _ := net.ParseCIDR(config.AddressIPv4)
    netlink.AddrAdd(bridge, &netlink.Addr{IPNet: ipNet})
    
    // 启用设备
    netlink.LinkSetUp(bridge)
    
    return nil
}

// 2. 为容器创建 veth pair 并连接到 bridge
func (d *driver) CreateEndpoint(nid, eid types.EndpointID, ...) error {
    // 生成 veth 名称
    vethName := "veth" + eid[:7]
    
    // 创建 veth pair
    veth := &netlink.Veth{
        LinkAttrs: netlink.LinkAttrs{
            Name:  vethName,
            MTU:   config.MTU,
        },
        PeerName: "eth0",  // 容器内的网卡名
    }
    netlink.LinkAdd(veth)
    
    // 将宿主机端加入 bridge（就像把网线插到交换机上）
    bridge, _ := netlink.LinkByName(config.BridgeName)
    vethHost, _ := netlink.LinkByName(vethName)
    netlink.LinkSetMaster(vethHost, bridge)
    
    // 将容器端移入容器的 network namespace
    // 使用 setns() 系统调用切换到容器的 netns
    containerNs, _ := netns.GetFromPid(containerPid)
    vethContainer, _ := netlink.LinkByName("eth0")
    netlink.LinkSetNsFd(vethContainer, int(containerNs))
    
    // 在容器 netns 内配置 IP
    withinNetNS(containerNs, func() {
        addr, _ := netlink.ParseAddr(containerIP + "/" + mask)
        netlink.AddrAdd(vethContainer, addr)
        netlink.LinkSetUp(vethContainer)
        
        // 添加默认路由（通过 gateway）
        route := &netlink.Route{
            LinkIndex: vethContainer.Attrs().Index,
            Gw:        gatewayIP,
            Dst:       defaultDst,
        }
        netlink.RouteAdd(route)
    })
    
    return nil
}
```

```go
    // 1. SNAT 规则：容器访问外网

        Chain:    "POSTROUTING",

            "-s", config.AddressIPv4,
            "!", "-o", config.BridgeName,
            "-j", "MASQUERADE",
        },
    }
    iptables.AppendRule(natRule)
    
    // 2. DNAT 规则：端口映射（如 -p 8080:8080）
    // iptables -t nat -A DOCKER -p tcp --dport 8080 -j DNAT --to-destination 10.10.0.2:8080

        Table:    "nat",
        Chain:    "DOCKER",
        Rule: []string{
            "-p", "tcp",
            "--dport", strconv.Itoa(hostPort),
            "-j", "DNAT",
            "--to-destination", fmt.Sprintf("%s:%d", containerIP, containerPort),
        },
    }
    iptables.AppendRule(dnatRule)
    
    // 3. docker-proxy 进程：处理 Hairpin NAT
    // 当容器访问自己的映射端口时，需要特殊的 NAT 处理
    // docker-proxy 监听宿主机端口，将流量转发给容器
    go func() {
        proxy := newProxy(hostIP, hostPort, containerIP, containerPort)
        proxy.Run()
    }()
    
    return nil
}
```

### 第15集：容器间通信：同一 Bridge 网络通信、跨 Host 通信（Overlay + VXLAN）

**💡 核心回答：**

容器间通信分为两种场景：

**1. 同一 Host、同一 Bridge 网络（最常见）：**

```
容器A（eth0）→ veth pair → docker0(bridge) → veth pair → 容器B（eth0）
```

- 容器在同一 Bridge 上，就像插在同一个交换机上
- 直接通过二层（MAC 地址）通信，无需路由
- Docker 内嵌 DNS 支持通过容器名解析 IP

**2. 跨 Host 通信（Overlay 网络）：**

```
Host A 容器 → veth → bridge → VXLAN 封装 → 物理网络 → Host B → VXLAN 解封装 → veth → 容器
```

- 使用 VXLAN（Virtual eXtensible LAN）在三层网络上叠加二层网络
- 每台主机上运行一个 VXLAN Tunnel Endpoint（VTEP）
- 数据包被封装在外层 UDP 包中（端口 4789），通过物理网络传输

**📦 实际例子：**

```go
func (d *driver) setupOverlayNetwork(network *network) error {
    // 1. 创建 VXLAN 设备（VTEP - VXLAN Tunnel Endpoint）
    vtep := &netlink.Vxlan{
        LinkAttrs: netlink.LinkAttrs{
            Name: "vxlan" + network.id[:7],
        },
        VxlanId:  network.vxlanID,  // 24 位 VNI（VXLAN Network Identifier）
        Group:     net.ParseIP("0.0.0.0"),  // 组播（或指定远端 VTEP IP）
        Port:      4789,  // IANA 分配的 VXLAN 端口
        Learning:  false,
        L2miss:    true,  // 启用 L2 miss 通知（用于 ARP 代理）
        L3miss:    true,  // 启用 L3 miss 通知
    }
    netlink.LinkAdd(vtep)
    
    // 2. 创建 sandbox bridge（容器连接到 overlay bridge）
    sboxBridge := &netlink.Bridge{
        LinkAttrs: netlink.LinkAttrs{Name: "br-overlay-" + network.id[:7]},
    }
    netlink.LinkAdd(sboxBridge)
    
    // 3. 将 VXLAN 设备加入 sandbox bridge
    vxlan, _ := netlink.LinkByName(vtep.Name)
    netlink.LinkSetMaster(vxlan, sboxBridge)
}

// 数据包的封装过程
// 原始包：srcMAC:dstMAC | srcIP:dstIP | TCP数据
// 
// VXLAN 封装后：
// 外层：outerSrcMAC:outerDstMAC | outerSrcIP:outerDstIP | UDP(4789)
// VXLAN 头：VNI(24位) | 标志位
// 原始包：srcMAC:dstMAC | srcIP:dstIP | TCP数据

func encapsulatePacket(originalPacket []byte, vni uint32, dstVTEP net.IP) []byte {
    // 1. 添加 VXLAN 头（8字节）
    vxlanHeader := buildVXLANHeader(vni)
    
    // 2. 添加外层 UDP 头（目标端口 4789）
    udpHeader := buildUDPHeader(4789, len(originalPacket)+8)
    
    // 3. 添加外层 IP 头（源=本机 VTEP IP，目标=远端 VTEP IP）
    ipHeader := buildIPHeader(localVTEPIP, dstVTEP)
    
    // 4. 添加外层以太网头
    ethHeader := buildEthHeader(localMAC, nextHopMAC)
    
    // 5. 组装：Ethernet | IP | UDP | VXLAN | 原始帧
    return concat(ethHeader, ipHeader, udpHeader, vxlanHeader, originalPacket)
}
```

```go
    // 3. Bridge 查询 FDB：10.20.0.3 → VTEP 192.168.1.11
    // 4. 数据包进入 VXLAN 设备
    // 5. VXLAN 封装：添加 UDP(4789) + IP(dst=192.168.1.11) + Ethernet
    // 6. 封装后的包通过物理网络发送到 Host B
    
    // Host B 上：
    // 7. 收到 UDP(4789) 包
    // 8. 内核 VXLAN 驱动解封装：剥离外层 UDP/IP/Ethernet + VXLAN 头
    // 9. 还原原始以太网帧
    // 10. 帧到达 overlay bridge
    // 11. Bridge 查 MAC 表，转发到 product-service 的 veth
    // 12. product-service 收到数据包
}
```

**⚠️ 常见坑/加分回答：**

1. **VXLAN 的 MTU 问题**：VXLAN 封装增加 50 字节开销（外层 Ethernet 14 + IP 20 + UDP 8 + VXLAN 8 = 50）。如果物理网络 MTU=1500，Overlay 网络的 MTU 应设为 1450。悦茶遇到过大包被丢弃的问题：`ip link set dev vxlan0 mtu 1450`。

2. **Overlay 网络的性能开销**：VXLAN 封装/解封装增加 CPU 开销（约 5-10%）。悦茶在性能敏感的场景中使用 `macvlan` 网络替代 Overlay。

3. **Docker Swarm 的 gossip 延迟**：Overlay 网络依赖 gossip 协议同步节点信息，在大规模集群中可能有 1-5 秒的延迟。悦茶在容器启动后立即访问跨 Host 服务时，偶尔遇到 DNS 解析失败，通过添加重试机制解决。

4. **加分回答**：提到 Cilium 的 eBPF-based Overlay（不需要 VXLAN 封装，通过 eBPF 直接在内核层面路由容器流量），性能接近 Host 网络模式。

### 第16集：Docker Compose 的编排原理：compose 文件解析、网络创建顺序、依赖管理

**💡 核心回答：**

Docker Compose 是一个用于定义和运行多容器应用的工具。它通过 YAML 文件描述服务、网络和卷，然后一次性创建和启动所有容器。

**Compose 的核心工作流程：**

1. **解析 YAML**：读取 `docker-compose.yml`，解析 services、networks、volumes 定义
2. **依赖排序**：根据 `depends_on` 构建服务启动的 DAG（有向无环图）
3. **创建网络**：先创建所有自定义网络
4. **创建 Volume**：创建所有定义的持久卷
5. **按序启动服务**：按依赖顺序逐个（或并行）启动容器
6. **健康检查等待**：如果 `depends_on` 包含 `condition: service_healthy`，等待上游服务健康后再启动

**`depends_on` 的三种条件：**

| 条件 | 含义 |
|------|------|
| `service_started`（默认） | 等待依赖容器启动（不等待健康检查） |
| `service_healthy` | 等待依赖容器健康检查通过 |
| `service_completed_successfully` | 等待依赖容器成功退出（如数据库迁移任务） |

Docker Compose v2 是用 Go 重写的，核心实现在 `compose-go` 库中：

```go
// 源码参考：github.com/docker/compose/v2/pkg/compose/create.go
// Compose 创建流程
func (s *ComposeService) Up(ctx context.Context, project *types.Project, options UpOptions) error {
    // 1. 创建网络
    for _, network := range project.Networks {
        err := s.ensureNetwork(ctx, network.Name)
    }
    
    // 2. 创建 Volume
    for _, volume := range project.Volumes {
        err := s.ensureVolume(ctx, volume.Name)
    }
    
    // 3. 按依赖拓扑排序
    // 构建 DAG，计算启动顺序
    sorted := topologicalSort(project.Services)
    // 返回 [[mysql, redis, es], [db-migration], [order, product], [nginx]]
    
    // 4. 按层启动（同一层可以并行）
    for _, layer := range sorted {
        var g errgroup.Group
        for _, svc := range layer {
            svc := svc
            g.Go(func() error {
                return s.startService(ctx, project, svc, options)
            })
        }
        g.Wait()  // 等待当前层全部启动
    }
    
    return nil
}
```

依赖排序的拓扑算法：

```go
// 源码参考：github.com/docker/compose/v2/pkg/compose/dependencies.go
// 拓扑排序：Kahn 算法
func topologicalSort(services []types.ServiceConfig) [][]types.ServiceConfig {
    // 1. 构建入度表和邻接表
    inDegree := make(map[string]int)
    graph := make(map[string][]string)
    
    for _, svc := range services {
        if _, ok := inDegree[svc.Name]; !ok {
            inDegree[svc.Name] = 0
        }
        for _, dep := range svc.DependsOn {
            graph[dep] = append(graph[dep], svc.Name)
            inDegree[svc.Name]++
        }
    }
    
    // 2. BFS 分层
    var result [][]types.ServiceConfig
    queue := []string{}
    
    // 入度为 0 的服务（无依赖）先启动
    for name, degree := range inDegree {
        if degree == 0 {
            queue = append(queue, name)
        }
    }
    
    for len(queue) > 0 {
        // 当前层的所有服务可以并行启动
        layer := make([]types.ServiceConfig, len(queue))
        nextQueue := []string{}
        
        for i, name := range queue {
            layer[i] = findService(services, name)
            // 减少下游服务的入度
            for _, downstream := range graph[name] {
                inDegree[downstream]--
                if inDegree[downstream] == 0 {
                    nextQueue = append(nextQueue, downstream)
                }
            }
        }
        
        result = append(result, layer)
        queue = nextQueue
    }
    
    return result
}
```

json-file 日志驱动的实现：

```go
// 源码参考：github.com/moby/moby/daemon/logger/jsonfilelog/jsonfilelog.go
type JSONFileLogger struct {
    mu       sync.RWMutex
    writers  []*logger.LogWatcher  // docker logs 的订阅者
    file     *os.File              // 当前日志文件
    capacity int64                 // max-size
    maxFiles int                   // max-file
    compress  bool                 // 是否压缩
    currentSize int64              // 当前文件大小
}

func (l *JSONFileLogger) Log(msg *logger.Message) error {
    l.mu.Lock()
    defer l.mu.Unlock()
    
    // 1. 序列化为 JSON
    // {"log":"...","stream":"stdout","time":"..."}
    line := marshalJSON(msg)
    
    // 2. 检查是否需要轮转
    if l.currentSize + int64(len(line)) > l.capacity {
        l.rotate()
    }
    
    // 3. 写入文件
    l.file.Write(line)
    l.file.Write([]byte("\n"))
    l.currentSize += int64(len(line))
    
    // 4. 通知所有订阅者（docker logs 实时输出）
    for _, w := range l.writers {
        w.Msg <- msg
    }
    
    return nil
}

func (l *JSONFileLogger) rotate() {
    // 1. 关闭当前文件
    l.file.Close()
    
    // 2. 重命名轮转
    // current.log → current.log.1
    // current.log.1 → current.log.2
    // ...（最多保留 maxFiles 个）
    // 最旧的文件删除
    for i := l.maxFiles - 1; i > 0; i-- {
        os.Rename(
            fmt.Sprintf("%s.%d", l.file.Name(), i),
            fmt.Sprintf("%s.%d", l.file.Name(), i+1),
        )
    }
    os.Rename(l.file.Name(), l.file.Name()+".1")
    
    // 3. 如果需要压缩
    if l.compress {
        go compressFile(l.file.Name() + ".1")
    }
    
    // 4. 创建新的日志文件
    l.file, _ = os.Create(l.file.Name())
    l.currentSize = 0
}
```

### 第19集：容器的优雅启停：SIGTERM 处理、preStop Hook、连接排空（Connection Draining）

**💡 核心回答：**

容器的优雅停止是生产环境的关键能力，确保在服务更新或缩容时不丢失用户请求。

**`docker stop` 的完整流程：**

```
1. docker stop 发送 SIGTERM 给容器 PID 1 进程
2. 应用收到 SIGTERM，开始优雅关闭：
   - 停止接收新请求
   - 等待在途请求处理完成（connection draining）
   - 关闭数据库连接、清理资源
3. 等待 grace period（默认 10 秒）
4. 如果进程还在运行，发送 SIGKILL 强制杀死
```

**优雅关闭的三个关键点：**

| 关键点 | 实现方式 |
|--------|---------|
| 捕获 SIGTERM | 应用代码中注册信号处理器 |
| Connection Draining | 停止接收新连接，处理完在途请求 |
| 资源清理 | 关闭数据库连接、释放锁、注销服务注册 |

**📦 实际例子：**

`docker stop` 的信号发送流程：

```go
// 源码参考：github.com/moby/moby/daemon/stop.go
func (daemon *Daemon) containerStop(container *container.Container, 
    seconds int) error {
    
    // 1. 检查容器是否在运行
    if !container.IsRunning() {
        return nil
    }
    
    // 2. 发送 SIGTERM
    // 通过 containerd 发送信号给 PID 1
    signal := syscall.SIGTERM  // 默认信号
    containerdTask.Signal(ctx, signal)
    
    // 3. 等待进程退出（grace period）
    // 通过 containerd-shim 监听进程退出事件
    exitCh := make(chan uint32, 1)
    go func() {
        exitStatus, _ := containerdTask.Wait(ctx)
        exitCh <- exitStatus.ExitCode()
    }()
    
    // 4. 设置超时
    timeout := time.Duration(seconds) * time.Second
    select {
    case exitCode := <-exitCh:
        // 进程已退出
        container.SetStopped(exitCode)
    case <-time.After(timeout):
        // 超时：发送 SIGKILL
        containerdTask.Kill(ctx, syscall.SIGKILL)
        // 等待进程被杀死
        <-exitCh
        container.SetStopped(137)  // 128 + 9 = SIGKILL
    }
    
    // 5. 清理容器资源
    daemon.cleanupContainer(container)
    
    return nil
}
```

containerd-shim 的信号转发：

```go
// 源码参考：github.com/containerd/containerd/runtime/v2/shim/
// shim 接收来自 containerd 的信号，转发给容器进程
func (s *Service) Kill(ctx context.Context, r *taskAPI.KillRequest) error {
    // 获取容器进程 PID
    pid := r.Pid  // 0 表示发送给所有进程
    
    // 发送信号
    signal := syscall.Signal(r.Signal)
    
    if pid == 0 {
        // 发送给 init 进程（PID 1）
        syscall.Kill(s.initProcess.Pid, signal)
    } else {
        // 发送给指定进程
        syscall.Kill(int(pid), signal)
    }
    
    return nil
}
```

**⚠️ 常见坑/加分回答：**

1. **Shell 形式 CMD 的信号丢失**：悦茶早期用 `CMD java -jar app.jar`（shell 形式），`docker stop` 发送 SIGTERM 被 `/bin/sh` 吞掉，Java 进程直接收到 SIGKILL 被强制杀死，导致订单数据不一致。改用 `CMD ["java", "-jar", "app.jar"]`（exec 形式）解决。

2. **Nacos 注销延迟**：服务从 Nacos 注销后，其他服务的 DNS 缓存可能还有旧记录（30-60 秒）。悦茶在注销后等待 10 秒再开始关闭，确保流量完全切换。

3. **数据库事务中断**：如果 SIGKILL 杀死了正在写数据库的进程，事务会回滚但连接可能残留。悦茶通过 HikariCP 的连接泄漏检测（`leakDetectionThreshold=30s`）来发现和处理。

4. **加分回答**：Kubernetes 的 preStop Hook 在 Docker SIGTERM 之前执行（如 `sleep 5` 或 `curl -X POST /shutdown`），为流量切换预留时间。悦茶在 K8s 中配置了 `preStop: exec: command: ["sh", "-c", "sleep 10"]`。

OOM Killer 的内核实现：

```c
// Linux 内核 mm/oom_kill.c
// OOM Killer 的选择逻辑
void oom_kill_process(struct oom_control *oc, const char *message)
{
    // 1. 计算所有进程的 OOM score
    // oom_score = badness(process) + oom_score_adj
    // badness 基于进程的 RSS（常驻集大小）
    
    // 2. 找到得分最高的进程
    struct task_struct *victim = select_bad_process(oc);
    
    // 3. 发送 SIGKILL
    do_send_sig_info(SIGKILL, SEND_SIG_FORCED, victim, true);
    
    // Docker 容器中的 OOM 检测：
    // containerd-shim 监听到进程被 SIGKILL 杀死
    // 检查 cgroup 的 oom_event_fd（Cgroup v1）
    // 或 memory.events 中的 oom_kill 计数（Cgroup v2）
}

// Cgroup v2 的 OOM 事件
// /sys/fs/cgroup/docker/<id>/memory.events
// low 0
// high 0
// max 3        ← 到达最大限制的次数
// oom 2        ← OOM 触发次数
// oom_kill 1   ← OOM Kill 次数
```

容器状态恢复（Docker daemon 重启后）：

```go
// 源码参考：github.com/moby/moby/daemon/daemon.go
// Docker daemon 重启后恢复容器状态
func (daemon *Daemon) restore() error {
    // 1. 扫描所有容器的元数据
    containers, _ := daemon.containersReplica.GetAll()
    
    for _, container := range containers {
        // 2. 检查容器进程是否还在运行
        // （通过检查 containerd-shim 和 PID 1 进程）
        pid := container.State.Pid
        if processExists(pid) {
            // 进程还在，恢复为 Running 状态
            container.State.Status = "running"
            // 重新连接日志
            daemon.reconnectContainerLogs(container)
        } else {
            // 进程已退出
            container.State.Status = "exited"
            
            // 3. 检查 restart policy
            switch container.HostConfig.RestartPolicy.Name {
            case "always":
                daemon.containerStart(container)
            case "on-failure":
                if container.State.ExitCode != 0 {
                    daemon.containerStart(container)
                }
            case "unless-stopped":
                daemon.containerStart(container)
            }
        }
    }
    
    return nil
}
```

**⚠️ 常见坑/加分回答：**

1. **exit code 137 vs 143**：137 = SIGKILL（OOM 或 docker kill），143 = SIGTERM（docker stop）。悦茶运维通过 exit code 快速判断容器退出原因。

2. **Volume 数据无法自动清理**：`docker system prune` 不会删除正在使用的 Volume。悦茶的运维手册要求定期检查未挂载的 Volume：`docker volume ls -f dangling=true`。

3. **Overlay2 磁盘占用**：每个容器的可写层在 `/var/lib/docker/overlay2/` 中，频繁写日志的容器可写层会很大。悦茶的解决方案是日志输出到 Volume（而非可写层），或直接使用 Fluent Bit 收集。

4. **加分回答**：提到 `docker events` 实时监控容器事件。悦茶编写了一个监控脚本，监听 `die` 事件并自动收集退出信息发送到告警群。

**🔍 源码解析：**

Swarm 的调度器实现：

```go
// 源码参考：github.com/moby/swarmkit/manager/scheduler/scheduler.go
// Swarm 的调度策略
func (s *Scheduler) schedule(ctx context.Context, task *api.Task) error {
    // 1. 获取可用节点
    nodes := s.nodeSet.getAll()
    
    // 2. 过滤不满足条件的节点
    // - 资源不足（CPU、Memory）
    // - 约束不满足（node.labels）
    // - Placement constraints
    feasible := filterNodes(nodes, task)
    
    // 3. 选择最优节点
    // Swarm 默认使用 "spread" 策略：
    // 选择运行该服务副本最少的节点（均匀分布）
    var bestNode *api.Node
    minTasks := math.MaxInt64
    
    for _, node := range feasible {
        taskCount := s.countTasksOnNode(node.ID, task.ServiceID)
        if taskCount < minTasks {
            minTasks = taskCount
            bestNode = node
        }
    }
    
    // 4. 将任务分配给最优节点
    task.NodeID = bestNode.ID
    task.Status.State = api.TaskStateAssigned
    
    return nil
}
```

Kubernetes 的调度器实现（对比）：

```go
// 源码参考：k8s.io/kubernetes/pkg/scheduler/
// K8s 调度器的两阶段：Filter + Score
func (sched *Scheduler) scheduleOne(ctx context.Context) {
    // 1. 从调度队列取出一个 Pod
    pod := sched.NextPod()
    
    // 2. Filter 阶段（排除不满足条件的节点）
    feasibleNodes, err := sched.findNodesThatFitPod(ctx, pod)
    // 过滤器包括：
    // - NodeResourcesFit：CPU/内存是否足够
    // - NodeAffinity：节点亲和性
    // - PodTopologySpread：拓扑分布约束
    // - TaintToleration：污点容忍
    
    if len(feasibleNodes) == 0 {
        // 无可用节点，记录事件，重新入队
        sched.recordError(pod, ErrNoNodesAvailable)
        return
    }
    
    // 3. Score 阶段（为每个可行节点打分）
    // 评分器包括：
    // - LeastRequestedPriority：资源使用率低的节点分高
    // - BalancedResourceAllocation：CPU 和内存使用均衡的节点分高
    // - ImageLocalityPriority：已有镜像的节点分高
    scoredNodes := sched.prioritizeNodes(ctx, pod, feasibleNodes)
    
    // 4. 选择得分最高的节点
    bestNode := highestScoreNode(scoredNodes)
    
    // 5. Bind：将 Pod 绑定到节点
    sched.bind(ctx, pod, bestNode)
}
```

**⚠️ 常见坑/加分回答：**

1. **Swarm 的局限**：Swarm 不支持 CRD（自定义资源）、不支持 Operator 模式、滚动更新策略有限。悦茶在需要金丝雀发布时，不得不手动管理 Nginx 权重。

2. **Kubernetes 的运维成本**：K8s 需要专门运维团队。悦茶从 Swarm 迁移到 K8s 后，团队增加了 2 名 K8s 运维工程师。

3. **加分回答**：提到 Docker Desktop 的 Kubernetes 集成——开发者可以在本地同时体验 Swarm 和 K8s。另外，Docker 官方已不再主推 Swarm，containerd 社区的重心在 K8s 生态。

### 第22集：Rootless 容器：无 root 权限运行容器的原理和安全收益

**💡 核心回答：**

Rootless 容器是指**不使用 root 权限运行容器进程和容器运行时**的模式。这是 Docker 和 Podman 支持的安全增强特性。

**Rootless 的核心机制：**

| 技术 | 作用 |
|------|------|
| **User Namespace** | 容器内的 root（UID 0）映射到宿主机的非特权用户（如 UID 100000） |
| **newuidmap/newgidmap** | 设置 UID/GID 映射（需要 /etc/subuid 和 /etc/subgid 配置） |
| **slirp4netns / pasta** | 用户态网络栈（不需要 root 创建网络命名空间） |
| **fuse-overlayfs** | 用户态 OverlayFS（不需要 root 挂载文件系统） |

**Rootless 的安全收益：**

1. 即使容器逃逸，攻击者也只是宿主机上的普通用户
2. 无法访问宿主机的敏感文件（/etc/shadow 等）
3. 无法修改宿主机的系统配置
4. 无法加载内核模块
5. 大幅减少攻击面

**📦 实际例子：**

悦茶开发人员在本地使用 Rootless Docker 进行开发：

```bash
# 1. 安装 Rootless Docker
dockerd-rootless-setuptool.sh install

# 2. 启动 Rootless Docker daemon（不需要 sudo）
systemctl --user start docker

# 3. 使用 Docker（不需要 sudo）
docker run -d --name order-service \
  -p 8080:8080 \
  yuecha/order-service:dev

# 4. 验证：容器内是 "root"，但实际映射到宿主机的普通用户
$ docker exec order-service whoami
root  # 容器内看起来是 root

# 但在宿主机上：
$ ps aux | grep order-service
100000  12345  2.1  15.3  java -jar order-service.jar
# 实际 UID 是 100000（subuid 映射的起始值）

# 5. 即使容器被攻破，攻击者只能获得 UID 100000 的权限
# 无法读取 /etc/shadow、无法安装软件、无法修改系统文件
```

**Rootless 的 UID/GID 映射配置：**

```bash
# /etc/subuid - 每个用户可用的子 UID 范围
$ cat /etc/subuid
devuser:100000:65536   # devuser 可以使用 100000-165535 的 UID
root:165536:65536      # root 可以使用 165536-231135 的 UID

# /etc/subgid - 每个用户可用的子 GID 范围
$ cat /etc/subgid
devuser:100000:65536
root:165536:65536

# 这意味着 devuser 运行的容器内：
# UID 0 (容器root) → UID 100000 (宿主机devuser的subuid)
# UID 1 (容器daemon) → UID 100001
# ...
# UID 65535 → UID 165535
```

**🔍 源码解析：**

Rootless Docker 的启动流程：

```go
// 源码参考：github.com/moby/moby/cmd/dockerd/rootless.go
// Rootless Docker daemon 启动时的特殊处理
func setupRootless() error {
    // 1. 检查 User Namespace 是否可用
    // 需要内核支持 CONFIG_USER_NS
    
    // 2. 检查 newuidmap/newgidmap 是否设置了 SUID bit
    // which newuidmap → /usr/bin/newuidmap (需要 suid)
    
    // 3. 使用 slirp4netns 创建用户态网络
    // （不需要 root 创建 Network Namespace 的 veth 设备）
    slirp4netns := &Slirp4netns{
        MTU: 65520,  // 接近标准 MTU
        // slirp4netns 在用户态实现 TCP/IP 栈
        // 通过 TAP 设备将容器网络桥接到宿主机
    }
    slirp4netns.Start()
    
    // 4. 使用 fuse-overlayfs 替代 overlay2
    // （标准 overlayfs 需要 root 权限）
    // fuse-overlayfs 通过 FUSE 在用户态实现 OverlayFS
    storageDriver = "fuse-overlayfs"
    
    // 5. 端口映射使用 rootlesskit
    // rootlesskit 通过 child process 持有特权端口
    // 将宿主机端口转发到容器的用户态网络
    rootlesskit.StartPortForwarder()
    
    // 6. 数据目录放在用户目录下
    // 默认：~/.local/share/docker/
    // 而非：/var/lib/docker/
    dataRoot = filepath.Join(os.Getenv("HOME"), ".local/share/docker")
    
    return nil
}
```

User Namespace 的内核实现：

```c
// Linux 内核 kernel/user_namespace.c
// UID/GID 映射的内核实现

struct uid_gid_map {
    unsigned int nr_extents;  // 映射条目数
    struct uid_gid_extent {
        u32 first;     // 起始 ID（当前命名空间）
        u32 lower_first; // 起始 ID（父命名空间）
        u32 count;     // 映射范围大小
    } extent[UID_GID_MAP_MAX_EXTENTS];
};

// 当容器内进程访问文件系统时，内核进行 UID 转换
// 容器内 UID 0 → 宿主机 UID 100000
kuid_t from_kuid(struct user_namespace *ns, kuid_t uid)
{
    // 查找 UID 映射表
    // 如果 uid = 0，映射到 lower_first = 100000
    // 实际返回 100000
    return map_id_down(&ns->uid_map, uid.val);
}

// 当宿主机查看容器创建的文件时
// 宿主机看到 UID 100000 → 容器内看到 UID 0
kuid_t make_kuid(struct user_namespace *ns, uid_t uid)
{
    return map_id_up(&ns->uid_map, uid);
}
```

**⚠️ 常见坑/加分回答：**

1. **Rootless 的性能开销**：slirp4netns 的网络性能比原生 Bridge 低约 30-50%（用户态网络栈开销）。悦茶在生产环境不使用 Rootless（性能要求高），但在开发环境广泛使用。

2. **端口限制**：Rootless 模式下无法绑定 < 1024 的端口（除非使用 rootlesskit 的特殊处理）。悦茶的开发服务统一使用 8000+ 端口。

3. **fuse-overlayfs 的限制**：某些文件系统操作（如 xattr）在 FUSE 上可能不完整。悦茶遇到过 SELinux 标签设置失败的问题。

4. **加分回答**：Podman 默认以 Rootless 模式运行，且不需要 daemon 进程（无守护进程架构）。悦茶的安全团队正在评估 Podman 作为 Rootless 容器的替代方案。

### 第23集：多架构镜像：Buildx 构建 ARM/AMD64 多平台镜像的原理

**💡 核心回答：**

Docker Buildx 支持构建**多架构镜像**（Multi-arch Image），即一个镜像 Tag 对应多个 CPU 架构的镜像。拉取时自动选择匹配宿主机架构的版本。

**支持的架构：**

| 架构 | 典型设备 | Docker 平台标识 |
|------|---------|----------------|
| AMD64 | x86_64 服务器 | `linux/amd64` |
| ARM64 | AWS Graviton、Apple M系列 | `linux/arm64` |
| ARM v7 | 树莓派 | `linux/arm/v7` |
| ARM v8 | 64位 ARM | `linux/arm64` |
| s390x | IBM Z 系列 | `linux/s390x` |
| ppc64le | IBM Power | `linux/ppc64le` |

**多架构镜像的实现原理：**

```
一个 Tag（如 yuecha/order-service:latest）
    ├── Manifest List（索引）
    │   ├── linux/amd64  → manifest_a → [layer1, layer2, layer3]
    │   ├── linux/arm64  → manifest_b → [layer1, layer2, layer3]
    │   └── linux/arm/v7 → manifest_c → [layer1, layer2, layer3]
    └── 拉取时根据 uname -m 自动选择
```

**Buildx 的构建方式：**

| 方式 | 原理 | 速度 |
|------|------|------|
| QEMU 模拟 | 在宿主机上模拟其他架构 | 慢（10-50x 减速） |
| 远程构建节点 | 在目标架构的机器上构建 | 快（原生速度） |
| 交叉编译 | 在宿主机编译目标架构二进制 | 快（需要交叉编译工具链） |

**📦 实际例子：**

悦茶构建多架构镜像的完整流程：

Buildx 使用 BuildKit 进行多架构构建：

```go
// 源码参考：github.com/docker/buildx/build/build.go
// Buildx 的多架构构建流程
func Build(ctx context.Context, opt Options) (*Result, error) {
    // 1. 解析目标平台列表
    platforms := opt.Platforms  // ["linux/amd64", "linux/arm64"]
    
    // 2. 为每个平台创建独立的构建任务
    // BuildKit 使用 LLB（Low-Level Build）定义构建图
    var defs []*llb.Definition
    for _, platform := range platforms {
        // 设置构建上下文的目标平台
        def, err := buildForPlatform(ctx, opt, platform)
        // 关键：$BUILDPLATFORM 和 $TARGETPLATFORM 被替换为实际值
        // TARGETOS=linux, TARGETARCH=arm64 → CGO_ENABLED=0 GOOS=linux GOARCH=arm64
        defs = append(defs, def)
    }
    
    // 3. 并行执行各平台的构建（如果 BuildKit 支持）
    // 通过 QEMU 或远程节点执行不同架构的构建
    
    // 4. 构建 Manifest List（索引）
    // 将各平台的 manifest 合并为一个 manifest list
    manifestList := buildManifestList(platforms, results)
    // {
    //   "schemaVersion": 2,
    //   "mediaType": "application/vnd.docker.distribution.manifest.list.v2+json",
    //   "manifests": [
    //     {"mediaType": "...", "digest": "sha256:abc...", "platform": {"architecture": "amd64", "os": "linux"}},
    //     {"mediaType": "...", "digest": "sha256:def...", "platform": {"architecture": "arm64", "os": "linux"}}
    //   ]
    // }
    
    // 5. 推送 Manifest List 到 Registry
    pushManifestList(ctx, manifestList)
    
    return result, nil
}
```

**⚠️ 常见坑/加分回答：**

1. **QEMU 模拟很慢**：在 AMD64 机器上交叉编译 ARM64 镜像，QEMU 模拟会导致构建时间增加 10-50 倍。悦茶的解决方案是使用 AWS Graviton 机器作为远程 Buildx 节点，原生构建 ARM64 镜像。

2. **基础镜像不支持目标架构**：某些 Docker Hub 镜像只提供 AMD64 版本。悦茶统一使用支持多架构的基础镜像（如 `eclipse-temurin`、`alpine`、`nginx` 官方镜像都支持多架构）。

3. **缓存策略**：多架构构建的缓存是各平台独立的。悦茶使用 BuildKit 的 `--cache-from` 和 `--cache-to` 功能，将缓存存储在 Registry 中。

4. **加分回答**：提到 Docker Scout 可以扫描多架构镜像中每个平台的漏洞，确保不同架构的镜像都是安全的。

**核心转储分析：**

nsenter 的实现原理（进入已有命名空间）：

```go
// 源码参考：github.com/moby/moby/cmd/nsenter/
// nsenter 的核心：setns() 系统调用
func main() {
    targetPid := flag.Int("t", 0, "target PID")
    namespaces := flag.String("a", "", "enter all namespaces")
    
    // 打开目标进程的命名空间文件
    // /proc/<pid>/ns/pid, /proc/<pid>/ns/net, /proc/<pid>/ns/mnt 等
    nsFiles := map[string]string{
        "pid": fmt.Sprintf("/proc/%d/ns/pid", *targetPid),
        "net": fmt.Sprintf("/proc/%d/ns/net", *targetPid),
        "mnt": fmt.Sprintf("/proc/%d/ns/mnt", *targetPid),
        "uts": fmt.Sprintf("/proc/%d/ns/uts", *targetPid),
        "ipc": fmt.Sprintf("/proc/%d/ns/ipc", *targetPid),
    }
    
    // 逐个进入命名空间
    for nsName, nsPath := range nsFiles {
        fd, _ := os.Open(nsPath)
        // setns() 系统调用：将当前进程加入目标命名空间
        // 源码：kernel/nsproxy.c -> sys_setns()
        syscall.Setns(int(fd.Fd()), namespaceFlag(nsName))
        fd.Close()
    }
    
    // 现在当前进程已经在容器的命名空间中了
    // 执行用户指定的命令
    syscall.Exec("/bin/sh", []string{"/bin/sh"}, os.Environ())
}
```

`setns` 在内核中的实现：

```c
// Linux 内核 kernel/nsproxy.c
SYSCALL_DEFINE2(setns, int, fd, int, flags)
{
    // 1. 从 fd 获取命名空间
    struct ns_common *ns = get_ns_from_fd(fd);
    
    // 2. 检查权限（需要 CAP_SYS_ADMIN）
    if (!ns_capable(ns->user_ns, CAP_SYS_ADMIN))
        return -EPERM;
    
    // 3. 将当前进程切换到目标命名空间
    // 对于 PID namespace：当前进程不会移动（只有子进程在新 namespace 中）
    // 对于 Network namespace：当前进程的网络栈切换到目标
    // 对于 Mount namespace：当前进程的挂载点切换到目标
    
    switch_task_namespaces(current, new_nsproxy);
    
    return 0;
}
```

**⚠️ 常见坑/加分回答：**

1. **distroless 镜像无法 exec**：Google 的 distroless 镜像没有 shell，`docker exec` 无法进入。悦茶的解决方案是使用 `nsenter` 或启动一个 `--pid=container:xxx` 的调试容器。

2. **strace 的性能影响**：strace 会显著降低进程性能（可达 10-100 倍减速）。悦茶只在必要时短暂使用，或使用 `strace -c` 收集统计信息而非逐条打印。

3. **PID Namespace 的限制**：`docker exec` 进入容器时，exec 进程在容器的 PID namespace 中，但不在容器的 cgroup 中（可能看不到准确的资源使用）。

4. **加分回答**：提到 Kubernetes 的 `debug` 命令（`kubectl debug`），它可以创建一个 ephemeral container 附加到已有 Pod，比 Docker exec 更灵活。

### 第25集：Docker 在 CI/CD 中的应用：构建缓存、Docker-in-Docker vs Kaniko 无守护镜像构建

**💡 核心回答：**

在 CI/CD 中构建 Docker 镜像有两种主流方案：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **Docker-in-Docker (DinD)** | 在 CI 容器中运行一个完整的 Docker daemon | 完整 Docker 功能 | 需要特权模式，安全风险高 |
| **Kaniko** | 无守护进程镜像构建，直接在用户态构建 | 无需特权模式，安全 | 不支持所有 Docker 功能 |
| **Buildah** | 用户态构建，兼容 OCI | 灵活，支持 rootless | 生态较新 |
| **BuildKit（远程）** | 远程 BuildKit 实例构建 | 高性能，安全 | 需要维护 BuildKit 集群 |

**构建缓存优化策略：**

| 策略 | 效果 |
|------|------|
| 层缓存（Dockerfile 顺序优化） | 避免不必要的层重建 |
| BuildKit 缓存挂载（`--mount=type=cache`） | 缓存 node_modules、Maven 依赖等 |
| 远程缓存（Registry/OCI cache） | 跨 CI runner 共享构建缓存 |
| 并行构建 | BuildKit 支持多阶段并行执行 |

Kaniko 的构建流程（无守护进程）：

```go
// 源码参考：github.com/GoogleContainerTools/kaniko/pkg/executor/
// Kaniko 在用户态执行 Dockerfile 指令，不依赖 Docker daemon
func DoBuild(opts *config.KanikoOptions) (v1.Image, error) {
    // 1. 解析 Dockerfile
    stages, err := dockerfile.ParseStages(opts.Dockerfile)
    
    // 2. 为每个阶段创建临时目录（模拟文件系统）
    for _, stage := range stages {
        // 创建临时目录作为该阶段的 rootfs
        stageDir := createTempDir()
        
        // 复制基础镜像的文件系统到临时目录
        if stage.Base != "scratch" {
            extractImage(stage.Base, stageDir)
        }
        
        // 3. 逐条执行 Dockerfile 指令
        for _, cmd := range stage.Commands {
            switch cmd := cmd.(type) {
            case *instructions.RunCommand:
                // RUN 指令：chroot 到临时目录，执行命令
                // 不需要 Docker daemon，直接 syscall.Chroot + syscall.Exec
                syscall.Chroot(stageDir)
                exec.Command("sh", "-c", cmd.CmdLine).Run()
                
            case *instructions.CopyCommand:
                // COPY 指令：直接文件复制
                copyFiles(cmd.Source, filepath.Join(stageDir, cmd.Destination))
                
            case *instructions.AddCommand:
                // ADD 指令：复制文件或解压
                handleAdd(cmd, stageDir)
            }
            
            // 4. 每条指令后，计算文件系统的快照作为新层
            layer := snapshotFilesystem(stageDir)
            layers = append(layers, layer)
        }
    }
    
    // 5. 将各层打包为 OCI 镜像
    image := buildImage(layers)
    
    // 6. 推送到 Registry
    pushImage(image, opts.Destinations)
    
    return image, nil
}
```

BuildKit 的缓存机制（LLB - Low-Level Build）：

```go
// 源码参考：github.com/moby/buildkit/solver/
// BuildKit 使用 LLB（Low-Level Build）定义构建图
// LLB 是一个内容寻址的 DAG（有向无环图）

// 构建缓存键的计算
func cacheKey(op Op) digest.Digest {
    h := sha256.New()
    
    // 1. 操作类型（exec, source, file copy 等）
    h.Write([]byte(op.Type()))
    
    // 2. 操作参数（命令、环境变量等）
    h.Write([]byte(op.Args()))
    
    // 3. 输入内容（源文件的哈希）
    for _, input := range op.Inputs() {
        h.Write(input.Digest())
    }
    
    // 4. 平台信息（amd64/arm64）
    h.Write([]byte(op.Platform()))
    
    return digest.NewDigest(h)
    
    // 如果缓存键匹配 → 直接使用缓存结果
    // 如果不匹配 → 重新执行，结果写入缓存
}
```

**⚠️ 常见坑/加分回答：**

1. **DinD 的安全风险**：DinD 需要 `--privileged` 模式，等于给 CI 容器完全的宿主机权限。悦茶从 DinD 迁移到 Kaniko，消除了这一风险。

2. **Kaniko 不支持所有 Dockerfile 功能**：Kaniko 不支持 `--privileged` 的 RUN 指令和某些网络操作。悦茶在需要特权操作的场景使用 BuildKit 替代。

3. **缓存爆炸**：`COPY . /app` 会导致每次代码修改都使缓存失效。悦茶将 `COPY go.mod go.sum` 放在 `COPY . .` 前面，先缓存依赖下载。

4. **加分回答**：提到 Earthly 和 Bazel 的容器构建——它们使用更高级的缓存机制（跨项目共享缓存、增量构建），悦茶的大型 Java 项目使用 Bazel 管理构建。

### 第26集：镜像版本管理策略：Tag 策略（语义化/时间戳/Git SHA）、滚动更新与回滚

**💡 核心回答：**

镜像版本管理是 CI/CD 的核心实践，直接影响部署的可靠性和可追溯性。

**三种主流 Tag 策略：**

| 策略 | 格式示例 | 优点 | 缺点 |
|------|---------|------|------|
| **语义化版本** | `v1.2.3` | 人类可读，表达变更含义 | 需要人工管理，可能冲突 |
| **Git SHA** | `a1b2c3d4` | 唯一、不可变、可追溯 | 不直观，需要查 Git |
| **时间戳** | `20240115-103000` | 有序、自动递增 | 较长，不表达语义 |
| **混合策略** | `v1.2.3-a1b2c3d4` | 兼顾可读性和唯一性 | 较长 |

**悦茶推荐：混合策略**

```
语义版本 + Git SHA：v2.1.0-a1b2c3d4
latest：指向最新版本（仅开发/测试环境使用）
v2.1：指向 v2.1.x 的最新补丁版本（便于回滚）
```

**滚动更新流程：**

```
v2.1 → 构建新镜像 v2.2
     → 灰度发布 1 个实例
     → 健康检查通过
     → 逐步替换所有实例
     → 旧版本保留（便于回滚）
```

**回滚策略：**

```
v2.2 上线后发现问题
     → 快速回滚到 v2.1（使用旧镜像 Tag）
     → 或回滚到 Git SHA 对应的精确版本
```

**📦 实际例子：**

Docker Swarm 的滚动更新实现：

```go
// 源码参考：github.com/moby/swarmkit/manager/orchestrator/update/updater.go
func (u *Updater) Run(ctx context.Context, service *api.Service, tasks []*api.Task) {
    // 1. 按并行度分批
    parallelism := service.Spec.Update.Parallelism  // 如 1
    
    for i := 0; i < len(tasks); i += parallelism {
        batch := tasks[i:min(i+parallelism, len(tasks))]
        
        // 2. 每批同时更新
        for _, task := range batch {
            // 启动新版本的任务
            newTask := createTask(service, task.NodeID)
            // 旧任务在新任务就绪后才停止
            
            // 3. 等待新任务就绪（健康检查）
            waitHealthy(ctx, newTask, service.Spec.Update.Monitor)
            
            // 4. 停止旧任务
            stopTask(task)
        }
        
        // 5. 等待更新间隔
        time.Sleep(service.Spec.Update.Delay)
        
        // 6. 检查是否需要回滚
        if checkFailure(ctx, service) {
            switch service.Spec.Update.FailureAction {
            case "rollback":
                u.Rollback(ctx, service)
                return
            case "pause":
                u.Pause()
                return
            }
        }
    }
}
```

```go
// Harbor 的镜像复制基于事件驱动
type ReplicationPolicy struct {
    Name            string
    SrcRegistry     *Registry  // 源 Registry
    DestRegistry    *Registry  // 目标 Registry
    Trigger         *Trigger   // 触发方式（手动/定时/事件）
    Filters         []*Filter  // 过滤条件（项目名、Tag 模式）
    ReplicateDeletion bool     // 是否同步删除
}

// 事件触发复制
func (m *Manager) onArtifactPushed(event *event.ArtifactEvent) {
    // 1. 查找匹配的复制策略
    policies := m.getPoliciesForArtifact(event.Artifact)
    
    for _, policy := range policies {
        // 2. 创建复制任务
        task := &ReplicationTask{
            PolicyID:   policy.ID,
            Artifact:   event.Artifact,
            Status:     "pending",
        }
        
        // 3. 加入任务队列
        m.taskQueue.Push(task)
    }
}

// 执行复制
func (m *Manager) executeTask(task *ReplicationTask) error {
    // 1. 从源 Registry 拉取 manifest
    manifest := pullManifest(task.SrcRegistry, task.Artifact)
    
    // 2. 对比目标 Registry，找出缺失的层
    missingLayers := diffLayers(manifest, task.DestRegistry)
    
    // 3. 只复制缺失的层（增量复制）
    for _, layer := range missingLayers {
        blob := pullBlob(task.SrcRegistry, layer.Digest)
        pushBlob(task.DestRegistry, blob)
    }
    
    // 4. 推送 manifest
    pushManifest(task.DestRegistry, manifest)
    
    return nil
}
```

**⚠️ 常见坑/加分回答：**

1. **Harbor 的存储增长**：Harbor 的 GC 不会自动运行，需要手动或定时触发。悦茶配置了每周日凌晨运行 GC：`docker run --rm goharbor/harbor-core gc --delete-untagged`。

2. **HTTPS 证书**：生产环境必须配置 HTTPS。悦茶使用 Let's Encrypt 自动续期。

3. **加分回答**：提到 Harbor 的代理缓存功能——配置一个 Docker Hub 代理项目，首次拉取 Docker Hub 镜像时自动缓存，后续从本地缓存读取。悦茶用此功能解决了 Docker Hub 拉取限速问题。

### 第28集：单机 Docker 资源规划：一台物理机跑多少容器合适、资源超售（Overcommit）策略

**💡 核心回答：**

单机 Docker 资源规划需要考虑 CPU、内存、磁盘、网络四个维度的容量。

**核心原则：**

| 资源 | 建议 | 注意事项 |
|------|------|---------|
| **CPU** | 容器总 CPU 限制 ≤ 物理 CPU 核数 × 超售比 | 超售比通常 2:1 ~ 4:1 |
| **内存** | 容器总内存限制 ≤ 物理内存 × 80% | 预留 20% 给系统和 Docker 守护进程 |
| **磁盘** | 预留 30% 以上可用空间 | 镜像、日志、Volume 都要占用 |
| **网络** | 考虑带宽和连接数 | 容器数量影响 bridge 性能 |

**资源超售（Overcommit）策略：**

资源超售是指分配的总资源超过物理资源的策略。因为不是所有容器都同时满载运行。

```
物理资源：32 核 CPU、64GB 内存
超售比：CPU 4:1，内存 1.5:1

可分配资源：
- CPU：32 × 4 = 128 核（可运行 64 个 2 核容器）
- 内存：64 × 1.5 = 96GB（可运行 24 个 4GB 容器）
```

```bash
#!/bin/bash
# /opt/yuecha/scripts/resource-check.sh
# 资源规划检查脚本

TOTAL_CPU=$(nproc)
TOTAL_MEM=$(free -g | awk '/^Mem:/{print $2}')
TOTAL_DISK=$(df -BG / | awk 'NR==2{print $4}' | tr -d 'G')

# 计算容器资源需求
ALLOCATED_CPU=0
ALLOCATED_MEM=0
for container in $(docker ps -q); do
    cpu=$(docker inspect $container --format '{{.HostConfig.NanoCpus}}')
    mem=$(docker inspect $container --format '{{.HostConfig.Memory}}')
    ALLOCATED_CPU=$((ALLOCATED_CPU + cpu / 1000000000))
    ALLOCATED_MEM=$((ALLOCATED_MEM + mem / 1073741824))
done

# 检查超售比
CPU_RATIO=$(echo "scale=2; $ALLOCATED_CPU / $TOTAL_CPU" | bc)
MEM_RATIO=$(echo "scale=2; $ALLOCATED_MEM / $TOTAL_MEM" | bc)

echo "CPU: ${ALLOCATED_CPU}/${TOTAL_CPU} (ratio: ${CPU_RATIO})"
echo "MEM: ${ALLOCATED_MEM}GB/${TOTAL_MEM}GB (ratio: ${MEM_RATIO})"
echo "DISK: ${TOTAL_DISK}GB available"

# 告警
if (( $(echo "$CPU_RATIO > 3.0" | bc -l) )); then
    echo "WARNING: CPU overcommit ratio > 3:1"
fi
if (( $(echo "$MEM_RATIO > 0.8" | bc -l) )); then
    echo "CRITICAL: Memory usage > 80%"
fi
```

**🔍 源码解析：**

Docker 的资源限制实现（Cgroup 层面）：

```go
// 源码参考：github.com/moby/moby/daemon/create.go
// 创建容器时的资源检查
func (daemon *Daemon) containerCreate(params types.ContainerCreateConfig) error {
    // CPU 检查
    if params.HostConfig.NanoCPUs > 0 {
        totalCPUs := int64(runtime.NumCPU())
        requestedCPUs := params.HostConfig.NanoCPUs / 1e9
        
        // Docker 默认不做超售检查（允许超过物理资源）
        // 但会记录警告日志
        if requestedCPUs > totalCPUs {
            logrus.Warnf("Requested %.1f CPUs but only %d available",
                float64(requestedCPUs), totalCPUs)
        }
    }
    
    // 内存检查
    if params.HostConfig.Memory > 0 {
        totalMem := getSystemMemory()
        if params.HostConfig.Memory > totalMem {
            return fmt.Errorf("requested memory %d exceeds system total %d",
                params.HostConfig.Memory, totalMem)
        }
    }
    
    return nil
}
```

**⚠️ 常见坑/加分回答：**

1. **内存超售导致 OOM**：内存不建议高比例超售。悦茶的 MySQL 和 Elasticsearch 容器分配了固定内存（不超售），其他服务可以适当超售。

2. **CPU 超售的时机问题**：所有容器同时需要 CPU 时会发生竞争。悦茶的批处理任务（如数据同步）安排在凌晨低峰期运行，错峰使用 CPU。

3. **磁盘 IO 竞争**：多个容器共享磁盘 IO。悦茶将 MySQL 和 Elasticsearch 的数据目录放在独立磁盘上，避免与其他服务竞争。

4. **加分回答**：提到 NUMA 架构对容器性能的影响——跨 NUMA 节点的内存访问延迟增加 30-50%。悦茶使用 `--cpuset-cpus` 将容器绑定到同一 NUMA 节点的 CPU 上。

Docker daemon 的 `live-restore` 功能实现：

```go
// 源码参考：github.com/moby/moby/daemon/daemon.go
// live-restore：daemon 重启时不杀死容器
func (daemon *Daemon) setupLiveRestore() {
    // 1. daemon 停止时，不向 containerd 发送停止信号
    // 2. containerd-shim 继续持有容器进程
    // 3. daemon 重启后，重新连接到已有的 shim
    
    // 实现原理：
    // daemon 停止 → shim 检测到连接断开 → shim 进入"孤儿"模式
    // → shim 继续运行容器，但不再向 daemon 报告状态
    // daemon 重启 → 扫描 /run/containerd/ 目录 → 发现已有的 shim
    // → daemon 重新连接到 shim → 恢复容器状态监控
}
```

Overlay2 的 `metacopy` 优化：

```go
// 源码参考：fs/overlayfs/copy_up.c
// metacopy 特性：只修改元数据时不需要 copy-up 整个文件
// Linux 4.19+ 支持

// 传统行为：chmod 修改文件权限
// → 将整个文件从 lower 复制到 upper（即使只改了一个权限位）
// → 大量 I/O

// metacopy 行为：
// → 只在上层创建一个 "metacopy" 文件（只包含元数据）
// → 数据仍然从 lower 层读取
// → 只有在文件内容被修改时才执行完整的 copy-up

// 效果：chmod、chown、touch 等操作性能提升 10-100 倍
// 悦茶的 Java 服务频繁修改配置文件权限，启用 metacopy 后构建速度提升 30%
```

**⚠️ 常见坑/加分回答：**

1. **`somaxconn` 不生效**：修改了 `net.core.somaxconn` 但 Java 应用还是只接受 128 个连接。原因：Spring Boot 的 Tomcat 有自己的 `server.tomcat.accept-count` 配置，需要同时修改。

2. **`nf_conntrack` 表满**：容器数量多时，连接跟踪表可能满，导致新连接被丢弃。错误信息：`nf_conntrack: table full, dropping packet`。悦茶的解决方案：增大表大小并加载 conntrack 模块。

3. **加分回答**：提到 `systemd` 作为 cgroup driver 比 `cgroupfs` 更稳定——systemd 统一管理 Cgroup 层次，避免 Docker 和其他进程（如 kubelet）的 Cgroup 冲突。

**⚠️ 常见坑/加分回答：**

1. **容器化的渐进式迁移**：悦茶没有一步到位全部容器化，而是先容器化无状态服务（订单、商品），再容器化有状态服务（MySQL、Redis），最后容器化监控栈。每一步都充分验证后才进入下一步。

2. **配置管理**：悦茶使用环境变量 + ConfigMap 的方式注入配置，不同环境（dev/staging/prod）通过不同的 `.env` 文件区分。敏感信息（数据库密码）使用 Docker Secret 或外部密钥管理服务。

3. **灾备方案**：MySQL 使用主从复制（容器化），数据通过 Volume 持久化，每天凌晨自动备份到 OSS。Redis 使用 AOF 持久化。

4. **加分回答**：提到悦茶从 Docker Compose 到 Kubernetes 的演进路径——当容器数量超过 30 个、需要跨主机部署时，Docker Compose 已经不够用，需要 Kubernetes 提供自动调度、自动扩缩、滚动更新等能力。Kubernetes 的学习曲线虽陡，但对于 3000+ 门店的悦茶平台来说，K8s 的运维自动化能力是不可或缺的。
