## 第1系列：分库分表基础（第1-4集）

### 第1集：为什么要分库分表？单库单表的瓶颈在哪？垂直拆分 vs 水平拆分的区别

**💡 核心回答：**

分库分表的核心目的是解决单机数据库在**数据量、并发连接、磁盘IO、CPU计算**四个维度上达到上限后的性能瓶颈问题。

**单库单表的瓶颈主要体现在：**
1. **磁盘容量瓶颈**：单表数据超过2000万行（约10GB+）后，B+树索引层数增加，查询性能显著下降
2. **连接数瓶颈**：单库最大连接数有限（MySQL默认151），高并发场景下连接池耗尽
3. **CPU瓶颈**：复杂查询（多表JOIN、排序、聚合）消耗大量CPU资源
4. **写入瓶颈**：单机磁盘IOPS有上限，高并发写入时成为瓶颈

**垂直拆分 vs 水平拆分：**

| 维度 | 垂直拆分 | 水平拆分 |
|------|---------|---------|
| 定义 | 按业务维度拆分，不同表放到不同库 | 同一张表的数据按规则拆分到多个库/表 |
| 场景 | 业务耦合度低，如订单库和用户库分离 | 单表数据量过大，如订单表超过5000万行 |
| 难点 | 跨库事务、跨库JOIN | 分布式ID、跨分片查询、扩容 |
| 对应用透明 | 是，业务无感知 | 部分透明，需处理分布式问题 |

**📦 实际例子：**

悦茶奶茶平台发展到3000+门店，日订单量突破50万单，订单表 `t_order` 数据量已经超过8000万行。运维团队发现：
- 订单列表查询从原来的50ms恶化到2000ms以上
- 高峰期数据库连接池频繁告警，活跃连接数打满
- 单表文件超过25GB，备份恢复时间超过2小时

**解决方案**：先做垂直拆分，将订单库（订单、支付、退款）与商品库（商品、SKU、库存）分离；再对订单表做水平拆分，按 `user_id` 分片到16个库，每个库4张表（共64张表），单表数据量控制在500万行以内。

**🔍 源码解析：**

ShardingSphere 的分库分表核心入口类为 `ShardingDataSource`，继承自 `AdapterDataSource`，在获取连接时通过分片规则路由到具体的数据源：

```java
// org.apache.shardingsphere.sharding.api.ShardingDataSource
public final class ShardingDataSource extends AdapterDataSource<ShardingSphereDataSource> {
    
    @Override
    public Connection getConnection() throws SQLException {
        // 获取运行时上下文，包含分片规则、SQL解析结果等
        ShardingSphereDataSource dataSource = getRuntimeContext().getDataSource();
        return dataSource.getConnection();
    }
}

// org.apache.shardingsphere.sharding.rule.ShardingRule - 分片规则核心
public final class ShardingRule implements Rule {
    // 获取表分片规则
    public Optional<TableRule> findTableRule(final String logicTableName) {
        return tableRules.stream()
            .filter(tableRule -> tableRule.getLogicTable().equalsIgnoreCase(logicTableName))
            .findFirst();
    }
    
    // 根据分片键值计算目标数据源和表
    public Collection<DataNode> route(final String logicTableName, 
                                       final Collection<ShardingCondition> shardingConditions) {
        TableRule tableRule = findTableRule(logicTableName).get();
        // 遍历分片条件，计算实际数据节点
        return shardingConditions.stream()
            .map(condition -> routeCondition(tableRule, condition))
            .flatMap(Collection::stream)
            .collect(Collectors.toList());
    }
}
```

分片规则配置的核心数据结构：

```java
    private final String logicTable;                    // 逻辑表名：t_order
    private final List<String> actualDataNodes;         // 实际数据节点：ds_0.t_order_0 ~ ds_15.t_order_3
```

**⚠️ 常见坑/加分回答：**

1. **分表阈值不是绝对的**：SSD盘和HDD盘的单表承载能力差异巨大，SSD环境下5000万行单表也能保持毫秒级查询，关键看实际压测数据
2. **不要过早分库分表**：先做好索引优化、读写分离、缓存层，数据量真正达到瓶颈再考虑分片
3. **加分回答**：可以提到 MySQL 8.0 的 Instant DDL 和 Clone Table 特性对大表操作的影响，以及阿里云 PolarDB、AWS Aurora 等云原生数据库对分库分表需求的冲击

### 第2集：ShardingSphere 的架构：Sharding-JDBC vs Sharding-Proxy vs Sharding-Sidecar 的定位和区别

**💡 核心回答：**

Apache ShardingSphere 提供三种部署模式，定位不同，适用场景各异：

| 模式 | 定位 | 部署方式 | 适用语言 | 性能 |
|------|------|---------|---------|------|
| **Sharding-JDBC** | Java SDK，嵌入式数据源 | 应用内嵌JAR | 仅Java | 最高（无网络开销） |
| **Sharding-Proxy** | 数据库代理服务 | 独立进程部署 | 语言无关 | 略低（多一跳网络） |
| **Sharding-Sidecar** | 服务网格模式 | 每Pod一侧车 | 语言无关 | 最低（双网络开销） |

**核心区别：**
- **Sharding-JDBC**：增强版JDBC驱动，应用直接引入依赖，对应用代码侵入性强但性能最好
- **Sharding-Proxy**：伪装成MySQL的独立服务，应用无感知，但多一层网络转发
- **Sharding-Sidecar**：K8s原生方案，每个Pod配一个代理，资源消耗最大

**📦 实际例子：**

悦茶平台技术栈选型过程：
- **订单服务**（Java/Spring Cloud）：选择 Sharding-JDBC，因为Java技术栈完全匹配，且订单查询QPS极高（峰值2万+），需要最低延迟
- **数据分析平台**（Python/Pandas）：选择 Sharding-Proxy，数据团队不需要改代码，直接用MySQL客户端连接Proxy查询分片后的数据
- **门店小程序后端**（Go语言）：原本考虑Sidecar，但团队评估后认为Go服务数量有限（8个Pod），直接配置Proxy地址更简单

**🔍 源码解析：**

ShardingSphere 的架构核心是 **Pluggable Architecture（可插拔架构）**，所有功能通过SPI机制动态加载：

```java
// org.apache.shardingsphere.infra.spi.ShardingSphereServiceLoader
public final class ShardingSphereServiceLoader {
    // SPI服务加载器，所有扩展点通过此机制发现
    private static final Map<Class<?>, Collection<Class<?>>> SERVICES = new ConcurrentHashMap<>();
    
    public static <T extends TypeBasedSPI> void register(final Class<T> serviceClass) {
        if (SERVICES.containsKey(serviceClass)) {
            return;
        }
        SERVICES.put(serviceClass, loadServiceClasses(serviceClass));
    }
    
    private static <T> Collection<Class<?>> loadServiceClasses(final Class<T> serviceClass) {
        return ServiceLoader.load(serviceClass)
            .stream()
            .map(ServiceLoader.Provider::type)
            .collect(Collectors.toList());
    }
}

// Sharding-JDBC 的核心数据源
// org.apache.shardingsphere.driver.ShardingSphereDriver
public final class ShardingSphereDriver implements Driver {
    @Override
    public Connection connect(final String url, final Properties info) throws SQLException {
        // 解析 JDBC URL 中的配置
        ShardingSphereDataSource dataSource = new ShardingSphereDataSource();
        dataSource.init(url);  // 初始化分片规则、数据源等
        return dataSource.getConnection();
    }
}

// Sharding-Proxy 的启动入口
// org.apache.shardingsphere.proxy.Bootstrap
public final class Bootstrap {
    public static void main(final String[] args) {
        // 启动MySQL协议的代理服务
        ProxyServer server = new ProxyServer();
        server.start(port);  // 默认3307端口
        // 注册数据库发现、分片路由等能力
        server.registerFeature(ShardingSphereFeature.SHARDING);
        server.registerFeature(ShardingSphereFeature.READWRITE_SPLITTING);
    }
}
```

请求处理流程对比：
```java
// Sharding-JDBC: 应用内直接处理
// App -> ShardingSphereDriver -> SQLParser -> Router -> Executor -> MySQL Driver -> MySQL

// Sharding-Proxy: 多一层网络
// App -> MySQL Protocol -> ProxyFrontend -> SQLParser -> Router -> Executor -> MySQL Backend -> MySQL
```

**⚠️ 常见坑/加分回答：**

1. **JDBC和Proxy不能混用**：同一个逻辑库不要一部分走JDBC一部分走Proxy，会导致分布式事务不一致
2. **Proxy的高可用**：Proxy本身是无状态的，前面挂LVS/HAProxy做负载均衡，后端连接MySQL连接池
3. **加分回答**：ShardingSphere 5.x 开始将JDBC和Proxy的代码统一，底层共享同一套SQL解析和路由引擎，差异仅在协议接入层

### 第3集：分片键（Sharding Key）的选择原则：如何选择合适的分片键，选择错误的后果

**💡 核心回答：**

分片键是决定数据分布到哪个分片的核心字段，选择原则：

1. **高频查询字段**：选择查询条件中最常出现的字段，避免全分片扫描
2. **数据分布均匀**：避免数据倾斜，某些分片数据量远超其他
3. **业务关联性强**：同一业务实体的数据尽量路由到同一分片，减少跨分片查询
4. **不可变字段**：分片键值一旦变化会导致数据迁移，选择后不能修改
5. **更新频率低**：避免频繁更新分片键导致的数据迁移开销

**选择错误的后果：**
- 选择 `create_time`：按时间分片导致老数据集中在早期分片，热点严重
- 选择 `order_no`：查询按 `user_id` 为主时，每次都需要全分片扫描（路由到64个分片）
- 选择 `status`：枚举值太少，导致数据严重倾斜

**📦 实际例子：**

悦茶订单表的 `t_order` 分片键选择过程：

| 候选分片键 | 优点 | 缺点 | 最终评估 |
|-----------|------|------|---------|
| `user_id` | C端查询90%按用户查，分布均匀 | 商户后台按门店查询需广播 | ✅ 采用 |
| `store_id` | 商户端查询友好 | 大门店数据倾斜严重 | ❌ 淘汰 |
| `order_no` | 唯一性好 | 和用户查询无关，全分片扫描 | ❌ 淘汰 |
| `create_time` | 范围查询友好 | 数据集中，热点严重 | ❌ 淘汰 |

最终方案：以 `user_id` 为主分片键，同时为商户后台查询建立 ES 索引（异构数据源），避免按 `store_id` 扫描数据库。

**🔍 源码解析：**

分片键在 ShardingSphere 中通过 `ShardingStrategy` 定义，核心接口：

```java
// org.apache.shardingsphere.sharding.api.sharding.ShardingStrategy
public interface ShardingStrategy {
    // 获取分片键列名
    Collection<String> getShardingColumns();
    
    // 执行分片，返回目标分片
    Collection<String> doSharding(final Collection<String> availableTargetNames, 
                                   final Collection<ShardingStrategyValue> shardingValues);
}

// org.apache.shardingsphere.sharding.api.sharding.standard.StandardShardingStrategy
// 标准分片策略，支持单分片键精确匹配和范围查询
public final class StandardShardingStrategy implements ShardingStrategy {
    
    @Override
    public Collection<String> doSharding(final Collection<String> availableTargetNames,
                                          final Collection<ShardingStrategyValue> shardingValues) {
        ShardingStrategyValue value = shardingValues.iterator().next();
        // 精确分片：走精确分片算法
        if (value instanceof PreciseShardingValue) {
            PreciseShardingValue preciseValue = (PreciseShardingValue) value;
            return Collections.singleton(
                shardingAlgorithm.doSharding(availableTargetNames, preciseValue)
            );
        }
        // 范围分片：走范围分片算法
        if (value instanceof RangeShardingValue) {
            RangeShardingValue rangeValue = (RangeShardingValue) value;
            return shardingAlgorithm.doSharding(availableTargetNames, rangeValue);
        }
        return availableTargetNames;  // 无分片条件时广播
    }
}

// 分片规则中如何绑定分片键
// org.apache.shardingsphere.sharding.rule.ShardingRule
private void buildShardingColumns(final ShardingTableRuleConfiguration config) {
    // 数据库分片键列
    this.databaseShardingStrategy = config.getDatabaseShardingStrategy();
    // 表分片键列  
    this.tableShardingStrategy = config.getTableShardingStrategy();
    // 分片键必须存在于SQL的WHERE条件中才能精确路由
}
```

SQL解析时如何判断是否携带分片键：

```java
// org.apache.shardingsphere.sharding.route.engine.condition.ShardingConditionRouter
public class ShardingConditionRouter {
    
    public ShardingRouteContext route(final SQLStatementContext sqlStatementContext,
                                       final ShardingRule shardingRule) {
        // 从SQL WHERE条件中提取分片键值
        ShardingConditions shardingConditions = 
            createShardingConditions(sqlStatementContext, shardingRule);
        
        // 判断是否所有分片键都有值（精确路由条件）
        if (shardingConditions.isAlwaysFalse()) {
            // 无分片条件 -> 全路由
            return ShardingRouteContext.fullRoute();
        }
        
        // 有分片条件 -> 精确路由到具体分片
        Collection<DataNode> dataNodes = shardingRule.route(logicTable, shardingConditions);
        return new ShardingRouteContext(dataNodes);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **多分片键场景**：如果业务确实需要按 `user_id` 和 `store_id` 两种维度查询，不要试图用双分片键，应该采用"主分片键+异构索引"方案（如ES冗余一份按store_id索引的数据）
2. **分片键为NULL**：ShardingSphere对分片键为NULL的查询会走广播路由，性能极差，必须业务层保证分片键非空
3. **加分回答**：可以提到Facebook的MySQL分片方案中使用的"Look-Aside Table"解决非分片键查询的问题

### 第4集：分片算法：Hash取模、范围分片、时间分片、自定义分片算法的实现和对比

**💡 核心回答：**

ShardingSphere 提供多种内置分片算法，各有适用场景：

| 分片算法 | 原理 | 优点 | 缺点 | 适用场景 |
|---------|------|------|------|---------|
| **Hash取模** | `hash(key) % N` | 数据分布均匀 | 扩容困难 | 用户表、通用业务表 |
| **范围分片** | 按ID范围划分，如1-100万→分片0 | 扩容方便 | 数据可能倾斜 | 订单表（按订单ID范围） |
| **时间分片** | 按时间区间划分 | 历史数据易归档 | 当前月数据热点 | 日志表、流水表 |
| **自定义** | 实现ShardingAlgorithm接口 | 灵活适配业务 | 开发成本高 | 特殊业务需求 |

**扩容友好度对比**：
- Hash取模：扩容需要全量数据重新分布（一致性Hash可缓解）
- 范围分片：只需新增分片，历史数据不动
- 时间分片：天然支持，新时间段直接用新分片

**📦 实际例子：**

悦茶平台不同表的算法选择：

**🔍 源码解析：**

ShardingSphere 的分片算法通过 SPI 扩展，核心接口：

```java
// org.apache.shardingsphere.sharding.spi.ShardingAlgorithm
public interface ShardingAlgorithm extends TypeBasedSPI {
    // 初始化算法配置
    void init(Properties props);
}

// 标准分片算法接口（精确+范围）
// org.apache.shardingsphere.sharding.spi.StandardShardingAlgorithm
public interface StandardShardingAlgorithm<T extends Comparable<?>> extends ShardingAlgorithm {
    // 精确分片：SQL中 WHERE sharding_key = ?
    String doSharding(Collection<String> availableTargetNames, PreciseShardingValue<T> shardingValue);
    
    // 范围分片：SQL中 WHERE sharding_key BETWEEN ? AND ?
    Collection<String> doSharding(Collection<String> availableTargetNames, RangeShardingValue<T> shardingValue);
}

// Hash取模算法实现
// org.apache.shardingsphere.sharding.algorithm.key.hash.HashModShardingAlgorithm
public final class HashModShardingAlgorithm implements StandardShardingAlgorithm<String> {
    
    private int shardingCount;
    
    @Override
    public void init(Properties props) {
        this.shardingCount = Integer.parseInt(props.getProperty("sharding-count"));
    }
    
    @Override
    public String doSharding(Collection<String> availableTargetNames, 
                              PreciseShardingValue<String> shardingValue) {
        // 对分片键值取hash后取模
        int hashValue = Math.abs(shardingValue.getValue().hashCode());
        int index = hashValue % shardingCount;
        // 拼接目标分片名，如 ds_3 或 t_order_2
        for (String each : availableTargetNames) {
            if (each.endsWith("_" + index) || each.endsWith(String.valueOf(index))) {
                return each;
            }
        }
        throw new ShardingSphereException("No matching sharding target found");
    }
}

// 自定义分片算法示例（悦茶按门店区域+用户ID混合路由）
// 实现：一线城市门店走高性能集群，二三线城市走标准集群
public class RegionMixedShardingAlgorithm implements StandardShardingAlgorithm<Long> {
    
    private static final Map<String, Integer> REGION_INDEX = Map.of(
        "tier1", 0,   // 一线城市 -> ds_tier1_*
        "tier2", 1,   // 二线城市 -> ds_tier2_*
        "tier3", 2    // 三线城市 -> ds_tier3_*
    );
    
    @Override
    public String doSharding(Collection<String> availableTargetNames, 
                              PreciseShardingValue<Long> shardingValue) {
        Long userId = shardingValue.getValue();
        // 根据用户注册时的区域标签路由
        int region = getUserRegion(userId);
        int subIndex = (int)(userId % 4);  // 每个区域4个分片
        String targetSuffix = region + "_" + subIndex;
        return availableTargetNames.stream()
            .filter(name -> name.endsWith(targetSuffix))
            .findFirst()
            .orElseThrow();
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **Hash取模扩容**：Hash取模分片数变更时（如从16扩到32），需要做数据迁移。推荐方案：翻倍扩容法（见第25集），从N扩到2N，每个分片拆成两个，只需迁移一半数据
2. **时间分片的当前月热点**：当前月分片承受全部写入压力，建议当前月再细分（如按天或按用户ID二级分片）
3. **一致性Hash**：ShardingSphere 4.x 提供了 ConsistentHash 算法，扩容时只需迁移部分数据，适合对扩容有要求的场景
4. **加分回答**：可以对比美团Leaf、阿里DRDS的分片策略实现差异

## 第2系列：SQL路由与重写（第5-8集）

### 第5集：SQL路由的完整流程：解析 → 路由 → 改写 → 执行的链路

**💡 核心回答：**

ShardingSphere 处理一条SQL的完整链路为：

```
SQL输入 → SQL解析(Parse) → SQL路由(Route) → SQL改写(Rewrite) → SQL执行(Execute) → 结果归并(Merge)
```

1. **SQL解析**：使用ANTLR将SQL文本解析为抽象语法树（AST），提取表名、条件、列名等信息
2. **SQL路由**：根据分片规则和SQL中的分片键值，计算目标数据源和表
3. **SQL改写**：将逻辑表名替换为真实表名，处理分页、AVG、ORDER BY等特殊SQL改写
4. **SQL执行**：多线程并发向各目标分片发送改写后的SQL
5. **结果归并**：将多个分片返回的结果集进行合并、排序、聚合，形成最终结果

**📦 实际例子：**

悦茶平台用户查询订单的场景：

```sql
-- 用户在前端查看自己的订单列表（逻辑SQL）
SELECT order_id, order_no, total_amount, status 
FROM t_order 
WHERE user_id = 10086 
  AND create_time > '2025-01-01'
ORDER BY create_time DESC 
LIMIT 10;
```

处理链路：
1. **解析**：识别出表名 `t_order`，分片键 `user_id = 10086`
2. **路由**：`hash(10086) % 16 = 5` → 路由到 `ds_5`，`hash(10086) % 4 = 2` → `t_order_2`
3. **改写**：`SELECT ... FROM ds_5.t_order_2 WHERE user_id = 10086 ... LIMIT 10`
4. **执行**：只需查询1个分片，直接执行
5. **归并**：单分片结果直接返回，无需归并

如果是商户后台按 `store_id` 查询（无分片键），则路由到全部64个分片，执行64次SQL后归并排序。

**🔍 源码解析：**

完整的执行链路在 `ShardingSphereStatementExecuteEngine` 中编排：

```java
                               final Collection<ParameterMarkerSegment> params,
                               final ShardingRule shardingRule,
                               final ShardingSphereDatabase database) {

            shardingConditionEngine.createShardingConditions(sqlStatementContext, params);

        if (shardingConditions.isAlwaysFalse()) {

            return createBroadcastRoute(shardingRule);
        }

        } else {

            return createCartesianRoute(shardingRule, shardingConditions);
        }
    }
}
```

1. **路由决策在解析阶段**：如果SQL解析失败（如不支持的SQL语法），整个SQL都无法执行，不只是路由失败
2. **SQLHint可以覆盖路由**：通过 `HintManager.getInstance().addDatabaseShardingValue()` 强制指定路由目标
3. **加分回答**：ShardingSphere 5.x 引入了 RouteContext 统一路由上下文，替代了4.x中的 RoutingResult，支持缓存路由结果减少重复计算

### 第6集：SQL解析引擎：ShardingSphere 的 SQLParser（基于 ANTLR）如何解析 SQL 抽象语法树

**💡 核心回答：**

ShardingSphere 的 SQL 解析引擎基于 **ANTLR4**（ANother Tool for Language Recognition）构建，支持 MySQL、PostgreSQL、Oracle、SQL Server 等主流数据库方言。

**解析流程：**
1. **词法分析（Lexer）**：将SQL字符串拆分为Token流（关键字、标识符、运算符、字面量等）
2. **语法分析（Parser）**：根据语法规则将Token流构建为**抽象语法树（AST）**
3. **语义提取**：遍历AST提取关键信息：表名、列名、条件、函数调用等
4. **统一抽象**：将不同数据库方言的AST统一转换为 ShardingSphere 的 `SQLStatement` 接口

**📦 实际例子：**

悦茶平台订单查询SQL的解析过程：

```sql
-- 原始SQL
SELECT o.order_no, o.total_amount, u.nickname 
FROM t_order o 
INNER JOIN t_user u ON o.user_id = u.id 
WHERE o.user_id = 10086 
  AND o.status IN (1, 2, 3)
ORDER BY o.create_time DESC 
LIMIT 0, 10;
```

解析后的AST关键节点：
```
SelectStatement
├── projection: [o.order_no, o.total_amount, u.nickname]
├── from: JoinTable
│   ├── left: SimpleTable(t_order, alias=o)
│   ├── right: SimpleTable(t_user, alias=u)
│   └── on: o.user_id = u.id
├── where: AndPredicate
│   ├── BinaryPredicate(o.user_id = 10086)     ← 分片键条件
│   └── InPredicate(o.status IN (1,2,3))
├── orderBy: o.create_time DESC
└── limit: offset=0, rowCount=10
```

**🔍 源码解析：**

ANTLR4 语法定义文件和解析引擎的核心类：

```java
// org.apache.shardingsphere.sql.parser.api.SQLParserEngine
public final class SQLParserEngine {
    
    private final SQLParserFactory sqlParserFactory;
    
    public SQLStatement parse(final String sql, final boolean useCache) {
        // 1. 缓存检查（相同SQL不重复解析）
        if (useCache) {
            Optional<SQLStatement> cachedStatement = cacheEngine.get(sql);
            if (cachedStatement.isPresent()) {
                return cachedStatement.get();
            }
        }
        
        // 2. 创建ANTLR解析器（根据数据库类型选择对应方言）
        SQLParser sqlParser = sqlParserFactory.newInstance(sql);
        
        // 3. 词法分析 + 语法分析 → 生成ParseTree
        ParseTree parseTree = sqlParser.parse();
        
        // 4. AST构建：遍历ParseTree构建ShardingSphere的AST
        SQLStatementASTExtractor extractor = new SQLStatementASTExtractor();
        SQLStatement statement = extractor.extract(parseTree);
        
        // 5. 缓存结果
        if (useCache) {
            cacheEngine.put(sql, statement);
        }
        return statement;
    }
}
```

### 第7集：SQL改写的核心逻辑：分表名替换、分页改写、AVG改写、ORDER BY 补列

**💡 核心回答：**

SQL改写是ShardingSphere将逻辑SQL转换为可在各分片上实际执行的物理SQL的核心环节，主要包括以下改写类型：

1. **分表名改写**：将逻辑表名替换为实际物理表名（`t_order` → `t_order_3`）
2. **分页改写**：将 `LIMIT 10, 5` 改写为 `LIMIT 0, 15`（确保所有分片返回足够数据用于归并排序）
3. **AVG改写**：将 `AVG(price)` 改写为 `SUM(price)/COUNT(price)`（因为跨分片不能直接求平均）
4. **ORDER BY补列**：当ORDER BY的列不在SELECT列表中时，自动补充到SELECT列表（归并排序需要）
5. **OFFSET改写**：将OFFSET值调整为0（每个分片从头开始取数据）

**📦 实际例子：**

悦茶平台订单列表查询的改写过程：

```sql
-- 逻辑SQL（用户输入）
SELECT order_no, status 
FROM t_order 
WHERE user_id = 10086 
ORDER BY create_time DESC 
LIMIT 20, 10;

-- 改写后的物理SQL（路由到 ds_5.t_order_2）
SELECT order_no, status, create_time   -- ORDER BY补列：create_time被补充
FROM t_order_2                          -- 分表名改写
WHERE user_id = 10086 
ORDER BY create_time DESC 
LIMIT 0, 30;                           -- 分页改写：OFFSET归零，行数=20+10=30
```

改写原因：
- **分表名**：物理表名是 `t_order_2`，不是逻辑表 `t_order`
- **ORDER BY补列**：归并排序需要 `create_time`，原始SQL没有SELECT它
- **分页改写**：各分片各自排序，需要取前30条才能保证全局前10条正确

**🔍 源码解析：**

SQL改写引擎的核心实现：

```java
// org.apache.shardingsphere.sql.rewrite.engine.SQLRewriteEngine
public final class SQLRewriteEngine {
    
    public SQLRewriteContext rewrite(final RouteContext routeContext,
                                      final QueryContext queryContext) {
        SQLRewriteContext context = new SQLRewriteContext(queryContext);
        
        // 1. 分表名改写（核心）
        context.getSqlRewriteResults().addAll(
            rewriteTableNames(routeContext, context)
        );
        
        // 2. 分页改写
        if (containsPagination(queryContext)) {
            context.getSqlRewriteResults().add(
                rewritePagination(queryContext)
            );
        }
        
        // 3. AVG改写
        if (containsAggregation(queryContext)) {
            context.getSqlRewriteResults().add(
                rewriteAggregation(queryContext)
            );
        }
        
        // 4. ORDER BY补列改写
        if (containsOrderByWithoutSelect(queryContext)) {
            context.getSqlRewriteResults().add(
                rewriteOrderBySupplement(queryContext)
            );
        }
        
        return context;
    }
    
    // 分页改写的核心逻辑
    private SQLRewriteResult rewritePagination(final QueryContext queryContext) {
        int offset = queryContext.getLimit().getOffset();
        int rowCount = queryContext.getLimit().getRowCount();
        
        // 改写：OFFSET归零，行数 = offset + rowCount
        // 确保每个分片返回足够数据供归并排序
        int rewrittenOffset = 0;
        int rewrittenRowCount = offset + rowCount;
        
        return new PaginationRewriteResult(rewrittenOffset, rewrittenRowCount);
    }
    
    // AVG改写：将 AVG(col) 改为 SUM(col), COUNT(col)
    private SQLRewriteResult rewriteAggregation(final QueryContext queryContext) {
        // 原始：SELECT AVG(price) FROM t_order
        // 改写：SELECT SUM(price), COUNT(price) FROM t_order
        // 归并时：全局AVG = 各分片SUM之和 / 各分片COUNT之和
        return new AggregationRewriteResult("SUM", "COUNT");
    }
}

// 分表名改写的实现
// org.apache.shardingsphere.sql.rewrite.engine.token.TableTokenRewriteEngine
public final class TableTokenRewriteEngine {
    
    public Collection<SQLToken> generateSQLTokens(final RouteContext routeContext) {
        Collection<SQLToken> tokens = new LinkedList<>();
        
        // 遍历路由结果中的每个执行单元
        for (ExecutionUnit unit : routeContext.getExecutionUnits()) {
            // 逻辑表名 → 实际表名
            String logicTable = unit.getLogicTable();
            String actualTable = unit.getActualTable();  // 如 t_order_2
            
            tokens.add(new TableToken(
                logicTable,     // 原始Token位置
                actualTable     // 替换后的表名
            ));
        }
        return tokens;
    }
}
```

分页改写的数学原理：
```
原始分页：LIMIT offset, rowCount（如 LIMIT 20, 10 表示跳过20条取10条）
分片数量：N = 64

改写后：LIMIT 0, (offset + rowCount)  = LIMIT 0, 30
原因：每个分片独立排序，取前30条
归并：从64个分片各30条（共1920条）中全局排序，取第21~30条

代价：分页越深，性能越差（LIMIT 10000, 10 需要每个分片取10010条）
```

**⚠️ 常见坑/加分回答：**

1. **深度分页问题**：`LIMIT 100000, 10` 会导致每个分片返回100010条数据，64个分片共640万条数据参与归并，性能极差。解决方案：使用"延迟关联"或"游标分页"（`WHERE id > last_id LIMIT 10`）
2. **AVG精度丢失**：改写后的 `SUM/COUNT` 在归并时需要注意浮点精度，建议使用 `DECIMAL` 类型
3. **加分回答**：ShardingSphere 4.1+ 引入了分页的"流式归并"，不把所有数据加载到内存，而是用归并排序的方式流式处理，大幅降低内存占用

### 第8集：广播路由 vs 标准路由 vs 笛卡尔路由：什么场景走哪种路由

**💡 核心回答：**

ShardingSphere 的路由策略根据SQL条件的完整度分为三类：

| 路由类型 | 触发条件 | 目标分片数 | 性能 |
|---------|---------|-----------|------|
| **标准路由** | 分片键有精确值（`WHERE user_id = ?`） | 1个分片 | 最优 |
| **笛卡尔路由** | 多个分片键部分有值，需要组合 | 多个分片（组合数） | 较差 |
| **广播路由** | 无分片键条件（`WHERE status = ?`） | 全部分片 | 最差 |

**判断逻辑**：
- SQL的WHERE条件包含分片键的精确值 → **标准路由**
- SQL包含多个分片键的条件，但需要笛卡尔积计算 → **笛卡尔路由**
- SQL不包含任何分片键 → **广播路由**（全分片扫描）

**📦 实际例子：**

悦茶平台的三种路由场景：

```sql
-- 场景1：标准路由（C端用户查自己的订单）
-- 分片键 user_id = 10086，精确路由到1个分片
SELECT * FROM t_order WHERE user_id = 10086 AND order_no = 'YC20250101001';
-- 路由结果：ds_5.t_order_2（1个分片）

-- 场景2：笛卡尔路由（按用户+门店组合查询）
-- 需要 user_id 和 store_id 的分片笛卡尔积
SELECT * FROM t_order WHERE user_id = 10086 AND store_id = 2001;
-- 路由结果：user_id→ds_5, store_id→ds_3,ds_7 → 笛卡尔积可能产生多个组合

-- 场景3：广播路由（运营后台按状态查询）
-- 无分片键，必须扫描全部分片
SELECT * FROM t_order WHERE status = 1 AND create_time > '2025-01-01';
-- 路由结果：ds_0~ds_15 的 t_order_0~t_order_3，共64个分片全部扫描
```

**🔍 源码解析：**

路由类型的判断逻辑在 `ShardingSQLRouter` 中：

```java
// org.apache.shardingsphere.sharding.route.engine.ShardingSQLRouter
public final class ShardingSQLRouter {
    
    public RouteContext route(final SQLStatementContext sqlStatementContext,
                               final ShardingRule shardingRule) {
        // 提取分片条件
        ShardingConditions shardingConditions = 
            shardingConditionEngine.createShardingConditions(sqlStatementContext);
        
        // 判断路由类型
        if (shardingConditions.getShardingConditions().isEmpty()) {
            // 无任何分片条件 → 广播路由
            return buildBroadcastRouteContext(shardingRule);
        }
        
        // 判断是否是笛卡尔路由
        if (isCartesianRoute(shardingConditions)) {
            return buildCartesianRouteContext(shardingRule, shardingConditions);
        }
        
        // 标准路由
        return buildStandardRouteContext(shardingRule, shardingConditions);
    }
    
    // 广播路由：全分片扫描
    private RouteContext buildBroadcastRouteContext(final ShardingRule shardingRule) {
        Collection<ExecutionUnit> executionUnits = new LinkedList<>();
        for (String dataSource : shardingRule.getAllDataSourceNames()) {
            for (String table : shardingRule.getAllTableNames()) {
                executionUnits.add(new ExecutionUnit(dataSource, new SQLUnit(table, Collections.emptyList())));
            }
        }
        return new RouteContext(executionUnits, RouteType.BROADCAST);
    }
    
    // 笛卡尔路由：多分片键组合
    private RouteContext buildCartesianRouteContext(final ShardingRule shardingRule,
                                                     final ShardingConditions conditions) {
        // 对每个分片键独立路由，然后取笛卡尔积
        Collection<Collection<String>> dataSourceResults = new LinkedList<>();
        Collection<Collection<String>> tableResults = new LinkedList<>();
        
        for (ShardingCondition condition : conditions.getShardingConditions()) {
            Collection<String> dataSources = routeDataSources(condition);
            Collection<String> tables = routeTables(condition);
            dataSourceResults.add(dataSources);
            tableResults.add(tables);
        }
        
        // 笛卡尔积计算
        Collection<List<String>> cartesianDataSources = Sets.cartesianProduct(dataSourceResults);
        Collection<List<String>> cartesianTables = Sets.cartesianProduct(tableResults);
        
        return buildRouteContext(cartesianDataSources, cartesianTables, RouteType.CARTESIAN);
    }
    
    // 标准路由：精确路由
    private RouteContext buildStandardRouteContext(final ShardingRule shardingRule,
                                                    final ShardingConditions conditions) {
        String dataSource = routeSingleDataSource(conditions);
        String table = routeSingleTable(conditions);
        return new RouteContext(
            Collections.singletonList(new ExecutionUnit(dataSource, new SQLUnit(table))),
            RouteType.STANDARD
        );
    }
}
```

广播路由的优化策略：

```java
// org.apache.shardingsphere.sharding.route.engine.type.broadcast.BroadcastRouteEngine
public final class BroadcastRouteEngine {
    
    // 广播路由优化：如果SQL中包含了可以用索引加速的条件
    // 可以在各分片上利用索引，减少全表扫描
    public Collection<ExecutionUnit> route(final BroadcastRouteContext context) {
        return context.getActualDataNodes().stream()
            .map(node -> new ExecutionUnit(
                node.getDataSourceName(),
                new SQLUnit(node.getTableName())
            ))
            .collect(Collectors.toList());
        // 注意：即使SQL有非分片键条件，也要广播到全部分片
        // 但在每个分片上可以利用该条件的索引加速
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **广播路由的性能灾难**：64个分片的广播路由相当于一次查询发起64次SQL，如果单片10ms，总耗时可能达到100ms+（线程池并行后约为单片耗时+网络开销）。**必须避免**在生产环境出现大量广播路由
2. **笛卡尔路由的放大效应**：如果两个分片键各自路由到3个分片，笛卡尔积就是 3×3=9 个分片
3. **减少广播路由的方案**：
   - 非分片键查询走 ES/ClickHouse 等异构数据源
   - 对于状态查询，增加分片键条件（如限定特定用户群体）
4. **加分回答**：可以提到 ShardingSphere 的 "Hint广播" 机制，通过 HintManager 手动指定路由目标，避免不必要的广播

### 第9集：分布式 ID 生成方案对比：UUID、数据库自增、号段模式、雪花算法、Leaf

**💡 核心回答：**

分库分表后，各分片数据库的自增ID不再全局唯一，必须使用分布式ID生成方案。

| 方案 | 全局唯一 | 趋势递增 | 有序性 | 性能 | 可预测 | 适用场景 |
|------|---------|---------|--------|------|--------|---------|
| **UUID** | ✅ | ❌ | ❌ 无序 | 高 | ❌ | 不要求有序的场景（临时令牌） |
| **数据库自增** | ✅（单库） | ✅ | ✅ | 低（单点） | ✅ | 单库场景 |
| **号段模式** | ✅ | ✅ | ✅ | 高（批量） | ✅ | 订单号、业务编号 |
| **雪花算法** | ✅ | ✅ | ✅ | 极高 | 部分 | 高并发通用场景 |
| **Leaf** | ✅ | ✅ | ✅ | 极高 | ✅ | 美团开源，生产级方案 |

**核心考量维度**：
- **全局唯一**：分库分表必须保证ID在所有分片不冲突
- **趋势递增**：数据库B+Tree索引偏好递增数据，避免页分裂
- **性能**：高并发场景要求ID生成QPS达到10万+
- **长度**：过长的ID影响索引大小和查询性能

**📦 实际例子：**

悦茶平台的订单号生成方案选择：


```java
// UUID实现（Java标准库）
public class UUIDGenerator {
    public String generate() {
        return UUID.randomUUID().toString().replace("-", ""); // 32位
    }
    // 缺点：完全无序，B+Tree插入时随机位置导致页分裂

// 雪花算法核心实现
// org.apache.shardingsphere.keygen.snowflake.algorithm.SnowflakeKeyGenerateAlgorithm
public final class SnowflakeKeyGenerateAlgorithm implements KeyGenerateAlgorithm {
    
    // 时间戳部分：41位，可用69年
    private static final long TIMESTAMP_SHIFT = 22;
    // WorkerID：10位，支持1024个节点
    private static final long WORKER_ID_BITS = 10L;
    // 序列号：12位，每毫秒4096个ID
    private static final long SEQUENCE_BITS = 12L;
    
    private final long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    @Override
    public synchronized long generateKey() {
        long currentTimestamp = System.currentTimeMillis();
        
        if (currentTimestamp < lastTimestamp) {
            // 时钟回拨处理！
            long refusedTimestamp = lastTimestamp - currentTimestamp;
            if (refusedTimestamp > 5) {
                throw new ClockMovedBackException("Clock moved back " + refusedTimestamp + "ms");
            }
            // 回拨小于5ms，等待追上来
            while (currentTimestamp <= lastTimestamp) {
                currentTimestamp = System.currentTimeMillis();
            }
        }
        
        if (currentTimestamp == lastTimestamp) {
            sequence = (sequence + 1) & ((1 << SEQUENCE_BITS) - 1);
            if (sequence == 0) {
                // 当前毫秒序列号用完，等待下一毫秒
                currentTimestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        
        lastTimestamp = currentTimestamp;
        
        // 组合：时间戳 | WorkerID | 序列号
        return ((currentTimestamp - EPOCH) << TIMESTAMP_SHIFT) 
             | (workerId << SEQUENCE_BITS) 
             | sequence;
    }
    
    private long waitNextMillis(final long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}

// 号段模式实现（类似美团Leaf-segment）
public class SegmentKeyGenerator {
    
    private final DataSource dataSource;  // 数据库存储当前最大ID
    private volatile Segment currentSegment;
    
    // 号段：每次从数据库取一批ID

        if (currentSegment == null || !currentSegment.hasAvailable()) {
            synchronized (this) {
                if (currentSegment == null || !currentSegment.hasAvailable()) {
                    currentSegment = loadNextSegment();  // 从DB加载下一个号段
                }
            }
        }
        return currentSegment.getAndIncrement();
    }
    
    private Segment loadNextSegment() {
        // SELECT max_id FROM id_generator WHERE biz_type = 'order' FOR UPDATE;
        // UPDATE id_generator SET max_id = max_id + step WHERE biz_type = 'order';
        long maxId = getMaxIdFromDB();
        int step = 1000;  // 每次取1000个ID
        return new Segment(maxId, maxId + step);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **UUID的索引灾难**：UUID完全无序，插入MySQL InnoDB时B+Tree频繁页分裂，写入性能比有序ID低30-50%。如果非要用UUID，建议用UUID v7（时间有序）或 ULID
2. **雪花算法的时钟依赖**：所有节点的时钟必须同步（NTP），否则可能产生重复ID。可以配置时钟回拨容忍阈值
3. **号段模式的预加载**：当号段用到50%时异步加载下一个号段（双Buffer），避免同步加载导致的ID生成抖动
4. **加分回答**：可以对比Leaf的两种模式（segment模式 vs snowflake模式），以及滴滴TinyID的改进方案

### 第10集：ShardingSphere 内置雪花算法的实现：Worker ID 的分配策略、时钟回拨处理

**💡 核心回答：**

ShardingSphere 的雪花算法实现在 `SnowflakeKeyGenerateAlgorithm` 类中，核心关注两个问题：

**Worker ID 分配策略：**
- **IP+Port组合**：默认使用 `IP地址的HashCode + 端口号` 取模得到WorkerID
- **Zookeeper协调**：分布式环境下通过ZK临时节点保证WorkerID不冲突
- **手动指定**：配置文件直接指定WorkerID（适合K8s环境）

**时钟回拨处理：**
- 回拨 < 5ms：自旋等待，等时钟追上来
- 回拨 5ms ~ 容忍阈值：等待或抛出异常
- 回拨 > 容忍阈值：直接拒绝生成，保护ID唯一性

**📦 实际例子：**

悦茶平台在K8s上部署订单服务（8个Pod），Worker ID分配：

```java
// org.apache.shardingsphere.keygen.snowflake.algorithm.SnowflakeKeyGenerateAlgorithm
public final class SnowflakeKeyGenerateAlgorithm implements KeyGenerateAlgorithm {
    
    private static final long EPOCH = 1489111200000L;  // 自定义纪元
    private static final long SEQUENCE_BITS = 12L;
    private static final long WORKER_ID_BITS = 10L;
    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);  // 1023
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);    // 4095
    
    private final long workerId;
    private final long maxTolerateTimeMilliseconds;
    private final long maxClockOffsetMilliseconds;
    
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    // Worker ID 的分配策略
    private static long getWorkerId(Properties props) {
        String configuredWorkerId = props.getProperty("worker-id");
        if (configuredWorkerId != null) {
            return Long.parseLong(configuredWorkerId);
        }
        // 默认：基于IP + Port计算
        String ip = InetAddress.getLocalHost().getHostAddress();
        int port = getServerPort();  // 应用端口
        return (ip.hashCode() + port) & MAX_WORKER_ID;
    }
    
    // 时钟回拨的核心处理逻辑
    @Override
    public synchronized long generateKey() {
        long currentTimestamp = tick();
        
        if (currentTimestamp < lastTimestamp) {
            long timeDiff = lastTimestamp - currentTimestamp;
            
            if (timeDiff <= maxClockOffsetMilliseconds) {
                // 小幅回拨：自旋等待
                while (currentTimestamp <= lastTimestamp) {
                    Thread.yield();
                    currentTimestamp = tick();
                }
            } else if (timeDiff <= maxTolerateTimeMilliseconds) {
                // 中等回拨：等待到容忍阈值
                long waitTime = maxTolerateTimeMilliseconds;
                try {
                    Thread.sleep(waitTime);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                currentTimestamp = tick();
                if (currentTimestamp < lastTimestamp) {
                    throw new ClockMovedBackException(
                        "Clock moved back. Last: " + lastTimestamp 
                        + ", Current: " + currentTimestamp
                    );
                }
            } else {
                // 大幅回拨：直接拒绝
                throw new ClockMovedBackException(
                    "Clock moved back significantly. Refusing to generate key for " 
                    + timeDiff + " milliseconds"
                );
            }
        }
        
        if (currentTimestamp == lastTimestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {
                // 当前毫秒用完，等待下一毫秒
                currentTimestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        
        lastTimestamp = currentTimestamp;
        
        return composeKey(currentTimestamp, workerId, sequence);
    }
    
    // ID组合：时间戳(41位) | WorkerID(10位) | 序列号(12位)
    private long composeKey(long timestamp, long workerId, long sequence) {
        return ((timestamp - EPOCH) << (WORKER_ID_BITS + SEQUENCE_BITS))
             | (workerId << SEQUENCE_BITS)
             | sequence;
    }
}
```

### 第11集：分布式 ID 在分库分表中的作用：为什么需要全局唯一 ID，和分片键的关系

**💡 核心回答：**

**为什么需要全局唯一ID：**
1. **数据标识唯一性**：分库分表后，各分片自增ID会重复（每个分片都有id=1的记录）
2. **跨分片定位**：需要通过ID直接定位到数据所在的分片，避免全分片扫描
3. **关联数据一致性**：订单ID关联的支付记录、物流记录需要引用同一个ID

**分布式ID和分片键的关系：**
- **理想情况**：分布式ID本身包含分片键信息，通过ID可以直接计算分片位置
- **常见做法**：分片键单独存储（如user_id），分布式ID独立生成（如订单号），两者通过映射表关联
- **进阶做法**：将分片键编码到分布式ID中，实现"ID即路由"

**📦 实际例子：**

```
- 订单号（分布式雪花ID）：245678901234567
- 分片键（user_id）：10086
- 关系：t_order表存储 order_id + user_id，通过user_id路由

方案B（编码方案 - 悦茶采用）：

- 分片键隐含在订单号中：后4位 0086 → hash(0086) % 16 = 5 → ds_5
- 优点：通过订单号直接路由，不需要先查user_id
```

### 第12集：分段模式（Segment）的实现原理：号段模式的优缺点、预加载机制

**💡 核心回答：**

号段模式（Segment Mode）的核心思想是：**每次从数据库批量获取一段ID（号段），在内存中使用，用完再取下一段**。

**工作原理：**
1. 维护一个数据库表存储当前最大ID（max_id）
2. 应用启动或号段用完时，从DB获取一个号段 [min, max)
3. 在内存中从min开始递增分配，直到max
4. 当用到max时，再次从DB获取下一个号段

**预加载机制（双Buffer）：**
- 当当前号段使用到 **50%** 时，异步线程开始加载下一个号段
- 当前号段用完时，下一个号段已准备就绪，无需等待DB IO
- 大幅降低ID生成的延迟抖动

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 高性能（内存中分配，无网络开销） | 应用重启会丢失号段中未使用的ID（ID不连续） |
| 趋势递增（数据库索引友好） | 依赖数据库可用性（DB挂掉影响号段获取） |
| 实现简单 | ID可预测（安全风险） |
| 支持多业务（不同biz_type独立号段） | 不适合超高并发（相比雪花算法有差距） |

**📦 实际例子：**

悦茶平台的退款单号生成采用号段模式：

```sql
    update_time DATETIME NOT NULL
```

ShardingSphere号段模式的完整实现：

```java
// org.apache.shardingsphere.keygen.segment.algorithm.SegmentKeyGenerateAlgorithm
public final class SegmentKeyGenerateAlgorithm implements KeyGenerateAlgorithm {
    
    private final SegmentIdGenerator segmentIdGenerator;
    private volatile CacheId cacheId;       // 当前号段
    private volatile CacheId nextCacheId;   // 预加载的下一个号段
    private final AtomicBoolean isLoading = new AtomicBoolean(false);
    
    // 号段使用阈值：50%时触发预加载
    private static final double PRELOAD_THRESHOLD = 0.5;
    
    @Override
    public synchronized long generateKey() {
        // 检查当前号段是否可用
        if (cacheId == null || !cacheId.isAvailable()) {
            if (nextCacheId != null && nextCacheId.isAvailable()) {
                // 预加载的号段已就绪，直接切换
                cacheId = nextCacheId;
                nextCacheId = null;
            } else {
                // 同步加载新号段（阻塞等待）
                cacheId = loadSegmentFromDB();
            }
        }
        
        long key = cacheId.incrementAndGet();
        
        // 检查是否需要预加载下一个号段
        checkAndPreload();
        
        return key;
    }
    
    // 从数据库加载号段（乐观锁更新）
    private CacheId loadSegmentFromDB() {
        int retryCount = 0;
        int maxRetry = 3;
        
        while (retryCount < maxRetry) {
            try {
                // SELECT max_id, step, version FROM t_id_generator 
                // WHERE biz_type = 'refund_order'
                SegmentDO segment = segmentMapper.selectByBizType(bizType);
                long currentMaxId = segment.getMaxId();
                int step = segment.getStep();
                int version = segment.getVersion();
                
                // UPDATE t_id_generator 
                // SET max_id = max_id + step, version = version + 1
                // WHERE biz_type = 'refund_order' AND version = ?
                int updated = segmentMapper.updateWithVersion(
                    bizType, currentMaxId + step, version + 1
                );
                
                if (updated > 0) {
                    // 乐观锁成功，获得号段 [currentMaxId, currentMaxId + step)
                    return new CacheId(currentMaxId, currentMaxId + step);
                }
                // 乐观锁失败，重试
                retryCount++;
            } catch (Exception e) {
                retryCount++;
                if (retryCount >= maxRetry) {
                    throw new KeyGenerateException("Failed to load segment after retries", e);
                }
            }
        }
        throw new KeyGenerateException("Failed to load segment");
    }
    
    // 预加载检查
    private void checkAndPreload() {
        if (nextCacheId != null) return;  // 已在预加载
        
        double usage = cacheId.getUsageRatio();
        if (usage >= PRELOAD_THRESHOLD) {
            // 异步加载下一个号段
            if (isLoading.compareAndSet(false, true)) {
                CompletableFuture.supplyAsync(() -> {
                    try {
                        nextCacheId = loadSegmentFromDB();
                    } finally {
                        isLoading.set(false);
                    }
                    return null;
                });
            }
        }
    }
}

// 号段的内存表示
public final class CacheId {
    private final long minId;     // 号段起始
    private final long maxId;     // 号段结束（不含）
    private final AtomicLong currentId;  // 当前已分配到的ID
    
    public CacheId(long minId, long maxId) {
        this.minId = minId;
        this.maxId = maxId;
        this.currentId = new AtomicLong(minId);
    }
    
    public boolean isAvailable() {
        return currentId.get() < maxId;
    }
    
    public long incrementAndGet() {
        return currentId.incrementAndGet();
    }
    
    public double getUsageRatio() {
        return (double)(currentId.get() - minId) / (maxId - minId);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **ID不连续的假象**：应用重启后，当前号段中未使用的ID会被浪费（如取到号段[1000,2000)，用了500个就重启，1500个ID丢失）。这对退款单号等场景无影响，但对需要严格连续的场景不适用
2. **step设置**：step太小会频繁访问DB，太大会浪费更多ID。建议根据QPS设置：QPS=1000时，step=2000（约2秒取一次号段）
3. **DB故障降级**：当DB不可用时，可以在内存中保留多个号段的缓存，避免ID生成服务完全不可用
4. **加分回答**：可以提到美团Leaf的号段模式优化——多DB双主热备，以及异步刷新号段减少延迟的方案

## 第4系列：读写分离与高可用（第13-15集）

### 第13集：ShardingSphere 读写分离的实现原理：主从路由策略、强制主库路由

**💡 核心回答：**

ShardingSphere 的读写分离通过 `ReadwriteSplittingRule` 实现，核心原理：

1. **读操作自动路由到从库**：SELECT语句默认路由到从库（可配置多个从库做负载均衡）
2. **写操作路由到主库**：INSERT/UPDATE/DELETE 始终路由到主库
3. **事务内读写一致**：同一事务内的读写都路由到主库，避免主从延迟导致读不到刚写入的数据
4. **强制主库路由**：通过 Hint 机制强制将特定查询路由到主库

**负载均衡策略**：
- **轮询（ROUND_ROBIN）**：按顺序轮流选择从库
- **随机（RANDOM）**：随机选择一个从库
- **权重（WEIGHT）**：根据从库配置权重分配流量

**📦 实际例子：**

悦茶平台的读写分离配置：

```yaml
spring:
  shardingsphere:
    rules:
      readwrite-splitting:
        data-sources:
          order-readwrite:
            write-data-source-name: order-master
            read-data-source-names:
              - order-slave-1
              - order-slave-2
              - order-slave-3
            transactional-strategy-name: PRIMARY_FIRST
            load-balancer-name: round_robin
        
        load-balancers:
          round_robin:
            type: ROUND_ROBIN
          weight_balance:
            type: WEIGHT
            props:
              order-slave-1: 50    # 高性能机器，50%流量
              order-slave-2: 30    # 普通机器，30%流量
              order-slave-3: 20    # 低配机器，20%流量
```

```java
// org.apache.shardingsphere.readwritesplitting.route.ReadwriteSplittingRouter
public final class ReadwriteSplittingRouter {
    
    public DataSourceDataNode route(final SQLStatementContext sqlStatementContext,
                                     final ReadwriteSplittingRule rule) {
        // 判断SQL类型
        if (isWriteOperation(sqlStatementContext)) {
            // 写操作：始终路由到主库
            return rule.getWriteDataSource();
        }
        
        // 事务内检查：事务中的读也走主库
        if (isInTransaction()) {
            TransactionContext txContext = TransactionContextHolder.get();
            if (txContext.isTransactionalReadPrimary()) {
                return rule.getWriteDataSource();
            }
        }
        
        // Hint强制主库
        if (HintManager.isMasterRouteOnly()) {
            return rule.getWriteDataSource();
        }
        
        // 读操作：通过负载均衡策略选择从库
        return rule.getReadDataSource(loadBalancer);
    }
    
    private boolean isWriteOperation(final SQLStatementContext sqlStatementContext) {
        SQLStatement statement = sqlStatementContext.getSqlStatement();
        return statement instanceof InsertStatement
            || statement instanceof UpdateStatement
            || statement instanceof DeleteStatement;
    }
}
```

3. **加分回答**：可以提到 MySQL 半同步复制（Semi-Sync）可以将主从延迟控制在1个RTT内，比异步复制更可靠

### 第14集：数据库发现（Database Discovery）机制：如何自动感知主从切换

**💡 核心回答：**

ShardingSphere 的数据库发现机制（Database Discovery）用于**自动检测数据库集群拓扑变化**，当主库故障、主从切换、从库宕机等事件发生时，自动更新路由规则，无需人工干预。

**支持的高可用方案：**
- **MGR（MySQL Group Replication）**：MySQL原生组复制
- **MHA**：Master High Availability
- **Keepalived + VIP**：VIP漂移方式

**核心机制：**
1. **心跳检测**：定时向各数据库节点发送心跳（默认3秒一次）
2. **状态感知**：检测到节点状态变化（UP/DOWN/SWITCH）
3. **规则更新**：自动更新读写分离的数据源列表
4. **故障摘除**：将从故障节点上的流量切走

**📦 实际例子：**

悦茶平台使用MGR + 数据库发现：

```yaml
spring:
  shardingsphere:
    rules:
      database-discovery:
        data-sources:
          order-cluster:
            type: MGR
            props:
              keep-alive-cron: '0/3 * * * * ?'      # 每3秒心跳检测
              recovery-policy: NEVER_LOSE             # 数据不丢失策略
        
        discovery-types:
          mgr:
            type: MGR
            props:
              group-name: grp_order                   # MGR组名
```

故障切换场景：
```
时间线：
T0: order-master(主) + slave-1(从) + slave-2(从) 正常运行
T1: order-master 宕机（心跳超时）
T2: MGR 自动选举 slave-1 为新主库
T3: ShardingSphere 数据库发现检测到拓扑变化
T4: 自动更新路由：写操作 → slave-1(新主)，读操作 → slave-2
T5: 原 slave-1 从读列表中移除
整个过程耗时约3-5秒，期间写操作短暂失败（需要业务重试）
```

**🔍 源码解析：**

```java
// org.apache.shardingsphere.dbdiscovery.core.DatabaseDiscoveryContext
public final class DatabaseDiscoveryContext {
    
    private final Map<String, DatabaseDiscoveryRule> rules;
    private final Map<String, DataSource> dataSources;
    
    // 定时心跳检测
    public void startHeartbeat() {
        scheduledExecutor.scheduleAtFixedRate(() -> {
            for (DatabaseDiscoveryRule rule : rules.values()) {
                rule.checkDatabaseDiscovery();
            }
        }, 0, keepAliveInterval, TimeUnit.SECONDS);
    }
}

// org.apache.shardingsphere.dbdiscovery.rule.DatabaseDiscoveryRule
public final class DatabaseDiscoveryRule {
    
    private final DatabaseGroupManager groupManager;
    private volatile String primaryDataSourceName;
    private final List<String> replicaDataSourceNames;
    
    public void checkDatabaseDiscovery() {
        // 1. 检查各节点状态
        for (DataSource dataSource : allDataSources) {
            boolean isAlive = checkNodeAlive(dataSource);
            if (!isAlive) {
                handleNodeDown(dataSource.getName());
            }
        }
        
        // 2. 检查主库是否变化（MGR场景）
        String newPrimary = groupManager.getPrimaryDataSource();
        if (!newPrimary.equals(primaryDataSourceName)) {
            handlePrimarySwitch(newPrimary);
        }
    }
    
    private boolean checkNodeAlive(final DataSource dataSource) {
        try (Connection conn = dataSource.getConnection();
             Statement stmt = conn.createStatement()) {
            stmt.executeQuery("SELECT 1");
            return true;
        } catch (SQLException e) {
            return false;
        }
    }
    
    private void handlePrimarySwitch(final String newPrimary) {
        log.info("Primary switched from {} to {}", primaryDataSourceName, newPrimary);
        this.primaryDataSourceName = newPrimary;
        // 更新读写分离规则
        updateReadwriteSplittingRule();
    }
    
    private void handleNodeDown(final String dataSourceName) {
        log.warn("DataSource {} is down, removing from routing", dataSourceName);
        if (replicaDataSourceNames.contains(dataSourceName)) {
            replicaDataSourceNames.remove(dataSourceName);
        }
        // 如果主库宕机，等待MGR选举新主库
    }
}

public final class MGRDatabaseDiscoveryType implements DatabaseDiscoveryType {
    
    @Override
    public void checkEnvironment(final Collection<DataSourceMember> dataSourceMembers) {
        // 查询MGR成员状态
        // SELECT * FROM performance_schema.replication_group_members
        for (DataSourceMember member : dataSourceMembers) {
            String memberState = queryMemberState(member);
            // ONLINE: 正常, RECOVERING: 正在同步

                markAsUnavailable(member);
            }
        }

        return dataSourceMembers.stream()
            .filter(member -> "PRIMARY".equals(member.getMemberRole()))
            .map(DataSourceMember::getDataSourceName)
            .findFirst()
            .orElseThrow(() -> new DatabaseDiscoveryException("No primary found in MGR group"));
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **主从切换期间的请求处理**：切换期间（3-5秒），写请求会失败，业务层必须实现**重试机制**（建议重试3次，间隔1秒）
2. **脑裂问题**：MGR可以防止脑裂（强一致模式），但MHA+VIP方案可能出现短暂脑裂
3. **心跳间隔设置**：太短（如1秒）会给数据库增加额外压力；太长（如10秒）会导致故障发现延迟
4. **加分回答**：可以提到 Zabbix/Prometheus 监控配合 ShardingSphere 的 DistSQL 实现自动告警和手动切换

### 第15集：高可用方案：ShardingSphere + MHA/Orchestrator/MGR 的配合方案

**💡 核心回答：**

生产环境需要一套完整的高可用方案，ShardingSphere 可以配合多种MySQL高可用工具：

| 方案 | 架构 | 切换速度 | 数据一致性 | 复杂度 | 推荐场景 |
|------|------|---------|-----------|--------|---------|
| **MGR** | MySQL原生组复制 | 快（自动） | 强一致（单主模式） | 中 | 数据一致性要求高 |
| **MHA** | 主从复制+自动切换 | 中（10-30秒） | 最终一致 | 低 | 传统方案，团队熟悉 |
| **Orchestrator** | 主从复制+编排工具 | 快（手动/自动） | 最终一致 | 高 | 大规模集群管理 |
| **Proxy+Proxy HA** | 双Proxy+LVS | 快 | 取决于后端 | 中 | Proxy层高可用 |

**各层高可用设计：**
1. **接入层**：Sharding-Proxy前面挂LVS/HAProxy，Proxy无状态可水平扩展
2. **路由层**：ShardingSphere的数据库发现机制自动感知拓扑变化
3. **存储层**：MySQL主从/MGR保证数据副本可用

**📦 实际例子：**

悦茶平台的完整高可用架构：

```
接入层：  LVS (Active-Standby)
            ↓
代理层：  Sharding-Proxy × 2（无状态，LVS轮询）
            ↓
路由层：  ShardingSphere DatabaseDiscovery (MGR)
            ↓
存储层：  每个分片组 = MGR集群（1主2从）
          16个分片组 × 3节点 = 48个MySQL实例
```

各层故障处理：
```
场景1：单个从库宕机
  → MGR自动摘除该节点，读写不受影响
  
场景2：主库宕机
  → MGR 10秒内选举新主库
  → ShardingSphere数据库发现感知到主库变化
  → 自动更新路由规则
  → 写请求短暂失败（需重试），读请求自动切到剩余从库
  
场景3：整个Proxy宕机
  → LVS检测到Proxy健康检查失败
  → 自动摘除故障Proxy，流量打到备用Proxy
  → 客户端连接断开，重连到LVS VIP
```

## 第5系列：分布式事务（第16-20集）

### 第16集：分库分表后的分布式事务问题：跨库事务的挑战，2PC/3PC/TCC/SAGA 对比

**💡 核心回答：**

分库分表后，一次业务操作可能涉及多个数据库实例，传统的本地事务（ACID）无法跨库保证一致性，必须引入分布式事务方案。

**跨库事务的核心挑战：**
1. **原子性**：多个库要么全部提交，要么全部回滚
2. **一致性**：中间状态不能对外可见（如订单已创建但库存未扣减）
3. **性能代价**：分布式事务的协调开销远大于本地事务
4. **死锁风险**：跨库锁的竞争可能导致分布式死锁

**四种分布式事务方案对比：**

| 方案 | 原理 | 一致性 | 性能 | 实现复杂度 | 适用场景 |
|------|------|--------|------|-----------|---------|
| **2PC** | 协调者+参与者，准备+提交两阶段 | 强一致 | 最低 | 中 | 对一致性要求极高的金融场景 |
| **3PC** | 2PC增强，增加CanCommit阶段，超时机制 | 强一致 | 略高于2PC | 高 | 理论上优于2PC，实际少用 |
| **TCC** | Try-Confirm-Cancel，业务层面补偿 | 最终一致 | 高 | 极高（需写3套逻辑） | 资金类操作（转账、支付） |
| **SAGA** | 正向操作链+反向补偿链 | 最终一致 | 高 | 中 | 长事务、跨多服务编排 |

**📦 实际例子：**

悦茶平台下单流程的分布式事务分析：

```
下单操作涉及3个分库：
1. 订单库（ds_5）：INSERT t_order → 创建订单
2. 库存库（ds_8）：UPDATE t_sku_stock → 扣减库存
3. 积分库（ds_3）：INSERT t_points_log → 赠送积分

场景分析：
- 如果订单库提交成功但库存库失败 → 订单存在但库存未扣（脏数据）
- 如果库存库扣减成功但积分库失败 → 库存已扣但积分未送（体验问题）
```

各方案的实现方式：

```sql
-- 2PC方案（XA事务）：数据库层面保证
-- 优点：业务代码无感知
-- 缺点：锁资源时间长，性能差

-- TCC方案：业务层面补偿
-- Try: 冻结库存（UPDATE stock SET frozen = frozen + 1 WHERE sku_id = ?）
-- Confirm: 扣减冻结库存（UPDATE stock SET stock = stock - 1, frozen = frozen - 1）
-- Cancel: 释放冻结库存（UPDATE stock SET frozen = frozen - 1）

-- SAGA方案：正向操作+补偿操作
-- 正向：创建订单 → 扣库存 → 送积分
-- 补偿：释放积分 → 恢复库存 → 取消订单（反向执行）
```

**🔍 源码解析：**

```java
        for (DataSource ds : dataSources.values()) {
            Connection conn = ds.getConnection();
            Xid xid = generateXid();
            conn.createStatement().execute("XA START " + xid);
        }
    }
    
    public boolean prepare() {
        // Phase 2-Prepare: 各分库执行 XA END + XA PREPARE
        boolean allPrepared = true;
        for (DataSource ds : dataSources.values()) {
            try {
                Connection conn = ds.getConnection();
                conn.createStatement().execute("XA END " + xid);
                int result = conn.createStatement().executeUpdate("XA PREPARE " + xid);
                if (result != 0) allPrepared = false;
            } catch (SQLException e) {
                allPrepared = false;
            }
        }
        return allPrepared;
    }
    
    public void commit() {
        // Phase 3-Commit: 各分库执行 XA COMMIT
        for (DataSource ds : dataSources.values()) {
            Connection conn = ds.getConnection();
            conn.createStatement().execute("XA COMMIT " + xid);
        }
    }
    
    public void rollback() {
        // 回滚：各分库执行 XA ROLLBACK
        for (DataSource ds : dataSources.values()) {
            Connection conn = ds.getConnection();
            conn.createStatement().execute("XA ROLLBACK " + xid);
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **2PC的性能问题**：XA事务在Prepare阶段会持有资源锁，直到所有参与者都Prepare完成。如果某个参与者响应慢，所有参与者都被阻塞
2. **3PC的实际应用**：3PC理论上解决了2PC的阻塞问题（通过超时机制），但引入了新的不一致窗口，生产环境很少使用
3. **TCC的侵入性**：每个业务操作都需要实现Try/Confirm/Cancel三个接口，代码量翻3倍。建议只在核心交易链路上使用
4. **加分回答**：可以提到Seata对AT模式（自动生成补偿SQL）的实现，比TCC更简单

### 第17集：ShardingSphere 的事务管理器：XA 事务的实现原理，两阶段提交的流程

**💡 核心回答：**

ShardingSphere 内置了 XA 分布式事务的支持，基于 XA 协议实现两阶段提交。

**XA事务的完整流程：**

```
应用层：  begin → 执行业务SQL → commit
                ↓
ShardingSphere事务管理器：
  Phase 1 (Prepare):
    1. 对所有分片执行 XA END（结束当前分支事务）
    2. 对所有分片执行 XA PREPARE（进入准备状态）
    3. 如果所有分片都PREPARE成功 → 进入Phase 2
    4. 如果有任何分片PREPARE失败 → 执行回滚
  
  Phase 2 (Commit/Rollback):
    - 成功：对所有分片执行 XA COMMIT
    - 失败：对所有分片执行 XA ROLLBACK
```

**XAResource 的关键状态：**
- `ACTIVE`：分支事务活跃中
- `IDLE`：分支事务挂起
- `PREPARED`：已准备，等待最终提交/回滚
- `COMMITTED`：已提交
- `ROLLEDBACK`：已回滚

```java
// org.apache.shardingsphere.transaction.xa.XAShardingSphereTransactionManager
public final class XAShardingSphereTransactionManager implements ShardingSphereTransactionManager {
    
    private final Map<String, XADataSourceWrapper> xaDataSourceWrappers = new LinkedHashMap<>();
    private XATransactionManagerProvider transactionManagerProvider;
    
    @Override
    public void init(final Map<String, DataSource> dataSources, final TransactionRule rule) {
        // 初始化每个数据源的XA事务资源
        for (Map.Entry<String, DataSource> entry : dataSources.entrySet()) {
            String dataSourceName = entry.getKey();
            XADataSource xaDataSource = createXADataSource(entry.getValue());
            XADataSourceWrapper wrapper = new XADataSourceWrapper(dataSourceName, xaDataSource);
            xaDataSourceWrappers.put(dataSourceName, wrapper);
            // 向事务管理器注册资源
            transactionManagerProvider.registerRecoverable(xaDataSource);
        }
    }
    
    @Override
    public TransactionStatus getTransactionStatus() {
        return transactionManagerProvider.getStatus();
    }
    
    // 事务开始
    public void begin(final Collection<String> dataSourceNames) throws SQLException {
        // 为每个数据源生成分支事务ID（Xid）
        Map<String, Xid> xids = new LinkedHashMap<>();
        for (String dsName : dataSourceNames) {
            Xid xid = transactionManagerProvider.createXid();
            xids.put(dsName, xid);
        }
        // 将Xid存入线程上下文
        TransactionContext.setXids(xids);
    }
    
    // 两阶段提交 - Phase 1: Prepare
    public boolean prepare(final Collection<String> dataSourceNames) throws SQLException {
        Map<String, Xid> xids = TransactionContext.getXids();
        boolean allPrepared = true;
        
        for (String dsName : dataSourceNames) {
            Xid xid = xids.get(dsName);
            XADataSourceWrapper wrapper = xaDataSourceWrappers.get(dsName);
            
            try {
                // XA END: 结束当前分支事务的活动
                wrapper.getConnection().getXAResource().end(xid, XAResource.TMSUCCESS);
                // XA PREPARE: 进入准备状态
                int result = wrapper.getConnection().getXAResource().prepare(xid);
                if (result == XAResource.XA_RDONLY) {
                    // 只读分支，无需提交（优化：只读分片直接完成）
                    continue;
                }
            } catch (XAException e) {
                allPrepared = false;
                log.error("XA PREPARE failed for datasource: {}", dsName, e);
            }
        }
        return allPrepared;
    }
    
    // 两阶段提交 - Phase 2: Commit
    public void commit(final Collection<String> dataSourceNames) throws SQLException {
        Map<String, Xid> xids = TransactionContext.getXids();
        
        for (String dsName : dataSourceNames) {
            Xid xid = xids.get(dsName);
            XADataSourceWrapper wrapper = xaDataSourceWrappers.get(dsName);
            
            try {
                // XA COMMIT: 最终提交
                wrapper.getConnection().getXAResource().commit(xid, false);
            } catch (XAException e) {
                // 提交异常！这是最危险的情况
                // 需要事务恢复机制（TM recovery）来重试提交
                log.error("XA COMMIT failed for datasource: {}, will retry", dsName, e);
                transactionManagerProvider.recover(dsName, xid);
            }
        }
    }
    
    // 回滚
    public void rollback(final Collection<String> dataSourceNames) throws SQLException {
        Map<String, Xid> xids = TransactionContext.getXids();
        
        for (String dsName : dataSourceNames) {
            Xid xid = xids.get(dsName);
            XADataSourceWrapper wrapper = xaDataSourceWrappers.get(dsName);
            
            try {
                wrapper.getConnection().getXAResource().rollback(xid);
            } catch (XAException e) {
                log.error("XA ROLLBACK failed for datasource: {}", dsName, e);
            }
        }
    }
}
```

### 第18集：BASE 柔性事务：ShardingSphere 的 BEST_EFFORT_DELIVERY 策略

**💡 核心回答：**

BASE（Basically Available, Soft State, Eventually Consistent）柔性事务是相对于强一致（ACID）的一种弱一致性方案。ShardingSphere 提供了 `BEST_EFFORT_DELIVERY`（最大努力送达）作为BASE事务的一种实现。

**BEST_EFFORT_DELIVERY 策略：**
- 各分片尽力执行自己的本地事务
- 不保证跨分片的原子性，通过**事务日志**保证最终一致性
- 如果某个分片事务失败，通过**事务协调器**进行补偿重试

**与XA的对比：**

| 维度 | XA（强一致） | BEST_EFFORT_DELIVERY（最终一致） |
|------|------------|-------------------------------|
| 一致性 | 强一致（提交前所有分片一致） | 最终一致（通过补偿达到一致） |
| 性能 | 低（锁资源等待） | 高（各分片独立执行） |
| 可用性 | 低（任一节点故障阻塞全局） | 高（节点故障可异步重试） |
| 实现复杂度 | 中（依赖XA协议） | 高（需要事务日志+补偿机制） |

**📦 实际例子：**

```java
// org.apache.shardingsphere.transaction.base.besteffort.BestEffortDeliveryTransaction
public final class BestEffortDeliveryTransaction {
    
    private final TransactionLogRepository logRepository;
    
    // 事务执行入口
    public void execute(final ExecutionContext executionContext) {
        Collection<ExecutionUnit> executionUnits = executionContext.getExecutionUnits();
        List<CompletableFuture<Void>> futures = new ArrayList<>();
        
        // 各分片独立执行（不等待其他分片）
        for (ExecutionUnit unit : executionUnits) {
            CompletableFuture<Void> future = CompletableFuture.runAsync(() -> {
                try {
                    executeLocalTransaction(unit);
                } catch (Exception e) {
                    // 执行失败：记录事务日志，等待重试
                    logRepository.save(TransactionLog.builder()
                        .bizType(unit.getBizType())
                        .bizKey(unit.getBizKey())
                        .executionUnit(unit)
                        .status(TransactionLogStatus.PENDING)
                        .retryCount(0)
                        .nextRetryTime(calculateNextRetry(0))
                        .build());
                }
            });
            futures.add(future);
        }
        
        // 注意：不等待所有Future完成（非阻塞）
        // 或者只等待核心操作完成，非核心操作异步处理
    }
    
    // 事务日志重试调度
    // org.apache.shardingsphere.transaction.base.besteffort.BestEffortDeliveryRecoveryJob
    @Scheduled(fixedDelay = 5000)  // 每5秒检查一次
    public void retryPendingTransactions() {
        List<TransactionLog> pendingLogs = logRepository.findRetryable(
            LocalDateTime.now()
        );
        
        for (TransactionLog log : pendingLogs) {
            try {
                executeLocalTransaction(log.getExecutionUnit());
                // 成功：标记完成
                logRepository.updateStatus(log.getId(), TransactionLogStatus.SUCCESS);
            } catch (Exception e) {
                // 失败：增加重试次数，计算下次重试时间（指数退避）
                int nextRetry = log.getRetryCount() + 1;
                if (nextRetry > MAX_RETRY_COUNT) {
                    logRepository.updateStatus(log.getId(), TransactionLogStatus.FAILED);
                    // 超过最大重试次数，告警人工介入
                    alarmService.send("Transaction retry exceeded: " + log.getBizKey());
                } else {
                    logRepository.updateRetryCount(log.getId(), nextRetry, 
                        calculateNextRetry(nextRetry));
                }
            }
        }
    }
    
    // 指数退避重试策略
    private LocalDateTime calculateNextRetry(int retryCount) {
        // 第1次：5秒后，第2次：25秒后，第3次：125秒后...
        long delayMs = (long) Math.pow(5, retryCount) * 1000;
        return LocalDateTime.now().plus(Duration.ofMillis(delayMs));
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **重试的幂等性**：补偿重试必须保证幂等（同一笔积分不能重复赠送），需要在业务层做幂等控制（如 `order_no + biz_type` 唯一约束）
2. **事务日志的清理**：成功的事务日志需要定期归档清理，避免表无限增长
3. **重试风暴**：大量事务同时重试会压垮数据库，需要控制重试并发度（如每次最多重试100条）
4. **加分回答**：可以提到 RocketMQ 的事务消息方案——半消息+本地事务+消息确认，比事务日志+重试更优雅

### 第19集：分布式事务的性能取舍：强一致 vs 最终一致，什么场景用什么方案

**💡 核心回答：**

分布式事务的核心矛盾是**一致性和性能的权衡**。没有银弹，需要根据业务场景选择合适的方案。

**决策框架：**

```
                    数据不一致是否可接受？
                    ├── 不可接受（资金、库存）
                    │   ├── 能容忍多少延迟？
                    │   │   ├── 0延迟 → XA（2PC）
                    │   │   └── 可容忍秒级延迟 → TCC
                    │   └── 业务能否实现补偿？
                    │       ├── 能 → TCC
                    │       └── 不能 → XA
                    └── 可接受（积分、通知、日志）
                        └── 需要多久一致？
                            ├── 秒级 → 本地消息表 + 重试
                            └── 分钟级 → 异步消息队列
```

**各场景推荐方案：**

| 场景 | 数据敏感性 | 推荐方案 | 理由 |
|------|-----------|---------|------|
| 订单创建+扣库存 | 极高 | XA或TCC | 超卖不可接受 |
| 支付扣款 | 极高 | XA | 资金操作，强一致 |
| 下单送积分 | 中 | 最终一致（异步） | 积分延迟可接受 |
| 下单发短信 | 低 | 异步消息 | 完全不阻塞主流程 |
| 跨库报表统计 | 低 | CDC+异步同步 | 允许分钟级延迟 |

**📦 实际例子：**

悦茶平台下单链路的混合事务策略：

```java
// org.apache.shardingsphere.transaction.rule.TransactionRule
public final class TransactionRule implements Rule {
    
    private final TransactionType defaultType;
    private final Map<String, ShardingSphereTransactionManager> transactionManagers;
    
    // 根据配置选择事务类型
    public ShardingSphereTransactionManager getTransactionManager(final String dataSourceName) {
        // 优先级：SQL级别配置 > 表级别配置 > 全局默认
        TransactionType type = resolveTransactionType(dataSourceName);
        return transactionManagers.get(type.name());
    }
    
    private TransactionType resolveTransactionType(final String dataSourceName) {
        // 检查是否有SQL Hint指定事务类型
        Optional<TransactionType> hintType = HintManager.getTransactionType();
        if (hintType.isPresent()) {
            return hintType.get();
        }
        
        // 检查表级别事务配置
        Optional<TransactionType> tableType = tableTransactionRules.stream()
            .filter(r -> r.matchDataSource(dataSourceName))
            .map(TableTransactionRule::getTransactionType)
            .findFirst();
        if (tableType.isPresent()) {
            return tableType.get();
        }
        
        // 使用全局默认
        return defaultType;
    }
}

public class MixedTransactionEngine {
    
    public void execute(final ExecutionContext context) {
        // 将执行单元按事务类型分组
        Map<TransactionType, Collection<ExecutionUnit>> groupedUnits = context.getExecutionUnits()
            .stream()
            .collect(Collectors.groupingBy(ExecutionUnit::getTransactionType));
        
        // XA组：两阶段提交
        if (groupedUnits.containsKey(TransactionType.XA)) {
            executeXA(groupedUnits.get(TransactionType.XA));
        }
        
        // BASE组：异步执行 + 事务日志
        if (groupedUnits.containsKey(TransactionType.BASE)) {
            executeBase(groupedUnits.get(TransactionType.BASE));
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **XA超时问题**：MySQL的XA事务超时后，事务并不会自动回滚，而是进入 `XA_TIMEOUT` 状态，需要手动清理。建议设置合理的 `xa_timeout` 参数
2. **TCC的空回滚和悬挂**：Cancel接口可能被调用但Try从未执行（空回滚），需要业务层判断并跳过。Try执行后网络超时，Cancel可能延迟到达（悬挂），需要加控制记录
3. **最终一致的"最终"不是"永远"**：需要设置重试上限和告警，超过阈值的失败事务必须人工介入
4. **加分回答**：可以提到蚂蚁金服的 SOFA 分布式事务框架，以及字节跳动在大规模场景下的分布式事务优化实践

### 第20集：分布式事务的性能取舍：强一致 vs 最终一致，什么场景用什么方案

**💡 核心回答：**

本集深入探讨分布式事务在生产环境中的**性能调优和故障处理**策略。

**核心性能瓶颈分析：**
1. **XA的锁竞争**：Prepare阶段持有资源锁，高并发下锁等待导致吞吐量下降
2. **TCC的业务开销**：Try阶段需要额外写入冻结记录，增加了数据库写入量
3. **最终一致的消息延迟**：消息队列的消费延迟导致数据不一致窗口扩大

**性能优化策略：**

| 优化点 | 具体措施 | 效果 |
|--------|---------|------|
| 减少参与分片 | 将非分片操作拆出事务 | XA性能提升2-3倍 |
| 缩短事务持有时间 | 事务内不做远程调用 | 减少锁等待 |
| 批量提交 | 多个小事务合并为批量 | 减少XA协调次数 |
| 连接池隔离 | XA连接池和普通连接池分离 | 避免XA慢请求占满连接池 |

```java
    public void executeBatch(final Collection<ExecutionContext> contexts) {
        // 合并所有执行单元
        Collection<ExecutionUnit> allUnits = contexts.stream()
            .flatMap(ctx -> ctx.getExecutionUnits().stream())
            .collect(Collectors.toList());
        
        // 按数据源分组，每个数据源只执行一次XA START/END/PREPARE/COMMIT
        Map<String, List<SQLUnit>> groupedByDataSource = allUnits.stream()
            .collect(Collectors.groupingBy(
                ExecutionUnit::getDataSourceName,
                Collectors.mapping(ExecutionUnit::getSqlUnit, Collectors.toList())
            ));
        
        // 批量执行：每个数据源一次XA事务
        xaTransactionManager.begin(groupedByDataSource.keySet());
        for (Map.Entry<String, List<SQLUnit>> entry : groupedByDataSource.entrySet()) {
            executeBatchSQL(entry.getKey(), entry.getValue());
        }
        xaTransactionManager.commit(groupedByDataSource.keySet());
    }
}
```

### 第21集：数据加密存储的实现：EncryptRule 的配置，加密器（AES/MD5/SM4）的选择

**💡 核心回答：**

ShardingSphere 提供了内置的数据加密功能，通过 `EncryptRule` 配置加密策略，在写入时自动加密、读取时自动解密，对业务代码透明。

**支持的加密算法：**
- **AES**：对称加密，可逆，适合需要查询原文的场景（如手机号、邮箱）
- **MD5**：摘要算法，不可逆，适合密码存储（只需验证不需要还原）
- **SM4**：国密对称加密，满足合规要求
- **RC4**：轻量级对称加密（不推荐用于生产）
- **自定义加密**：实现 `EncryptAlgorithm` 接口

**核心概念：**
- **逻辑列**：业务代码中使用的列名（如 `phone`）
- **密文列**：实际存储加密数据的列名（如 `cipher_phone`）
- **协助查询列**：存储可索引的加密辅助值（用于等值查询）

```java
// org.apache.shardingsphere.encrypt.rule.EncryptRule
public final class EncryptRule implements Rule {
    
    private final Map<String, EncryptTable> encryptTables;
    private final Map<String, EncryptAlgorithm> encryptors;
    
    // 写入时的加密处理
    public void encryptInsert(final String logicTable, final InsertSQLStatementContext insertContext) {
        EncryptTable encryptTable = encryptTables.get(logicTable);
        if (encryptTable == null) return;
        
        for (EncryptColumn encryptColumn : encryptTable.getColumns()) {
            String logicColumn = encryptColumn.getLogicColumn();
            String cipherColumn = encryptColumn.getCipherColumn();
            
            // 获取明文值
            Object plainValue = insertContext.getColumnValue(logicColumn);
            
            // 执行加密
            EncryptAlgorithm encryptor = encryptors.get(encryptColumn.getEncryptorName());
            String cipherValue = encryptor.encrypt(plainValue.toString());
            
            // 替换为密文列
            insertContext.setColumnName(logicColumn, cipherColumn);
            insertContext.setColumnValue(cipherColumn, cipherValue);
            
            // 如果有协助查询列，生成协助值
            if (encryptColumn.getAssistedQueryColumn().isPresent()) {
                String assistedColumn = encryptColumn.getAssistedQueryColumn().get();
                String assistedValue = encryptor.getAssistedQueryValue(plainValue.toString());
                insertContext.setColumnValue(assistedColumn, assistedValue);
            }
        }
    }
    
    // 查询时的解密处理
    public void decryptResultSet(final String logicTable, final MergedResult mergedResult) {
        EncryptTable encryptTable = encryptTables.get(logicTable);
        if (encryptTable == null) return;
        
        for (EncryptColumn encryptColumn : encryptTable.getColumns()) {
            String cipherColumn = encryptColumn.getCipherColumn();
            String logicColumn = encryptColumn.getLogicColumn();
            
            // 获取密文值
            String cipherValue = mergedResult.getValue(cipherColumn, String.class);
            
            // 执行解密
            EncryptAlgorithm encryptor = encryptors.get(encryptColumn.getEncryptorName());
            String plainValue = encryptor.decrypt(cipherValue);
            
            // 替换为明文返回
            mergedResult.setValue(logicColumn, plainValue);
        }
    }
}

// AES加密器实现
// org.apache.shardingsphere.encrypt.algorithm.aes.AESEncryptAlgorithm
public final class AESEncryptAlgorithm implements EncryptAlgorithm {
    
    private String aesKeyValue;
    
    @Override
    public void init(final Properties props) {
        this.aesKeyValue = props.getProperty("aes-key-value");
    }
    
    @Override
    public String encrypt(final Object plainValue) {
        if (plainValue == null) return null;
        byte[] plainBytes = plainValue.toString().getBytes(StandardCharsets.UTF_8);
        byte[] keyBytes = aesKeyValue.getBytes(StandardCharsets.UTF_8);
        
        // AES/ECB/PKCS5Padding 加密
        SecretKeySpec keySpec = new SecretKeySpec(Arrays.copyOf(keyBytes, 16), "AES");
        Cipher cipher = Cipher.getInstance("AES/ECB/PKCS5Padding");
        cipher.init(Cipher.ENCRYPT_MODE, keySpec);
        byte[] encrypted = cipher.doFinal(plainBytes);
        
        // Base64编码存储
        return Base64.getEncoder().encodeToString(encrypted);
    }
    
    @Override
    public String decrypt(final Object cipherValue) {
        if (cipherValue == null) return null;
        byte[] cipherBytes = Base64.getDecoder().decode(cipherValue.toString());
        byte[] keyBytes = aesKeyValue.getBytes(StandardCharsets.UTF_8);
        
        SecretKeySpec keySpec = new SecretKeySpec(Arrays.copyOf(keyBytes, 16), "AES");
        Cipher cipher = Cipher.getInstance("AES/ECB/PKCS5Padding");
        cipher.init(Cipher.DECRYPT_MODE, keySpec);
        byte[] decrypted = cipher.doFinal(cipherBytes);
        
        return new String(decrypted, StandardCharsets.UTF_8);
    }
    
    // 协助查询值：对明文做MD5（用于等值查询）
    @Override
    public String getAssistedQueryValue(final Object plainValue) {
        return DigestUtils.md5DigestAsHex(plainValue.toString().getBytes());
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **ECB模式的安全风险**：上述代码使用AES/ECB模式，相同明文产生相同密文，可能被分析出规律。生产环境建议使用 AES/CBC 或 AES/GCM 模式
2. **密钥管理**：密钥不能硬编码在配置文件中，建议使用 KMS（密钥管理服务）或 Vault 动态获取
3. **加密后的模糊查询**：加密后无法做 LIKE 查询，如果需要模糊搜索，需要建立额外的分词索引
4. **加分回答**：可以提到国密SM4在银行等金融机构的合规要求，以及 HSM（硬件安全模块）对密钥的保护

### 第22集：数据脱敏（Mask）：敏感字段（手机号、身份证、银行卡）的脱敏策略

**💡 核心回答：**

数据脱敏（Data Masking）与加密不同：
- **加密**：可逆操作，存储密文，需要时解密
- **脱敏**：不可逆操作，将敏感数据替换为部分遮蔽的形式，用于日志输出、非授权查询等场景

**ShardingSphere 支持的脱敏算法：**
- **手机号脱敏**：`138****8000`（保留前3后4）
- **身份证脱敏**：`110***********1234`（保留前3后4）
- **银行卡脱敏**：`6222 **** **** 1234`（保留前4后4）
- **邮箱脱敏**：`z***@example.com`（保留首字母）
- **自定义脱敏**：实现 `MaskAlgorithm` 接口

```java
// org.apache.shardingsphere.mask.rule.MaskRule
public final class MaskRule implements Rule {
    
    private final Map<String, MaskTable> maskTables;
    private final Map<String, MaskAlgorithm> maskAlgorithms;
    
    // 查询结果脱敏
    public void maskResultSet(final String logicTable, final MergedResult result) {
        MaskTable maskTable = maskTables.get(logicTable);
        if (maskTable == null) return;
        
        for (MaskColumn column : maskTable.getColumns()) {
            String columnName = column.getColumnName();
            String algorithmName = column.getMaskAlgorithmName();
            
            // 获取原始值
            Object originalValue = result.getValue(columnName, Object.class);
            if (originalValue == null) continue;
            
            // 执行脱敏
            MaskAlgorithm algorithm = maskAlgorithms.get(algorithmName);
            Object maskedValue = algorithm.mask(originalValue);
            
            // 替换为脱敏后的值
            result.setValue(columnName, maskedValue);
        }
    }
}

public final class PhoneBefore3After4MaskAlgorithm implements MaskAlgorithm {

        if (value == null) return null;
        String phone = value.toString();
        if (phone.length() < 7) return "****";
        
        // 保留前3位和后4位，中间用*替代

             + "****" 
             + phone.substring(phone.length() - 4);
```

### 第23集：加密字段查询的实现原理：如何在加密后仍然支持等值查询（辅助列方案）

**💡 核心回答：**

数据加密后最大的挑战是**丧失可查询性**：`SELECT * FROM t_user WHERE phone = '13800138000'` 无法直接匹配加密后的密文。

**ShardingSphere 的解决方案——协助查询列（Assisted Query Column）：**

核心思路：为加密列额外存储一个**可索引的辅助值**，查询时改写为查询辅助列。

| 查询类型 | 支持情况 | 原理 |
|---------|---------|------|
| 等值查询（`=`） | ✅ 支持 | 辅助列存储 `f(明文)` 的固定值 |
| 范围查询（`>`, `<`） | ❌ 不支持 | 加密后丧失大小关系 |
| 模糊查询（`LIKE`） | ❌ 不支持 | 加密后丧失字符串结构 |
| IN查询 | ✅ 支持 | 等同于多次等值查询 |

**辅助列的设计：**
- 存储 `HMAC(明文, 密钥)` 或 `加密算法.getAssistedQueryValue(明文)`
- 相同明文产生相同辅助值（保证等值匹配）
- 辅助值不可逆推原文（安全）

**📦 实际例子：**

悦茶平台按手机号查询用户的场景：


```java
// org.apache.shardingsphere.encrypt.rewrite.EncryptSQLRewriteEngine
public final class EncryptSQLRewriteEngine {
    
    // 查询SQL的改写：将逻辑列查询改写为协助查询列查询
    public SQLRewriteResult rewriteQuery(final String logicTable,
                                          final SelectStatement selectStatement,
                                          final EncryptRule encryptRule) {
        EncryptTable encryptTable = encryptRule.findEncryptTable(logicTable);
        
        // 遍历WHERE条件
        for (WhereSegment where : selectStatement.getWhere()) {
            for (Expression expr : where.getExpressions()) {
                if (expr instanceof BinaryExpression) {
                    BinaryExpression binary = (BinaryExpression) expr;
                    String columnName = binary.getLeft().toString();
                    
                    // 检查是否是加密列
                    Optional<EncryptColumn> encryptColumn = 
                        encryptTable.findEncryptColumn(columnName);
                    
                    if (encryptColumn.isPresent() && isEqualsOperator(binary.getOperator())) {
                        EncryptColumn column = encryptColumn.get();
                        
                        // 检查是否有协助查询列
                        if (column.getAssistedQueryColumn().isPresent()) {
                            String assistedColumn = column.getAssistedQueryColumn().get();
                            Object plainValue = binary.getRight().getValue();
                            
                            // 将明文值转换为协助查询值
                            EncryptAlgorithm algorithm = getAlgorithm(column);
                            Object assistedValue = algorithm.getAssistedQueryValue(plainValue);
                            
                            // 改写SQL：phone = '13800138000' → assisted_phone = 'MD5值'
                            binary.setLeft(new ColumnSegment(assistedColumn));
                            binary.setRight(new LiteralValue(assistedValue));
                        }
                    }
                }
            }
        }
        return new SQLRewriteResult(selectStatement);
    }
    
    // 写入时的处理：同时写入密文列和协助查询列
    public void rewriteInsert(final String logicTable,
                               final InsertStatement insertStatement,
                               final EncryptRule encryptRule) {
        EncryptTable encryptTable = encryptRule.findEncryptTable(logicTable);
        
        for (EncryptColumn column : encryptTable.getColumns()) {
            Object plainValue = getColumnValue(insertStatement, column.getLogicColumn());
            
            if (plainValue != null) {
                EncryptAlgorithm algorithm = getAlgorithm(column);
                
                // 写入密文列
                String cipherValue = algorithm.encrypt(plainValue.toString());
                setColumnValue(insertStatement, column.getCipherColumn(), cipherValue);
                
                // 写入协助查询列（如果有）
                if (column.getAssistedQueryColumn().isPresent()) {
                    String assistedValue = algorithm.getAssistedQueryValue(plainValue.toString());
                    setColumnValue(insertStatement, column.getAssistedQueryColumn().get(), assistedValue);
                }
                
                // 移除原始逻辑列（物理表中不存在）
                removeColumn(insertStatement, column.getLogicColumn());
            }
        }
    }
}

// 协助查询值的生成策略
// 不同加密算法有不同的协助查询策略
public interface EncryptAlgorithm {
    // 加密
    String encrypt(Object plainValue);
    // 解密
    String decrypt(Object cipherValue);
    // 生成协助查询值（用于等值查询）
    default String getAssistedQueryValue(Object plainValue) {
        // 默认使用MD5（不可逆，但等值匹配）
        return DigestUtils.md5DigestAsHex(plainValue.toString().getBytes());
    }
}

// AES加密器的协助查询策略
public final class AESEncryptAlgorithm implements EncryptAlgorithm {
    
    @Override
    public String getAssistedQueryValue(final Object plainValue) {
        // 使用HMAC-SHA256作为协助查询值（比纯MD5更安全）
        String key = aesKeyValue;
        return hmacSha256(plainValue.toString(), key);
    }
}
```

**等值查询的完整流程：**

```
用户查询：SELECT * FROM t_user WHERE phone = '13800138000'

Step 1 - SQL解析：识别到 phone 是加密列
Step 2 - 改写SQL：
  原始：WHERE phone = '13800138000'
  改写：WHERE assisted_phone = HMAC_SHA256('13800138000', key)
Step 3 - 执行查询：用协助查询值在 assisted_phone 列上查询
Step 4 - 结果解密：返回时 cipher_phone 自动解密为 phone 明文
```

**⚠️ 常见坑/加分回答：**

1. **安全性考量**：协助查询列本质上是明文的确定性Hash，如果攻击者获得了协助列的数据，可以通过彩虹表反推常见手机号/身份证。建议使用加盐Hash（HMAC）而非纯MD5
2. **范围查询不支持**：加密后无法做 `phone > '138'` 的范围查询，因为加密后丧失了字符序关系。如果业务需要，可以使用"保序加密"（OPE）但安全性会降低
3. **索引设计**：协助查询列需要建立索引（普通B+Tree索引即可），否则等值查询会变成全表扫描
4. **加分回答**：可以提到 Homomorphic Encryption（同态加密）是未来方向——加密后仍可计算，但目前性能开销太大，不适合生产

### 第24集：跨分片查询问题：跨库 JOIN、跨分片分页、跨分片排序的解决方案

**💡 核心回答：**

分库分表后，原本简单的查询变得复杂，主要面临三大挑战：

| 问题 | 难度 | 原因 |
|------|------|------|
| 跨库JOIN | ★★★★★ | 不同库的表无法直接JOIN |
| 跨分片分页 | ★★★★ | 每个分片独立排序，需要全局归并 |
| 跨分片排序 | ★★★ | 需要从所有分片取数据后全局排序 |

**解决方案矩阵：**

| 问题 | 方案 | 适用场景 | 复杂度 |
|------|------|---------|--------|
| 跨库JOIN | 数据冗余/宽表 | 关联查询频繁 | 中 |
| 跨库JOIN | 应用层组装 | 关联查询少 | 低 |
| 跨库JOIN | ER分片绑定 | 主子表同分片 | 低 |
| 跨分片分页 | 禁止深翻页 | C端列表 | 低 |
| 跨分片分页 | 游标分页 | 后台管理 | 中 |
| 跨分片排序 | 内存归并排序 | 数据量不大 | 中 |
| 跨分片排序 | 异构数据源 | 数据量大 | 高 |

**📦 实际例子：**

悦茶平台的跨分片查询解决方案：

```sql
-- 问题1：订单+用户信息的JOIN
-- 订单表按user_id分片，用户表按user_id分片
-- 解决方案：ER分片绑定（订单和用户按相同规则路由到同一分片）
-- 这样 t_order 和 t_user 在同一分片上，可以做本地JOIN

-- 问题2：运营后台按门店查询所有订单
-- 门店ID不是分片键，需要全分片扫描后归并
-- 解决方案：建立ES索引，运营查询走ES而非数据库

-- 问题3：商户后台按门店分页查询订单
-- 解决方案：游标分页
SELECT * FROM t_order 
WHERE store_id = 2001 
  AND order_id > {last_order_id}  -- 游标
ORDER BY order_id DESC 
LIMIT 20;
```

```java
// 跨分片排序的归并实现
// org.apache.shardingsphere.merge.engine orderby.OrderByStreamMergeUtil
public final class OrderByStreamMergeUtil {
    
    // 多分片结果归并排序（类似归并排序的merge步骤）
    public void mergeOrderBy(final List<QueryResult> queryResults, 
                              final OrderByContext orderByContext) {
        // 每个分片的查询结果已经按ORDER BY排序
        // 使用优先队列（堆）进行多路归并
        
        PriorityQueue<QueryResultRow> heap = new PriorityQueue<>((a, b) -> {
            for (OrderByColumn orderCol : orderByContext.getOrderByColumns()) {
                int compare = compareValues(
                    a.getValue(orderCol.getColumnIndex()),
                    b.getValue(orderCol.getColumnIndex()),
                    orderCol.isAsc()
                );
                if (compare != 0) return compare;
            }
            return 0;
        });
        
        // 初始化：每个分片取第一条数据放入堆
        for (QueryResult result : queryResults) {
            if (result.next()) {
                heap.offer(result.getCurrentRow());
            }
        }
        
        // 归并：每次从堆顶取出最小值，然后从对应分片取下一条
        while (!heap.isEmpty()) {
            QueryResultRow row = heap.poll();
            output(row);  // 输出到结果集
            // 从同一分片取下一条放入堆
            QueryResult sourceResult = row.getSourceResult();
            if (sourceResult.next()) {
                heap.offer(sourceResult.getCurrentRow());
            }
        }
    }
}

// ER分片绑定（主子表路由到同一分片）
// org.apache.shardingsphere.sharding.rule.binding.ShardingBindingTableRule
public final class ShardingBindingTableRule {
    
    // 绑定表：保证关联表路由到同一分片
    // 配置：<binding-table actual-data-nodes="ds_${0..15}.t_order_${0..3}, ds_${0..15}.t_order_item_${0..3}" />
    // 效果：t_order和t_order_item按相同规则分片，同一订单和订单项在同一分片
    
    public boolean isBindingTable(final String logicTable1, final String logicTable2) {
        return bindingTables.stream()
            .anyMatch(group -> group.contains(logicTable1) && group.contains(logicTable2));
    }
    
    // JOIN时检查绑定关系
    public boolean canLocalJoin(final Collection<String> tables) {
        // 如果所有表都是绑定表且分片规则一致，可以做本地JOIN
        return tables.stream()
            .allMatch(t -> isBindingTable(tables.iterator().next(), t));
    }
}

// 跨分片分页的改写和归并
// org.apache.shardingsphere.sql.rewrite.engine.token.PaginationRewriteEngine
public class PaginationRewriteEngine {
    
    public PaginationToken rewrite(final int offset, final int rowCount, final int shardingCount) {
        // 原始：LIMIT offset, rowCount（如 LIMIT 100, 20）
        // 改写：LIMIT 0, offset + rowCount（即 LIMIT 0, 120）
        // 每个分片返回前120条
        // 归并时：64个分片 × 120条 = 7680条参与全局排序
        // 全局排序后取第101~120条
        
        int rewrittenOffset = 0;
        int rewrittenRowCount = offset + rowCount;
        return new PaginationToken(rewrittenOffset, rewrittenRowCount);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **深翻页的性能灾难**：`LIMIT 100000, 20` 在64分片场景下，每个分片返回100020条，共640万条数据参与归并。建议改用游标分页 `WHERE id > last_id LIMIT 20`
2. **跨库JOIN的替代方案**：
   - **宽表**：将关联数据冗余到一张表（如订单表冗余用户昵称）
   - **应用层组装**：先查订单列表，再批量查用户信息，在应用层拼装
   - **异构数据源**：将需要JOIN的数据同步到ES/ClickHouse
3. **加分回答**：ShardingSphere 5.x 的 SQL Federation 功能可以在不改变SQL的情况下实现跨分片JOIN（将数据拉到计算节点做内存JOIN）

### 第25集：扩容与数据迁移：在线扩容分片数的方案（翻倍扩容法），ShardingSphere 的数据迁移工具

**💡 核心回答：**

当数据量增长超过原有分片承载能力时，需要在线扩容分片数。核心方案是**翻倍扩容法**。

**翻倍扩容法原理：**
- 分片数从 N 扩到 2N（如16→32，32→64）
- 每个原分片拆成两个新分片
- 只需迁移50%的数据（奇偶分片）
- 数据迁移过程中业务不中断

**迁移流程：**
1. **新增数据源**：配置新的数据库实例
2. **数据路由切换**：ShardingSphere同时支持新旧分片规则
3. **数据迁移**：后台任务将旧分片数据按新规则迁移
4. **双写验证**：迁移期间新写入同时写到新旧分片
5. **切换完成**：迁移完毕后切换到新规则

**📦 实际例子：**

悦茶平台订单库从16库扩到32库：

```
扩容前：16个库 × 4张表 = 64个分片
扩容后：32个库 × 4张表 = 128个分片

迁移策略：
- ds_0 → ds_0（偶数ID数据）+ ds_16（奇数ID数据）
- ds_1 → ds_1（偶数ID数据）+ ds_17（奇数ID数据）
- ...
- ds_15 → ds_15（偶数ID数据）+ ds_31（奇数ID数据）

每个旧分片的数据按 user_id 的 hash 值奇偶拆分
```

```yaml
# 扩容配置：同时配置新旧规则

      sharding:
        tables:
          t_order:
            actual-data-nodes: ds_${0..31}.t_order_${0..3}  # 新规则
            # 迁移期间的兼容配置
            migration:
              enabled: true
              old-actual-data-nodes: ds_${0..15}.t_order_${0..3}  # 旧规则
              migration-strategy: DOUBLE_WRITE  # 双写策略
```

```java
// 数据迁移工具核心逻辑
// org.apache.shardingsphere.data.migration.core.DataMigrationEngine
public final class DataMigrationEngine {
    
    private final DataSource oldDataSource;
    private final DataSource newDataSource;
    private final ShardingRule newShardingRule;
    
    // 翻倍扩容的迁移策略
    public void migrateByDoubling(final String logicTable, 
                                   final int oldShardCount, 
                                   final int newShardCount) {
        // 新增的分片数 = oldShardCount
        // 每个旧分片拆分为2个新分片
        
        int batchSize = 500;  // 每批迁移500条
        long lastId = 0;
        
        while (true) {
            // 1. 从旧分片读取一批数据
            List<Map<String, Object>> batch = readBatch(
                oldDataSource, logicTable, lastId, batchSize
            );
            if (batch.isEmpty()) break;
            
            // 2. 按新规则重新计算目标分片
            for (Map<String, Object> row : batch) {
                String targetDataSource = calculateNewDataSource(row, newShardingRule);
                String targetTable = calculateNewTable(row, newShardingRule);
                
                // 3. 写入新分片
                insertToNewShard(newDataSource, targetDataSource, targetTable, row);
            }
            
            lastId = batch.get(batch.size() - 1).get("id");
            log.info("Migrated {} rows, lastId={}", batch.size(), lastId);
        }
    }
    
    // 双写策略：迁移期间新写入同时写新旧分片
    public void doubleWrite(final ExecutionContext context) {
        // 写入旧分片（保证旧规则下数据一致）
        executeOnOldShards(context);
        
        // 同时写入新分片（保证新规则下数据一致）
        executeOnNewShards(context);
        
        // 通过对比确保双写一致性
        // 定期校验：对比新旧分片的数据差异
    }
}
```

```java
    private final Map<String, MigrationStatus> shardStatus = new ConcurrentHashMap<>();

        long newCount2 = countRows(newDataSource, newShard2);

    }
```

**⚠️ 常见坑/加分回答：**

1. **迁移期间的数据一致性**：必须实现双写（同时写新旧分片），否则迁移期间新写入的数据只在旧分片，迁移完毕后数据丢失
2. **迁移速度控制**：不能全速迁移（会影响在线业务的IO），建议限制迁移速度为总IO的30%
3. **回滚方案**：迁移期间必须保留回滚能力——如果新分片有问题，可以快速切回旧规则
4. **加分回答**：可以提到 Canal 作为数据同步工具在分片迁移中的应用，以及 PingCAP TiDB 的自动扩容（无需手动迁移数据）

### 第26集：分库分表后的全局唯一约束：分布式环境下的唯一索引问题

**💡 核心回答：**

分库分表后，原本的单表唯一约束（如 `UNIQUE KEY (order_no)`）无法跨分片生效。每个分片独立维护自己的唯一约束，无法保证全局唯一。

**解决方案：**

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **全局唯一索引表** | 单独一张表存储唯一值 | 简单可靠 | 单点瓶颈，需分库 |
| **分片内唯一** | 依赖分布式ID保证唯一 | 无额外开销 | 只适用于ID类字段 |
| **数据库唯一+业务校验** | 每个分片唯一+业务层查重 | 折中方案 | 存在极小概率冲突 |
| **Redis分布式锁** | 写入前Redis检查唯一性 | 高性能 | Redis和DB的一致性问题 |

**📦 实际例子：**

悦茶平台的订单号全局唯一保证：

```java

// ShardingSphere 本身不直接解决全局唯一约束问题
// 但可以通过自定义路由+唯一索引表配合实现

// 唯一索引校验拦截器（自定义扩展）
public class UniqueConstraintInterceptor implements SQLInterceptor {
    
    private final UniqueIndexService uniqueIndexService;
    
    @Override
    public void beforeSQLExecute(final SQLStatementContext sqlStatementContext) {
        if (!(sqlStatementContext.getSqlStatement() instanceof InsertStatement)) {
            return;
        }
        
        InsertStatement insert = (InsertStatement) sqlStatementContext.getSqlStatement();
        String tableName = insert.getTables().iterator().next().getTableName().getIdentifier().getValue();
        
        // 检查该表是否有全局唯一约束
        List<UniqueConstraint> constraints = getUniqueConstraints(tableName);
        
        for (UniqueConstraint constraint : constraints) {
            // 提取唯一字段的值
            Object uniqueValue = extractUniqueValue(insert, constraint.getColumn());
            
            // 全局唯一性检查
            if (!uniqueIndexService.checkUnique(constraint.getBizType(), uniqueValue.toString())) {
                throw new DuplicateKeyException(
                    "Duplicate entry '" + uniqueValue + "' for unique constraint '" + constraint.getName() + "'"
                );
            }
        }
    }
}

// 全局唯一索引服务
@Service
public class UniqueIndexService {
    
    // 本地缓存（减少数据库查询）
    private final LoadingCache<String, Boolean> localCache = CacheBuilder.newBuilder()
        .maximumSize(100000)
        .expireAfterWrite(5, TimeUnit.MINUTES)
        .build(new CacheLoader<String, Boolean>() {
            @Override
            public Boolean load(String key) {
                return checkFromDB(key);
            }
        });
    
    public boolean checkUnique(String bizType, String value) {
        String cacheKey = bizType + ":" + value;
        try {
            return !localCache.get(cacheKey);  // 不存在则唯一
        } catch (Exception e) {
            return checkFromDB(cacheKey);
        }
    }
    
    public boolean checkFromDB(String cacheKey) {
        // 查询唯一索引表
        return uniqueIndexMapper.exists(cacheKey) > 0;
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **唯一索引表的容量**：唯一索引表本身也需要分库分表（按 biz_type 分片），否则会成为性能瓶颈
2. **分布式ID本身就是唯一约束**：如果使用雪花算法生成主键ID，天然全局唯一，不需要额外的唯一约束保证
3. **幂等写入**：分布式环境下，网络超时重试可能导致重复写入。必须在业务层做幂等处理（如 `INSERT IGNORE` + 唯一索引）
4. **加分回答**：可以提到 Google Spanner 的全局唯一索引方案——使用分布式事务保证全局唯一，但写入延迟较高

```java
        // 策略1：按分片分组，同分片的SQL合并为一条批量SQL
        Map<String, List<ExecutionUnit>> groupedByShard = groupByShard(batchUnit.getUnits());

            if (units.size() == 1) {
                // 单条SQL：直接执行
                responses.add(executeSingle(dataSourceName, units.get(0)));
            } else {
                // 多条SQL：合并为批量执行（addBatch + executeBatch）
                responses.add(executeBatch(dataSourceName, units));
            }
        }
        return responses;
    }
    
    // JDBC批量执行
    private ExecuteResponse executeBatch(String dataSourceName, List<ExecutionUnit> units) {
        try (Connection conn = getDataSource(dataSourceName).getConnection();
             PreparedStatement pstmt = conn.prepareStatement(units.get(0).getSql())) {
            
            for (ExecutionUnit unit : units) {
                // 设置参数
                for (int i = 0; i < unit.getParameters().size(); i++) {
                    pstmt.setObject(i + 1, unit.getParameters().get(i));
                }
                pstmt.addBatch();
            }
            
            int[] results = pstmt.executeBatch();
            return new ExecuteResponse(results);
        } catch (SQLException e) {
            throw new SQLExecuteException(e);
        }
    }
}
```

### 第28集：分库分表的容量规划：如何根据数据量、TPS、增长率确定分片数

**💡 核心回答：**

分片数的确定是一个**容量规划问题**，需要综合考虑数据量、QPS、TPS、增长率和运维成本。

**分片数计算公式：**

```
分片数 = max(
    数据量分片数 = 预估总数据量 / 单分片最大数据量,
    TPS分片数 = 峰值TPS / 单分片最大TPS,
    连接数分片数 = 峰值连接数 / 单分片最大连接数
)
然后向上取到 2的N次方（方便后续翻倍扩容）
```

**关键参数参考值：**

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| 单表最大行数 | 500万-2000万 | SSD盘可以更大 |
| 单表最大容量 | 5GB-20GB | 影响备份恢复时间 |
| 单库最大QPS | 3000-8000 | 取决于SQL复杂度 |
| 单库最大TPS | 1000-3000 | 取决于事务大小 |

**2的N次方原则：**
- 选择 2、4、8、16、32、64、128 作为分片数
- 原因：翻倍扩容时只需将 N 扩到 2N，每个分片拆分为2个

**📦 实际例子：**

悦茶平台订单库容量规划过程：

```
已知条件：
- 3000+门店，日均订单50万单
- 峰值TPS：2000（双十一5倍 = 10000）
- 订单保留3年（365 × 3 × 50万 = 5.475亿条）
- 单条订单约500字节
- 总数据量：5.475亿 × 500B ≈ 250GB

Step 1：按数据量计算
  单表推荐500万行 → 需要 5.475亿 / 500万 = 110个分片
  如果每分片4张表 → 需要 110/4 = 28个库 → 取32个库

Step 2：按TPS计算
  单库推荐TPS 3000 → 需要 10000 / 3000 ≈ 4个库（峰值）
  但考虑日常峰值2000 → 2000/3000 ≈ 1个库
  TPS不是瓶颈

Step 3：最终决策
  32个库 × 4张表 = 128个分片
  单表最大数据量 = 5.475亿 / 128 ≈ 428万行 ✅
  峰值每库TPS = 10000 / 32 ≈ 313 ✅
  
  选择 32库4表 = 128分片，未来可扩到64库（翻倍扩容）
```

```java
// 容量规划工具（悦茶内部工具类）
public class ShardingCapacityPlanner {
    
    // 分片数计算器
    public ShardingPlan calculate(ShardingRequirement requirement) {
        // 按数据量计算
        int dataBasedShards = (int) Math.ceil(
            (double) requirement.getTotalRows() / requirement.getMaxRowsPerShard()
        );
        
        // 按TPS计算
        int tpsBasedShards = (int) Math.ceil(
            (double) requirement.getPeakTPS() / requirement.getMaxTPSPerShard()
        );
        
        // 按数据量+TPS取最大值
        int rawShardCount = Math.max(dataBasedShards, tpsBasedShards);
        
        // 向上取到2的N次方
        int finalShardCount = roundUpToPowerOf2(rawShardCount);
        
        // 计算库表分配
        int tableCount = determineTableCount(finalShardCount, requirement);
        int databaseCount = finalShardCount / tableCount;
        
        return new ShardingPlan(databaseCount, tableCount, finalShardCount);
    }
    
    // 向上取到2的N次方
    private int roundUpToPowerOf2(int value) {
        int n = 1;
        while (n < value) {
            n <<= 1;
        }
        return n;
    }
    
    // 确定每个库的表数（通常2-8张）
    private int determineTableCount(int totalShards, ShardingRequirement requirement) {
        // 原则：数据库数量不宜太多（运维成本），表数量也不宜太多
        // 推荐：数据库数量在 4-64 之间
        for (int tableCount = 8; tableCount >= 2; tableCount--) {
            int dbCount = totalShards / tableCount;
            if (dbCount >= 4 && dbCount <= 64) {
                return tableCount;
            }
        }
        return 4;  // 默认每库4张表
    }
}

public class ShardingPlan {
    private final int databaseCount;    // 数据库数量
    private final int tableCount;       // 每个库的表数量
    private final int totalShards;      // 总分片数
    
    // 预估数据分布
    public void printAnalysis(ShardingRequirement requirement) {
        long rowsPerShard = requirement.getTotalRows() / totalShards;
        long sizePerShard = rowsPerShard * requirement.getAvgRowSize();
        
        System.out.println("分片方案: " + databaseCount + "库 × " + tableCount + "表");
        System.out.println("总分片数: " + totalShards);
        System.out.println("每分片数据量: " + rowsPerShard + " 行");
        System.out.println("每分片存储: " + formatSize(sizePerShard));
        System.out.println("峰值TPS/分片: " + requirement.getPeakTPS() / totalShards);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **不要过度分片**：分片数越多，广播路由代价越大，运维复杂度越高。建议在满足需求的前提下尽量减少分片数
2. **预留扩容空间**：分片数选择时要考虑未来1-2年的增长。如果当前需要10个分片，建议直接选16个
3. **冷热数据分离**：历史订单可以迁移到归档库，减少在线分片的数据量压力
4. **加分回答**：可以提到云原生数据库（如PolarDB-X、TiDB）的自动扩缩容能力，减少手动容量规划的需求

```java
// SQL Federation 引擎
// org.apache.shardingsphere.sql.federation.engine.SQLFederationEngine
public final class SQLFederationEngine {
    
    private final SQLFederationPlanner planner;
    private final SQLFederationExecutor executor;
    
    // 判断是否需要Federation（复杂查询才走Federation）
    public boolean needFederation(final SQLStatementContext sqlStatementContext) {
        // 包含跨分片JOIN、子查询、窗口函数等复杂操作
        return containsCrossShardJoin(sqlStatementContext)
            || containsSubQuery(sqlStatementContext)
            || containsWindowFunction(sqlStatementContext);
    }
    
    // Federation执行流程
    public MergedResult executeFederation(final SQLStatementContext context,
                                           final RouteContext routeContext) {
        // 1. 生成执行计划
        FederationPlan plan = planner.plan(context, routeContext);
        
        // 2. 根据计划选择执行策略
        switch (plan.getStrategy()) {
            case BROADCAST_HASH_JOIN:
                // 广播所有分片数据到计算节点做Hash Join
                return executeBroadcastJoin(plan);
            case PUSHDOWN_MERGE:
                // 将能下推的条件推到各分片执行，结果归并
                return executePushdownMerge(plan);
            case SHUFFLE_JOIN:
                // 按Join Key Shuffle到不同计算节点
                return executeShuffleJoin(plan);
        }
    }
}
```

```
示例：YC20250615143052 010086 1234
```

```java
// 完整SQL执行链路
// org.apache.shardingsphere.driver.executor.engine.ShardingSphereStatementExecuteEngine
public final class ShardingSphereStatementExecuteEngine {
    
    public ExecuteResponseEngine execute(final String sql, final Object[] params) {
        // 1. SQL解析（ANTLR）
        SQLStatementContext sqlStatementContext = sqlParserEngine.parse(sql, params);
        
        // 2. SQL路由（分片路由 + 读写分离路由 + Hint路由）
        RouteContext routeContext = routeEngine.route(sqlStatementContext, params);
        
        // 3. SQL Federation检查（是否需要联邦查询）
        if (federationEngine.needFederation(sqlStatementContext)) {
            return federationEngine.execute(sqlStatementContext, routeContext);
        }
        
        // 4. SQL改写（表名替换、分页改写、AVG改写）
        SQLRewriteContext rewriteContext = rewriteEngine.rewrite(routeContext, sql);
        
        // 5. SQL执行（多线程并发）
        List<QueryResult> results = executeEngine.execute(rewriteContext);
        
        // 6. 结果归并（流式归并/内存归并）
        return mergeEngine.merge(results, rewriteContext);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **ZooKeeper集群的稳定性**：ShardingSphere Cluster模式依赖ZK存储规则和元数据，ZK抖动会导致路由规则加载失败。建议ZK集群至少3节点，且与应用同机房部署
2. **分片规则变更的灰度发布**：修改分片规则不能一次性生效所有节点，应该分批灰度（先灰度1台机器，验证无误后再全量推送）
3. **数据倾斜监控**：定期检查各分片的数据量分布，如果某分片数据量超过平均值50%，需要调整分片算法或分片键
4. **加分回答**：可以提到悦茶平台的整体技术架构——订单库用ShardingSphere分片，商品库用Redis缓存+单库，用户库用ES做全文检索，形成多层次的数据架构
