### 1.1 DDL

`vtsl-shortlink-keygenerator/src/main/resources/schema-kgs.sql`：

```sql
-- 号段表：一行就是一个业务线的发号游标
CREATE TABLE IF NOT EXISTS t_key_segment (
    biz_tag     VARCHAR(64)  NOT NULL COMMENT '业务标识',
    max_id      BIGINT       NOT NULL DEFAULT 0 COMMENT '已分配出去的最大 id（下一个号段从 max_id 开始）',
    step        INT          NOT NULL DEFAULT 1000 COMMENT '每次领取的号段长度',
    updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (biz_tag)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO t_key_segment (biz_tag, max_id, step)
VALUES ('shortlink', 0, 1000)
ON DUPLICATE KEY UPDATE biz_tag = biz_tag;
```

> 建议放在**业务库同一个 MySQL 实例**（KGS 只需要一张表，独立实例是浪费）。若追求极致隔离可独立库，但会失去单机事务能力——本方案不需要跨库事务，同实例即可。

### 1.2 pom 依赖变更

```xml
<!-- ❌ 删除 -->
<dependency>
```

**为什么用 `JdbcTemplate` 而不是 JPA**（面试可讲的决策点）：

> KGS 全模块的数据库操作只有一条 `SELECT ... FOR UPDATE` 和一条 `UPDATE`。为此引入 Hibernate/JPA 意味着多一层 ORM 映射、一级缓存、脏检查、实体生命周期管理——对一个只需要执行两条 SQL 的轻量发号服务来说是净负担。`JdbcTemplate` 零 ORM 开销，且 `FOR UPDATE` 的行锁语义在这里必须显式可见，ORM 反而容易把它藏起来。

## 2. 阶段 2：编码层（混淆 + Base58）

### 2.1 `util/ObfuscationCodec.java`

```java
package com.jolumn.vtslkgs.util;

import java.util.Optional;

/**
 * 短码编解码器：id → 混淆 → Base58。
 *
 * <p>混淆采用限定域内的乘法逆元：codeInt = (id * KEY) mod 2^bits。
 * KEY 为奇数时与 2^bits 互质，存在逆元，因此这是一个<b>双射</b>——
 * 既保证不可预测（无密钥无法反推），又保证永不碰撞（置换必然一对一）。
 *
 * <p>字符集与 Gateway {@code ShortCodeValidationFilter} 的 {@code [1-9A-HJ-NP-Za-km-z]}
 * 完全一致（标准 Bitcoin Base58，去掉易混淆的 0/O/I/l），因此网关侧校验天然兼容。
 */
public final class ObfuscationCodec {

    private static final char[] BASE58 =
            "123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz".toCharArray();

    private final long mask;
    private final long key;
    private final long inverse;

    /**
     * @param bits 混淆域位宽。40 ⇒ 短码 ≤ 7 字符、容量 1.1e12；64 ⇒ ≤ 11 字符、容量 1.8e19
     * @param key  混淆密钥，<b>必须为奇数</b>（否则在 2^bits 域内不存在乘法逆元）
     */
    public ObfuscationCodec(int bits, long key) {
        if (bits <= 0 || bits > 64) {
            throw new IllegalArgumentException("bits must be in (0, 64], got " + bits);
        }
        if ((key & 1L) == 0L) {
            throw new IllegalArgumentException("key must be odd to have a modular inverse, got " + key);
        }
        this.mask = (bits == 64) ? -1L : ((1L << bits) - 1L);
        this.key = key & this.mask;
        this.inverse = modInverse64(this.key);
    }

    /** 2-adic Newton 迭代求 Z/2^64 下的乘法逆元；每轮精度翻倍，6 轮远超 64 位 */
    private static long modInverse64(long odd) {
        long inv = odd;
        for (int i = 0; i < 6; i++) {
            inv *= 2 - odd * inv;
        }
        return inv;
    }

    /** id → 混淆整数（双射） */
    public long obfuscate(long id) {
        return (id * key) & mask;
    }

    /** 混淆整数 → id（逆运算） */
    public long deobfuscate(long codeInt) {
        return (codeInt * inverse) & mask;
    }

    /** id → 短码 */
    public String encode(long id) {
        long n = obfuscate(id);
        StringBuilder sb = new StringBuilder(12);
        do {
            sb.append(BASE58[(int) Long.remainderUnsigned(n, 58L)]);
            n = Long.divideUnsigned(n, 58L);
        } while (n != 0L);
        return sb.reverse().toString();
    }

    /** 短码 → id；含非法字符或超出域宽时返回 empty */
    public Optional<Long> decode(String code) {
        long n = 0L;
        for (int i = 0; i < code.length(); i++) {
            int d = indexOf(code.charAt(i));
            if (d < 0) return Optional.empty();
            n = n * 58L + d;
            if (Long.compareUnsigned(n, mask) > 0) return Optional.empty();
        }
        return Optional.of(deobfuscate(n));
    }

    /** 当前 bits 下的最大短码长度（40 ⇒ 7，64 ⇒ 11） */
    public int maxLength() {
        int len = 0;
        long v = mask;
        while (v != 0L) {
            len++;
            v = Long.divideUnsigned(v, 58L);
        }
        return len;
    }

    private static int indexOf(char c) {
        if (c < '1') return -1;
        for (int i = 0; i < BASE58.length; i++) {
            if (BASE58[i] == c) return i;
        }
        return -1;
    }
}
```

### 2.2 长度与容量速算

| bits | 容量 | `maxLength()` | 说明 |
|---|---|---|---|
| **40**（默认） | 1.1 × 10¹² | **7** | 与现状 6 位随机码长度接近，容量绝对够 |
| 64 | 1.8 × 10¹⁹ | **11** | 恰好等于 Gateway 正则 `{1,11}` 的上限 |

推导：`log₅₈(2^bits) = bits × log₁₀2 / log₁₀58 = bits × 0.30103 / 1.76343`

- bits=40：`40 × 0.17068 = 6.83` ⇒ 上限 **7**
- bits=64：`64 × 0.17068 = 10.92` ⇒ 上限 **11**

### 2.3 密钥选择建议

| bits | 推荐密钥 | 来源 |
|---|---|---|
| 40 | `0x9E3779B97FL` | Knuth 黄金分割乘法散列常数的截断，奇数，位分布均匀 |
| 64 | `0xFF51AFD7ED558CCDL` | splitmix64 常数，奇数 |

> **务必为奇数**，否则 `(key & mask)` 与 `2^bits` 不互质，逆元不存在 ⇒ 混淆退化成非双射 ⇒ 会碰撞。构造函数已做防御性校验。

### 3.2 `repository/SegmentAllocator.java`

```java
package com.jolumn.vtslkgs.repository;

import com.jolumn.vtslkgs.entity.Segment;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;

@Repository
public class SegmentAllocator {

    private final JdbcTemplate jdbc;
    private final String bizTag;
    private final int step;

    public SegmentAllocator(JdbcTemplate jdbc,
                            @Value("${shortly.kgs.segment.biz-tag:shortlink}") String bizTag,
                            @Value("${shortly.kgs.segment.step:1000}") int step) {
        this.jdbc = jdbc;
        this.bizTag = bizTag;
        this.step = step;
    }

    /**
     * 领取下一个号段。
     *
     * <p><b>必须包在同一个事务里</b>：SELECT ... FOR UPDATE 在 autocommit 下锁会随语句结束立即释放，
     * 两个并发领取者会读到同一个 max_id 并各自推进 ⇒ 号段重叠。
     * 同一事务保证锁持有到 UPDATE 完成，天然把并发领取者串行化——
     * 这同时解决了旧方案的【P1-6 惊群补货】，且不需要任何分布式锁或 Lua 脚本。
     */
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public Segment nextSegment() {
        Long maxId = jdbc.queryForObject(
                "SELECT max_id FROM t_key_segment WHERE biz_tag = ? FOR UPDATE",
                Long.class, bizTag);
        if (maxId == null) {
            throw new IllegalStateException("segment row not found for bizTag=" + bizTag);
        }
        long start = maxId;
        long end = start + step;
        jdbc.update("UPDATE t_key_segment SET max_id = ? WHERE biz_tag = ?", end, bizTag);
        return new Segment(start, end);
    }
}
```

### 3.3 `segment/SegmentBuffer.java`（双 buffer）

```java
package com.jolumn.vtslkgs.segment;

import com.jolumn.vtslkgs.entity.Segment;
import com.jolumn.vtslkgs.repository.SegmentAllocator;
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.*;
import java.util.concurrent.locks.LockSupport;

/**
 * 号段双缓冲。
 *
 * <ul>
 *   <li>{@code current}：正在发放的号段，消耗由 {@link AtomicLong} 自增完成，<b>零 IO、零网络</b></li>
 *   <li>{@code standby}：消耗到 {@code preloadRatio} 时由后台线程异步预领的下一段</li>
 * </ul>
 *
 * <p>只要 standby 提前就位，号段切换就是一次引用赋值，发放线程永不阻塞。
 * standby 未就绪时同步兜底领取（会阻塞一次，仅在数据库抖动时发生）。
 */
@Component
public class SegmentBuffer {

    private static final Logger log = LoggerFactory.getLogger(SegmentBuffer.class);

    private final SegmentAllocator allocator;
    private final double preloadRatio;

    private final AtomicReference<Segment> current = new AtomicReference<>();
    private final AtomicReference<Segment> standby = new AtomicReference<>();
    private final AtomicLong cursor = new AtomicLong();
    private final AtomicBoolean switching = new AtomicBoolean(false);
    private final AtomicBoolean loading = new AtomicBoolean(false);

    private final ExecutorService loader = Executors.newSingleThreadExecutor(
            Thread.ofVirtual().name("kgs-seg-loader-", 0).factory());

    public SegmentBuffer(SegmentAllocator allocator,
                         @Value("${shortly.kgs.segment.preload-ratio:0.2}") double preloadRatio) {
        this.allocator = allocator;
        this.preloadRatio = preloadRatio;
    }

    @PostConstruct
    public void init() {
        Segment first = allocator.nextSegment();
        current.set(first);
        cursor.set(first.start());
        log.info("KGS initial segment [{}, {})", first.start(), first.end());
    }

    /** 领取下一个 id：纯内存自增 */
    public long nextId() {
        for (;;) {
            long id = cursor.getAndIncrement();
            Segment seg = current.get();
            if (id < seg.end()) {
                maybePreload(id, seg);
                return id;
            }
            // 当前号段耗尽：第一个到达者负责切换，其余短暂自旋等待
            if (switching.compareAndSet(false, true)) {
                try {
                    doSwitch();
                } finally {
                    switching.set(false);
                }
            } else {
                LockSupport.parkNanos(1_000_000L);   // 1ms
            }
        }
    }

    private void maybePreload(long issued, Segment seg) {
        long remaining = seg.end() - issued;
        if (remaining > seg.size() * preloadRatio) return;
        if (standby.get() != null) return;
        if (!loading.compareAndSet(false, true)) return;   // 已有线程在领
        CompletableFuture.runAsync(this::loadStandby, loader)
                .whenComplete((r, t) -> loading.set(false));
    }

    private void loadStandby() {
        try {
            Segment s = allocator.nextSegment();
            standby.set(s);
            log.debug("Standby segment ready [{}, {})", s.start(), s.end());
        } catch (Exception e) {
            // 不抛出：发放线程会在号段耗尽时同步兜底领取
            log.error("Failed to preload standby segment, will fetch synchronously later", e);
        }
    }

    private void doSwitch() {
        Segment next = standby.getAndSet(null);
        if (next == null) {
            log.warn("Standby segment not ready, fetching synchronously (issuing thread blocked)");
            next = allocator.nextSegment();
        }
        current.set(next);
        cursor.set(next.start());
        log.info("Switched to segment [{}, {})", next.start(), next.end());
    }

    @PreDestroy
    public void shutdown() {
        loader.close();
    }
}
```

> 落地提示：`nextId()` 在号段边界可能出现多个线程同时越过 `seg.end()`。此时只有一个线程 CAS 成功执行 `doSwitch()` 重置 `cursor`，其余线程 `parkNanos(1ms)` 后重试。这个自旋只在号段切换的瞬间出现，且 `doSwitch()` 通常因 standby 已就位而是纯引用赋值，实际停顿在微秒级。

## 4. 阶段 4：改造 KeyService（60 行 → 12 行）

```java
package com.jolumn.vtslkgs.service;

import com.jolumn.vtslkgs.segment.SegmentBuffer;
import com.jolumn.vtslkgs.util.ObfuscationCodec;
import org.springframework.stereotype.Service;

@Service
public class KeyService {

    private final SegmentBuffer buffer;
    private final ObfuscationCodec codec;

    public KeyService(SegmentBuffer buffer, ObfuscationCodec codec) {
        this.buffer = buffer;
        this.codec = codec;
    }

    /**
     * 发放短码。
     *
     * <p>纯 CPU 路径：号段内原子自增 + 乘法混淆 + Base58 编码。
     * 无网络往返、无磁盘写、无跨存储状态机 —— 预生成/队列的全部收益得以完整保留。
     */
    public String getKey() {
        return codec.encode(buffer.nextId());
    }
}
```

**对比原实现，消失的东西**：

| 原逻辑 | 去哪了 |
|---|---|
| `LLEN` 检查 + 阈值补货 | → `SegmentBuffer` 双 buffer 预领 |
| `RPOP` 出队 | → `AtomicLong.getAndIncrement()` |
| Mongo `insert(available)` | → 删除（无账本） |
| Mongo `updateFirst` CAS | → 删除（单调递增数学保证唯一） |
| `MAX_ISSUE_ATTEMPTS` 重试 | → `AtomicLong` 不会失败，无需重试 |
| `DuplicateKeyException` 重试 | → 不可能碰撞，不存在该分支 |
| Redis 可用性检查 | → 发号不再依赖 Redis |

**`KeyGrpcService` 完全不改**，`GetKey(Empty) → KeyResponse` 契约不变。

### 5.3 `config/KgsCodecConfig.java`

```java
package com.jolumn.vtslkgs.config;

import com.jolumn.vtslkgs.util.ObfuscationCodec;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class KgsCodecConfig {

    @Bean
    public ObfuscationCodec obfuscationCodec(@Value("${shortly.kgs.codec.bits:40}") int bits,
                                             @Value("${shortly.kgs.codec.key}") long key) {
        ObfuscationCodec codec = new ObfuscationCodec(bits, key);
        if (codec.maxLength() > 11) {
            // Gateway ShortCodeValidationFilter 的 Base58 分支上限为 11
            throw new IllegalStateException("configured bits produce too long codes: " + codec.maxLength());
        }
        return codec;
    }
}
```

## 6. 阶段 6：api 侧修复事务内 RPC

> 与存储选型正交，但是同一批重构必须一起修的问题（【P2-9】）。

### 6.1 问题

```java
@Transactional
public CreateUrlResponse create(Long userId, CreateUrlRequest req) {
    existsByOriginalUrl...            // ← 已占用 DB 连接
    shortKey = keyServiceClient.getKey();   // ← 事务内最长 2s 的 gRPC
    save(url);
}
```

KGS 抖动 ⇒ HikariCP 30 个连接被慢事务占满 ⇒ 短链跳转也跟着挂。

### 6.2 改造：把 RPC 移出事务边界

```java
public CreateUrlResponse create(Long userId, CreateUrlRequest req) {
    // ① 事务外：只读校验（不占长连接）
    if (urlRepository.existsByOriginalUrlAndUserIdAndDeletedAtIsNull(req.getOriginalUrl(), userId)) {
        throw new BizException(409, "This URL has already been shortened.");
    }

    // ② 事务外：取码（慢操作，绝不放事务里）
    String shortKey = resolveShortKey(userId, req);

    // ③ 短事务：冲突检查 + 落库
    Url url;
    try {
        url = urlWriteService.insert(userId, req, shortKey);
    } catch (DuplicateKeyException e) {
        // MySQL uk_short_key 是最终裁判 —— 把 DB 异常翻译成业务语义
        throw new BizException(409, "ShortKey conflict, please retry");
    }

    // ④ 事务外：写缓存
    cacheUrlAsync(url);
    return CreateUrlResponse.from(url);
}
```

### 6.3 ⚠️ 必须新开一个类，否则 `@Transactional` 自调用失效

Spring 声明式事务基于 AOP 代理，**同一个类内部方法互调不会经过代理**。因此不能把 `insert` 写成 `UrlService` 里的另一个方法：

```java
@Service
public class UrlWriteService {

    private final UrlRepository urlRepository;

    @Transactional
    public Url insert(Long userId, CreateUrlRequest req, String shortKey) {
        if (urlRepository.existsByShortKeyAndDeletedAtIsNull(shortKey)) {
            throw new BizException(409, "This short key already exists.");
        }
        Url url = new Url();
        url.setOriginalUrl(req.getOriginalUrl());
        url.setShortKey(shortKey);
        url.setTitle(req.getTitle());
        url.setUserId(userId);
        return urlRepository.save(url);
    }
}
```

> 顺带把原先缺失的 `DuplicateKeyException` 兜底补上了（旧文档 §15-1 承认的 TOCTOU 边界）。

### 7.2 `step` 的调优建议

| 场景 | step | 理由 |
|---|---|---|
| 低流量（< 10 创建/秒） | 1000 | 每 ~100 秒领一次号段，DB 压力可忽略 |
| 高流量（> 1000 创建/秒） | 10000~100000 | 降低领号频率；代价是重启时丢弃的 ID 更多（但 ID 空洞无成本） |
| 多 KGS 实例 | 同上 | 各实例领不同号段，`FOR UPDATE` 保证不重叠 |

## 8. 阶段 8：灰度、回滚与数据迁移

### 8.1 数据迁移：**零迁移**

这是本方案最舒服的一点。新旧短码都是 `t_url.short_key` 里的一个字符串：

```java
// redirect 只当字符串用，不关心它由什么算法产生
Url url = urlRepository.findByShortKeyAndDeletedAtIsNull(shortKey)
```

| 短码批次 | 格式 | 长度 | Gateway `DB_CODE` 正则 `^[a-zA-Z0-9]{2,20}$` |
|---|---|---|---|
| 切换前产生 | 随机 Base62 | 6 | ✅ 匹配 |
| 切换后产生 | 混淆 Base58 | ≤7（bits=40）或 ≤11（bits=64） | ✅ 匹配 |

⇒ **历史短链全部继续可用，不需要任何回填或双写。**

### 8.2 灰度步骤

| 步骤 | 动作 | 观察指标 |
|---|---|---|
| 1 | 部署新 KGS，**先不要删 Mongo 数据** | 服务健康、gRPC 连通 |
| 2 | 观察 24h | `t_key_segment.max_id` 匀速增长、无 `Failed to preload` 错误日志 |
| 3 | 抽查新生成的短码 | 长度 ≤7、字符在 Base58 内、无重复 |
| 4 | 确认无异常后**停用** Mongo 实例 | 无业务影响 |
| 5 | 再观察 7 天 | 确认稳定后 `drop collection shortkeys` |

### 8.3 回滚方案

**不引入代码级开关**（保留 `legacy` 分支意味着必须保留 Mongo 依赖，等于重构没做）。回滚 = 回滚部署：

```bash
git revert <重构提交>
重新部署 KGS
# Mongo 里的 shortkeys 在第 5 步之前都还在，旧逻辑可立即恢复
```

回滚窗口：只要在 §8.2 第 5 步之前，随时可回滚，且**已发出的短码不会失效**（无论新旧都由同一张 `t_url` 承接）。

### 8.4 为什么不引入配置开关

| 理由 | 说明 |
|---|---|
| 新逻辑无外部依赖 | 纯 CPU + 一条 `FOR UPDATE`，失败面远小于旧逻辑（旧逻辑依赖 Redis + Mongo 两个外部组件） |
| 保留开关成本高 | 两套 `KeyService` 并存 ⇒ Mongo 依赖不能删 ⇒ 组件数不降反维持 3 个 |
| 回滚已足够快 | gRPC 契约不变，KGS 可独立回滚，api 无感知 |

## 10. 阶段 10：收益度量

### 10.1 交付前后对比

| 指标 | 改造前 | 改造后 | 度量方式 |
|---|---|---|---|
| 发号路径外部 RTT | 2 次（Redis + Mongo） | **0** | SkyWalking 打点 |
| 发号 P99 | ~1–3 ms | **< 0.01 ms** | JMH / Micrometer Timer |
| 号段切换毛刺 | 无（但有周期性同步补货毛刺数十 ms） | **无**（异步预领） | P99.9 对比 |

| KGS 常驻数据量 | 约 N（短码数）× 150B 线性增长 | **1 行** | `db.t_key_segment.countDocuments()` → `SELECT COUNT(*)` |
| 九大问题 | 9 个 | **0 个** | 对照 `问题剖析` §2.10 汇总表 |

### 10.2 建议补的观测点

```java
// SegmentBuffer
MeterRegistry registry;
registry.counter("kgs.key.issued");                        // 累计发放
Timer record = registry.timer("kgs.key.issue.latency");    // 发放耗时（应接近 0）
registry.counter("kgs.segment.switch");                    // 号段切换次数
registry.counter("kgs.segment.sync_switch");               // 兜底同步切换（应长期为 0，非 0 说明 preload 跟不上）
```

> `kgs.segment.sync_switch > 0` 是一个很有价值的告警信号：说明 `step` 太小或 DB 变慢，需要调大 `step` / `preload-ratio`。

### 10.3 后续可选增强（方案 C）

若要保留 MongoDB，把它挪到点击流（详见《问题剖析与方案对比》§四-C）：

```
t_analytics (MySQL)  ──双写灰度──▶  click_events (MongoDB, TTL 180 天)
                                     └─ $group 聚合管道做多维下钻
```

此时 Mongo 的存在理由才成立：**写多读少的半结构化埋点流水，需要 schema 自由演进 + 多维聚合 + TTL 自动归档 + 与主库物理隔离**。

## 附：一句话总结

> 改造的本质不是「把 Mongo 换成 MySQL」，而是**删掉一个因为错误的技术选择而诞生的数据结构**。
> 短码唯一性从「事后检测 + 状态机」变成「事前数学保证」之后，账本、CAS、队列、孤儿库存、惊群补货、出队失联，一并消失。
