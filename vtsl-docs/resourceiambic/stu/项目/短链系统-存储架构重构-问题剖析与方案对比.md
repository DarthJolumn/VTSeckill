### 1.1 三存储分工

| 存储 | 用途 | 集合 / 表 | 关键文件 |
|---|---|---|---|
| **MongoDB** | 短码全局库存（唯一性 + 状态机） | `shortkeys` | `ShortKeyDocument.java` / `KeyGenerator.java` / `KeyService.java` |

### 1.2 发号链路（当前实现）

```
【生成侧（重）】                              【发放侧（应当轻）】
SecureRandom 随机 6 位 Base62                 Redis RPOP（原子 O(1)）
      │                                              │
Mongo insert(status=available) ──▶ Redis List ───────┘
      │                                              │
  唯一索引防重                              Mongo CAS(available→used)
```

```43:65:vtsl-shortlink-keygenerator/src/main/java/com/jolumn/vtslkgs/service/KeyService.java
            String key = redisTemplate.opsForList().rightPop(KgsConstants.REDIS_QUEUE_NAME);
            if (key == null) {
                log.warn("Queue empty after refill (attempt {}/{})", attempt + 1, KgsConstants.MAX_ISSUE_ATTEMPTS);
                continue;
            }

            // CAS 更新：仅当 key 仍为 available 时才置为 used。
            // 若此前出现过"标记超时但实际已成功"，key 已是 used → modifiedCount=0。
            // 不再 push 回队列：已 USED 的脏 key 若回队会陷入"取出→CAS 失败→回队"死循环，直接丢弃取下一个。
            var result = mongoTemplate.updateFirst(
                    Query.query(Criteria.where("key").is(key).and("status").is(KgsConstants.STATUS_AVAILABLE)),
                    Update.update("status", KgsConstants.STATUS_USED),
                    "shortkeys"
            );

            if (result.getModifiedCount() > 0) {
                log.debug("Key issued: {}", key);
                return key;
            }
            log.warn("CAS failed for key {}, discarded (attempt {}/{})", key, attempt + 1, KgsConstants.MAX_ISSUE_ATTEMPTS);
        }
        throw new RuntimeException("Failed to issue key after " + KgsConstants.MAX_ISSUE_ATTEMPTS + " attempts");
```

## 二、旧方案九大问题

> 分级：**P0** = 设计错误（应修复）/ **P1** = 生产风险（必须有兜底）/ **P2** = 工程质量

---

### 【P0-1】Mongo 唯一索引对短码唯一性的贡献为 **零**

用户自定义短码路径**完全绕开 KGS**，只查 MySQL：

```60:72:vtsl-shortlink-api/src/main/java/com/jolumn/vtslshortlinkapi/service/UrlService.java

        if (shortKey == null || shortKey.isBlank()) {
            try {
                shortKey = keyServiceClient.getKey();

                throw new BizException(500, "Failed to generate short key");
            }
        }

        if (urlRepository.existsByShortKeyAndDeletedAtIsNull(shortKey)) {
            throw new BizException(409, "The generated ShortKey already exists, please try again");

```

**判据**：短码唯一性这条业务不变量的**最终裁判是 `t_url.uk_short_key`**。「Mongo 说 `available`、MySQL 说已占用」是允许共存的状态，而系统实际生效的只有 MySQL 那份。

于是 `shortkeys.key` 唯一索引剩下的唯一作用是——**让 `generateBatch` 自己不撞自己**。而「批量随机码互不重复」这件事用数学方式（递增 ID / 号段 + 编码）零成本即可保证，不需要一个 O(N) 的全量账本去做**出生即碰撞检测**。

> **面试官一句话击穿**：既然最终裁判是 MySQL 的唯一索引，那 Mongo 那份唯一索引防住了什么？

---

### 【P0-2】CAS 防的是一个不存在的问题，却把「预生成」的全部收益吐了回去

整个「预生成 + Redis 队列」的设计动机是：**让发放路径不碰磁盘**。但发放路径碰了（`updateFirst` = 唯一索引查找 + WiredTiger 磁盘写 + journal）。

**追问链**：

| 面试官 | 你的回答 |
|---|---|
| 为什么预生成？ | 生成是重操作，要让发放变成 O(1) 出队 |
| 那为什么发放还要写一次 Mongo？ | 双保险，防重复发放 |
| 防什么？ | 防同一个 key 被发两次 |
| `RPOP` 不是原子的吗？同一个元素能被两个客户端取出来吗？ | 不能…… |
| 那 CAS 防的是什么？ | …… |

**根因**：
- `RPOP` 在 Redis 单线程语义下保证「一个元素只会交给一个客户端」。
- CAS 唯一能防的场景是「同一个 key 被重复入队」，而这在当前代码里**不可能发生**——`KeyGenerator.generateBatch()` 撞 `DuplicateKeyException` 时是**整批重试**，失败的那批根本没执行 `leftPushAll`。

**代价**：每次取号多一次 Mongo 网络往返 + 唯一索引 B-tree 查找 + 磁盘写。发放耗时从「纯 Redis ~0.2ms」退化成「1~3ms 带磁盘写 + 写锁竞争」。

---

### 【P0-3】账本只写不读，且永不回收

全模块搜索 `STATUS_USED` / `remove(` / `delete(` / `expireAfter` / `TTL`：除了 `Update.update("status", STATUS_USED)` 这一行写入，**没有任何地方读它、清理它、归档它**。

每个短码的生命周期：

```
insert(available)  ──▶  update(used)  ──▶  永寂
     写 1 次              写 1 次          读 0 次
```

- **容量测算**：`ShortKeyDocument` 每条约 100~150 字节（`_id` 12B + `key` 6B + `status` 9B + `createdAt` 8B + 唯一索引 B-tree 条目开销）。1000 万短链 ≈ **1~1.5 GB 纯垃圾**。
- **性能退化**：集合越大，新增 insert 的唯一性检查在 B-tree 里越深，补货越慢。
- **正确归属**：「写两次、读零次」的数据应该进归档/日志/审计流，而不是主库热点集合。

---

### 【P0-4】出队即失联 —— RPOP 成功、CAS 未执行 = 短码永久泄漏

```
RPOP 成功 ──▶ 进程崩溃 / Mongo 超时 / Full GC ──▶ CAS 未执行
                    │
                    └─▶ 该 key 已从队列移除，状态仍是 available
                        但没有任何机制把它重新入队
                        ⇒ 永久不可达，永远不会被再发放
```

这是真正的**号段泄漏**，且**无任何对账补偿**。对比你们秒杀模块：`cancelOrder()` 有 `ReconciliationScheduler` 每 5 分钟对账——短链这边同一类问题裸奔。

---

### 【P1-5】发号成功但业务落库失败 → 短码永久丢失

```
KGS: CAS available→used  ✅ 已完成
api: urlRepository.save(url)  ✗ 撞 uk_short_key / 超时 → 事务回滚
结果：这个短码已是 used，永远回不到 available，也没有回收逻辑
```

这是典型的**跨服务分布式事务无补偿**。而且由于短码是「稀缺随机资源」（不像递增 ID 丢了再取一个即可），泄漏是永久性的。

---

### 【P1-6】惊群式补货 —— 无锁导致 N 并发 = N×1000 条 Mongo insert


队列剩 199 个时，**每一个并发请求都会各自触发一次 `generateBatch(1000)`**（无 `SETNX` 互斥锁）：

```
100 并发请求 × generateBatch(1000) = 100,000 条 Mongo insert
```

这是**能真实打爆 Mongo 的路径**，且在创建短链有任何流量尖峰时必然发生。

### 【P1-7】孤儿库存 —— 跨存储双写非原子

### 【P1-8】Redis 才是真单点，Mongo 不提升任何可用性

## 三、根因：一个不该存在的数据结构

把九大问题收敛，真正的根因只有一句话：

> **「短码账本」的存在理由是假的。它被创造出来是为了解决「随机码会碰撞」，而「随机码会碰撞」这件事本可以用数学方式彻底消除。**

### 3.1 错误的因果链

```
目标：发放一个全局不重复的短码
  ↓ 选了「随机生成」
  ↓ 于是产生「碰撞」这个新问题
  ↓ 于是需要一个全量账本做去重（Mongo 唯一索引）
  ↓ 于是需要状态机做发放确认（CAS）
  ↓ 于是产生跨存储一致性、账本膨胀、孤儿库存、泄漏、惊群……
  ↓ 于是需要一堆补偿机制
```

每一步都在为**上一步的错误选择**买单。

### 3.2 正确的因果链

```
目标：发放一个全局不重复的短码
  ↓ 选了「单调递增 ID / 号段」（数学保证不重复）
  ↓ 唯一性问题直接消失 → 账本不需要了
  ↓ 担心可枚举？加一层双射混淆（乘法逆元 / Feistel）
  ↓ 混淆是双射 ⇒ 仍然零碰撞，且对外不可预测
  ↓ 完成。没有账本、没有 CAS、没有跨存储一致性问题
```

### 3.3 一个反证：同生日悖论的量级计算

6 位 Base62 空间 ≈ 5.68×10¹⁰。按生日悖论，发放 *n* 个随机码的碰撞概率 ≈ `1 - e^(-n²/2N)`：

| 已发放短码数 | 至少一次碰撞的概率 |
|---|---|
| 100 万 | 0.00088% |
| 1000 万 | 0.088% |
| 1 亿 | 8.5% |

**你的真实业务量级（几万~几百万）下，碰撞概率接近 0**。整套「账本 + 唯一索引 + 3 次重试」机制，为一个概率不到千分之一、且 MySQL 唯一索引已经完全兜底的事件，付出了：一个中间件、一次额外磁盘写、一份无限膨胀的数据、六类一致性风险。

## 四、新方案 A / B / C

### 方案 A：彻底去 Mongo —— MySQL 单库 + 算法派生短码（最简）

**思路**：删除 KGS 的账本，短码由递增 ID 直接编码派生，不需要任何碰撞检测。

```
短码 = Base58( 混淆( 递增 ID ) )
        ↑ 双射    ↑ 不可预测  ↑ 数学保证唯一
```

**关键组件**

| 组件 | 实现 |
|---|---|
| ID 来源 | Snowflake（本地）/ MySQL 自增 / Redis `INCR` |
| 混淆层 | **splitmix64 非线性混合**（推荐）；备选：Feistel 网络（需控制长度时） |
| 编码 | Base58，字符集与 Gateway 校验正则**完全一致** |

**为什么用 splitmix64 而不是乘法逆元**

> 这是本方案第一版的**设计缺陷**，已通过实跑验证并修正，详见《实施方案》§11。

乘法逆元（`codeInt = id * K mod 2^bits`）虽然满足双射，但有两个实测确认的硬伤：

```
缺陷 1（致命）：线性，密钥可被已知明文攻击破解
  用户能看到自己创建的短码；只要能推断自己的 id，即可解出 K：
      K = codeInt * inverse(id) mod 2^bits
  一旦 K 泄露，全站短码可被离线推导。

缺陷 2：mod 意义下 codeInt 是等差数列（步长恒为 K mod 2^bits）
  实测 deltas：-419976070785, 679535556991, -419976070785   <- 就是正负 K
  输入输出相关性完全可预测。
```

splitmix64 由两次 XOR-shift 和两次奇常数乘法串联：

```java
long z = id + seed;
z = (z ^ (z >>> 30)) * 0xBF58476D1CE4E5B9L;
z = (z ^ (z >>> 27)) * 0x94D049BB133111EBL;
return z ^ (z >>> 31);
```

**实测结果**（JDK 17 实跑，代码见《实施方案》§11.4）：

| 验证项 | splitmix64 | 乘法逆元（对比） |
|---|---|---|
| 20 万随机 64 位 id 的 `unmix(mix(id)) == id` | **0 失败** | — |
| 200 万 id 编码后无重复（双射性） | **0 碰撞** | 理论上双射但无实测 |
| 相邻 id 前 4 字符相同 | **0 / 100000** | 相关性可预测 |
| 能否用单个方程反推密钥 | **否**（非线性） | **是**（单方程可解） |
| 短码长度范围 | 8 ~ **11** | 4 ~ 7（bits=40） |
| 最短码会撞 Gateway 下限 2 吗 | **不会**（最短 8） | 理论可能 1 字符 |

性质：
- **双射**：XOR-shift（`x ^ x>>>k`）与奇常数乘法在 `Z/2^64` 上都是双射，串联后仍是双射，因此**永不碰撞**
- **非线性**：无法用单个模方程反推 `seed`，因此无已知明文攻击
- **avalanche**：相邻 id 输出完全不相关，因此无前缀可枚举
- **O(1) 纯整数运算**，两次乘法加三次移位，远快于 `SecureRandom` 采样

取 40 位域（或 64 位域），选一个奇数密钥 `K`，则 `K` 在 `Z/2^40` 上存在乘法逆元 `K⁻¹`：

```
编码： codeInt = (id * K)        & MASK      // MASK = 2^40 - 1
解码： id      = (codeInt * K⁻¹) & MASK
```

性质：
- **双射**（线性同余是置换）⇒ **永不碰撞**，这是它强于「随机 + 去重」的根本原因
- **不可预测**（不知道 K 无法从 codeInt 反推 id，也无法预测下一个 id 的码）
- **O(1) 纯整数运算**，一次乘法一次掩码，比 `SecureRandom` 采样快若干个数量级

**长度推导**（决定 `CODE_BITS` 取值）

| CODE_BITS | 容量 | Base58 后长度 | 适用场景 |
|---|---|---|---|
| 40 | 1.1 × 10¹² | ≤ **7** 字符 | **推荐默认**，与现状 6 位接近，容量绝对够 |
| 64 | 1.8 × 10¹⁹ | ≤ **11** 字符 | 超大规模，且天然匹配 Gateway 正则的 11 位上限 |

> 验证：`log58(2^40) = 40 × log10(2)/log10(58) = 40 × 0.30103/1.76343 = 6.83` ⇒ 上限 7 字符。
> `log58(2^64) = 10.92` ⇒ 上限 11 字符，恰好落在 Gateway `ShortCodeValidationFilter` 的 `{1,11}` 上限内。

**字符集一致性**（重要）

现状 Gateway 过滤器的 Base58 正则字符集为 `[1-9A-HJ-NP-Za-km-z]`，与标准 Bitcoin Base58 字母表 `123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz` **完全一致**（去掉了易混淆的 `0 O I l`）。新方案直接复用同一字符集 ⇒ **Gateway 校验天然兼容，零改动**。

**成本**：移除 MongoDB 依赖、移除 `KeyGenerator`、移除 `ShortKeyDocument`。若进一步取消 KGS 服务，则 gRPC 链路也可去掉（但会损失架构亮点，见方案 B）。

### 方案 B：KGS 保留，Mongo 换成「号段（Leaf-Segment）」 —— **推荐**

> 保留「独立发号微服务 + gRPC 契约 + 预生成 + 惰性补货」的全部架构亮点，只把最不协调的部件换成业界标准方案。

#### B-1 核心设计

```
                    ┌───────────────────────────────────────┐
                    │ t_key_segment (MySQL)                  │
                    │ biz_tag='shortlink'  max_id  step      │
                    └───────────────┬───────────────────────┘
                                    │ SELECT ... FOR UPDATE 行锁，天然串行
                                    │ 一次领 [start, start+step)
                                    ▼
┌─────────────────────────────────────────────────────────────┐
│ KGS 进程内 SegmentBuffer                                     │
│   current = [start, end)        ← 发放线程池纯内存消费        │
│   standby = [start+step, ...)   ← 异步预领（双 buffer）       │
│                                                              │
│   getKey() = Base58(混淆(cursor++))    ← 零 IO，零网络       │
└─────────────────────────────────────────────────────────────┘
```

#### B-2 号段领取（解决 P1-6 惊群）

```sql
SELECT max_id, step FROM t_key_segment WHERE biz_tag = ? FOR UPDATE;   -- 行锁
UPDATE t_key_segment SET max_id = max_id + step WHERE biz_tag = ?;
```

`FOR UPDATE` **天然把并发领取者串行化**——不存在两个 KGS 实例领到重叠号段，也不存在 N 个请求各补一批。**一行锁同时解决了惊群（#6）和分布式互斥，无需分布式锁，无需 Lua**。

#### B-3 发放路径

```java
public String getKey() {
    long id = buffer.nextId();        // AtomicLong 自增，纯内存
    return codec.encode(id);          // 混淆 + Base58，纯整数运算
}
```

**零网络往返、零磁盘写、零外部依赖。** 整个「 Mongo CAS」「出队」「补货」全部消失。

#### B-4 九个问题的解决对照

| # | 问题 | 方案 B 如何解决 |
|---|---|---|
| 1 | Mongo 索引贡献 0 | 无 Mongo，唯一性由单增 ID **数学保证** |
| 2 | CAS 抵消预生成收益 | 无 CAS，发放路径零 IO，预生成收益完整保留 |
| 3 | 账本只写不读 | 无账本，MySQL 只剩一行号段记录 |
| 4 | 出队即失联 | 无队列，`cursor++` 是进程内原子操作，无中间态 |
| 5 | 发号成功落库失败 | 递增 ID 非稀缺资源，**丢弃即可**，无任何损失 |
| 6 | 惊群补货 | `FOR UPDATE` 行锁串行化 |
| 7 | 孤儿库存 | 无跨存储双写 |
| 8 | Redis 单点 | Redis 队列中 Redis 依赖移除，只剩缓存/限流（有 DB 兜底） |
| 9 | 事务内 RPC | 见实施方案 §5：把取码移出事务边界 |

#### B-5 派生亮点（面试加分）

| 亮点 | 话术锚点 |
|---|---|
| **号段 + 双 buffer** | 美团 Leaf 的标准做法；消耗到阈值异步预领下一段，发放线程永不阻塞 |
| **双射混淆防枚举** | 乘法逆元保持双射 ⇒ 零碰撞；不知道密钥无法反推 |
| **优雅降级** | KGS 全挂时，api 可降级到本地 Snowflake + Base58 发号（因为数学保证唯一，无需中心点仲裁） |
| **零迁移** | 旧 6 位随机码与新 Base58 码在 `redirect` 路径上完全等价（都只是 `shortKey` 字符串），**双轨共存，无需数据迁移** |

### 方案 C：Mongo 挪到它真正的位置 —— 存点击流

> 如果一定要保留 MongoDB（学习/简历目的），把它放到**唯一站得住的位置**。

#### C-1 为什么 `t_analytics` 才是 Mongo 的正确战场

| 特征 | 现状 MySQL `t_analytics` | Mongo `click_events` |
|---|---|---|
| 写模式 | **每次点击 INSERT 一条明细**，写放大大（现状文档 §15-5 已承认） | 批量 `insertMany`，写吞吐高 |
| Schema | 加埋点维度要 `ALTER TABLE` | 文档模型，自由演进 |
| 查询 | 多维下钻要多个 `GROUP BY` + 组合索引 | `$group` 聚合管道，一次管道出多维结果 |
| 生命周期 | 无归档机制，表无限膨胀 | **TTL 索引** `expireAfterSeconds` 自动过期 |
| 隔离性 | 埋点写入与业务读写抢同一批 HikariCP 连接 | 独立实例，物理隔离 |

#### C-2 文档 Schema 与索引

```javascript
// click_events
{
  _id: ObjectId,
  urlId: NumberLong(123),
  shortKey: "7nK9qP",
  ts: ISODate("2026-10-14T08:12:31Z"),
  ip: "203.0.113.7",
  country: "United States",
  ua: { raw: "Mozilla/5.0 ...", device: "mobile", browser: "Safari 17", os: "iOS 17" },
  referer: "https://x.com/"
}

db.click_events.createIndex({ urlId: 1, ts: -1 });
db.click_events.createIndex({ ts: 1 }, { expireAfterSeconds: 15552000 });  // 180 天 TTL 自动归档
```

#### C-3 聚合下钻（一行取代多个 SQL）

```javascript
db.click_events.aggregate([
  { $match: { urlId: 123, ts: { $gte: ISODate("2026-10-01") } } },
  { $group: {
      _id:   { country: "$country", device: "$ua.device" },
      clicks:{ $sum: 1 },
      uv:    { $addToSet: "$ip" }
  }},
  { $project: { clicks: 1, uv: { $size: "$uv" } } },
  { $sort: { clicks: -1 } }
]);
```

#### C-4 配合使用

方案 C **不是** A/B 的替代品，而是可与 B 叠加：

```
短码生成/发放：MySQL 号段 + Base58 混淆     （方案 B）
业务主数据：   MySQL t_url                  （事务/归属/JOIN）
点击流水：     MongoDB click_events         （方案 C —— Mongo 在这里的理由才成立）
缓存/限流：    Redis
```

**此时「为什么用 Mongo」的话术才成立**：

> 业务主数据在 MySQL 保证事务和归属校验；点击流水是写多读少、维度随埋点演进的半结构化数据，放 MongoDB 用聚合管道做多维下钻，TTL 索引自动归档，并且和主库物理隔离，埋点写入不挤占业务表连接池。

这与「MongoDB 三高、High Performance / Huge Storage」那种放之四海皆准的营销话术，有本质区别：**前者是基于这份数据真实访问模式的推理，后者是用结论找理由。**

### 6.2 推荐路径

**第一步（必做）：方案 B** —— 把发号器换成号段 + 混淆编码，删掉 Mongo 账本。
> 理由：改动集中在 KGS 三个文件内，gRPC 契约不变 ⇒ **api 侧零改动**，风险最低，收益最大（九大问题一并根治，且是唯一能同时解决「发号正确性」和「发号性能」的方案）。

## 七、面试话术改造

### 7.1 千万别这么说

> ❌ 「MongoDB 是为了顺便学习一下用的。」

这句话主动承认架构不合理，等于把刀递给面试官。

### 7.2 推荐说法

> **Q：为什么选择了 MongoDB？**

**若采纳方案 B（推荐）：**

> 我第一版确实用了 MongoDB 做短码账本 + CAS 去重，后来复盘发现这是过度设计，有三处不成立：
> 一是 `RPOP` 本身已经保证一个元素只会交给一个客户端，CAS 防的是一个不存在的问题，而它让发放路径多了一次磁盘写，把「预生成」的全部收益都抵消了；
> 二是这个账本**只写不读、永不回收**——每个短码写两次、读零次，1000 万短链就是 1.5G 垃圾数据；
> 三是短码唯一性的最终裁判其实一直是 MySQL 的 `uk_short_key`，Mongo 那份唯一索引对系统正确性贡献为零，反而引入了出队失联、孤儿库存、惊群补货这些跨存储一致性问题。
>
> 所以我把发号器改成了**号段方案**：KGS 用 `SELECT ... FOR UPDATE` 从号段表一次领一段递增 ID，进程内双 buffer 缓存，发放就是 `AtomicLong` 自增 + Base58 编码，**零网络零磁盘**。唯一性由单调递增在数学上保证，不需要账本也不需要 CAS。为了防止有人遍历短码，我加了一层乘法逆元混淆——它是双射，所以既不可预测又绝不碰撞。这个方案对标美团 Leaf。

**若采纳方案 C（保留 Mongo）：**

> 我的存储是按**数据的访问模式**来分的：业务主数据（URL 映射、归属关系）在 MySQL，因为需要事务保障和外键语义；点击流水是写多读少、埋点维度会持续演进的半结构化数据，放 MongoDB，用聚合管道做多维度下钻分析，TTL 索引自动归档 180 天，并且和主库物理隔离，埋点写入不会挤占业务表的连接池。

### 7.3 主动暴露演化过程的价值

**「我第一版踩过坑、复盘后重构了」远强于「我用了 XX 技术」**——前者是工程判断力，后者是技术堆砌。面试官真正想看的是你能否发现自己的设计问题。

配套的追问弹药：

| 追问 | 答法要点 |
|---|---|
| 混淆用 XOR 不行吗？ | 行，但 XOR 抗差分分析弱；乘法逆元是线性同余置换，且可逆（`codeInt * K⁻¹`），**双射是关键** |
| 号段丢了怎么办？ | 号段是进程内状态，重启丢弃剩余部分，下次从 `max_id` 继续 ⇒ ID 有空洞但绝不重复，正确性不受影响 |
| 多实例会领到重叠号段吗？ | 不会，`FOR UPDATE` 行锁把这些领取者串行化了；这也是它天然不带惊群问题的原因 |
| KGS 全挂了怎么办？ | 因为 ID 只需要「不重复」而不需要中心仲裁，api 可降级为本地 Snowflake + Base58 ⇒ 创建短链不受影响 |
| 新短码和老短码怎么共存？ | `redirect` 只把 shortKey 当字符串查表，两种格式完全等价，零迁移双轨运行 |
