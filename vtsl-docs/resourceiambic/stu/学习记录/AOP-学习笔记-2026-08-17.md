## 1. AOP 是什么 & 解决什么问题

**一句话**：面向切面编程，把**横切关注点**（日志/耗时/事务/权限/缓存/链路追踪等与核心业务无关但必须存在的通用逻辑）从业务代码中剥离，用动态代理在运行时织入，实现**业务零侵入**，符合开闭原则。

**解决了什么**：
- **代码冗余**：改日志格式不用改几十个文件（DRY）
- **职责混乱**：业务方法不再被迫承担基础设施职责（非功能需求与业务逻辑分离）
- **无侵入增强**：业务代码只关心业务本身

**⚠️ 术语**：是"面向切面编程"，不是"面向切片"；"横切关注点"（Cross-Cutting Concerns）是面试加分术语。

## 2. 介绍 AOP 的四步话术（面试直接用）

**「痛点 → 方案 → 原理 → 落地」四步叙事**：

**① 痛点（Why）**
> "没有 AOP 前，业务代码里每个接口都要写日志/耗时/权限/事务，这些像胶水一样粘在业务里：代码冗余，改一格式要改几十处；职责混乱，业务方法被迫背基础设施。"

**② 价值（What）**
> "AOP 把横切关注点从业务中解耦，抽成独立切面，运行时自动织入，业务代码零侵入，符合开闭原则。"

**③ 原理（How）**
> "Spring AOP 底层依赖动态代理：目标有接口用 JDK 动态代理，否则 CGLIB 生成子类。调用方拿到的是代理对象，代理在方法前后插入增强逻辑。这也是同类内部调用失效的原因——绕过了代理。"

**④ 落地（Proof）**
> "我们项目的链路追踪和耗时监控就是 @Around 环绕通知统一实现的：切点匹配 Controller 层方法，proceed() 前后记录时间戳和 TraceId，异常统一捕获格式化。业务代码零改动。@Transactional、@Cacheable 本质上都是 AOP。"

**表达技巧**：避免一上来背"面向切面编程"缩写；强调"无侵入"反复点题；被追问就补 Spring AOP vs AspectJ；主动提"AOP 不是万能，过度使用导致调试困难/性能损耗/隐式行为认知负担"体现工程判断力。

## 3. 五大术语（从定义到代码映射）

| 术语 | 定义 | 类比 | Spring AOP 实例 |
|---|---|---|---|
| **连接点** JoinPoint | 程序执行流中所有可被拦截的位置（被拦截方，无需使用者操作） | 地图上所有可建加油站的位置 | `UserService.save()/delete()...` 每个 public 方法调用 |
| **切点** Pointcut | 连接点的子集，实际选择增强的位置（匹配规则） | 你实际选定的加油站 | `execution(* UserService.save*(..))` |
| **通知** Advice | 定义在切面中，控制增强逻辑"做什么 + 何时做" | 加油站的服务 | `@Before/@After/@Around` 里的代码 |
| **切面** Aspect | 切点 + 通知的模块（@Aspect 类） | 整个加油站 | `@Aspect` 类 |
| **织入** Weaving | 把切面应用到目标对象并创建代理的过程 | 建加油站的过程 | Spring 容器启动时创建代理 |

> ✅ **关键认知**：你不需要"使用"连接点，它自动存在；你只需用切点从中筛选。切点本身不含业务逻辑，逻辑在通知方法体里。

**修正**：切点表达式不只是"某包某类某方法"，还有注解式 `@annotation`；连接点之前模糊，现在明确 = Spring AOP 中每个 public 方法调用。

## 4. 使用与配置

### 4.1 需要的注解全景

| 注解 | 作用 | 位置 |
|---|---|---|
| `@Aspect` | 声明切面类 | 类上 |
| `@Pointcut` | 定义可复用切点表达式 | 方法上（方法体为空） |
| `@Before` / `@After` / `@AfterReturning` / `@AfterThrowing` / `@Around` | 五种通知 | 方法上 |
| `@Order(n)` | 切面优先级，数字越小优先级越高 | 类上/方法上 |
| `@EnableAspectJAutoProxy` | 开启 AOP 支持 | 配置类 |

> ⚠️ **Spring Boot 项目不需要手动加 @EnableAspectJAutoProxy**：`spring-boot-starter-aop` 的自动配置已默认开启。传统 Spring/XML 项目才需要手动加。

### 4.2 五种通知 & 执行顺序

| 通知 | 时机 | 能力 |
|---|---|---|
| `@Before` | 目标方法前 | 只能拿入参，无法阻止执行（除非抛异常） |
| `@AfterReturning` | 正常返回后 | 可拿/改返回值 |
| `@AfterThrowing` | 抛异常后 | 拿异常，决定重抛或吞 |
| `@After` | 执行后（无论成败，finally 语义） | 拿不到返回值和异常详情 |
| `@Around` | 环绕 | **最强大**：可决定是否执行、改入参/返回值、proceed() 控制执行 |

**单个切面内执行顺序（Spring 5.x+）：**
```
Around(前半) → Before → 目标方法 → Around(后半) → After → AfterReturning
                                          ↘ (异常) AfterThrowing
```
> 90% 场景（耗时/链路/统一响应）直接用 @Around 即可，它包含其他四种能力。

**@Order 洋葱模型**：`@Order(1) Around Before → @Order(2) Around Before → 目标 → @Order(2) Around After → @Order(1) Around After`。高优先级在外层。⚠️ 同一切面类内多个通知顺序不确定，需要顺序就拆成多个切面类或用 @Around。

### 4.3 切点表达式（两种主流）

**① 注解驱动（最常用）**
```java
@Pointcut("@annotation(com.example.MyLog)")
```
- 场景：自定义审计日志/限流/缓存标记等声明式横切关注点
- 语义清晰，开发者在业务方法贴注解即生效

**② 路径匹配 execution**
```java
@Pointcut("execution(public * com.example.service..*.*(..))")
```
- 匹配 service 包下所有类的所有 public 方法
- 需要按包/类/方法批量匹配、无法改源码加注解时才用
- 各部分：返回值模式 `*`/`void`、声明类型 `com.example.service..*Service`、方法名 `save*`、参数 `(..)`/`(String,int)`

**③ 组合**
```java
@Pointcut("execution(* com.example.service..*.*(..)) && @annotation(com.example.MyLog)")
```
> `execution` 适用有限，`@annotation` 更灵活，90% 用 @annotation；两者可用 `&&`/`||`/`!` 组合。

### 4.4 @EnableAspectJAutoProxy(proxyTargetClass=true)

- 作用：强制用 CGLIB 代理，忽略目标是否实现接口
- 默认值：Spring Boot 3.x 前默认 false（优先 JDK），3.x 起默认 true

## 5. 原理机制：动态代理

### 5.1 JDK 动态代理

**本质公式**：`接口 + InvocationHandler + 运行时生成实现类 + 反射调用真实方法`

- 前提：目标类必须实现接口
- 运行时 `Proxy.newProxyInstance()` 生成 `$Proxy0/$Proxy1...`（有名字的**顶层类**，不是匿名类）
- `$Proxy0` 只做一件事：**把方法调用转发给 handler.invoke()**，本身不含增强逻辑！类长这样：
```java
public final class $Proxy0 extends Proxy implements UserService {
    private static Method m_login; // static 缓存，避免每次 getMethod 反射查找
    public void login() {
        super.h.invoke(this, m_login, null); // 纯转发，无增强
    }
}
```
- **所有增强逻辑（Before/After）在你自己写的 InvocationHandler.invoke() 方法体里**
- **唯一反射点**：`method.invoke(target, args)`
- Spring 帮你把 @Before/@After 注解方法组装进内置的 `JdkDynamicAopProxy`（它实现 InvocationHandler）

**完整调用链：**
```
外部 proxy.login()
  → $Proxy0.login()（普通调用，无反射）
    → h.invoke(this, m_login, args)（进入 Handler）
      → 【你的 @Before 逻辑】
      → m_login.invoke(target)（唯一反射点）
      → 【你的 @After 逻辑】
      → 返回
```

> 一句话：**代理类负责"拦截转发"，Handler 负责"增强"**。CGLIB 则相反——增强直接写进子类字节码。

### 5.2 CGLIB（读音 CG-Lib = Code Generation Library）

**本质公式**：`继承 + ASM 字节码生成子类 + 直接方法调用`

- 前提：目标类不能是 final，方法不能是 private/final/static
- 底层用 **ASM 框架在运行时内存中生成新字节码**（不是修改旧 .class 文件），`ClassLoader.defineClass()` 加载
- **增强逻辑（Before/After + super.method()）被 ASM 直接写进生成的子类方法体**，没有 Handler 转发，无反射：
```java
public class UserService$$EnhancerByCGLIB extends UserService {
    @Override public void login() {
        System.out.println("【Before】..."); // ASM 直接写入
        super.login();                        // invokespecial，无反射
        System.out.println("【After】...");   // ASM 直接写入
    }
}
```
- 关键：ASM 生成的是**新子类字节码**，原始 .class 没被碰过

**对比记忆：** JDK = "运行时找人代办（Handler）"；CGLIB = "直接把活写进基因里（子类字节码）"。

### 5.3 Spring 如何选择

| | JDK 动态代理 | CGLIB |
|---|---|---|
| 代理方式 | 实现接口 | 继承子类 |
| 核心机制 | Proxy + InvocationHandler + 反射 | ASM 字节码生成子类 |
| 增强逻辑位置 | Handler 的 Java 代码 | 子类字节码内 |
| 原始方法调用 | method.invoke() 反射 | super.method() 直接调用 |
| 性能 | 反射有开销（JDK8+ 有膨胀优化） | 字节码直调更快 |
| 限制 | 必须有接口 | 不能代理 final 类/方法 |
| Spring 默认 | Boot 2.x 默认 CGLIB；Framework6/Boot3.0 **统一默认 CGLIB** | ✅ |

> **版本演进原因**：Boot 3.x / Spring 6 起默认 CGLIB，因 JDK 代理在自调用、非接口方法增强等场景有天然缺陷，CGLIB 行为更一致。

**反射膨胀（性能题加分）**：JDK8+ 当同一 Method 被反射调用超阈值，JVM 生成专门访问器类替代原生反射，性能提升几十倍近直接调用。所以 JDK 代理瓶颈常在 Handler 拦截器链过长，而非反射本身。

## 6. 自调用失效（this 绕过代理）

**唯一根因：`this` 永远指向原始对象实例，而不是代理对象。**

即使 CGLIB 生成了完美子类：
- **外部调用** `proxy.method()`：入口是代理对象 ✅
- **内部自调用** `this.method()`：`this` 编译期就绑定原始类型，直接走原始方法，绕开代理 ❌

> 这是 **Java 语言本身的设计**（`this` 词法作用域绑定），不是 CGLIB bug。JDK 代理同理。

**适用所有 Spring AOP 代理**（@Transactional/@Cacheable/@Async/@自定义切面都一样）：

| 场景 | 是否走代理 | 切面是否生效 |
|---|---|---|
| 外部 Bean 调用本类方法 | ✅ | ✅ |
| 本类 `this.method()` | ❌ | ❌ |
| 本类通过注入的 self 调用 | ✅ | ✅ |
| private / final 方法 | ❌（CGLIB 无法重写） | ❌ |
| static 方法 | ❌ | ❌ |

**解法（3 种）**：
1. 注入自身：`@Autowired private OrderService self; self.method();`（Spring 自注入特殊处理不触发循环依赖问题）
2. `AopContext.currentProxy()`（需 `@EnableAspectJAutoProxy(exposeProxy=true)`）
3. 重构拆分为两个 Service（最根本，符合单一职责）
4. （补充）AspectJ 编译期/加载期织入可从根本消除，重量级方案

## 7. 拦截器链 & Advisor

**拦截器链（Interceptor Chain）= 责任链模式**：和 Servlet FilterChain、Netty Pipeline 同一个设计模式。

```
proxy.method()
  → ExposeInvocationInterceptor
    → AspectJAroundAdvice（包装成 MethodInterceptor）
      → MethodBeforeAdviceInterceptor
        → AfterReturningAdviceInterceptor
          → ReflectiveMethodInvocation.proceed()
            → target.method()（最后一个调用真实目标）
```
- 每个 Advisor 被适配为一个 MethodInterceptor
- 按 Order 排序组成 List
- `proceed()` 递归调用下一个拦截器

**Advisor / Advice / Pointcut 三者**：
```
Advisor = Advice + Pointcut
- Advice：做什么（增强逻辑）
- Pointcut：在哪做（匹配规则）
- Advisor：把"做什么"+"在哪做"绑定的完整单元，是拦截器链的基本元素
```

**通知注解 → 拦截器映射**：@Before→MethodBeforeAdviceInterceptor、@AfterReturning→AfterReturningAdviceInterceptor、@AfterThrowing→ThrowsAdviceInterceptor、@Around→AspectJAroundAdvice。

## 8. 为什么 AOP 只能拦截 public 方法

| 代理方式 | 不能拦截非 public 的原因 |
|---|---|
| JDK 动态代理 | 生成的 $ProxyN 实现接口，**接口方法天然 public**；反射调私有方法需 setAccessible，代理框架不做 |
| CGLIB | 子类只能 override 父类**可见**方法；private 对子类不可见，无法生成覆写；Spring 统一限定 public 保证一致性 |

**前提**：AOP 拦截的前提是**方法调用必须经过代理对象**。即使 public，`this.` 自调用同样不拦截。准确说法：**"AOP 只能拦截通过代理对象调用的 public 方法"**。

## 9. @Transactional 失效场景（5+1）

1. **自调用/private/final**：`this.method()` 走原始对象；private 不可见无法重写；final 不可 override。解决：注入自身或拆分 Service。
2. **异常被 try-catch 吞掉**：事务管理器通过捕获代理抛出的异常决定回滚；catch 吞掉后代理层看到"正常返回"→提交。解决：catch 后重新 `throw new RuntimeException(e)`；或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。
3. **传播机制误用**：REQUIRED/REQUIRES_NEW/NESTED 等 7 种行为差异；REQUIRES_NEW 异常被外层 catch 外层仍可能回滚。解决：明确每种传播边界、画时序图。
4. **@Async + @Transactional 顺序**：两注解都生成代理；若事务代理在外层、异步在内层 → 事务主线程开启、异步方法新线程没有事务上下文 → 失效。解决：@Order 控制代理优先级，或将异步/事务方法拆到不同类。
5. **数据库引擎不支持**：MyISAM 不支持事务，commit/rollback 静默忽略。解决：用 InnoDB。
6. **（常考第 6 条）rollbackFor 未指定**：默认只回滚 RuntimeException 和 Error，checked exception（IOException）不回滚。务必写 `@Transactional(rollbackFor = Exception.class)`。

## 10. 反射 vs 动态代理（面试 4 问）

**1. 什么关系？**
> "反射是 Java 运行时获取类信息、调用方法的能力，是动态代理的基石。JDK 动态代理正是通过 `Proxy.newProxyInstance()` 和 `Method.invoke()` 实现方法转发和调用。"

**2. JDK vs CGLIB 区别 + Spring 怎么选？**
> "JDK 基于接口 + InvocationHandler + 反射；CGLIB 基于继承 + ASM 字节码生成无反射。Spring Boot 3.x/Spring6 默认统一 CGLIB，因 JDK 代理在自调用、非接口方法有局限。"

**3. 反射慢，JDK 代理性能差？**
> "JDK8+ 反射膨胀优化：同一 Method 反射调用超阈值（15 次）JVM 生成专门访问器，性能提升几十倍近直接调用。实际瓶颈常在 Handler 拦截器链过长，不在反射本身。极致性能用 CGLIB。"

**4. 除了 Spring AOP，还用在哪？**
> "MyBatis（Mapper 接口无实现类，JDK 代理生成实现）；Dubbo/RPC（消费端为远程接口生成代理转网络请求）；Mockito（mock 对象）；数据库连接池（Connection.close() 被代理拦截，归还连接而非真关闭）。"

## 14. 复习记录

### 8/17 下午（AOP 完整学习）

本次覆盖：AOP 概念 → 介绍话术 → 术语 → 使用配置 → JDK/CGLIB 原理 → 自调用失效 → 拦截器链 → public 限制 → @Transactional 失效 → 反射面试 4 问。

**关键收获/校准：**
- 「匿名类里补增强逻辑」表述修正 → `$Proxy0` 只是转发器，增强在 Handler 里（这更接近 CGLIB 的行为，两者容易混）
- JDK 代理生成的是有名字的顶层类 $ProxyN，不是匿名类；Method static 缓存避免反射查找
- CGLIB 读音 CG-Lib（Code Generation Library）；ASM 生成**新字节码**非改旧文件；增强直接写入子类方法体无反射
- Spring Framework 6.0/Boot 3.0 起统一默认 CGLIB
- 自调用失效是 `this` 词法作用域绑定原始对象所致，Java 语言设计，非 CGLIB bug
- @Transactional 传播机制 7 种行为曾模糊 → 本笔记 §9 已列出
