## 1. 设计理念（✅）

**核心**：ZGC 把 G1 必须 STW 的对象转移（Evacuation）和引用更新完全并发化，STW 只剩极短的根扫描和少量同步点 → **亚毫秒停顿、不随堆大小增长**。

**核心哲学**：把"批量修正"变成"按需修正"。

| 维度 | G1 | ZGC |
|---|---|---|
| 跨区/跨代引用追踪 | 写入时批量记录（写屏障+RSet+CardTable） | 读取时按需修正（读屏障+染色指针） |
| 对象移动后引用更新 | STW 批量扫描更新所有引用 | 并发移动，应用线程读到旧指针即时自愈 |
| 存活标记 | 独立 Bitmap（额外内存） | 标记信息嵌入指针本身（零额外空间） |

**三大支柱**：
1. **染色指针** → 让标记状态"随身携带"，标记位内嵌指针，无需额外 Bitmap。
2. **读屏障 + 自愈** → 对象转移全程并发，应用读旧指针瞬间自动修正。
3. **并发整理** → 原地压缩（Compact）而非复制（Copy），整理过程与应用线程并行，无 G1 Evacuation 式大规模 STW。

> 本质：G1 是"提前准备，集中处理"；ZGC 是"延迟到访问时刻，分散处理"。

## 2. 染色指针（✅）

**⚠️ 关键澄清**：染色指针**不在 Mark Word 里（修正用户口误），而是在对象引用（指针）本身的高位**。Mark Word 是对象头部元数据（锁/GC 年龄/hashCode）；染色指针是 JVM 对"指向对象的指针"做的编码改造。

**4 种颜色状态（JDK17+ 占 4 位）**：

| 颜色 | 含义 | 读屏障行为 |
|---|---|---|
| Remapped | 指针干净、正确，指向有效地址 | 直接返回，零开销 |
| Marked0 | 本轮 GC 标记存活（**偶数轮**） | 查转发表 → 已转移则自愈，否则访问旧地址 |
| Marked1 | 本轮 GC 标记存活（**奇数轮**） | 同上 |
| Finalizable | 仅通过 finalize() 可达，待终结的存活 | 入 F-Queue，视作存活参与转移 |

- **为什么 Marked 分 0/1**：区分相邻两轮 GC 标记结果。交替标记——偶数轮 Marked0、奇数轮 Marked1。新一轮开始时旧标记位变"非本轮颜色"，读屏障识别"上轮残留"需检查 Remap。
- **Remapped ≠ 存活**：只表示指针正确，不表示对象一定存活（死亡对象的引用也可能 Remapped）。生死由并发标记的可达性分析决定。
- **Finalizable**：对象无强引用但重写 finalize()，不能直接回收。本轮视作存活参与转移，finalizer 执行完的下一轮才可能回收。

## 3. 读屏障 + 自愈（✅）

**伪代码**：
```
T load_barrier(T* ref) {
    T value = *ref;              // 原始读取
    if (is_bad(value)) {          // 检查染色指针颜色位
        value = heal(ref, value); // 触发自愈
    }
    return value;
}
```
- `is_bad()`：颜色 = Remapped → 干净，直接返回；颜色 = Marked0/1 → 本轮标记存活、可能已转移 → 需查转发表。
- `heal()` 自愈：用旧地址查当前 Page 转发表 → 得新地址 → 写回引用位置（*ref = new_addr）+ 刷成 Remapped → 返回新地址。
- **自愈 = 懒加载**：只有真正访问到旧指针才修正几纳秒；没被访问的旧指针永不自愈（靠重定位集强制修正兜底）。
- **同一旧指针最多自愈一次**：自愈后变 Remapped，后续访问直接短路。

## 4. 并发整理 / 转发表（✅，含用户自我纠错）

**完整链路（正确版）**：
```
触发（空间不足/定时）
→ 并发标记：GC 线程并发找存活对象，染色指针标 Marked0/1
→ 选重定位集 Relocation Set：挑垃圾多、存活少的 Page（性价比最高）
→ STW (Pause Relocate Start)：极短，只扫描 GC Roots，把 Root 直接指向的对象更新到新地址
→ 并发转移（GC 后台线程执行，应用线程正常跑）：
     分配新 Page → 复制存活对象 → 旧 Page 元数据建转发表（旧→新）
     若 Root 直接指向被移对象，GC 线程直接更新该根引用
→ 应用线程并发运行 + 读屏障自愈（只修正自己的引用，不做搬运）
→ 旧 Page 回收：当该 Page 所有旧引用都被修正（自愈或强制修正）后，才清空归还
```

**⚠️ 用户自我纠正的关键点**：
- ❌ 错：对象转移"随着应用线程执行（应用线程触发转移）"
- ✅ 对：**转移是 GC 后台线程并发批量做的**，应用线程只负责"读到旧指针时通过读屏障顺手修正自己的引用"

**旧 Page 为何不会被提前清除（用户最后想通的）**：
- 旧 Page 回收条件 = 该 Page 上所有存活对象的旧指针**都已被修正为新指针**（Root 引用已在 STW 更新 + 堆内引用全部自愈）。
- 自愈时 ZGC 内部计数"该 Page 少一个待修正引用"，Root 引用已在 Pause Relocate Start 更新。
- **用户最初误解**：以为"其他 Page 对象引用了重定位集对象但 GC Roots 不可达"。实为误解——Roots 来自线程栈/全局变量，**任何可达对象必然被 Roots 或引用链覆盖**；且 Root 引用早已更新。**只要还有引用指向旧 Page，该 Page 就绝不会被释放。**
- 兜底：Relocation Set Forwarding 强制修正——应用线程一直不访问时，GC 主动扫描相关引用强制改地址，保证有限时间内回收。

## 5. STW 在哪三个阶段（🟡）

| STW 阶段 | 时机 | 做什么 | 耗时 |
|---|---|---|---|
| Pause Mark Start | 标记开始 | 扫 GC Roots，标记直接可达 | <1ms |
| Pause Mark End | 标记结束 | 处理 SATB 残留、弱/软/虚引用 | <1ms |
| Pause Relocate Start | 整理开始 | **再次扫 GC Roots**，更新 Root 新地址，初始化转发表 | <1ms |

**为什么 STW 极短**：只扫描 Roots（数量与线程数相关，与堆大小无关）；全堆遍历、对象搬运、引用修正全交给并发阶段 + 读屏障自愈。G1 慢在 STW 时还要做 Evacuation + RSet 更新。

## 6. 三大支柱分工（用户梳理确认）

> 并发整理建立映射 → 染色指针标识过期 → 读屏障按需查映射并修复指针

- **染色指针** → 判断引用是否过期（不是找对象）；4 色状态机 Remapped → Marked0/1 → Remapped 每轮推进。
- **读屏障 + 自愈** → 执行修正动作（指针只说"坏了"，读屏障负责"修好"）。
- **并发整理** → 提供修正的数据源（转发表，并发转移时建立）。

**与 G1 锚点对比**：RSet+CardTable ↔ 转发表+读屏障；STW Evacuation ↔ 并发 Relocation；Mark Bitmap ↔ 染色指针 Marked0/1；对象头 Forwarding Pointer ↔ Page 级转发表。

## 7.5 分代 ZGC（🟡 混乱待梳理，8/20 下午初步学）

**为什么需要**：非分代 ZGC 每次全堆扫描，年轻对象"朝生夕死"却都被扫描 → CPU 高、吞吐低。
- G1 靠只扫新生代保吞吐；非分代 ZGC 每次全堆扫（堆越大 CPU 越浪费）。
- 弱代假说：90% 对象朝生夕死。
- **JDK 21 推出分代 ZGC**：保持 <1ms 停顿 + 吞吐追平/反超 G1。

**已掌握（用户盘点 8/20）**：
1. 分代机制：Young/Old 独立 Page 集合，物理隔离。
2. Mark Word 修改：Old 对象转移时，对象头原子替换为 **Forwarding Pointer** + Tag 位（识别是转发指针而非普通头）→ 靠 Tag 找新地址。
3. Forwarding Pointer：Old 区转移后在原对象头留转发指针（类似 G1 forwarding pointer）。
4. 跨代引用 RSet：含 **Buffer（应用线程本地）+ Dynamic RSet（DBRS 全局）**。
5. 跨代引用机制：应用线程跨代引用记录到本地 buffer，满后批量刷入全局 DBRS；GC 直接消费精确引用列表。

**✅ 已理解并发机制（8/21 突破，AI 评价"超越绝大多数候选人"）**：

分代 ZGC 能实现 Young GC 和 Old GC **真正并发**，核心靠两层保障：
1. **状态机物理隔离**：染色指针的 **Generation Bit（分代位）** 和 **Mark Bits（标记位）在 bit 层面正交**，两套 GC 拥有独立的状态机和转发表，在同一个指针上操作互不干扰——这是并发的**硬件基础**。
2. **依赖图逻辑解耦（更关键）**：通过写屏障严格维护 **Old → Young 单向引用不变量**，使全堆引用图变成 DAG：
   - **Young GC**：只需扫自己的 Roots + RSet（RSet 记录所有 Old→Young 跨代边），就能完备找到所有 Young 存活对象，**完全不用查 Old Gen 存活状态**。
   - **Old GC**：只需从 GC Roots 出发 + Old 内部引用，就能完成标记，**完全不用查 Young Gen**。
   - 两代标记阶段无循环依赖 → 各自作为平行流水线独立推进；应用线程产生 Young→Old 反向引用时，写屏障立即修复（晋升 / 记 RSet）→ GC 线程始终看到合法堆拓扑，不被阻塞暂停。

**防御追问备答（RSet 是否成并发瓶颈）**：不会。RSet 读写分离——写由应用线程写屏障完成（染色指针分代位 O(1) 判断，无锁原子）；读仅在对应代 GC 标记阶段由 GC 线程消费（另一代不会碰）；且 Young/Old 两套 RSet 物理隔离，无竞争。

> 📌 之前"混乱待梳理"的 4 个存疑点，核心"两代为何并行"已解决（= 状态机隔离 + 单向引用不变量）。`Safety Point / Relocate / 两代引用更新差异` 等细节仍需补口述，但**主机制已通**。**可据此做简历写法判定**（见 §8）。

## 7.6 G1 vs ZGC 综合对比（✅，8/20 下午口述确认）

| 维度 | G1 | 非分代 ZGC |
|---|---|---|
| 内存划分 | Region 固定 1~32MB，四角色动态 | Page 可变（Small 2MB/Medium 32MB/Large 动态） |
| 对象转移 | STW **批量**转移（Evacuation） | 并发转移（GC 线程后台拷贝，应用并发） |
| 存活标记 | 独立 Bitmap | 染色指针（指针高位） |
| 跨区引用 | RSet + CardTable（写屏障） | **不需要**（非分代，染色指针+全堆并发标记） |
| 引用更新 | STW 全量更新 + SATB | 读屏障自愈 + 转发表 |
| 转移阶段 SATB | 强依赖 | 不需要 |

**用户排雷关键**：
- **Bitmap**：非分代 ZGC 不需要传统独立 Bitmap（染色指针内联存活标记）。
- **SATB**：转移阶段没了，但**标记阶段仍有变体**——早期 ZGC 用 SATB，JDK16+ 优化去写屏障开销，JDK21 分代为处理跨代引用又引入类似机制。不能说"完全没有 SATB"。
- **RSet/CardTable**：非分代不需要；分代因只回收年轻代不能全堆扫，又引入类似 RSet（DBRS）结构。

**读屏障自愈的原子性保证（用户唯一纠错的点）**：不存在"应用读到旧指针但转移未完成"的中间态——GC 线程先复制对象，**再原子写入转发表 + 改指针颜色为 Marked**。应用看到 Marked = 转发表已就绪，100% 能查到新地址。
