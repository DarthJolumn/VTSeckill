## 1. 底层架构：堆表 vs 聚簇索引（✅）

**一句话**：InnoDB 是"表即索引"，PG 是"表是表、索引是索引，通过 TID 关联"。

| 维度 | MySQL InnoDB | PostgreSQL |
|---|---|---|
| 存储 | 聚簇索引：数据按主键物理有序，叶子节点就是行数据 | 堆表：数据按插入顺序无序追加 |
| 表与索引 | 表 = 主键索引 | 完全独立的两个物理文件 |
| 行地址 | 主键值 | **TID = (BlockNumber, ItemOffset)**，物理指针 |
| 索引叶子 | 二级索引存 (k, 主键值) | 所有索引（含主键）只存 (k, TID) |
| MVCC | 数据文件只有最新版，旧版在 Undo Log | 新旧版本共存于堆表，靠指针串联 |

**PG 页结构（8KB Page）**：ItemId Array（行偏移，4B/条，从页头生长）+ Tuple Data（从页尾生长）相向而行；行物理地址 = TID；删除行只标记 ItemId 无效，不移动数据。

**B-Tree 命名澄清**：PG 默认索引叫 B-Tree，但**非叶子节点只存键值+指针（不存 TID）**，叶子节点存 (key, TID)，行为上就是 B+ Tree，只是沿用了 B-Tree 术语。标准 B-Tree 才是非叶子也存数据。

**N 个索引 = N 棵独立 B-Tree**：每创建一个索引就是一个独立文件；复合索引是一棵键值为 (a,b) 的树，跳第一列则无法利用有序性（最左前缀）。

## 2. 查询路径（✅）

| 查询 | PG | MySQL InnoDB |
|---|---|---|
| 主键等值 | 索引找 TID → **回表**（2 次 IO） | 聚簇叶子即数据（1 次 IO）✅ |
| 二级索引等值 | 索引找 TID → 回表（约 4 次 IO）✅ | 二级树找主键 → 再走聚簇树（约 6 次 IO） |
| 主键范围/排序 | TID 离散 → 随机 IO ❌ | 聚簇叶子双向链表顺序扫 ✅ 碾压 |

- **PG 没有"主键查数据更快"这回事**：主键只是一个带唯一约束的普通 B-Tree 索引，查询路径与其他索引完全相同（唯一性保证最多回表一次）。
- **快慢的真正原因**：查询模式（等值 vs 范围）、唯一性（找到即停）、是否 Index-Only Scan（覆盖索引跳过回表，需 VACUUM 维护 VM）。
- **选型**：主键点查/自增追加/时序范围 → MySQL；二级索引筛选多/复杂查询 → PG（TID 直达恒定开销）。

## 3. 写入与更新性能（✅）

| 场景 | MySQL | PG |
|---|---|---|
| INSERT | 自增主键尾部顺序写 ✅；**非自增（UUID）页分裂灾难** ❌ | 堆表尾部追加 + N 棵索引各自插入 |
| UPDATE 非索引列 | 原地修改 + 写 Undo | **HOT 更新**：同页有空间则新行写同页，`t_ctid` 指向新行，**索引不用动** ✅ |
| 主键更新 | 灾难：行移动 + 所有二级索引重写 | 代价低（堆表 + 独立索引） |
| 空间 | 页分裂碎片，OPTIMIZE TABLE | **表膨胀**（死元组），VACUUM 回收 |

> 口诀：MySQL 成也自增败也自增；PG 成也解耦败也解耦。

## 4. MVCC 实现（✅）

### 4.1 载体

- **MySQL**：单物理版本（聚簇索引只存最新）+ Undo Log 逻辑多版本；版本链靠 `DB_ROLL_PTR` 指向 Undo，新→旧方向。
- **PG**：物理多版本共存于堆表；靠行头字段串联，**所有版本同文件** → 读最新数据也可能加载大量死元组页 → **有效密度降低，膨胀直接拖慢查询**。

### 4.2 Tuple 行头（23 字节）

| 字段 | 含义 | 对应 MySQL |
|---|---|---|
| `t_xmin` | 创建此版本的事务 ID | DB_TRX_ID（插入时） |
| `t_xmax` | 删除/修改此版本的事务 ID | DB_TRX_ID（删除时） |
| `t_ctid` | 指向最新版本 TID（或自身） | DB_ROLL_PTR（但指向物理地址） |
| `t_cid` | 事务内命令序列号 | 无直接对应 |
| `t_infomask` | 状态标志（是否提交/删除） | 无直接对应 |

> 术语确认：Tuple = 数据行 = MySQL 的 Row（PG 关系代数出身）；tid/tuple id；ctid = current tuple id（版本链）；cid = command id。

### 4.3 可见性：ReadView vs Snapshot + CLOG

**算法抽象层一样**：拿一个快照比对事务 ID。但 PG 多一步查 CLOG：

- MySQL ReadView：64 位单调递增 trx_id，数值大小 = 时间先后，`m_ids` 自包含判断，"不在活跃列表且 < low_limit → 已提交"，无需外部结构。
- PG Snapshot：32 位环形 XID **无法仅凭数值判断先后/状态** → 必须查 **CLOG（pg_xact）** 确认最终状态。Snapshot + CLOG 是不可分割的整体。
- 性能代价≈0：CLOG 用 **SLRU 缓存**，42 亿事务 × 2bit ≈ 1GB，活跃部分常驻内存。

### 4.4 为什么 PG 坚持 32 位环形（vs MySQL 64 位）

| | MySQL 64 位 | PG 32 位环形 |
|---|---|---|
| 语义 | 数值 = 时间戳，判断极简 | 环形比较 (A-B) mod 2^32，像钟表 |
| 优点 | ReadView 自包含 | 每行省 4 字节（xmin/xmax 各省）；天然支持**冻结语义**；分配轻量 |
| 代价 | 全局互斥锁分配 trx_id，高并发瓶颈 | 必须引入 CLOG；需要 VACUUM 冻结防回卷 |

> 关键因果链（用户自己推出来的）：32 位环形 → 无法单靠数值判断 → 引入 CLOG → 换每行省 4 字节 + 支持冻结。**冻结标记不在 CLOG 里**，在行头（FrozenTransactionId=2，永远在过去）。

## 5. 事务隔离级别（✅）

| 级别 | MySQL | PG |
|---|---|---|
| RU | 支持（脏读） | **不支持**，最低 RC（MVCC 天然隔离未提交） |
| RC | 每次 SELECT 重新生成 ReadView | 每次 SELECT 重新获取 Snapshot，行为一致 |
| RR | 快照 + **Gap Lock / Next-Key Lock** 防幻读（悲观） | 快照天然防读幻读（新行 xmin > 快照 xmax 不可见），**无 Gap Lock**；但**不防写偏斜** |
| Serializable | 2PL 两阶段锁 + 铺天盖地 Gap Lock（悲观，并发差） | **SSI** 乐观：MVCC 快照读 + 后台追踪读写依赖图，成环 → 直接 Abort 报 `serialization failure`，应用层重试 |

**核心理解（用户口述推导）：**
- **幻读根因**：MySQL 的 UPDATE/INSERT 前要执行**当前读**（写操作触发当前读），当前读要加锁 → 才有幻读风险 → 才需要 Next-Key Lock。
- **PG RR**：整个事务用同一个 Snapshot，别人新插入的行天然不可见，**读层面没有幻读**；但两个事务各读快照后修改不同行（写偏斜）允许发生。
- **First-committer-wins**：PG RR 下 UPDATE 冲突时后提交者直接报错回滚。
- **RR 解决不了写偏斜，要升级 Serializable 或应用层加锁**。从 MySQL 迁 PG 若依赖 RR 防写偏斜，必须改。

## 6. VACUUM 与空间管理（✅）

**解决痛点**：死元组堆积 → 表膨胀（堆表+索引表）→ 查询性能退化（有效密度降低）。

**VACUUM 多阶段流水线**：
1. 扫描堆表识别死元组（xmax 已提交且无快照需要）
2. 标记死元组空间可重用（通常不缩小文件）
3. 更新 **VM（Visibility Map）**：标记哪些页"全部可见"→ 支撑 **Index-Only Scan**（跳过回表）
4. **冻结事务 ID**（防回卷）

**事务 ID 回卷（灾难事故）**：32 位用完回 0 → "未来事务变过去事务" → 可见性混乱；距回卷 1000 万 XID 时 PG 强制停机保护，必须 VACUUM 冻结。环形比较例：当前 41 亿，出现 19 亿 → 差值约 22 亿 < 2^31 → 19 亿是"较旧"的（用户自己算通的）。

**HOT 更新联动**：UPDATE 非索引列 → 同页新行，索引仍指向旧行，旧行 `t_ctid` 指向新行 → 索引不用改。**索引可能指向已删除未 VACUUM 的旧版本**（此时 t_ctid 链回溯找可见版本）；若 UPDATE 涉及索引列 → 索引需顺序写入新条目，查索引→回表→可见性判断。

## 7. GIN 倒排索引 / JSONB（✅）

- **倒排结构**：传统 B-Tree 是"值 → 行号"一对一；**GIN 是"词项 → 行号列表"一对多**（倒过来），索引表倒转。
- **适用**：JSONB、全文检索、数组等"一个值对应多行"场景。
- **JSONB 查询**：`@>` 包含操作符（短链场景：JSON 倒排索引）。
- ⚠️ 纠正：倒排索引**不是只能用于 JSONB**（数组/全文都可以）；GIN 大表到千万级也会慢 → 分区表是解药（见 §8 待补）。
