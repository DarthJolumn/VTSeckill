## 1. B+ 树 vs B 树（✅）

**一句话**：B 树为内存等值查找设计；B+ 树为磁盘范围扫描+高扇出+顺序 IO 定制。**B 树能做范围扫描，但代价是全树中序遍历的海量随机 IO，磁盘场景不可接受。**

| 维度 | B 树 | B+ 树 | 本质 |
|---|---|---|---|
| 非叶子节点 | 存索引+数据 | **只存索引+指针** | 扇出大（16KB 页 ≈1170 项）→ 树矮（3 层 ≈2200 万行）→ IO 少 |
| 范围查询 | 中序遍历全树（随机 IO） | 叶子双向链表**顺序扫描** | 随机 IO → 顺序 IO + OS 预读 |
| 全表扫描 | 遍历所有节点 | 只遍历叶子层 | 扫描量锐减 |
| 排序 | 需额外排序 | 叶子物理有序 = 逻辑有序 | 消除 filesort；LIMIT 可提前终止 |
| 内存缓存 | 导航/数据混杂，LRU 难分冷热 | 导航页热、数据页按需加载 | BP 缓存效率最大化 + 预读命中 |

**四维是同一个物理设计决策的四个投影**：非叶子只存索引（IO 少）→ 叶子连续+链表（范围/缓存/排序）。

## 2. 索引体系（✅，含 3 处 AI 修正）

- 聚簇索引 = 数据本身（.ibd）；二级索引 = 索引键 + 主键，需回表；覆盖索引 = 查询列全在二级索引中，零回表。
- **最左前缀：不是"失效"，是"部分使用"**（修正①）：
  - 等值查询可**穿透**中间缺失列（A=1 AND C=2 AND D=3 → A 走索引定位，C/D 子树内逐行检查，无需回表也能过滤）。
  - **范围匹配（> < BETWEEN LIKE 'abc%'）才真正截断**该列之后的有序性传递。
  - 排序要求更严格：WHERE A=1 ORDER BY C,D ✅ 可利用；WHERE B=1 ORDER BY C,D ❌ filesort。
- **ICP 在存储引擎层，不在 Server 层**（修正②）：InnoDB 遍历二级索引页时直接读索引中已有列（如 C）提前过滤，只对符合条件的行回表。Server 层看不到二级索引内部结构。
- **覆盖索引 vs ICP 的边界**（修正③）：`SELECT A,C WHERE A=1 AND C=3` + 索引(A,B,C) = **纯覆盖索引**（Using index，B 列"安静躺着不读取"），ICP 不参与（没回表可减）。ICP 只在"必须回表"时减少回表次数。

**EXPLAIN 三标志速查**：
| Extra | 含义 | 回表 |
|---|---|---|
| `Using index` | 覆盖索引 | ❌ |
| `Using index condition` | ICP（存储引擎层预过滤） | ✅ 部分 |
| `Using where` | Server 层过滤 | ✅ 全量 |

**决策链**：聚簇定义物理顺序 → 二级提供定位 → 覆盖消除回表 → ICP 抢救剩余索引列 → Server 层兜底。优先级：**覆盖 > ICP > Server 过滤**。

## 3. Buffer Pool（✅）

- **架构**：多个 Chunk → 控制块数组（buf_block_t）+ frames[]；控制块与 frame 终身绑定；控制块含 buf_page_t（space_id/page_no/access_time/oldest_modification_time/state）。
- **三链表**：
  - Free List：空闲帧池；取帧加载数据 → 控制块入 LRU。
  - LRU List：分代 Young(5/8) + Old(3/8)；新页入 **Old 头部**，超 **1000ms（innodb_old_blocks_time）** 再访问才晋升 Young → 防全表扫描污染/预读失效。
  - Flush List：按 **oldest_modification_time**（首次修改 LSN）升序；脏页修改时就已在其中（不是淘汰才加入）。
- **淘汰**：Free 耗尽 → 从 LRU 尾部（Old 尾部最冷）淘汰；脏页先刷盘（已在 Flush List），干净页直接归还 Free。
- **page_hash**：(space_id, page_no) → 控制块，O(1) 定位。
- **锁粒度**：Chunk 级 mutex（控制块状态）+ 全局 mutex（链表头尾）+ 页级锁（block->lock）。
- **与行锁衔接**：行锁挂在页控制块的 lock 结构中；持锁页 access_time 持续更新 → 不被 LRU 淘汰 → **长事务导致 BP 污染**的物理根源。

## 4. Redo Log（✅，含 AI 微调）

- **MTR 流程（修正）**：不是"先写日志再改数据"——MTR 内**改内存数据 + 生成 Redo Record 同步进行**（都在内存）；mtr_commit 时一次性批量拷入全局 Log Buffer。WAL 真正含义：**日志落盘先于脏页落盘**（刷盘阶段，非内存阶段）。
- **物理结构**：Log Buffer = 连续字节数组（innodb_log_buffer_size 默认 16MB）→ 磁盘 Log Block（512B，循环文件）。
- **LSN**：启动以来累计写入 Redo 字节数（含 Block Header）。
- **两个 LSN 必须区分**：
  - `oldest_modification_time`（首次修改）→ Flush List 排序依据 / **Checkpoint 推进依据**。
  - `newest_modification_time`（最近修改，写页头）→ **崩溃恢复**判断该页是否需要重放。
- **Checkpoint 两种**：
  - Sharp：关闭时同步刷所有脏页，Checkpoint LSN 直接推进到当前最大，阻塞。
  - Fuzzy：page_cleaner 定期刷最老一批，Checkpoint LSN = 已刷脏页最小 oldest_modification_time，渐进不阻塞。
- **循环写**：日志文件写满且 Checkpoint 未推进 → 阻塞用户线程强制刷脏（innodb_log_file_size 太小会频繁阻塞）。

## 5. Redo vs Undo 协作（✅，用户提问打通）

- **已写全局 Log Buffer 甚至已刷盘的 Redo Record 永不删除**：Redo 是顺序追加物理历史，删除会破坏顺序写 + 崩溃恢复完整性。未提交事务的 Redo 同样受 WAL 保护。
- **失败事务回滚**：不删旧 Redo → 读 Undo Log 执行反向修改 → **生成新的 Redo Record 抵消**（A + B = 无修改）。崩溃恢复先重放 A 再重放 B，数据依然正确。
- **Redo 何时"清理"**：不是按事务清理，而是 Checkpoint 推进后**循环覆盖**（前提是脏页已刷盘，与事务是否提交无关）。

> 锚点：Redo 记录"物理发生了什么"（不管成败）；Undo 记录"逻辑上怎么撤销"。回滚不是抹除历史，是用新历史抵消旧历史。

## 6. Undo + MVCC 三基石（✅）

**三基石：行记录隐藏字段 + Undo Log 版本链 + ReadView。**

- **隐藏字段**（在**行记录**头部，不是页头）：DB_TRX_ID（6B，最后修改事务 ID）/ DB_ROLL_PTR（7B，指向上个版本在 Undo 的位置）/ DB_ROW_ID（6B，仅无主键时才有）。
- **版本链**：roll_ptr 把同一主键的多个历史版本串成链表（最新在聚簇行，旧版本在 Undo Log）。
- **ReadView**：可见性过滤器——事务读时沿版本链遍历，用规则判断每个版本的 trx_id 是否可见，返回第一个可见版本。
- 链路：Undo 存历史 → 隐藏字段标记版本 → roll_ptr 串链 → ReadView 挑可见版本。

## 7. RR vs RC + Binlog 主从一致（👀 AI 讲未口述）

- **场景**：T1 DELETE（先无数据可删）、T2 INSERT 先提交 → 主库有数据，从库按 Binlog 顺序（先 T2 INSERT 再 T1 DELETE）重放把数据删了 → **主从不一致**。
- **RC + Statement 的问题**：RC 无 Next-Key Lock（不锁间隙），T2 能插入；Statement 只记 SQL 原文，从库按提交顺序重放，物理执行顺序 ≠ 提交顺序。
- **RR 解决**：Next-Key Lock 锁间隙 → T2 阻塞 → 强制串行化 → 物理顺序 = 提交顺序。
- **终极认知**：MySQL 默认 RR 的**真正原因**是早期只有 Statement 格式 Binlog，RR 靠 Next-Key Lock 堵主从复制漏洞；**ROW 格式**记录具体行变化后无此问题 → 大厂普遍 **RC + ROW**。
- 这是面试"为什么 MySQL 默认 RR 不是 RC"的标准答案，需补口述。
