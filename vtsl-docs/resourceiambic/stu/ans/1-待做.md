### 二、非对称流控：还差什么

| 缺失点 | 为什么重要 | 建议补充位置 |
| :--- | :--- | :--- |
| **窗口大小 100 的选择依据** | 为什么是 100 而不是 50 或 500？太小统计不稳，太大响应迟钝。需要一句话说明：100 ≈ 2000 QPS 下 50ms 的数据量，既保证统计显著性，又能在 1~2 秒内反映趋势变化。 | SlidingWindowStats 介绍处 |

### 三、两份文档之间的衔接缺口

这两份文档是独立的，但实际系统里它们是**联动的**。面试官很可能问：

> "你的流控降级到 ASYNC 后，消息可靠性那套 Pending + 补投机制，会不会因为流量突增而被压垮？"

建议在流控文档末尾或策略文档开头加一段**联动说明**：

-   流控切到 ASYNC 时，所有请求都走异步路径，Pending 写入量会从原来的 5%（仅探针）瞬间涨到 100%。
-   Redis Pending 的写入是 O(1) SET，2000 QPS 下对 Redis 压力可忽略。
-   但**补投定时任务的扫描范围会扩大**，需要确认扫描逻辑是增量扫描（SCAN + TTL 过滤）而非全量 KEYS，否则降级期间补投任务本身会成为瓶颈。
-   消费端的处理能力也要评估：ASYNC 模式下消息产生速率可能短暂超过消费速率，Kafka 消费 lag 会上升，需要监控告警。
