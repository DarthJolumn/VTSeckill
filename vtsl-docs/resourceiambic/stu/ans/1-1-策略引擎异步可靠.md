## 一、策略引擎整体设计（30秒）

> 扣减这块我用的是**策略模式 + 工厂模式**的组合。
>
> **策略模式**解决的问题是：三种扣减方式的执行逻辑完全不同，如果用 if-else 写在 SeckillService 里，每加一种策略就要改主流程代码，违反开闭原则。所以我抽了一个 `SeckillStrategy` 接口，定义统一的 `execute()` 方法，三种策略各自实现。
>
> **工厂模式**解决的问题是：策略的选择和实例化不应该散落在业务代码里。`SeckillStrategyFactory` 根据活动配置（或者运行时动态下发的策略标识）返回对应的策略实例。调用方只面向接口编程，**不感知具体是哪种策略在执行**。
>
> 好处是：新增策略只需要加一个实现类 + 工厂注册，主流程零改动。秒杀场景下如果要在 ASYNC 和 SYNC 之间做灰度切换，改一个配置就行，不用发版。

## 二、三种策略逐一介绍

### 策略一：ASYNC（Redis Lua + Kafka 异步）

> **适用场景**：高并发秒杀主战场，追求极致吞吐。
>
> **执行流程**：
> 1. 请求进来，先走 `ActivityCacheService` 做活动状态校验（是否开始、是否结束、是否已抢完），全部走本地缓存 + Redis，**不打数据库**。
> 2. 校验通过后，执行 **Redis Lua 脚本**做原子扣减。Lua 里同时判断：库存是否充足、用户是否已购（防重），两个条件在一个脚本里原子完成，不存在并发超卖。
> 3. 扣减成功后，**先在 Redis 里写一个 Pending 标记**（这个很关键，后面讲可靠性会说）。
> 4. 然后调 `KafkaOrderSender.sendAsyncReliable()`，用 `CompletableFuture` 异步投递消息，**当前线程立即返回**，不等 Broker ack。
> 5. 用户拿到的响应是"抢购成功，订单处理中"。
>
> **性能数据**：压测 3000 并发，稳定 2000 QPS，P99 < 112ms。

---

### 策略二：SYNC（Redis Lua + Kafka 同步）

> **适用场景**：对一致性要求更高的场景，比如限量优惠券、需要即时确认的支付前置扣减。
>
> **执行流程**：
> 1. 前面和 ASYNC 一样：活动校验 → Lua 原子扣减。
> 2. 区别在发送环节：调 `KafkaOrderSender.sendSync()`，内部是 `producer.send(record).get(timeout)`，**同步阻塞等 Broker 返回 ack**。
> 3. 拿到 ack 后才返回用户"下单成功"。
>
> **和 ASYNC 的取舍**：SYNC 保证了"用户看到成功 = 消息一定到了 Kafka"，但代价是每次请求都要等 Broker 响应，P99 在 50~90ms。配合前面讲的自适应流控，Broker 变慢时会自动降级到 ASYNC。

---

### 策略三：DB_QUEUE（乐观锁 + Kafka 顺序消费）

> **适用场景**：库存量极小（比如 10 件、50 件）但并发极高的场景，或者需要严格顺序保证的场景。
>
> **执行流程**：
> 1. 不走 Redis 扣减，直接对数据库库存做**乐观锁 CAS**：`UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0 AND version = ?`。
> 2. 扣减成功后发 Kafka 消息，但这里用的是**顺序消费**——同一个活动的消息路由到同一个 partition，消费端单线程顺序处理，保证落库顺序和扣减顺序一致。
> 3. 适合库存本身就是数据库权威数据的场景，省去了 Redis 和 DB 之间的库存同步问题。
>
> **代价**：每次扣减都是一次 DB 写，QPS 上限远低于 Redis Lua，但**数据一致性最强**，不存在 Redis 宕机丢库存的风险。

---

### 三种策略对比（面试时画表）

| 维度 | ASYNC | SYNC | DB_QUEUE |
|---|---|---|---|
| 扣减层 | Redis Lua | Redis Lua | DB 乐观锁 |
| 发送方式 | 异步 + Pending | 同步 `.get()` | 异步 + 顺序分区 |
| 用户感知 | 立即返回"处理中" | 等 ack 后返回"成功" | 等 DB 扣减后返回 |
| P99 | < 112ms | 50~90ms | 取决于 DB |
| 一致性 | 最终一致 | 强一致（消息层） | 强一致（库存层） |
| 适用 | 高并发主战场 | 需即时确认 | 极小库存/强顺序 |

## 三、异步消息可靠性（重点，单独展开）

> 面试官大概率会追问："ASYNC 模式下，Kafka 发送是异步的，如果发送失败或者进程挂了，消息不就丢了吗？"

> 对，这是 ASYNC 策略最核心的问题。我用了**四层保障**：

### 第一层：发送前写 Pending 标记

> 在调 `sendAsyncReliable()` **之前**，先在 Redis 里写一条 Pending 记录：`SET pending:{orderId} {messageBody} EX 300`。
>
> 这一步的意义是：**不管后面 Kafka 发没发成功，这条消息的"凭据"已经落盘了。** 即使进程下一秒就挂，重启后也能从 Redis 里捞出来补投。

### 第二层：CompletableFuture 回调感知结果

> `sendAsyncReliable()` 内部不是 fire-and-forget，而是：
> ```java
> producer.send(record, (metadata, exception) -> {
>     if (exception == null) {
>         // 发送成功，删除 Pending 标记
>         redis.delete("pending:" + orderId);
>     } else {
>         // 发送失败，Pending 保留，等定时任务补投
>         log.error("Kafka send failed", exception);
>     }
> });
> ```
> 成功就删 Pending，失败就留着。**正常路径下，99.9% 的消息在这一步就完成了闭环。**

### 第三层：消费端手动 ACK

> 消费端不是自动提交 offset，而是：
> 1. 拉到消息 → 反序列化
> 2. 执行落库（创建订单、扣减确认）
> 3. **落库成功后才手动 `commitSync()`**
>
> 如果落库过程中消费者挂了，offset 没提交，重启后会**重新消费这条消息**。配合订单表的唯一索引（`orderId` 做幂等键），重复消费不会导致重复下单。

### 第四层：定时扫描 Pending 补投

> 一个定时任务（比如每 30 秒）扫描 Redis 里所有 `pending:*` 的 key：
> - 如果 key 还存在，说明这条消息**要么发送失败了，要么回调没执行到**（比如进程在发送和回调之间挂了）。
> - 重新调 `sendAsyncReliable()` 补投。
> - 补投成功后删除 Pending。
> - 如果超过最大重试次数（比如 5 次），转入死信表，人工介入。
>
> **这一层是兜底中的兜底，覆盖所有"中间态"故障。**

---

### 可靠性总结（一句话收）

> 所以整条链路是：**发送前写 Pending → 异步发送 → 成功删 Pending / 失败留 Pending → 消费端手动 ACK 保幂等 → 定时扫描补投兜底。** 四层叠起来，ASYNC 模式下的消息丢失率可以做到无限接近于零，同时不牺牲异步的性能优势。

## 四、可能的追问 & 速答

| 追问 | 回答要点 |
|---|---|
| "为什么不用本地消息表代替 Redis Pending？" | 本地消息表需要和业务库在同一个事务里，多一次 DB 写。Redis Pending 是 O(1) 的 SET，对主流程延迟影响更小。极端情况下 Redis 也挂了，那确实会丢，但概率远低于 DB 事务回滚。 |
| "幂等怎么做的？" | 订单表 `order_id` 唯一索引 + 消费端先 `SELECT` 再 `INSERT`，或者用 `INSERT IGNORE`。重复消息直接跳过。 |
| "顺序消费怎么保证的？" | 生产端用 `activityId` 做 partition key，同一活动的所有消息进同一个 partition。消费端该 partition 只分配给一个消费者实例，单线程顺序处理。 |
| "策略怎么切换的？" | 活动配置表里有个 `strategy_type` 字段，工厂启动时加载到内存。也支持运行时通过配置中心热更新，不用重启。 |
| "如果 Redis Lua 扣减成功但 Kafka 一直发不出去怎么办？" | Pending 补投会持续重试。如果最终进了死信表，有一个**库存回补任务**会把 Redis 里扣掉的库存加回去，保证不丢库存。 |

## 五、完整话术串联（60秒版）

> 扣减这块我用了策略模式加工厂模式。`SeckillStrategy` 是统一接口，`SeckillStrategyFactory` 根据活动配置路由到具体实现，主流程只面向接口，不感知策略细节。
>
> 三种策略：**ASYNC** 是 Redis Lua 原子扣减加 Kafka 异步投递，追求极致吞吐，P99 在 112 毫秒以内；**SYNC** 同样 Lua 扣减但用 `send().get()` 同步等 ack，保证消息层强一致；**DB_QUEUE** 是数据库乐观锁加 Kafka 顺序消费，适合极小库存、强顺序场景。
>
> ASYNC 模式的消息可靠性我做了四层：发送前写 Redis Pending 标记、CompletableFuture 回调成功删标记、消费端落库后手动 ACK 保幂等、定时任务扫描 Pending 补投兜底。四层叠起来，异步链路消息不丢，同时不牺牲性能。
