### KGS 预生成发号器

#### 🎯 核心亮点
-   **生成与发放彻底解耦**：预生成 + Redis List 缓冲，发放侧仅 RPOP O(1) 读取，创建链路零等待
-   **双保险一致性**：Redis 原子取号 + Mongo CAS 条件确认，脏 key 丢弃不回队，杜绝死循环与无效短码
-   **批量 IO 合并**：insertMany + leftPushAll 将 N 次写入压缩为 2 次，生成吞吐量提升数个量级

#### 💬 面试话术
> 短链发号器我没有用自增 ID，也没有实时生成，而是做了预生成加批量缓冲加异步发放三层设计。
>
> 首先说为什么不用自增、也不用实时生成。自增短码可枚举，别人拿到一个短码就能反推业务量，有安全风险；实时生成的话，每次创建短链都要等 Base62 编码、Mongo 写入、Redis 写入整条链路完成才能返回，高并发下延迟不可控，Mongo 写入直接成为瓶颈。所以我选择提前批量生成好一批短码存起来，发放时只做轻量读取，把生成和发放彻底解耦。
>
> 再说为什么是批量而不是单条。单条生成的话，每产出一个短码就要写一次 Mongo、写一次 Redis，IO 开销太大。批量生成 1000 条，Mongo 用 insertMany 一次落账，Redis 用 leftPushAll 一次入队，把 N 次 IO 合并成 2 次，生成效率提升几个数量级。同时批量也天然形成了缓冲池，队列里有存货，发放侧就永远不用等生成侧。
>
> 具体架构分两层。生成侧：SecureRandom 生成 Base62 6 位随机短码，容量约 568 亿，随机防枚举；先批量落 MongoDB 做持久化账本，再批量写入 Redis List 队列。必须先落 Mongo 再写 Redis，保证即使 Redis 丢了也能从 Mongo 重建，不会出现没有账本的孤儿 key。
>
> 发放侧只做一件事：RPOP 取号。Redis 单线程模型保证 RPOP 是 O(1) 原子操作，无竞争、无需加锁，取完直接返回，不阻塞创建链路。
>
> 兜底靠 Mongo CAS 条件更新：把 shortKey 状态从 available 改为 used，通过 modifiedCount 判断是否成功。万一 Redis 和 Mongo 不一致拿到了脏 key，CAS 失败就直接丢弃、继续 RPOP 取下一个。不回写队列，因为同一个脏 key 回写后可能被反复取出又失败，形成死循环。

#### ⚠️ 高频追问预备
-   **"为什么先落 Mongo 再写 Redis，顺序能反吗？"**
    不能反。先落 Mongo 保证持久化，即使 Redis 丢了也能从 Mongo 重建队列；如果先写 Redis 再落 Mongo，Mongo 写入失败就会发出没有账本的孤儿 key，无法追溯也无法回收。
-   **"批量 1000 条是怎么定的？"**
    经验值加压测。太小缓冲不够、补货频繁；太大单次生成耗时长、内存占用高。1000 条在测试环境生成耗时小于 50ms，队列阈值设为 200 触发补货，保证正常流量下几乎不会同步等待补货。生产环境可通过配置中心动态调整。
-   **"如果生成过程中服务挂了，已落 Mongo 但未入 Redis 的 key 怎么办？"**
    启动时或定时任务扫描 Mongo 中 status=available 且不在 Redis 队列中的 key，重新入队。Mongo 是权威账本，Redis 只是缓存层，可以从 Mongo 完全恢复。
-   **"Base62 随机会有碰撞吗？怎么处理？"**
    6 位 Base62 有 568 亿种组合，当前业务量级下碰撞概率极低。代码里批量插入时用了唯一索引兜底，insertMany 遇到重复会抛异常，捕获后重试生成，不会把重复 key 写入账本。
-   **"补货会不会阻塞发放请求？"**
    当前实现是 getKey 时同步检查队列长度低于 200 就触发补货 1000 条，极端情况下某次请求会承担补货耗时。生产环境优化方向是改为异步监听队列长度或定时任务触发补货，让发放请求永远只走 RPOP 路径。
