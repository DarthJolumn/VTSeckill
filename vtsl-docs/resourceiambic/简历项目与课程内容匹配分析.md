## 二、项目一：基于分代 ZGC 和虚拟线程的秒杀系统

### 1. 秒杀扣减策略引擎（策略模式，三种可动态调整的扣减策略）

**简历原文**：基于策略模式实现三种可动态调整的扣减策略——Redis+Kafka 异步、Redis+Kafka 同步、DB 乐观锁直扣。

**课程怎么讲、要考虑什么**：

- **第6章 §5 商品秒杀「秒杀执行——Filter + 策略模式 + 双模式秒杀」**：课程本身就用**策略工厂**按 `secKillMode` 动态路由到不同秒杀策略，并深入对比"实时秒杀（REAL_TIME）vs MQ 排队秒杀（MQ_QUEUE）"的适用场景——**根据商品价值在"快"与"准"之间做取舍**。你的三种策略本质上就是该思想的扩展，课程能帮你补的论证是：**每种模式的一致性级别、对用户体感的影响、以及"策略动态调整"时的切换时点**（存量流量怎么平滑过渡）。
- **第4章 §1.3 库存扣减与 TCC 幂等机制**：课程回答了你的策略引擎最核心的一个问题——**"为什么不能在 Try 阶段直接扣减"**：直接扣减违背 TCC 语义、Cancel 需反向补偿+作废流水、流水变成无效凭证；正确做法是"先冻结后确认"（Try 只转移 usableStock→lockStock，Confirm 才真正消耗）。**DB 乐观锁直扣策略一定要回答这个问题**，否则面试会追问"为什么敢直扣"。
- **第3章 §3 库存系统（双库存模型）**：课程把库存拆成"交易逻辑层（用户侧虚拟额度）+ 仓储物理层（usableStock/preStock）"，核心考虑是**上下两层异步最终一致、物理隔离防跨场景超卖**。你的三种策略如果只扣一层库存，需要考虑课程强调的"总量对等无差额"约束。
- **第6章 §5「三层库存隔离架构」（预占→扣减→消费）**：秒杀库存与真实库存物理隔离——你是否有独立的秒杀库存池？课程强调**预占与真实库存互不影响**。

### 2. Redis + Kafka 异步 / 同步落库

**简历原文**：Lua 脚本原子扣减 + Kafka 异步/同步落库，保证最终一致性 / 兼容高吞吐与强一致性。

**课程怎么讲、要考虑什么**：

- **第6章 §5 商品秒杀**：课程的核心链路就是"Redis Lua 原子扣减 + MQ 异步落库"，与你的方案同构。课程补充了三个你没有明说的点：
  1. **缓存预热**：商品上架时用 Redis 原子 Long 做库存预热，多副本分片缓存（同一数据写 8 个 Key，CRC16 均匀分布到 6 个节点）；
  2. **结果轮询**：秒杀结果状态机驱动（成功/发放中/已售空），Redis TTL 管理生命周期——**为什么选轮询而非 WebSocket**；
  3. **三级漏斗消减流量**：把瞬时高并发逐层削峰。
- **第8章 §1 MQ事务消息发送组件**：课程解决"本地业务落库与 MQ 发送的最终一致性"——**先 DB 后内存、事务提交（afterCommit）后才发送、5 分钟缓冲定时补投**。你写"Kafka 异步落库"时，面试必问：**如果 Kafka 发送失败怎么办？** 课程答案：本地消息表 + 时间轮重试 + DB 兜底补偿，而不是直接调 kafkaTemplate.send。
- **第8章 §3 MQ事务消息消费组件**：消费端要考虑**AOP 自动幂等、分布式锁防重复消费、18 级阶梯延迟重试、死信隔离、定时任务补偿**——"消息不丢不重"是课程给消费端的验收标准。
- **第6章 §6 优惠券秒杀**：课程给出"四层削峰策略"：缓存预热 → Token 准入 → MQ 异步排队 → 数据库兜底。你的同步落库模式实际是把"MQ 异步排队"改成了同步，**代价是吞吐下降**——课程提醒你量化这个 trade-off。

### 3. DB 乐观锁直扣 + MQ 顺序消费（强一致低并发场景）

**简历原文**：乐观锁直扣 + MQ 顺序消费，保障强一致低并发场景。

**课程怎么讲、要考虑什么**：

- **第6章 §11 高并发点赞设计「MQ异步落库——顺序消费 + 乐观锁更新」**：课程有一个**完全相同的组合**（点赞事件 RocketMQ 异步落库 MongoDB），并解释了**为什么必须 ORDERLY 顺序消费**：同一评论的点赞/取消必须按顺序处理，乱序会导致最终结果错误；用 version 乐观锁避免并发覆盖。你的"DB 乐观锁直扣 + MQ 顺序消费"可以完全复用这套论证。
- **第4章 §1.4 优惠券冻结与乐观锁控制**：课程演示乐观锁在业务扣减中的标准姿势：**查询 status=0 + version 乐观锁更新（version+1），affectedRows=0 则冲突重试**；外层再叠 tcc_operation 的 bizKey 幂等。你的"强一致低并发"场景课程给出的完整答案 = **乐观锁 + 唯一索引 + 幂等表三层保障**。
- **第3章 §2.1 状态机五大设计约束「乐观锁幂等更新」**：状态流转必须基于 version 字段更新，affectedRows=0 代表版本冲突需重试——这是乐观锁在订单状态侧的一致性基础。

### 4. 数据一致性与回补机制（取消订单自动回补库存）

**简历原文**：取消订单按策略自动回补库存（Redis Lua 幂等回补 / DB 原子更新）。

**课程怎么讲、要考虑什么**：

- **第4章 §4 取消订单「库存回滚与优惠券回滚：幂等保障实战」**：课程完整讲了回补的幂等方案——**flowNo 唯一索引 + DuplicateKeyException 兜底，双重保障不重复回滚**；MQ 消费失败抛 MessageRetryConsumeException 触发自动重试。你的"Lua 幂等回补"要能讲出**幂等键是什么、重复回滚怎么拦**。
- **第3章 §3.5 库存流转「订单取消与库存回滚机制」**：课程给出回滚的**标准四步**：查原始出库流水 → 幂等校验（cancelFlowNo 是否已存在）→ 回滚 usableStock → 记录回滚流水（changeQuantity 为正数，与正向扣减对称）。并强调**回滚后库存即时恢复，用户可再次购买**。
- **第5章 §2 库存对账**：课程提醒：MQ 异步同步 + TCC 最终一致性决定了**用户侧与仓储侧数据"天然存在不一致概率"**——回补之外必须有对账兜底（三流合一、四层短路检查、差异处理矩阵：哪些可自动修复、哪些必须人工）。**面试追问"回补失败了怎么办"就用对账来答**。

### 5. 唯一索引 + 手动 ACK + Semaphore 背压（对齐 HikariCP 池大小）

**简历原文**：杜绝消息丢失与连接耗尽。

**课程怎么讲、要考虑什么**：

- **第8章 §3 MQ事务消息消费组件**：课程对消费端可靠性的完整答案：
  - **幂等**：AOP 切面 + Redisson 分布式锁（Key=mq:consume:messageId:group）+ 本地状态表（status 0/1/2 三态），status=1 直接过滤重复消息；
  - **背压**：课程用"信号量/限流"控制消费速率，与你的 Semaphore 背压思路一致——**本质是"消费能力 < 生产速率时，宁可让 Broker 感知慢消费降速，也不能让本地任务无限堆积"**；
  - **重试**：18 级阶梯延迟 + HashedWheelTimer + 反射绕代理（防 AOP 递归死循环）+ 定时任务兜底；
  - **死信隔离**：status=2 天然实现死信隔离，可扩展死信队列、人工补偿、告警。
- **第8章 §1 MQ事务消息发送组件「重试机制——双重引擎与防御性编程」**：课程给出发送侧的防御三板斧：**去重（ConcurrentHashMap.newKeySet 防重复入队）、限流（AtomicInteger+10000 上限防内存溢出）、分布式锁（Redisson tryLock 多实例幂等）**。你的"连接耗尽"担忧在课程里的解法是**限流 + 分片取模（ID % instanceCount）**。
- **对比提示**：你写"对齐 HikariCP 池大小（30）"很有亮点，课程虽未提具体数值，但**"限流上限对齐下游连接池"是课程认可的背压设计原则**——可引用第6章 §9 超时（连接池耗尽量化：20 连接 vs 30 秒慢 SQL 的数学推导）作为理论支撑。

### 6. JVM 延迟治理（G1 856ms STW → 分代 ZGC 3ms）

**简历原文**：同口径压测 G1 同步 Evacuation 856ms STW；切换分代 ZGC 后 GC 耗时降至 3ms，排除 GC 抖动对 P99 的干扰。

**课程怎么讲、要考虑什么**：

- **第6章 §8 熔断「熔断阈值设定哲学——为什么不是越敏感越好」**：课程有一个**反直觉但关键的观点：阈值锚定用户体验 SLA，而非 P99**；用"延迟差"构建故障黄金检测窗口，区分"正常波动"和"真实故障"。你压测 P99 改善 856ms→3ms 是漂亮的量化结果，但要准备好回答：**P99 改善 32% 如何转译为用户体验提升？是否用 SLA/错误率定义过你的目标？** 课程会引导你把"GC 优化"绑定到"用户体验指标"而非纯技术数字。
- **第6章 §9 超时「5秒漏斗的设计哲学——体感与安全边界的解耦」**：课程强调"用户感知 3 秒卡顿"与"系统允许 5 秒执行"是两个维度——**GC 停顿是"系统安全边界"的一部分，ZGC 的意义是把系统边界内的抖动清除，让超时漏斗更可靠**。可借此把 JVM 优化与全链路超时设计串起来讲。
- **第1章 §3 课程核心价值**：课程明确"AI 只会 CRUD，不会分布式容错/故障兜底；底层架构思想十年不变"——GC 调优这类**底层原理**正是课程认为的长期护城河，面试可强调"我研究过 G1/ZGC 的 Region/TLAB/RSet/CardTable"。

### 7. 瓶颈精准定位（SkyWalking 链路追踪 + 控制变量）

**简历原文**：定位 REDIS_SYNC 模式尾部延迟根因为"Kafka 同步阻塞 + Redis 跨 VM 网络"叠加放大（P99=264ms, Max RTT=3342ms）；异步化 + 本地化 Redis 后 P99 降至 92ms（↓67%）。

**课程怎么讲、要考虑什么**：

- **第6章 §9 超时「为什么需要超时——四大致命问题」**：课程指出超时配置缺失的致命后果并给出**连接池耗尽的量化计算**（20 个连接 vs 30 秒慢 SQL）和**级联故障的雪崩链路**——你的"Kafka 同步阻塞 + Redis 跨 VM 网络"正是典型的"同步调用吃掉连接池"案例，课程提供了把它讲成系统级问题的框架（不只是"改异步"）。
- **第6章 §8 熔断**：熔断解决"给故障服务喘息时间，防止级联雪崩"——你定位出的瓶颈如果没有熔断兜底，慢调用会拖垮调用方自身。**课程建议的完整叙事**：定位（链路追踪）→ 治理（异步化/本地化）→ 防护（熔断/超时/降级兜底）。
- **第6章 §7 订单详细缓存架构「写入路径——MQ事件驱动异步刷新」**：你的"Redis 本地化"思路与课程"事件驱动异步刷新"一致——**把同步写 Redis 改为异步事件驱动**，课程会追问：异步后如何保证数据最终一致？答：MQ 顺序消费 + 幂等 + 对账兜底。

### 8. 降级预案（关闭虚拟线程、切换 G1 GC，无缝回退 JDK17/21）

**简历原文**：提供降级预案：关闭虚拟线程并切换 G1 GC 即可无缝回退 JDK17/21 环境运行。

**课程怎么讲、要考虑什么**：

- **第6章 §10 降级**：课程对降级的完整框架：
  - **核心目的**：不是放弃功能，而是"资源最优配置"；两大原则：**核心链路永远不死 + 非必要不展示**；
  - **服务/接口降级 L0~L4 五级优先级体系**：L0 永不降级 → L4 资源紧张时降级；你的"回退 JDK17/21"本质是**性能特性降级（L3/L4 级别）**，要明确它在五级体系中的位置；
  - **两阶段降级**：先用户端止损（前端降级），后资源端腾挪（关闭 VT/切 GC）——**你的预案属于"资源端腾挪"，前端配合策略是什么？**课程会追问这一环；
  - **K8s 资源调度联动**：非核心缩容 → 释放资源 → 核心扩容；垂直调度 vs 水平调度。
- **第6章 §8 熔断 / §9 超时**：降级预案要配合**熔断阈值和超时漏斗**一起讲——"切换 GC"不是瞬间完成的，期间靠什么兜底？课程答案：熔断+超时+降级三层联动。

## 三、项目二：企业级短链平台

### 9. KGS 预生成发号器（Base62 编码 6 位短码，MongoDB 自增账本分段取号 → Redis List，RPOP O(1) + 阈值异步补货）

**简历原文**：MongoDB 自增账本分段取号写入 Redis List 队列；RPOP 原子取号 O(1) + 阈值异步补货；Base62 6 位短码容量≈568 亿。

**课程怎么讲、要考虑什么**：

- **第6章 §1 分库分表概述「水平分片：四种核心策略对比与选型」**：课程在"分布式全局唯一 ID"里给出两种主流方案——**雪花算法 / 号段模式**。你的 KGS 发号器本质是**号段模式（segment）**的变体，课程能帮你补的论证：为什么选号段而非雪花（无时钟回拨问题、可批量取号、DB 压力小）。
- **第4章 §1.1 单笔下单准备阶段「订单编号生成与金额计算」**：课程给出订单号生成的幂等设计——**Redis 分布式锁快速去重 + 数据库唯一索引兜底**。发号器同样要考虑：**取号并发时怎么防重复发码？** 课程答案：唯一索引 + 分布式锁双层兜底。
- **第8章 §2 多实例定时任务动态分片方案**：你的"阈值异步补货"与课程"定时分配编号（临时大脑 + 分布式锁竞争）"是同一类问题——**多实例下补货任务如何避免重复执行**。课程方案：Nacos 实例列表排序编号 + Redis Hash 映射 + 取模路由（ID % instanceCount），可无缝移植到你的补货逻辑。
- **考虑点（课程视角）**：Mongo 账本是"发号正确性"的单一事实源，Redis List 是性能层——**两者一致性靠什么保证？** 课程模式：先 DB 后缓存（参照第8章 §1"先 DB 后内存"），以及账本号段耗尽时的并发控制。

### 10. API 业务层二级缓存（Caffeine 本地 + Redis 分布式，缓存命中零 DB 查询，跳转 P99 < 5ms）

**简历原文**：二级缓存（Caffeine 本地 + Redis 分布式），缓存命中直接返回 urlId 实现零 DB 查询，短码跳转 P99 < 5ms。

**课程怎么讲、要考虑什么**：

- **第6章 §7 订单详细缓存架构设计**：课程给出了**与你的二级缓存完全同构**的架构，并深入讲解：
  - **读路径 Cache-Aside**：缓存命中直接返回 → 未命中走 DB → 回填缓存；
  - **写路径 MQ 事件驱动异步刷新**：数据变更不阻塞主流程，**为什么选事件驱动而非 Cache-Aside 删除重建**（"缓存永远不空窗"、用户体验差异）；
  - **顺序消费细节**：为什么用 ORDERLY，并发刷新会导致什么后果；
  - **L1 Caffeine (3s TTL) + L2 Redis (24h±10%) 二级缓存**（知识库中记录的设计）：TTL 随机偏移规避雪崩。
- **第4章 §1.1 商品详情查询与缓存架构（缓存三板斧）**：课程完整覆盖**击穿 / 穿透 / 雪崩**三个面试必考点：
  - 击穿：ConcurrentHashMap + CompletableFuture + putIfAbsent，保证同一 key 只有一个线程回源 DB；
  - 穿透：缓存 NULL_VALUE + 返回兜底降级数据；
  - 雪崩：ThreadLocalRandom 随机过期偏移量（0~60 分钟）。
  - **你的短链系统同样要面对这三个问题**（短码被刷、不存在的短码、热点短码集中过期），建议按课程三板斧补齐论证。
- **第6章 §6 优惠券秒杀「缓存预热」**：短链可参考课程的**预热策略**（活动/热点短码提前预热，TTL 动态计算）。

### 11. 网关前置 Base62 格式校验（拦截无效请求）

**简历原文**：网关前置 Base62 格式校验拦截无效请求。

**课程怎么讲、要考虑什么**：

- **第7章 §3 接口签名「SignFilter 七步验签流程」**：课程把"网关层过滤"做成**Filter 拦截链 + 防重放（Timestamp + Nonce 原子双锁）**。你的 Base62 校验是**格式层拦截**（成本最低的第一道门），课程会建议你往上叠加：**签名验签（防篡改）+ 防重放（防脚本刷量）**。
- **第7章 §2 C端鉴权**：网关校验之后是**身份校验（JWT + Redis 双保险、设备 ID 绑定防重放）**——短链跳转若需统计归属，要考虑匿名 vs 登录两种来源（对照课程"双密钥来源——未登录 vs 已登录"）。
- **知识库提示**（`AGENTS.md` 秒杀审计记录）：**Ant 通配符 `*` 只匹配一级路径**，网关白名单路径需用 `**`——短链解析路径若走网关白名单，注意此坑。

### 12. 软删除 + 归属校验

**简历原文**：短链 CRUD（软删除 + 归属校验）。

**课程怎么讲、要考虑什么**：

- **第7章 §1 多租户架构设计与实现**：课程给出"数据隔离"的完整答案——**MyBatis Plus 拦截器自动拼接 tenant_id 条件，业务代码无感知**；微服务间租户透传（Feign 上下文传递）。你的"归属校验"是单用户维度的隔离，可对照课程 C 端按 user_id 隔离 vs Admin 端按 tenant_id 隔离的**差异化设计**。
- **第7章 §2 C端鉴权**：归属校验的前提是**可靠的身份来源**——课程强调 JWT 无状态 + Redis 有状态的"正交拆分"、多端互斥。短链创建/删除接口需要同样级别的鉴权链路。

### 13. 存储选型分离（Mongo 账本 + MySQL 业务映射表）

**简历原文**：Mongo 账本负责全局唯一性（自增 ID 天然适配分段发号），MySQL 承载归属/统计/过期等业务属性，短码字符串作为解耦键，两套存储独立演进。

**课程怎么讲、要考虑什么**：

- **第1章 §1 分层架构介绍「数据存储层」**：课程本身就是**混合存储**策略——MySQL 存事务性核心数据、Elasticsearch 支撑搜索、MongoDB 存海量文档型数据。你的"Mongo 管唯一性、MySQL 管业务"完全符合课程的**按数据特征选存储**哲学。
- **第6章 §3 订单库分库分表「ES冗余订单数据：异构查询架构设计」**：课程给出了与你的"双存储解耦"同构的工业级实践——**MySQL 为主存储、ES 为搜索索引，只冗余少量字段，MQ 顺序消费 + 乐观锁保证最终一致性**。你可以在"两套存储独立演进互不阻塞"的基础上，补充**两库一致性保障方案**（课程：MQ 事件 + 幂等 + 对账），这是面试加分点。
- **考虑点（课程视角）**：短码字符串作为解耦键——注意课程第6章 §3 强调"回查必须带分片键"的强制约束，短链跳转若分表，**短码必须作为路由键**（可对照知识库"商品短链算法派生、0 存储"的设计：雪花 ID 全 64 位 Base58 编码，短码↔ID 双向确定性推导）。

### 14. gRPC 契约通信（双服务架构）

**简历原文**：KGS 发号器 + API 业务层双服务架构，通过 gRPC 契约通信实现服务解耦。

**课程怎么讲、要考虑什么**：

- **第3章 §1 Hmily框架源码解析「本地调用与 Feign 跨服务调用核心差异」**：课程详细对比了跨服务调用的**上下文传递机制**（Feign 通过 Header 透传事务上下文）。你的 gRPC 方案要能回答：**跨服务时业务上下文（如请求 ID、用户信息）如何透传？** 课程模式：网关注入 Header → 下游 Filter 解析 → ScopedValue/ThreadLocal 绑定（见知识库 ScopedValue 用户上下文改造）。
- **考虑点（课程视角）**：gRPC 契约通信带来强类型与性能优势，但课程主线（Feign/Dubbo）强调**可观测性与链路追踪**——两服务间 RPC 是否纳入 SkyWalking？可把 gRPC + 链路追踪作为亮点展开。

## 五、简历尚未体现、但课程可补强的面试亮点

以下课程核心模块在简历中缺失，建议补充为项目能力的**深水区**（面试官追问时的弹药库）：

1. **TCC 分布式事务（第3章 §1 + 第4章 §1.3）**：tcc_operation 表如何解决**空回滚、悬挂、幂等**三大难题；bizKey 设计哲学；为什么不能在 Try 阶段直接扣减。秒杀 + 订单 + 库存跨服务场景必考。
2. **对账体系（第5章）**：支付对账（长款/短款/金额不一致/状态不一致）、库存对账（三流合一、四层短路检查）——"分布式必然不一致，靠对账兜底"是高阶叙事。
3. **分库分表（第6章 §1~§4）**：分片键选型黄金法则（90% 读写命中）、绑定表、ES 异构查询、"回查必须带分片键"。秒杀订单量大，分库分表是自然延伸。
4. **状态机/事件驱动/接口编排/聚合事务边界（第3章 §2）**：订单状态机五大约束、Outbox 发件箱模式、DDD 应用层编排——把你的策略引擎放到这些架构模式下讲，层次立刻不同。
5. **安全架构（第7章）**：多租户、双 Token、接口签名 + 防重放——短链平台天然适合补一套签名体系。
6. **MQ 可靠发送/消费组件（第8章 §1/§3）**：你的手动 ACK + 背压可以升级为课程完整的"本地消息表 + 18 级重试 + 死信隔离 + 定时兜底"框架。
7. **降级五级体系（第6章 §10）**：你的"关闭 VT / 切 G1"降级预案可纳入 L0~L4 体系，形成完整的高可用叙事。

## 六、总结

- **秒杀系统**与课程**第6章（高并发高可用）+ 第4章（下单/取消链路）+ 第8章（MQ 组件）+ 第3章（库存/TCC）** 高度同构，你的三策略引擎、Lua 扣减、手动 ACK + 背压都是课程的工业级实践，只需补齐：**TCC 幂等论证、缓存三板斧、降级五级定位、对账兜底**。
- **短链平台**与课程**第6章（缓存架构/分库分表）+ 第7章（安全）+ 第8章（动态分片）+ 第1章（混合存储）** 对应，发号器（号段模式）与二级缓存（Cache-Aside + 事件驱动）是最大亮点，建议补充：**缓存击穿/穿透/雪崩三板斧、两库一致性保障、网关签名防重放**。
- **专业技能**中 JVM、并发、MySQL、Redis 底层均可与课程的**架构决策（为什么这么设计）**绑定，形成"原理 → 设计 → 压测数据"的完整证据链。
