# 秒杀 REDIS_SYNC 同步等待降级为异步不等待 · 设计方案

> **问题**：`RedisSyncStrategy.createOrder()` 中 `kafkaTemplate.send().get(3s)` 同步等待 broker 确认。当流量打到 get 等待成为瓶颈时，如何自动降级为异步不等待？
>
> **现状代码**：
> - `RedisSyncStrategy.java:43` → `send().get(3s)`，超时/失败 → `SeckillService.placeOrder` catch → `refundStock()` 回补 + 503
> - `RedisAsyncStrategy.java:46` → `send()` fire-and-forget 不等待
> - `SeckillService.java:95` → `seckillStrategyFactory.getStrategy(activity.getMode())` 按活动模式路由
> - `SeckillMode`：`REDIS_ASYNC / REDIS_SYNC / DB_QUEUE`，活动 `seckill_mode` 列决定，切换需改 DB（无运行时切换）

---

## 一、瓶颈分析：为什么 get 等待是崩盘点

| 环节 | 耗时 | 说明 |
|---|---|---|
| `deductStock()` | ~1ms | Redis Lua 原子扣减，**快** |
| `createOrder()` 的 `send().get(3s)` | **0~3000ms** | 等 broker ack，网络/RPC 不确定性全在这里 |
| 超时兜底 | +回补+503 | `refundStock()` 回补后用户仍失败 |

**崩盘路径**：Kafka broker 慢/网络抖动 → 部分请求 get 逼近 3s → 超时率升高 → 回补风暴（refund 又打 Redis）→ producer buffer-memory(32MB) 排队 → 更多超时 → **雪崩**。

**本质**：把"落库可靠性的等待"放在**用户请求路径**上——可靠性诉求（等 ack）与吞吐诉求（不等待）在同一个动作里打架。降级的目标就是把这两个诉求**解耦**：流量正常时等 ack（强一致），流量异常时不等（保吞吐），可靠性交给异步补偿。

---

## 二、核心洞察：SYNC ↔ ASYNC 是可逆的轻量切换

```
REDIS_SYNC  = Redis Lua 扣库存 + Kafka 同步发送（等 ack）
REDIS_ASYNC = Redis Lua 扣库存 + Kafka 异步发送（不等）
             └──────── 库存模型完全相同 ────────┘
```

- **两模式共用同一套 Lua 扣减库存**（`StockService.deduct`），无"双库存"问题；
- 差异仅在 `createOrder()` 一个方法的发送语义；
- **因此降级 = 在 RedisSyncStrategy 内部把"等 ack"降为"不等"**，不需要切到另一个策略类，不需要动库存。

> ⚠️ 注意：`DB_QUEUE` 是另一套库存模型（DB 乐观锁直扣），**不能**与 SYNC/ASYNC 互切（除非单独维护库存）。本方案只讨论 SYNC→ASYNC。

---

## 三、降级方案设计（三层：策略切换 / 内部自适应 / 超时缩短）

### 方案 1：策略级切换（管理面，手动 + 运营决策）

**做法**：活动 `seckill_mode` 支持运行时覆盖——新增管理接口 `PUT /seckill/activity/{id}/mode` 或 Nacos 配置下发，把活动的 `REDIS_SYNC` 切为 `REDIS_ASYNC`。

```java
// SeckillService 增加
public void updateMode(Long activityId, SeckillMode mode) {
    SeckillActivity activity = ...;         // 校验存在
    if (mode == SeckillMode.DB_QUEUE) throw ...;  // 库存模型不同，禁止互切
    activity.setMode(mode);
    activityRepo.save(activity);            // 也可走 Caffeine refresh()
    cacheService.refresh(activityId);       // 让 placeOrder 读到新 mode
}
```

**优点**：语义清晰（整个活动切模式）、实现简单、可运营决策（大促预案里人工切换）。
**缺点**：有感知延迟（DB 读写 + 缓存刷新）、依赖人/外部系统决策，**不能应对秒级突发的自动降级**。

### 方案 2：策略内部自适应降级（运行面，自动，**推荐**）

**做法**：在 `RedisSyncStrategy` 内部加一个轻量"降级决策器"（三态状态机），滚动统计 get 耗时/超时率，超阈值自动切异步，冷却后试探恢复。

```
状态：SYNC ──超阈值──▶ ASYNC ──冷却结束──▶ PROBE ──试探成功──▶ SYNC
                        ▲                                        │
                        └─────────── 试探失败回退 ────────────────┘
```

**指标**（滚动窗口，如最近 30s / 最近 100 次）：
- get 平均耗时 > `sync-max-avg-ms`（如 500ms）→ 降级
- get 超时率 > `sync-max-timeout-rate`（如 5%）→ 降级
- 两者都不触发 → 维持 SYNC

**降级后行为**：`createOrder()` 走 `kafkaTemplate.send()` 不等待，**立即返回成功**。

**恢复**：降级进入 ASYNC 后，冷却 `degrade-cool-down-seconds`（如 60s）；冷却结束进入 PROBE，**试探发一条同步消息**（`send().get(1s)`），成功 → 恢复 SYNC，失败 → 回 ASYNC 再冷却。

**代码骨架**：

```java
@Component
public class RedisSyncStrategy implements SeckillStrategy {

    private static final int WINDOW_SIZE = 100;               // 滚动窗口样本数

    enum SendMode { SYNC, ASYNC, PROBE }

    private final AtomicReference<SendMode> mode = new AtomicReference<>(SendMode.SYNC);
    private final AtomicInteger syncCount = new AtomicInteger();   // 窗口内同步发送数
    private final AtomicInteger timeoutCount = new AtomicInteger(); // 窗口内超时数
    private volatile long degradedAt;                              // 进入 ASYNC 的时间戳
    private volatile boolean probeSuccess = true;

    // 配置注入：seckill.sync-degrade.*
    private final SyncDegradeProperties props;

    @Override
    public void createOrder(SeckillActivity activity, Long userId, String orderNo) {
        String msg = userId + ":" + activity.getId() + ":" + orderNo;
        SendMode m = mode.get();
        if (m == SendMode.SYNC) {
            if (trySendSync(msg, orderNo)) return;   // 成功
            // 超时/失败：不立即 refund，走降级异步重发（可靠性交给异步兜底）
            degradeIfNeeded();
            sendAsync(msg);                           // 异步兜底发送
            return;
        }
        // ASYNC / PROBE：异步不等待（PROBE 期间也异步，避免试探放大流量）
        sendAsync(msg);
        if (m == SendMode.PROBE) tryProbeRecover();
    }

    private boolean trySendSync(String msg, String orderNo) {
        try {
            kafkaTemplate.send("seckill-order", msg).get(3, TimeUnit.SECONDS);
            syncCount.incrementAndGet();
            return true;
        } catch (TimeoutException e) {
            timeoutCount.incrementAndGet();  // 统计窗口内超时
            return false;
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        } catch (ExecutionException e) {
            return false;
        }
    }

    private void sendAsync(String msg) {
        kafkaTemplate.send("seckill-order", msg);   // fire-and-forget
        // 可靠性兜底：见"四、降级必须配套的 3 件事"
    }

    private void degradeIfNeeded() {
        if (mode.get() != SendMode.SYNC) return;
        int total = syncCount.get() + timeoutCount.get();
        if (total < WINDOW_SIZE) return;                       // 样本不足不降级
        long avg = ...;                                        // 滚动均值
        double rate = timeoutCount.get() * 1.0 / total;
        if (avg > props.getMaxAvgMs() || rate > props.getMaxTimeoutRate()) {
            mode.set(SendMode.ASYNC);
            degradedAt = System.currentTimeMillis();
            log.warn("REDIS_SYNC 降级为 ASYNC: avg={}ms rate={}%", avg, rate * 100);
        }
    }

    private void tryProbeRecover() {
        // 冷却期：degradedAt + coolDown 内不试探
        if (System.currentTimeMillis() - degradedAt < props.getCoolDownSeconds() * 1000L) return;
        try {
            kafkaTemplate.send("seckill-order", "probe:" + System.nanoTime())
                    .get(1, TimeUnit.SECONDS);
            mode.set(SendMode.SYNC);
            syncCount.set(0); timeoutCount.set(0);
            log.info("REDIS_ASYNC 试探成功，恢复 SYNC");
        } catch (Exception e) {
            degradedAt = System.currentTimeMillis();  // 回退，重新冷却
        }
    }
}
```

**优点**：秒级自动响应、无人工依赖、无外部中间件依赖、降级/恢复闭环。
**缺点**：需要设计好阈值与防抖（见第六节问题清单）。

### 方案 3：超时缩短 + 快速降级（软降级，最小改动）

**做法**：`get(3s)` → `get(800ms)`，超时后不 refund，直接降级异步重发。

```java
try {
    kafkaTemplate.send("seckill-order", msg).get(800, TimeUnit.MILLISECONDS);
} catch (TimeoutException e) {
    kafkaTemplate.send("seckill-order", msg);   // 降级：异步重发，不等
}
```

**优点**：改动最小（几行）。**缺点**：阈值固定、无恢复机制、超时后异步重发有**重复消息风险**（broker 可能已收到，重发会双写）——需要消费端幂等兜底（项目已有 `uk_activity_user` 唯一索引 ✅）。

## 四、降级必须配套的 3 件事（缺一不可）

> 降级后"不等 ack"，意味着**消息可能丢失**（send() 异步失败无感知）或**可能重复**（超时后重发）。必须配套兜底，否则降级换来的是丢单。

### 1️⃣ 可靠性兜底：本地消息表（Q4 改造项，与降级强耦合）

降级模式下 `sendAsync()` 失败的消息要能补投：

```
扣库存成功 → 写本地消息表 t_mq_send_message(status=0)
         → @Transactional afterCommit → kafkaTemplate.send()（异步）
         → @Scheduled 每 5min 扫描 status=0 且超时 → 补投
```

> 参照课程第8章 §1「MQ 事务消息发送组件」：先 DB 后内存、事务提交后发送、5 分钟缓冲定时补投。

### 2️⃣ 幂等兜底：消费端唯一索引（已有 ✅）

超时后异步重发可能产生**重复消息**，消费端靠 `uk_activity_user` 唯一索引 + `DuplicateKeyException` 捕获幂等 ack（`SeckillOrderConsumer` 已实现）。

### 3️⃣ 对账兜底：丢单扫描（Q3 改造项）

"扣了库存但订单没落库"的最终兜底：`ReconciliationScheduler` 扩展扫描 Redis `ordered:{activityId}:{userId}` 标记存在但 DB 无订单的超时记录 → 补单或回补。

## 五、推荐落地组合

| 层 | 方案 | 作用 |
|---|---|---|
| 自动降级 | **方案 2（内部自适应）** | 秒级响应突发流量，SYNC→ASYNC 自动切换+恢复 |
| 运营决策 | **方案 1（mode 切换接口）** | 大促预案人工切换、事后复盘 |
| 可靠性 | 本地消息表 + 唯一索引 + 对账（Q4/Q9/Q3） | 降级后消息不丢不重 |
| 可观测 | Micrometer gauge 暴露当前 SendMode + 降级计数 | 告警与复盘 |

**推荐以方案 2 为主线**：它把"同步等待的降级"做成了策略类内部的自治能力，最贴合你"流量打到 get 等待成为瓶颈时如何降级"的诉求，且不引入新中间件。

## 六、需要考虑的问题清单（面试官追问 & 设计自查）

### 用户感知
- **Q：降级后用户拿到的"ok"语义变了吗？**
  - 答：变了。SYNC 的"ok"= 消息已可靠送达；ASYNC 的"ok"= 已扣减、落库异步进行。**前端需区分**：正常时提示"下单成功"，降级时可提示"已抢到，订单处理中"（复用前端 QUEUING 状态 + WS 推送兜底）。
- **Q：用户立刻查订单查不到怎么办？**
  - 答：查询接口对"Redis 已扣、DB 未落"返回"处理中"而非"无记录"（Q1 改造项）。

### 一致性
- **Q：降级后消息丢了谁负责？**
  - 答：本地消息表定时补投 + 对账扫描（第四节 1️⃣3️⃣）。
- **Q：超时后异步重发会不会重复扣库存/重复下单？**
  - 答：库存侧 Lua `ordered` 标记幂等（一人一单）；订单侧 `uk_activity_user` 唯一索引幂等。重发无害。

### 故障场景
- **Q：降级后 Kafka 彻底不可用？**
  - 答：ASYNC 的 send() 失败→本地消息表积压→超上限触发**二级降级**（直接拒绝 503 + 回补库存，Fail Fast，参照现有 REDIS_SYNC catch 路径）。
- **Q：多实例部署，降级状态是否一致？**
  - 答：每实例独立统计（都观测同一 Kafka 慢，会**同时降级**，天然一致）；无需 Redis 共享计数器（避免引入新依赖）。恢复同理。

### 幂等
- **Q：降级切换瞬间，同一请求被处理两次？**
  - 答：placeOrder 幂等由 ordered 标记（Lua 内 SETNX）+ 唯一索引双层保障，与发送模式无关。

### 性能
- **Q：降级阈值怎么定？为什么 500ms/5%？**
  - 答：锚定**用户体验 SLA**（课程第6章 §8：阈值锚定 SLA 而非 P99）——3s 超时是"安全边界"，500ms 是"体感阈值"；5% 超时率表示系统已明显劣化。参数全部 yml 化可调。
- **Q：PROBE 试探会不会放大流量？**
  - 答：试探用**独立的探针消息**（不走业务 topic 或走专用 topic），每秒 1 条，不放大业务流量；也可改为"业务消息中取 1/N 走同步"。

### 扩展性
- **Q：新增第四种发送方式（如 DB_QUEUE 的保序发送）？**
  - 答：降级决策器只关心"等不等"，发送实现仍是策略内部一个方法；新增发送方式不影响降级逻辑（开闭原则，见 `SeckillStrategyFactory` 改造 Q14）。

### 降级恢复
- **Q：恢复后立刻又降级（抖动）？**
  - 答：冷却期（60s）+ PROBE 单次试探成功才恢复；恢复后若再次超阈值，重新进入 ASYNC 且**冷却期翻倍**（指数退避，防抖）。

## 七、落地步骤建议（按序执行）

1. **配置类** `SyncDegradeProperties`：`seckill.sync-degrade.max-avg-ms=500 / max-timeout-rate=0.05 / cool-down-seconds=60 / probe-timeout-ms=1000`（yml 化）
2. **状态机**：`RedisSyncStrategy` 内实现三态（SYNC/ASYNC/PROBE）+ 滚动窗口统计 + 防抖
3. **探针**：PROBE 用独立 topic/消息，避免污染业务数据
4. **可观测**：`PrometheusMeterRegistry` gauge 暴露 `seckill_send_mode`（0/1/2）+ counter `seckill_sync_timeout_total` / `seckill_degrade_total`
5. **兜底联动**：Q4 本地消息表 + Q3 丢单对账（本方案的前提）
6. **前端**：降级期间文案区分 + 查询"处理中"兜底（Q1）
7. **压测验证**：模拟 Kafka 慢（broker 限速/网络丢包），验证降级触发 → 吞吐保持 → 恢复闭环；数据补充到 `vtsl-docs/performance/`
8. **面试话术**：在 `简历设计点-面试追问问题清单.md` 的 Q4 处补充本方案，标注"已实现"
