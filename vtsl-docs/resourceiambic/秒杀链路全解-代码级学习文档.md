```
│                                                       ▼                │
```

## 二、第一层：Gateway 入口（鉴权 + 签名 + 限流）

### 2.1 完整过滤链

秒杀请求进 Gateway 依次经过三个过滤器（按 Order 排序）：

| 过滤器 | 职责 | 位置 |
|---|---|---|
| `SignVerifyGlobalFilter` | HMAC-SHA256 签名验签 + Timestamp/Nonce 防重放 | `vtsl-gateway/.../filter/` |
| `JwtAuthGlobalFilter` | JWT 验签 → 解析 subject/role → 注入 `X-User-Id` / `X-User-Role` / `X-Device-Id` 头 | 同上 |
| Sentinel 限流 | 令牌桶 QPS 限流（Nacos 动态规则） | 配置 |

**关键点**：Gateway 只做**头注入**，不绑定用户上下文（WebFlux 无 Servlet API）；下游服务通过 `UserContextFilter`（vtsl-common）读取 `X-User-Id` 头绑定 ScopedValue。

### 2.2 路由配置（application.yml）

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: seckill
              uri: lb://vtsl-seckill
              predicates:
                - Path=/seckill/**
```

> ⚠️ Boot 4 / Gateway 5 配置路径是 `spring.cloud.gateway.server.webflux.routes`（不是旧版 `spring.cloud.gateway.routes`）。

## 三、第二层：Controller 接入

```java
@RestController
@RequestMapping("/seckill")
public class SeckillController {

    private final SeckillService seckillService;
    private final SnowflakeIdGenerator idGenerator;
    private final RedisSyncStrategy redisSyncStrategy;

    public SeckillController(SeckillService seckillService,
                             SnowflakeIdGenerator idGenerator,
                             RedisSyncStrategy redisSyncStrategy) {
        this.seckillService = seckillService;
        this.idGenerator = idGenerator;
        this.redisSyncStrategy = redisSyncStrategy;
    }

    @PostMapping("/activity")
    public Result<SeckillActivity> createActivity(@Valid @RequestBody CreateActivityRequest request) {
        return Result.ok(seckillService.createActivity(request.toEntity()));
    }

    @PutMapping("/activity/{id}/status")
    public Result<Void> updateStatus(@PathVariable Long id, @RequestBody Map<String, Integer> body) {
        seckillService.updateStatus(id, body.get("status"));
        return Result.ok();
    }

    /** 运行时动态切换扣减策略（REDIS_ASYNC ↔ REDIS_SYNC） */
    @PutMapping("/activity/{id}/mode")
    public Result<Void> updateMode(@PathVariable Long id, @RequestBody Map<String, String> body) {
        seckillService.updateMode(id, SeckillMode.valueOf(body.get("mode")));
        return Result.ok();
    }

    /** 查看 RedisSync 降级执行模式（运维/面试演示） */
    @GetMapping("/strategy/status")
    public Result<Map<String, String>> strategyStatus() {
        return Result.ok(Map.of(
                "redisSyncEffectiveMode", redisSyncStrategy.currentMode().name()
        ));
    }

    @GetMapping("/activity/{id}")
    public Result<SeckillActivity> activityDetail(@PathVariable Long id) {
        return Result.ok(seckillService.getActivityCached(id));
    }

    @GetMapping("/activity/list")
    public Result<List<SeckillActivity>> activityList(@RequestParam(required = false) Long roomId) {
        return Result.ok(seckillService.getActivities(roomId));
    }

    /** 秒杀下单入口 */
    @PostMapping("/order")
    public Result<Map<String, Object>> placeOrder(@RequestBody Map<String, Long> body,
                                                  @RequestHeader("X-User-Id") Long userId) {
        Long activityId = body.get("activityId");
        String orderNo = idGenerator.nextOrderNo();      // 雪花 ID 生成订单号
        String result = seckillService.placeOrder(activityId, userId, orderNo);
        return Result.ok(Map.of("result", result, "orderNo", orderNo));
    }

    @GetMapping("/order/list")
    public Result<List<SeckillOrder>> orderList(@RequestHeader("X-User-Id") Long userId) {
        return Result.ok(seckillService.getUserOrders(userId));
    }

    @GetMapping("/order/{orderNo}")
    public Result<SeckillOrder> orderDetail(@PathVariable String orderNo) {
        return Result.ok(seckillService.getOrder(orderNo));
    }

    @PutMapping("/order/{orderNo}/cancel")
    public Result<Void> cancelOrder(@PathVariable String orderNo,
                                    @RequestHeader("X-User-Id") Long userId) {
        seckillService.cancelOrder(orderNo, userId);
        return Result.ok();
    }

    @PutMapping("/order/{orderNo}/refund")
    public Result<Void> refundOrder(@PathVariable String orderNo) {
        seckillService.refundOrder(orderNo);
        return Result.ok();
    }
}
```

**学习要点**：
- `X-User-Id` 来自 Gateway 注入的请求头（不是前端传的，防伪造）
- `orderNo` 用雪花 ID 生成，全局唯一（幂等的基础）
- `@Valid` 校验 `CreateActivityRequest`（mode 字段可选，创建时指定策略）

## 四、第三层：SeckillService.placeOrder 主链路

`vtsl-seckill/.../biz/service/SeckillService.java`

```java
@Service
public class SeckillService {

    private final SeckillActivityRepository activityRepo;
    private final SeckillOrderRepository orderRepo;
    private final StockService stockService;
    private final ActivityCacheService cacheService;
    private final SeckillStrategyFactory seckillStrategyFactory;

    public SeckillService(SeckillActivityRepository activityRepo,
                          SeckillOrderRepository orderRepo,
                          StockService stockService,
                          ActivityCacheService cacheService,
                          SeckillStrategyFactory factory) {
        this.activityRepo = activityRepo;
        this.orderRepo = orderRepo;
        this.stockService = stockService;
        this.cacheService = cacheService;
        this.seckillStrategyFactory = factory;
    }

    /** 扣库存（主链路核心） */
    public String placeOrder(Long activityId, Long userId, String orderNo) {
        // ① 活动校验：Caffeine 缓存读（refreshAfterWrite 5s 后台刷新，永不阻塞）
        SeckillActivity activity = cacheService.getActivity(activityId);
        if (activity == null)
            return BizErrorCode.ACTIVITY_NOT_EXIST.getMsg();

        if (activity.getStatus() != 1)
            return BizErrorCode.ACTIVITY_NOT_STARTED.getMsg();

        LocalDateTime now = LocalDateTime.now();
        if (now.isBefore(activity.getStartTime()) || now.isAfter(activity.getEndTime()))
            return BizErrorCode.ACTIVITY_NOT_IN_TIME.getMsg();

        // ② 策略路由：按活动 mode 选扣减+落库策略
        SeckillStrategy strategy = seckillStrategyFactory.getStrategy(activity.getMode());

        // ③ 扣库存（Lua 或 DB CAS），Redis 异常 → 503（不误导用户"库存不足"）
        int result;
        try {
            result = strategy.deductStock(activityId, userId);
        } catch (RuntimeException e) {
            throw new BizException(503, "系统繁忙，请稍后重试");
        }

        // ④ 扣减成功 → 发 Kafka 落库
        if (result == 200) {
            try {
                strategy.createOrder(activity, userId, orderNo);
                return "ok";
            } catch (Exception e) {
                // ⑤ 创建订单失败（如 Kafka 彻底不可用）→ 回补库存 + 503 Fail Fast
                strategy.refundStock(activityId, userId);
                throw new BizException(503, "系统繁忙，请稍后重试");
            }
        }

        // ⑥ 业务失败码：-1 重复下单 / -2 库存不足 / -3 未初始化
        return switch (result) {
            case -1 -> BizErrorCode.USER_REPEAT_ORDER.getMsg();
            case -2 -> BizErrorCode.STOCK_NOT_ENOUGH.getMsg();
            case -3 -> BizErrorCode.ACTIVITY_NOT_INIT.getMsg();
            default -> BizErrorCode.SYSTEM_BUSY.getMsg();
        };
    }

    /** 消费端落库（SeckillOrderConsumer 调用） */
    @Transactional
    public SeckillOrder createOrder(SeckillActivity activity, Long userId, String orderNo) {
        SeckillOrder order = new SeckillOrder();
        order.setOrderNo(orderNo);
        order.setActivityId(activity.getId());
        order.setUserId(userId);
        order.setProductId(activity.getProductId());
        order.setSeckillPrice(activity.getSeckillPrice());
        order.setStatus(0);                    // 0=待支付
        return orderRepo.save(order);
    }

    /** 用户取消订单 → 回补库存 */
    @Transactional
    public void cancelOrder(String orderNo, Long userId) {
        SeckillOrder order = orderRepo.findByOrderNo(orderNo)
                .orElseThrow(() -> new BizException(404, "订单不存在"));
        if (!order.getUserId().equals(userId)) {
            throw new BizException(403, "无权操作");
        }
        if (order.getStatus() != 0) {
            throw new BizException(400, "订单状态不允许取消");
        }
        order.setStatus(2);                    // 2=已取消
        order.setCancelledAt(LocalDateTime.now());
        orderRepo.save(order);                 // @Version CAS 防并发（超时取消同时触发时）

        SeckillActivity activity = activityRepo.findById(order.getActivityId())
                .orElseThrow(() -> new BizException(404, "活动不存在"));
        SeckillStrategy strategy = seckillStrategyFactory.getStrategy(activity.getMode());
        strategy.refundStock(order.getActivityId(), userId);   // 按策略回补
    }

    /** 运行时切换策略（DB_QUEUE 与其他互切保护） */
    @Transactional
    public void updateMode(Long activityId, SeckillMode mode) {
        SeckillActivity activity = activityRepo.findById(activityId)
                .orElseThrow(() -> new BizException(404, "活动不存在"));
        SeckillMode current = activity.getMode();
        if (current == mode) return;
        // 库存模型隔离：DB_QUEUE（DB 直扣）与 Redis 系（Lua 扣减）不可互切
        boolean dbSwitch = (current == SeckillMode.DB_QUEUE || mode == SeckillMode.DB_QUEUE);
        if (dbSwitch) {
            throw new BizException(400,
                    "DB_QUEUE 与其他策略库存模型不同，禁止运行时互切: " + current + " -> " + mode);
        }
        activity.setMode(mode);
        activityRepo.save(activity);
        cacheService.refresh(activityId);      // 刷新 Caffeine，placeOrder 立即读到新 mode
        log.info("活动策略运行时切换: activityId={}, {} -> {}", activityId, current, mode);
    }
}
```

**学习要点**：
- **placeOrder 是同步返回的**：扣库存成功即返回 `"ok"`，订单落库是异步的（用户感知：立即成功，落库稍后）
- 异常分级：`deductStock` 的 RuntimeException → 503（系统错误）；业务失败码 -1/-2/-3（业务错误）分开
- `createOrder` 是消费端调用的**落库方法**（与 placeOrder 里的 `strategy.createOrder` 不同——后者是发 Kafka 消息）
- `cancelOrder` 的 `@Version` 防并发：用户手动取消与超时取消同时触发时，版本冲突的一方抛 `OptimisticLockException`

## 五、第四层：策略引擎（三模式可插拔）

### 5.1 接口与枚举

`strategy/SeckillStrategy.java`：

```java
public interface SeckillStrategy {
    int deductStock(Long activityId, Long userId);                    // 扣库存
    void createOrder(SeckillActivity activity, Long userId, String orderNo);  // 发 Kafka
    void refundStock(Long activityId, Long userId);                  // 回补库存
}
```

`model/enums/SeckillMode.java`：

```java
public enum SeckillMode {
    REDIS_ASYNC,   // Redis Lua 原子扣减 + Kafka 异步发送（send() 不等待）→ 最终一致性
    REDIS_SYNC,    // Redis Lua 原子扣减 + Kafka 同步发送（send().get(3s) 等 ack）→ 强一致性
    DB_QUEUE       // DB 乐观锁扣减（@Version CAS）+ Kafka 顺序消费（key=activityId 保序）
}
```

### 5.2 工厂路由

`strategy/SeckillStrategyFactory.java`：

```java
@Component
public class SeckillStrategyFactory {

    private final Map<SeckillMode, SeckillStrategy> strategyMap;

    public SeckillStrategyFactory(List<SeckillStrategy> strategyList) {
        this.strategyMap = strategyList.stream()
                .collect(Collectors.toMap(
                        this::resolveMode, Function.identity()
                ));
    }

    public SeckillMode resolveMode(SeckillStrategy seckillStrategy) {
        if (seckillStrategy instanceof RedisAsyncStrategy) return SeckillMode.REDIS_ASYNC;
        if (seckillStrategy instanceof RedisSyncStrategy) return SeckillMode.REDIS_SYNC;
        if (seckillStrategy instanceof DBQueueStrategy) return SeckillMode.DB_QUEUE;
        throw new IllegalStateException("未知策略模式:" + seckillStrategy.getClass());
    }

    public SeckillStrategy getStrategy(SeckillMode mode) {
        SeckillStrategy strategy = strategyMap.get(mode);
        if (strategy == null) {
            throw new IllegalStateException("不支持的秒杀模式: " + mode);
        }
        return strategy;
    }
}
```

**学习要点**：
- Spring 自动注入 `List<SeckillStrategy>`（所有 `@Component` 实现）→ `Collectors.toMap` 按 mode 建 Map
- 新增策略 = 实现接口 + 工厂加一个分支，符合开闭原则
- `placeOrder` / `cancelOrder` / `TimeoutCancelScheduler` 都通过工厂拿策略——**回补也按策略走**（Lua 回补 vs DB 原子更新）

## 六、第五层：库存扣减（Redis Lua / DB 乐观锁）

### 6.1 StockService（Redis Lua 扣减/回补统一入口）

`vtsl-seckill/.../biz/service/StockService.java`

```java
@Service
public class StockService {

    private static final Logger log = LoggerFactory.getLogger(StockService.class);

    private final StringRedisTemplate redisTemplate;
    private final DefaultRedisScript<Long> deductScript;
    private final DefaultRedisScript<Long> refundScript;
    private final boolean dedupEnabled;

    public StockService(StringRedisTemplate redisTemplate,
                        @Value("${seckill.dedup-enabled:true}") boolean dedupEnabled) {
        this.redisTemplate = redisTemplate;
        this.dedupEnabled = dedupEnabled;

        this.deductScript = new DefaultRedisScript<>();
        this.deductScript.setLocation(new ClassPathResource("lua/deduct_stock.lua"));
        this.deductScript.setResultType(Long.class);

        this.refundScript = new DefaultRedisScript<>();
        this.refundScript.setLocation(new ClassPathResource("lua/refund_stock.lua"));
        this.refundScript.setResultType(Long.class);
    }

    /** 初始化库存（活动上架时调用） */
    public void initStock(Long activityId, int totalStock) {
        redisTemplate.opsForValue().set("stock:{" + activityId + "}", String.valueOf(totalStock));
        log.info("库存初始化: activityId={}, total={}", activityId, totalStock);
    }

    /**
     * 原子扣库存。返回值：
     *  200 = 扣减成功
     *  -1 = 重复下单
     *  -2 = 库存不足
     *  -3 = 活动未初始化
     */
    public int deduct(Long activityId, Long userId) {
        String stockKey = "stock:{" + activityId + "}";
        String orderedKey = "ordered:{" + activityId + "}:" + userId;
        String dedupFlag = dedupEnabled ? "1" : "0";
        Long result = redisTemplate.execute(deductScript, List.of(stockKey, orderedKey), dedupFlag);

        if (result == null) {
            // Redis 连接失败 → 抛异常 → placeOrder catch → 503（不误导"库存不足"）
            throw new RuntimeException("Redis 连接失败，库存扣减中断");
        }
        int code = result.intValue();
        if (code == 200) {
            log.info("库存扣减成功: activityId={}, userId={}", activityId, userId);
        }
        return code;
    }

    /** 回补库存 */
    public void refund(Long activityId, Long userId) {
        String stockKey = "stock:{" + activityId + "}";
        String orderedKey = "ordered:{" + activityId + "}:" + userId;
        redisTemplate.execute(refundScript, List.of(stockKey, orderedKey));
        log.info("库存回补: activityId={}, userId={}", activityId, userId);
    }
}
```

### 6.2 deduct_stock.lua（原子扣减脚本）

`vtsl-seckill/src/main/resources/lua/deduct_stock.lua`

```lua
-- 原子扣库存（Redis Cluster 兼容：所有 key 通过 KEYS 数组传入）
-- KEYS[1] = stock:{activityId}
-- KEYS[2] = ordered:{activityId}:{userId}（ARGV[1]=0 时不检查/不写入）
-- ARGV[1] = "1" 启用去重（默认）, "0" 跳过去重检查
-- 返回: 200=成功, -1=重复下单, -2=库存不足, -3=活动未初始化

-- 前置检查：库存 key 不存在说明活动未上架
if redis.call("EXISTS", KEYS[1]) == 0 then
    return -3
end

local dedup = ARGV[1] ~= "0"
if dedup then
    local ordered = redis.call("GET", KEYS[2])
    if ordered then return -1 end
end

local stock = redis.call("DECR", KEYS[1])
if stock >= 0 then
    if dedup then
        redis.call("SETEX", KEYS[2], 86400, "1")
    end
    return 200
end
redis.call("INCR", KEYS[1])
return -2
```

### 6.3 refund_stock.lua（幂等回补脚本）

```lua
-- 回补库存（幂等：ordered key 存在才 INCR，防并发重复回补）
-- KEYS[1] = stock:{activityId}
-- KEYS[2] = ordered:{activityId}:{userId}
-- 返回 1 表示已补偿，0 表示无需补偿（orderedKey 不存在）

if redis.call("EXISTS", KEYS[2]) == 1 then
    redis.call("INCR", KEYS[1])
    redis.call("DEL", KEYS[2])
    return 1
end
return 0
```

**学习要点（防超卖核心）**：
- **Lua 原子性**：Redis 单线程执行脚本，查重→扣减→标记一气呵成，无并发窗口
- **Hash Tag `{activityId}`**：Redis Cluster 中 `stock:{1}` 与 `ordered:{1}:100` 落在同一 slot，Lua 多 key 操作不报 CROSSSLOT
- **扣减失败回滚**：`DECR` 后 <0 则 `INCR` 恢复（Redis 无回滚，手动 INCR 抵消）
- **幂等回补**：`refund_stock.lua` 只在 ordered key 存在时才 INCR+DEL，重复回补不 double-INCR
- **一人一单**：`ordered:{activityId}:{userId}` 是用户维度去重键（TTL 86400s=24h）
- **DB_QUEUE 用 DB CAS**：`decrementStockIfAvailable`（见 Repository），`@Version` + `total_stock > 0` 条件更新，affectedRows=0 表示冲突/不足

## 七、第六层：订单落库（Kafka 消费端）

`vtsl-seckill/.../biz/consumer/SeckillOrderConsumer.java`

```java
@Component
public class SeckillOrderConsumer {

    private static final Logger log = LoggerFactory.getLogger(SeckillOrderConsumer.class);
    private static final int MAX_RETRIES = 3;
    private static final String WS_PUSH_TOPIC = "ws:push:seckill-result";
    private final ConcurrentHashMap<String, AtomicInteger> retryCounts = new ConcurrentHashMap<>();
    private final Semaphore SEM;                       // 背压信号量

    private final SeckillService seckillService;
    private final ActivityCacheService cacheService;
    private final StockService stockService;
    private final StringRedisTemplate redisTemplate;

    public SeckillOrderConsumer(SeckillService seckillService,
                                ActivityCacheService cacheService,
                                StockService stockService,
                                StringRedisTemplate redisTemplate,
                                @Value("${seckill.consumer-max-concurrency:30}") int maxConcurrency) {
        this.seckillService = seckillService;
        this.cacheService = cacheService;
        this.stockService = stockService;
        this.redisTemplate = redisTemplate;
        this.SEM = new Semaphore(maxConcurrency);      // 默认 30 = HikariCP 池大小
    }

    @KafkaListener(topics = "seckill-order", groupId = "vtsl-seckill")
    public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
        // ① 背压：信号量耗尽 → 阻塞 poll → Broker 降速
        try {
            SEM.acquire();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        }

        // ② 虚拟线程处理（不占平台线程）
        Thread.startVirtualThread(() -> {
            try {
                // ③ 解析消息 userId:activityId:orderNo
                String[] parts = record.value().split(":", 3);
                if (parts.length < 3) {
                    log.error("Kafka 消息格式错误: {}", record.value());
                    ack.acknowledge();
                    return;
                }
                Long userId = Long.parseLong(parts[0]);
                Long activityId = Long.parseLong(parts[1]);
                String orderNo = parts[2];

                // ④ 活动校验：缺失 → 幂等回补库存（Redis 已扣但无法落库）
                SeckillActivity activity = cacheService.getActivity(activityId);
                if (activity == null) {
                    try {
                        stockService.refund(activityId, userId);   // refund Lua 幂等
                        log.error("活动不存在，已幂等回补库存: activityId={}, userId={}", activityId, userId);
                    } catch (Exception refundEx) {
                        log.error("活动不存在且回补库存失败: activityId={}, userId={}", activityId, userId, refundEx);
                    }
                    ack.acknowledge();
                    return;
                }

                // ⑤ DB 落库（唯一索引 uk_activity_user 幂等兜底）
                seckillService.createOrder(activity, userId, orderNo);

                // ⑥ WebSocket 推送结果（Redis Pub/Sub 广播）
                try {
                    String payload = String.format(
                            "{\"userId\":%d,\"orderNo\":\"%s\",\"ok\":true,\"message\":\"%s\",\"timestamp\":%d}",
                            userId, orderNo, "抢购成功", System.currentTimeMillis());
                    redisTemplate.convertAndSend(WS_PUSH_TOPIC, payload);
                } catch (Exception e) {
                    log.warn("Redis Pub/Sub 推送异常: userId={}, error={}", userId, e.getMessage());
                }

                ack.acknowledge();    // ⑦ 手动 ACK：落库成功才确认
            } catch (DuplicateKeyException e) {
                // ⑧ 幂等：重复消息撞唯一索引 → 直接 ack（不重复落库）
                log.warn("重复订单（幂等兜底）: orderNo={}", e.getMessage());
                ack.acknowledge();
            } catch (TransactionException e) {
                // ⑨ 事务异常：内存重试 3 次，超过 ack 放弃（幂等兜底）
                String key = record.value();
                AtomicInteger count = retryCounts.computeIfAbsent(key, k -> new AtomicInteger(0));
                int retried = count.incrementAndGet();
                if (retried >= MAX_RETRIES) {
                    log.error("DB/事务异常已达最大重试({}), 放弃并 ack: {}", MAX_RETRIES, key);
                    ack.acknowledge();
                    retryCounts.remove(key);
                } else {
                    log.error("DB/事务异常({}/{}), 不 ack 等待重投: {}", retried, MAX_RETRIES, key);
                }
            } catch (Exception e) {
                log.error("订单消费异常", e);
                ack.acknowledge();
            } finally {
                SEM.release();
            }
        });
    }
}
```

**学习要点**：
- **Semaphore 背压**：上限 30 对齐 HikariCP。信号量耗尽 → 阻塞 listener 线程 → poll 暂停 → Broker 感知消费慢 → 降速。从根源杜绝 VT 堆积 → 连接耗尽/OOM
- **手动 ACK**：`enable-auto-commit: false` + `ack-mode: manual`，落库成功才 `ack.acknowledge()`
- **幂等三重**：① DB 唯一索引 `uk_activity_user`（activity_id,user_id）② DuplicateKeyException 捕获 ③ 消息格式校验
- **⚠️ 异常类型坑**：JPA 抛的是 Hibernate 的 `ConstraintViolationException`（不是 Spring 的 `DuplicateKeyException`）——catch 链必须**同时捕获两者**，否则重复消息落入通用 Exception 打 ERROR（压测踩坑：降级重发重复订单被当成"消费异常"）
- **活动缺失回补**：Redis 库存已扣但活动没了 → 无法落库 → refund 幂等回补（refund Lua 只在 ordered 存在时 INCR）
- **TransactionException 重试**：内存计数 3 次，不 ack 等 Kafka 重投；超过放弃（DuplicateKey 兜底不重复）

## 八、可靠性架构：发送结果语义统一（SendOutcome）

> **重构背景**（2026-08-14）：旧版 `createOrder` 混了模式判断+发送+降级+委托 4 件事，且成功路径耗时没进窗口导致降级不触发。重构为**三分层**：编排（placeOrder）/ 决策（SyncDegradeController）/ 发送（KafkaOrderSender）。

### 8.1 SendOutcome 枚举（失败语义统一）

`vtsl-seckill/.../model/enums/SendOutcome.java`

```java
public enum SendOutcome {
    CONFIRMED,   // 同步确认送达（broker ack）
    ACCEPTED,    // 异步受理（pending 已落，不代表送达）
    TRANSIENT,   // 瞬时失败（超时/网络抖动）→ 统一回补
```

**设计要点**：上层 `placeOrder` 对非 CONFIRMED/ACCEPTED **统一幂等回补 + 503**，不再依赖异常做控制流——同步/异步失败语义一致，可测试、可扩展。

```java
    public SendOutcome sendAsyncReliable(String msg, String orderNo) { ... }

```

**sendAsyncReliable 四层保障**（从旧 RedisAsyncStrategy 迁移至此，职责收敛到"发送器"）：

```
① SET pending:{orderNo} (TTL 5min)  → ② send() 立即返回（~1ms）
   → ③ 回调 whenComplete: 成功删 pending / 失败 LPUSH compensate_queue（pending 保留）
   → ④ PendingOrderScanner 30s 补投 + CompensateQueueConsumer 5s 重试（>3 次进死信）
   → ⑤ LostOrderReconciler 对账: ordered 标记存在但 DB 无订单 → 幂等回补
```

**学习要点**：
- **回调 ≠ 等回调**：`send()` 只把消息放 producer 缓冲，`CompletableFuture` 由 Kafka I/O 线程完成——请求线程 1ms 返回，回调异步执行
- **JVM 崩溃窗口**：send() 后回调前宕机 → pending 残留 → 定时补投兜底
- **API 注意**：Spring 6+ 移除 `ListenableFuture`，Spring Kafka `send()` 直接返回 `CompletableFuture`

### 9.2 RedisSyncStrategy（薄外观：模式判断 + 委托）

```java
@Override
public SendOutcome createOrder(SeckillActivity activity, Long userId, String orderNo) {
    String msg = userId + ":" + activity.getId() + ":" + orderNo;
    if (degrade.isSyncMode()) {
        // 同步模式：发送（返回 outcome+耗时）→ 窗口上报真实耗时 → 失败由 placeOrder 统一回补
        KafkaOrderSender.SendSyncResult r = sender.sendSync(msg);
        degrade.record(r.outcome(), r.elapsedMs());
        return r.outcome();
    }
    // 降级模式：5% 探针（成功恢复/失败清 streak），消息一律走可靠异步
    if (degrade.shouldSample()) {
        KafkaOrderSender.SendSyncResult probe = sender.sendSync(msg);
        if (probe.outcome() == SendOutcome.CONFIRMED) degrade.onSampleSuccess();
        else degrade.onSampleFailure();
    }
    return sender.sendAsyncReliable(msg, orderNo);   // 降级后异步受理（pending+回调+补投）
}
```

### 9.3 降级状态机（完整闭环）

```
SYNC ──窗口 avg>500ms 或 rate>5%──▶ ASYNC（降级）
  ▲                                     │
  │            ┌────────────────────────┤
  │            ▼                        ▼
  │   有流量: 5% 采样连续 5 次成功     无流量: TTL 60s 到期
  └────────────── 切回 SYNC + 清窗口 ───┘
               （若 Kafka 未恢复，下个请求失败 → 窗口重积累 → 再降级）
```

### 9.4 失败语义分层（关键设计，面试必讲）

| 场景 | 行为 | 理由 |
|---|---|---|
| **单次失败** | Fail Fast：返回 TRANSIENT/FATAL → placeOrder 统一回补 + 503 | producer 已有 retries:3 内部重试，应用层重试叠加 3s 延迟（长尾来源） |
| **持续失败**（窗口超阈值） | 整体降级 REDIS_ASYNC → 后续请求异步受理 | 降级是窗口决策，不是单次反应 |
| **降级中 Kafka 恢复** | 采样/TTL 双路径恢复 | 不依赖请求、不产生探针消息 |

**学习要点**：
- **为什么降级不丢一致性**：SYNC/ASYNC 共用同一 Lua 库存，降级是纯发送语义切换，无库存迁移
- **为什么单次失败不异步兜底**：裸 send() 无 pending/回调 → 消息丢 + 库存泄漏破一致性；Fail Fast 回补后用户可再抢
- **为什么 TTL 不用探针**：探针消息污染业务 topic（消费者按 userId:activityId:orderNo 解析会报错），TTL 零额外消息

## 十一、兜底专题 D：对账 + 超时取消 + 取消回补

### 11.1 ReconciliationScheduler（对账：取消单回补兜底）

`vtsl-seckill/.../scheduler/ReconciliationScheduler.java`

```java
@Component
public class ReconciliationScheduler {

    private static final Logger log = LoggerFactory.getLogger(ReconciliationScheduler.class);
    private static final int CANCELLED_STATUS = 2;
    private static final String LOCK_KEY = "lock:reconciliation:cancelled";
    private static final long LOCK_TTL_SECONDS = 300;

    private final SeckillOrderRepository orderRepo;
    private final SeckillActivityRepository activityRepo;
    private final StringRedisTemplate redisTemplate;
    private final DefaultRedisScript<Long> refundScript;

    @Value("${seckill.reconciliation-enabled:true}")
    private boolean reconciliationEnabled;

    @Value("${seckill.reconciliation-window-minutes:60}")
    private int reconciliationWindowMinutes;

    @Value("${seckill.reconciliation-scan-ms:300000}")
    private long scanIntervalMs;

    @Value("${seckill.reconciliation-batch-size:500}")
    private int batchSize;

    public ReconciliationScheduler(SeckillOrderRepository orderRepo,
                                   SeckillActivityRepository activityRepo,
                                   StringRedisTemplate redisTemplate) {
        this.orderRepo = orderRepo;
        this.activityRepo = activityRepo;
        this.redisTemplate = redisTemplate;
        this.refundScript = new DefaultRedisScript<>();
        this.refundScript.setLocation(new ClassPathResource("lua/refund_stock.lua"));
        this.refundScript.setResultType(Long.class);
    }

    @Scheduled(fixedDelayString = "${seckill.reconciliation-scan-ms:300000}")
    public void reconcileCancelledOrders() {
        if (!reconciliationEnabled) return;

        if (!acquireLock()) {          // 分布式锁：多实例只一个执行
            log.debug("其他实例正在执行对账，本次跳过");
            return;
        }

        try {
            doReconcile();
        } finally {
            releaseLock();
        }
    }

    private void doReconcile() {
        // 只扫最近 60min 的已取消订单（避免全表扫描）
        LocalDateTime windowStart = LocalDateTime.now().minusMinutes(reconciliationWindowMinutes);
        Pageable pageable = PageRequest.of(0, batchSize);
        List<SeckillOrder> cancelledOrders = orderRepo.findByStatusAndCancelledAtAfter(CANCELLED_STATUS, windowStart, pageable);
        if (cancelledOrders.isEmpty()) return;

        Set<Long> activityIds = cancelledOrders.stream()
                .map(SeckillOrder::getActivityId)
                .collect(Collectors.toSet());
        Map<Long, SeckillActivity> activityMap = activityRepo.findAllById(activityIds).stream()
                .collect(Collectors.toMap(SeckillActivity::getId, a -> a));

        int fixed = 0;
        int skipped = 0;

        for (SeckillOrder order : cancelledOrders) {
            SeckillActivity activity = activityMap.get(order.getActivityId());
            if (activity == null || activity.getMode() == SeckillMode.DB_QUEUE) {
                skipped++;    // DB_QUEUE 库存不在 Redis，无需对账
                continue;
            }

            String stockKey = "stock:{" + order.getActivityId() + "}";
            String orderedKey = "ordered:{" + order.getActivityId() + "}:" + order.getUserId();

            // refund Lua 幂等：ordered 存在才 INCR+DEL；返回 1 表示补偿了，0 表示已回补过
            Long result = redisTemplate.execute(refundScript, List.of(stockKey, orderedKey));
            if (Long.valueOf(1L).equals(result)) {
                log.info("对账补偿回补库存: orderNo={}, activityId={}, userId={}",
                        order.getOrderNo(), order.getActivityId(), order.getUserId());
                fixed++;
            } else {
                skipped++;
            }
        }

        log.info("对账补偿完成: 检查 {} 笔, 补偿 {} 笔, 跳过 {} 笔",
                cancelledOrders.size(), fixed, skipped);
    }

    private boolean acquireLock() {
        try {
            Boolean acquired = redisTemplate.opsForValue()
                    .setIfAbsent(LOCK_KEY, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
            return Boolean.TRUE.equals(acquired);
        } catch (Exception e) {
            log.warn("获取对账分布式锁失败: {}", e.getMessage());
            return false;
        }
    }

    private void releaseLock() {
        try {
            redisTemplate.delete(LOCK_KEY);
        } catch (Exception e) {
            log.warn("释放对账分布式锁失败: {}", e.getMessage());
        }
    }
}
```

**学习要点**：
- **对账对象**：扫描"已取消(status=2)但 Redis ordered 标记未清"的订单 → Lua 幂等回补。不是"库存 vs 订单数"比对，不会误判在途消息
- **场景**：`cancelOrder` 中 DB save 成功但 Redis refund 失败（应用宕机/Redis 抖动）→ 对账兜底
- **分页**：`PageRequest.of(0, 500)` 每批 500，防积压订单全量加载 OOM（评审 P1-3 修复）
- **分布式锁**：多实例只有一个执行，防重复回补
- **DB_QUEUE 跳过**：DB 库存由 `incrementStockIfAvailable` 原子更新，不依赖 Redis

### 11.2 TimeoutCancelScheduler（超时取消）

`vtsl-seckill/.../scheduler/TimeoutCancelScheduler.java`

```java
@Component
public class TimeoutCancelScheduler {

    private static final Logger log = LoggerFactory.getLogger(TimeoutCancelScheduler.class);

    private final SeckillOrderRepository orderRepo;
    private final SeckillActivityRepository activityRepo;
    private final SeckillStrategyFactory strategyFactory;

    @Value("${seckill.order-timeout-minutes:15}")
    private int timeoutMinutes;

    @Value("${seckill.timeout-cancel-enabled:true}")
    private boolean timeoutCancelEnabled;

    @Value("${seckill.timeout-scan-batch:500}")
    private int batchSize;

    public TimeoutCancelScheduler(SeckillOrderRepository orderRepo,
                                  SeckillActivityRepository activityRepo,
                                  SeckillStrategyFactory strategyFactory) {
        this.orderRepo = orderRepo;
        this.activityRepo = activityRepo;
        this.strategyFactory = strategyFactory;
    }

    @Scheduled(fixedDelayString = "${seckill.timeout-scan-ms:15000}")
    public void cancelTimeoutOrders() {
        if (!timeoutCancelEnabled) return;
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(timeoutMinutes);
        // 分页扫描：待支付(status=0) 且超过 15min 未支付
        List<SeckillOrder> timeoutOrders = orderRepo.findByStatusAndCreatedAtBeforeOrderByCreatedAtAsc(
                0, deadline, PageRequest.of(0, batchSize));

        for (SeckillOrder order : timeoutOrders) {
            Thread.startVirtualThread(() -> {     // 每单一个 VT，不阻塞扫描线程
                try {
                    // DB 先更新（@Version CAS 防与用户手动取消并发）
                    order.setStatus(2);
                    order.setCancelledAt(LocalDateTime.now());
                    orderRepo.save(order);

                    SeckillActivity activity = activityRepo.findById(order.getActivityId()).orElse(null);
                    if (activity != null) {
                        SeckillStrategy strategy = strategyFactory.getStrategy(activity.getMode());
                        strategy.refundStock(order.getActivityId(), order.getUserId());
                    }
                    log.info("超时取消订单成功: orderNo={}", order.getOrderNo());
                } catch (OptimisticLockException e) {
                    // 用户已手动取消（version 冲突）→ 不重复处理
                    log.info("订单已被用户主动取消: orderNo={}", order.getOrderNo());
                } catch (Exception e) {
                    log.error("超时取消失败: orderNo={}", order.getOrderNo(), e);
                }
            });
        }
    }
}
```

**学习要点**：
- **DB 先 → Redis 后**：先 CAS 更新订单状态（防并发），再回补库存——顺序不能反（Redis 先回补、DB 失败 → 库存泄漏）
- **@Version 防并发**：用户手动取消 vs 超时取消同时触发 → version 冲突一方抛 `OptimisticLockException`，另一方成功
- **VT 处理**：`Thread.startVirtualThread` 每单一个虚拟线程，15s 扫描 + 500 单也不阻塞
- **回补按策略**：DB_QUEUE 走 `incrementStockIfAvailable`（DB 原子），Redis 系走 Lua

### 11.3 DBQueueStrategy（DB 乐观锁直扣 + 顺序消费）

`vtsl-seckill/.../biz/service/strategy/DBQueueStrategy.java`

```java
@Component
public class DBQueueStrategy implements SeckillStrategy {

    private static final Logger log = LoggerFactory.getLogger(DBQueueStrategy.class);

    private final SeckillActivityRepository activityRepo;
    private final KafkaTemplate<String, String> kafkaTemplate;

    public DBQueueStrategy(SeckillActivityRepository activityRepo,
                           KafkaTemplate<String, String> kafkaTemplate) {
        this.activityRepo = activityRepo;
        this.kafkaTemplate = kafkaTemplate;
    }

    /** DB 乐观锁直扣：@Version + total_stock>0 条件更新，原子防超卖 */
    @Transactional
    @Override
    public int deductStock(Long activityId, Long userId) {
        SeckillActivity activity = activityRepo.findById(activityId).orElse(null);
        if (activity == null) return -3;
        int updated = activityRepo.decrementStockIfAvailable(activityId, activity.getVersion());
        if (updated > 0) {
            return 200;
        }
        return -2;    // 版本冲突或库存不足
    }

    /** 发 Kafka 消息，key=activityId → 同一活动消息进同一分区 → 顺序消费 */
    @Override
    public void createOrder(SeckillActivity activity, Long userId, String orderNo) {
        String msg = userId + ":" + activity.getId() + ":" + orderNo;
        kafkaTemplate.send("seckill-order", activity.getId().toString(), msg);
        log.info("DBQueue 发送顺序 MQ 消息: key={}, msg={}", activity.getId(), msg);
    }

    /** DB 原子回补（无需 Redis） */
    @Transactional
    @Override
    public void refundStock(Long activityId, Long userId) {
        activityRepo.incrementStockIfAvailable(activityId);
        log.info("DBQueue 回补库存: activityId={}", activityId);
    }
}
```

## 十二、工具类：SlidingWindowStats 滑动窗口

`vtsl-seckill/.../biz/util/SlidingWindowStats.java`

```java
/**
 * 环形数组滑动窗口统计：记录最近 N 次采样的耗时与超时标记，
 * 支持查询窗口平均耗时、超时率。线程安全（synchronized 内部状态）。
 *
 * 用途：RedisSyncStrategy 降级判定——只统计最近 N 次 Kafka 发送结果，
 * 避免累计统计对突发故障不敏感。
 */
public class SlidingWindowStats {

    private final int capacity;
    private final long[] elapsedMs;
    private final boolean[] timeout;
    private int head;          // 环形写指针（指向最旧样本，覆盖时替换）
    private int filled;        // 已填样本数（0..capacity）
    private long sum;          // 窗口内总耗时(ms)
    private int timeoutCount;  // 窗口内超时/失败次数

    public SlidingWindowStats(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be > 0: " + capacity);
        }
        this.capacity = capacity;
        this.elapsedMs = new long[capacity];
        this.timeout = new boolean[capacity];
    }

    public synchronized void record(long elapsedMs, boolean timeout) {
        if (filled == capacity) {
            // 覆盖最旧样本：先扣减其统计（O(1)，无需搬移）
            sum -= this.elapsedMs[head];
            if (this.timeout[head]) timeoutCount--;
        } else {
            filled++;
        }
        this.elapsedMs[head] = elapsedMs;
        this.timeout[head] = timeout;
        head = (head + 1) % capacity;
        sum += elapsedMs;
        if (timeout) timeoutCount++;
    }

    public synchronized boolean isFull() { return filled == capacity; }
    public synchronized long averageMs() { return filled == 0 ? 0 : sum / filled; }
    public synchronized double timeoutRate() { return filled == 0 ? 0.0 : (double) timeoutCount / filled; }
    public synchronized int size() { return filled; }
    public int capacity() { return capacity; }
    public synchronized void reset() { head = 0; filled = 0; sum = 0; timeoutCount = 0; }
    public synchronized long maxMs() { ... }   // 窗口内最大耗时（诊断用）
}
```

**学习要点**：
- **环形数组**：head 指向最旧样本，满后覆盖并 O(1) 扣减，不搬移元素
- **为什么不用累计计数**：累计统计对突发不敏感——健康跑 10000 次后突发 100 次超时 rate≈1% 检测不到；滑动窗口只反映最近 N 次，即时触发
- **线程安全**：`synchronized` 保护内部状态（高并发 record/averageMs）
- **⚠️ 真实耗时是关键**：`record()` 必须传**成功路径的实际耗时**（不是 0）——否则窗口 avg 恒为 0，`avg>500ms` 永不触发降级（压测踩坑：成功耗时记 0 导致降级不触发）
- **单一职责**：纯统计工具，被 `RedisSyncStrategy` 复用（解耦自策略类）

## 十四、链路关键点速查

### 完整时序（一次成功下单）

```
用户 → Gateway(JWT) → Controller(雪花orderNo) → SeckillService.placeOrder
  → Caffeine 活动校验 → 策略工厂选策略 → Lua 扣减(200)
  → RedisAsync: SET pending → send() 返回 ok(~1ms)
  → Kafka → SeckillOrderConsumer(Semaphore背压 + VT)
  → 活动校验 → createOrder DB 落库 → WS 推送"抢购成功" → 手动 ACK
```

### 所有兜底一览（异常时谁负责）

| 场景 | 兜底机制 | 触发 |
|---|---|---|
| Lua 扣减成功、Kafka 发送失败 | 回调 → compensate_queue → 5s 重发 | 实时 |
| send() 后 JVM 崩溃 | pending 残留 → 30s 补投 | 30s |
| 补投/重发重复消息 | 消费端 uk_activity_user 唯一索引 | 消费时 |
| 补偿重试 >3 次 | dead_letter_queue + 监控告警 | 5s |
| 取消订单 Redis 回补失败 | ReconciliationScheduler 对账（5min） | 5min |
| 超时未支付 | TimeoutCancelScheduler（15min/15s） | 定时 |
| Redis 扣减连接失败 | 抛 503（不误导"库存不足"） | 实时 |
| Kafka 彻底不可用 | send() 抛异常 → refund + 503 Fail Fast | 实时 |
| 同步等待变慢 | 滑动窗口降级 REDIS_ASYNC | 实时 |

### 15.2 双 Listener 设计（为什么 Offset Explorer 连不上）

**核心概念**：`advertised.listeners` 是 broker 告诉客户端"我在哪"的地址，**必须是客户端视角可达的地址**。

```
客户端视角:
  容器内应用    → 能解析 seckill-kafka1 → 用 INTERNAL (9092/9094/9096)
  宿主机 GUI    → 只能访问 VM IP       → 用 EXTERNAL (19092/19094/19096)
```

**之前的坑**：单 listener `PLAINTEXT://kafka1:9092`，宿主机 Offset Explorer 连上 broker 后，broker 返回"我在这：kafka1:9092"，宿主机解析不了容器名 → 握手失败。

**修复**：双 listener，各自 advertised 各自视角的地址：

```yaml
# docker-compose.yml（seckill-kafka1 为例）
KAFKA_LISTENERS: INTERNAL://:9092,CONTROLLER://:9093,EXTERNAL://:19092
KAFKA_ADVERTISED_LISTENERS: INTERNAL://seckill-kafka1:9092,EXTERNAL://${KAFKA_EXTERNAL_HOST:-192.168.147.132}:19092
KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT
KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
```

> ⚠️ 不要写 `EXTERNAL://localhost:...`——除非 Kafka 与客户端同机。Kafka 在 VM、客户端在宿主机时，EXTERNAL advertised 必须是 **VM IP**。

**客户端连接矩阵**：

| 客户端 | bootstrap-servers | 走哪个 listener |
|---|---|---|
| 容器内应用（docker 化） | `seckill-kafka1:9092,seckill-kafka2:9094,seckill-kafka3:9096` | INTERNAL（默认值） |
| 本机 IDE 跑应用 | 环境变量 `KAFKA_ADDR=192.168.147.132:19092,192.168.147.132:19094,192.168.147.132:19096` | EXTERNAL |
| Offset Explorer（宿主机） | `192.168.147.132:19092,192.168.147.132:19094,192.168.147.132:19096` | EXTERNAL |

### 15.3 Producer/Consumer 高可用配置

```yaml
      acks: all                # 等所有 ISR 副本确认（RF=3 + min.insync.replicas=2）
      retries: 3
      enable-idempotence: true # 幂等生产者：网络重试不产生重复消息
    consumer:
      group-id: vtsl-seckill   # ⚠️ 消费组名是持久化的，上线后不要改（改了=新组=重放全部历史）
      enable-auto-commit: false
    listener:
      ack-mode: manual         # ⚠️ 用 manual（落库成功才 ack），不要用 MANUAL_IMMEDIATE
      concurrency: 4           # 4 消费线程（topic 6 partition ≥ 4，线程全活跃）
```

**3 个"不要照抄别人配置"的点**：
1. `group-id` 保持 `vtsl-seckill`——代码 `@KafkaListener(groupId = "vtsl-seckill")` 与 yml 一致；改名 = 新消费组从 earliest 重放 → 重复下单
2. `ack-mode: manual`——MANUAL_IMMEDIATE 不等方法返回就 ack，落库前 ack → 落库失败消息丢失
3. `concurrency: 4`——≥ topic partition 数时线程全活跃；改小浪费并行度

### 15.4 Topic 初始化：KafkaAdmin 自动创建

**为什么需要**：`AUTO_CREATE_TOPICS=false`，topic 不预建则应用启动消费报 "Topic not found"。

**方案①：Spring KafkaAdmin + NewTopic Bean（单机秒杀主用，启动即建）**

`vtsl-seckill/.../config/KafkaTopicConfig.java`

```java
@Configuration
public class KafkaTopicConfig {

    @Value("${kafka.topic.seckill-order:seckill-order}")
    private String seckillOrderTopic;

    @Value("${kafka.topic.seckill-order-partitions:6}")
    private int seckillOrderPartitions;

    @Value("${kafka.topic.replication-factor:3}")
    private short replicationFactor;

    @Bean
    public NewTopic seckillOrderTopic() {
        return TopicBuilder.name(seckillOrderTopic)
                .partitions(seckillOrderPartitions)
                .replicas(replicationFactor)
                .config("cleanup.policy", "delete")
                .config("retention.ms", "86400000")   // 消息保留 1 天
                .build();
    }
}
```

> Spring 启动时 `KafkaAdmin` 检测到 `NewTopic` Bean 自动创建；**幂等**——已存在则跳过，重启不重复建。

**方案②：init-kafka.sh（运维显式建，首次上线用）**

```bash
kafka-topics.sh --bootstrap-server seckill-kafka1:9092 --create --if-not-exists \
    --topic seckill-order --partitions 6 --replication-factor 3 \
    --config cleanup.policy=delete --config retention.ms=86400000
```

> ⚠️ 纠错：`ws:push:seckill-result` 是 **Redis Pub/Sub channel**（`SeckillOrderConsumer.java:89` 的 `redisTemplate.convertAndSend`），**不是 Kafka topic**，无需在 Kafka 创建。

### 15.5 partition 设计（单机秒杀场景）

```
partition = 6，消费并发 concurrency = 4

为什么 6？
  · 6 ≥ 4：4 个消费线程瓜分 6 分区，全部活跃（若 1 分区 → 只有 1 线程消费）
  · 留余量：未来加消费者实例时，6 分区最多 6 并行消费；partition 只能增不能减
  · 顺序性：DBQueueStrategy 用 key=activityId，同 key 恒进同分区，与分区数无关
```
