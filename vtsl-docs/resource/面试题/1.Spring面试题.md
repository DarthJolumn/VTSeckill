### 第1集：什么是IoC？别再背"控制反转"四个字了

**🎯 面试官问法：**
> "你说你用了Spring，那什么是IoC？用你的话解释一下。"

**💡 核心回答：**
IoC就是**对象的创建和依赖关系的管理，从你自己写代码new，变成了交给Spring容器来管理**。你不再关心"谁来做"，Spring帮你做好了一切。

**📦 实际例子：**

假设你做了一个电商订单系统，订单创建后要发通知：

```java
// ❌ 没有IoC的时候：你自己new依赖
public class OrderService {
    private NotificationService notification = new EmailNotificationService();
    
    public void createOrder(Order order) {
        // 创建订单逻辑...
        notification.send(order.getUserId(), "订单创建成功");
    }
}
```

问题在哪？你想换成短信通知，就得改源码。你想单元测试，还得真连邮件服务器。

```java
// ✅ 有IoC之后：依赖由Spring注入
@Service
public class OrderService {
    private final NotificationService notification;
    
    // Spring帮你把NotificationService的实现类注入进来
    @Autowired
    public OrderService(NotificationService notification) {
        this.notification = notification;
    }
    
    public void createOrder(Order order) {
        // 创建订单逻辑...
        notification.send(order.getUserId(), "订单创建成功");
    }
}

// 用哪个实现类，由Spring配置决定
@Service
public class EmailNotificationService implements NotificationService { ... }

@Service
public class SmsNotificationService implements NotificationService { ... }
```

**你想切换通知方式？改一行配置就行，业务代码一行不用动。这就是IoC。**

**⚠️ 常见坑/加分回答：**
- 加分回答：IoC的核心好处是**解耦+可测试**。单元测试时可以注入Mock对象，不用真实连接数据库或邮件服务器。
- 加分回答：IoC的三种DI方式——**构造器注入**（推荐）、**Setter注入**、**字段注入**（不推荐）。构造器注入保证对象不可变，且在对象创建时就暴露依赖缺失问题。

### 第2集：构造器注入vs字段注入，为什么大厂只用一种？

**🎯 面试官问法：**
> "你项目里用@Autowired注入还是构造器注入？为什么？"

**💡 核心回答：**
**大厂规范几乎都用构造器注入**。字段注入虽然写着爽，但有三个致命问题。

**📦 实际例子：**

三种注入方式对比：

```java
// ❌ 方式1：字段注入 — 爽但有问题
@Service
public class OrderService {
    @Autowired
    private UserService userService;      // 不能final，不能测试时替换
    @Autowired  
    private StockService stockService;
}

// ⚠️ 方式2：Setter注入 — 可选依赖时用
@Service
public class OrderService {
    private NotificationService notification;
    
    @Autowired(required = false)  // 这个依赖可以没有
    public void setNotification(NotificationService notification) {
        this.notification = notification;
    }
}

// ✅ 方式3：构造器注入 — 推荐
@Service
public class OrderService {
    private final UserService userService;      // 可以final
    private final StockService stockService;
    
    @Autowired  // Spring 4.3+，单构造器可以省略@Autowired
    public OrderService(UserService userService, StockService stockService) {
        this.userService = userService;
        this.stockService = stockService;
    }
}
```

**为什么字段注入不行？看这个真实场景：**

```java
// 字段注入：你写单元测试的时候……
@Test
public void testCreateOrder() {
    OrderService service = new OrderService();
    // userService是null！没法测试！
    // 字段注入的对象，你连setter都没有，根本塞不进去
}

// 构造器注入：单元测试轻松搞定
@Test
public void testCreateOrder() {
    UserService mockUserService = Mockito.mock(UserService.class);
    StockService mockStockService = Mockito.mock(StockService.class);
    OrderService service = new OrderService(mockUserService, mockStockService);
    // 测试随便跑！
}
```

| 对比维度 | 字段注入 | 构造器注入 |
|---------|---------|-----------|
| 代码简洁度 | ✅ 最简洁 | ⚠️ 稍长 |
| 不可变性 | ❌ 不能final | ✅ 可以final |
| 单元测试 | ❌ 无法手动注入Mock | ✅ 直接new传参 |
| 循环依赖检测 | ❌ 启动不报错，运行时NPE | ✅ 启动就报错，提前暴露 |
| 依赖是否清晰 | ❌ 藏在一堆字段里 | ✅ 构造器一目了然 |

**⚠️ 常见坑/加分回答：**
- 加分回答：字段注入在Spring处理循环依赖时看似能工作（因为先创建空对象再注入），但构造器注入会在启动时直接报错，**提前暴露设计问题**——循环依赖本身就是不好的设计。
- 加分回答：Spring官方从4.3开始，单构造器可以省略`@Autowired`注解。
- 坑：如果一个Service依赖太多（比如超过7个），说明这个类职责过重，应该拆分。

### 第3集：Spring循环依赖，三级缓存到底在缓存什么？

**🎯 面试官问法：**
> "Spring怎么解决循环依赖的？三级缓存每一级存的是什么？"

**💡 核心回答：**
循环依赖就是A依赖B，B又依赖A。Spring用**三级缓存**来解决：
- **一级缓存（singletonObjects）**：存完全初始化好的Bean，可以直接用
- **二级缓存（earlySingletonObjects）**：存提前暴露的半成品Bean（属性还没注入完）
- **三级缓存（singletonFactories）**：存Bean的工厂方法（ObjectFactory），用来生成早期代理对象

**📦 实际例子：**

用一个用户系统来演示循环依赖：

```java
@Component
public class UserService {
    @Autowired
    private OrderService orderService;  // UserService依赖OrderService
    
    public User getUserWithOrders(Long userId) {
        User user = getUser(userId);
        user.setOrders(orderService.getRecentOrders(userId));
        return user;
    }
}

@Component
public class OrderService {
    @Autowired
    private UserService userService;  // OrderService依赖UserService
    
    public Order getOrderWithUser(Long orderId) {
        Order order = getOrder(orderId);
        order.setUser(userService.getUser(order.getUserId()));
        return order;
    }
}
```

**Spring启动时，三级缓存的工作过程：**

```
1. 创建UserService → 实例化（空对象）
   → 放入三级缓存：singletonFactories.put("userService", () -> 早期引用)
   
2. 注入属性时发现需要OrderService → 去创建OrderService
   → 实例化OrderService（空对象）
   → 放入三级缓存
   
3. 注入OrderService的属性时发现需要UserService
   → 从三级缓存拿到UserService的工厂 → 生成早期引用
   → 提升到二级缓存：earlySingletonObjects.put("userService", 早期对象)
   → 删除三级缓存
   
4. OrderService拿到UserService的早期引用 → 注入完成 → OrderService创建完成
   → 放入一级缓存：singletonObjects.put("orderService", 完整的OrderService)
   
5. 回到UserService，拿到完整的OrderService → 注入完成
   → 放入一级缓存：singletonObjects.put("userService", 完整的UserService)
```

**⚠️ 常见坑/加分回答：**
- 加分回答：三级缓存的关键设计是**延迟代理创建**。如果A需要被AOP代理，三级缓存的ObjectFactory会在被取出时提前创建代理对象，而不是等到初始化完成后。
- 加分回答：**构造器注入的循环依赖无解**！因为创建对象本身就需要依赖。解决方案：用`@Lazy`延迟加载，或重构代码打破循环。
- 坑：Spring Boot 2.6+默认禁止循环依赖，会直接报错。需要`spring.main.allow-circular-references=true`才能开启。

### 第4集：为什么Spring不用两级缓存解决循环依赖？

**🎯 面试官问法：**
> "三级缓存听着挺复杂，两级缓存不行吗？为什么要第三级？"

**💡 核心回答：**
两级缓存能解决**没有AOP**的循环依赖。但一旦加上AOP代理，就必须三级。因为第三级缓存解决的是**"代理对象该什么时候创建"**的问题。

**📦 实际例子：**

还是上面那个UserService和OrderService，现在UserService需要加AOP做日志：

```java
@Component
public class UserService {
    @Autowired
    private OrderService orderService;
    
    // 假设这个类被AOP代理了（比如加了@Async或@Transactional）
}
```

**两级缓存的问题：**

```
如果用两级缓存：
1. 创建UserService → 放二级缓存（原始对象，不是代理！）
2. 创建OrderService → 拿到UserService的原始对象
3. UserService初始化完成后，AOP创建代理对象
4. 但OrderService拿的是原始对象，不是代理对象！

结果：OrderService里调UserService的方法，不经过AOP代理！
日志、事务、权限切面全部失效！
```

**三级缓存的解决方式：**

```java
// 第三级缓存存的是一个ObjectFactory（工厂方法）
singletonFactories.put("userService", () -> {
    // 这个lambda会在被调用时执行
    Object earlyRef = userService;  // 先拿原始对象
    
    // 关键：如果这个Bean需要被AOP代理，就在这里提前创建代理
    if (需要AOP代理) {
        earlyRef = aopProxyFactory.createProxy(userService);
    }
    return earlyRef;
});
```

**这样，当OrderService从二级缓存拿UserService时，拿到的是代理对象！**

| 场景 | 两级缓存 | 三级缓存 |
|------|---------|---------|
| 无AOP的循环依赖 | ✅ 能解决 | ✅ 能解决 |
| 有AOP的循环依赖 | ❌ 拿到的是原始对象 | ✅ 拿到的是代理对象 |
| 代理创建时机 | 初始化完成后（太晚） | 被引用时（刚好） |

**⚠️ 常见坑/加分回答：**
- 加分回答：三级缓存的`ObjectFactory`是一种**延迟计算**的设计模式，它不是一开始就创建代理，而是等到被其他Bean引用时才决定是否创建代理。
- 加分回答：如果AOP代理在Bean初始化之后才创建（两级缓存的做法），会导致同一个Bean在容器中有两个实例（原始对象+代理对象），其他Bean拿到的引用不一致。
- 坑：`@Async`注解也会触发代理，所以加了`@Async`的Bean参与循环依赖时，也需要三级缓存。

### 第5集：Bean生命周期，面试官要你画出完整流程图

**🎯 面试官问法：**
> "一个Bean从创建到销毁，经历了哪些步骤？请画出完整流程。"

**💡 核心回答：**
Bean生命周期分**6大阶段**，每一步都有具体的回调点：

```
1. 实例化（Instantiation）     → new对象，分配内存
2. 属性注入（Populate）         → @Autowired、@Value注入
3. BeanNameAware/BeanFactoryAware回调
4. BeanPostProcessor前置处理    → postProcessBeforeInitialization()
5. 初始化                       → @PostConstruct → InitializingBean → init-method
6. BeanPostProcessor后置处理    → postProcessAfterInitialization() → AOP代理在这里！
7. 使用中...
8. 销毁                        → @PreDestroy → DisposableBean → destroy-method
```

**📦 实际例子：**

用一个电商商品服务来演示：

```java
@Component
public class ProductService implements InitializingBean, DisposableBean, BeanNameAware {
    
    private String productName;
    
    // ① 构造器 — 实例化
    public ProductService() {
        System.out.println("1. 构造器：对象创建了");
    }
    
    // ② 属性注入
    @Autowired
    private ProductDao productDao;
    
    @Value("默认商品")
    private String defaultName;
    
    // ③ Aware回调
    @Override
    public void setBeanName(String name) {
        System.out.println("3. BeanNameAware：我的名字是 " + name);
    }
    
    // ④ @PostConstruct（JSR-250注解）
    @PostConstruct
    public void postConstruct() {
        System.out.println("5a. @PostConstruct：初始化数据字典缓存");
        // 实际场景：启动时加载商品分类到本地缓存
    }
    
    // ⑤ InitializingBean接口
    @Override
    public void afterPropertiesSet() {
        System.out.println("5b. InitializingBean：校验必要配置");
    }
    
    // ⑥ BeanPostProcessor后置处理（AOP代理在这一步生成）
    // 你不用自己写，Spring自动执行
    
    // ⑦ 业务方法
    public Product getProduct(Long id) {
        return productDao.findById(id);
    }
    
    // ⑧ 销毁回调
    @PreDestroy
    public void preDestroy() {
        System.out.println("8a. @PreDestroy：关闭连接池、清理缓存");
    }
    
    @Override
    public void destroy() {
        System.out.println("8b. DisposableBean：释放资源");
    }
}
```

**执行顺序（打印结果）：**
```
1. 构造器：对象创建了
3. BeanNameAware：我的名字是 productService
5a. @PostConstruct：初始化数据字典缓存
5b. InitializingBean：校验必要配置
8a. @PreDestroy：关闭连接池、清理缓存（容器关闭时）
8b. DisposableBean：释放资源（容器关闭时）
```

**⚠️ 常见坑/加分回答：**
- 加分回答：`@PostConstruct` → `InitializingBean.afterPropertiesSet()` → `init-method` 这三者的执行顺序是固定的，面试常考。
- 加分回答：AOP代理是在`BeanPostProcessor.postProcessAfterInitialization()`这一步创建的，也就是初始化完成之后。所以代理对象是在Bean生命周期的最后阶段才生成的。
- 坑：`@PreDestroy`只在**单例Bean**且容器正常关闭时才会执行。prototype作用域的Bean，Spring不会帮你销毁。

### 第6集：Spring单例Bean是线程安全的吗？

**🎯 面试官问法：**
> "Spring的Bean默认是单例的，那它是线程安全的吗？"

**💡 核心回答：**
**不是。** Spring只管创建单例对象，不管线程安全。如果你的Bean里有**可变的成员变量**，多线程下就会出问题。

**📦 实际例子：**

```java
// ❌ 有状态Bean — 线程不安全！
@Service
public class OrderService {
    // 这个成员变量会被所有线程共享！
    private int orderCount = 0;
    
    public void createOrder(Order order) {
        orderCount++;  // 多线程下，这行代码会丢失计数！
        // 线程A读orderCount=5，线程B也读orderCount=5
        // 两个都写6，实际应该是7
        order.setId(orderCount);
        save(order);
    }
}

// ✅ 方案1：用无状态Bean（推荐）
@Service
public class OrderService {
    @Autowired
    private OrderDao orderDao;  // 无状态，只是调用DAO
    
    public void createOrder(Order order) {
        // 不存成员变量，用数据库自增ID
        orderDao.save(order);
    }
}

// ✅ 方案2：用AtomicInteger
@Service
public class OrderService {
    private AtomicInteger orderCount = new AtomicInteger(0);
    
    public int getNextOrderNo() {
        return orderCount.incrementAndGet();  // 原子操作，线程安全
    }
}

// ✅ 方案3：用ThreadLocal（每个线程一份）
@Service
public class UserService {
    private ThreadLocal<User> currentUser = new ThreadLocal<>();
    
    public void setCurrentUser(User user) {
        currentUser.set(user);  // 每个线程独立存储
    }
    
    public User getCurrentUser() {
        return currentUser.get();
    }
    // 注意：请求结束后要 currentUser.remove()，防止内存泄漏！
}
```

| 场景 | 是否线程安全 | 原因 |
|------|------------|------|
| Bean里没有任何成员变量 | ✅ 安全 | 无状态，没有共享数据 |
| 成员变量是final/不可变 | ✅ 安全 | 只读不写 |
| 成员变量是可变的 | ❌ 不安全 | 多线程同时读写 |
| 使用ThreadLocal | ✅ 安全 | 每个线程独立副本 |

**⚠️ 常见坑/加分回答：**
- 加分回答：Spring的Controller、Service、Dao默认都是单例，所以**千万不要在Service里定义可变成员变量**来存储请求级别的数据（比如当前用户信息）。
- 加分回答：`SimpleDateFormat`是非线程安全的，如果在单例Bean里定义为成员变量共享使用，一定会出bug。应该用`DateTimeFormatter`（线程安全）或每次new一个。
- 坑：ThreadLocal用完必须`remove()`，否则在线程池场景下会导致内存泄漏和数据串号。

### 第7集：Bean的6种作用域，99%的人只知道前两种

**🎯 面试官问法：**
> "Spring Bean有哪些作用域？除了Singleton和Prototype你还知道哪些？"

**💡 核心回答：**
Spring定义了6种Bean作用域，Web环境下有4种额外的作用域。

**📦 实际例子：**

```java
// 1. singleton（默认）：整个容器只有一个实例
// 场景：Service、Dao、配置类 —— 无状态的服务
@Service  // 默认就是singleton
public class OrderService { ... }

// 2. prototype：每次获取都创建新实例
// 场景：有状态的工具类，比如每次请求需要一个独立的计算上下文
@Scope("prototype")
@Component
public class ReportGenerator {
    private List<String> errors = new ArrayList<>();  // 每次new一份，互不干扰
    public void generate() { ... }
}

// 3. request：每个HTTP请求一个实例（Web环境）
// 场景：存储当前请求的用户信息
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class UserRequestInfo {
    private String userId;
    private String loginIp;
    // 每个请求独立，不会互相干扰
}

// 4. session：每个HTTP Session一个实例
// 场景：购物车（老式Session方案）
@Component
@Scope(value = "session", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class ShoppingCart {
    private List<Item> items = new ArrayList<>();
    // 同一用户会话期间共享
}

// 5. application：整个ServletContext一个实例
// 场景：应用级配置
@Component
@Scope("application")
public class AppConfig { ... }

// 6. websocket：每个WebSocket会话一个实例
@Component
@Scope("websocket")
public class ChatSession { ... }
```

**一个容易踩的坑——Singleton引用Prototype：**

```java
@Service  // singleton
public class ReportService {
    @Autowired
    private ReportGenerator generator;  // prototype
    
    public void generateReport() {
        // 你以为每次调用都是新的generator？错！
        // generator在ReportService创建时就被注入了，一直是同一个！
        generator.generate();  
    }
}

// ✅ 解决方案：用ObjectFactory或@Lookup
@Service
public class ReportService {
    @Autowired
    private ObjectFactory<ReportGenerator> generatorFactory;
    
    public void generateReport() {
        ReportGenerator generator = generatorFactory.getObject(); // 每次都是新的！
        generator.generate();
    }
}

// 或者用@Lookup
@Service
public abstract class ReportService {
    public void generateReport() {
        ReportGenerator generator = createGenerator(); // 每次返回新实例
        generator.generate();
    }
    
    @Lookup  // Spring会自动重写这个方法
    protected abstract ReportGenerator createGenerator();
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：prototype Bean被注入到singleton Bean后，**不会每次都创建新的**。这是经典面试陷阱。解决方案是ObjectFactory或`@Lookup`。
- 加分回答：prototype Bean的销毁Spring不管！你需要自己实现`DisposableBean`或者在代码里手动清理资源。
- 坑：`@Scope(value="request", proxyMode=ScopedProxyMode.TARGET_CLASS)` 中的proxyMode必须加，否则在singleton中注入request作用域的Bean会报错。

### 第8集：AOP到底是什么？一个比喻你就懂了

**🎯 面试官问法：**
> "用你自己的话解释一下AOP，什么是切面、切点、通知？"

**💡 核心回答：**
AOP就是**把散落在各个地方的重复逻辑（日志、权限、事务）抽出来，统一处理**。你不用在每个方法里写重复代码，而是定义一个"切面"，告诉Spring"在哪些方法执行前后，自动帮我做这些事"。

**📦 实际例子——用一个生活比喻：**

想象一个奶茶店：
- **核心业务**（业务方法）：做奶茶（点单→制作→出品）
- **重复动作**（横切关注点）：每一杯都要**洗手**、**拍照记录**、**登记出品时间**

没有AOP：每个员工做每杯奶茶前后，自己洗手、拍照、登记 → 重复、容易忘
有AOP：店长安排一个**质检员**（切面），在每杯奶茶制作前后自动执行这些动作 → 统一、不遗漏

**用代码演示：**

```java
// 没有AOP：每个Service方法里都写日志和权限检查
@Service
public class OrderService {
    public void createOrder(Order order) {
        // 1. 记录日志（重复！）
        log.info("用户{}创建订单", order.getUserId());
        long start = System.currentTimeMillis();
        
        // 2. 权限检查（重复！）
        if (!SecurityUtils.hasPermission("order:create")) {
            throw new ForbiddenException();
        }
        
        // 3. 真正的业务逻辑
        orderDao.save(order);
        
        // 4. 记录耗时（重复！）
        log.info("创建订单耗时：{}ms", System.currentTimeMillis() - start);
    }
    
    public void cancelOrder(Long orderId) {
        // 又写一遍日志、权限检查、耗时统计...
    }
}

// 有AOP：业务代码干干净净
@Service
public class OrderService {
    public void createOrder(Order order) {
        orderDao.save(order);  // 只有业务逻辑！
    }
}

// 日志+耗时 → 交给AOP切面
@Aspect
@Component
public class LogAspect {
    
    // 定义切点：匹配所有Service的方法
    @Pointcut("execution(* com.example.service.*.*(..))")
    public void serviceLayer() {}
    
    // 环绕通知：方法执行前后自动处理
    @Around("serviceLayer()")
    public Object logAndTime(ProceedingJoinPoint joinPoint) throws Throwable {
        String methodName = joinPoint.getSignature().getName();
        log.info("▶ 开始执行：{}", methodName);
        long start = System.currentTimeMillis();
        
        Object result = joinPoint.proceed();  // 执行原方法
        
        long cost = System.currentTimeMillis() - start;
        log.info("◀ 执行完成：{}，耗时：{}ms", methodName, cost);
        return result;
    }
}
```

**AOP核心概念速查：**

| 概念 | 解释 | 奶茶店比喻 |
|------|------|-----------|
| Aspect（切面） | 横切逻辑的模块化封装 | 质检员这个岗位 |
| Pointcut（切点） | 定义切面作用在哪些方法上 | "所有奶茶的制作过程" |
| Advice（通知） | 具体要执行的逻辑 | 洗手、拍照、登记 |
| JoinPoint（连接点） | 程序执行中的某个点 | 某一杯奶茶的制作 |
| Weaving（织入） | 把切面应用到目标对象的过程 | 质检员上岗工作 |

**⚠️ 常见坑/加分回答：**
- 加分回答：AOP的5种通知类型——`@Before`（前置）、`@After`（最终）、`@AfterReturning`（返回后）、`@AfterThrowing`（异常后）、`@Around`（环绕）。**@Around最强大**，可以控制是否执行原方法。
- 加分回答：AOP的实现本质是**代理模式**。Spring AOP用动态代理，AspectJ用编译时织入。

### 第9集：JDK动态代理vs CGLIB，Spring到底用哪个？

**🎯 面试官问法：**
> "Spring AOP用的是JDK动态代理还是CGLIB？有什么区别？"

**💡 核心回答：**
Spring AOP默认策略：**如果目标类实现了接口，用JDK动态代理；否则用CGLIB**。但Spring Boot 2.x之后，默认都改成CGLIB了。

**📦 实际例子：**

```java
// 场景：你有一个UserService接口和实现类
public interface UserService {
    User getUser(Long id);
}

@Service
public class UserServiceImpl implements UserService {
    @Override
    public User getUser(Long id) {
        return userDao.findById(id);
    }
}

// AOP切面
@Aspect
@Component
public class CacheAspect {
    @Around("execution(* com.example.service.*.*(..))")
    public Object cache(ProceedingJoinPoint pjp) throws Throwable {
        // 缓存逻辑...
        return pjp.proceed();
    }
}
```

**两种代理的区别：**

```java
// JDK动态代理：基于接口
// 原理：在运行时生成一个实现了相同接口的新类
// 要求：目标类必须实现接口
proxy.getClass().getInterfaces();  
// → [UserService.class]  代理对象实现了UserService接口

// 生成的代理类长这样（伪代码）：
public class $Proxy implements UserService {
    private InvocationHandler handler;
    
    @Override
    public User getUser(Long id) {
        // 前置处理（AOP逻辑）
        handler.before();
        // 调用真实对象
        User result = (User) handler.invoke(realObject, method, args);
        // 后置处理
        handler.after();
        return result;
    }
}

// CGLIB代理：基于继承
// 原理：在运行时生成目标类的子类
// 要求：目标类不能是final
proxy.getClass().getSuperclass();
// → UserServiceImpl.class  代理对象是UserServiceImpl的子类

// 生成的代理类长这样（伪代码）：
public class UserServiceImpl$$EnhancerByCGLIB extends UserServiceImpl {
    @Override
    public User getUser(Long id) {
        // 前置处理
        interceptor.before();
        // 调用父类方法
        User result = super.getUser(id);
        // 后置处理
        interceptor.after();
        return result;
    }
}
```

| 对比维度 | JDK动态代理 | CGLIB |
|---------|-----------|-------|
| 原理 | 实现接口 | 继承目标类 |
| 要求 | 必须有接口 | 不能是final类/method |
| 性能 | 创建快，调用慢（反射） | 创建慢，调用快（FastClass） |
| Spring Boot 2.x+默认 | ❌ | ✅ |

**⚠️ 常见坑/加分回答：**
- 加分回答：Spring Boot 2.0开始，`spring.aop.proxy-target-class`默认改为`true`，统一使用CGLIB。所以即使你的Bean实现了接口，默认也用CGLIB代理。
- 坑：如果目标类或方法是`final`的，CGLIB无法创建子类代理，AOP会**静默失效**（不报错但不生效）。
- 坑：`private`方法不会被代理！因为CGLIB是继承，子类无法override父类的private方法。
- 面试加分：可以说说Spring选择代理的策略源码——`AopProxyFactory.createAopProxy()`方法。

### 第10集：AOP在项目里到底怎么用？给我看代码

**🎯 面试官问法：**
> "你项目里AOP用来做什么？能给我讲讲具体实现吗？"

**💡 核心回答：**
AOP最常见的三个应用场景：**操作日志记录**、**接口权限校验**、**接口耗时监控**。

**📦 实际例子1：操作日志（电商后台最常见）**

```java
// 自定义注解，标记需要记录日志的接口
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface OperationLog {
    String module() default "";      // 模块名
    String operation() default "";   // 操作类型
}

// Controller中使用
@RestController
@RequestMapping("/api/product")
public class ProductController {
    
    @OperationLog(module = "商品管理", operation = "新增商品")
    @PostMapping
    public Result addProduct(@RequestBody ProductDTO dto) {
        productService.add(dto);
        return Result.ok();
    }
    
    @OperationLog(module = "商品管理", operation = "删除商品")
    @DeleteMapping("/{id}")
    public Result deleteProduct(@PathVariable Long id) {
        productService.delete(id);
        return Result.ok();
    }
}

// AOP切面：自动记录操作日志
@Aspect
@Component
public class OperationLogAspect {
    
    @Autowired
    private OperationLogMapper logMapper;
    
    // 切点：所有标注了@OperationLog的方法
    @Around("@annotation(operationLog)")
    public Object recordLog(OperationLog operationLog, ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        
        // 执行原方法
        Object result = pjp.proceed();
        
        // 组装日志对象
        com.example.entity.OperationLog log = new com.example.entity.OperationLog();
        log.setModule(operationLog.module());
        log.setOperation(operationLog.operation());
        log.setMethod(pjp.getSignature().getName());
        log.setParams(Arrays.toString(pjp.getArgs()));
        log.setCost(System.currentTimeMillis() - start);
        log.setOperator(SecurityUtils.getCurrentUsername());
        log.setIp(RequestContextHolder.getRequestIP());
        log.setCreateTime(LocalDateTime.now());
        
        // 异步保存日志，不影响业务响应速度
        CompletableFuture.runAsync(() -> logMapper.insert(log));
        
        return result;
    }
}
```

**📦 实际例子2：接口耗时监控**

```java
@Aspect
@Component
public class PerformanceAspect {
    
    // 监控所有Controller接口
    @Around("@within(org.springframework.web.bind.annotation.RestController)")
    public Object monitorPerformance(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        String api = pjp.getSignature().toShortString();
        
        try {
            Object result = pjp.proceed();
            long cost = System.currentTimeMillis() - start;
            
            // 超过1秒的慢接口，打印告警
            if (cost > 1000) {
                log.warn("⚠️ 慢接口告警：{} 耗时 {}ms，参数：{}", 
                    api, cost, Arrays.toString(pjp.getArgs()));
            }
            
            // 推送到监控系统（如Prometheus）
            metrics.recordApiLatency(api, cost);
            
            return result;
        } catch (Throwable e) {
            long cost = System.currentTimeMillis() - start;
            log.error("❌ 接口异常：{} 耗时 {}ms", api, cost, e);
            throw e;
        }
    }
}
```

**📦 实际例子3：接口权限校验**

```java
// 自定义权限注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequirePermission {
    String value();  // 权限标识，如 "order:delete"
}

@RestController
public class OrderController {
    
    @RequirePermission("order:delete")
    @DeleteMapping("/{id}")
    public Result deleteOrder(@PathVariable Long id) {
        orderService.delete(id);
        return Result.ok();
    }
}

@Aspect
@Component
public class PermissionAspect {
    
    @Before("@annotation(perm)")
    public void checkPermission(RequirePermission perm) {
        String requiredPerm = perm.value();
        User currentUser = SecurityUtils.getCurrentUser();
        
        if (!currentUser.hasPermission(requiredPerm)) {
            throw new ForbiddenException("没有权限：" + requiredPerm);
        }
    }
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：`@Around`比`@Before`更常用，因为它可以**控制是否执行原方法**（比如权限校验失败直接抛异常，不需要执行原方法），还能**修改返回值**。
- 坑：同一个类内部方法调用，AOP不会生效！因为AOP基于代理，内部调用走的是`this`而不是代理对象。
- 坑：AOP切面的执行顺序默认不确定，多个切面时可以用`@Order`注解控制优先级。

### 第11集：@Transactional的7种传播行为，一张图记住

**🎯 面试官问法：**
> "Spring事务传播行为有几种？分别什么含义？"

**💡 核心回答：**
7种传播行为，核心记住3个常用的，再知道其他4个的含义就够了。

**📦 实际例子——电商下单场景：**

```java
@Service
public class OrderService {
    @Autowired private StockService stockService;
    @Autowired private PayService payService;
    @Autowired private LogService logService;
    
    // 下单：扣库存 → 创建订单 → 扣款 → 记日志
    @Transactional(propagation = Propagation.REQUIRED)  // 默认值
    public void createOrder(OrderDTO dto) {
        stockService.deductStock(dto.getSkuId(), dto.getQty());  // 加入当前事务
        orderDao.save(buildOrder(dto));                            // 加入当前事务
        payService.deductBalance(dto.getUserId(), dto.getAmount()); // 加入当前事务
        logService.recordOrderLog(dto);                            // 看传播行为设置
    }
}
```

**7种传播行为速查表：**

| 传播行为 | 含义 | 用下单场景举例 | 常用？ |
|---------|------|-------------|-------|
| **REQUIRED** | 有事务就加入，没有就新建 | 扣库存：加入下单事务，一起回滚 | ⭐⭐⭐ |
| **REQUIRES_NEW** | 不管有没有，都新建一个事务 | 记操作日志：不管下单成功失败，日志都要保存 | ⭐⭐ |
| **NESTED** | 有事务就嵌套（子事务），没有就新建 | 扣优惠券：如果扣券失败只回滚扣券，不影响下单 | ⭐⭐ |
| SUPPORTS | 有事务就加入，没有就非事务运行 | 查询订单详情：有事就跟着事务，没事就直接查 | ⭐ |
| NOT_SUPPORTED | 以非事务方式运行，有事务就挂起 | 发送通知邮件：不受事务影响 | ⭐ |
| MANDATORY | 必须在事务中运行，否则抛异常 | 转账操作：必须在某个事务上下文中 | 罕见 |
| NEVER | 以非事务方式运行，有事务就抛异常 | 审计日志写入：明确不允许在事务中 | 罕见 |

**重点理解三个关键区别：**

```java
// 场景：下单扣优惠券
@Service
public class CouponService {
    
    // REQUIRED：如果下单事务回滚了，优惠券也回滚（一起失败）
    @Transactional(propagation = Propagation.REQUIRED)
    public void useCoupon(Long userId, Long couponId) {
        couponDao.markUsed(couponId);
    }
    
    // REQUIRES_NEW：独立事务，下单回滚不影响优惠券的使用记录
    // 但注意：如果外层事务回滚，这个独立事务不会回滚
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordCouponUsage(Long userId, Long couponId) {
        couponUsageLogDao.save(userId, couponId);
    }
    
    // NESTED：嵌套事务，扣券失败只回滚扣券操作，下单可以继续
    @Transactional(propagation = Propagation.NESTED)
    public void tryUseCoupon(Long userId, Long couponId) {
        try {
            couponDao.markUsed(couponId);
        } catch (Exception e) {
            // 只回滚markUsed，不影响外层事务
            log.info("扣券失败，继续下单流程");
        }
    }
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：NESTED底层依赖数据库的savepoint（保存点）机制，不是所有数据库都支持。MySQL InnoDB支持，但有些不支持。
- 加分回答：REQUIRES_NEW会挂起外层事务，开一个新的数据库连接。如果连接池不够，可能导致线程等待甚至死锁。
- 坑：`@Transactional`默认只在抛出`RuntimeException`和`Error`时回滚，**checked异常（如IOException）不会回滚**！需要`@Transactional(rollbackFor = Exception.class)`。

### 第12集：@Transactional失效的6种场景，你中了几个？

**🎯 面试官问法：**
> "@Transactional什么时候会失效？你能说出几种情况？"

**💡 核心回答：**
6种经典失效场景，**自调用**和**异常类型错误**是最常踩的两个坑。

**📦 实际例子：**

```java
@Service
public class OrderService {
    @Autowired private OrderDao orderDao;
    @Autowired private StockService stockService;
    
    // ❌ 场景1：方法不是public的
    @Transactional
    private void createOrder(OrderDTO dto) {  // private！事务不生效！
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
    }
    // Spring AOP代理无法拦截private方法，事务直接无效
    
    // ❌ 场景2：同类自调用（最隐蔽的坑！）
    public void placeOrder(OrderDTO dto) {
        // 这里调用createOrder，虽然createOrder有@Transactional，但不生效！
        createOrderPublic(dto);
    }
    
    @Transactional
    public void createOrderPublic(OrderDTO dto) {
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
    }
    // 原因：placeOrder()通过代理调用，但内部createOrderPublic()
    // 是通过this调用的，走的是真实对象而不是代理对象！
    
    // ❌ 场景3：异常被try-catch吞了
    @Transactional
    public void createOrder(OrderDTO dto) {
        try {
            orderDao.save(buildOrder(dto));
            stockService.deductStock(dto.getSkuId(), dto.getQty()); // 这里抛异常
        } catch (Exception e) {
            log.error("下单失败", e);
            // 异常被吞了！Spring以为执行成功，不会回滚！
        }
    }
    
    // ❌ 场景4：rollbackFor没设置，抛了checked异常
    @Transactional
    public void importOrders(MultipartFile file) throws Exception {
        // 如果抛出IOException（checked异常），默认不回滚！
        parseAndSave(file);
    }
    // 解决：@Transactional(rollbackFor = Exception.class)
    
    // ❌ 场景5：数据库引擎不支持事务
    // MySQL的MyISAM引擎不支持事务！
    // 如果表用的是MyISAM，@Transactional完全无效
    
    // ❌ 场景6：传播行为设置错误
    @Transactional(propagation = Propagation.NOT_SUPPORTED)
    public void createOrder(OrderDTO dto) {
        // NOT_SUPPORTED意味着"以非事务方式运行"
        // 事务根本没开！
    }
}
```

**✅ 正确写法：**

```java
@Service
public class OrderService {
    
    @Transactional(rollbackFor = Exception.class)  // 指定回滚异常
    public void createOrder(OrderDTO dto) {
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
        // 如果抛异常，不要catch，让它抛出去！
        // 如果必须catch，catch后要重新throw
    }
}
```

| 失效场景 | 原因 | 解决方案 |
|---------|------|---------|
| 非public方法 | AOP无法拦截 | 改成public |
| 同类自调用 | 走this不走代理 | 抽到另一个类/注入自己/@Lookup |
| 异常被catch吞掉 | Spring感知不到异常 | 不catch或catch后rethrow |
| 抛checked异常 | 默认只回滚RuntimeException | `rollbackFor = Exception.class` |
| 数据库不支持事务 | MyISAM不支持 | 改用InnoDB |
| 传播行为错误 | NOT_SUPPORTED等 | 检查传播行为配置 |

**⚠️ 常见坑/加分回答：**
- 加分回答：可以提到Spring事务的底层原理——通过`TransactionInterceptor`（AOP拦截器）在方法执行前开启事务，执行后根据是否异常决定commit或rollback。
- 加分回答：自调用的问题本质上是因为Spring AOP是基于代理的，`this.method()`绕过了代理对象。

### 第13集：同一个类里事务失效，怎么解决？

**🎯 面试官问法：**
> "同一个类中A方法调B方法，B上有@Transactional但不生效，怎么解决？"

**💡 核心回答：**
三种方案，推荐程度从高到低：**抽到另一个类** > **注入自己** > **AopContext.currentProxy()**。

**📦 实际例子：**

```java
@Service
public class OrderService {
    @Autowired private OrderDao orderDao;
    @Autowired private StockService stockService;
    @Autowired private MessageService messageService;
    
    // 下单主流程
    public void placeOrder(OrderDTO dto) {
        // 1. 校验库存
        checkStock(dto);
        // 2. 创建订单（需要事务）
        doCreateOrder(dto);  // ❌ 自调用，事务不生效！
        // 3. 发送通知（不需要事务）
        messageService.sendNotification(dto.getUserId(), "下单成功");
    }
    
    @Transactional(rollbackFor = Exception.class)
    public void doCreateOrder(OrderDTO dto) {
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
    }
}
```

**三种解决方案：**

```java
// ✅ 方案1（推荐）：把事务方法抽到另一个类
@Service
public class OrderCommandService {
    @Autowired private OrderDao orderDao;
    @Autowired private StockService stockService;
    
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(OrderDTO dto) {
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
    }
}

@Service
public class OrderService {
    @Autowired private OrderCommandService orderCommandService;
    @Autowired private MessageService messageService;
    
    public void placeOrder(OrderDTO dto) {
        checkStock(dto);
        orderCommandService.createOrder(dto);  // ✅ 通过代理调用，事务生效
        messageService.sendNotification(dto.getUserId(), "下单成功");
    }
}

// ✅ 方案2：注入自己（简单但有点hack）
@Service
public class OrderService {
    @Autowired
    private OrderService self;  // 注入自己！
    
    public void placeOrder(OrderDTO dto) {
        checkStock(dto);
        self.doCreateOrder(dto);  // ✅ 通过代理调用
        messageService.sendNotification(dto.getUserId(), "下单成功");
    }
    
    @Transactional(rollbackFor = Exception.class)
    public void doCreateOrder(OrderDTO dto) {
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
    }
}

// ✅ 方案3：AopContext.currentProxy()
@Service
public class OrderService {
    
    public void placeOrder(OrderDTO dto) {
        checkStock(dto);
        // 获取当前代理对象
        OrderService proxy = (OrderService) AopContext.currentProxy();
        proxy.doCreateOrder(dto);  // ✅ 通过代理调用
    }
    
    @Transactional(rollbackFor = Exception.class)
    public void doCreateOrder(OrderDTO dto) {
        orderDao.save(buildOrder(dto));
        stockService.deductStock(dto.getSkuId(), dto.getQty());
    }
}
// 注意：需要配置 @EnableAspectJAutoProxy(exposeProxy = true)
```

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|-------|
| 抽到另一个类 | 最干净，符合单一职责 | 多一个类 | ⭐⭐⭐ |
| 注入自己 | 改动最小 | 代码不够直观，循环依赖 | ⭐⭐ |
| AopContext | 不需要额外类 | 强耦合Spring API，需开启配置 | ⭐ |

**⚠️ 常见坑/加分回答：**
- 加分回答：Spring官方推荐方案1（抽到另一个类），因为它符合"单一职责"的设计原则。事务方法本身就是一个独立的业务单元，应该独立成一个类。
- 加分回答：方案2（注入自己）在Spring Boot 2.6+需要开启循环依赖支持，否则启动报错。
- 坑：方案3需要`exposeProxy=true`，这个配置在生产环境要谨慎开启，因为会带来额外的性能开销。

### 第14集：分布式事务，为什么@Transactional不够用了？

**🎯 面试官问法：**
> "微服务架构下，跨两个数据库的事务怎么保证一致性？@Transactional为什么不行？"

**💡 核心回答：**
`@Transactional`只管**一个数据库连接**的事务。微服务里，订单服务一个数据库，库存服务一个数据库，两个服务通过HTTP/RPC调用——这已经是两个独立的数据库连接了，本地事务管不了。

**📦 实际例子：**

```java
// 单体时代：一个@Transactional搞定
@Service
public class OrderService {
    @Transactional
    public void createOrder(OrderDTO dto) {
        orderDao.save(order);           // 同一个数据库
        stockDao.deduct(skuId, qty);    // 同一个数据库，同一个事务
        accountDao.deduct(userId, money); // 同一个数据库，同一个事务
        // 任何一步失败，全部回滚 ✅
    }
}

// 微服务时代：三个服务，三个数据库
@Service
public class OrderService {
    @Autowired private StockFeignClient stockClient;   // HTTP调用库存服务
    @Autowired private AccountFeignClient accountClient; // HTTP调用账户服务
    
    @Transactional  // 只管order表！
    public void createOrder(OrderDTO dto) {
        orderDao.save(order);  // ✅ 在本地事务中
        
        stockClient.deduct(skuId, qty);  // ❌ HTTP调用，不在本地事务中！
        // 如果这里成功了，但下面失败了...
        
        accountClient.deduct(userId, money);  // ❌ 如果这里抛异常...
        // 本地事务回滚了order，但库存已经扣了！数据不一致！
    }
}
```

**四种分布式事务方案：**

```
方案1：2PC（两阶段提交）—— 强一致，但性能差
┌──────────┐   阶段1: prepare   ┌──────────┐
│ 订单服务  │ ──────────────────→ │ 库存服务  │
│ (协调者)  | ←────────────────── | (参与者)  │
│          |   阶段2: commit     |          │
│          | ──────────────────→ |          │
└──────────┘ ←────────────────── └──────────┘
问题：所有参与者在阶段1都要锁定资源等待，性能极差

方案2：TCC（Try-Confirm-Cancel）—— 业务层面实现
Try：     预扣库存（冻结100件，不是真的扣）
Confirm： 确认扣库存（把冻结的100件正式扣掉）
Cancel：  取消冻结（释放冻结的100件）

方案3：Saga —— 长事务拆成多个本地事务
下单 → 扣库存 → 扣款
如果扣款失败：反向补偿 → 还库存 → 取消订单

方案4：消息最终一致性（最常用）
下单 → 发MQ消息 → 库存服务消费消息扣库存
如果消费失败 → 重试 → 重试N次还失败 → 人工介入
```

| 方案 | 一致性 | 性能 | 实现难度 | 适用场景 |
|------|-------|------|---------|---------|
| 2PC | 强一致 | ❌ 差 | 中 | 银行转账等金融场景 |
| TCC | 最终一致 | ✅ 好 | 高（每个接口要写3个方法） | 电商下单、资金操作 |
| Saga | 最终一致 | ✅ 好 | 中 | 长流程业务编排 |
| 消息最终一致 | 最终一致 | ✅ 最好 | 低 | 大部分业务场景 |

**⚠️ 常见坑/加分回答：**
- 加分回答：实际项目中，**消息最终一致性**用得最多。核心是：本地事务+MQ消息表，保证"业务操作"和"发消息"的原子性（本地事务表方案）。
- 加分回答：Seata是阿里开源的分布式事务框架，支持AT（自动补偿）、TCC、Saga、XA四种模式。AT模式对业务代码零侵入。
- 坑：消息最终一致性不是"强一致"，在消息还没消费完的时间窗口内，数据是不一致的。业务上要能接受这种"短暂不一致"。

### 第15集：@SpringBootApplication到底做了哪三件事？

**🎯 面试官问法：**
> "@SpringBootApplication这个注解底层做了什么？"

**💡 核心回答：**
它是一个组合注解，做了三件事：**组件扫描** + **自动配置** + **标记配置类**。

**📦 实际例子：**

```java
// 你每天写的启动类
@SpringBootApplication
public class MallApplication {
    public static void main(String[] args) {
        SpringApplication.run(MallApplication.class, args);
    }
}

// 展开来看，@SpringBootApplication = 三个注解
@SpringBootConfiguration    // = @Configuration，标记这是一个配置类
@EnableAutoConfiguration    // 开启自动配置（Spring Boot的灵魂）
@ComponentScan              // 组件扫描（扫描当前包及子包）
```

**三个注解分别干什么：**

```java
// 1. @ComponentScan：扫描你写的Bean
// 默认扫描启动类所在包及其子包
// 启动类在 com.example.mall 包下
// → 扫描 com.example.mall.controller
// → 扫描 com.example.mall.service
// → 扫描 com.example.mall.dao
// → ... 所有带@Component/@Service/@Controller的类都会被注册

// 如果你的包名写错了，Bean就扫不到！
// com.example.mall          ← 启动类在这里
// com.example.mall.controller ← 能扫到 ✅
// com.other.controller      ← 扫不到 ❌

// 2. @EnableAutoConfiguration：自动配置第三方组件
// 你引入了spring-boot-starter-web
// → 自动配置Tomcat、Spring MVC、Jackson...
// 你引入了spring-boot-starter-data-redis
// → 自动配置RedisTemplate、Lettuce连接池...
// 不需要你手动写任何配置代码！

// 3. @Configuration：标记为配置类
// 告诉Spring这个类里可能有@Bean方法来创建Bean
```

**⚠️ 常见坑/加分回答：**
- 加分回答：`@SpringBootConfiguration`和`@Configuration`的区别是，它限制了每个Spring Boot应用只能有一个`@SpringBootConfiguration`，通常就是启动类。
- 加分回答：`@ComponentScan`可以通过`excludeFilters`排除某些类，比如`@ComponentScan(excludeFilters = @Filter(type = FilterType.REGEX, pattern = ".*Test.*"))`。
- 坑：新手常犯的错误是把启动类放错包层级，导致Service、Controller扫不到，报`NoSuchBeanDefinitionException`。

### 第16集：Spring Boot自动配置原理，一张图讲透

**🎯 面试官问法：**
> "Spring Boot自动配置的原理是什么？为什么引入一个starter就能自动配好？"

**💡 核心回答：**
自动配置的核心是：**Spring Boot启动时，读取`spring.factories`（或`AutoConfiguration.imports`）文件中列出的所有配置类，通过条件注解判断是否满足条件，满足的就加载，不满足就跳过。**

**📦 实际例子——以Redis自动配置为例：**

```java
// 你只需要做两件事：
// 1. pom.xml引入starter
// <dependency>
//     <groupId>org.springframework.boot</groupId>
//     <artifactId>spring-boot-starter-data-redis</artifactId>
// </dependency>

// 2. application.yml配置连接信息
// spring:
//   redis:
//     host: 127.0.0.1
//     port: 6379

// 然后RedisTemplate就直接能用了！
@Autowired
private RedisTemplate<String, Object> redisTemplate;

// 这背后发生了什么？
```

**自动配置流程图：**

```
1. Spring Boot启动
   ↓
2. 加载 META-INF/spring.factories（Spring Boot 2.x）
   或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（3.x）
   ↓
3. 找到所有自动配置类，例如：
   - RedisAutoConfiguration
   - DataSourceAutoConfiguration  
   - MvcAutoConfiguration
   - ... 100多个
   ↓
4. 条件过滤（关键！）：
   RedisAutoConfiguration 上面标注了：
   
   @AutoConfiguration
   @ConditionalOnClass(RedisOperations.class)     // classpath下有redis的类？
   @EnableConfigurationProperties(RedisProperties.class)  // 读取application.yml配置
   
   → 条件满足 → 加载这个配置类 → 创建RedisTemplate Bean
   → 条件不满足 → 跳过（比如你没引入redis依赖，就不会配Redis）
   
5. RedisAutoConfiguration 内部：
   @Bean
   @ConditionalOnMissingBean   // 如果用户没自定义，才创建默认的
   public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
       RedisTemplate<String, Object> template = new RedisTemplate<>();
       template.setConnectionFactory(factory);
       template.setKeySerializer(new StringRedisSerializer());
       template.setValueSerializer(new GenericJackson2JsonRedisSerializer());
       return template;
   }
```

**核心条件注解速查：**

| 条件注解 | 含义 | 示例 |
|---------|------|------|
| @ConditionalOnClass | classpath下有某个类才生效 | 有Redis类 → 配Redis |
| @ConditionalOnMissingClass | classpath下没有某个类才生效 | 没有HikariCP → 用Tomcat连接池 |
| @ConditionalOnBean | 容器里有某个Bean才生效 | 有DataSource → 配JdbcTemplate |
| @ConditionalOnMissingBean | 容器里没有某个Bean才生效 | 用户没自定义RedisTemplate → 创建默认 |
| @ConditionalOnProperty | 配置文件有某个属性才生效 | server.port存在 → 配Web服务器 |

**⚠️ 常见坑/加分回答：**
- 加分回答：Spring Boot 3.x把`spring.factories`改成了`AutoConfiguration.imports`文件，一行一个配置类名，更简洁。
- 加分回答：`@ConditionalOnMissingBean`是一个很重要的设计——它意味着"框架提供默认实现，但用户可以自定义覆盖"。这就是Spring Boot的"约定优于配置"理念。
- 坑：如果你自己定义了一个`RedisTemplate`的Bean，Spring Boot就不会创建默认的了。有时候你想在默认基础上改一点配置，结果发现整个默认配置被覆盖了。

### 第17集：Spring Boot Starter是什么？为什么不直接引依赖？

**🎯 面试官问法：**
> "Starter和普通依赖有什么区别？为什么不直接引spring-mvc、jackson这些依赖？"

**💡 核心回答：**
Starter是一个**依赖聚合器+自动配置**的组合。它不仅帮你引入一堆依赖，还自动帮你配好这些组件。

**📦 实际例子：**

```xml
<!-- 你写了一行starter -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<!-- 它实际帮你引入了这些（用mvn dependency:tree查看） -->
spring-boot-starter-web
├── spring-boot-starter
│   ├── spring-boot（核心）
│   ├── spring-boot-autoconfigure（自动配置）
│   └── spring-boot-starter-logging（日志：Logback）
├── spring-webmvc（Spring MVC框架）
├── spring-boot-starter-tomcat（内嵌Tomcat）
├── spring-boot-starter-json（Jackson JSON处理）
├── hibernate-validator（参数校验）
└── ...
```

**如果不引Starter，你要自己写：**

```xml
<!-- 手动引入10多个依赖 -->
<dependency>spring-webmvc</dependency>
<dependency>spring-boot-starter-tomcat</dependency>
<dependency>jackson-databind</dependency>
<dependency>hibernate-validator</dependency>
<dependency>spring-boot-starter-logging</dependency>
<!-- ... 还有很多 -->
<!-- 而且你还要自己写自动配置类，配好每个组件 -->
```

**自定义Starter——以短信服务为例：**

```java
// 1. 配置属性类
@ConfigurationProperties(prefix = "sms")
public class SmsProperties {
    private String appId;
    private String appSecret;
    private String signName;
    // getter/setter...
}

// 2. 核心服务类
public class SmsService {
    private final SmsProperties properties;
    
    public SmsService(SmsProperties properties) {
        this.properties = properties;
    }
    
    public boolean send(String phone, String content) {
        // 调用第三方短信API
        // 使用 properties.getAppId() 等配置
        return httpClient.send(phone, content, properties);
    }
}

// 3. 自动配置类
@AutoConfiguration
@ConditionalOnClass(SmsService.class)
@EnableConfigurationProperties(SmsProperties.class)
public class SmsAutoConfiguration {
    
    @Bean
    @ConditionalOnMissingBean
    @ConditionalOnProperty(prefix = "sms", name = "app-id")
    public SmsService smsService(SmsProperties properties) {
        return new SmsService(properties);
    }
}

// 4. 注册自动配置
// META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
// com.example.sms.SmsAutoConfiguration

// 5. 打包发布后，其他人只需：
// pom.xml引入你的starter
// <dependency>
//     <groupId>com.example</groupId>
//     <artifactId>sms-spring-boot-starter</artifactId>
//     <version>1.0.0</version>
// </dependency>
// 
// application.yml配置
// sms:
//   app-id: xxx
//   app-secret: yyy
//   sign-name: 我的商城
//
// 然后直接@Autowired SmsService就能用了！
```

**⚠️ 常见坑/加分回答：**
- 加分回答：Starter的命名规范——官方的叫`spring-boot-starter-xxx`，第三方的叫`xxx-spring-boot-starter`（前缀不同）。
- 加分回答：自定义Starter通常分两个模块：`xxx-spring-boot-autoconfigure`（自动配置逻辑）和`xxx-spring-boot-starter`（只包含依赖，不含代码），方便用户按需引入。
- 坑：Starter中的自动配置类要注意执行顺序，用`@AutoConfigureBefore`/`@AutoConfigureAfter`控制。

### 第18集：Spring Boot启动流程，12步速记法

**🎯 面试官问法：**
> "Spring Boot启动时做了什么？说说启动流程。"

**💡 核心回答：**
Spring Boot的启动流程核心分两大阶段：**创建ApplicationContext** 和 **刷新ApplicationContext**。

**📦 启动流程12步速查表：**

```
步骤  操作                          关键事件
─────────────────────────────────────────────────────
1    创建SpringApplication对象      加载主启动类、判断Web类型、加载ApplicationContextInitializer
2    运行run()方法                   
3    创建BootstrapContext           （Spring Boot 2.4+）
4    获取并启动ApplicationListener   发布ApplicationStartingEvent
5    解析命令行参数                  
6    推断并设置WebApplicationType    SERVLET/REACTIVE/NONE
7    创建ApplicationContext          AnnotationConfigServletWebServerApplicationContext
8    准备Context（prepareContext）   执行Initializer、注册BeanDefinition
9    刷新Context（refreshContext）    ★ 核心步骤：创建Bean、自动配置、启动内嵌Tomcat ★
10   刷新后回调（afterRefresh）      可扩展的钩子
11   发布ApplicationStartedEvent    应用已启动
12   发布ApplicationReadyEvent      ★ 应用完全就绪，可以接收请求 ★
```

**关键步骤详解——Tomcat在哪一步启动：**

```java
// 在第9步 refreshContext() 中：
// → AbstractApplicationContext.refresh()
//   → onRefresh()  ← 子类实现
//     → ServletWebServerApplicationContext.onRefresh()
//       → createWebServer()  ← ★ Tomcat在这里启动！
//         → TomcatServletWebServerFactory.getWebServer()
//           → 创建Tomcat实例
//           → 配置端口、Connector
//           → 添加Servlet（DispatcherServlet）
//           → tomcat.start()  ← Tomcat启动！

// 所以答案是：Tomcat在refresh()阶段的onRefresh()回调中启动
// 大约是整个启动流程的60%-70%处
```

**一个实际场景：启动时初始化数据缓存**

```java
// 方式1：CommandLineRunner（在第11步之后执行）
@Component
public class DataCacheInitializer implements CommandLineRunner {
    @Autowired
    private ProductDao productDao;
    
    @Override
    public void run(String... args) {
        // 启动时加载商品分类到Redis缓存
        List<Category> categories = productDao.findAllCategories();
        redisTemplate.opsForHash().putAll("categories", toMap(categories));
        System.out.println("✅ 商品分类缓存初始化完成");
    }
}

// 方式2：ApplicationRunner（同上，但参数是ApplicationArguments）
// 方式3：@EventListener(ApplicationReadyEvent.class)（推荐）
@Component
public class StartupListener {
    
    @EventListener(ApplicationReadyEvent.class)
    public void onApplicationReady() {
        // 应用完全就绪后执行
        log.info("应用启动完成，开始预热缓存...");
        warmUpCache();
    }
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：ApplicationStartingEvent在环境准备之前发布，ApplicationStartedEvent在Context刷新之后发布，ApplicationReadyEvent在最后发布。如果要在启动完成后执行初始化逻辑，用ApplicationReadyEvent。
- 加分回答：`ApplicationStartup`接口可以记录每个步骤的耗时，用于性能分析。Spring Boot Actuator的`/actuator/startup`端点可以查看启动耗时。
- 坑：`CommandLineRunner`里如果有耗时操作（如大量数据加载），会阻塞启动。可以改为异步执行。

### 第19集：application.yml和application.properties有什么区别？

**🎯 面试官问法：**
> "yml和properties两种配置格式有什么区别？优先级怎么算？多环境配置怎么做？"

**💡 核心回答：**
功能上基本等价，yml支持层级结构和多文档，properties更简单直接。同一位置yml优先级高于properties。

**📦 实际例子：**

```properties
# application.properties — 扁平结构
spring.datasource.url=jdbc:mysql://localhost:3306/mall
spring.datasource.username=root
spring.datasource.password=123456
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
spring.redis.host=127.0.0.1
spring.redis.port=6379
server.port=8080
```

```yaml
# application.yml — 层级结构，更直观
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mall
    username: root
    password: 123456
    driver-class-name: com.mysql.cj.jdbc.Driver
  redis:
    host: 127.0.0.1
    port: 6379
server:
  port: 8080
```

| 对比维度 | properties | yml |
|---------|-----------|-----|
| 层级结构 | ❌ 不支持 | ✅ 用缩进表示 |
| 可读性 | 配置多时难维护 | 清晰直观 |
| 注释 | ✅ 支持# | ✅ 支持# |
| 多文档 | ❌ | ✅ 用---分隔 |
| 特殊字符 | 直接写 | 注意空格和冒号 |
| 中文支持 | 需要unicode转义或设置编码 | 直接支持UTF-8 |
| @PropertySource | ✅ 支持 | ❌ 不支持（只支持properties） |

**配置加载优先级（从高到低）：**

```
1. 命令行参数      java -jar app.jar --server.port=9090
2. 系统环境变量    SERVER_PORT=9090
3. JVM系统属性    -Dserver.port=9090
4. application-{profile}.yml   application-prod.yml
5. application.yml              application.yml
6. @PropertySource注解          代码中的配置
```

### 第20集：一个请求从浏览器到返回JSON，经历了什么？

**🎯 面试官问法：**
> "用户在浏览器访问你的商品列表接口，从请求发出到收到JSON响应，中间经过了哪些步骤？"

**💡 核心回答：**
核心经过**DispatcherServlet**（前置控制器）分发，经过HandlerMapping找到Controller，通过HandlerAdapter执行方法，最后通过HttpMessageConverter转成JSON返回。

**📦 实际例子：**

```
用户在浏览器访问：GET /api/products?page=1&size=10

完整流程：

浏览器  →  Tomcat  →  DispatcherServlet  →  HandlerMapping  →  Controller  →  Service  →  DAO  →  DB
                                                                              ↓
浏览器  ←  Tomcat  ←  DispatcherServlet  ←  HttpMessageConverter  ←  List<Product>
```

**逐步拆解：**

```java
// 第1步：请求到达Tomcat，转发给DispatcherServlet
// Tomcat是Servlet容器，所有HTTP请求先到DispatcherServlet

// 第2步：DispatcherServlet调用HandlerMapping
// HandlerMapping根据URL找到对应的Controller方法
// RequestMappingHandlerMapping：
//   GET /api/products → ProductController.listProducts()

// 第3步：DispatcherServlet调用HandlerAdapter执行Controller方法
// 中间经过：
//   ① 拦截器preHandle()（如果有的话，比如登录检查）
//   ② 参数解析（@RequestParam、@RequestBody、@PathVariable等）
//   ③ 参数校验（@Valid / @Validated）
//   ④ 执行Controller方法
//   ⑤ 拦截器postHandle()

// 第4步：Controller返回结果
@RestController
@RequestMapping("/api/products")
public class ProductController {
    @Autowired
    private ProductService productService;
    
    @GetMapping
    public Result<List<ProductVO>> listProducts(
            @RequestParam(defaultValue = "1") int page,
            @RequestParam(defaultValue = "10") int size) {
        
        List<ProductVO> products = productService.listProducts(page, size);
        return Result.ok(products);  // 返回Result对象
    }
}

// 第5步：HttpMessageConverter把对象转成JSON
// MappingJackson2HttpMessageConverter：
//   Result<List<ProductVO>> → JSON字符串
//   设置Content-Type: application/json
//   写入HTTP响应体

// 第6步：响应返回给浏览器
// {
//   "code": 200,
//   "data": [
//     {"id": 1, "name": "iPhone 15", "price": 5999},
//     {"id": 2, "name": "MacBook Pro", "price": 12999}
//   ],
//   "msg": "success"
// }
```

**核心组件速查：**

| 组件 | 职责 | 类比 |
|------|------|------|
| DispatcherServlet | 前置控制器，统一入口 | 公司前台/总机 |
| HandlerMapping | 根据URL找到对应的Controller方法 | 通讯录/查号台 |
| HandlerAdapter | 调用Controller方法，处理参数 | 传话人 |
| HttpMessageConverter | 对象↔JSON互转 | 翻译官 |
| ViewResolver | 视图解析（JSP/Thymeleaf时用到） | 排版师 |

**⚠️ 常见坑/加分回答：**
- 加分回答：DispatcherServlet本身不处理业务逻辑，它只负责"分发"——这就是"前置控制器"模式（Front Controller Pattern），是MVC中C的核心。
- 加分回答：`HandlerInterceptor`（拦截器）在HandlerAdapter执行前后被调用，常用来做登录检查、日志记录、权限校验。和AOP的区别是：拦截器只能用在Controller层，AOP可以用在任何层。
- 坑：`@RequestParam`如果不设`required=false`，默认是必填的。参数缺失会报400错误。

### 第21集：@Controller和@RestController的区别，别再搞混了

**🎯 面试官问法：**
> "@Controller和@RestController有什么区别？@ResponseBody做什么的？"

**💡 核心回答：**
`@RestController = @Controller + @ResponseBody`。加了`@ResponseBody`后，方法返回值直接写到HTTP响应体里（通常是JSON），而不是视图名。

**📦 实际例子：**

```java
// ❌ 只用@Controller：返回值被当作视图名
@Controller
public class ProductController {
    @GetMapping("/products")
    public String listProducts() {
        return "productList";  // Spring去找 productList.jsp 或 productList.html
        // 如果你没有这个视图文件，就报404！
    }
}

// ✅ 用@RestController：返回值直接写成JSON
@RestController
public class ProductController {
    @GetMapping("/api/products")
    public List<Product> listProducts() {
        return productService.list();
        // 直接返回JSON：[{"id":1,"name":"iPhone"...}]
    }
}

// ✅ 或者用@Controller + @ResponseBody（等价于@RestController）
@Controller
@ResponseBody  // 加在类上，所有方法都返回JSON
public class ProductController {
    @GetMapping("/api/products")
    public List<Product> listProducts() {
        return productService.list();
    }
}
```

**底层JSON转换过程：**

```java
// 当用@RestController时，返回值的转换链路：
// Product对象 → MappingJackson2HttpMessageConverter → JSON字符串

// 核心是HttpMessageConverter接口，Spring Boot自动配置了：
// 请求体JSON → Java对象：MappingJackson2HttpMessageConverter.canRead()
// Java对象 → 响应体JSON：MappingJackson2HttpMessageConverter.canWrite()

// 返回null的情况
@RestController
public class ProductController {
    @DeleteMapping("/api/products/{id}")
    public Result<Void> delete(@PathVariable Long id) {
        productService.delete(id);
        return Result.ok();  // data为null
        // 返回：{"code":200, "data":null, "msg":"success"}
    }
}
```

**什么时候用哪个：**

| 场景 | 用哪个 | 原因 |
|------|-------|------|
| REST API接口 | @RestController | 返回JSON给前端/移动端 |
| 页面渲染（JSP/Thymeleaf） | @Controller | 返回视图名 |
| 混合场景 | @Controller + 个别方法加@ResponseBody | 大部分返回视图，个别返回JSON |

**⚠️ 常见坑/加分回答：**
- 加分回答：`@ResponseBody`底层通过`HandlerMethodReturnValueHandler`来处理，不同的返回类型有不同的Handler。`@ResponseBody`标注的方法会用`RequestResponseBodyMethodProcessor`处理。
- 加分回答：返回`ResponseEntity`可以自定义HTTP状态码和响应头：`return ResponseEntity.status(201).header("X-Request-Id", "123").body(result);`
- 坑：如果`@RestController`的方法返回类型是`String`，它不会跳转到页面，而是直接把字符串写到响应体。新手经常在这里踩坑。

### 第22集：Spring常用注解大全，这20个必须记住

**🎯 面试官问法：**
> "Spring常用注解你能说出哪些？@Autowired和@Resource有什么区别？"

**💡 核心回答：**
Spring注解按功能分5大类，每类记住最重要的几个。

**📦 20个核心注解速查表：**

```
一、DI注入类（6个）
──────────────────────────────────────────
@Autowired        按类型自动注入（Spring的）
@Resource         按名称注入（JSR-250标准）
@Inject           按类型注入（JSR-330标准，少用）
@Qualifier        配合@Autowired指定Bean名称
@Value            注入配置文件中的值或常量
@Lazy             延迟注入，用到时才创建

二、组件声明类（4个）
──────────────────────────────────────────
@Component        通用组件
@Service          业务层（语义化，本质=Component）
@Repository       数据访问层（语义化+异常转换）
@Controller       控制层（语义化+支持MVC）

三、配置类（4个）
──────────────────────────────────────────
@Configuration    标记配置类
@Bean             在配置类中声明Bean
@PropertySource   加载外部配置文件
@Import           导入其他配置类

四、MVC类（4个）
──────────────────────────────────────────
@RestController  = @Controller + @ResponseBody
@RequestMapping  映射URL路径
@PathVariable     获取URL路径参数 /users/{id}
@RequestParam     获取查询参数 ?name=xxx

五、其他重要注解（2个）
──────────────────────────────────────────
@Transactional    开启事务
@Async            异步执行方法
```

**@Autowired vs @Resource——经典面试题：**

```java
@Service
public class OrderService {
    
    // @Autowired：Spring的注解，默认按类型匹配
    @Autowired
    private UserService userService;
    // 先按类型找，找到1个→注入
    // 找到多个→按字段名匹配
    // 找不到→报错（除非required=false）
    
    // @Resource：Java标准注解（JSR-250），默认按名称匹配
    @Resource
    private UserService userService;
    // 先按字段名"userService"找Bean名
    // 找到→注入
    // 找不到→按类型匹配
    // 还找不到→报错
    
    // 有多个实现类时的区别：
    // UserService有两个实现：UserServiceImpl、VipUserServiceImpl
    
    @Autowired
    @Qualifier("vipUserServiceImpl")  // 指定用哪个
    private UserService userService;
    
    @Resource(name = "vipUserServiceImpl")  // 直接指定名称
    private UserService userService2;
}
```

| 对比维度 | @Autowired | @Resource |
|---------|-----------|-----------|
| 来源 | Spring | Java标准（JSR-250） |
| 默认策略 | 按类型 | 按名称 |
| 多实现时 | 按字段名再匹配 | 按name属性匹配 |
| 配合使用 | @Qualifier指定 | name属性指定 |
| 构造器注入 | ✅ 支持 | ❌ 不支持 |

**⚠️ 常见坑/加分回答：**
- 加分回答：大厂规范一般推荐用**构造器注入**（不用@Autowired标注，单构造器自动注入），或者用`@Resource`（Java标准，更通用）。
- 加分回答：`@Service`、`@Repository`、`@Controller`本质上都是`@Component`，只是语义化标注。`@Repository`有个额外功能：自动把数据库异常转换为`DataAccessException`。
- 坑：`@Value("${sms.appId}")`从配置文件取值，如果配置项不存在会启动报错。可以设默认值：`@Value("${sms.appId:defaultId}")`。

### 第23集：Spring中如何实现统一返回结果？

**🎯 面试官问法：**
> "你项目里接口返回格式是怎么统一的？异常是怎么统一处理的？"

**💡 核心回答：**
定义一个统一的Result类，配合`@RestControllerAdvice`全局异常处理，保证所有接口返回格式一致。

**📦 实际例子：**

```java
// 1. 统一返回结果类
@Data
public class Result<T> {
    private int code;       // 业务状态码
    private String msg;     // 提示信息
    private T data;         // 数据
    
    public static <T> Result<T> ok(T data) {
        Result<T> result = new Result<>();
        result.setCode(200);
        result.setMsg("success");
        result.setData(data);
        return result;
    }
    
    public static <T> Result<T> fail(int code, String msg) {
        Result<T> result = new Result<>();
        result.setCode(code);
        result.setMsg(msg);
        return result;
    }
}

// 2. 全局异常处理器
@RestControllerAdvice  // = @ControllerAdvice + @ResponseBody
public class GlobalExceptionHandler {
    
    // 自定义业务异常
    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusinessException(BusinessException e) {
        log.warn("业务异常：{}", e.getMessage());
        return Result.fail(e.getCode(), e.getMessage());
        // 返回：{"code":400, "msg":"库存不足", "data":null}
    }
    
    // 参数校验异常
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<?> handleValidationException(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(error -> error.getField() + ": " + error.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return Result.fail(400, "参数校验失败：" + msg);
        // 返回：{"code":400, "msg":"参数校验失败：name: 不能为空; price: 必须大于0"}
    }
    
    // 权限异常
    @ExceptionHandler(AccessDeniedException.class)
    public Result<?> handleAccessDeniedException(AccessDeniedException e) {
        return Result.fail(403, "没有权限访问");
    }
    
    // 兜底：所有未捕获的异常
    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.fail(500, "服务器内部错误");
        // 注意：不要把异常详情返回给前端，只返回通用提示
    }
}

// 3. Controller代码变得非常简洁
@RestController
@RequestMapping("/api/products")
public class ProductController {
    
    @GetMapping("/{id}")
    public Result<ProductVO> getProduct(@PathVariable Long id) {
        ProductVO product = productService.getById(id);
        return Result.ok(product);
        // 返回：{"code":200, "msg":"success", "data":{"id":1,"name":"iPhone"}}
    }
    
    @PostMapping
    public Result<Long> addProduct(@RequestBody @Valid ProductDTO dto) {
        Long id = productService.add(dto);
        return Result.ok(id);
    }
    
    @DeleteMapping("/{id}")
    public Result<Void> deleteProduct(@PathVariable Long id) {
        productService.delete(id);
        return Result.ok(null);
    }
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：`@RestControllerAdvice`的`basePackages`可以指定只对某些包生效：`@RestControllerAdvice(basePackages = "com.example.controller")`。
- 加分回答：异常处理器有优先级，最具体的异常类型优先匹配。`BusinessException`的处理器会优先于`Exception`的处理器。
- 坑：`@ExceptionHandler`只能拦截Controller层抛出的异常。如果异常在Filter或Interceptor中抛出，全局异常处理器**拦截不到**！需要在Filter中单独处理。
- 坑：`@RequestBody`解析JSON失败（如格式错误）抛的是`HttpMessageNotReadableException`，需要单独处理，否则返回500。

### 第24集：Spring中如何实现接口幂等性？

**🎯 面试官问法：**
> "用户重复提交订单怎么办？你怎么保证接口的幂等性？"

**💡 核心回答：**
幂等性就是**同一个请求执行一次和执行多次，结果一样**。常见方案：Token令牌机制、数据库唯一索引、乐观锁、分布式锁。

**📦 实际例子——电商下单防重复提交：**

```java
// 方案1：Token令牌机制（最常用，适合提交类接口）

// 前端获取Token
@GetMapping("/api/order/token")
public Result<String> getOrderToken() {
    String token = UUID.randomUUID().toString();
    // 存入Redis，设置30分钟过期
    redisTemplate.opsForValue().set(
        "order:token:" + token, 
        SecurityUtils.getUserId(), 
        30, TimeUnit.MINUTES
    );
    return Result.ok(token);
}

// 提交订单时使用Token
@PostMapping("/api/order")
public Result<Long> createOrder(@RequestBody OrderDTO dto, 
                                 @RequestHeader("X-Order-Token") String token) {
    
    String userId = SecurityUtils.getUserId();
    String key = "order:token:" + token;
    
    // 用Redis的DEL命令做原子判断：能删掉说明Token有效，删不掉说明已用过
    Boolean deleted = redisTemplate.delete(key);
    if (Boolean.FALSE.equals(deleted)) {
        return Result.fail(400, "请勿重复提交");
    }
    
    // Token验证通过，创建订单
    Long orderId = orderService.createOrder(dto);
    return Result.ok(orderId);
}

// 方案2：数据库唯一索引（简单粗暴）
// 订单表加唯一索引：user_id + product_id + date
// 同一个用户同一天购买同一商品，只能创建一笔订单
// CREATE UNIQUE INDEX uk_user_product_date ON orders(user_id, product_id, DATE(create_time));

// 方案3：分布式锁（适合需要严格控制的场景）
@PostMapping("/api/order")
public Result<Long> createOrder(@RequestBody OrderDTO dto) {
    String lockKey = "lock:order:" + SecurityUtils.getUserId() + ":" + dto.getSkuId();
    
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
    
    if (Boolean.FALSE.equals(locked)) {
        return Result.fail(400, "请求处理中，请勿重复提交");
    }
    
    try {
        Long orderId = orderService.createOrder(dto);
        return Result.ok(orderId);
    } finally {
        redisTemplate.delete(lockKey);
    }
}

// 方案4：自定义幂等注解（最优雅）
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    String key() default "";            // 幂等key的前缀
    long expire() default 5;            // 过期时间（秒）
    TimeUnit timeUnit() default TimeUnit.SECONDS;
    String message() default "请勿重复提交";
}

// AOP实现
@Aspect
@Component
public class IdempotentAspect {
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Around("@annotation(idempotent)")
    public Object around(ProceedingJoinPoint pjp, Idempotent idempotent) throws Throwable {
        String userId = SecurityUtils.getUserId();
        String method = pjp.getSignature().toShortString();
        String lockKey = "idempotent:" + idempotent.key() + ":" + userId + ":" + method;
        
        Boolean success = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", idempotent.expire(), idempotent.timeUnit());
        
        if (Boolean.FALSE.equals(success)) {
            throw new BusinessException(idempotent.message());
        }
        
        try {
            return pjp.proceed();
        } catch (Exception e) {
            // 业务异常，删除幂等key，允许重试
            redisTemplate.delete(lockKey);
            throw e;
        }
    }
}

// 使用时只需加一个注解
@PostMapping("/api/order")
@Idempotent(key = "createOrder", expire = 5, message = "订单提交中，请勿重复操作")
public Result<Long> createOrder(@RequestBody OrderDTO dto) {
    return Result.ok(orderService.createOrder(dto));
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：分布式锁要注意锁的粒度——太粗（如按用户ID）会影响并发，太细（如按请求参数）key太长。一般按"用户+业务类型"或"用户+商品ID"设置。
- 加分回答：Redis分布式锁要注意：①设置过期时间防止死锁 ②释放锁时验证value（或Lua脚本）防止误删别人的锁 ③生产环境推荐Redisson的RedLock。
- 坑：Token方案中，如果订单创建失败（如库存不足），要把Token重新放回Redis，允许用户重试。

### 第25集：Spring缓存怎么用？这三个注解必须会

**🎯 面试官问法：**
> "Spring的缓存注解有哪些？@Cacheable、@CachePut、@CacheEvict有什么区别？"

**💡 核心回答：**
三个注解分别对应三种缓存策略：**查了再存**、**更新了缓存**、**删了缓存**。

**📦 实际例子——电商商品缓存：**

```java
@Service
public class ProductService {
    @Autowired
    private ProductDao productDao;
    
    // 1. @Cacheable：先查缓存，有就直接返回；没有就查数据库，然后存入缓存
    @Cacheable(value = "product", key = "#id")
    // value="product" → 缓存名（类似Redis的key前缀）
    // key="#id" → 缓存key用方法参数id的值
    // 实际Redis key: product::1, product::2, ...
    public Product getById(Long id) {
        return productDao.findById(id);  // 只有缓存没命中时才执行这行
    }
    
    // 2. @CachePut：无论如何都执行方法，然后更新缓存
    // 适用场景：更新数据库后同步更新缓存
    @CachePut(value = "product", key = "#product.id")
    public Product updateProduct(Product product) {
        productDao.update(product);  // 每次都执行
        return product;              // 返回值存入缓存
    }
    
    // 3. @CacheEvict：删除缓存
    // 适用场景：删除或更新数据后清除缓存
    @CacheEvict(value = "product", key = "#id")
    public void deleteProduct(Long id) {
        productDao.deleteById(id);
    }
    
    // 清除整个缓存空间的所有缓存
    @CacheEvict(value = "product", allEntries = true)
    public void clearAllProductCache() {
        // 批量更新后，清除所有商品缓存
    }
}
```

**三个注解对比表：**

| 注解 | 执行时机 | 方法是否执行 | 适用场景 |
|------|---------|------------|---------|
| @Cacheable | 方法执行前 | 缓存命中→不执行；未命中→执行 | 查询（读多写少） |
| @CachePut | 方法执行后 | 始终执行 | 新增/更新（写操作） |
| @CacheEvict | 方法执行前/后 | 始终执行 | 删除（清除缓存） |

**配置Redis作为缓存：**

```yaml
# application.yml
spring:
  cache:
    type: redis
    redis:
      time-to-live: 3600000    # 默认缓存1小时（毫秒）
      key-prefix: "mall:"      # key前缀
    cache-names:
      - product
      - category
      - user
```

```java
// 开启缓存
@EnableCaching
@SpringBootApplication
public class MallApplication { ... }

// 更细粒度的缓存配置
@Configuration
public class CacheConfig {
    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        // 商品缓存：30分钟过期
        RedisCacheConfiguration productConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()));
        
        // 分类缓存：2小时过期（变化少）
        RedisCacheConfiguration categoryConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofHours(2));
        
        return RedisCacheManager.builder(factory)
            .cacheDefaults(productConfig)           // 默认配置
            .withCacheConfiguration("product", productConfig)
            .withCacheConfiguration("category", categoryConfig)
            .build();
    }
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：`@Cacheable`可以设置条件缓存：`@Cacheable(value="product", key="#id", condition="#id > 0")` — 只有id大于0才缓存。还有`unless`：`unless="#result == null"` — 结果为null时不缓存。
- 加分回答：缓存三大问题——穿透（查不存在的数据）、击穿（热点key过期瞬间大量请求）、雪崩（大量key同时过期）。Spring Cache本身不解决这些问题，需要配合布隆过滤器、互斥锁、随机过期时间等方案。
- 坑：`@Cacheable`的key默认用的是方法的**所有参数**组合，如果参数是复杂对象，要确保正确实现了`equals()`和`hashCode()`，或者用SpEL表达式指定key。
- 坑：`@CachePut`返回的对象会存入缓存。如果方法返回void或者返回了错误的对象，缓存里就是空数据。

### 第26集：Spring Security认证流程，一张图讲清楚

**🎯 面试官问法：**
> "Spring Security的认证流程是怎样的？FilterChain里有哪些核心过滤器？"

**💡 核心回答：**
核心流程就5步：请求 → Filter拦截 → AuthenticationManager验证 → UserDetailsService加载用户 → 认证成功写入SecurityContext。

**📦 实际例子——电商后台登录流程：**

```java
// 1. Security配置
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf().disable()   // REST API关闭CSRF
            .sessionManagement().sessionCreationPolicy(SessionCreationPolicy.STATELESS) // 无Session，用JWT
            .and()
            .authorizeRequests()
                .antMatchers("/api/auth/login", "/api/auth/register").permitAll()  // 登录注册不需要认证
                .antMatchers("/api/admin/**").hasRole("ADMIN")                     // 后台需要管理员角色
                .anyRequest().authenticated()                                       // 其他请求需要登录
            .and()
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class); // 自定义JWT过滤器
        
        return http.build();
    }
    
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();  // 密码加密
    }
}

// 2. 认证流程中的5个关键步骤：

// 步骤1：用户提交登录请求
// POST /api/auth/login  {"username":"admin", "password":"123456"}

// 步骤2：JWT认证过滤器拦截请求
@Component
public class JwtAuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, 
                                     HttpServletResponse response, 
                                     FilterChain chain) throws Exception {
        String token = request.getHeader("Authorization");
        if (token != null && token.startsWith("Bearer ")) {
            token = token.substring(7);
            // 解析JWT，获取用户信息
            String username = jwtUtil.getUsername(token);
            if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
                UserDetails userDetails = userDetailsService.loadUserByUsername(username);
                if (jwtUtil.validateToken(token, userDetails)) {
                    // 步骤5：认证成功，写入SecurityContext
                    UsernamePasswordAuthenticationToken auth = 
                        new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());
                    SecurityContextHolder.getContext().setAuthentication(auth);
                }
            }
        }
        chain.doFilter(request, response);
    }
}

// 步骤3：AuthenticationManager处理认证
// 登录时：
@PostMapping("/api/auth/login")
public Result<String> login(@RequestBody LoginDTO dto) {
    // 创建未认证的Authentication对象
    UsernamePasswordAuthenticationToken authToken = 
        new UsernamePasswordAuthenticationToken(dto.getUsername(), dto.getPassword());
    
    // AuthenticationManager调用UserDetailsService验证
    Authentication auth = authenticationManager.authenticate(authToken);
    // 如果密码错误，这里直接抛BadCredentialsException
    
    // 步骤4：UserDetailsService加载用户信息
    // （authenticate内部调用的）
    
    // 登录成功，生成JWT Token
    String token = jwtUtil.generateToken(auth.getName());
    return Result.ok(token);
}

// 步骤4：自定义UserDetailsService
@Service
public class CustomUserDetailsService implements UserDetailsService {
    @Autowired
    private UserMapper userMapper;
    
    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        User user = userMapper.findByUsername(username);
        if (user == null) {
            throw new UsernameNotFoundException("用户不存在：" + username);
        }
        
        return new org.springframework.security.core.userdetails.User(
            user.getUsername(),
            user.getPassword(),        // BCrypt加密后的密码
            user.getEnabled(),         // 是否启用
            true, true, true,
            user.getRoles().stream()   // 角色/权限
                .map(role -> new SimpleGrantedAuthority("ROLE_" + role.getName()))
                .collect(Collectors.toList())
        );
    }
}
```

**认证流程图：**

```
登录请求：
POST /api/auth/login → JwtAuthFilter → UsernamePasswordAuthenticationFilter
                                       ↓
                              AuthenticationManager.authenticate()
                                       ↓
                              UserDetailsService.loadUserByUsername()
                                       ↓
                              PasswordEncoder.matches()（密码比对）
                                       ↓
                              认证成功 → 生成JWT → 返回Token

后续请求：
GET /api/orders → JwtAuthFilter（解析Token）→ SecurityContext（已有认证信息）→ Controller
```

**⚠️ 常见坑/加分回答：**
- 加分回答：Spring Security的过滤器链有十几个Filter，按顺序执行。核心的几个：`SecurityContextPersistenceFilter`（维持SecurityContext）→ `UsernamePasswordAuthenticationFilter`（处理表单登录）→ `ExceptionTranslationFilter`（处理认证/授权异常）。
- 加分回答：JWT和Session方案的核心区别：JWT是无状态的（不需要服务端存储），适合分布式/微服务；Session是有状态的（需要共享Session），需要Redis Session。
- 坑：`SecurityContextHolder`默认用`ThreadLocal`存储认证信息。如果你用了异步线程（如`@Async`或线程池），子线程拿不到SecurityContext。需要配置`SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL)`或手动传递。

### 第27集：Spring Boot和Spring Cloud什么关系？别再搞混

**🎯 面试官问法：**
> "Spring Boot和Spring Cloud有什么区别和联系？"

**💡 核心回答：**
Spring Boot是**造砖瓦**（快速创建独立应用），Spring Cloud是**盖房子**（把多个应用组织成微服务架构）。

**📦 实际例子：**

```
单体应用（只用Spring Boot）：
┌─────────────────────────────┐
│        电商系统（一个应用）     │
│  用户模块 + 订单模块 + 库存模块  │
│  共用一个数据库                │
│  Spring Boot启动一个Tomcat     │
└─────────────────────────────┘

微服务（Spring Boot + Spring Cloud）：
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 用户服务  │  │ 订单服务  │  │ 库存服务  │  │ 支付服务  │
│ Boot应用  │  │ Boot应用  │  │ Boot应用  │  │ Boot应用  │
└────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
     │              │              │              │
     └──────────────┴──────┬───────┴──────────────┘
                           │
                    ┌──────┴──────┐
                    │  Nacos注册中心 │  ← Spring Cloud提供
                    │  Gateway网关  │  ← Spring Cloud提供
                    │  OpenFeign调用 │  ← Spring Cloud提供
                    │  Sentinel限流  │  ← Spring Cloud提供
                    └─────────────┘
```

**一句话总结关系：**
- **Spring Boot** = 让你快速创建一个独立运行的应用
- **Spring Cloud** = 让多个Spring Boot应用协同工作（注册发现、负载均衡、熔断、配置中心）
- Spring Cloud**依赖**Spring Boot，每个微服务本身就是一个Spring Boot应用

| 对比维度 | Spring Boot | Spring Cloud |
|---------|-----------|-------------|
| 定位 | 快速开发单个应用 | 微服务整体解决方案 |
| 独立性 | 可以独立运行 | 需要多个Boot应用组合 |
| 关注点 | 简化配置、内嵌容器 | 服务治理、分布式协作 |
| 核心组件 | 自动配置、Starter | Nacos、Gateway、Feign、Sentinel |

**⚠️ 常见坑/加分回答：**
- 加分回答：Spring Cloud有多个版本系列——Netflix系（Eureka/Hystrix/Ribbon，已停更）→ Alibaba系（Nacos/Sentinel，国内主流）→ 官方系（Spring Cloud LoadBalancer）。新项目推荐Alibaba系。
- 加分回答：Spring Cloud和Spring Boot有**版本对应关系**，不能随便搭配。比如Spring Cloud 2022.0.x 对应 Spring Boot 3.0.x。

### 第28集：Nacos、Eureka、Consul三大注册中心对比

**🎯 面试官问法：**
> "注册中心三选一，你们为什么选Nacos？和Eureka有什么区别？"

**💡 核心回答：**
Nacos = 注册中心 + 配置中心，支持AP/CP模式切换，国内生态好。Eureka只支持AP（最终一致性），已停止更新。Consul支持CP（强一致性），但配置中心功能弱。

**📦 实际例子——电商微服务注册：**

```java
// 订单服务注册到Nacos
// application.yml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: mall-prod        # 命名空间隔离
        group: ORDER_GROUP          # 分组

// 库存服务通过Nacos发现订单服务
@RestController
public class StockController {
    // OpenFeign自动从Nacos获取订单服务地址
    @Autowired
    private OrderFeignClient orderClient;
}

// 订单服务的Feign接口
@FeignClient(name = "order-service")  // 从Nacos找到这个服务
public interface OrderFeignClient {
    @GetMapping("/api/orders/{id}")
    Result<OrderVO> getOrder(@PathVariable("id") Long id);
}
```

**三大注册中心对比表：**

| 对比维度 | Nacos | Eureka | Consul |
|---------|-------|--------|--------|
| 一致性协议 | AP+CP可切换 | AP（最终一致） | CP（强一致） |
| 健康检查 | TCP/HTTP/MySQL/命令 | 心跳 | TCP/HTTP/gRPC |
| 配置中心 | ✅ 内置 | ❌ | ✅ 内置 |
| 负载均衡 | 支持权重 | Ribbon | Fabio |
| 雪崩保护 | ✅ | ✅（有但不够灵活） | ❌ |
| 跨数据中心 | ✅ | ❌ | ✅ |
| 管理界面 | ✅ 中文 | ✅ 英文 | ✅ 英文 |
| Spring Cloud兼容 | ✅ | ⚠️ 已停止维护 | ✅ |
| 国内生态 | ✅ 阿里开源 | ❌ | ❌ |

**AP vs CP选择：**
```
AP（Nacos默认/Eureka）：
  保证可用性 → 某个节点挂了，其他节点继续服务
  可能短暂读到过期数据
  适合：大部分业务场景（宁可读到旧数据，不能不响应）

CP（Nacos可配/Consul）：
  保证一致性 → 数据一定最新
  节点选举期间不可用
  适合：金融交易等强一致场景
```

**⚠️ 常见坑/加分回答：**
- 加分回答：Eureka已经停止更新（最后版本2022年），新项目不建议用。国内项目首选Nacos，国外项目可以看Consul。
- 加分回答：Nacos作为配置中心时，支持配置热更新——修改配置后不用重启应用，通过`@RefreshScope`注解自动刷新。
- 坑：Nacos的临时实例（默认）用的是AP模式，如果所有Nacos节点都挂了，服务间调用会失败。生产环境建议至少3个Nacos节点。

### 第29集：OpenFeign调用原理，面试被追问三层怎么答？

**🎯 面试官问法：**
> "OpenFeign底层是怎么工作的？调用超时了怎么办？"

**💡 核心回答：**
OpenFeign = **动态代理** + **负载均衡** + **HTTP客户端**。你定义一个接口，它帮你生成代理对象，自动处理服务发现、URL拼接、请求发送、结果反序列化。

**📦 实际例子：**

```java
// 你只需要定义一个接口
@FeignClient(name = "stock-service", fallback = StockFeignFallback.class)
public interface StockFeignClient {
    
    @GetMapping("/api/stock/{skuId}")
    Result<Integer> getStock(@PathVariable("skuId") Long skuId);
    
    @PostMapping("/api/stock/deduct")
    Result<Boolean> deductStock(@RequestBody StockDeductDTO dto);
}

// 使用时像调本地方法一样
@Service
public class OrderService {
    @Autowired
    private StockFeignClient stockClient;
    
    public void createOrder(OrderDTO dto) {
        // 像调本地方法一样调用远程服务
        Result<Integer> stockResult = stockClient.getStock(dto.getSkuId());
        if (stockResult.getData() < dto.getQty()) {
            throw new BusinessException("库存不足");
        }
        
        stockClient.deductStock(new StockDeductDTO(dto.getSkuId(), dto.getQty()));
        // ... 创建订单
    }
}
```

**底层调用流程：**

```
1. 启动时：OpenFeign扫描@FeignClient注解
   → 为每个接口创建动态代理对象（和AOP用的JDK动态代理类似）
   → 注册到Spring容器

2. 调用时：
   OrderService → stockClient.getStock(1001)
                       ↓
              Feign动态代理拦截
                       ↓
              从Nacos获取stock-service的实例列表
              → [192.168.1.10:8080, 192.168.1.11:8080]
                       ↓
              负载均衡选择一个实例（默认轮询）
              → 选中 192.168.1.10:8080
                       ↓
              拼接完整URL
              → http://192.168.1.10:8080/api/stock/1001
                       ↓
              HTTP客户端发送请求（默认用URLConnection，推荐换成HttpClient/OkHttp）
                       ↓
              接收响应 → HttpMessageConverter反序列化
              → Result<Integer>对象返回
```

**超时配置（面试常问）：**

```yaml
# 超时配置
spring:
  cloud:
    openfeign:
      client:
        config:
          default:                    # 全局配置
            connectTimeout: 3000      # 连接超时3秒
            readTimeout: 5000         # 读取超时5秒
          stock-service:              # 针对特定服务配置
            connectTimeout: 2000
            readTimeout: 3000
```

**熔断降级（配合Sentinel）：**

```java
// 降级处理类
@Component
public class StockFeignFallback implements StockFeignClient {
    
    @Override
    public Result<Integer> getStock(Long skuId) {
        // 远程调用失败时的降级逻辑
        // 返回默认值或从本地缓存读取
        return Result.fail(503, "库存服务暂时不可用，请稍后再试");
    }
    
    @Override
    public Result<Boolean> deductStock(StockDeductDTO dto) {
        return Result.fail(503, "库存服务暂时不可用");
    }
}

// 或者用fallbackFactory，能拿到异常信息
@Component
public class StockFeignFallbackFactory implements FallbackFactory<StockFeignClient> {
    @Override
    public StockFeignClient create(Throwable cause) {
        return new StockFeignClient() {
            @Override
            public Result<Integer> getStock(Long skuId) {
                log.error("调用库存服务失败：{}", cause.getMessage());
                // 可以判断异常类型做不同处理
                if (cause instanceof RetryableException) {
                    return Result.fail(503, "库存服务繁忙，请重试");
                }
                return Result.fail(500, "库存服务异常");
            }
            // ...
        };
    }
}
```

**⚠️ 常见坑/加分回答：**
- 加分回答：OpenFeign默认的HTTP客户端是`URLConnection`，**没有连接池**。生产环境建议换成Apache HttpClient或OkHttp，它们支持连接池，性能更好。
- 加分回答：OpenFeign调用是**同步阻塞**的，如果下游服务响应慢，会占用当前线程。高并发场景可以考虑用Spring Cloud OpenFeign的异步支持（返回`CompletableFuture`）或者用WebFlux的响应式客户端。
- 坑：Feign调用默认**不传递请求头**（如Token）。如果下游服务也需要认证，需要配置`RequestInterceptor`传递Header：
  ```java
  @Bean
  public RequestInterceptor headerInterceptor() {
      return requestTemplate -> {
          String token = SecurityContextHolder.getContext()...;
          requestTemplate.header("Authorization", "Bearer " + token);
      };
  }
  ```

### 第30集：Sentinel限流熔断，核心概念一张图搞定

**🎯 面试官问法：**
> "Sentinel的限流和熔断有什么区别？怎么配置？"

**💡 核心回答：**
**限流是保护系统不被过多请求打垮**（控制入口流量），**熔断是保护系统不被下游故障拖死**（控制出口调用）。一个是"进来的太多我挡一挡"，一个是"下游挂了我别跟着挂"。

**📦 实际例子——电商秒杀场景：**

```java
// 场景：秒杀接口，预计QPS 1万，但系统最多扛5000
@Service
public class SeckillService {
    
    // 限流：保护秒杀接口不被打爆
    @SentinelResource(value = "seckill", 
                      blockHandler = "seckillBlock")
    public Result<String> seckill(Long userId, Long skuId) {
        // 核心业务逻辑：扣库存、创建订单
        // 这个接口最多承受5000 QPS
        
        stockService.deduct(skuId, 1);
        orderService.createSeckillOrder(userId, skuId);
        return Result.ok("秒杀成功");
    }
    
    // 限流触发时的降级方法
    public Result<String> seckillBlock(Long userId, Long skuId, BlockException ex) {
        return Result.fail(429, "活动太火爆，请稍后再试");
    }
}

// 限流规则配置（代码方式）
@Configuration
public class SentinelConfig {
    @PostConstruct
    public void initRules() {
        // QPS限流：每秒最多5000个请求
        List<FlowRule> rules = new ArrayList<>();
        FlowRule rule = new FlowRule();
        rule.setResource("seckill");           // 资源名
        rule.setGrade(RuleConstant.FLOW_GRADE_QPS);  // QPS模式
        rule.setCount(5000);                    // 阈值
        rule.setControlBehavior(
            RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER);  // 匀速排队
        rule.setMaxQueueingTimeMs(500);         // 最长等待500ms
        rules.add(rule);
        FlowRuleManager.loadRules(rules);
    }
}
```

**熔断降级场景：**

```java
@Service
public class OrderService {
    @Autowired
    private StockFeignClient stockClient;
    
    // 熔断：保护订单服务不被库存服务的故障拖死
    @SentinelResource(value = "createOrder",
                      fallback = "createOrderFallback")
    public void createOrder(OrderDTO dto) {
        // 调用库存服务

    rule.setResource("createOrder");
    rule.setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType()); // 慢调用比例
    rule.setCount(0.5);           // 慢调用比例超过50%触发熔断
    rule.setSlowRatioThreshold(200); // 响应时间超过200ms算慢调用
    rule.setTimeWindow(30);       // 熔断持续30秒
    rule.setMinRequestAmount(10); // 最少10个请求才统计
    rule.setStatIntervalMs(10000); // 统计窗口10秒
    rules.add(rule);
```

**限流 vs 熔断对比：**

| 对比维度 | 限流（Flow） | 熔断（Degrade/CircuitBreaker） |
|---------|------------|------|
| 保护目标 | 保护自己不被打垮 | 保护自己不被下游拖死 |
| 控制方向 | 控制入口流量 | 控制出口调用 |
| 触发条件 | QPS/线程数超过阈值 | 下游错误率/慢调用比例超过阈值 |
| 效果 | 多余的请求被拒绝 | 一段时间内不调用下游，直接降级 |
| 恢复 | 流量降低后自动恢复 | 熔断期后尝试恢复（半开状态） |
| 类比 | 餐厅限号排队 | 某道菜原料断货，暂时下架 |

**Sentinel的三种限流模式：**

```
1. 直接拒绝：超过阈值直接拒绝
   QPS > 5000 → 直接返回 "系统繁忙"

2. 匀速排队（漏桶算法）：请求匀速通过
   1万个请求瞬间到达 → 每秒处理5000个，其余排队等待
   超过等待时间 → 拒绝

3. Warm Up（预热）：冷启动，慢慢增加
   前10秒阈值从1000慢慢升到5000
   适合：系统刚启动，需要预热缓存、建立连接
```

**⚠️ 常见坑/加分回答：**
- 加分回答：熔断器有三种状态：CLOSED（正常）→ OPEN（熔断中，所有请求走降级）→ HALF_OPEN（试探性放行一个请求，成功则恢复，失败则继续熔断）。这和电路保险丝的原理一样。
- 加分回答：Sentinel和Hystrix的区别——Sentinel支持QPS限流、支持流量控制（预热、排队），Hystrix只支持线程池/信号量隔离。Sentinel有可视化Dashboard，Hystrix的Dashboard已停更。
- 坑：`@SentinelResource`的`blockHandler`和`fallback`方法，**参数列表必须和原方法一致**，blockHandler还要多一个`BlockException`参数。
- 坑：Sentinel默认不持久化规则，应用重启规则就丢了。生产环境要配置规则持久化到Nacos。
