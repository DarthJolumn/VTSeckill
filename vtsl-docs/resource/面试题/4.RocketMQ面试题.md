## 第1系列：消息发送

### 第1集：RocketMQ 的消息发送方式——同步、异步、单向的区别和适用场景

**💡 核心回答：**

RocketMQ 提供三种消息发送方式：同步发送（Sync）、异步发送（Async）、单向发送（Oneway）。

| 发送方式 | 是否需要 Broker 响应 | 是否阻塞 | 适用场景 |
|---------|-------------------|---------|---------|
| 同步发送 | 是 | 阻塞，等待响应 | 核心业务（订单、支付、扣库存） |
| 异步发送 | 是 | 不阻塞，回调通知 | 对响应时间敏感但需确认（通知类） |
| 单向发送 | 否 | 不阻塞，不等待 | 日志收集、审计记录 |

底层实现差异：
- 同步：Netty 的 `invokeSync` —— 通过 `CountDownLatch` 阻塞等待 Response
- 异步：Netty 的 `invokeAsync` —— 注册 `ResponseFuture` + `invokeCallback`，非阻塞
- 单向：Netty 的 `invokeOneway` —— 写入 Channel 后立即返回，不注册任何回调

**📦 实际例子：**

悦茶奶茶平台三种典型场景：
- **同步发送**：用户下单后发送「订单创建」消息到 `ORDER_CREATED_TOPIC`，需要确认消息落盘成功才能返回「下单成功」，否则需要回滚订单。
- **异步发送**：订单完成后发送「积分发放」消息到 `POINT_GRANT_TOPIC`，主线程不等待，通过回调判断是否需要重试。
- **单向发送**：用户每次打开小程序记录「用户行为日志」到 `USER_ACTION_TOPIC`，允许极少量丢失，追求最大吞吐。

**🔍 源码解析：**

核心类：`DefaultMQProducerImpl`（`org.apache.rocketmq.client.impl.producer`）

```java
// 同步发送核心逻辑
private SendResult sendDefaultImpl(Message msg, ...) throws MQException {
    // 1. 获取 Topic 路由信息
    TopicPublishInfo topicPublishInfo = this.checkTopicAndMsgRoute(msg.getTopic());
    // 2. 选择 MessageQueue（轮询 + 延迟规避）
    MessageQueue mq = this.selectOneMessageQueue(topicPublishInfo, lastBrokerName);
    // 3. 调用 Netty 同步发送
    return this.sendKernelImpl(msg, mq, communicationMode, sendCallback, ...);
}

// sendKernelImpl 中根据 communicationMode 分派
switch (communicationMode) {
    case SYNC:
        // invokeSync 阻塞等待，超时抛 RemotingTimeoutException
        return this.mqClientFactory.getMQClientAPIImpl().sendMessage(
            brokerAddr, mq, msg, requestHeader, timeoutMillis, ...);
    case ASYNC:
        // invokeAsync + ResponseFuture 回调
        this.mqClientFactory.getMQClientAPIImpl().sendMessage(
            brokerAddr, mq, msg, requestHeader, timeoutMillis, sendCallback, ...);
        return null;
    case ONEWAY:
        // 写 Channel 后直接返回
        this.mqClientFactory.getMQClientAPIImpl().sendMessageOneway(
            brokerAddr, mq, msg, requestHeader, timeoutMillis);
        return null;
}
```

底层 Netty 客户端：`NettyRemotingClient` 中通过 `processRequestCommand` 将请求放入 `responseTable`（ConcurrentHashMap），异步等待时通过 `EventExecutor` 调度超时检测。

**⚠️ 常见坑/加分回答：**

1. **同步发送的超时设置**：默认 `sendMsgTimeout = 3000ms`，生产环境必须根据 Broker 响应时间调整。超时后会触发重试（默认重试 2 次 = 总共 3 次），每次重试选择不同的 Broker。
2. **异步发送的回调线程池**：回调在 Netty 的 Worker 线程中执行，如果回调逻辑耗时（如操作数据库），必须自行丢入业务线程池，否则会阻塞 Netty 线程，影响所有后续消息发送。
3. **单向发送不等于不丢消息**：单向发送的「不保证」是指不保证 Broker 收到，但如果 Broker 正常，消息一样会落盘。关键是「发不出去」的概率极低。
4. **加分点**：同步发送支持发送失败重试，通过 `retryTimesWhenSendFailed`（默认 2）控制；异步发送通过 `retryTimesWhenSendAsyncFailed`（默认 2）控制。每次重试会切换到不同 Broker，避免单点故障。

### 第2集：消息发送的完整流程——从 Producer 到落盘的全链路

**💡 核心回答：**

消息发送完整链路：

```
Producer → NameServer(获取路由) → 选择 Broker → 发送消息 → Broker 存储 → 返回结果
```

详细步骤：
1. **Producer 启动**：创建 `MQClientInstance`，启动定时任务每 30s 从 NameServer 拉取最新路由表
2. **发送消息时**：先从本地缓存 `topicPublishInfoTable` 获取路由，找不到则主动请求 NameServer
3. **选择 Broker**：根据 `MessageQueueSelector`（轮询/哈希/自定义）选择队列
4. **发送请求**：通过 Netty 长连接发送 `SendMessageRequestHeader` 到目标 Broker
5. **Broker 处理**：接收消息 → 写入 CommitLog → 构建 ConsumeQueue/IndexFile → 返回结果

**📦 实际例子：**

悦茶平台「用户下单」场景：
1. 订单服务调用 `producer.send(msg)` 发送订单消息到 `ORDER_TOPIC`
2. Producer 从本地缓存查到 `ORDER_TOPIC` 有 8 个队列分布在 4 个 Broker 上
3. 轮询选择 `Broker-A` 的 `queue-3`
4. 通过 Netty 连接 Broker-A 的 `10911` 端口发送
5. Broker-A 将消息写入 CommitLog（`/store/commitlog/00000000000002345678`）
6. 异步构建 ConsumeQueue 和 IndexFile
7. 返回 `SendResult`（含 msgId、queueId、queueOffset）给 Producer

**🔍 源码解析：**

核心类调用链：

```java
// 1. Producer 端路由获取
public class TopicPublishInfo {
    private volatile boolean orderTopic = false;
    private List<MessageQueue> messageQueueList = new ArrayList<>();
    private ThreadLocalIndex sendWhichQueue = new ThreadLocalIndex();
}

// 2. 选择队列：默认轮询 + 延迟规避
public MessageQueue selectOneMessageQueue(final String lastBrokerName) {
    if (lastBrokerName == null) {
        int index = this.sendWhichQueue.incrementAndGet();
        int pos = Math.abs(index) % this.messageQueueList.size();
        return this.messageQueueList.get(pos);
    } else {
        for (int i = 0; i < this.messageQueueList.size(); i++) {
            int index = this.sendWhichQueue.incrementAndGet();
            int pos = Math.abs(index) % this.messageQueueList.size();
            MessageQueue mq = this.messageQueueList.get(pos);
            if (!mq.getBrokerName().equals(lastBrokerName)) {
                return mq;
            }
        }
        return null;
    }
}

// 3. Broker 端处理：SendMessageProcessor
public RemotingCommand processRequest(ChannelHandlerContext ctx, RemotingCommand request) {
    SendResult sendResult = this.brokerController.getMessageStore().putMessage(messageExt);
    // 返回 SEND_OK / FLUSH_DISK_TIMEOUT / SLAVE_NOT_AVAILABLE 等
}
```

NameServer 路由更新：`MQClientInstance` 中 `updateTopicRouteInfoFromNameServer` 方法每 30s 执行，发送 `GET_ROUTEINTO_BY_TOPIC` 请求到所有 NameServer 节点。

**⚠️ 常见坑/加分回答：**

1. **路由缓存的坑**：Producer 本地缓存路由默认 30s 更新一次。如果新增 Broker 或队列数变更，最多 30s 后才会感知。紧急扩容时可通过 `producer.getDefaultMQProducerImpl().updateTopicRouteInfoFromNameServer(topic)` 主动刷新。
2. **选择队列的延迟规避**：发送失败重试时，`LatencyFaultToleranceImpl` 会记录每个 Broker 的「不可用时长」，在不可用期间内跳过该 Broker。
3. **大消息问题**：Broker 默认 `maxMessageSize = 4MB`，超过会抛异常。悦茶平台的「商品详情图」消息不要直接塞消息体，应该传 OSS URL。
4. **加分点**：`MQClientInstance` 是单例的（per `clientId`），同一个 JVM 中多个 Producer 共享同一个 Netty 连接池和定时任务。`clientId` 默认为 `IP@instanceName`。

### 第3集：消息发送的高可用保障——刷盘策略与主从复制

**💡 核心回答：**

RocketMQ 的高可用通过两个维度保障：

| 维度 | 配置项 | 选项 | 说明 |
|-----|-------|-----|------|
| 刷盘策略 | `flushDiskType` | `SYNC_FLUSH` / `ASYNC_FLUSH` | 消息写入 OS PageCache 后何时刷到磁盘 |
| 主从复制 | `brokerRole` | `SYNC_MASTER` / `ASYNC_MASTER` / `DLedger` | 消息写入 Master 后何时同步到 Slave |

可靠性等级（从低到高）：
1. 异步刷盘 + ASYNC_MASTER：最快，可能丢消息
2. 异步刷盘 + SYNC_MASTER：消息到 Slave 才返回，但可能丢在 PageCache
3. 同步刷盘 + ASYNC_MASTER：消息落盘才返回，但 Slave 可能不同步
4. 同步刷盘 + SYNC_MASTER：最安全，性能最低

**📦 实际例子：**

悦茶平台分级存储策略：
- **订单创建消息**：同步刷盘 + SYNC_MASTER（订单数据绝不能丢）
- **优惠券发放消息**：异步刷盘 + SYNC_MASTER（可接受极小概率丢失）
- **门店日报消息**：异步刷盘 + ASYNC_MASTER（追求性能，丢了可重算）

**🔍 源码解析：**

核心类：`CommitLog`（`org.apache.rocketmq.store`）

```java
// 同步刷盘：GroupCommitService
public class GroupCommitService extends FlushRealTimeService {
    public void putRequest(final CommitRequest request) {
        synchronized (this.requestsWrite) {
            this.requestsWrite.add(request);
        }
        this.wakeup();
    }

    @Override
    public void run() {
        while (!this.isStopped()) {
            this.swapRequests(); // 双缓冲设计，减少锁竞争
            for (CommitRequest req : this.requestsRead) {
                boolean result = CommitLog.this.mappedFileQueue.flush(0);
                if (req.getOffset() <= CommitLog.this.confirmOffset) {
                    req.wakeupCustomer(result);
                }
            }
            this.waitForRunning(interval);
        }
    }
}

// 异步刷盘：FlushRealTimeService（定时刷盘，默认 500ms 间隔）
public class FlushRealTimeService extends ServiceThread {
    @Override
    public void run() {
        while (!this.isStopped()) {
            this.waitForRunning(interval);
            CommitLog.this.mappedFileQueue.flush(0);
        }
    }
}

// 主从同步：HAService
public class HAService {
    // Master 端 AcceptSocketService 监听 Slave 连接
    // GroupTransferService 实现同步复制
    public class GroupTransferService extends ServiceThread {
        synchronized (this) {
            while (!isTransferOK(request)) {
                this.wait(1000);
            }
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **同步刷盘的性能损失**：同步刷盘会将 TPS 降低 50%~70%。悦茶平台压测发现同步刷盘从 8 万 TPS 降到 2.5 万 TPS，因此只有订单类 Topic 使用同步刷盘。
2. **PageCache 的丢失风险**：异步刷盘时，消息写入 OS PageCache 后如果机器宕机，PageCache 中未刷盘的消息会丢失。解决方案：使用 `mlock` 锁定内存。
3. **Slave 同步延迟**：SYNC_MASTER 模式下，Slave 同步延迟会导致 Producer 等待时间增加。建议 Master-Slave 之间网络延迟 < 5ms。
4. **加分点**：RocketMQ 4.x 的同步复制通过 `GroupTransferService` 实现，Master 写入 CommitLog 后等待 Slave 通过 HA 连接确认偏移量。如果等待超时（默认 5s），则根据 `isSyncMaster` 判断是否返回失败。DLedger 模式（5.x）使用 Raft 协议，一致性更强。

### 第4集：事务消息的实现原理——Half Message 与回查机制

**💡 核心回答：**

RocketMQ 事务消息采用「两阶段提交 + 回查」机制：

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                     RocketMQ 事务消息完整流程图                                  │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  Producer                    Broker                        Consumer             │
│  ────────                    ──────                        ────────             │
│                                                                                 │
│  ① 发送 Half 消息                                             │
│  ─────────────────►                                              │
│                         ┌──────────────────┐                    │
│                         │ RMQ_SYS_TRANS_   │                    │
│                         │ HALF_TOPIC       │ ◄── 对Consumer不可见│
│                         │ (半消息存储区)    │                    │
│                         └──────────────────┘                    │
│  ◄──────── 返回 Half 消息发送成功                                │
│                                                                                 │
│  ② 执行本地事务                                                │
│  ┌──────────────────┐                                        │
│  │ 创建订单          │                                        │
│  │ 扣减库存          │                                        │
│  │ 记录流水          │                                        │
│  └────────┬─────────┘                                        │
│           │                                                   │
│     ┌─────┴─────┬──────────────┐                              │
│     ▼           ▼              ▼                              │
│  ✅ 成功      ❌ 失败       ⚠️ 未知/超时                       │
│     │           │              │                              │
│  ③ 发送     ③ 发送         ③ 不发送                           │
│  Commit     Rollback        EndTransaction                    │
│  ─────────►  ─────────►         ✗                             │
│                         │              │                       │
│                    ┌────┴────┐    ┌────┴──────────┐           │
│                    │转移到真实│    │删除 Half 消息  │           │
│                    │Topic    │    │(Consumer永远   │           │
│                    │         │    │ 看不到此消息)  │           │
│                    └────┬────┘    └───────────────┘           │
│                         │                                      │
│                    Consumer可消费 ──────────────────────►       │
│                                                                                 │
│  ═══════════════════════ 回查机制（未知状态时触发）═══════════════════════        │
│                                                                                 │
│                   ┌────────────────────────────┐                                │
│                   │ TransactionalMessageCheck  │                                │
│                   │ Service (定时扫描线程)       │                                │
│                   │ 间隔: 默认60s               │                                │
│                   │ 超时: transactionTimeout=6s │                                │
│                   └──────────┬─────────────────┘                                │
│                              │                                                  │
│                   检查 Half 消息是否超时未确认                                    │
│                              │                                                  │
│                   ◄──────────┘                                                  │
│  ◄──── CHECK_TRANSACTION ────                                   │
│  │                                                               │
│  ④ 回查本地事务状态                                               │
│  checkLocalTransaction(msg)                                      │
│  │                                                               │
│  ├── COMMIT ────► 发送 EndTransaction(COMMIT) ──► 转移到真实Topic │
│  ├── ROLLBACK ──► 发送 EndTransaction(ROLLBACK) ──► 删除Half消息  │
│  └── UNKNOWN ───► 不做任何操作，等待下次回查                       │
│                   (最多回查 transactionCheckMax=15 次)             │
│                   超过15次 → 消息进入死信队列(DLQ)                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

对比其他 MQ 的事务实现：
- Kafka：无原生事务消息（Kafka 事务是跨 Partition 的原子写，不是业务事务）
- RabbitMQ：无事务消息，需自行实现最终一致性
- RocketMQ：原生支持，且支持回查机制，可靠性最高

**📦 实际例子：**

悦茶平台「下单扣库存」场景：

```java
TransactionMQProducer producer = new TransactionMQProducer("order_tx_group");
producer.setNamesrvAddr("namesrv1:9876;namesrv2:9876");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrder(msg.getBody());
            inventoryService.deductStock(orderId);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String orderId = msg.getProperty("orderId");
        Order order = orderMapper.selectById(orderId);
        if (order != null && order.getStatus() == PAID) {
            return LocalTransactionState.COMMIT_MESSAGE;
        } else if (order != null && order.getStatus() == CANCELLED) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
        return LocalTransactionState.UNKNOW;
    }
});
producer.start();

Message msg = new Message("ORDER_TOPIC", "create", JSON.toJSONBytes(orderDTO));
msg.putUserProperty("orderId", orderDTO.getOrderId());
producer.sendMessageInTransaction(msg, null);
```

**🔍 源码解析：**

核心类：`TransactionMQProducer` → `DefaultMQProducerImpl` → Broker 端 `TransactionalMessageServiceImpl`

```java
// 1. 发送 Half 消息（对 Consumer 不可见）
public TransactionSendResult sendMessageInTransaction(Message msg, Object arg) {
    // Half 消息先写入 TRANS_HALF_TOPIC
    msg.setTopic(MixAll.RMQ_SYS_TRANS_HALF_TOPIC);
    SendResult sendResult = this.send(msg);

    // 执行本地事务
    LocalTransactionState localState =
        this.transactionListener.executeLocalTransaction(msg, arg);

    // 发送 EndTransaction 请求给 Broker
    this.endTransaction(sendResult, localState);
}

    // 默认每 60s 扫描，检查超过 transactionTimeout（默认 6s）未确认的消息
    public void check(long transactionTimeout, int transactionCheckMax, ...) {
        // 从 TRANS_HALF_TOPIC 读取消息
        // 检查 Op 消息确认是否已处理
        // 未处理且超时的，发送 CHECK_TRANSACTION 请求给 Producer
    }
```

**⚠️ 常见坑/加分回答：**

1. **回查性能问题**：回查会访问 Producer 端，如果回查逻辑涉及数据库查询且耗时长，会阻塞 Broker 的事务检查线程。悦茶平台建议回查逻辑只查 Redis 缓存的事务状态。
2. **Half 消息对 Consumer 不可见**：Half 消息存储在 `RMQ_SYS_TRANS_HALF_TOPIC`，Consumer 订阅的是真实 Topic，所以不会收到 Half 消息。
3. **事务消息不支持延迟消息**：这是 RocketMQ 的限制，Half 消息不能被标记为延迟消息。
4. **加分点**：RocketMQ 事务消息的性能开销主要来自回查，正常情况下性能损耗 < 5%。建议将 `transactionTimeout` 设置合理（默认 6s），并根据业务调整 `transactionCheckMax`。

### 第5集：CommitLog 的设计原理——为什么所有 Topic 的消息顺序写入同一个文件

**💡 核心回答：**

RocketMQ 的核心设计：**所有 Topic 的消息都顺序写入同一个 CommitLog 文件**。这个设计的原因：

1. **磁盘顺序写入 vs 随机写入**：磁盘顺序写入速度约 600MB/s，随机写入仅约 100 字节/s（机械盘）。即使 SSD，顺序写也远快于随机写。
2. **Mmap（内存映射）**：CommitLog 通过 `MappedByteBuffer` 将文件映射到内存，写入 CommitLog 实际上是写入 PageCache，由 OS 负责刷盘。
3. **消息结构**：每条消息在 CommitLog 中存储为连续字节流，包含：消息长度（4B）+ 魔数（4B）+ 消息体CRC（4B）+ 队列ID（4B）+ 偏移量（8B）+ 各种标志（4B）+ 物理偏移（8B）+ 系统标记（8B）+ 时间戳（8B）+ 属性长度（2B）+ 属性（变长）+ 消息体长度（4B）+ Topic 长度（1B）+ Topic + 消息体

为什么不用每个 Topic 单独文件？
- 多 Topic 并发写入会导致磁盘随机 IO
- 消息的「写多读少」特性，写入性能是第一优先级
- 读性能通过异步构建 ConsumeQueue 来弥补

**📦 实际例子：**

悦茶平台同时有多个 Topic 并发写入：
- `ORDER_TOPIC`：每秒 5000 条订单消息
- `INVENTORY_TOPIC`：每秒 3000 条库存变更消息
- `COUPON_TOPIC`：每秒 2000 条优惠券发放消息
- `NOTIFICATION_TOPIC`：每秒 10000 条通知消息

所有消息顺序写入同一个 CommitLog，总 TPS 达到 2 万条/秒。如果每个 Topic 独立文件，磁盘 IO 会变成 4 路并发随机写，TPS 可能只有 2000。

**🔍 源码解析：**

核心类：`CommitLog`、`MappedFileQueue`、`MappedFile`

```java
// 1. CommitLog 消息写入
public class CommitLog {
    private final MappedFileQueue mappedFileQueue;
    // 默认每个文件大小 1GB
    private final int mappedFileSize = 1024 * 1024 * 1024;

    public PutMessageResult putMessage(final MessageExtBrokerInner msg) {
        // 获取当前可写的 MappedFile
        MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();
        // 追加写入
        AppendMessageResult result = this.appendMessageCallback.doAppend(
            mappedFile.getFileFromOffset(),
            mappedFile,
            maxMessageSize,
            this.defaultMessageStore,
            msg
        );
    }
}

// 2. MappedFile：基于 Mmap 的文件映射
public class MappedFile extends ReferenceResource {
    private File file;
    private MappedByteBuffer mappedByteBuffer; // 核心：内存映射
    private final AtomicLong wrotePosition = new AtomicLong(0);

    // 写入消息
    public AppendMessageResult appendMessage(final MessageExtBrokerInner msg,
            final AppendMessageCallback cb) {
        int currentPos = this.wrotePosition.get();
        // 空间不足则返回需要创建新文件
        if (currentPos >= this.fileSize) return null;

        // 通过 MappedByteBuffer 写入
        ByteBuffer byteBuffer = this.mappedByteBuffer.slice();
        byteBuffer.position(currentPos);
        // 写入消息内容到 byteBuffer
        cb.doAppend(...);
        this.wrotePosition.addAndGet(msgLen);
    }
}

// 3. 刷盘操作
public boolean flush(final long flushPhysicOffset) {
    MappedByteBuffer mappedByteBuffer = this.mappedByteBuffer;
    // 如果 wrotePosition > committedPosition，说明有未提交的数据
    if (this.isAbleToFlush(flushPhysicOffset)) {
        mappedByteBuffer.force(); // 调用 OS fsync
        this.flushedPosition.set(this.wrotePosition.get());
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **CommitLog 文件大小**：默认 1GB，可通过 `mapedFileSizeCommitLog` 配置。悦茶平台保持默认，因为太大会导致 JVM GC 压力（`DirectByteBuffer` 的回收依赖 `cleaner`），太小会导致文件频繁创建。
2. **写入锁竞争**：`CommitLog` 使用 `ReentrantLock` 或 `CAS`（自旋锁）来保证写入顺序。RocketMQ 4.1+ 默认使用自旋锁（`putMessageSpin`），在高并发下性能更好。
3. **冷数据写入**：如果 CommitLog 所在的文件是「冷」的（不在 PageCache 中），写入会触发缺页中断，延迟增加。预热方案：Broker 启动时通过 `warmMappedFile` 方法逐页访问，将所有文件加载到 PageCache。
4. **加分点**：`doAppend` 方法中会为每条消息生成两个关键 ID：`msgId`（Broker 端生成，全局唯一）和 `keys`（用户设置的 Key，用于查询）。`msgId` 由 Broker IP + 端口 + CommitLog 偏移量拼接，保证全局唯一。

### 第6集：ConsumeQueue 的设计——消费者如何定位到 CommitLog 中的消息

**💡 核心回答：**

ConsumeQueue 是 CommitLog 的「索引文件」，每个 Topic 的每个 Queue 对应一个 ConsumeQueue 文件。它的设计非常精简：

**每条 ConsumeQueue 记录只有 20 字节：**
- `offset`（8 字节）：消息在 CommitLog 中的物理偏移
- `size`（4 字节）：消息在 CommitLog 中的长度
- `tagsCode`（8 字节）：消息 Tag 的哈希值（用于 Broker 端过滤）

消费者拉取消息的流程：
1. 从 ConsumeQueue 中按 Offset 读取 20 字节记录 → 得到 CommitLog 偏移和长度
2. 根据偏移从 CommitLog 中读取完整消息
3. 在 Consumer 端进行 Tag 二次过滤（因为 Broker 端的 tagsCode 是哈希值，可能哈希冲突）

```
     └──────────────────┬──────────────────────────┘
                        │
                        ▼
  ⑥ Consumer 端 Tag 校验
     消息实际Tag="deduct" → hash → 0x1C4E8A03
     与 CQ 中的 tagsCode=0x1C4E8A03 一致 → 匹配 ✓
     消费消息，处理库存扣减逻辑
                        │
                        ▼
  ⑦ 更新消费位点
     consumerOffset.json: ORDER_TOPIC@orderGroup@0 = 1 → 2
     （每 5 秒批量提交一次，不是每条都提交）
```

**ConsumeQueue 与 CommitLog 的关系（一图看懂偏移量映射）：**

```
ConsumeQueue (ORDER_TOPIC/queue-0)          CommitLog (混写所有Topic)

关键理解：
- CQ 只存当前 Topic+Queue 的消息索引，其他 Topic 的消息在 CQ 中"看不到"
- CQ 的"逻辑 offset"是连续递增的（0,1,2,3...），代表该 Queue 中的消息序号
- CommitLog 的"物理 offset"是全局的，所有 Topic 的消息混在一起
- CQ 记录中的 commitLogOffset 就是连接两者的"指针"
```

```java
// 1. ConsumeQueue 结构
public class ConsumeQueue {
    // 每条记录 20 字节
    public static final int CQ_STORE_UNIT_SIZE = 20; // 8+4+8
    private final MappedFileQueue mappedFileQueue;
    // 默认每个 ConsumeQueue 文件 30 万条记录 = 6MB
    private final int mappedFileSize = 300000 * CQ_STORE_UNIT_SIZE;

    // 写入一条记录
    public boolean putMessagePositionInfoWrapper(DispatchRequest request) {
        // 构建 20 字节记录
        ByteBuffer byteBuffer = ByteBuffer.allocate(CQ_STORE_UNIT_SIZE);
        byteBuffer.putLong(request.getCommitLogOffset());  // 8B
        byteBuffer.putInt(request.getMsgSize());           // 4B
        byteBuffer.putLong(request.getTagsCode());         // 8B
        // 写入 MappedFile
        mappedFile.appendMessage(byteBuffer.array());
    }
}

// 2. ReputMessageService：异步构建 ConsumeQueue
public class ReputMessageService extends ServiceThread {
    // reputFromOffset：当前分发到 CommitLog 的哪个位置
    private volatile long reputFromOffset = 0;

    @Override
    public void run() {
        while (!this.isStopped()) {
            // 从 CommitLog 读取新消息
            while (this.isCommitLogAvailable()) {
                // 构建 DispatchRequest
                DispatchRequest request = this.checkMessageAndReturnSize(
                    commitLogOffset, true);
                // 分发到 ConsumeQueue 和 IndexFile
                DefaultMessageStore.this.putMessagePositionInfo(request);
                this.reputFromOffset += request.getMsgSize();
            }
            Thread.sleep(1); // 1ms 轮询间隔
        }
    }

    // 分发监听器
    public interface DispatchRequest {
        void handle(DispatchRequest request);
    }
    // ConsumeQueue 的 DispatchRequest 实现：写入 CQ
    // IndexFile 的 DispatchRequest 实现：写入索引
}
```

**⚠️ 常见坑/加分回答：**

1. **ConsumeQueue 的延迟构建**：ReputMessageService 是异步的，ConsumeQueue 的构建有毫秒级延迟。如果消费者在消息写入 CommitLog 后立即拉取，可能拉不到（ConsumeQueue 还没构建完）。这就是为什么消费端有时看到的延迟。
2. **ConsumeQueue 文件清理**：ConsumeQueue 文件和 CommitLog 文件关联清理。当 CommitLog 的最老文件被删除时，对应的 ConsumeQueue 中过期记录也会被清理。
3. **TagsCode 的哈希冲突**：tagsCode 是 Tag 字符串的 hashCode（8 字节），不同 Tag 可能产生相同 hashCode。Broker 端基于 tagsCode 过滤可能有误判，所以 Consumer 端需要二次精确过滤。
4. **加分点**：`reputFromOffset` 是 ConsumeQueue 构建进度的标记。Broker 启动时会从 CommitLog 的最后一条消息位置开始构建（`maxOffset - lastMsgSize`），而不是从头开始，节省启动时间。

### 第7集：IndexFile 的设计——消息索引的哈希链表结构

**💡 核心回答：**

IndexFile 用于支持按消息 Key 和时间范围查询消息。其核心数据结构是一个**哈希链表**：

**IndexFile 结构（每个文件固定大小）：**
- **Header**（40 字节）：beginTimestamp、endTimestamp、beginPhyOffset、endPhyOffset、hashSlotNum、indexNum
- **Hash Slot 表**（默认 500 万个槽位，每个 4 字节）：存储每个哈希值的第一个 Index 位置
- **Index 链表**（默认 2000 万条，每条 20 字节）：keyHash + phyOffset + storeTimestamp + nextIndex

**查询流程：**
1. 对 Key 做哈希，定位到 Hash Slot
2. 从 Slot 中取出第一个 Index 的位置
3. 沿着 nextIndex 链表遍历，逐个比对 keyHash（解决哈希冲突）
4. 根据时间范围过滤
5. 找到匹配的 Index，从中取出 CommitLog 偏移量
6. 从 CommitLog 读取完整消息

**IndexFile 文件内部布局（磁盘上的真实结构）：**

```
单个 IndexFile 文件（400MB）：

offset=0        offset=40          offset=20,000,040              offset=400MB（文件末尾）
├────────────────┼─────────────────┼──────────────────────────────┼───────┐
│ Header (40B)   │ Hash Slot 区域   │ Index 链表区域                │ 未使用 │
│                │ (500万 × 4B     │ (2000万 × 20B               │ 空间  │
│                │  = 20MB)        │  = 400MB)                    │       │
├────────────────┼─────────────────┼──────────────────────────────┼───────┤
│                │                 │                               │       │
│ beginTimestamp │ Slot[0]  = 3    │ Index[0]: {keyHash, phyOff,  │       │
│ endTimestamp   │ Slot[1]  = 0    │   timestamp, next=0}          │       │
│ beginPhyOffset │ Slot[2]  = 7    │ Index[1]: {keyHash, phyOff,   │       │
│ endPhyOffset   │ Slot[3]  = 5    │   timestamp, next=0}          │       │
│ hashSlotNum    │ ...             │ Index[2]: {keyHash, phyOff,   │       │
│ indexNum       │ Slot[4999999]=0 │   timestamp, next=0}          │       │
│                │                 │ Index[3]: {keyHash, phyOff,   │       │
│ (40 bytes)     │ (20 MB)        │   timestamp, next=1}  ← 链表  │       │
│                │                 │   指向Index[1]                 │       │
│                │                 │ ...                           │       │
│                │                 │ Index[7]: {keyHash, phyOff,   │       │
│                │                 │   timestamp, next=0}          │       │
│                │                 │                               │       │
│                │                 │ (400 MB)                     │       │
└────────────────┴─────────────────┴──────────────────────────────┴───────┘
```

**哈希链表查询过程（以查询 Key="order_20240101_001" 为例）：**

```
  ① 计算哈希
     hash("order_20240101_001") = 12345678
                         │
                         ▼
  ② 定位 Hash Slot
     slotIndex = 12345678 % 5000000 = 2345678
     Slot 位置 = 40 + 2345678 × 4 = 9,382,752 字节处
     读取 Slot 值 = 15  ← 这是链表头节点的 Index 编号
                         │
                         ▼
  ③ 遍历链表（从头到尾）
     
     Slot[2345678] = 15（链表头）
         │
         ▼
     Index[15]: {keyHash=12345678, phyOffset=5242880,
                 timestamp=1721534400, next=8}
                 ↑ keyHash 匹配 ✓ → 检查时间范围 ✓
                 → 但继续遍历（可能有同 hash 的不同 Key）
         │
         ▼ (next=8)
     Index[8]: {keyHash=99887766, phyOffset=3145728,
                timestamp=1721530800, next=0}
                ↑ keyHash 不匹配 ✗ → 跳过（不同 Key 碰巧落到同一 Slot）
         │
         ▼ (next=0，链表结束)
     
     结果：找到 1 条匹配 → phyOffset=5242880
                         │
                         ▼
  ④ 从 CommitLog 读取消息
     CommitLog offset=5242880 → 读取完整消息
     → 验证消息的 Key 确实是 "order_20240101_001" ✓
     → 返回给调用方

注意：IndexFile 只做"粗定位"，最终要回到 CommitLog 读完整消息
      哈希冲突时（不同 Key 落到同一 Slot），靠 keyHash 字段过滤
      极端情况下同一 Slot 链表很长，性能退化为 O(n)
```

**🔍 源码解析：**

核心类：`IndexFile`、`IndexHeader`

```java
public class IndexFile {
    // 每个 IndexFile 文件 400MB
    // Hash Slot 数量：默认 500 万
    private static final int HASH_SLOT_SIZE = 4;
    // 每个 Index 条目 20 字节：keyHash(4) + phyOffset(8) + timestamp(4) + nextIndex(4)
    private static final int INDEX_SIZE = 20;
    // 最大 Index 数：2000 万
    private static final int MAX_INDEX_NUM = 20000000;

    private final MappedFile mappedFile;
    private final ByteBuffer mappedByteBuffer;
    // Hash Slot 区域起始偏移 = Header(40B)
    private final int hashSlotOffset = 40;
    // Index 区域起始偏移 = Header(40B) + HashSlot(500万*4B)
    private final int indexOffset = 40 + 5000000 * 4;

    // 写入索引
    public boolean putKey(final String key, final long phyOffset, final long storeTimestamp) {
        int keyHash = indexKeyHashMethod(key); // 对 key 做 hash
        int slotPos = hashSlotOffset + keyHash % hashSlotNum * HASH_SLOT_SIZE;

        // 读取当前 slot 值（链表头）
        int absSlotPos = this.hashSlotOffset + (keyHash % hashSlotNum) * 4;
        int slotValue = this.mappedByteBuffer.getInt(absSlotPos);

        // 写入新的 Index 条目
        int indexPos = indexOffset + (indexNum % MAX_INDEX_NUM) * INDEX_SIZE;
        this.mappedByteBuffer.putInt(indexPos, keyHash);        // 4B
        this.mappedByteBuffer.putLong(indexPos + 4, phyOffset); // 8B
        this.mappedByteBuffer.putInt(indexPos + 12, (int)(storeTimestamp / 1000)); // 4B
        this.mappedByteBuffer.putInt(indexPos + 16, slotValue); // 4B (nextIndex)

        // 更新 Slot 头指向新的 Index
        this.mappedByteBuffer.putInt(absSlotPos, indexNum);
    }

    // 查询索引
    public void selectPhraseOffset(final String key, final long begin, final long end,
            final List<Long> phyOffsets) {
        int keyHash = indexKeyHashMethod(key);
        int slotPos = hashSlotOffset + (keyHash % hashSlotNum) * 4;
        int slotValue = this.mappedByteBuffer.getInt(slotPos);

        // 沿链表遍历
        while (slotValue > 0) {
            int indexPos = indexOffset + slotValue * INDEX_SIZE;
            int readKeyHash = this.mappedByteBuffer.getInt(indexPos);
            long readPhyOffset = this.mappedByteBuffer.getLong(indexPos + 4);
            int readTimestamp = this.mappedByteBuffer.getInt(indexPos + 12);

            if (readKeyHash == keyHash && readTimestamp >= begin/1000 && readTimestamp <= end/1000) {
                phyOffsets.add(readPhyOffset);
            }
            // 下一个节点
            slotValue = this.mappedByteBuffer.getInt(indexPos + 16);
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **IndexFile 的容量限制**：每个 IndexFile 最多存 2000 万条索引，超过后会创建新文件。如果同一 Key 的消息很多，Slot 链表会很长，查询性能下降。悦茶平台建议 Key 要尽量分散。
2. **哈希冲突处理**：不同 Key 可能映射到同一个 Slot（链表中 keyHash 不同），查询时需要比对 keyHash 过滤。极端情况下所有 Key 哈希到同一个 Slot，性能退化为 O(n)。
3. **IndexFile 是可选的**：可以通过 `messageIndexEnable=false` 关闭 IndexFile，减少磁盘 IO。如果不需要按 Key 查询消息，可以关闭以提升性能。
4. **加分点**：一个消息可以设置多个 Key（用空格分隔），每个 Key 都会写入 IndexFile。悦茶平台设置 Key 为 `orderId storeId`，这样既可按订单号查，也可按门店号查。

### 第8集：存储文件的清理策略——文件保留与删除机制

**💡 核心回答：**

RocketMQ 对 CommitLog、ConsumeQueue、IndexFile 都有清理机制，通过 `CleanCommitLogService` 和 `CleanConsumeQueueService` 两个定时服务完成：

**清理触发条件（满足任一即触发）：**
1. **磁盘空间不足**：磁盘使用率超过 `diskMaxUsedSpaceRatio`（默认 75%）
2. **文件过期**：文件最后修改时间超过 `fileReservedTime`（默认 72 小时 = 3 天）
3. **手动触发**：通过 AdminTools 或 Console 手动删除

**两种清理策略：**
- **删除（Delete）**：直接删除过期的 MappedFile，释放磁盘空间。默认策略。
- **清理（Clean）**：将文件内容填充为 0（`deleteWhen=04` 表示凌晨 4 点清理）。适用于需要「安全删除」的场景。

**清理的安全保障：**
- 不会删除正在被写入的文件（`wrotePosition > 0` 的文件）
- 不会删除最近修改的文件（即使超过保留时间，如果在写入中也不删除）
- ConsumeQueue 的清理依赖 CommitLog 的清理：CommitLog 删除后，对应的 ConsumeQueue 中过期部分被清理

**📦 实际例子：**

悦茶平台存储清理策略：
- 生产环境：`fileReservedTime = 72`（3 天），`diskMaxUsedSpaceRatio = 75`
- 压测环境：`fileReservedTime = 4`（4 小时），因为压测不需要回溯
- 合规要求：订单 Topic 需要保留 180 天，通过配置独立的 `fileReservedTime` 或使用消息备份到 OSS

**🔍 源码解析：**

核心类：`CleanCommitLogService`、`MappedFileQueue`

```java

public class CleanCommitLogService {
    private final int fileReservedTime = 72; // 小时
    private final int diskMaxUsedSpaceRatio = 75; // 百分比

    @Override
    public void run() {
        while (!this.isStopped()) {
            // 每 10s 执行一次清理检查
            this.waitForRunning(interval);

            // 1. 检查磁盘空间
            if (this.isSpaceFull()) {
                this.deleteExpiredFiles();
            }
            // 2. 检查文件是否过期
            int count = this.deleteExpiredFilesByTime();
        }
    }

    // 删除过期文件
    private int deleteExpiredFilesByTime() {
        // 获取所有 MappedFile
        MappedFile[] files = mappedFileQueue.getMappedFiles();
        int deleteCount = 0;
        for (MappedFile file : files) {
            // 跳过正在写入的文件
            if (file.isInCreateEditTime()) continue;

            long lastModified = file.getLastModified();
            // 超过保留时间
            if (lastModified + fileReservedTime * 3600 * 1000 < System.currentTimeMillis()) {
                // 确保不是最近的两个文件（保护期）
                if (mappedFileQueue.getMinOffsetInQueue() >= file.getFileSize()) {
                    mappedFileQueue.deleteExpiredFile(file);
                    deleteCount++;
                }
            }
        }
        return deleteCount;
    }

    // 磁盘空间检查
    private boolean isSpaceFull() {
        double ratio = getFileUsageRatio();
        return ratio >= diskMaxUsedSpaceRatio / 100.0;
    }
}

    public boolean deleteExpiredFileByOffset(long offset, int unitSize) {
        // 根据 offset 找到需要删除的文件
        // 从 committedFiles 中移除并调用 file.destroy()
    }

    // 文件销毁
    public boolean destroy(final long interval) {
        // 1. 关闭 MappedByteBuffer
        this.mappedByteBuffer.force();
        // 2. 关闭文件通道
        this.fileChannel.close();
```

**⚠️ 常见坑/加分回答：**

1. **清理不及时的坑**：`CleanCommitLogService` 每 10s 执行一次，且只在凌晨 4 点执行磁盘空间检查（`cleanResourceTimestamp = 04`）。如果白天磁盘突然满了，不会立即清理。解决方案：设置 `diskMaxUsedSpaceRatio` 更保守（如 70%）。
2. **删除 vs 清理的区别**：`deleteWhen` 配置的是「清理时间」，在这个时间之前只删除过期文件，在这个时间之后才会清理未过期的文件来释放空间。
3. **ConsumeQueue 的清理依赖**：ConsumeQueue 的文件清理不是独立的，而是当 CommitLog 的文件被删除后，对应的 ConsumeQueue 条目才被视为过期。
4. **加分点**：悦茶平台在凌晨 2-5 点有大量定时任务（日报生成、数据归档），这个时间段正好和 RocketMQ 的清理时间（凌晨 4 点）冲突。建议将 RocketMQ 清理时间调整为凌晨 6 点，或确保存储有足够余量。

## 第3系列：消息消费

### 第9集：推模式（Push）vs 拉模式（Pull）vs 长轮询的区别

**💡 核心回答：**

| 模式 | 实现方式 | 实时性 | 资源消耗 | RocketMQ 中的实现 |
|------|---------|-------|---------|-----------------|
| Pull | Consumer 主动轮询拉取 | 取决于轮询间隔 | 低（按需拉取） | `DefaultMQPullConsumer` |
| Push | 服务端推送 | 高 | 高（需维护连接） | 实际不存在真正的 Push |
| 长轮询 | Consumer 拉取，Broker 无消息时 hold 住请求 | 高 | 中 | **Push 模式的底层实现** |

**RocketMQ 的 Push 模式本质是长轮询**：
- `DefaultMQPushConsumer` 内部维护一个 `PullMessageService` 线程
- 该线程不断向 Broker 发送 Pull 请求
- Broker 端如果没有新消息，不会立即返回，而是 hold 住连接等待（默认最多 15s）
- 有新消息或超时时才返回响应
- Consumer 收到响应后处理消息，然后立即发起下一次 Pull 请求

**📦 实际例子：**

悦茶平台使用场景：
- **Push 模式**：订单状态变更通知（实时性要求高，需要秒级触达）
- **Pull 模式**：数据同步任务（定时批量拉取，控制消费速率）
- **长轮询的体现**：悦茶门店的「新订单通知」消费者使用 Push 模式，底层实际是长轮询，当有新订单消息时几乎实时推送。

**🔍 源码解析：**

核心类：`DefaultMQPushConsumerImpl`、`PullMessageService`

```java
// 1. PushConsumer 启动后，启动 PullMessageService
public class DefaultMQPushConsumerImpl {
    public synchronized void start() throws MQClientException {
        // 启动 PullMessageService 线程
        this.pullMessageService.start();
        // 启动 RebalanceService
        this.rebalanceService.start();
    }
}

// 2. PullMessageService：长轮询的核心
public class PullMessageService extends ServiceThread {
    private final LinkedBlockingQueue<PullRequest> pullRequestQueue = new LinkedBlockingQueue<>();

    @Override
    public void run() {
        while (!this.isStopped()) {
            // 从队列中取出 PullRequest
            PullRequest pullRequest = this.pullRequestQueue.take();
            // 执行拉取
            this.pullMessage(pullRequest);
        }
    }

    private void pullMessage(final PullRequest pullRequest) {
        // 向 Broker 发送 Pull 请求（长轮询模式）
        this.defaultMQPushConsumerImpl.pullBlockIfNotFound(
            pullRequest.getMessageQueue(),
            null,
            pullRequest.getNextOffset(),
            32, // 每次拉取 32 条
            new PullCallback() {
                @Override
                public void onSuccess(PullResult pullResult) {
                    // 处理拉取到的消息
                    processPullResult(pullRequest, pullResult);
                    // 立即发起下一次 Pull（形成持续轮询）
                    this.executePullRequestLater(pullRequest, 0);
                }

                @Override
                public void onException(Throwable e) {
                    // 异常后延迟重试
                    this.executePullRequestLater(pullRequest, 3000);
                }
            }
        );
    }
}

// 3. Broker 端长轮询：PullMessageProcessor
public class PullMessageProcessor {
    private final long suspendMaxTime = 15000; // 最长 hold 15 秒

    public RemotingCommand processRequest(final ChannelHandlerContext ctx,
            final RemotingCommand request) {
        // 检查是否有新消息
        GetMessageResult getResult = brokerController.getMessageStore().getMessage(...);

        switch (getResult.getStatus()) {
            case FOUND:
                // 有消息，立即返回
                return buildResponse(getResult);
            case NO_MATCHED_MESSAGE:
            case OFFSET_OVERFLOW_ONE:
            case OFFSET_OVERFLOW_BADLY:
                // 无消息，检查是否开启长轮询
                if (this.brokerController.getBrokerConfig().isLongPollingEnable()) {
                    // 将请求挂起，等待新消息到达或超时
                    this.suspendPullRequest(request, suspendMaxTime);
                } else {
                    // 短轮询：立即返回 NO_MESSAGE
                    return buildResponse(NO_MESSAGE);
                }
        }
    }

    // 挂起请求，有新消息时唤醒
    private void suspendPullRequest(RemotingCommand request, long maxSuspendTime) {
        PullRequest pullRequest = new PullRequest(request, ctx);
        // 放入等待队列
        this.pullRequestHoldService.suspendPullRequest(topic, queueId, pullRequest);
        // 设置超时定时器
        scheduledExecutorService.schedule(() -> {
            this.pullRequestHoldService.notifyMessageArriving(topic, queueId);
        }, maxSuspendTime, TimeUnit.MILLISECONDS);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **长轮询 vs 短轮询的性能差异**：短轮询（每次无消息立即返回）会导致 Consumer 频繁发起请求，网络开销大。长轮询通过 hold 住请求，大幅减少无效请求。悦茶平台生产环境长轮询减少了 80% 的网络请求量。
2. **Pull 批量的设置**：`pullBatchSize` 默认 32，悦茶平台根据消息体大小调整。小消息（< 1KB）可调大到 128，大消息（> 10KB）调小到 16。
3. **拉取间隔**：`pullInterval` 默认为 0（连续拉取），如果消费者处理能力强，保持 0 可最大化吞吐；如果处理不过来，设置 `pullInterval > 0` 降低拉取频率。
4. **加分点**：Broker 端的 `PullRequestHoldService` 在 `ReputMessageService` 构建出新的 ConsumeQueue 条目后，会主动通知被 hold 的 Pull 请求有新消息到达，实现「准实时」推送效果。

### 第10集：消费者组和消息队列的重平衡（Rebalance）机制

**💡 核心回答：**

Rebalance（重平衡）是 RocketMQ 消费者组中消费者与消息队列的动态分配机制。核心目标：**一个队列在同一时刻只能被一个消费者消费**。

**触发时机：**
1. 消费者上线/下线（加入/退出 ConsumerGroup）
2. Topic 的队列数变化（扩容/缩容 Broker）
3. 订阅关系变化
4. 定时触发：每 20s 执行一次 `doRebalance`

**分配算法：**
- **平均分配（默认）**：`AllocateMessageQueueAveragely`，将队列尽可能均匀分配给消费者
- **环形分配**：`AllocateMessageQueueAveragelyByCircle`，按环形依次分配
- **机房分配**：`AllocateMessageQueueByMachineRoom`，优先分配同机房的队列

**Rebalance 流程：**
1. 获取当前 Topic 的所有 MessageQueue
2. 获取当前 ConsumerGroup 的所有 ConsumerId
3. 按分配算法计算当前消费者应该消费哪些队列
4. 与当前持有的队列比较，新增/移除订阅

**📦 实际例子：**

悦茶平台有 3 个消费者实例消费 `ORDER_TOPIC`（8 个队列）：
- Consumer-A（门店集群1）：分配 queue-0, queue-1, queue-2
- Consumer-B（门店集群2）：分配 queue-3, queue-4
- Consumer-C（门店集群3）：分配 queue-5, queue-6, queue-7

当 Consumer-B 宕机后，触发 Rebalance：
- Consumer-A：分配 queue-0, queue-1, queue-2, queue-3, queue-4
- Consumer-C：分配 queue-5, queue-6, queue-7

**🔍 源码解析：**

核心类：`RebalanceService`、`RebalanceImpl`

```java
// 1. RebalanceService 定时触发
public class RebalanceService extends ServiceThread {
    @Override
    public void run() {
        while (!this.isStopped()) {
            this.waitForRunning(waitInterval); // 默认 20s
            this.mqClientFactory.doRebalance();
        }
    }
}

// 2. RebalanceImpl 核心逻辑
public abstract class RebalanceImpl {
    // 每个 Topic 的 Rebalance
    public void doRebalance(final boolean isOrder) {
        Map<String, SubscriptionData> subTable = this.getSubscriptionInner();
        for (Map.Entry<String, SubscriptionData> entry : subTable.entrySet()) {
            final String topic = entry.getKey();
            try {
                this.rebalanceByTopic(topic, isOrder);
            } catch (Exception e) { ... }
        }
    }

    private void rebalanceByTopic(final String topic, final boolean isOrder) {
        // 1. 获取 Topic 的所有 MessageQueue
        Set<MessageQueue> mqSet = this.topicSubscribeInfoTable.get(topic);
        // 2. 获取 ConsumerGroup 中所有 ConsumerId
        List<String> cidAll = this.mqClientFactory.findConsumerIdList(topic, consumerGroup);

        // 3. 按分配算法计算当前消费者应持有的队列
        AllocateMessageQueueStrategy strategy = this.allocateMessageQueueStrategy;
        List<MessageQueue> allocatedResult = strategy.allocate(
            consumerGroup, currentCID, mqSet, cidAll);

        // 4. 与当前持有的队列对比
        Set<MessageQueue> currentSet = new HashSet<>(processQueueTable.keySet());
        for (MessageQueue mq : allocatedResult) {
            if (!currentSet.contains(mq)) {
                // 新增的队列：创建 ProcessQueue，开始拉取
                this.messageQueueChanged(topic, mq, ...);
            }
        }
        for (MessageQueue mq : currentSet) {
            if (!allocatedResult.contains(mq)) {
                // 需要移除的队列：更新 ProcessQueue 为 dropped
                ProcessQueue pq = this.processQueueTable.get(mq);
                pq.setDropped(true);
                this.removeProcessQueue(mq);
            }
        }
    }
}

// 3. 平均分配算法
public class AllocateMessageQueueAveragely implements AllocateMessageQueueStrategy {
    public List<MessageQueue> allocate(String consumerGroup, String currentCID,
            List<MessageQueue> mqAll, List<String> cidAll) {
        int index = cidAll.indexOf(currentCID);
        int mod = mqAll.size() % cidAll.size();
        int averageSize = mod <= index ?
            mqAll.size() / cidAll.size() :
            mqAll.size() / cidAll.size() + 1;
        int startIndex = mod <= index ?
            index * averageSize :
            index * averageSize + mod;
        int range = Math.min(averageSize, mqAll.size() - startIndex);

        List<MessageQueue> result = new ArrayList<>();
        for (int i = 0; i < range; i++) {
            result.add(mqAll.get((startIndex + i) % mqAll.size()));
        }
        return result;
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **Rebalance 过程中的消息重复**：消费者 A 持有 queue-0，Rebalance 后分配给消费者 B。但消费者 A 可能还有 queue-0 的消息正在处理。B 开始拉取 queue-0 后，可能消费到 A 已经消费但未提交 Offset 的消息，导致重复。解决方案：消费者端做幂等处理。
2. **消费者数量 > 队列数**：多出的消费者不会分配到任何队列，处于空闲状态。悦茶平台建议队列数至少为消费者数的 2 倍，保证负载均衡。
3. **Rebalance 延迟**：定时任务每 20s 执行一次，加上心跳上报间隔（30s），消费者下线后最多需要 50s 才能完成 Rebalance。
4. **加分点**：`ProcessQueue` 是每个队列的消费状态容器，包含 `msgAccumulation`（积压消息数）、`lastConsumeTimestamp`（最后消费时间戳）等关键指标。Rebalance 时会检查 ProcessQueue 的状态，如果 `droped=true` 则停止拉取。

### 第11集：消费进度（Offset）的管理——集群消费 vs 广播消费

**💡 核心回答：**

消费进度管理是消费者「记录自己消费到哪了」的机制。RocketMQ 支持两种消费模式：

| 特性 | 集群消费（Clustering） | 广播消费（Broadcasting） |
|------|---------------------|---------------------|
| 消息投递 | 每条消息只投递给组内一个消费者 | 每条消息投递给组内所有消费者 |
| Offset 存储 | Broker 端 | Consumer 本地 |
| 适用场景 | 任务处理（只需处理一次） | 本地缓存刷新（每个节点都需要处理） |

**Offset 存储位置：**

- **集群消费**：Offset 存储在 Broker 端的 `config/consumerOffset.json` 文件中，Key 为 `topic@consumerGroup@queueId`。Consumer 定时（每 5s）向 Broker 提交 Offset。
- **广播消费**：Offset 存储在 Consumer 本地的 `~/.rocketmq_offsets/{clientId}/offsets.json` 文件中。每个 Consumer 实例独立管理自己的进度。

- 集群消费：消费失败后，消息进入重试 Topic（`%RETRY%ConsumerGroup`），延迟重试，最大重试 16 次后进入死信队列（`%DLQ%ConsumerGroup`）

**📦 实际例子：**

- **集群消费**：订单处理服务。一条订单消息只需要一个消费者处理一次，使用集群消费保证不重复处理。
- **广播消费**：门店商品价格缓存更新。当价格变更时，所有门店节点的缓存都需要更新，使用广播消费确保每个节点都收到消息。

**⚠️ 常见坑/加分回答：**

1. **Offset 提交延迟导致重复消费**：Consumer 消费了消息但还没提交 Offset 就宕机了，重启后会从上次提交的 Offset 开始消费，导致消息重复。这就是为什么消费端必须做幂等。
2. **广播消费的 Offset 不共享**：每个 Consumer 实例独立管理 Offset。如果 Consumer 实例扩容，新实例会从 0 开始消费所有消息。悦茶平台的缓存刷新服务在扩容时会重复处理所有消息，需要做好幂等。
3. **重置 Offset 的坑**：通过 `consumer.resetOffsetByTimestamp()` 可以重置消费位点，但集群消费和广播消费的实现不同。集群消费需要在 Broker 端重置，广播消费只需清除本地 Offset 文件。
4. **加分点**：悦茶平台在生产中发现，消费者重启时 `offsetTable` 为空，会从 Broker 拉取最新 Offset（默认行为），导致重启期间积压的消息被跳过。解决方案：设置 `consumer.setConsumeFromWhere(ConsumeFromWhere.CONSUME_FROM_FIRST_OFFSET)` 确保从最早未消费的消息开始。

### 第12集：顺序消息的实现原理——全局顺序 vs 分区顺序

**💡 核心回答：**

RocketMQ 的顺序消息分为两种：

| 类型 | 说明 | 实现方式 |
|------|------|---------|
| 全局顺序 | 同一个 Topic 下所有消息严格有序 | 只有一个队列（不现实，性能极差） |
| 分区顺序 | 同一个 Sharding Key 的消息有序 | 相同 Key 路由到同一队列，消费端单线程消费 |

```

│                                                                                 │

│  消息: order-001 支付     ─┤  hash("order-001") % 4 = 3                        │
│  消息: order-001 制作     ─┼──────────────────────►  Queue-3  (Broker-A)       │
│  消息: order-001 完成     ─┘                                                    │
│                                                                                 │
│  消息: order-002 创建     ─┐                                                    │
│  消息: order-002 支付     ─┤  hash("order-002") % 4 = 1                        │
│  消息: order-002 制作     ─┼──────────────────────►  Queue-1  (Broker-A)       │
│  消息: order-002 完成     ─┘                                                    │
│                                                                                 │
│  消息: order-003 创建     ─┐                                                    │
│  消息: order-003 支付     ─┤  hash("order-003") % 4 = 3  ◄── 和order-001同队列  │
│  消息: order-003 制作     ─┼──────────────────────►  Queue-3  (Broker-A)       │
```

**发送端保证有序**：
- 使用 `MessageQueueSelector` 将相同 Sharding Key 的消息发送到同一个 MessageQueue
- 默认通过 `hash(shardingKey) % queueSize` 路由

**消费端保证有序**：
- 同一个 MessageQueue 在同一时刻只有一个线程消费（`ConsumeMessageOrderlyService`）
- 通过 `ProcessQueue.lock()` 加锁保证
- 消费失败后不会跳过，而是重试当前消息（本地重试 + 发送到重试 Topic）

悦茶平台「订单状态流转」场景：

```java
// 发送端：同一个订单的消息发送到同一个队列
Message msg = new Message("ORDER_STATUS_TOPIC", tag, body);
// Sharding Key = orderId
producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        String orderId = (String) arg;
        int index = Math.abs(orderId.hashCode()) % mqs.size();
        return mqs.get(index);

// 订单状态变更消息流（同一 orderId 保证有序）：
// 1. 订单创建 → queue-3

// 3. 开始制作 → queue-3
// 4. 制作完成 → queue-3
// 5. 配送中 → queue-3
```

**🔍 源码解析：**

核心类：`ConsumeMessageOrderlyService`、`MessageQueueSelector`

```java
// 1. 发送端选择队列
public class DefaultMQProducerImpl {
    public SendResult send(Message msg, MessageQueueSelector selector, Object arg) {
        // 通过 selector 选择队列（而非默认轮询）
        MessageQueue mq = selector.select(
            topicPublishInfo.getMessageQueueList(), msg, arg);
        // 发送到选中的队列
        return this.sendKernelImpl(msg, mq, ...);
    }
}

// 2. 消费端顺序消费
public class ConsumeMessageOrderlyService {
    public void submitConsumeRequest(final List<MessageExt> msgs,
            final ProcessQueue processQueue, final MessageQueue messageQueue,
            final boolean disordered) {

        if (!disordered) {
            // 对 MessageQueue 加锁（保证同一时刻只有一个线程消费）
            while (true) {
                if (this.tryLock(messageQueue, processQueue)) {
                    break;
                }
            }
        }

        // 提交到消费线程池（单线程池 per queue）
        this.consumeExecutor.submit(new ConsumeRequest(
            msgs, processQueue, messageQueue));
    }

    // 消费请求
    class ConsumeRequest implements Runnable {
        @Override
        public void run() {
            // 遍历消息，按顺序逐条消费
            for (MessageExt msg : msgs) {
                ConsumeOrderlyStatus status = listener.consumeMessage(
                    Collections.singletonList(msg), context);

                switch (status) {
                    case SUCCESS:
                        // 提交 Offset，处理下一条
                        processQueue.commit();
                        break;
                    case SUSPEND_CURRENT_QUEUE_A_MOMENT:
                        // 消费失败，延迟重试当前消息
                        // 本地重试 consumeOrderlyMaxRetry 次（默认 Integer.MAX）
                        if (retryTimes > maxRetryTimes) {
                            // 超过最大重试次数，发送到重试 Topic
                            sendMessageBack(msg);
                        } else {
                            // 延迟后重试
                            scheduledExecutor.schedule(this, suspendTime, TimeUnit.MILLISECONDS);
                        }
                        return; // 停止处理后续消息，保证顺序
                }
            }
            // 解锁
            processQueue.unlock();
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **顺序消息的性能**：由于同一队列单线程消费，TPS 受限于单线程处理能力。悦茶平台通过增加队列数（如从 4 个增加到 16 个）来提升并行度，前提是不同 Sharding Key 分布在不同队列。
2. **消费失败不能跳过**：顺序消息消费失败时必须重试当前消息，不能直接跳到下一条。否则后续消息的消费顺序就乱了。这是与普通消息最大的区别。
3. **Rebalance 导致顺序中断**：Rebalance 期间，队列从一个消费者转移到另一个消费者，可能存在短暂的消息乱序。解决方案：使用 `lock` 机制，只有拿到锁的消费者才能消费。
4. **加分点**：悦茶平台对 Sharding Key 的选择非常讲究。订单相关的消息用 `orderId` 做 Key，同一门店的消息用 `storeId` 做 Key。如果一个消息需要同时保证门店顺序和订单顺序，只能选一个维度。悦茶选择了 `orderId`，因为订单状态流转是强顺序需求，而门店级别只需要最终一致。

**发送端保障：**
- 使用同步发送，等待 Broker 确认
- 设置 `retryTimesWhenSendFailed = 3`（重试 3 次，不同 Broker）
- 发送失败后降级：写入数据库待重发、写入本地 MQ（如 RocksDB）

**Broker 端保障：**
- 同步刷盘：`flushDiskType = SYNC_FLUSH`
- 同步复制：`brokerRole = SYNC_MASTER`
- 至少 2 个 Broker 组，互为备份

**消费端保障：**
- 消费前不提交 Offset（处理成功后再提交）
- 消费失败返回 `RECONSUME_LATER`，进入重试 Topic
- 重试 16 次后进入死信队列（DLQ），人工介入处理

```java
    private SendResult sendDefaultImpl(Message msg, ...) {
        int timesTotal = communicationMode == CommunicationMode.SYNC ?
            (1 + this.defaultMQProducer.getRetryTimesWhenSendFailed()) : 1;

        for (int times = 0; times < timesTotal; times++) {
            try {
                SendResult result = this.sendKernelImpl(msg, mq, ...);
                if (result.getSendStatus() == SendStatus.SEND_OK) {
                    return result;
                }
                // 非 SEND_OK，尝试不同 Broker
                lastBrokerName = mq.getBrokerName();
            } catch (Exception e) {
                lastBrokerName = mq.getBrokerName();
            }
        }
        throw new MQClientException("发送失败，已重试" + timesTotal + "次", null);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **同步发送≠不丢消息**：同步发送只保证消息到达 Broker，但 Broker 如果异步刷盘，消息可能还在 PageCache 中。必须配合 `SYNC_FLUSH` 才能真正做到消息持久化。
2. **消费端的「至少一次」语义**：RocketMQ 保证消息「至少被消费一次」，不是「精确一次」。这意味着消费者必须实现幂等。
3. **重试 Topic 的消息堆积**：消费失败进入 `%RETRY%ConsumerGroup` 后，延迟时间会递增（1s, 5s, 10s, ..., 2h）。如果持续失败，重试消息会大量堆积。悦茶平台设置了报警，当重试消息堆积超过 1000 条时触发告警。
4. **加分点**：悦茶平台在关键业务场景采用「本地消息表」模式：先写数据库事务（订单 + 消息记录），再由定时任务扫描消息记录发送到 MQ。这样即使 MQ 完全不可用，消息也不会丢失，恢复后自动补发。

**⚠️ 常见坑/加分回答：**

1. **Redis 去重的 Key 过期时间**：如果 Key 过期太早，在过期后的重复消息会绕过幂等检查。建议设置 24 小时或更长。悦茶平台根据业务场景设置，订单类 72 小时，优惠券类 24 小时。
2. **数据库唯一索引的局限**：只能防止重复插入，不能防止重复更新。对于更新操作，需要配合乐观锁。
3. **分布式事务中的幂等**：如果消息消费涉及多个数据库操作，单库的唯一索引不够。需要引入分布式幂等 Key（如 Redis 或数据库幂等表）。
4. **加分点**：悦茶平台采用「幂等表」模式：在业务数据库中维护一张 `idempotent_record` 表，记录已处理的消息 ID。消费前先查该表，处理成功后写入记录。这样即使 Redis 故障，仍然可以通过数据库保障幂等。

**RocketMQ 4.x（ScheduledTopic 方式）：**
- 支持固定延迟等级：`1s, 5s, 10s, 30s, 1m, 2m, 3m, ..., 2h`（共 18 个等级）
- 不支持任意时间延迟
- 原理：
  1. Producer 发送延迟消息，指定延迟等级
  2. Broker 将消息存储到 `SCHEDULE_TOPIC_XXXX` 的对应等级队列中
  3. `ScheduleMessageService` 定时扫描各等级队列
  4. 到达延迟时间后，将消息转移回真实 Topic
  5. Consumer 从真实 Topic 消费

**RocketMQ 5.x（TimerWheel 方式）：**
- 支持任意精度的延迟（毫秒级）
- 基于时间轮算法，性能更优
- 原理类似但使用时间轮（TimerWheel）替代固定等级

- **配送超时提醒**：骑手接单后 15 分钟未取餐，发送超时提醒（延迟等级 15 = 20min，近似）
- **门店数据日报**：每天凌晨 2 点生成前一天的销售日报（延迟等级 18 = 2h，循环调度）

**🔍 源码解析：**

核心类：`ScheduleMessageService`（Broker 端）

```java
// 1. 延迟消息存储
public class ScheduleMessageService {
    // 延迟等级映射表
    private final Map<Integer, Long> delayLevelTable = new LinkedHashMap<>();
    // 初始化：1->1s, 2->5s, 3->10s, ..., 18->2h

    // 消息存储到 SCHEDULE_TOPIC_XXXX
    public void executeScheduleMessageDelivery(MessageExtBrokerInner msg) {
        int delayLevel = msg.getDelayTimeLevel();
        // 修改 Topic 为 SCHEDULE_TOPIC_XXXX
        msg.setTopic(SCHEDULE_TOPIC);
        // 修改 QueueId 为 delayLevel - 1（每个等级一个队列）
        msg.setQueueId(delayLevel - 1);
        // 存储到 CommitLog
        this.defaultMessageStore.putMessage(msg);
    }

    // 2. 定时扫描：将到期消息转移回真实 Topic
    public class DeliverDelayedMessageTimerTask extends TimerTask {
        @Override
        public void run() {
            for (Map.Entry<Integer, Long> entry : delayLevelTable.entrySet()) {
                int delayLevel = entry.getKey();
                long delayMillis = entry.getValue();

                // 读取 SCHEDULE_TOPIC_XXXX 的对应队列
                ConsumeQueue cq = getMessageStore().getConsumeQueueTable()
                    .get(SCHEDULE_TOPIC).get(delayLevel - 1);

                // 遍历消息
                while (true) {
                    DispatchRequest request = cq.get(cqOffset);
                    MessageExt msg = getMessageStore().lookMessageByOffset(
                        request.getCommitLogOffset());

                    long deliverTimestamp = msg.getStoreTimestamp() + delayMillis;

                    if (System.currentTimeMillis() >= deliverTimestamp) {
                        // 到期：转移回真实 Topic
                        msg.setTopic(msg.getProperty(MessageConst.PROPERTY_REAL_TOPIC));
                        msg.setQueueId(msg.getProperty(MessageConst.PROPERTY_REAL_QUEUE_ID));
                        // 重新写入 CommitLog（真实 Topic）
                        getMessageStore().putMessage(msg);
                        // 更新延迟队列的 Offset
                        cqOffset += request.getMsgSize();
                    } else {
                        break; // 后面的消息还没到期
                    }
                }
            }
            // 注册下一次扫描（100ms 后）
            scheduledExecutor.schedule(this, 100, TimeUnit.MILLISECONDS);
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **延迟精度问题**：扫描间隔 100ms，加上消息处理时间，实际延迟可能有 200-500ms 的误差。对于「30 分钟超时」这种场景可以接受，但对于「秒级延迟」需要注意。
2. **延迟消息不支持事务消息**：RocketMQ 的事务消息和延迟消息是互斥的。如果需要延迟事务消息，只能通过业务代码实现（先发事务消息，消费者中判断时间再延迟重试）。
3. **SCHEDULE_TOPIC 的队列膨胀**：每个延迟等级对应一个队列，如果消息量大，SCHEDULE_TOPIC 的 CommitLog 会很大。悦茶平台将延迟等级控制在 5 个以内。
4. **加分点**：悦茶平台的「订单超时取消」使用延迟消息方案时，发现高峰期（午间）延迟消息量暴增导致 `SCHEDULE_TOPIC` 写入压力大。优化方案：将超时判断改为「时间轮 + 数据库轮询」混合模式，减少 MQ 的压力。

消息积压的处理分三步：排查原因 → 紧急处理 → 长期优化。

**排查原因：**
1. 消费能力不足：消费者数量不够、消费逻辑太慢（数据库查询慢、外部接口慢）
2. 消费者频繁 Rebalance：心跳超时导致消费者频繁上下线
3. 消费逻辑阻塞：死锁、线程池满、连接池满
4. 发送端突然暴增：活动流量、数据导入、重试风暴

**紧急处理方案：**
1. **临时扩容消费者**：增加消费者实例数
2. **临时扩容队列**：增加 Topic 的 ReadQueueNums
3. **降级消费逻辑**：暂时只记录消息到本地，后续批量处理
4. **跳过非关键消息**：重置 Offset 跳过积压消息

**死信队列（DLQ）：**
- 消息重试超过最大次数（默认 16 次）后进入 `%DLQ%ConsumerGroup`
- 死信队列中的消息不会自动投递，需要人工处理
- 可通过 Console 查看、重新投递死信消息

### 第17集：NameServer 的设计原理——为什么不用 Zookeeper

**💡 核心回答：**

NameServer 是 RocketMQ 的注册中心，负责管理 Broker 的路由信息。它的设计哲学是「简单优先」：

**为什么不用 Zookeeper：**
1. **架构简单**：NameServer 无状态、节点间不通信，而 Zookeeper 使用 ZAB 协议需要强一致性，增加了运维复杂度
2. **性能更好**：NameServer 不需要选举和共识，路由信息最终一致即可，延迟更低
3. **运维成本低**：无需维护 ZK 集群，NameServer 进程轻量，内存占用小

**NameServer 核心设计：**
- **无状态**：每个 NameServer 节点独立运行，不互相通信
- **最终一致**：路由信息通过心跳机制最终一致（Broker 每 30s 向所有 NameServer 发送心跳）
- **路由表内存存储**：路由信息全部存储在内存中，读写性能极高

**⚠️ 常见坑/加分回答：**

1. **NameServer 数据不一致**：由于 Broker 向各个 NameServer 独立注册，不同 NameServer 上的路由信息可能短暂不一致。在 Broker 刚启动或刚下线时，Producer 可能从某个 NameServer 获取到旧路由。解决方案：Producer 发送失败后会切换 Broker（`LatencyFaultTolerance`）。

### 第18集：Broker 的主从架构——DLedger 模式 vs 传统主从模式

**💡 核心回答：**

| 特性 | 传统主从模式 | DLedger（Raft）模式 |

**⚠️ 常见坑/加分回答：**

1. **DLedger 的性能开销**：Raft 协议要求多数派确认，写延迟 = 网络 RTT + 日志复制时间。悦茶平台测试发现 DLedger 模式比传统主从模式 TPS 降低约 30%，但可靠性大幅提升。
2. **脑裂问题**：网络分区时可能产生两个 Leader。Raft 通过 Term（任期号）解决：旧 Leader 的 Term 小于新 Leader 的 Term，旧 Leader 收到更大 Term 的请求会退位。
3. **节点数必须是奇数**：3 节点组允许 1 节点故障，5 节点组允许 2 节点故障。不建议用偶数节点（4 节点组和 3 节点组的容错能力相同，但多一个节点的开销）。
4. **加分点**：悦茶平台在 DLedger 模式下，将 `electionTimeoutMs` 从默认 2s 调整为 3s，避免网络抖动导致的误切换。同时设置了 `enableElectUncleanLeader = false`，防止选出不一致的 Leader（丢失数据的节点被选为 Leader）。

### 第19集：Broker 故障转移（Failover）——Producer 端如何感知并切换

**💡 核心回答：**

Producer 端的故障转移通过 `LatencyFaultToleranceImpl` 实现，核心思路是：**不等待 NameServer 的路由更新，自己维护 Broker 的可用性状态**。

**故障感知方式：**
1. **发送失败感知**：Producer 发送消息失败（网络超时、Broker 拒绝等），记录该 Broker 的不可用时间
2. **路由更新感知**：定时从 NameServer 拉取路由，如果 Broker 从路由中消失，说明已下线
3. **心跳感知**：Consumer 端通过心跳检测 Broker 可用性

**故障转移流程：**
```
1. Producer 向 Broker-A 发送消息失败（连接超时）
2. LatencyFaultToleranceImpl 记录 Broker-A 的不可用时间
3. 下次发送时，selectOneMessageQueue 跳过 Broker-A
4. 选择 Broker-B 重试发送
5. 当 Broker-A 恢复后（不可用时间到期），重新纳入可用列表
```

**Consumer 端的故障转移：**
- 消费者拉取消息失败时，自动切换到其他 Broker 或 Slave 节点
- `consumeFromWhere = CONSUME_FROM_LAST_OFFSET` 确保切换后从最新位置消费
- 通过 `fetchSubscribeMessageQueues` 获取最新的队列信息

**📦 实际例子：**

悦茶平台 Broker 宕机处理：
```
场景：Broker-A（Master）在午高峰宕机
1. Producer 向 Broker-A 发送消息超时（sendMsgTimeout = 3s）
2. LatencyFaultToleranceImpl 标记 Broker-A 不可用 30s
3. 后续消息自动路由到 Broker-B 和 Broker-C
4. 消费者从 Broker-A-Slave 继续拉取（读取 Slave 配置为 true）
5. 5 分钟后运维恢复 Broker-A，重新注册到 NameServer
6. Producer 30s 后重新将流量路由到 Broker-A
```

**🔍 源码解析：**

核心类：`LatencyFaultToleranceImpl`、`MQFaultStrategy`

```java
// 1. 延迟容错策略
public class MQFaultStrategy {
    private LatencyFaultTolerance latencyFaultTolerance;

    public MessageQueue selectOneMessageQueue(
            final TopicPublishInfo tpInfo, final String lastBrokerName) {

        if (this.latencyFaultTolerance.isStarted() && this.latencyFaultTolerance.isAvailable(lastBrokerName)) {
            // 上次发送成功的 Broker 仍可用，继续使用
            // 轮询选择该 Broker 的队列
        }

        // 遍历所有队列，跳过不可用的 Broker
        for (int i = 0; i < tpInfo.getMessageQueueList().size(); i++) {
            int index = tpInfo.getSendWhichQueue().incrementAndGet();
            int pos = index % tpInfo.getMessageQueueList().size();
            MessageQueue mq = tpInfo.getMessageQueueList().get(pos);

            // 检查 Broker 是否可用
            if (!this.latencyFaultTolerance.isAvailable(mq.getBrokerName())) {
                continue; // 跳过不可用的 Broker
            }
            return mq;
        }
        // 所有 Broker 都不可用，随机选一个（降级策略）
        return tpInfo.getMessageQueueList().get(
            Math.abs(tpInfo.getSendWhichQueue().incrementAndGet()) % size);
    }
}

// 2. 延迟容错实现
public class LatencyFaultToleranceImpl implements LatencyFaultTolerance {
    // 每个 Broker 的不可用时长
    private final ConcurrentHashMap<String, FaultItem> faultItemTable;

    // 记录发送延迟
    public void updateFaultItem(final String brokerName, final long currentLatency,
            boolean isolation) {
        if (isolation) {
            // 发送隔离（超时/连接失败），标记不可用 10 分钟
            faultItemTable.put(brokerName, new FaultItem(brokerName,
                System.currentTimeMillis() + 600000));
        } else {
            // 根据延迟时间确定不可用时长
            long duration = computeNotAvailableDuration(currentLatency);
            faultItemTable.put(brokerName, new FaultItem(brokerName,
                System.currentTimeMillis() + duration));
        }
    }

    // 延迟 -> 不可用时长映射
    private long computeNotAvailableDuration(long currentLatency) {
        // latencyMax: 50, 100, 550, 1000, 2000
        // notAvailableDuration: 0, 0, 30000, 60000, 120000, 600000
        if (currentLatency < 50) return 0;
        if (currentLatency < 100) return 0;
        if (currentLatency < 550) return 30000;      // 30s
        if (currentLatency < 1000) return 60000;     // 1min
        if (currentLatency < 2000) return 120000;    // 2min
        return 600000;                                // 10min
    }

    public boolean isAvailable(final String name) {
        FaultItem faultItem = this.faultItemTable.get(name);
        if (faultItem != null) {
            return faultItem.isAvailable(); // startTimestamp + notAvailableDuration < now
        }
        return true;
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **不可用时长的粒度**：延迟 50ms 以下不可用时长为 0（即不惩罚），延迟超过 2s 惩罚 10 分钟。这意味着偶发的慢请求（如 GC）不会触发故障转移，但持续慢请求会导致 Broker 被隔离。
2. **降级策略的风险**：当所有 Broker 都不可用时，Producer 会降级为「随机选择一个 Broker 发送」。这可能导致消息发送到正在恢复的 Broker，该 Broker 可能还没准备好接受写入。
3. **Consumer 端的故障转移更简单**：Consumer 拉取失败后，只需换一个 Broker 或 Slave 即可。因为 Consumer 读取的是 CommitLog（所有 Broker 都有完整数据），不存在数据一致性问题。
4. **加分点**：悦茶平台配置了 `isolation = false`（非隔离模式），即只有真正连接失败才触发故障转移，超时但不返回错误的情况只记录延迟不触发隔离。这样避免了 GC 导致的假性故障转移。

### 第20集：多机房部署方案——跨机房同步、就近访问与脑裂防范

**💡 核心回答：**

RocketMQ 多机房部署有三种常见方案：

**方案一：同城双机房（主从模式）**
```
机房A：Broker-A(Master) + Broker-B(Slave)
机房B：Broker-A(Slave) + Broker-B(Master)
NameServer：机房A x2 + 机房B x1
```

**方案二：同城三机房（DLedger 模式）**
```
机房A：DLedger Node-1
机房B：DLedger Node-2
机房C：DLedger Node-3
NameServer：每个机房 1 个
```

**方案三：异地多活（跨地域）**
```
北京：完整 RocketMQ 集群
上海：完整 RocketMQ 集群
数据同步：通过 MQ Bridge 或业务层双写
```

**就近访问策略：**
- Producer 优先连接同机房的 NameServer
- Consumer 优先消费同机房 Broker 的消息
- 跨机房消费作为降级方案

**脑裂防范：**
- DLedger 模式通过 Raft 协议防范（需要多数派）
- 传统主从模式需要外部协调（如 Zookeeper 的分布式锁）
- 双机房部署时，使用「仲裁节点」（第三个机房的一个轻量进程）决定谁是主

**📦 实际例子：**

悦茶平台多机房部署方案：
- 3 个机房（北京亦庄、北京顺义、河北廊坊），延迟 < 2ms
- 使用 DLedger 模式，每个机房 1 个 DLedger 节点
- 每个 DLedger 组 3 节点（跨 3 个机房）
- Producer 优先连接同机房 Broker，同机房 Broker 宕机后跨机房

**🔍 源码解析：**

关键配置和代码逻辑：

```java
// 网络分区时，少数派分区无法选出 Leader（需要多数票）
// 多数派分区正常选举，保证只有一个 Leader
public class DLedgerLeaderElector {
    // Raft 选举：需要 > N/2 票
    public void changeRoleToCandidate() {
        this.role = DLedgerRole.CANDIDATE;
        this.term.incrementAndGet(); // 新任期
        // 发起投票请求
        for (peer : peers) {
            VoteRequest request = new VoteRequest(this.term, this.selfId);
            VoteResponse response = peer.vote(request);
            if (response.getTerm() > this.term) {
                // 对方 Term 更大，自己退位
                this.role = DLedgerRole.FOLLOWER;
                return;
            }
            if (response.isGranted()) {
                voteCount++;
            }
        }
        if (voteCount > peers.size() / 2) {
            this.role = DLedgerRole.LEADER;
        }
    }
}

// 4. 跨机房数据同步（异步）
// DLedger 模式下，跨机房的 Raft 复制延迟 = 机房间网络 RTT
// 北京-廊坊 延迟约 1-2ms，对写入性能影响可控
```

**⚠️ 常见坑/加分回答：**

1. **跨机房延迟对性能的影响**：DLedger 模式需要多数派确认，跨机房写入的延迟 = max(同机房 RTT, 跨机房 RTT)。悦茶平台 3 机房部署时，跨机房 RTT 约 2ms，总写入延迟增加约 4ms。
2. **NameServer 的跨机房部署**：建议 NameServer 至少部署在 2 个机房，且每个机房至少 1 个 NameServer。Producer 连接最近的 NameServer 即可。
3. **脑裂的真实案例**：悦茶平台曾遇到交换机故障导致机房 A 和 B 之间网络中断。由于使用 DLedger 3 节点模式（A、B、C），C 节点正常，所以 A 或 B 中能获得 C 投票的成为 Leader，不会脑裂。
4. **加分点**：悦茶平台的异地多活方案采用「MQ Bridge」模式：北京和上海各部署一套完整的 RocketMQ 集群，通过 Bridge 组件同步关键消息（如订单状态变更）。Bridge 是一个消费者 + 生产者，消费北京的消息后发送到上海，实现跨地域数据同步。

```java
// 1. Tag 过滤 - Broker 端
public class ConsumeQueue {
    // ConsumeQueue 每条记录包含 tagsCode（Tag 的 hashCode）
    public boolean isMessageMatched(long tagsCode, Set<String> subTags) {
        // 快速过滤：先比对 hashCode
        // 如果 hashCode 不匹配，直接跳过（不读取 CommitLog）
        for (String tag : subTags) {
            if (tag.hashCode() == tagsCode) {
                return true; // 可能匹配（存在哈希冲突的可能）
            }
        }
        return false;
    }
}

// 2. SQL92 过滤 - Broker 端
public class ExpressionMessageFilter implements MessageFilter {
    private final FilterExpression filterExpression;

    @Override
    public boolean isMatchedByConsumeQueue(long tagsCode, ConsumeQueueContext ctx) {
        // Tag 过滤阶段
        if (filterExpression.getExpressionType().equals("TAG")) {
            return tagsCode == filterExpression.getTopicCode();
        }
        // SQL92 需要读取消息属性
        return true; // SQL92 在 isMatchedByCommitLog 中过滤
    }

    @Override
    public boolean isMatchedByCommitLog(MessageExt msg, ConsumeQueueContext ctx) {
        if (filterExpression.getExpressionType().equals("SQL92")) {
            // 解析消息的 UserProperty
            Map<String, String> properties = msg.getProperties();
            // 使用 SQL 表达式求值
            EvaluationContext context = new PropertyFilter(properties);
            Object result = filterExpression.evaluate(context);
            return Boolean.TRUE.equals(result);
        }
        return true;
    }
}

// 3. SQL92 表达式解析器
// RocketMQ 使用自研的 SQL92 解析器
// 支持：=, <>, >, >=, <, <=, IS NULL, IS NOT NULL,
//       AND, OR, NOT, IN, BETWEEN, LIKE
// 注意：不支持 JOIN, GROUP BY, HAVING 等 SQL 特性

// 4. Consumer 端二次过滤
// PushConsumer 的 ConsumeMessageConcurrentlyService 中
public void processPullResult(PullRequest pullRequest, PullResult pullResult) {
    // 二次过滤：精确匹配 Tag 字符串
    List<MessageExt> filteredMsgs = new ArrayList<>();
    for (MessageExt msg : pullResult.getMsgFoundList()) {
        if (subscriptionData.getTagsSet().contains(msg.getTags())) {
            filteredMsgs.add(msg);
        }
    }
    pullResult.setMsgFoundList(filteredMsgs);
}
```

**⚠️ 常见坑/加分回答：**

1. **SQL92 需要开启配置**：Broker 端需要设置 `enablePropertyFilter=true`，否则 SQL92 过滤不生效。悦茶平台在部署文档中特别标注了这一点。
2. **Tag 过滤的性能优势**：Tag 过滤在 ConsumeQueue 层完成，不需要读取 CommitLog，性能极高。SQL92 过滤需要读取消息的 UserProperty，涉及 CommitLog 的随机读，性能较低。悦茶平台优先使用 Tag 过滤。
3. **过滤的粒度**：Broker 端过滤是按 MessageQueue 粒度的。如果一个 Queue 中符合条件的消息很少，Consumer 可能需要多次 Pull 才能凑满 `pullBatchSize`。建议将高频消息分散到多个 Queue。
4. **加分点**：悦茶平台的「门店订单通知」场景使用了 Tag 过滤：每个门店订阅自己的 Tag（`subscribe("STORE_ORDER_TOPIC", "store_001")`）。由于 3000+ 门店，每个门店一个 Tag。但 Tag 过滤使用 hashCode，3000 个 Tag 的哈希冲突概率不可忽略。解决方案：Consumer 端二次精确过滤保证正确性。

### 第22集：批量消息的设计——使用场景与内部实现

**💡 核心回答：**

批量消息允许 Producer 一次发送多条消息，减少网络往返，提升吞吐量。

**使用场景：**
- 日志收集：批量发送用户行为日志
- 数据同步：批量发送数据变更记录
- 非实时通知：批量发送短信/推送通知

**限制条件：**
1. 所有消息必须属于同一个 Topic
2. 所有消息不能有延迟等级（批量不支持延迟消息）
3. 总大小不超过 `maxMessageSize`（默认 4MB）
4. 不支持事务消息

**内部实现：**
- Producer 端：将多条消息合并为一个大的 `MessageExtBatch`
- Broker 端：将批量消息写入 CommitLog 时，为每条消息生成独立的 CommitLog 偏移
- Consumer 端：正常消费，每次拿到的是单条消息

**📦 实际例子：**

悦茶平台批量消息场景：
- **每日门店数据汇总**：凌晨 3 点将 3000 个门店的销售数据打包发送
- **用户行为日志**：每 5 秒批量发送积攒的用户浏览/点击日志

```java
// 批量发送
List<Message> msgs = new ArrayList<>();
for (StoreDailyReport report : reports) {
    Message msg = new Message("STORE_REPORT_TOPIC", "daily",
        JSON.toJSONBytes(report));
    msg.setKeys(report.getStoreId() + "_" + report.getDate());
    msgs.add(msg);
}

// 批量发送（注意总大小不超过 4MB）
producer.send(msgs);
```

**🔍 源码解析：**

核心类：`DefaultMQProducerImpl`、`MessageExtBatch`

```java
// 1. Producer 端批量发送
public class DefaultMQProducerImpl {
    public SendResult send(Collection<Message> msgs) throws MQClientException {
        // 1. 校验：同一 Topic
        String topic = null;
        for (Message msg : msgs) {
            if (topic == null) {
                topic = msg.getTopic();
            } else if (!topic.equals(msg.getTopic())) {
                throw new MQClientException("批量消息必须属于同一 Topic", null);
            }
        }

        // 2. 编码批量消息
        MessageExtBatch messageExtBatch = new MessageExtBatch();
        messageExtBatch.setTopic(topic);
        messageExtBatch.setBornTimestamp(System.currentTimeMillis());

        // 3. 将多条消息编码为一个 byte[]
        List<byte[]> bodyList = new ArrayList<>();
        int totalBodySize = 0;
        for (Message msg : msgs) {
            byte[] body = msg.getBody();
            bodyList.add(body);
            totalBodySize += body.length;
        }

        // 校验总大小
        if (totalBodySize > maxMessageSize) {
            throw new MQClientException("批量消息超过大小限制: " + maxMessageSize, null);
        }

        // 4. 组装批量 body
        ByteBuffer byteBuffer = ByteBuffer.allocate(totalBodySize);
        for (byte[] body : bodyList) {
            byteBuffer.put(body);
        }
        messageExtBatch.setBody(byteBuffer.array());

        // 5. 发送到同一个 Broker（同一个 Queue）
        return this.sendKernelImpl(messageExtBatch, mq, CommunicationMode.SYNC, ...);
    }
}

// 2. Broker 端拆分批量消息
public class CommitLog {
    public PutMessageResult putMessage(MessageExtBatch messageExtBatch) {
        // 批量消息在 CommitLog 中存储为一条连续记录
        // 但在 DispatchRequest 中会被拆分为多条
        AppendMessageResult result = this.appendMessageCallback.doAppend(
            mappedFile.getFileFromOffset(), mappedFile, maxMessageSize,
            this.defaultMessageStore, messageExtBatch);
        // result 的 msgNum 表示批量中的消息数

        // 3. ReputMessageService 处理时，按 msgNum 拆分
        for (int i = 0; i < result.getMsgNum(); i++) {
            DispatchRequest request = new DispatchRequest(...);
            // 每条消息有独立的 offset 和 size
            this.putMessagePositionInfo(request);
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **批量大小控制**：悦茶平台经验值——单条消息平均 1KB 时，批量 100 条（总约 100KB）是比较安全的。超过 500 条可能触发 Broker 端的写入超时。
2. **批量消息的失败粒度**：批量发送是一个原子操作，要么全部成功，要么全部失败。不能只成功一部分。悦茶平台在发送失败后会拆分为单条重发。
3. **批量消息的 Key**：每条消息可以设置不同的 Key，批量发送时 Key 也会被拆分到各条消息的 IndexFile 中。
4. **加分点**：悦茶平台的「日志收集」场景使用批量消息后，TPS 从 5000 提升到 30000，网络往返次数减少 83%。但需要注意消费端的处理逻辑：批量发送的消息在消费端仍然是单条消费，不会变成批量消费。

2. 将轨迹数据异步发送到内部 Topic `TRACE_TOPIC_XXX`
3. 通过 RocketMQ Console 或 API 查询轨迹数据

```java
    @Override
    public void sendMessageBefore(SendMessageContext context) {
        // 记录发送前的轨迹数据

        // 记录发送后的轨迹数据
        TraceBean traceBean = context.getTraceContext().getTraceBean();
        traceBean.setStoreTimestamp(System.currentTimeMillis());
        traceBean.setStoreHost(response.getBrokerAddr());

        // 异步发送轨迹消息
        AsyncTraceDispatcher dispatcher = context.getTraceDispatcher();
        dispatcher.appendTraceData(context.getTraceContext());
    }
}

// 2. 异步轨迹发送
public class AsyncTraceDispatcher {
    // 轨迹数据缓冲区
    private final BlockingQueue<TraceContext> traceContextQueue =
        new LinkedBlockingQueue<>(1024);

    // 后台线程定时批量发送轨迹
    public void run() {
        while (!stopped) {
            List<TraceContext> batch = new ArrayList<>();
            // 从队列中取出一批轨迹数据
            traceContextQueue.drainTo(batch, 20);
            if (!batch.isEmpty()) {
                // 编码为一条轨迹消息
                Message traceMsg = buildTraceMessage(batch);
                // 异步发送到 TRACE_TOPIC
                traceProducer.send(traceMsg, new SendCallback() {
                    @Override
                    public void onSuccess(SendResult result) { }
                    @Override
                    public void onException(Throwable e) {
                        // 轨迹发送失败不影响业务
                        log.warn("轨迹消息发送失败", e);
                    }
                });
            }
            Thread.sleep(100); // 100ms 批量发送
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **轨迹 Topic 的消息堆积**：如果轨迹消息量很大，`TRACE_TOPIC` 可能堆积。悦茶平台为高频 Topic 设置独立的轨迹 Topic，避免相互影响。
2. **轨迹数据的保留时间**：轨迹消息的保留时间建议设置为 3 天（与 CommitLog 一致）。太短无法排查历史问题，太长浪费存储。
3. **轨迹消息本身也有轨迹**：这会造成无限递归。RocketMQ 通过 `isTraceEnabled` 标记避免轨迹消息再次被追踪。
4. **加分点**：悦茶平台在排查「订单消息延迟」问题时，通过消息轨迹发现：消息在 Broker 端存储只用了 5ms，但从发送端发出到 Broker 接收用了 200ms。进一步排查发现是跨机房网络抖动导致。消息轨迹帮助快速定位了问题环节。

### 第25集：消息堆积的排查与解决——消费能力不足、频繁 Rebalance、消费阻塞

**💡 核心回答：**

消息堆积的排查流程：

```
1. 发现堆积：RocketMQ Console 监控告警
2. 确认堆积量：查看 Topic 的 Diff（maxOffset - consumerOffset）
3. 排查原因：
   a. 消费者数量是否足够？
   b. 消费者是否在频繁 Rebalance？
   c. 消费逻辑是否阻塞？
   d. 发送端是否突然暴增？
4. 针对性解决
```

**常见原因与解决方案：**

| 原因 | 排查方法 | 解决方案 |
|------|---------|---------|
| 消费者数量不足 | 消费者数 < 队列数 | 扩容消费者或增加队列 |
| 消费逻辑太慢 | 监控单条消费耗时 | 优化消费逻辑/增加线程 |
| 频繁 Rebalance | 查看消费者上下线日志 | 修复心跳超时/订阅不一致 |
| 消费逻辑阻塞 | 线程 dump 分析 | 修复死锁/扩大连接池 |
| 发送端暴增 | 对比发送 TPS 和消费 TPS | 临时扩容 + 降级 |

**📦 实际例子：**

悦茶平台消息堆积排查案例：

```
问题：ORDER_TOPIC 积压 100 万条

排查步骤：
1. Console 查看：8 个队列，4 个消费者
2. 每个消费者分配 2 个队列
3. 查看消费者日志：发现 Consumer-2 频繁打印 "rebalance triggered"
4. 查看心跳日志：Consumer-2 每 30s 才发一次心跳（应该是 10s）
5. 进一步分析：Consumer-2 的 GC 时间过长（Full GC 每次 15s）
6. 导致心跳超时，Broker 认为 Consumer-2 下线
7. 触发 Rebalance，其他消费者重新分配队列
8. 新分配后 Consumer-2 又上线，再次触发 Rebalance
9. 最终结果：所有消费者都在处理 Rebalance，消费 TPS 降为接近 0

解决：
1. 调整 JVM 参数：增大堆内存，减少 Full GC
2. 增加 Broker 端心跳超时时间：heartbeatTimeoutMillis 从 120s 调到 180s
3. 临时扩容消费者到 8 个（等于队列数）
4. 优化消费逻辑中的数据库查询（加索引）
```

```java
    private void pullMessage(final PullRequest pullRequest) {
        ProcessQueue pq = pullRequest.getProcessQueue();
        // 检查 ProcessQueue 是否被丢弃（Rebalance 导致）

        // 检查消费线程池是否满载
```

**⚠️ 常见坑/加分回答：**

1. **堆积不等于消费失败**：消息堆积可能是因为发送端突然暴增（如大促），消费速度跟不上。不一定是消费逻辑有问题。悦茶平台在双11 前会预扩容消费者。
2. **消费线程池大小**：默认 `consumeThreadMin = 20, consumeThreadMax = 64`。如果消费逻辑是 IO 密集型（如查数据库），可以适当调大到 128。CPU 密集型则保持默认。
3. **ProcessQueue 的流控**：`consumeConcurrentlyMaxSpan` 默认 2000，表示一个 ProcessQueue 最多缓存 2000 条消息。如果消息处理慢，即使消费线程有空闲也不会拉取更多消息。
4. **加分点**：悦茶平台开发了「堆积自动处理」机制：当积压量超过 10 万条时，自动触发扩容（K8s HPA）并发送钉钉告警；超过 100 万条时，自动将非核心消费者降级（暂停消费通知类消息，优先处理订单消息）。

### 第26集：消费者频繁 Rebalance 的原因和解决方案

**💡 核心回答：**

频繁 Rebalance 的表现：消费者日志中频繁出现 `doRebalance`、`messageQueueChanged` 等关键字。

**常见原因：**

| 原因 | 原理 | 排查方法 |
|------|------|---------|
| 心跳超时 | Consumer 未按时发心跳，Broker 认为下线 | 查看心跳间隔和超时配置 |
| 订阅关系不一致 | 同一 ConsumerGroup 内订阅关系不同 | 检查所有消费者的 subscribe 调用 |
| IP 变化 | Consumer IP 变化导致 clientId 变化 | 查看 Consumer 注册日志 |
| GC 停顿 | Full GC 导致心跳线程阻塞 | JVM GC 日志分析 |
| 网络抖动 | 网络不稳定导致心跳丢失 | 网络监控 |

**解决方案：**
1. **心跳超时**：增大 `heartbeatBrokerInterval`（默认 5s）或增大 Broker 端 `consumerFallbehindThreshold`
2. **订阅关系不一致**：确保同一 ConsumerGroup 内所有消费者调用相同的 `subscribe`
3. **IP 变化**：固定 `instanceName`，避免容器 IP 变化导致 clientId 变化
4. **GC 停顿**：优化 JVM 参数，使用 G1/ZGC 减少 GC 时间

**📦 实际例子：**

悦茶平台频繁 Rebalance 案例：

```
问题：每天凌晨 2 点出现短暂 Rebalance 风暴

排查：
1. 凌晨 2 点有数据备份任务，磁盘 IO 打满
2. 消费者的 GC 因 IO 等待变慢，Full GC 时间从 200ms 增加到 5s
3. 心跳线程被 GC 阻塞，超过 Broker 端的超时时间（120s）
4. Broker 认为消费者下线，触发 Rebalance
5. GC 结束后消费者重新注册，再次触发 Rebalance

解决：
1. 将数据备份任务调整到凌晨 4 点（避开业务高峰）
2. JVM 参数优化：-XX:MaxGCPauseMillis=200 -XX:+UseG1GC
3. 增大 Broker 端 consumerFallbehindThreshold 到 180s
4. 心跳线程独立于业务线程，不受 GC 影响
```

### 第27集：如何保证消息的顺序性不被破坏——完整链路分析

**💡 核心回答：**

消息顺序性的保障需要贯穿整个链路，任何一个环节出错都可能导致顺序破坏：

**完整链路保障：**

| 环节 | 风险 | 保障措施 |
|------|------|---------|
| 发送端 | 消息路由到不同队列 | 使用 MessageQueueSelector，相同 Key 路由到同一队列 |
| Broker 端 | 主从切换导致数据不一致 | DLedger 模式保证 Raft 共识 |
| Rebalance | 队列转移导致消费中断 | 使用 lock 机制，消费端保证顺序 |
| 消费端 | 多线程消费导致乱序 | ConsumeMessageOrderlyService 单线程消费 |
| 消费失败 | 跳过失败消息导致顺序断裂 | 消费失败不跳过，重试当前消息 |

**关键原则：**
1. 同一个 Sharding Key 的消息 → 同一个 MessageQueue → 同一个消费者 → 单线程消费
2. 消费失败 → 重试当前消息 → 不跳过
3. Rebalance → 加锁保证 → 同一时刻只有一个消费者消费一个队列

**📦 实际例子：**

悦茶平台订单状态流转的顺序保障：

```
订单 ORD-20240101-001 的状态流转：
1. 创建订单 → 发送到 queue-3
2. 支付成功 → 发送到 queue-3（相同 orderId 哈希）
3. 开始制作 → 发送到 queue-3
4. 制作完成 → 发送到 queue-3
5. 配送中 → 发送到 queue-3

消费端（Consumer-A）：
- 锁定 queue-3 的消费权
- 单线程按顺序处理：创建 → 支付 → 制作 → 完成 → 配送
- 如果「支付成功」消费失败：
  - 重试「支付成功」（最多 maxRetry 次）
  - 不处理后续的「开始制作」
```

**🔍 源码解析：**

核心类：`MessageQueueSelector`、`ConsumeMessageOrderlyService`、`ProcessQueue`

```java
// 1. 发送端：保证相同 Key 路由到同一队列
public class DefaultMQProducerImpl {
    public SendResult send(Message msg, MessageQueueSelector selector, Object arg) {
        TopicPublishInfo topicPublishInfo = this.checkTopicAndMsgRoute(msg.getTopic());
        // 关键：通过 selector 选择队列（而非默认轮询）
        MessageQueue mq = selector.select(
            topicPublishInfo.getMessageQueueList(), msg, arg);
        // 如果 selector 返回 null 或抛出异常，消息发送失败
        // 注意：发送失败重试时会切换到其他 Broker！
        // 如果重试到不同 Broker 的不同队列，顺序可能被破坏
        return this.sendKernelImpl(msg, mq, ...);
    }
}

// 2. 消费端：顺序消费保证
public class ConsumeMessageOrderlyService {
    class ConsumeRequest implements Runnable {
        @Override
        public void run() {
            if (processQueue.isDropped()) return;

            // 关键：消费前锁定 MessageQueue
            try {
                boolean lockOK = ConsumeMessageOrderlyService.this.lockMQPeriodically();
                if (!lockOK) {
                    // 没拿到锁，延迟 200ms 重试
                    scheduleConsumeRequest(200);
                    return;
                }

                // 遍历消息，逐条消费
                for (MessageExt msg : msgs) {
                    ConsumeOrderlyStatus status = listener.consumeMessage(
                        Collections.singletonList(msg), context);

                    switch (status) {
                        case SUCCESS:
                            // 提交 Offset
                            processQueue.commit();
                            break;
                        case SUSPEND_CURRENT_QUEUE_A_MOMENT:
                            // 关键：不提交 Offset，不处理后续消息
                            // 延迟 retryTime 后重试当前消息
                            int retryTimes = msg.getReconsumeTimes();
                            if (retryTimes >= maxRetryTimes) {
                                // 超过最大重试，发送到重试 Topic
                                sendMessageBack(msg);
                                processQueue.commit();
                            } else {
                                // 延迟重试
                                scheduledExecutor.schedule(
                                    this, suspendCurrentQueueTimeMillis, TimeUnit.MILLISECONDS);
                                return; // 停止遍历！保证顺序
                            }
                            break;
                    }
                }
            } finally {
                processQueue.unlockConsumeMessage();
            }
        }
    }
}

// 3. 发送端重试对顺序的影响
// LatencyFaultToleranceImpl 在重试时选择不同 Broker
// 如果新 Broker 的队列编号不同，顺序可能被破坏
// 解决方案：设置 retryTimesWhenSendFailed = 0（顺序消息不重试）
// 或自定义 MessageQueueSelector 在重试时选择同一 Broker 的同一队列
```

**⚠️ 常见坑/加分回答：**

1. **发送失败重试破坏顺序**：这是最隐蔽的坑。同步发送失败后重试，`LatencyFaultToleranceImpl` 会选择不同 Broker 的不同队列。悦茶平台的解决方案：顺序消息设置 `retryTimesWhenSendFailed = 0`，发送失败直接返回错误，由业务层决定是否重发。
2. **消费线程池的大小**：顺序消费的线程池不是单线程的，而是「每个队列一个锁」，不同队列可以并行消费。悦茶平台有 16 个队列，实际有 16 个「单线程消费者」在并行。
3. **消费失败的延迟时间**：`suspendCurrentQueueTimeMillis` 默认 1000ms。如果业务处理需要更长时间才能成功，可以适当增大。悦茶平台设置为 3000ms。
4. **加分点**：悦茶平台对顺序消息的监控非常严格：每个队列的消费延迟、每条消息的处理耗时、消费失败的重试次数都有独立指标。当某个队列的消费延迟超过 10s 时触发告警，运维人员立即排查是否是「有毒消息」导致持续消费失败。

### 第28集：RocketMQ 性能调优——刷盘、页缓存、线程池与 JVM

**💡 核心回答：**

RocketMQ 性能调优分为四个层面：

**1. 刷盘策略调优：**
- 异步刷盘：`flushDiskType=ASYNC_FLUSH`（默认），TPS 最高
- 同步刷盘：`flushDiskType=SYNC_FLUSH`，可靠性高但 TPS 降低 50%+
- 刷盘间隔：`flushInterval`（异步刷盘默认 500ms），增大可降低 IO 但增加丢失风险

**2. 页缓存（PageCache）优化：**
- 预热：`warmMappedFile=true`（Broker 启动时预热所有文件到内存）
- 内存锁定：`mlockAll` 防止 PageCache 被 OS 换出
- 文件映射：`transferMsgByHeap=true`（默认，通过堆内存传输）vs `false`（零拷贝，性能更好）

**3. 线程池调优：**
- 发送线程：`sendMessageThreadPoolNums`（默认 1 + CPU 核数）
- 消费线程：`consumeThreadMin=20, consumeThreadMax=64`
- Pull 线程：`pullMessageThreadPoolNums`（默认 16 + CPU 核数 * 2）
- 刷盘线程：`flushCommitLogTimed=true`（定时刷盘线程数）

**4. JVM 参数调优：**
- 堆内存：建议 8-16GB（Broker）
- GC：推荐使用 G1GC `-XX:+UseG1GC -XX:MaxGCPauseMillis=200`
- DirectMemory：RocketMQ 大量使用 Mmap，需要 `-XX:MaxDirectMemorySize=8g`
- 关闭偏向锁：`-XX:-UseBiasedLocking`（减少锁竞争）

### 第29集：容量规划——根据 TPS 估算 Broker 数量、磁盘和 CommitLog 大小

**💡 核心回答：**

容量规划的核心公式：

```
Broker 数量 = 总 TPS / 单 Broker TPS
磁盘大小 = 消息 TPS × 平均消息大小 × 保留天数 × 副本数
CommitLog 文件数 = 磁盘大小 / 单文件大小（默认 1GB）
```

**单 Broker TPS 估算：**

| 配置 | 单 Broker TPS | 说明 |
|------|-------------|------|
| 异步刷盘 + 异步复制 + SSD | 10 万+ | 最高性能 |
| 异步刷盘 + 异步复制 + HDD | 3-5 万 | 机械盘 |
| 同步刷盘 + SSD | 2-4 万 | 可靠性优先 |
| 同步刷盘 + 同步复制 + SSD | 1-2 万 | 最高可靠性 |

**磁盘容量估算（以悦茶平台为例）：**
```
- 消息 TPS：5000 条/秒（日常）/ 20000 条/秒（高峰）
- 平均消息大小：2KB
- 日常写入：5000 × 2KB = 10MB/s = 864GB/天
- 保留 3 天：864 × 3 = 2592GB ≈ 3TB
- 3 副本（1 Master + 2 Slave 或 DLedger 3 节点）
- 总磁盘需求：3TB × 3 = 9TB（建议 12TB，留 25% 余量）
```

**CommitLog 文件大小：**
- 默认 1GB，通常不需要修改
- 文件太小：频繁创建/删除文件，IO 开销大
- 文件太大：Mmap 映射范围大，OS 管理压力大，GC 回收 DirectByteBuffer 慢
- 建议保持默认 1GB

```
   → 事务提交成功 → 消息投递到 Consumer

2. 订单处理服务（CID_ORDER_PROCESS）消费消息
   → 发送顺序消息到 INVENTORY_DEDUCT_TOPIC（Key=skuId）
   → 发送普通消息到 COUPON_GRANT_TOPIC
   → 发送消息到 STORE_NOTIFY_TOPIC（Tag=storeId）
   → 发送延迟消息到 ORDER_TIMEOUT_TOPIC（30min 超时取消）

3. 库存服务（CID_INVENTORY_DEDUCT）消费消息
   → 扣减库存（幂等：基于 msgId 的 Redis SETNX）
   → 更新库存状态

4. 优惠券服务（CID_COUPON_GRANT）消费消息
   → 发放优惠券（幂等：数据库唯一索引 order_id）

5. 门店通知服务（CID_STORE_NOTIFY）消费消息
   → 每个门店实例订阅自己的 Tag（Tag=storeId）
   → 门店 POS 系统收到新订单通知

6. 用户通知服务（CID_USER_NOTIFY）消费消息
   → 发送 App Push / 短信通知
```

```java
// 1. 事务消息：下单
@Service
public class OrderService {
    private TransactionMQProducer producer;

    @PostConstruct
    public void init() {
        producer = new TransactionMQProducer("order_tx_group");
        producer.setNamesrvAddr(namesrvAddr);
        producer.setTransactionListener(new TransactionListener() {
            @Override
            public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
                try {
                    Order order = (Order) arg;
                    // 本地事务：创建订单
                    orderMapper.insert(order);
                    return LocalTransactionState.COMMIT_MESSAGE;
                } catch (Exception e) {
                    return LocalTransactionState.ROLLBACK_MESSAGE;
                }
            }

            @Override
            public LocalTransactionState checkLocalTransaction(MessageExt msg) {
                String orderId = msg.getUserProperty("orderId");
                Order order = orderMapper.selectById(orderId);
                return order != null ?
                    LocalTransactionState.COMMIT_MESSAGE :
                    LocalTransactionState.ROLLBACK_MESSAGE;
            }
        });
        producer.start();
    }

    public void createOrder(Order order) {
        Message msg = new Message("ORDER_CREATED_TOPIC", "create",
            JSON.toJSONBytes(order));
        msg.putUserProperty("orderId", order.getOrderId());
        producer.sendMessageInTransaction(msg, order);
    }
}

// 2. 订单处理服务（拆分消息到多个下游 Topic）
@Component
public class OrderCreatedConsumer {
    private DefaultMQProducer downstreamProducer;

    @RocketMQMessageListener(
        topic = "ORDER_CREATED_TOPIC",
        consumerGroup = "CID_ORDER_PROCESS"
    )
    public void onMessage(MessageExt msg) {
        Order order = JSON.parseObject(msg.getBody(), Order.class);

        // a. 发送库存扣减消息（顺序消息）
        Message invMsg = new Message("INVENTORY_DEDUCT_TOPIC", "deduct",
            JSON.toJSONBytes(order.getItems()));
        invMsg.setKeys(order.getOrderId());
        downstreamProducer.send(invMsg, new MessageQueueSelector() {
            public MessageQueue select(List<MessageQueue> mqs, Message m, Object arg) {
                String skuId = (String) arg;
                return mqs.get(Math.abs(skuId.hashCode()) % mqs.size());
            }
        }, order.getItems().get(0).getSkuId());

        // b. 发送优惠券消息
        Message couponMsg = new Message("COUPON_GRANT_TOPIC", "grant",
            JSON.toJSONBytes(order.getCouponInfo()));
        couponMsg.setKeys(order.getOrderId());
        downstreamProducer.send(couponMsg);

        // c. 发送门店通知（Tag = storeId）
        Message storeMsg = new Message("STORE_NOTIFY_TOPIC",
            order.getStoreId(), JSON.toJSONBytes(order));
        storeMsg.setKeys(order.getOrderId());
        downstreamProducer.send(storeMsg);

        // d. 发送超时取消延迟消息
        Message timeoutMsg = new Message("ORDER_TIMEOUT_TOPIC", "cancel",
            JSON.toJSONBytes(order));
        timeoutMsg.setDelayTimeLevel(16); // 30min
        downstreamProducer.send(timeoutMsg);
    }
}

// 3. 幂等处理（Redis SETNX）
@Component
public class IdempotentChecker {
    @Autowired
    private StringRedisTemplate redisTemplate;

    public boolean checkAndMark(String msgId) {
        String key = "mq:idempotent:" + msgId;
        Boolean result = redisTemplate.opsForValue()
            .setIfAbsent(key, "1", Duration.ofHours(24));
        return Boolean.TRUE.equals(result);
    }
}
```

**⚠️ 常见坑/加分回答：**

1. **Topic 数量规划**：悦茶平台初期只有 3 个 Topic，后来发现不同业务的可靠性要求不同，拆分为 6 个 Topic。每个 Topic 可以独立配置队列数、消费者数、保留时间。
2. **消费者组的命名规范**：悦茶平台采用 `CID_{业务域}_{操作}` 格式，如 `CID_ORDER_PROCESS`。避免不同业务使用相同 ConsumerGroup 导致 Rebalance 互相影响。
3. **消息体大小控制**：悦茶平台规定消息体不超过 10KB。订单详情（含商品列表）如果超过 10KB，只发送订单 ID，消费者通过 RPC 查询详情。
4. **加分点**：悦茶平台的消息架构经过双11 验证：30000 TPS 峰值下，消息延迟 P99 < 200ms，积压量始终为 0。关键优化：DLedger 模式保障核心消息可靠性，批量消息用于日志收集，单向发送用于非核心通知，消费者弹性伸缩应对流量波峰。
