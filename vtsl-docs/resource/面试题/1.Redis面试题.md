

# Redis面试题·带实例源码版（30集完整内容）

## 第1系列：Redis数据结构与应用场景

### 第1集：Redis有哪些数据类型？每种类型的底层数据结构是什么

**💡 核心回答：**

Redis 提供 5 种基础数据类型和多种高级数据类型：

| 数据类型 | 底层编码（encoding） | 典型用途 |
|---------|---------------------|---------|
| String | int / embstr / raw（SDS） | 缓存、计数器、分布式锁 |
| Hash | ziplist / hashtable | 对象属性存储（用户信息、商品详情） |
| List | ziplist / quicklist | 消息队列、时间线、最新浏览记录 |
| Set | intset / hashtable | 标签、共同好友、抽奖 |
| ZSet | ziplist / skiplist + dict | 排行榜、延迟队列、带权重的任务 |

高级数据类型包括：Bitmap（本质是 String）、HyperLogLog（本质是 String）、GEO（本质是 ZSet）、Stream（独立结构，类似 quicklist + radix tree）。

每个 key 对应的 value 在 Redis 内部用 `redisObject` 结构体表示：

```c
typedef struct redisObject {
    unsigned type:4;      // 数据类型：OBJ_STRING, OBJ_HASH, OBJ_LIST, OBJ_SET, OBJ_ZSET
    unsigned encoding:4;  // 底层编码：int/embstr/raw/ziplist/hashtable/skiplist...
    unsigned lru:24;      // LRU 淘汰信息
    int refcount;         // 引用计数
    void *ptr;            // 指向底层数据结构的指针
} robj;
```

**📦 实际例子：**

悦茶奶茶平台的用户积分系统中，多种数据类型协同工作：

- **String**：用户积分总量 `user:point:{uid}` = 580，用 `INCRBY` 原子增减
- **Hash**：用户基本信息 `user:info:{uid}` = {name, phone, level, registerTime}
- **ZSet**：积分排行榜 `rank:point:monthly`，score 为积分数，member 为 uid
- **Set**：用户签到记录 `sign:{uid}:202401`，member 为日期字符串
- **List**：用户最近浏览商品 `browse:{uid}`，最多保留 50 条

**🔍 源码解析：**

`redisObject` 是 Redis 的类型系统的核心。源码位于 `server.h`：

```c
// server.h 中的类型常量
#define OBJ_STRING 0
#define OBJ_LIST   1
#define OBJ_SET    2
#define OBJ_ZSET   3
#define OBJ_HASH   4
// Redis 5.0+ 新增
#define OBJ_STREAM 5

// encoding 常量
#define OBJ_ENCODING_RAW        0   /* Raw SDS string */
#define OBJ_ENCODING_INT        1   /* Encoded as integer */
#define OBJ_ENCODING_HT         2   /* Hash table (dict *) */
#define OBJ_ENCODING_ZIPLIST    9   /* Ziplist */
#define OBJ_ENCODING_SKIPLIST   5   /* Skip list (zset *) */
#define OBJ_ENCODING_EMBSTR     8   /* Embedded string (embstr) */
#define OBJ_ENCODING_QUICKLIST  10  /* Quicklist */
```

当执行 `TYPE` 命令时，实际是返回 `robj->type`；执行 `OBJECT ENCODING` 命令时返回 `robj->encoding`。Redis 会根据数据量和元素特征自动切换 encoding，这个过程对客户端完全透明。

**⚠️ 常见坑/加分回答：**

- 面试官常问"Redis 为什么不用 C 原生字符串而用 SDS"——SDS（Simple Dynamic String）支持 O(1) 获取长度、二进制安全、自动扩容（减少内存重分配）、兼容部分 C 字符串函数。
- 加分点：Redis 7.0 引入了 listpack 替代 ziplist（解决 ziplist 的级联更新问题），在 Hash、ZSet 等类型中开始使用 listpack。

### 第2集：String类型的底层编码（embstr/int/raw）什么时候切换

**💡 核心回答：**

String 类型根据值的特征，使用三种不同的底层编码：

| 条件 | encoding | 内存布局 |
|------|----------|---------|
| 值为整数值，且能用 long（64位）表示 | `int` | 直接存 int64，无指针间接 |
| 值长度 ≤ 32 字节（Redis 5.0+，之前是 39 字节）且非数字 | `embstr` | redisObject 和 SDS 连续分配 |
| 其他所有情况 | `raw` | redisObject 和 SDS 分别分配，ptr 指向 SDS |

切换规则：
1. **初始为 int**：`SET key 123`，值能转为 long，直接存整数
2. **int → raw**：`SET key hello`，非数字值且长度 > 32 字节 → raw
3. **embstr → raw**：先 embstr，后来追加内容超过 32 字节 → 重新分配为 raw
4. **raw → int**：几乎不可能，需要值恰好是整数（实际中很少发生）

```redis
127.0.0.1:6379> SET counter 100
OK
127.0.0.1:6379> OBJECT ENCODING counter
"int"
127.0.0.1:6379> SET greeting "hello"
OK
127.0.0.1:6379> OBJECT ENCODING greeting
"embstr"
127.0.0.1:6379> SET longstr "This is a very long string that exceeds thirty-two bytes limit"
OK
127.0.0.1:6379> OBJECT ENCODING longstr
"raw"
```

**📦 实际例子：**

悦茶平台的优惠券编号是纯数字（如 `coupon:code:202401010001`），用 String 存储。由于编号超过 32 字节，编码是 raw。而用户的优惠券剩余数量 `coupon:remain:{couponId}` 存的是整数，编码为 int，直接节省了指针开销。

门店日营业额缓存 `store:daily:revenue:{storeId}:20240101` 存储的是金额（如 `12580.50`），因为带小数点无法编码为 int，长度也未超过 32 字节，所以编码为 embstr。

**🔍 源码解析：**

SDS（Simple Dynamic String）的结构定义在 `sds.h`：

```c
// sds.h - Redis 5.0+ 的 SDS 结构
// 根据字符串长度分为5种类型，减少小字符串的内存开销
typedef char *sds;

struct __attribute__ ((__packed__)) sdshdr8 {  // 最大 2^8-1 = 255 字节
    uint8_t len;
    uint8_t alloc;
    uint8_t flags;
    char buf[];
};

struct __attribute__ ((__packed__)) sdshdr32 { // 最大 2^32-1 字节
    uint32_t len;
    uint32_t alloc;
    uint8_t flags;
    char buf[];
};
```

embstr 的核心实现在 `object.c` 的 `createEmbeddedStringObject` 函数：

```c
// object.c
robj *createEmbeddedStringObject(sds s) {
    robj *o = zmalloc(sizeof(robj) + sizeof(struct sdshdr8) + sdslen(s) + 1);
    // 关键：redisObject 和 SDS 在同一个内存块中连续分配
    struct sdshdr8 *sh = (void*)(o + 1);  // SDS 头紧跟在 robj 后面
    o->type = OBJ_STRING;
    o->encoding = OBJ_ENCODING_EMBSTR;
    o->ptr = sh + 1;  // ptr 指向 SDS 的 buf 起始位置
    // ... 初始化 len, alloc 等
    return o;
}
```

embstr 的优势：一次内存分配（`zmalloc`），redisObject 和字符串内容在内存上连续，减少了一次内存分配开销，也提升了 CPU cache 命中率。代价是 embstr 不可修改（因为后面可能没有预留空间），任何修改操作（如 `APPEND`）都会导致重新分配为 raw。

**⚠️ 常见坑/加分回答：**

- embstr 的阈值在 Redis 不同版本有变化：Redis 3.0 是 39 字节，Redis 5.0+ 是 32 字节（因为引入了多种 sdshdr 类型，结构体变大了）。
- 加分点：`INCR` 命令对 int 编码直接做整数加法，不需要字符串转换，性能极高。但如果对 embstr/raw 编码的 key 执行 INCR，会先尝试转换为 long，转换失败则返回错误。
- 坑：用 `SET key "123"` 和 `SET key 123` 编码不同——前者是 embstr（因为引号内的值被当作字符串处理，但 Redis 会尝试解析），实际上 Redis 在 SET 时如果值是纯数字会自动用 int 编码。

### 第3集：Hash类型的底层实现：ziplist vs hashtable 的转换条件

**💡 核心回答：**

Hash 类型在底层有两种编码实现：

- **ziplist（Redis 7.0+ 改为 listpack）**：当所有 field 和 value 的长度都较小，且键值对数量不多时使用
- **hashtable**：当数据量超过阈值时切换

转换条件（可通过 `redis.conf` 配置）：

```bash
# Redis 5.0 及之前
hash-max-ziplist-entries 512    # 键值对数量 ≤ 512 时用 ziplist
hash-max-ziplist-value 64       # 每个 field 和 value 长度 ≤ 64 字节

# Redis 7.0+ 改名为
hash-max-listpack-entries 128
hash-max-listpack-value 64
```

只要任一条件被突破（数量超限或某个值超长），Redis 就会将整个 ziplist 转换为 hashtable。这个过程不可逆——一旦升级为 hashtable，即使后续删除元素也不会回到 ziplist。

**📦 实际例子：**

悦茶平台的用户收货地址信息存储在 Hash 中：

```redis
HSET address:{uid} name "张三"
HSET address:{uid} phone "13800138000"
HSET address:{uid} province "广东省"
HSET address:{uid} city "深圳市"
HSET address:{uid} district "南山区"
HSET address:{uid} detail "科技园南路88号悦茶大厦3楼"
```

这个 Hash 只有 6 个字段，每个值都不超过 64 字节，底层使用 ziplist 存储，内存非常紧凑。而 `user:profile:{uid}` 如果存储了用户详细资料（包含头像 URL 等长字符串），某个 value 超过 64 字节就会触发编码切换。

**🔍 源码解析：**

ziplist 是一个连续内存块，每个 entry 结构如下：

```c
// t_ziplist.c (Redis 源码)
typedef struct zlentry {
    unsigned int prevrawlensize;  // 前一个 entry 的长度编码所占字节数（1 or 5）
    unsigned int prevrawlen;      // 前一个 entry 的实际长度
    unsigned int lensize;         // 当前 entry 的长度编码所占字节数
    unsigned int len;             // 当前 entry 的实际长度
    unsigned int headersize;      // prevrawlensize + lensize
    unsigned char encoding;       // 编码类型
    unsigned char *p;             // 指向实际数据的指针
} zlentry;
```

ziplist 的致命缺陷——**级联更新（cascade update）**：当修改一个 entry 导致其长度变化，需要更新下一个 entry 的 `prevrawlen` 字段。如果下一个 entry 的 prevrawlen 从 1 字节变为 5 字节，又会触发连锁反应，最坏情况下需要遍历整个 ziplist。

ziplist 在 Hash 中的存储方式：field1, value1, field2, value2, ... 交替排列。

hashtable 编码使用 Redis 的标准字典 `dict`：

```c
// dict.h
typedef struct dict {
    dictType *type;
    void *privdata;
    dictht ht[2];          // 两个哈希表，用于 rehash
    long rehashidx;        // rehash 进度，-1 表示未在 rehash
    int iterators;         // 正在迭代的迭代器数量
} dict;

typedef struct dictht {
    dictEntry **table;      // 哈希表数组
    unsigned long size;     // 哈希表大小（总是 2 的幂）
    unsigned long sizemask; // size - 1，用于快速取模
    unsigned long used;     // 已使用节点数
} dictht;

typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    struct dictEntry *next;  // 链地址法解决冲突
} dictEntry;
```

渐进式 rehash 是 Redis 的经典设计：每次对 dict 执行增删改查时，顺便从 ht[0] 迁移一个 bucket 到 ht[1]，避免一次性迁移导致阻塞。

**⚠️ 常见坑/加分回答：**

- ziplist 的查询复杂度是 O(N)，hashtable 是 O(1)。生产环境中如果 Hash 字段数较多，务必确认编码是 hashtable，否则 HGET 性能会很差。
- 加分回答：Redis 7.0 用 listpack 替代了 ziplist，listpack 每个 entry 独立存储自身长度，修改一个 entry 不会影响其他 entry，彻底解决了级联更新问题。
- 坑：`HSETALL` 返回的字段顺序在 ziplist 编码下是插入顺序，在 hashtable 编码下是无序的。不要依赖 Hash 的字段顺序。

### 第4集：ZSet的底层实现：ziplist + skiplist + dict，为什么这样设计

**💡 核心回答：**

ZSet 是 Redis 中最复杂的数据类型，底层有三种编码：

- **ziplist（listpack）**：元素少且值短时使用
- **skiplist + dict**：元素多或值长时使用，两者协同工作

为什么需要 skiplist 和 dict 两个结构？因为它们解决不同的问题：

| 需求 | 依赖的数据结构 | 时间复杂度 |
|------|-------------|-----------|
| 根据 member 查 score | dict | O(1) |
| 根据 score 范围查成员 | skiplist | O(log N + M) |
| 根据 rank（排名）查成员 | skiplist | O(log N) |
| 按 score 排序遍历 | skiplist | O(N) |

dict 存储 `member → score` 的映射，实现 O(1) 查找；skiplist 按 score 有序排列所有节点，实现范围查询和排名查询。

```redis
# 悦茶平台积分排行榜
ZADD rank:point:monthly 850 "uid:1001"
ZADD rank:point:monthly 920 "uid:1002"
ZADD rank:point:monthly 780 "uid:1003"
ZRANGEBYSCORE rank:point:monthly 800 1000  # 查 800-1000 分的用户
ZREVRANK rank:point:monthly "uid:1001"     # 查 uid:1001 排名
```

**📦 实际例子：**

悦茶奶茶平台的月度积分排行榜 `rank:point:monthly`，3000+ 门店的店长都有积分。使用 ZSet 存储：
- member = 店长uid，score = 月度积分
- `ZREVRANGE rank:point:monthly 0 9 WITHSCORES` 查看 Top 10
- `ZRANK rank:point:monthly uid:{me}` 查看自己的排名
- `ZRANGEBYSCORE rank:point:monthly 1000 2000` 查看 1000-2000 分区间的所有店长

当排行榜元素较少（≤128 且每个值 ≤64 字节）时，底层用 ziplist，节省内存；当排行榜元素增多后自动切换为 skiplist + dict。

**🔍 源码解析：**

skiplist 的节点定义在 `server.h`：

```c
// server.h - 跳表节点
typedef struct zskiplistNode {
    sds ele;                          // 成员元素
    double score;                     // 分数
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;            // 跨度（用于计算 rank）
    } level[];                        // 层级数组（随机高度）
    struct zskiplistNode *backward;   // 后退指针
} zskiplistNode;

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;  // 头尾节点
    unsigned long length;                 // 节点数
    int level;                            // 当前最高层数
} zskiplist;

// ZSet 的完整结构（skiplist 编码时）
typedef struct zset {
    dict *dict;          // member → score 的映射
    zskiplist *zsl;     // 跳表
} zset;
```

skiplist 的层数通过随机算法决定（P=0.25，最高 32 层）。每个节点至少有 1 层，有 25% 的概率拥有第 2 层，以此类推。`span` 字段记录该层两个节点之间跨越了多少个底层节点，用于 O(log N) 计算排名。

dict 中每个 dictEntry 的 key 是 member，value 存 score。同时 skiplist 的每个节点也持有 member 和 score。这就是为什么 ZSet 的内存开销较大——同一份数据存了两份。

**⚠️ 常见坑/加分回答：**

- ZSet 的内存开销是 5 种基础类型中最大的，因为 dict + skiplist 双重存储。生产环境中监控大 ZSet 的内存占用很重要。
- 加分点：为什么用 skiplist 而不用平衡树（如红黑树）？Redis 源码注释给出原因：(1) skiplist 实现更简单，代码可读性好；(2) 范围查找时 skiplist 找到起点后沿链表遍历即可，红黑树需要中序遍历，更复杂；(3) skiplist 插入/删除时不需要旋转操作，局部修改更少。
- 坑：`ZADD` 的 `XX`/`NX` 选项在 Redis 不同版本行为不同，Redis 6.2+ 支持 `GT`/`LT` 选项来限制只在 score 增大/减小时更新。

### 第5集：List类型的底层实现：ziplist vs quicklist，为什么Redis 3.2换了实现

**💡 核心回答：**

List 类型的底层实现经历了三代演进：

| 版本 | 底层结构 | 特点 |
|------|---------|------|
| Redis 2.x | linkedlist（双向链表） | 每个节点独立分配内存，内存碎片严重 |
| Redis 3.0+ | ziplist + linkedlist | 小列表用 ziplist，大列表用 linkedlist |
| Redis 3.2+ | quicklist | 统一用 quicklist，融合 ziplist 和 linkedlist 的优点 |

quicklist 的本质是一个双向链表，但每个节点不再存储单个元素，而是存储一个 ziplist（Redis 7.0+ 改为 listpack）。这样既保留了链表的 O(1) 头尾插入能力，又利用了 ziplist 的内存紧凑特性。

```redis
# 悦茶平台最新消息推送
LPUSH msg:push:{uid} "您的奶茶已制作完成"
LPUSH msg:push:{uid} "骑手已取餐"
LTRIM msg:push:{uid} 0 49   # 只保留最新50条
LRANGE msg:push:{uid} 0 -1  # 查看所有消息
```

**📦 实际例子：**

悦茶平台的订单状态流转记录使用 List 存储：

```redis
LPUSH order:status:20240101001 "CREATED:2024-01-01T10:00:00"
LPUSH order:status:20240101001 "PAID:2024-01-01T10:00:05"
LPUSH order:status:20240101001 "MAKING:2024-01-01T10:01:00"
LPUSH order:status:20240101001 "READY:2024-01-01T10:05:00"
LPUSH order:status:20240101001 "DELIVERED:2024-01-01T10:15:00"
```

订单状态记录通常只有 5-8 条，每个状态字符串很短，底层用 quicklist 的单个 ziplist 节点就能装下，内存利用率极高。

**🔍 源码解析：**

quicklist 的核心结构定义在 `quicklist.h`：

```c
// quicklist.h (Redis 3.2+)
typedef struct quicklist {
    quicklistNode *head;      // 双链表头节点
    quicklistNode *tail;      // 双链表尾节点
    unsigned long count;      // 所有 ziplist 中的元素总数
    unsigned long len;        // quicklistNode 节点数
    int fill;                 // ziplist 的最大填充量（负数表示字节限制）
    unsigned int compress;    // 压缩深度（LZF 压缩）
    // ...
} quicklist;

typedef struct quicklistNode {
    struct quicklistNode *prev;
    struct quicklistNode *next;
    unsigned char *zl;        // 指向 ziplist 的指针
    unsigned int sz;          // ziplist 的字节大小
    unsigned int count:16;    // 此节点中的元素个数
    unsigned int encoding:2;  // NODE_ENCODING_ZIPLIST 或 NODE_ENCODING_LZF
    // ...
} quicklistNode;
```

`fill` 字段对应配置项 `list-max-ziplist-size`，默认值 -5 表示每个 ziplist 最大 64KB。正值表示最大元素个数。

`compress` 字段对应配置项 `list-compress-depth`，表示从两端向中间第 N 个节点开始用 LZF 压缩。例如值为 1 表示头尾节点不压缩，其余全部压缩。因为列表的两端是访问频率最高的，中间的节点可以压缩节省内存。

为什么从 linkedlist 换到 quicklist？
1. linkedlist 每个元素一个 malloc，内存碎片严重
2. linkedlist 每个节点需要额外 2 个指针（prev + next）+ 1 个 void*（数据），每存一个元素额外开销 24 字节（64位系统）
3. quicklist 把多个元素打包在一个 ziplist 中，减少了 malloc 次数和指针开销

**⚠️ 常见坑/加分回答：**

- quicklist 支持 LZF 压缩，生产环境中如果 List 元素较多（如上千条），开启压缩可以节省 30%-50% 内存。
- 坑：`LINDEX list 5000` 这种随机访问在 quicklist 中是 O(N) 的，需要先定位到哪个 quicklistNode，再在 ziplist 内找。不要用 List 做随机访问场景。
- 加分回答：Redis 7.0 开始将 quicklist 中的 ziplist 替换为 listpack，解决了 ziplist 的级联更新问题。底层结构的演进体现了 Redis 在内存效率和操作性能之间的持续优化。

## 第2系列：持久化机制

### 第6集：RDB持久化的原理？bgsave怎么做到的（fork + COW）

**💡 核心回答：**

RDB（Redis Database）是 Redis 的快照持久化方式，将某一时刻的全量数据以二进制格式保存到磁盘（默认 `dump.rdb`）。

RDB 的生成过程（bgsave）：

1. Redis 主进程调用 `fork()` 创建子进程
2. 子进程获得父进程内存的**副本**（逻辑上）
3. 子进程将内存数据写入临时 RDB 文件
4. 写完后用临时文件替换旧的 RDB 文件
5. 子进程退出

关键在于 `fork()` + COW（Copy-On-Write，写时复制）：
- fork 后，父子进程共享同一份物理内存页（页表指向相同）
- 父进程继续处理客户端请求，当父进程**修改**某个内存页时，OS 会先复制该页，父进程修改副本，子进程仍然读取原始页
- 如果父进程没有修改操作，子进程读取的就是完整的快照数据
- 这就是为什么 bgsave 不会阻塞主进程，也不会占用 2 倍内存

```bash
# 手动触发 bgsave
redis-cli BGSAVE

# 查看 RDB 最后保存时间
redis-cli LASTSAVE

# 配置自动触发（redis.conf）
save 900 1       # 900秒内至少1个key变化就触发
save 300 10      # 300秒内至少10个key变化
save 60 10000    # 60秒内至少10000个key变化
```

**📦 实际例子：**

悦茶平台的 Redis 存储了大量运行时数据：用户会话、积分缓存、门店库存等。RDB 文件作为冷备份，每小时生成一次：

```bash
# redis.conf 配置
save 3600 1
dbfilename dump.rdb
dir /data/redis/

# 运维脚本：每天凌晨备份 RDB 文件
cp /data/redis/dump.rdb /data/backup/rdb_$(date +%Y%m%d).rdb
```

当 Redis 异常宕机后，重启时自动加载 RDB 文件恢复数据。悦茶平台接受最多丢失 1 小时数据（RDB 间隔），如果需要更小的数据丢失窗口，需要配合 AOF。

**🔍 源码解析：**

bgsave 的核心实现在 `rdb.c` 的 `rdbSaveBackground` 函数：

```c
// rdb.c
int rdbSaveBackground(int req, char *filename, rdbSaveInfo *rsi) {
    // 如果已有 bgsave 在进行，直接返回
    if (server.child_type == CHILD_TYPE_RDB) return C_ERR;

    pid_t childpid;
    if ((childpid = fork()) == 0) {
        /* 子进程 */
        retval = rdbSave(req, filename, rsi);  // 写入 RDB 文件
        if (retval == C_OK)
            sendChildCowInfo(CHILD_INFO_TYPE_RDB, "RDB");  // 报告 COW 内存
        exitFromChild(retval);
    } else {
        /* 父进程 */
        server.child_type = CHILD_TYPE_RDB;
        server.rdb_child_pid = childpid;
        // 父进程继续处理请求，不阻塞
    }
    return C_OK;
}
```

COW 的实现依赖操作系统的虚拟内存管理：

```
fork 之后的内存状态：
┌──────────────────────────────────────────────┐
│ 物理内存页                                     │
│ ┌─────────┐ ┌─────────┐ ┌─────────┐         │
│ │ Page 1  │ │ Page 2  │ │ Page 3  │  ...    │
│ └────┬────┘ └────┬────┘ └────┬────┘         │
│      ↑           ↑           ↑               │
│      └───────────┼───────────┘               │
│            页表指向（共享）                      │
│      ↑           ↑                           │
│   父进程页表   子进程页表                       │
└──────────────────────────────────────────────┘

父进程写入 Page 2 后：
┌──────────────────────────────────────────────┐
│ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│ │ Page 1  │ │ Page 2a │ │ Page 2b │ │ Page 3  │
│ │ (共享)  │ │ (父修改) │ │ (子读取) │ │ (共享)  │
│ └─────────┘ └─────────┘ └─────────┘ └─────────┘
```

RDB 文件格式采用 `REDIS` 魔数 + 版本号 + 辅助信息 + 数据库数据 + EOF + 校验和的结构。数据序列化使用 LZF 压缩算法。

**⚠️ 常见坑/加分回答：**

- fork 本身是阻塞操作。当 Redis 内存很大（如 20GB）时，fork 可能需要几十毫秒到几百毫秒。在此期间主线程无法处理请求。解决方案：(1) 控制 Redis 内存大小；(2) 使用 `lazy-free` 减少大对象；(3) Linux 内核使用 THP（Transparent Huge Pages）可能加剧 fork 延迟，建议关闭。
- 加分点：可以通过 `INFO persistence` 中的 `rdb_last_cow_size` 查看上次 bgsave 的 COW 内存大小，据此评估 fork 对系统的影响。

### 第7集：AOF持久化的原理？三种刷盘策略（always/everysec/no）的区别和性能差异

**💡 核心回答：**

AOF（Append Only File）通过记录每一条写命令来实现持久化。Redis 启动时可以重新执行 AOF 文件中的命令来恢复数据。

三种刷盘策略：

| 策略 | 刷盘时机 | 数据安全 | 性能 | 说明 |
|------|---------|---------|------|------|
| `always` | 每条命令写入后立即 fsync | 最高，最多丢 1 条 | 最差，每次都要磁盘 IO | 适合对数据零丢失的场景 |
| `everysec` | 每秒刷一次 | 较高，最多丢 1 秒 | 较好，折中方案 | **推荐默认**，兼顾安全和性能 |
| `no` | 由 OS 决定何时刷盘 | 最低，取决于 OS | 最好 | 类似 RDB 的可靠性 |

```bash
# redis.conf
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec   # always / everysec / no
```

AOF 重写（Rewrite）是另一个关键机制：随着时间推移，AOF 文件会越来越大。重写是生成一份能恢复当前数据的最小命令集，替换旧的 AOF 文件。重写过程也使用 bgsave 类似的 fork + COW 机制，不会阻塞主进程。

**📦 实际例子：**

悦茶平台的订单支付回调处理，对数据一致性要求较高。针对支付相关的 Redis 操作（如扣减库存、写入支付状态），使用独立的 Redis 实例配置 `appendfsync always`；而普通的缓存数据（如商品详情、门店信息）使用 `everysec`。

```bash
# 支付核心 Redis 实例
appendonly yes
appendfsync always

# 普通缓存 Redis 实例
appendonly yes
appendfsync everysec
```

AOF 重写在悦茶平台中每天凌晨低峰期手动触发一次，保持 AOF 文件体积在合理范围内。

**🔍 源码解析：**

AOF 写入的核心流程在 `aof.c`：

```c
// aof.c - AOF 写入流程
void flushAppendOnlyFile(int force) {
    // 1. 将命令追加到 AOF 缓冲区
    // server.aof_buf 是一个 sds 缓冲区
    
    // 2. 根据策略决定何时 fsync
    if (server.aof_fsync == AOF_FSYNC_ALWAYS) {
        // always：立即 fsync，阻塞等待完成
        redis_fsync(server.aof_fd);
        server.aof_lastfsync = server.unixtime;
    } else if (server.aof_fsync == AOF_FSYNC_EVERYSEC) {
        // everysec：后台线程每秒 fsync
        // 由 bio.c 中的后台线程执行
        if (flush_in_background) {
            // 已有后台 fsync 在跑，暂存到延迟队列
            aof_background_fsync(server.aof_fd);
        }
    }
    // no：什么都不做，交给 OS 的 page cache 刷盘
}
```

everysec 的实现细节：Redis 使用 BIO（Background I/O）线程来执行 fsync。主线程将需要 fsync 的文件描述符放入队列，后台线程从队列取出并执行。如果上一次的后台 fsync 还没完成，新的 fsync 会被延迟，此时 `server.aof_delayed_fsync` 计数器增加。可以通过 `INFO persistence` 的 `aof_delayed_fsync` 监控这个指标。

AOF 重写的关键在 `bgrewriteaof`：

```c
// aof.c
void bgrewriteaof(void) {
    pid_t childpid;
    if ((childpid = fork()) == 0) {
        /* 子进程 */
        // 遍历内存中的数据库，生成最小命令集
        // 写入临时文件 /tmp/temp-rewriteaof-bg-<pid>.aof
        rewriteAppendOnlyFileChild();
    } else {
        /* 父进程 */
        // 重写期间的新命令同时写入 AOF 缓冲区
        // 和 AOF 重写缓冲区（rewrite buffer）
        server.aof_rewrite_bufs = ...;
    }
}
// 子进程完成后，父进程将 rewrite buffer 中的增量命令追加到新的 AOF 文件
```

**⚠️ 常见坑/加分回答：**

- AOF 文件体积膨胀是常见问题。悦茶平台曾遇到 AOF 文件达到 10GB 导致重启恢复时间过长。解决方案：配置 `auto-aof-rewrite-percentage` 和 `auto-aof-rewrite-min-size` 自动触发重写。
- 坑：`everysec` 策略下，如果 fsync 延迟（磁盘 IO 繁忙），可能导致主线程缓冲区积压。严重时 Redis 会阻塞以等待 fsync 完成。监控 `aof_delayed_fsync` 指标可以提前发现这个问题。
- 加分回答：AOF 文件使用 AOF 格式（RESP 协议文本格式），可读性好但体积大。Redis 4.0+ 支持 AOF 和 RDB 混合格式（混合持久化），重写时前半段是 RDB 格式，后半段是增量 AOF 格式，兼顾加载速度和数据安全。

### 第8集：RDB和AOF混合持久化（Redis 4.0+）怎么工作的

**💡 核心回答：**

Redis 4.0 引入了混合持久化，将 RDB 和 AOF 的优点结合在一起：

- AOF 重写时，**前半段**以 RDB 格式写入全量数据（二进制，紧凑、加载快）
- **后半段**以 AOF 格式写入重写期间产生的增量命令（文本格式，可读、增量）

这样做的效果：
1. 加载速度接近纯 RDB（因为大部分数据是二进制的 RDB 格式）
2. 数据安全性接近纯 AOF（因为增量部分记录了所有写命令）
3. 文件体积比纯 AOF 小很多

```bash
# redis.conf 开启混合持久化
aof-use-rdb-preamble yes   # Redis 4.0+ 默认开启

# 触发 AOF 重写（混合持久化随之生效）
redis-cli BGREWRITEAOF
```

加载流程：Redis 启动时先识别 AOF 文件开头是否为 `REDIS` 魔数。如果是，说明是混合格式——先用 RDB 方式加载前半段全量数据，再执行后半段的 AOF 增量命令。

**📦 实际例子：**

悦茶平台的 Redis 生产环境全部开启混合持久化：

```bash
# redis.conf 完整持久化配置
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes

# 自动重写配置
auto-aof-rewrite-percentage 100   # AOF 文件增长 100% 时触发
auto-aof-rewrite-min-size 64mb    # 最小 64MB 才触发重写
```

悦茶平台运维团队观察到：开启混合持久化后，AOF 文件从纯文本的 8GB 缩小到约 2.5GB，Redis 重启恢复时间从 15 分钟缩短到 4 分钟。

**🔍 源码解析：**

混合持久化的核心实现在 `aof.c` 的 `rewriteAppendOnlyFile` 函数中：

```c
// aof.c - AOF 重写（混合持久化）
int rewriteAppendOnlyFileBackground(void) {
    // ...
    if (server.aof_use_rdb_preamble) {
        // 混合模式：前半段用 RDB 格式
        rioInitWithFile(&rdb, fp);
        rdbSaveRio(&rdb, &error, RDB_SAVE_AOF_PREAMBLE, NULL);
        // RDB_SAVE_AOF_PREAMBLE 标志告诉 RDB 序列化代码
        // 这不是普通 RDB 文件，而是 AOF 的前导部分
    }
    // 后半段：用 AOF 格式写入重写缓冲区中的增量命令
    while (1) {
        // 从 aof_rewrite_buf 中取出增量命令
        // 以 RESP 协议文本格式追加写入
        if (aofRewriteBufferGet(&buf, &size) == 0) break;
        rioWrite(&rdb, buf, size);
    }
}
```

加载时的判断逻辑：

```c
// aof.c - AOF 加载
int loadAppendOnlyFile(char *filename) {
    fp = fopen(filename, "r");
    // 读取文件开头几个字节
    char buf[AOF_MAX_PREFIX_LEN];
    fread(buf, 1, 5, fp);
    
    if (buf[0] == 'R' && buf[1] == 'E' && buf[2] == 'D' && 
        buf[3] == 'I' && buf[4] == 'S') {
        // 检测到 RDB 魔数 → 混合格式
        // 先用 RDB 加载器加载全量数据
        if (rdbLoadRio(&rdb, RDB_SAVE_AOF_PREAMBLE, NULL) != C_OK) {
            // 加载失败处理
        }
        // RDB 部分加载完毕后，继续以 AOF 格式加载增量命令
        // ...
    } else {
        // 纯 AOF 格式，直接逐条执行命令
    }
}
```

混合持久化文件的结构：

```
┌─────────────────────────────────┐
│  RDB 格式全量数据（二进制）        │
│  REDIS0011...（RDB 版本号）       │
│  ...数据序列化...                 │
│  FF（RDB EOF 标记）              │
│  CRC64 校验和                    │
├─────────────────────────────────┤
│  AOF 格式增量命令（文本）          │
│  *3\r\n$3\r\nSET\r\n...        │
│  *3\r\n$3\r\nSET\r\n...        │
│  ...                            │
└─────────────────────────────────┘
```

**⚠️ 常见坑/加分回答：**

- 混合持久化在 AOF 重写时触发，不是实时生效。刚开启配置后需要手动触发一次 `BGREWRITEAOF` 才会生效。
- 坑：混合持久化的 AOF 文件不是纯文本格式，不能像纯 AOF 那样用文本编辑器直接修改。如果需要修复数据，需要特殊处理。
- 加分回答：混合持久化文件中的 RDB 部分包含了过期信息，所以加载后过期 key 会被正确标记。而纯 AOF 格式是通过执行 `EXPIRE` 命令来实现过期标记的。混合模式的加载速度优势主要体现在大内存实例上。

### 第9集：Redis 4.0 引入的 Lazy Free（异步删除）是什么？解决了什么问题

**💡 核心回答：**

在 Redis 4.0 之前，删除一个大 key（如包含百万元素的 Hash）会导致主线程阻塞，因为 `DEL` 命令是同步执行的——需要释放该 key 关联的所有内存。

Lazy Free（惰性删除/异步删除）将耗时的内存释放操作放到后台线程执行，主线程只负责将 key 从数据库中摘除（O(1)），实际的内存回收交给后台线程异步完成。

```redis
# 同步删除（阻塞主线程）
DEL bigkey                    # 百万级元素的 Hash 可能阻塞数秒

# 异步删除（不阻塞主线程）
UNLINK bigkey                 # 主线程只做摘除，内存释放交给后台线程

# 异步刷新数据库
FLUSHALL ASYNC
FLUSHDB ASYNC

# 异步 AOF 重写
BGREWRITEAOF  # 内部已使用异步机制

# 异步过期（配置）
lazyfree-lazy-expire yes      # 过期删除也走后台线程
lazyfree-lazy-server-del yes  # RENAME 等内部删除也走后台线程
```

**📦 实际例子：**

悦茶平台的每日数据清理任务：每天凌晨需要清理前一天的门店临时缓存数据（`store:temp:order:{storeId}:*`），这些 key 是 Hash 类型，每个包含几百个字段。如果使用 `DEL`，3000+ 个门店的临时数据删除可能导致 Redis 短暂阻塞，影响在线服务。

```bash
# 错误的做法：循环 DEL（阻塞）
for key in $(redis-cli KEYS "store:temp:*"); do
    redis-cli DEL $key
done

# 正确的做法：使用 UNLINK（不阻塞）
redis-cli --scan --pattern "store:temp:*" | xargs -L 100 redis-cli UNLINK
```

**🔍 源码解析：**

Lazy Free 的实现核心在 `object.c` 和 `lazyfree.c`：

```c
// object.c - del 和 unlink 的区别
void delCommand(client *c) {
    // 同步删除
    for (int j = 1; j < c->argc; j++) {
        // 直接从数据库中删除并同步释放内存
        dbDelete(c->db, c->argv[j]);
    }
}

void unlinkCommand(client *c) {
    // 异步删除
    for (int j = 1; j < c->argc; j++) {
        // 从数据库中摘除 key（O(1)）
        // 将 robj 放入异步删除队列
        if (dbAsyncDelete(c->db, c->argv[j])) {
            // 放入后台线程处理
            lazyfreeQueueFreeObject(c->argv[j]);
        }
    }
}

// lazyfree.c
#define LAZYFREE_THREAD_NUM 3  // 后台线程数量

void lazyfreeThread(void) {
    while (1) {
        // 从队列中取出待释放的对象
        robj *obj = lazyfreeGetNextObject();
        if (obj) {
            // 在后台线程中释放内存
            decrRefCount(obj);  // 引用计数减为 0 时真正释放
        }
    }
}
```

关键细节：`decrRefCount` 函数在引用计数降为 0 时，会根据对象的 encoding 调用不同的释放函数：

```c
// object.c
void decrRefCount(robj *o) {
    if (o->refcount == 1) {
        switch(o->encoding) {
            case OBJ_ENCODING_HT:
                // 释放 dict，如果 dict 很大，释放时间很长
                dictRelease(o->ptr);
                break;
            case OBJ_ENCODING_SKIPLIST:
                // 释放 zset（skiplist + dict）
                freeZsetObject(o);
                break;
            case OBJ_ENCODING_QUICKLIST:
                // 释放 quicklist（所有 ziplist 节点）
                quicklistRelease(o->ptr);
                break;
            // ...
        }
        zfree(o);
    } else {
        o->refcount--;
    }
}
```

UNLINK 只是让主线程执行 `dbDelete`（从 dict 中移除 dictEntry），然后将 `robj` 放入后台线程的队列。后台线程执行 `decrRefCount` 时，才会真正释放底层的 dict/ziplist/skiplist 等结构。

**⚠️ 常见坑/加分回答：**

- Lazy Free 不是万能的。如果后台线程释放内存的速度跟不上 UNLINK 的投递速度，后台队列会积压，内存不会及时回收。可以通过 `INFO stats` 的 `lazyfree_pending_objects` 监控积压情况。
- 坑：`UNLINK` 只是异步释放内存，key 从客户端视角已经不存在了（`EXISTS` 返回 0）。但如果紧接着执行 `SET samekey newValue`，新值和旧值的内存释放是并行的，不会有冲突。
- 加分回答：除了显式的 UNLINK 命令，Redis 的过期删除（`LAZYFREE_LAZY_EXPIRE`）和淘汰（eviction）也可以使用异步释放。在大内存实例中，建议全部开启：
```bash
lazyfree-lazy-expire yes
lazyfree-lazy-server-del yes
lazyfree-lazy-eviction yes
lazyfree-lazy-user-del yes  # 即 UNLINK 默认行为
```

## 第3系列：内存管理

### 第10集：Redis的内存淘汰策略有哪些？每种策略适用什么场景

**💡 核心回答：**

当 Redis 内存使用达到 `maxmemory` 限制时，会根据配置的淘汰策略（eviction policy）删除部分 key 来腾出空间。

8 种淘汰策略：

| 策略 | 淘汰范围 | 选择标准 | 适用场景 |
|------|---------|---------|---------|
| `noeviction` | 不淘汰 | — | 默认值。内存满时拒绝写入，适合不允许丢数据的场景 |
| `allkeys-lru` | 所有 key | 最近最少使用 | 通用缓存，最常用 |
| `volatile-lru` | 设置了过期时间的 key | 最近最少使用 | 只缓存部分数据，持久数据不能丢 |
| `allkeys-lfu` | 所有 key | 最不经常使用（按频率） | Redis 4.0+，适合读多写少 |
| `volatile-lfu` | 设置了过期时间的 key | 最不经常使用 | 同上但只淘汰有过期时间的 |
| `allkeys-random` | 所有 key | 随机 | 几乎不用 |
| `volatile-random` | 设置了过期时间的 key | 随机 | 几乎不用 |
| `volatile-ttl` | 设置了过期时间的 key | TTL 最小的优先 | 希望快过期的先淘汰 |

```bash
# redis.conf
maxmemory 2gb
maxmemory-policy allkeys-lfu
```

**📦 实际例子：**

悦茶平台的 Redis 用于缓存层，配置 2GB 内存上限：

```bash
maxmemory 2gb
maxmemory-policy allkeys-lfu
```

选择 `allkeys-lfu` 的原因：
- 商品详情页缓存（`product:detail:{sku}`）访问频率极高，LFU 会保留
- 用户临时浏览记录（`browse:{uid}`）访问频率低，优先被淘汰
- 门店实时库存（`stock:{storeId}:{sku}`）设置有过期时间，不会被 LRU 误删（因为有 volatile 前缀的策略不会碰它们——不对，allkeys-lfu 会淘汰所有 key，包括库存）

实际上悦茶平台使用的是 `volatile-lfu`，只对设置了过期时间的缓存 key 进行淘汰，而库存等关键数据不设过期时间（由业务层控制更新），不会被误淘汰。

**🔍 源码解析：**

Redis 的 LRU 实现不是传统的全局 LRU（不需要维护链表），而是**近似 LRU**：

```c
// evict.c - 近似 LRU 实现
void performEvictions(void) {
    // 每次淘汰时，随机采样 maxmemory-samples（默认5）个 key
    // 从中选择最"旧"的淘汰
    // 重复直到释放足够内存或无法继续淘汰
    
    while (mem_freed < (long)mem_to_free) {
        // 随机采样 N 个 key
        dictEntry *samples[MAX_MEMORY_SAMPLES];  // 默认 5
        dictGetSomeKeys(samples, ...);
        
        // 找到最"旧"的 key
        for (int j = 0; j < samples; j++) {
            int idle = estimateObjectIdleTime(sample);
            if (idle > best_idle) {
                bestkey = sample;
                best_idle = idle;
            }
        }
        // 淘汰 bestkey
        dbDelete(server.db[dbid], bestkey);
    }
}
```

Redis 的 LRU 近似算法的优势：不需要为每个 key 维护链表指针，内存开销极低（`robj->lru` 字段只有 24 位，记录最后一次访问时间）。采样数越大越接近精确 LRU，但开销也越大。

LFU 的实现（Redis 4.0+）使用对数计数器：

```c
// Redis 的 LFU 使用 8 位存储，实现 0-255 的对数计数
// 高 16 位：上次衰减时间（分钟级别）
// 低 8 位：对数计数器（logarithmic counter）
#define LFU_LOG_FACTOR 10  // 衰减因子

// 访问频率越高，计数器增长越慢（对数增长）
// 时间越久，计数器自动衰减（模拟热度衰减）
```

**⚠️ 常见坑/加分回答：**

- `maxmemory-samples` 默认值在 Redis 5.0+ 从 5 改为 10，提高淘汰精度。
- 坑：`noeviction` 策略下内存满了不会报错，只是写入命令返回 `OOM` 错误，读取命令仍然正常。客户端需要捕获 OOM 异常。
- 加分回答：生产环境推荐使用 LFU 而非 LRU。LFU 基于访问频率淘汰，能更好地保留热点数据。可以用 `OBJECT FREQ key` 查看 key 的 LFU 频率值（0-255）。

### 第11集：Redis的内存碎片是怎么产生的？怎么解决（activedefrag）

**💡 核心回答：**

内存碎片是指 Redis 进程实际占用的物理内存（RSS）远大于实际数据占用的内存。碎片率 = RSS / 实际数据内存。碎片率 > 1.5 时需要关注。

产生原因：
1. **频繁分配释放**：大量 key 的创建和删除，导致内存中出现无法利用的"空洞"
2. **allocator 特性**：Redis 默认使用 jemalloc（Linux），不同的分配器碎片率不同
3. **大小类不匹配**：频繁修改 value 导致反复 realloc，产生碎片

解决方案：
1. **重启 Redis**：最彻底但影响最大
2. **activedefrag（Redis 4.0+）**：在线碎片整理，不影响服务
3. **调整 allocator**：jemalloc 通常比 libc 碎片率低

```bash
# 查看碎片率
redis-cli INFO memory | grep frag
# mem_fragmentation_ratio: 1.85  ← 碎片率较高

# 开启主动碎片整理
redis-cli CONFIG SET activedefrag yes
redis-cli CONFIG SET active-defrag-threshold-lower 10    # 碎片率 > 10% 开始整理
redis-cli CONFIG SET active-defrag-cycle-min 5           # 最少占用 5% CPU
redis-cli CONFIG SET active-defrag-cycle-max 75          # 最多占用 75% CPU
```

**📦 实际例子：**

悦茶平台的 Redis 在促销活动后（大量临时缓存创建和过期），碎片率飙升到 2.1。运维团队通过开启 activedefrag，在不重启的情况下将碎片率降至 1.2：

```bash
# 碎片率监控脚本
FRAG=$(redis-cli INFO memory | grep mem_fragmentation_ratio | cut -d: -f2 | tr -d '\r')
echo "当前碎片率: $FRAG"

if (( $(echo "$FRAG > 1.5" | bc -l) )); then
    redis-cli CONFIG SET activedefrag yes
    echo "已开启主动碎片整理"
fi
```

**🔍 源码解析：**

activedefrag 的核心实现在 `defrag.c`，利用 Redis 的事件循环在空闲时执行碎片整理：

```c
// defrag.c
void activeDefragCycle(void) {
    if (!server.active_defrag_enabled) return;
    
    mstime_t start = mstime();
    mstime_t budget;  // 本轮可以使用的 CPU 时间
    
    // 根据碎片率动态调整 CPU 占用比例
    if (server.stat_active_defrag_running == 0) {
        float frag = getMemoryFragmentationRatio();
        if (frag > server.active_defrag_threshold_upper) {
            server.stat_active_defrag_running = server.active_defrag_cycle_max;
        } else if (frag > server.active_defrag_threshold_lower) {
            // 线性插值：碎片率越高，分配的 CPU 时间越多
            server.stat_active_defrag_running = ...;
        }
    }
    
    // 遍历数据库中的 key，对 value 进行重新分配
    // 核心操作：jemalloc 的 mallocx + dallocx
    // 将数据从碎片化的内存位置搬到连续的内存位置
    while (mstime() - start < budget) {
        // 对每个 key 的 robj 检查是否需要 defrag
        defragKey(db, key);
    }
}
```

activedefrag 依赖 jemalloc 的 `jemalloc_ptr_malloct()` 接口来查询指针所在的内存块大小，然后用 `jemalloc_mallocx()` 分配新的合适大小的内存块，复制数据后释放旧的。这个过程需要遍历 dict 的每个 entry，所以 CPU 开销较大。

**⚠️ 常见坑/加分回答：**

- activedefrag 只在 Redis 4.0+ 且使用 jemalloc 时可用。如果使用 libc allocator，则不支持在线碎片整理，只能重启。
- 坑：开启 activedefrag 会消耗 CPU，在高负载时可能导致延迟增加。建议设置 `active-defrag-cycle-max` 不超过 30%，避免影响正常请求。
- 加分回答：可以通过 `CONFIG SET activedefrag no` 临时关闭碎片整理。也可以通过 `INFO memory` 中的 `allocator_frag_ratio` 精确查看 jemalloc 层面的碎片情况。

### 第12集：Redis对象池和共享整数集合是什么？内存优化的细节

**💡 核心回答：**

Redis 有两层内存优化机制，对客户端完全透明：

**1. 整数共享（Integer Sharing）**

Redis 会缓存 0-9999 的整数值。当多个 key 的值恰好是这些整数时，它们共享同一个 `robj` 对象（引用计数 > 1），而不是每个 key 创建独立的对象。

```redis
SET key1 100
SET key2 100
# key1 和 key2 的 robj 指向同一个整数对象
OBJECT REFCOUNT key1  # 返回 2
OBJECT REFCOUNT key2  # 返回 2
```

**2. SDS 共享（embstr 复用）**

短字符串（≤ 32 字节）使用 embstr 编码，虽然不是跨 key 共享，但通过连续内存分配减少了内存碎片。

**3. 对象池的体现**

Redis 内部不直接 `malloc/free` 小对象，而是通过内存分配器（jemalloc）的 tcache 机制实现类似对象池的效果。频繁分配释放的相同大小的内存块会被缓存复用。

**📦 实际例子：**

悦茶平台的订单状态缓存中，大量订单的状态值是整数（如 0=待支付、1=已支付、2=制作中、3=配送中、4=已完成）。由于这些值都在 0-9999 范围内，Redis 自动共享这些整数对象：

```redis
SET order:status:10001 2  # 制作中
SET order:status:10002 2  # 制作中
SET order:status:10003 0  # 待支付
# 在高峰期，可能有上万个订单的状态值都是 2
# 这些 key 共享同一个 robj，节省了大量内存
```

悦茶平台有 5 万个并发订单，其中约 2 万个处于"制作中"（状态值 2），共享整数对象为这 2 万个 key 节省了约 2 万个 robj 的内存开销（每个约 16 字节），总共节省约 320KB。

**🔍 源码解析：**

整数共享的实现在 `object.c`：

```c
// object.c
#define OBJ_SHARED_INTEGERS 10000

// 全局共享整数对象数组
static robj *shared_integers[OBJ_SHARED_INTEGERS];

// 初始化时预创建
void initSharedObjects(void) {
    for (int j = 0; j < OBJ_SHARED_INTEGERS; j++) {
        shared_integers[j] = createObject(OBJ_STRING, (void*)(long)j);
        shared_integers[j]->encoding = OBJ_ENCODING_INT;
        // refcount 初始设为 1，使用时递增
    }
}

// 创建 String 对象时检查是否可共享
robj *createStringObject(const char *ptr, size_t len) {
    // 尝试转换为整数
    if (string2l(ptr, len, &value)) {
        if (value >= 0 && value < OBJ_SHARED_INTEGERS) {
            // 使用共享整数对象
            shared_integers[value]->refcount++;
            return shared_integers[value];
        }
    }
    // 不在共享范围内，创建新对象
    return createStringObjectFromLongLong(value);
}
```

jemalloc 的 tcache 机制：

```
jemalloc 的内存分配层级：
┌─────────────┐
│ Application │ SET key1 value1 → malloc(32)
├─────────────┤
│ tcache      │ 缓存最近释放的小内存块（per-thread）
│ (per-thread)│ 下次 malloc(32) 直接从 tcache 取
├─────────────┤
│ arena       │ 实际的内存区域，按 size class 管理
│             │ size class: 16, 32, 48, 64, 80, 96, ...
├─────────────┤
│ OS          │ mmap/brk 向操作系统申请内存
└─────────────┘
```

Redis 频繁创建/销毁相同大小的 robj（如 SDS、dictEntry），jemalloc 的 tcache 会将这些内存块缓存住，下次分配时直接复用，避免了系统调用开销。

**⚠️ 常见坑/加分回答：**

- 整数共享范围是 0-9999（`OBJ_SHARED_INTEGERS` 宏定义），负数和大于等于 10000 的整数不会共享。
- 坑：`OBJECT REFCOUNT key` 返回的引用计数包含了共享引用。当你看到 refcount > 1 时，不一定是你的程序有 bug，可能是整数共享导致的。
- 加分回答：RESP2 协议下，Redis 还有一些预分配的共享对象，如 `shared.ok`、`shared.err`、`shared.emptybulk` 等常用回复对象，减少重复创建。RESP3 协议（Redis 6.0+）进一步优化了一些共享对象的使用。

### 第13集：Redis的大KEY问题怎么发现和解决？bigkeys工具和scan方案

**💡 核心回答：**

大 Key（Big Key）是指 value 占用内存过大或元素数量过多的 key。大 Key 会导致：

1. **操作阻塞**：DEL 一个大 Hash 可能阻塞主线程数秒
2. **内存不均**：一个大 key 占用了不成比例的内存
3. **网络拥塞**：读取大 key 返回大量数据，占用带宽
4. **集群失衡**：在 Cluster 模式下，大 key 可能导致某个分片内存过高

大 Key 的阈值（经验值）：
- String：value > 10KB
- Hash/List/Set/ZSet：元素数 > 5000 或内存 > 100KB

```bash
# 方法1：redis-cli --bigkeys（采样分析）
redis-cli --bigkeys

# 方法2：SCAN + STRLEN/LEN 扫描（精确但慢）
# 方法3：MEMORY USAGE key（查看单个 key 内存）
redis-cli MEMORY USAGE bigkey

# 方法4：RDB 分析工具（推荐，离线分析不影响线上）
redis-cli --rdb /dev/stdout | redis-rdb-tools rdb -p memory --only-keys -
```

**📦 实际例子：**

悦茶平台上线新功能"门店历史订单缓存"后，发现 Redis 内存暴涨。排查发现某个门店的 key `store:order:history:10086` 是一个 List，包含了该门店所有历史订单（超过 50 万条），单个 key 占用内存 200MB。

```bash
# 用 redis-cli --bigkeys 扫描
$ redis-cli --bigkeys

# Biggest zset found: 'rank:point:alltime' with 85000 entries
# Biggest hash found: 'store:order:history:10086' with 500000 fields (200MB)
```

解决方案：
1. 将 List 拆分为按日期分片：`store:order:history:{storeId}:{date}`
2. 使用 `LTRIM` 限制 List 最大长度
3. 对已有的大 key 使用 `UNLINK` 异步删除

**🔍 源码解析：**

`redis-cli --bigkeys` 的实现原理：

```c
// redis-cli.c (简化版)
void getBigKeys(void) {
    // 使用 SCAN 遍历所有 key
    cursor = "0";
    do {
        reply = redisCommand(ctx, "SCAN %s COUNT 1000", cursor);
        // 获取一批 key
        keys = reply->element[1];
        
        for (int i = 0; i < keys->elements; i++) {
            key = keys->element[i]->str;
            // 获取 key 的类型
            type = redisCommand(ctx, "TYPE %s", key);
            
            // 根据类型调用不同的统计命令
            if (type == "string") {
                len = redisCommand(ctx, "STRLEN %s", key);
            } else if (type == "hash") {
                len = redisCommand(ctx, "HLEN %s", key);
            } else if (type == "list") {
                len = redisCommand(ctx, "LLEN %s", key);
            } else if (type == "set") {
                len = redisCommand(ctx, "SCARD %s", key);
            } else if (type == "zset") {
                len = redisCommand(ctx, "ZCARD %s", key);
            }
            
            // 更新各类型的最大 key 统计
            if (len > biggest[type]) {
                biggest[type] = len;
                biggest_key[type] = key;
            }
        }
    } while (cursor != "0");
}
```

为什么不用 `KEYS *` 而用 `SCAN`？因为 `KEYS *` 是阻塞操作，会遍历整个 keyspace 才返回，在大内存实例上可能阻塞数秒。`SCAN` 是增量遍历，每次只返回少量 key，不会长时间阻塞主线程。

`MEMORY USAGE` 的实现：

```c
// object.c
void memoryCommand(client *c) {
    robj *o = dbLookupKeyRead(c->db, c->argv[1]);
    // 计算对象的内存占用
    size_t size = sizeof(robj);  // 16 字节（redisObject 本身）
    size += getStringObjectLength(o);  // SDS 的实际长度
    
    // 根据 encoding 累加底层结构的内存
    switch(o->encoding) {
        case OBJ_ENCODING_HT:
            size += dictSize(o->ptr) * sizeof(dictEntry);  // 每个 entry
            size += dictBuckets(o->ptr) * sizeof(dictEntry*);  // hash 桶
            break;
        case OBJ_ENCODING_SKIPLIST:
            size += zsl->length * sizeof(zskiplistNode);
            // 加上每层的指针开销
            break;
    }
    addReplyLongLong(c, size);
}
```

**⚠️ 常见坑/加分回答：**

- `redis-cli --bigkeys` 使用采样方式（SCAN COUNT 默认不是全量扫描），可能漏掉部分大 key。生产环境推荐使用 `rdb-tools` 离线分析 RDB 文件，能获取精确的全量数据。
- 坑：发现大 key 后不能直接 `DEL`，否则会导致主线程阻塞。必须使用 `UNLINK`（异步删除）或者用 `HSCAN`/`SSCAN` 逐步删除元素。
- 加分回答：从 Redis 6.2 开始，`lazyfree-lazy-user-del` 默认开启，即 `DEL` 命令默认异步执行。但为了安全，生产环境仍建议对大 key 使用显式的 `UNLINK`，并设置 `lazyfree-lazy-user-del yes`。

## 第4系列：缓存三大问题

### 第14集：缓存穿透是什么？布隆过滤器的原理和实现，怎么防穿透

**💡 核心回答：**

**缓存穿透**：查询一个**根本不存在**的数据，缓存层和数据库都不会命中，每次请求都打到数据库。如果有大量此类请求，数据库会承受巨大压力。

常见场景：恶意攻击者用不存在的 ID 频繁请求、数据已被删除但请求仍在。

解决方案：
1. **缓存空值**：查不到数据时，在缓存中存一个空值（设置较短 TTL），下次请求直接返回空
2. **布隆过滤器**：在缓存前置一层布隆过滤器，快速判断 key 是否存在
3. **参数校验**：在应用层校验参数合法性，过滤明显非法的 ID

```java
// 方案1：缓存空值
public Product getProduct(Long id) {
    String key = "product:detail:" + id;
    String cached = redis.get(key);
    if ("NULL".equals(cached)) {
        return null;  // 已确认不存在
    }
    if (cached != null) {
        return JSON.parseObject(cached, Product.class);
    }
    // 查数据库
    Product product = productMapper.selectById(id);
    if (product == null) {
        // 缓存空值，TTL 3分钟，防止穿透
        redis.setex(key, 180, "NULL");
        return null;
    }
    redis.setex(key, 3600, JSON.toJSONString(product));
    return product;
}
```

**📦 实际例子：**

悦茶平台曾遭受恶意爬虫攻击，攻击者用随机生成的商品 ID（大部分不存在）高频请求商品详情接口，导致 MySQL 被打到 CPU 100%。

解决方案：引入布隆过滤器。悦茶平台所有上架商品的 SKU ID 在入库时同步写入布隆过滤器。请求到达时先查布隆过滤器，如果判断不存在则直接返回 404，不会到达数据库。

```java
// 悦茶平台布隆过滤器实现
public class BloomFilterService {
    private static final long NUM_BITS = 1L << 30;  // 1G bit ≈ 128MB
    private static final int HASH_COUNT = 7;
    
    // 商品入库时添加到布隆过滤器
    public void addProduct(String skuId) {
        for (int i = 0; i < HASH_COUNT; i++) {
            long hash = murmurHash(skuId, i);
            long bitPos = hash % NUM_BITS;
            redis.setbit("bloom:product", bitPos, true);
        }
    }
    
    // 查询时先检查布隆过滤器
    public boolean mightExist(String skuId) {
        for (int i = 0; i < HASH_COUNT; i++) {
            long hash = murmurHash(skuId, i);
            long bitPos = hash % NUM_BITS;
            if (!redis.getbit("bloom:product", bitPos)) {
                return false;  // 一定不存在
            }
        }
        return true;  // 可能存在（有误判率）
    }
}
```

**🔍 源码解析：**

Redis 的 Bitmap 底层就是 String 类型的 SDS：

```c
// 当执行 SETBIT 时，Redis 扩展 SDS 到足够大
// setbitCommand -> setBit -> extendBitmapIfNeeded
void setbitCommand(client *c) {
    long bitoffset = getLongLongFromObject(c->argv[2]);
    long byte = bitoffset >> 3;        // bit 位置 / 8 = byte 位置
    long bit = bitoffset & 0x7;        // bit 位置 % 8 = byte 内的偏移
    
    // 如果 byte 位置超出当前 SDS 长度，需要扩展
    if (byte >= sdslen(o->ptr)) {
        // 扩展 SDS，新字节填充 0
        o->ptr = sdsMakeRoomFor(o->ptr, byte - sdslen(o->ptr) + 1);
        memset(sdslen(o->ptr) + (char*)o->ptr, 0, byte - sdslen(o->ptr) + 1);
    }
    // 设置/清除指定的 bit
    byte_val = ((uint8_t*)o->ptr)[byte];
    if (on) byte_val |= (1 << bit);
    else    byte_val &= ~(1 << bit);
}
```

布隆过滤器的数学原理：

```
误判率（False Positive Rate）公式：
P = (1 - e^(-k*n/m))^k

其中：
- m = 位数组大小（bit 数量）
- n = 元素数量
- k = 哈希函数个数

悦茶平台的布隆过滤器参数：
- m = 2^30 ≈ 10亿位 ≈ 128MB
- n = 500万（所有 SKU 数量）
- k = 7
- 误判率 ≈ 0.008%（约万分之0.8）
```

**⚠️ 常见坑/加分回答：**

- 布隆过滤器**只能判断"一定不存在"和"可能存在"**，不支持删除（标准布隆过滤器）。如果需要删除功能，可以使用 Counting Bloom Filter（用计数器替代单 bit）。
- 坑：布隆过滤器的误判率与容量直接相关。如果实际元素数量远超预期容量，误判率会急剧上升。需要预留足够的容量空间。
- 加分回答：Redis 4.0+ 可以使用 RedisBloom 模块直接支持布隆过滤器的命令（`BF.ADD`、`BF.EXISTS`），自动处理扩容。生产环境推荐使用模块而非自己实现。

### 第15集：缓存击穿是什么？热点key过期瞬间大量请求打DB，互斥锁和逻辑过期两种方案

**💡 核心回答：**

**缓存击穿**：一个**热点 key** 在过期的瞬间，大量并发请求同时发现缓存失效，全部去查数据库，导致数据库瞬间压力飙升。

与缓存穿透的区别：
- 穿透：数据**不存在**，缓存和 DB 都没有
- 击穿：数据**存在**，但缓存刚好过期，大量请求同时打到 DB

两种主流解决方案：

**方案1：互斥锁（Mutex Lock）**
- 只允许一个线程去查 DB 并重建缓存，其他线程等待
- 优点：数据一致性好
- 缺点：有等待延迟

**方案2：逻辑过期（Logical Expiration）**
- 缓存不设物理 TTL，由业务层记录逻辑过期时间
- 发现过期时先返回旧数据，异步线程去重建缓存
- 优点：无等待，性能好
- 缺点：短时间内可能返回旧数据

```java
// 方案1：互斥锁实现
public Product getProductWithLock(Long id) {
    String key = "product:detail:" + id;
    String cached = redis.get(key);
    if (cached != null) return JSON.parseObject(cached, Product.class);
    
    String lockKey = "lock:product:" + id;
    // 尝试获取分布式锁
    if (redis.set(lockKey, "1", "NX", "PX", 3000)) {
        try {
            // 双重检查
            cached = redis.get(key);
            if (cached != null) return JSON.parseObject(cached, Product.class);
            
            // 查 DB 并重建缓存
            Product product = productMapper.selectById(id);
            redis.setex(key, 3600, JSON.toJSONString(product));
            return product;
        } finally {
            redis.del(lockKey);
        }
    } else {
        // 未获取到锁，短暂等待后重试
        Thread.sleep(50);
        return getProductWithLock(id);  // 递归重试
    }
}

// 方案2：逻辑过期实现
public Product getProductWithLogicExpire(Long id) {
    String key = "product:detail:" + id;
    Map<String, String> cached = redis.hgetAll(key);
    if (cached.isEmpty()) return null;  // 缓存未建立，由另一个线程处理
    
    Product product = JSON.parseObject(cached.get("data"), Product.class);
    long expireTime = Long.parseLong(cached.get("expireTime"));
    
    if (System.currentTimeMillis() < expireTime) {
        return product;  // 未过期，直接返回
    }
    
    // 已过期：先返回旧数据，异步重建缓存
    String lockKey = "lock:product:" + id;
    if (redis.set(lockKey, "1", "NX", "PX", 3000)) {
        // 异步线程池重建缓存
        executor.submit(() -> {
            try {
                Product fresh = productMapper.selectById(id);
                Map<String, String> newCache = new HashMap<>();
                newCache.put("data", JSON.toJSONString(fresh));
                newCache.put("expireTime", String.valueOf(System.currentTimeMillis() + 3600000));
                redis.hmset(key, newCache);  // 不设物理 TTL
            } finally {
                redis.del(lockKey);
            }
        });
    }
    return product;  // 返回旧数据
}
```

**📦 实际例子：**

悦茶平台的"今日特价"商品详情页是一个典型的热点 key。每天 10:00 准时更新特价商品，旧缓存过期瞬间可能有上千个并发请求。

悦茶采用**逻辑过期方案**：特价商品缓存不设物理 TTL，而是记录逻辑过期时间。10:00 更新时，第一个发现过期的请求返回旧特价信息，同时异步触发新特价数据的加载。用户端几乎无感知延迟。

```java

//   data: {"skuId": "SKU001", "name": "茉莉花茶", "price": 9.9}
//   expireTime: 1704106800000  (逻辑过期时间戳)
```

**🔍 源码解析：**

互斥锁方案中 `SET key value NX PX` 的原子性来自 Redis 源码：

```c
// t_string.c - SET 命令实现
void setCommand(client *c) {
    // 解析 NX/PX/EX 等选项
    int unit = 1000;  // PX 毫秒
    int nx = 0, xx = 0;
    long long milliseconds = -1;
    
    // 解析参数...

        addReply(c, shared.nullbulk);  // key 已存在，返回 nil
```

`SET ... NX PX` 是一个原子命令，从检查到写入在同一个事件循环迭代中完成，不会有并发问题。

热点 key 过期时大量请求打 DB 的时序：

```
时间线：
T0: 热点 key 过期
T1: 1000 个请求同时 GET → 全部 miss
T2: 1000 个请求同时查询 DB → DB 压力飙升
T3: DB 返回 → 1000 个请求同时 SET 相同值 → 浪费

使用互斥锁后：
T0: 热点 key 过期
T1: 1000 个请求同时 GET → 全部 miss
T2: 第 1 个请求获取锁成功，其余 999 个等待
T3: 第 1 个请求查 DB → SET 缓存 → 释放锁
T4: 其余 999 个请求重试 → GET 命中缓存 → 直接返回
```

**⚠️ 常见坑/加分回答：**

- 互斥锁方案中，如果获取锁的线程异常退出没有释放锁，其他线程会永久等待。必须设置锁的 TTL，并在 finally 中释放。
- 坑：逻辑过期方案在缓存为空时（首次加载或手动清理后），需要有兜底机制。可以用"缓存空值 + 同步加载"处理首次加载的情况。
- 加分回答：热点 key 问题不仅仅是缓存击穿，如果 key 一直在同一个 Redis 节点上，还会导致该节点 CPU/网络过载。Redis 4.0+ 可以使用 `redis-cli --hotkeys`（基于 LFU 频率）发现热点 key，再通过 `redis-trib` 或手动迁移到独立节点。




### 第16集：缓存雪崩是什么？过期时间加随机值、多级缓存、熔断降级

**💡 核心回答：**

**缓存雪崩**：大量缓存 key 在同一时间集中过期，或者 Redis 实例宕机，导致大量请求直接打到数据库，造成数据库压力骤增甚至崩溃。

与缓存穿透、缓存击穿的区别：
- **穿透**：数据不存在，查不到
- **击穿**：单个热点 key 过期，并发打 DB
- **雪崩**：大批量 key 同时过期，或 Redis 整体不可用

三种解决方案：

**1. 过期时间加随机值**
- 在基础过期时间上加一个随机偏移，避免大量 key 同时过期
- `TTL = baseTTL + random(0, maxJitter)`

**2. 多级缓存架构**
- L1：本地缓存（Caffeine/Guava），应对极端热点数据
- L2：Redis 分布式缓存
- L3：数据库兜底
- 即使 Redis 全部过期，本地缓存仍能扛住一部分

**3. 熔断降级**
- 当数据库压力过大时，触发熔断，返回默认值或缓存中的旧数据
- 使用 Sentinel/Resilience4j 等熔断框架

```java
// 方案1：过期时间加随机值
public void setWithJitter(String key, String value, long baseTTL) {
    // 基础 TTL + 0~300秒的随机偏移
    long jitter = ThreadLocalRandom.current().nextLong(0, 300);
    redis.setex(key, baseTTL + jitter, value);
}

// 方案2：多级缓存
public Product getProduct(Long id) {
    String key = "product:" + id;
    
    // L1: 本地缓存
    Product product = localCache.getIfPresent(key);
    if (product != null) return product;
    
    // L2: Redis 缓存
    String cached = redis.get(key);
    if (cached != null) {
        product = JSON.parseObject(cached, Product.class);
        localCache.put(key, product);  // 回填本地缓存
        return product;
    }
    
    // L3: 数据库
    product = productMapper.selectById(id);
    if (product != null) {
        redis.setex(key, 3600 + ThreadLocalRandom.current().nextInt(300),
                     JSON.toJSONString(product));
        localCache.put(key, product);
    }
    return product;
}

// 方案3：熔断降级
@CircuitBreaker(name = "productService", fallbackMethod = "fallbackGetProduct")
public Product getProductWithBreaker(Long id) {
    return getProduct(id);
}

public Product fallbackGetProduct(Long id, Throwable t) {

    if (oldData != null) return JSON.parseObject(oldData, Product.class);
    return Product.DEFAULT;  // 兜底默认值
}
```

**📦 实际例子：**

悦茶平台在 2024 年春节促销活动中，由于运营批量配置了 2000+ 个商品的缓存过期时间为同一时刻（活动结束时间 23:59:59），导致 00:00:00 瞬间大量缓存同时过期，MySQL 被瞬时 5 万 QPS 的查询打到 CPU 100%，触发数据库告警。

事后修复方案：
1. 所有缓存 TTL 增加随机偏移（`3600 + random(0, 600)`）
2. 引入 Caffeine 本地缓存作为 L1，配置 5 分钟过期
3. 数据库层增加 Sentinel 熔断，当 RT > 500ms 时触发降级，返回缓存中的旧数据

**🔍 源码解析：**

Redis 的过期 key 删除策略（与雪崩相关）：

```c
// expire.c - Redis 的过期删除策略

// 1. 惰性删除：访问 key 时检查是否过期
int expireIfNeeded(redisDb *db, robj *key) {
    mstime_t when = getExpire(db, key);
    if (when < 0) return 0;  // 没有设置过期期
    if (server.current_time < when) return 0;  // 未过期
    
    // 已过期，删除 key
    return expireAndPropagate(db, key, ...);
}

// 2. 定期删除：每 100ms（serverCron 的一部分）随机抽样检查
void activeExpireCycle(int type) {
    // 每次从数据库中随机取 20 个设置了过期的 key
    #define ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP 20
    
    for (int j = 0; j < ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP; j++) {
        // 随机取一个有过期 key 的 bucket
        dictEntry *de = dictGetRandomKey(db->expires);
        if (de == NULL) break;
        
        // 检查是否已过期
        if (activeExpireCycleTryExpire(db, de, now)) {
            expired++;
        }
    }
    
    // 如果超过 25% 的 key 已过期，继续扫描
    if (expired > ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP / 4) {
        // 继续下一轮扫描
    }
}
```

大量 key 同时过期时的行为：
1. 定期删除每 100ms 最多检查 20 个过期 key → 无法及时清理
2. 大量 key 在被访问时才惰性删除 → 访问时触发删除操作，增加响应延迟
3. 如果同时过期的 key 数量巨大（如百万级），即使定期删除也需要多轮才能清理完毕

这就是为什么需要在业务层避免 key 集中过期——给 TTL 加随机值，让过期时间分散开。

**⚠️ 常见坑/加分回答：**

- 过期时间加随机值是成本最低的防雪崩方案，建议在封装 Redis 工具类时统一处理，而不是让每个业务方自己加。
- 坑：多级缓存的 L1（本地缓存）会导致数据不一致窗口更长。如果数据更新频繁，本地缓存的 TTL 不宜过长（建议 1-5 分钟）。可以配合 Canal 监听 binlog 主动失效本地缓存。
- 加分回答：Redis 集群模式下，雪崩可能表现为"某个分片整体不可用"。此时需要使用 Sentinel/Cluster 的故障转移能力，配合客户端的重试和降级策略。悦茶平台对关键 Redis 实例配置了 3 个哨兵节点，故障转移时间控制在 10 秒以内。

### 第17集：缓存和数据库双写一致性怎么保证？先删缓存还是先更新DB？延迟双删方案

**💡 核心回答：**

缓存和数据库双写一致性的核心矛盾：更新数据时，需要同时更新数据库和缓存，但两个操作不是原子的，任何顺序都可能在极端情况下产生不一致。

三种策略对比：

| 策略 | 操作顺序 | 一致性保证 | 问题 |
|------|---------|-----------|------|
| 先更新 DB，再删缓存 | ✅ 推荐 | 最终一致 | 删缓存失败时数据不一致 |
| 先更新 DB，再更新缓存 | ❌ 不推荐 | 较差 | 并发写时可能脏数据覆盖 |
| 先删缓存，再更新 DB | ❌ 不推荐 | 差 | 读写并发时缓存被旧数据覆盖 |

**推荐方案：先更新 DB，再删除缓存 + 重试机制**

```java
// 推荐方案：先更新DB，再删缓存
@Transactional
public void updateProduct(Product product) {
    // 1. 更新数据库
    productMapper.updateById(product);
    
    // 2. 删除缓存
    boolean deleted = redis.del("product:detail:" + product.getId());
    
    // 3. 删除失败时重试（或发消息给 MQ 异步重试）
    if (!deleted) {
        retryQueue.send("product:detail:" + product.getId());
    }
}
```

**延迟双删方案**（更激进的一致性保证）：

```java
public void updateWithDoubleDelete(Product product) {
    // 1. 先删缓存
    redis.del("product:detail:" + product.getId());
    
    // 2. 更新数据库
    productMapper.updateById(product);
    
    // 3. 延迟 N 毫秒后再删一次缓存
    // N > 读请求的耗时，确保读请求已回填完缓存
    Thread.sleep(500);
    redis.del("product:detail:" + product.getId());
}
```

**📦 实际例子：**

悦茶平台的商品价格更新场景中，运营在后台修改某个商品的促销价。如果使用"先删缓存再更新DB"，在删缓存后、DB更新前，有用户查询该商品，会将旧价格写入缓存。等DB更新完成后，缓存中仍是旧价格，造成价格不一致——用户看到的价格与实际支付价格不同，这是严重的业务 bug。

悦茶采用"先更新DB + 再删缓存 + 异步重试"方案，并通过 Canal 监听 MySQL binlog 作为兜底，确保缓存最终一致。

**🔍 源码解析：**

"先删缓存再更新DB"为什么有问题？分析并发时序：

```
线程A（写操作）：              线程B（读操作）：
1. DEL cache（删除缓存）
                               2. GET cache → miss
                               3. SELECT DB → 旧数据（A还没更新）
                               4. SET cache = 旧数据
5. UPDATE DB = 新数据
                               → 缓存是旧数据，DB是新数据 ❌ 不一致！
```

"先更新DB再删缓存"的一致性分析：

```
线程A（写操作）：              线程B（读操作）：
1. UPDATE DB = 新数据
                               2. GET cache → 命中旧缓存
                               3. 返回旧数据（暂时不一致，但缓存即将过期）
4. DEL cache
                               5. 下次 GET → miss
                               6. SELECT DB → 新数据
                               7. SET cache = 新数据 ✓
```

删缓存失败的问题可以通过订阅 MySQL binlog（Canal）来补偿：

```java
// Canal 监听 binlog 的消费者
public class BinlogConsumer {
    public void onMessage(BinlogMessage msg) {
        if (msg.getOperation() == UPDATE) {
            // 兜底：重新删除缓存
            redis.del("product:detail:" + msg.getId());
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

- "延迟双删"中的延迟时间需要大于读请求的最大耗时。如果读请求涉及多个 SQL 查询，延迟时间可能较长，不太实用。
- 加分回答：对于强一致性要求的场景（如金融），不建议用缓存，直接查数据库。缓存适合"最终一致性可接受"的场景。
- 坑：删除缓存时如果用的是 Redis Cluster，DEL 可能只在一个节点上成功。需要确保 Cluster 模式下缓存删除的一致性。

## 第5系列：分布式锁

### 第18集：用Redis怎么实现分布式锁？SETNX的问题和正确写法（SET with NX PX）

**💡 核心回答：**

分布式锁的核心需求：互斥（同一时刻只有一个客户端持有锁）、防死锁（锁自动过期）、防误删（只能删除自己持有的锁）。

错误实现：
```redis
# 错误1：SETNX 和 EXPIRE 不是原子操作
SETNX lock:order 1
EXPIRE lock:order 30
# 如果 SETNX 成功但 EXPIRE 前进程崩溃 → 死锁

# 错误2：SETNX + EXPIRE 原子了，但释放锁不安全
SETNX lock:order 1
EXPIRE lock:order 30
# 业务完成后...
DEL lock:order
# 如果业务执行超过30秒，锁已过期被其他客户端获取，这里的 DEL 删了别人的锁
```

正确实现：
```redis
# 加锁：原子操作 SET key value NX PX
SET lock:order {unique_value} NX PX 30000

# 释放锁：Lua 脚本保证原子性
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order {unique_value}
```

```java
// Java 实现
public class RedisLock {
    private StringRedisTemplate redis;
    private String lockKey;
    private String uniqueValue;  // UUID + threadId

    public boolean tryLock(long timeoutMs) {
        this.uniqueValue = UUID.randomUUID().toString();
        Boolean result = redis.opsForValue()
            .setIfAbsent(lockKey, uniqueValue, Duration.ofMillis(timeoutMs));
        return Boolean.TRUE.equals(result);
    }

    public void unlock() {
        // Lua 脚本：检查并删除，原子操作
        String luaScript = 
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('del', KEYS[1]) " +
            "else " +
            "  return 0 " +
            "end";
        redis.execute(new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(lockKey), uniqueValue);
    }
}
```

**📦 实际例子：**

`SET key value NX PX` 在 Redis 源码中的原子性保证：

```c
// t_string.c - setCommand 简化
void setCommand(client *c) {
    // 1. 解析所有参数（key, value, NX, PX, EX, XX 等）
    // 2. 在同一个函数调用中完成检查和写入
    // 由于 Redis 单线程事件循环模型，这个函数执行期间不会被打断
    
    if (nx && lookupKeyWrite(c->db, key) != NULL) {
        // key 已存在，返回 nil（NX 语义）
        addReplyNull(c);
        return;
    }
    
    // 写入 key
    setKey(c->db, key, val);
    // 设置过期时间
    if (milliseconds > 0) {
        setExpire(c, c->db, key, mstime() + milliseconds);
    }
    
    // 整个过程在同一个事件循环迭代中完成
    // Redis 单线程保证不会被其他客户端的命令打断
    addReply(c, shared.ok);
}
```

为什么 Redis 单线程能保证原子性？因为 Redis 的核心命令处理是单线程的（Redis 6.0+ 网络 IO 多线程，但命令执行仍然单线程）。一个命令从开始执行到返回结果，不会被其他命令打断。这就是 SET NX PX 原子性的本质。

锁超时的问题：

```
T0: 客户端A获取锁，设置30秒超时
T15: 客户端A GC 暂停（Full GC）15秒
T30: 锁过期自动释放
T31: 客户端B获取锁
T32: 客户端A GC 结束，继续执行 → 认为还持有锁，实际已被B持有 ❌
T33: 客户端A释放锁 → 删了客户端B的锁 ❌
```

unique_value 的作用就是防止这种误删。每个客户端用 UUID 标识自己，释放锁时通过 Lua 脚本检查"这个锁是不是我的"。

**⚠️ 常见坑/加分回答：**

- 锁的超时时间要大于业务执行时间。但设太长会导致持锁者崩溃后其他客户端等待太久。这就是为什么需要 Redisson 的 WatchDog 续期机制（下一集详细讲）。
- 坑：`SETNX` 命令在 Redis 2.6.12 之后被 `SET ... NX` 替代。虽然 SETNX 仍可用，但 SET NX PX 是更推荐的写法。
- 加分回答：Redis 的锁不能保证 100% 可靠（特别是在主从切换时），如果对一致性有极高要求，需要考虑 RedLock 或使用 ZooKeeper。

### 第19集：Redisson分布式锁的实现原理？看门狗（WatchDog）续期机制

**💡 核心回答：**

Redisson 是 Java 生态最流行的 Redis 客户端，其分布式锁实现解决了原生 Redis 锁的几个痛点：

1. **自动续期（WatchDog）**：持锁期间自动延长锁的过期时间，避免业务未执行完锁就过期
2. **可重入锁**：同一个线程可以多次获取同一把锁
3. **阻塞/非阻塞获取**：支持 `tryLock` 和 `lock` 两种方式
4. **公平锁**：支持公平锁模式

核心流程：
1. 加锁：使用 Lua 脚本保证原子性，底层用 Hash 结构记录锁的持有者和重入次数
2. WatchDog：每 10 秒（默认锁时间的 1/3）检查一次，如果当前线程仍持有锁，则续期 30 秒
3. 释放锁：Lua 脚本检查持有者身份，减计数或删除锁

```java
// Redisson 使用示例
Config config = new Config();
config.useSingleServer().setAddress("redis://127.0.0.1:6379");
RedissonClient redisson = Redisson.create(config);

RLock lock = redisson.getLock("lock:order:" + orderId);
try {
    // 等待最多10秒获取锁，锁自动过期时间30秒
    if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
        try {
            // 业务逻辑
            processOrder(orderId);
        } finally {
            lock.unlock();
        }
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

**📦 实际例子：**

悦茶平台的订单支付回调处理中，使用 Redisson 分布式锁保证幂等性。支付平台可能重复发送回调通知，通过分布式锁确保同一笔订单只被处理一次：

```java
                    return;  // 已处理，直接返回
                }
                // 处理支付结果
                orderService.processPayResult(orderId, result);

                lock.unlock();
            }
        } else {
            log.warn("获取支付回调锁失败, orderId={}", orderId);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}
```

**🔍 源码解析：**

Redisson 的加锁 Lua 脚本（简化版）：

```lua
-- KEYS[1] = 锁的 key
-- ARGV[1] = 锁过期时间（毫秒）
-- ARGV[2] = 客户端唯一标识（UUID:threadId）

-- 检查锁是否存在
if (redis.call('exists', KEYS[1]) == 0) then
    -- 锁不存在，创建 Hash 类型的锁
    redis.call('hset', KEYS[1], ARGV[2], 1);  -- field=客户端ID, value=重入次数
    redis.call('pexpire', KEYS[1], ARGV[1]);   -- 设置过期时间
    return nil;  -- 加锁成功
end;

-- 锁存在，检查是否是当前客户端
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    -- 是同一客户端（可重入），重入次数 +1
    redis.call('hincrby', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;  -- 加锁成功
end;

-- 锁被其他客户端持有，返回锁的剩余过期时间
return redis.call('pttl', KEYS[1]);
```

释放锁 Lua 脚本：

```lua
if (redis.call('hexists', KEYS[1], ARGV[2]) == 0) then
    return nil;  -- 不是锁的持有者，直接返回
end;

local counter = redis.call('hincrby', KEYS[1], ARGV[2], -1);
if (counter > 0) then
    -- 重入次数 > 0，只减计数不删锁
    redis.call('pexpire', KEYS[1], ARGV[2]);
    return 0;
else
    -- 重入次数 = 0，删除锁
    redis.call('del', KEYS[1]);
    return 1;
end;
```

WatchDog 续期机制（Java 端实现）：

```java
// Redisson 源码简化
public class RedissonLock implements RLock {
    private static final long LOCK_WATCHDOG_TIMEOUT = 30000;  // 30秒
    private static final long WATCHDOG_RENEW_INTERVAL = LOCK_WATCHDOG_TIMEOUT / 3;  // 10秒
    
    // 加锁成功后启动 WatchDog
    private void renewExpiration() {
        ExpirationEntry ee = new ExpirationEntry();
        expirationRenewalMap.put(entryName, ee);
        
        // 定时任务：每10秒执行一次
        Timeout task = commandExecutor.getConnectionManager().newTimeout(new TimerTask() {
            @Override
            public void run(Timeout timeout) {
                // Lua 脚本续期
                Boolean result = commandExecutor.evalAsync(...,
                    "if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then " +
                    "  redis.call('pexpire', KEYS[1], ARGV[1]); " +
                    "  return 1; " +
                    "end; " +
                    "return 0;",
                    Collections.singletonList(lockKey),
                    LOCK_WATCHDOG_TIMEOUT, clientId);
                
                if (Boolean.TRUE.equals(result)) {
                    // 续期成功，继续调度下一次
                    renewExpiration();
                } else {
                    // 锁已不存在（被释放或超时），停止续期
                    expirationRenewalMap.remove(entryName);
                }
            }
        }, WATCHDOG_RENEW_INTERVAL, TimeUnit.MILLISECONDS);
    }
}
```

**⚠️ 常见坑/加分回答：**

- WatchDog 的续期时间是锁过期时间的 1/3（默认 10 秒），如果续期时网络抖动导致 Redis 不可达超过 10 秒，锁可能过期。生产环境需要监控 Redis 连接健康。
- 坑：`tryLock` 不指定 `leaseTime` 时才会启用 WatchDog。如果指定了 `leaseTime`，则使用固定过期时间，WatchDog 不生效。
- 加分回答：Redisson 的可重入锁使用 Hash 结构，key 是锁名，field 是 `UUID:threadId`，value 是重入次数。这使得同一个线程可以多次获取同一把锁而不死锁。

### 第20集：RedLock算法是什么？为什么有争议？Martin Kleppmann vs Antirez的争论

**💡 核心回答：**

RedLock 是 Redis 作者 Antirez 提出的分布式锁算法，用于解决单点 Redis 锁不可靠的问题（主从切换丢锁）。

**算法步骤：**
1. 部署 N 个独立的 Redis 实例（推荐 5 个，无主从关系）
2. 客户端依次向所有 N 个实例请求加锁（带超时和唯一值）
3. 如果在超过 N/2 + 1 个实例上加锁成功，且总耗时小于锁的有效时间，则认为加锁成功
4. 锁的实际有效时间 = 设定时间 - 获取锁耗时 - 时钟漂移补偿
5. 如果加锁失败，向所有实例发送释放锁请求

**争议焦点：**

Martin Kleppmann（《DERTA》作者）在 2016 年发表文章批评 RedLock：

| 批评点 | Antirez 的回应 |
|-------|--------------|
| 依赖时钟同步不安全 | 假设进程会暂停（GC），时钟可能跳跃 |
| 进程 GC 暂停后锁已过期 | WatchDog 可以缓解 |
| 网络分区时不安全 | 大多数场景下足够安全 |
| 不如用 ZooKeeper/Etcd | 承认 ZK 在强一致性锁场景更优 |

Martin 的核心观点：RedLock 的安全性依赖于"假设时钟是同步的"和"假设进程不会长时间暂停"，这两个假设在真实分布式系统中不成立。

**📦 实际例子：**

悦茶平台在技术选型时评估了 RedLock。考虑到悦茶的场景是电商缓存场景（允许极小概率的锁失效），最终选择了 Redisson 的单实例分布式锁 + WatchDog，而非 RedLock。原因是 RedLock 需要 5 个独立 Redis 实例，运维成本过高，且电商场景下锁失效可以重试。

如果悦茶的核心支付系统需要更强的锁保证，会考虑使用 ZooKeeper 的临时顺序节点来实现分布式锁。

**🔍 源码解析：**

RedLock 的核心实现在 Redisson 的 `RedissonRedLock` 类中：

```java
// Redisson 源码简化
public class RedissonRedLock extends RedissonMultiLock {
    
    public boolean tryLock(long waitTime, long leaseTime, TimeUnit unit) {
        // N = 锁的数量（Redis 实例数）
        int failedLocksLimit = failedLocksLimit();  // N/2 + 1
        int acquiredLocks = 0;
        long totalTime = 0;
        
        // 依次向每个 Redis 实例请求加锁
        for (RLock lock : locks) {
            long elapsed = System.currentTimeMillis();
            boolean lockAcquired = lock.tryLock(
                waitTime - totalTime,   // 剩余等待时间
                leaseTime, 
                unit
            );
            totalTime += System.currentTimeMillis() - elapsed;
            
            if (lockAcquired) {
                acquiredLocks++;
            } else {
                failedLocksLimit--;
            }
            
            // 如果失败数量超过 N/2，放弃
            if (failedLocksLimit <= 0) {
                // 加锁失败，释放所有已获取的锁
                unlockInner(Arrays.asList(locks));
                return false;
            }
        }
        
        // 检查：成功数 >= N/2 + 1 且总耗时 < 锁有效时间
        if (acquiredLocks >= (locks.size() / 2 + 1) && 
            totalTime < unit.toMillis(leaseTime)) {
            return true;
        }
        
        // 不满足条件，释放所有锁
        unlockInner(Arrays.asList(locks));
        return false;
    }
}
```

Martin Kleppmann 指出的关键问题（简化为时序）：

```
场景：进程 GC 暂停导致锁失效

T0: 客户端A从节点1获取锁（有效30秒）
T1: 节点1发生主从切换，锁数据丢失
T2: 客户端B从新主节点获取同一把锁
T3: 客户端A GC 结束（实际暂停了60秒）
T4: 客户端A继续执行，认为还持有锁 → 数据一致性被破坏

问题根源：
1. Redis 主从复制是异步的，主节点宕机时未同步的数据丢失
2. 进程暂停（GC/网络延迟）后，锁已过期但进程不知道
```

**⚠️ 常见坑/加分回答：**

- RedLock 需要 N 个完全独立的 Redis 实例，不是主从关系。这意味着运维成本是 N 倍。
- 加分回答：Martin 的建议是——如果需要强一致的分布式锁，使用 ZooKeeper（基于 ZAB 协议，有共识保证）或 Etcd（基于 Raft 协议）。Redis 的优势在于高性能，不在于强一致性。
- 坑：RedLock 的时间计算依赖系统时钟，如果某台机器的时钟发生跳跃（NTP 同步），可能导致锁的有效期计算错误。

### 第21集：分布式锁的容错设计：锁超时、不可重入、主从切换丢锁问题

**💡 核心回答：**

分布式锁的三个经典容错问题：

**1. 锁超时：业务执行时间超过锁的过期时间**

解决：WatchDog 自动续期（Redisson）、合理设置超时时间、锁续约接口

**2. 不可重入：同一线程多次获取同一把锁导致死锁**

解决：可重入锁（Redisson 用 Hash 结构记录重入次数）

**3. 主从切换丢锁：Redis 主节点宕机，锁数据未同步到从节点**

解决：(a) 接受风险（大多数场景可接受）；(b) RedLock 多实例；(c) 使用强一致性存储（ZooKeeper/Etcd）

**📦 实际例子：**

悦茶平台的订单创建流程中，需要对用户维度的操作加分布式锁防止并发创建：

```java
    }
```

**🔍 源码解析：**

主从切换丢锁的详细时序：

```
初始状态：
Master: lock:order = {value: "client_A", expire: T+30}
Slave:  lock:order = {value: "client_A", expire: T+30}  (异步复制，可能延迟)

T0: Master 宕机
T1: Slave 被提升为新的 Master
    问题：如果异步复制未完成，新 Master 上没有锁数据
T2: Client B 向新 Master 请求加锁 → 成功
T3: Client A 继续执行（认为锁还在），与 Client B 并发操作 → 数据不一致
```

Redisson 对主从切换问题的应对策略：

```java
// Redisson 的 RedLockWait 策略（可选）
// 在主从架构上使用 RedLock 的变种
public RLock getLock(String name) {
    // 默认使用单实例锁
    return new RedissonLock(commandExecutor, name);
}

// 如果需要更高可靠性，可以使用 RedLock
public RLock getRedLock(String... keys) {
    List<RLock> locks = new ArrayList<>();
    for (String key : keys) {
        locks.add(getLock(key));  // 每个 Redis 实例一把锁
    }
    return new RedissonRedLock(locks.toArray(new RLock[0]));

```

**⚠️ 常见坑/加分回答：**

- 生产环境中最常见的锁问题不是主从切换，而是"锁超时设置不合理"。建议根据 P99 接口耗时来设置锁超时时间，并启用 WatchDog。
- 加分回答：可以通过 `redis-cli MONITOR` 命令实时观察 Redisson 锁的命令交互，理解其工作原理。加锁时你会看到 `HSET` + `PEXPIRE`（或合并的 Lua 脚本），续期时看到 `PEXPIRE` 命令每 10 秒执行一次。
- 坑：Redisson 的 `lock()` 方法如果不指定超时时间，默认使用 WatchDog（30 秒过期，10 秒续期）。但如果 Redisson 客户端与 Redis 的连接断开，WatchDog 无法续期，锁会在 30 秒后过期。

## 第6系列：Redis集群与高可用

### 第22集：Redis主从复制的原理？全量同步和增量同步怎么切换

**💡 核心回答：**

Redis 主从复制（Replication）实现数据的读写分离和高可用。

**复制流程分为两个阶段：**

**1. 全量同步（Full Resync）**：从节点首次连接主节点时
- 主节点执行 `BGSAVE` 生成 RDB 快照
- 主节点将 RDB 文件发送给从节点
- 从节点加载 RDB 文件到内存
- 主节点将 RDB 生成期间的增量命令发送给从节点执行

**2. 增量同步（Partial Resync）**：网络短暂中断后重连
- 从节点带上次的 `offset`（偏移量）请求重连
- 主节点检查 `repl_backlog`（复制缓冲区）中是否包含从节点缺失的数据
- 如果包含 → 增量同步（只发送缺失部分）
- 如果不包含（缓冲区被覆盖）→ 退回全量同步

```bash
# 配置主从
# 从节点 redis.conf
replicaof 192.168.1.100 6379
masterauth your_password

# 运行时配置
redis-cli REPLICAOF 192.168.1.100 6379

# 查看复制状态
redis-cli INFO replication
```

**📦 实际例子：**

悦茶平台的 Redis 采用一主两从架构。写操作走主节点，读操作通过 `READONLY` 命令分散到从节点，减轻主节点压力：

```bash

# 从节点1：192.168.1.101:6379
# 从节点2：192.168.1.102:6379

replica-serve-stale-data no   # 数据过期时拒绝读请求
```

悦茶的从节点用于读取商品详情、门店信息等允许短暂延迟的数据。订单创建、库存扣减等写操作必须走主节点。

**🔍 源码解析：**

`repl_backlog`（复制积压缓冲区）是增量同步的关键：

```c
// replication.c
typedef struct {
    char *buf;          // 环形缓冲区
    long buf_size;      // 缓冲区大小（默认 1MB）
    long histlen;       // 已写入的总字节数（单调递增）
    long repl_offset;   // 当前偏移量
} replBacklog;

// 主节点每次执行写命令时，将命令追加到 repl_backlog
void replicationFeedSlaves(list *slaves, int dictid, robj **argv, int argc) {
    // 将命令序列化为 RESP 协议格式
    // 追加到 repl_backlog
    incrRefCount(buf);
    // 如果 repl_backlog 满了，覆盖最旧的数据（环形缓冲区）
}
```

全量同步 vs 增量同步的判断：

```c
// replication.c - PSYNC 命令处理
void psyncCommand(client *c) {
    long long offset = getLongLongFromObject(c->argv[2]);
    char *master_runid = c->argv[1]->ptr;
    
    // 检查 runid 是否匹配（是否是同一个主节点）
    if (strcmp(master_runid, server.runid) != 0) {
        // 不是同一个主节点 → 全量同步
        return FULL_RESYNC;
    }
    
    // 检查 offset 是否在 repl_backlog 范围内
    if (offset < server.repl_backlog_off ||
        offset > (server.repl_backlog_off + server.repl_backlog_histlen)) {
        // offset 超出缓冲区范围 → 数据已被覆盖 → 全量同步
        return FULL_RESYNC;
    }
    
    // offset 在范围内 → 增量同步
    // 从 offset 位置开始发送 repl_backlog 中的数据
    return PARTIAL_RESYNC;
}
```

repl_backlog 大小直接影响增量同步的成功率：

```bash
# 默认 repl_backlog_size 1mb
# 如果主从网络中断时间长，1MB 可能不够
# 建议根据写入 QPS 调整：
# 假设写入 10KB/s，中断 1 小时 = 36MB
repl-backlog-size 64mb
```

**⚠️ 常见坑/加分回答：**

- 全量同步期间，从节点可以配置 `replica-serve-stale-data yes`（默认）继续提供读服务（可能读到旧数据），或设为 `no` 拒绝所有读请求。
- 坑：从节点过多会加重主节点负担（RDB 传输 + 命令复制）。悦茶平台建议从节点不超过 3-5 个，更多读需求通过级联复制（从节点的从节点）解决。
- 加分回答：Redis 4.0+ 引入了无磁盘复制（`repl-diskless-sync yes`），主节点直接通过 socket 将 RDB 发送给从节点，跳过磁盘写入步骤，减少全量同步的时间和磁盘 IO。

### 第23集：Redis Sentinel哨兵模式的原理？故障检测和自动转移流程

**💡 核心回答：**

Redis Sentinel（哨兵）是 Redis 的高可用解决方案，提供三大功能：
1. **监控**：持续检查主从节点是否正常运行
2. **通知**：当节点异常时通知管理员/客户端
3. **自动故障转移**：主节点宕机时，自动将从节点提升为新主节点

**故障检测流程（三阶段）：**

1. **SDOWN（Subjectively Down）**：单个 Sentinel 认为节点不可达（连续 PING 超时）
2. **ODOWN（Objectively Down）**：多个 Sentinel 达成共识，认为主节点确实宕机（quorum 投票）
3. **故障转移**：选出一个 Sentinel 作为 Leader，执行转移操作

**自动转移流程：**
1. 从所有从节点中选择一个提升为新主节点
2. 新主节点开始服务
3. 其他从节点改为复制新主节点
4. 旧主节点恢复后变为从节点

```bash
# sentinel.conf
sentinel monitor mymaster 192.168.1.100 6379 2   # quorum=2
sentinel down-after-milliseconds mymaster 5000    # 5秒无响应判定 SDOWN
sentinel failover-timeout mymaster 60000          # 故障转移超时
sentinel parallel-syncs mymaster 1                # 同时只有1个从节点做全量同步
```

**📦 实际例子：**

悦茶平台的 Redis 高可用架构：1 主 2 从 3 哨兵，部署在不同物理机/可用区：

```
可用区A: Master(192.168.1.100) + Sentinel1
可用区B: Slave1(192.168.1.101) + Sentinel2  
可用区C: Slave2(192.168.1.102) + Sentinel3
```

当可用区A的网络中断时：
1. Sentinel1（本地网络正常但连不上 Master）报告 SDOWN
2. Sentinel2、Sentinel3 也报告 SDOWN
3. 3 个 Sentinel 投票确认 ODOWN（quorum=2，满足）
4. Sentinel2 被选为 Leader，执行故障转移
5. Slave1 被提升为新 Master
6. Slave2 改为复制 Slave1
7. 悦茶应用通过 Sentinel 客户端自动发现新 Master 地址

**🔍 源码解析：**

Sentinel 故障检测的核心逻辑在 `sentinel.c`：

```c
// sentinel.c - 故障检测
void sentinelCheckSubjectivelyDown(sentinelRedisInstance *ri) {
    // 检查 PING 响应超时
    mstime_t info_period = (mstime() - ri->last_pong_time);
    
    if (info_period > ri->down_after_period) {
        // 超过 down-after-milliseconds 未收到有效响应
        // 标记为 SDOWN
        ri->flags |= SRI_S_DOWN;
        
        // 如果是主节点，发起 ODOWN 投票
        if (ri->flags & SRI_MASTER) {
            // 向其他 Sentinel 询问
            sentinelAskMasterStateToOtherSentinels(ri, ...);
        }
    }
}

// sentinel.c - ODOWN 投票
void sentinelCheckObjectivelyDown(sentinelRedisInstance *master) {
    // 统计认为主节点 SDOWN 的 Sentinel 数量
    int voters = sentinelVotersCount(master);
    
    if (voters >= master->quorum) {
        // 达到 quorum → 标记 ODOWN
        master->flags |= SRI_O_DOWN;
        // 触发故障转移选举
        sentinelStartFailover(master);
    }
}

// 选择新主节点的算法
sentinelRedisInstance *sentinelSelectSlave(sentinelRedisInstance *master) {
    // 评分规则（按优先级）：
    // 1. 排除 S_DOWN / O_DOWN / Disconnected 的从节点
    // 2. 排除 master_link_down_time 过长的
    // 3. 优先选择 replica_priority 高的
    // 4. 优先选择 offset 最大的（数据最新）
    // 5. 优先选择 runid 最小的（确定性排序）
    
    // 排序后选择得分最高的从节点
    return best_slave;
}
```

选择从节点的优先级：

```
选择规则（优先级从高到低）：
1. 断开连接时间 < down-after * 10
2. replica-priority 值最小（0 表示不参与选举）
3. 复制偏移量最大（数据最新）
4. runid 字典序最小
```

**⚠️ 常见坑/加分回答：**

- 哨兵本身也需要部署至少 3 个，保证 quorum 选举的可靠性。如果只有 2 个哨兵，一个挂了就无法达成 quorum。
- 坑：`parallel-syncs` 设为 1 时，故障转移后只有一个从节点在做全量同步，其他从节点暂时不可用。如果从节点很多，可以考虑设大一些。
- 加分回答：Sentinel 模式下的数据丢失窗口 = `down-after-milliseconds` + 异步复制延迟。如果对数据丢失零容忍，需要配合 `min-replicas-to-write` 和 `min-replicas-max-lag` 参数。

### 第24集：Redis Cluster集群模式的原理？16384个hash slot的分片机制

**💡 核心回答：**

Redis Cluster 是 Redis 官方的分布式方案（Redis 3.0+），通过数据分片实现水平扩展。

核心设计：
- **16384 个哈希槽（Hash Slot）**：所有 key 通过 `CRC16(key) % 16384` 计算所属槽
- **每个节点负责一部分槽**：如 3 个节点，各负责约 5461 个槽
- **去中心化**：所有节点通过 gossip 协议通信，没有中心节点
- **客户端重定向**：请求发到错误节点时，返回 `MOVED` 或 `ASK` 指示正确节点

```bash
# 创建 3 主 3 从集群
redis-cli --cluster create \
  192.168.1.1:7000 192.168.1.2:7000 192.168.1.3:7000 \
  192.168.1.1:7001 192.168.1.2:7001 192.168.1.3:7001 \
  --cluster-replicas 1

# 查看集群状态
redis-cli -p 7000 cluster info
redis-cli -p 7000 cluster nodes
```

```java
// Java 客户端连接 Cluster
Set<HostAndPort> nodes = new HashSet<>();
nodes.add(new HostAndPort("192.168.1.1", 7000));
nodes.add(new HostAndPort("192.168.1.2", 7000));
nodes.add(new HostAndPort("192.168.1.3", 7000));

JedisCluster cluster = new JedisCluster(nodes);
cluster.set("order:10001", "data");  // 自动路由到正确节点
```

**📦 实际例子：**

悦茶平台从单实例 Redis 迁移到 6 节点 Cluster（3 主 3 从），支撑 3000+ 门店的数据存储：

```
节点A (7000): slot 0-5460     → 华南区门店数据
节点B (7001): slot 5461-10921 → 华东区门店数据  
节点C (7002): slot 10922-16383 → 华北区门店数据
```

由于 CRC16 哈希的随机性，不同区域的数据会分散在各节点上，而不是按区域集中。如果需要同一区域的数据在同一个节点上（减少跨节点访问），可以使用 Hash Tag：

```redis
# Hash Tag：用 {} 包裹的部分参与哈希计算
SET store:{guangdong}:info "..."     # CRC16("guangdong") % 16384 = 某个固定槽
SET store:{guangdong}:revenue "..."  # 同一个槽，在同一个节点
SET store:{beijing}:info "..."       # CRC16("beijing") % 16384 = 可能不同的槽
```

**🔍 源码解析：**

CRC16 哈希和槽分配的实现：

```c
// cluster.c
#define CLUSTER_SLOTS 16384

// key 到 slot 的映射
unsigned int keyHashSlot(char *key, int keylen) {
    // 处理 Hash Tag: {tag} 中的部分参与哈希
    int s = 0, e = keylen - 1;
    // 找到第一个 {
    for (int i = 0; i < keylen; i++) {
        if (key[i] == '{') { s = i; break; }
    }
    if (s == keylen) return crc16(key, keylen) % CLUSTER_SLOTS;
    
    // 找到匹配的 }
    for (int i = s + 1; i < keylen; i++) {
        if (key[i] == '}') { e = i - 1; break; }
    }
    if (e == keylen - 1 || e <= s) return crc16(key, keylen) % CLUSTER_SLOTS;
    
    // 只对 {tag} 中的部分做哈希
    return crc16(key + s + 1, e - s) % CLUSTER_SLOTS;
}

// 集群节点结构
typedef struct clusterNode {
    char name[CLUSTER_NAMELEN];     // 40 字符的节点 ID
    int flags;                       // MASTER/SLAVE/FAIL/PFAIL...
    uint64_t configEpoch;            // 配置纪元（用于冲突解决）
    unsigned char slots[CLUSTER_SLOTS/8];  // 位图：负责的槽
    int numslots;                    // 负责的槽数量
    clusterNode **replicas;          // 从节点列表
    clusterNode *slaveof;            // 主节点（如果是从节点）
} clusterNode;
```

MOVED 重定向：

```c
// cluster.c - 客户端请求路由
void clusterRedirectClient(client *c, clusterNode *n, int hashslot, int error_code) {
    if (error_code == CLUSTER_REDIR_MOVED) {
        // 槽已经永久迁移到其他节点
        // 返回 -MOVED slot ip:port
        addReplyErrorSds(c, sdscatprintf(sdsempty(),
            "-MOVED %d %s:%d", hashslot, n->ip, n->port));
    } else if (error_code == CLUSTER_REDIR_ASK) {
        // 槽正在迁移中（临时状态）
        // 返回 -ASK slot ip:port
        addReplyErrorSds(c, sdscatprintf(sdsempty(),
            "-ASK %d %s:%d", hashslot, n->ip, n->port));
        // 客户端需要先发 ASKING 命令，再发实际命令
    }
}
```

为什么是 16384 个槽？

```
Redis 作者 Antirez 的解释：
1. 节点间心跳包需要携带槽位信息（压缩后），16384 个 bit = 2KB
   65536 个 bit = 8KB，心跳包太大
2. Redis 压缩最多 9 层，CRC16 的输出范围足够大
3. 单个节点不太可能超过 1000 个（16384/1000 = 每个节点约 16 个槽）
```

**⚠️ 常见坑/加分回答：**

- Cluster 模式不支持多 key 操作（如 `MGET`、`MSET`），除非所有 key 在同一个槽（使用 Hash Tag）。
- 坑：Cluster 不支持 `SELECT` 切换数据库，只支持 db0。
- 加分回答：16384 个槽在节点间迁移时，使用两步迁移：先设置 `MIGRATING`/`IMPORTING` 状态，再逐槽传输 key。迁移过程中，已迁移的 key 返回 ASK，未迁移的 key 返回 MOVED。

### 第25集：Redis Cluster的gossip协议是什么？节点间怎么通信和检测故障

**💡 核心回答：**

Gossip（流言）协议是 Redis Cluster 节点间通信的基础，采用去中心化的方式传播集群状态。

**核心机制：**

1. **PING/PONG 消息**：节点间周期性互相发送 PING，对方回复 PONG（携带集群状态信息）
2. **MEET**：新节点加入集群时的握手协议
3. **FAIL/PFAIL**：故障检测与传播
   - PFAIL（Possible Fail）：单个节点认为对方可能宕机
   - FAIL：多数节点确认对方宕机（超过半数投票）
4. **配置传播**：槽位变更、节点增减等配置通过 gossip 传播

```bash
# 集群通信端口 = 数据端口 + 10000
# 数据端口 7000 → 通信端口 17000

# 查看集群总线消息
redis-cli -p 7000 cluster nodes
# <id> <ip:port@cport> <flags> <master> <ping-sent> <pong-recv> <config-epoch> <slots>
```

**📦 实际例子：**

悦茶平台的 6 节点 Redis Cluster 中，gossip 协议保证所有节点对集群拓扑有统一认知。当悦茶平台新增一个从节点时：

```bash
# 新节点通过 MEET 加入集群
redis-cli --cluster add-node 192.168.1.4:7000 192.168.1.1:7000

# 加入后，gossip 协议会自动将新节点信息传播给所有节点
# 每个节点在 1 秒内就能感知到新节点的存在
```

悦茶运维团队通过 `CLUSTER NODES` 命令监控各节点的 PING/PONG 时间差，及时发现网络异常节点。

**🔍 源码解析：**

Gossip 消息的发送频率和大小：

```c
// cluster.c - clusterCron 定时任务
void clusterCron(void) {
    // 每秒执行 10 次（每 100ms 一次）
    static int iteration = 0;
    iteration++;
    
    // 1. 向随机一个节点发送 PING
    // 2. 向 10% 的已知节点发送 PING
    // 3. 向长时间没收到 PONG 的节点发送 PING
    int max_to_send = max(1, cluster->numnodes / 10);
    
    // Gossip 消息格式
    typedef struct {
        char sig[4];              // "RCmb" (Redis Cluster message bus)
        uint32_t totlen;          // 消息总长度
        uint16_t version;         // 协议版本
        uint16_t port;            // 客户端端口
        uint16_t type;            // 消息类型：PING/PONG/MEET/FAIL...
        uint16_t count;           // 附带信息数量
        uint64_t currentEpoch;    // 当前配置纪元
        uint64_t configEpoch;     // 节点配置纪元
        unsigned char myslots[CLUSTER_SLOTS/8];  // 我的槽位图
        char slaveof[CLUSTER_NAMELEN];  // 我的主节点 ID
        char myip[NET_IP_STR_LEN];      // 我的 IP
        // ... 后面跟着 N 个 clusterMsgDataGossip 条目
    } clusterMsg;
    
    // 每条 PING/PONG 消息携带若干节点的 gossip 信息
    typedef struct {
        char name[CLUSTER_NAMELEN];    // 节点 ID
        uint32_t ping_sent;            // 最近发送 PING 的时间
        uint32_t pong_received;        // 最近收到 PONG 的时间
        char ip[NET_IP_STR_LEN];       // 节点 IP
        uint16_t port;                 // 节点端口
        uint16_t flags;                // 节点状态标志
    } clusterMsgDataGossip;
}
```

故障检测的传播机制：

```
节点 A 检测到节点 C 超时（连续不回复 PONG）：

T0: A 标记 C 为 PFAIL（仅 A 认为 C 可能故障）
T1: A 在 PING/PONG 消息中携带 "C 是 PFAIL" 的信息
T2: B 收到 A 的消息，也认为 C 可能故障，B 也标记 C 为 PFAIL
T3: B 在自己的 PING/PONG 消息中传播 "C 是 PFAIL"
T4: 当超过半数节点标记 C 为 PFAIL → 某个节点将 C 标记为 FAIL
T5: FAIL 标记以更高的优先级传播，所有节点很快接受

传播时间复杂度：O(log N) 轮 gossip 后所有节点都知道
```

**⚠️ 常见坑/加分回答：**

- 集群通信端口（数据端口 + 10000）必须开放，否则节点间无法通信。这是 Redis Cluster 部署中最常见的坑。
- 坑：gossip 消息有大小限制（`cluster-link-sendbuf-limit` 默认无限制），但如果集群节点很多（100+），gossip 消息会变大，可能影响节点间通信效率。
- 加分回答：Redis 7.0 引入了 Cluster bus port 配置（`cluster-port`），不再强制使用数据端口 + 10000，允许自定义通信端口。

### 第26集：秒杀系统的Redis设计：库存预热、令牌限流、异步扣减的完整链路

**💡 核心回答：**

秒杀系统的核心挑战：**高并发、低延迟、不超卖**。Redis 在其中承担三个关键角色：

1. **库存预热**：活动开始前将库存加载到 Redis
2. **令牌限流**：用 Redis 控制并发请求量，保护后端
3. **异步扣减**：Redis 原子扣减库存，成功后异步创建订单

完整链路：

```
用户请求 → Nginx限流 → Redis令牌桶 → Redis库存预扣 → MQ → 异步下单 → DB扣减库存
```

```java
// 1. 库存预热（活动开始前执行）
public void preheatStock(String activityId, int totalStock) {
    redis.set("seckill:stock:" + activityId, String.valueOf(totalStock));
    redis.set("seckill:sold:" + activityId, "0");
}

// 2. 令牌限流（控制并发）
public boolean acquireToken(String activityId, String userId) {
    // 每个用户只能获取一个令牌
    if (redis.sismember("seckill:tokens:" + activityId, userId)) {
        return false;  // 已有令牌
    }
    // 限制总令牌数
    Long tokenCount = redis.scard("seckill:tokens:" + activityId);
    if (tokenCount >= 5000) {  // 最多 5000 个令牌
        return false;
    }
    redis.sadd("seckill:tokens:" + activityId, userId);
    redis.expire("seckill:tokens:" + activityId, 300);  // 5分钟过期
    return true;
}

// 3. Redis 原子扣减库存（Lua 脚本保证原子性）
public Long deductStock(String activityId) {
    String luaScript = 
        "local stock = tonumber(redis.call('get', KEYS[1])) " +
        "if (stock <= 0) then return -1 end " +  // 库存不足
        "local sold = redis.call('incr', KEYS[2]) " +
        "if (sold > stock) then " +
        "  redis.call('decr', KEYS[2]) " +       // 回滚
        "  return -1 " +
        "end " +
        "return stock - sold";                     // 返回剩余库存
    
    return redis.eval(luaScript, 2,
        "seckill:stock:" + activityId,
        "seckill:sold:" + activityId);
}
```

**📦 实际例子：**

悦茶平台的"双11限量奶茶券"秒杀活动，限量 1000 张，预期 10 万人同时抢：

```
活动配置：
- 总库存：1000 张
- 令牌限流：5000 个令牌（允许 5000 人进入扣库存阶段）
- 预估 QPS：10 万+

链路设计：
1. 活动开始前 1 小时：库存预热到 Redis
2. 秒杀开始：
   a. 所有请求先到 Nginx 层限流（10万 QPS → 1万 QPS）
   b. Redis 令牌桶：1万 QPS → 5000 个令牌
   c. Redis Lua 脚本原子扣库存：5000 → 1000 张被抢到
   d. 成功的 1000 个请求发 MQ 消息
   e. 消费者异步创建订单、扣减数据库库存
```

**🔍 源码解析：**

Redis 单线程模型为什么能承受秒杀的并发压力：

```
Redis 事件循环（ae.c）：
┌──────────────────────────────────────────┐
│              Event Loop                   │
│  ┌─────────────────────────────────┐     │
│  │  File Event Handler              │     │
│  │  (epoll/kqueue 多路复用)         │     │
│  │  读取客户端请求 → 解析 RESP      │     │
│  │  → 执行命令 → 返回结果           │     │
│  └─────────────────────────────────┘     │
│  ┌─────────────────────────────────┐     │
│  │  Time Event Handler              │     │
│  │  serverCron（每秒执行 10 次）     │     │
│  │  过期 key 清理、内存管理等        │     │
│  └─────────────────────────────────┘     │
└──────────────────────────────────────────┘

单个 Redis 实例 QPS 约 8-10 万（简单命令如 GET/SET）
Lua 脚本的 QPS 约 5-8 万（因为脚本执行期间独占 CPU）
```

Lua 脚本在 Redis 中的原子性保证：

```c
// scripting.c
void evalCommand(client *c) {
    // Lua 脚本作为一个整体执行
    // 执行期间不会被其他客户端的命令打断
    // 这就是为什么库存扣减不会超卖
    
    lua_State *lua = server.lua;
    // 执行 Lua 脚本
    if (lua_pcall(lua, 0, 1, 0) != 0) {
        addReplyError(c, lua_tostring(lua, -1));
        return;
    }
    // Lua 脚本中调用的所有 Redis 命令在同一个"事务"中执行
}
```

**⚠️ 常见坑/加分回答：**

- 库存扣减的 Lua 脚本必须保证"检查 + 扣减"是一个原子操作。如果分成 GET + DECR 两步，并发下会超卖。
- 坑：Redis 扣减库存成功后，如果 MQ 发送失败或消费者异常，会导致"Redis 库存已扣但订单未创建"的不一致。需要定时任务补偿：对比 Redis 已售数量和 DB 订单数量，差异部分恢复库存或重新创建订单。
- 加分回答：超大规模秒杀（百万级 QPS）可以引入本地缓存 + Redis 两级限流，本地缓存拦截大部分请求，只有少量请求到达 Redis。

### 第27集：用户Session怎么存Redis？分布式Session的方案对比

**💡 核心回答：**

| Token 无状态 | JWT Token 自包含用户信息 | ✅ 无状态，但 Token 无法主动失效 |

```java
// Spring Session 源码简化
public class RedisOperationsSessionRepository implements SessionRepository<RedisSession> {
    
    private static final String SPRING_SESSION_CONTEXT_PREFIX = "spring:session:sessions:";
    
    @Override
    public RedisSession createSession() {
        RedisSession session = new RedisSession();
        session.setMaxInactiveInterval(Duration.ofSeconds(1800));  // 30分钟
        return session;
    }
    
    @Override
    public void save(RedisSession session) {
        String key = SPRING_SESSION_CONTEXT_PREFIX + session.getId();
        Map<String, Object> attrs = session.getAttributes();
        
        // 使用 Hash 存储所有属性
        Map<String, String> redisAttrs = new HashMap<>();
        for (Map.Entry<String, Object> entry : attrs.entrySet()) {
            redisAttrs.put("sessionAttr:" + entry.getKey(), serialize(entry.getValue()));
        }
        redisAttrs.put("lastAccessedTime", String.valueOf(session.getLastAccessedTime()));
        
        // Pipeline 批量写入
        redisTemplate.executePipelined((RedisCallback<Object>) connection -> {
            byte[] keyBytes = key.getBytes();
            connection.hMSet(keyBytes, redisAttrs);
            // 设置过期时间
            connection.expire(keyBytes, session.getMaxInactiveInterval().getSeconds());
            return null;
        });
    }
    
    @Override
    public RedisSession findById(String id) {
        String key = SPRING_SESSION_CONTEXT_PREFIX + id;
        Map<Object, Object> entries = redisTemplate.boundHashOps(key).entries();
        if (entries.isEmpty()) return null;
        
        // 反序列化为 RedisSession
        return deserialize(entries);
    }
}
```

- 加分回答：JWT 方案适合移动端和微服务间调用（无状态），但无法主动使 Token 失效（除非维护黑名单）。Session + Redis 方案适合 Web 应用，可以主动删除 Session 实现强制下线。悦茶平台同时使用两种：Web 端用 Session + Redis，App 端用 JWT + Redis 黑名单。

### 第28集：Redis怎么实现延迟队列？ZSet实现延迟任务的原理和坑

**💡 核心回答：**

延迟队列是指消息发出后不立即消费，而是等待指定时间后才被消费。

Redis 没有原生的延迟队列功能，但可以通过 ZSet 实现：
- **member**：任务消息（JSON 字符串或任务 ID）
- **score**：执行时间的时间戳

消费端用一个定时轮询线程，不断用 `ZRANGEBYSCORE` 取出到期任务：

```java
// 生产者：发送延迟消息
public void sendDelayTask(String taskId, long delaySeconds) {
    double executeTime = System.currentTimeMillis() / 1000.0 + delaySeconds;
    redis.zadd("delay:queue", executeTime, taskId);
}

// 消费者：轮询取出到期任务
@Scheduled(fixedDelay = 1000)  // 每秒轮询一次
public void pollTasks() {
    double now = System.currentTimeMillis() / 1000.0;
    // 取出 score <= now 的所有任务
    Set<String> readyTasks = redis.zrangeByScore("delay:queue", 0, now);
    
    for (String taskId : readyTasks) {
        // 使用 Lua 脚本原子性：取出 + 删除
        String luaScript = 
            "local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1]) " +
            "if #tasks > 0 then " +
            "  for i, task in ipairs(tasks) do " +
            "    redis.call('ZREM', KEYS[1], task) " +
            "  end " +
            "end " +
            "return tasks";
        
        List<String> tasks = redis.eval(luaScript, 1, "delay:queue", String.valueOf(now));
        for (String task : tasks) {
            processTask(task);  // 处理任务
        }
    }
}
```

**📦 实际例子：**

悦茶平台的订单超时自动取消功能：用户下单后 30 分钟内未支付，自动取消订单并释放库存。

**🔍 源码解析：**

ZSet 实现延迟队列的性能分析：

```
ZRANGEBYSCORE 的时间复杂度：O(log N + M)
- N = ZSet 中的总元素数
- M = 返回的元素数（到期任务数）

当 ZSet 元素较多时（如百万级），ZRANGEBYSCORE 的性能会下降：
- skiplist 查找起点：O(log N)
- 遍历到期元素：O(M)

悦茶平台的实际数据：
- 同时存在的延迟任务：约 5 万
- 每秒到期任务：约 30-50
- ZRANGEBYSCORE 单次耗时：< 1ms ✓
```

轮询方案的优化——`ZPOPMIN`（Redis 5.0+）：

```java

public void pollWithZPopMin() {
    double now = System.currentTimeMillis() / 1000.0;
    
    // 先检查是否有到期任务（非阻塞）
    Set<Tuple> tasks = redis.zrangeByScoreWithScores("delay:queue", 0, now, 0, 10);
    
    if (!tasks.isEmpty()) {
        // 使用 Lua 脚本保证原子性
        String luaScript = 
            "local result = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, 10) " +
            "if #result > 0 then " +
            "  for i, task in ipairs(result) do " +
            "    redis.call('ZREM', KEYS[1], task) " +
            "  end " +
            "end " +
            "return result";
        // ...
    }
}
```

ZSet 延迟队列的底层数据结构：

```
ZSet 底层：skiplist（按 score 排序）+ dict（按 member 查找）

skiplist 结构示意（按执行时间排序）：
    ┌──────┐     ┌──────┐     ┌──────┐     ┌──────┐
    │L0 10:00│────→│L0 10:05│────→│L0 10:10│────→│L0 10:15│→ ...
    └──────┘     └──────┘     └──────┘     └──────┘
    ↑ 已到期          ↑ 未到期

ZRANGEBYSCORE 0 10:05 → 返回 L0 10:00 和 L0 10:05 两个任务
```

**⚠️ 常见坑/加分回答：**

- 轮询间隔决定了延迟的精度。1 秒轮询意味着任务可能在到期后最多延迟 1 秒才执行。如果对延迟精度要求高，需要缩短轮询间隔，但会增加 Redis 的 QPS。
- 坑：多消费者场景下，ZRANGEBYSCORE + ZREM 不是原子的，可能导致多个消费者处理同一个任务。必须用 Lua 脚本保证"取出 + 删除"的原子性。
- 加分回答：对于更复杂的延迟队列需求（优先级、重试、死信队列），推荐使用 Redisson 的 `RDelayedQueue` 或直接使用 RocketMQ/RabbitMQ 的延迟消息功能。Redis 的 ZSet 延迟队列适合轻量级场景。

### 第29集：Redis事务（MULTI/EXEC）的坑：不支持回滚、WATCH乐观锁的实现

**💡 核心回答：**

Redis 事务与关系型数据库事务有本质区别：

| 特性 | 关系型数据库 | Redis 事务 |
|------|-----------|-----------|
| 原子性 | ✅ 全部成功或全部回滚 | ❌ 不支持回滚，错误命令继续执行 |
| 隔离性 | ✅ 有多种隔离级别 | ✅ 命令串行执行（单线程） |
| 持久性 | ✅ | ⚠️ 取决于持久化策略 |

Redis 事务的核心流程：

```redis
# 基本事务
MULTI                    # 开启事务
SET order:status 1       # 入队（不执行）
INCR order:count         # 入队（不执行）
EXEC                     # 一次性执行所有命令

# 带 WATCH 的事务（乐观锁）
WATCH stock:{skuId}      # 监视 key
SET currentStock [redis.get("stock:{skuId}")]
MULTI
DECR stock:{skuId}
INCR sold:{skuId}
EXEC                     # 如果 WATCH 的 key 被修改，EXEC 返回 nil（事务失败）
```

Redis 事务不支持回滚的表现：

```redis
127.0.0.1:6379> SET counter 10
OK
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> INCR counter      # 正确命令
QUEUED
127.0.0.1:6379> INVALID_COMMAND   # 语法错误（运行时错误）
(error) ERR unknown command
127.0.0.1:6379> INCR counter      # 正确命令
QUEUED
127.0.0.1:6379> EXEC
1) (integer) 11    # 第一个 INCR 执行成功
2) (integer) 12    # 第三个 INCR 也执行成功
# 中间的错误命令不会导致整个事务回滚！
# 注意：入队阶段发现的语法错误会拒绝整个事务
```

**📦 实际例子：**

悦茶平台的库存扣减原本使用 Redis 事务，但遇到了"部分成功"的问题：

```java
// 有坑的写法：Redis 事务
public boolean deductStock(String skuId) {
    Transaction tx = redis.multi();
    tx.get("stock:" + skuId);       // 读取库存
    tx.decr("stock:" + skuId);      // 扣减

    List<Object> result = tx.exec();
    
    // 问题：如果 decr 执行时 key 被其他客户端删除，decr 返回 -1
    // 但 incr 仍然会执行，导致数据不一致

    return result != null;

        "local stock = tonumber(redis.call('get', KEYS[1])) " +
        "if (stock == nil or stock <= 0) then return 0 end " +
        "redis.call('decr', KEYS[1]) " +
        "redis.call('incr', KEYS[2]) " +
        "return 1";
    
    Long result = redis.eval(luaScript, 2, "stock:" + skuId, "sold:" + skuId);
    return result == 1;

```

**🔍 源码解析：**

WATCH 乐观锁的实现原理：

```c
// multi.c - WATCH 实现
void watchCommand(client *c) {
    // 为客户端监视的 key 添加 watched 标记
    for (int j = 1; j < c->argc; j++) {
        robj *key = c->argv[j];
        
        // 在 key 的 dict 中标记"被客户端 c 监视"
        // 同时在客户端 c 的 watched_keys 列表中记录
        watchForKey(c, key);
    }
}

// 当被监视的 key 被修改时（通过任何写命令）
void touchWatchedKey(dict *db, robj *key) {
    // 查找监视该 key 的所有客户端
    list *clients = dictFetchValue(db->watched_keys, key);
    if (clients == NULL) return;
    
    // 将这些客户端标记为 CLIENT_DIRTY_CAS
    listIter li;
    listNode *ln;
    listRewind(clients, &li);
    while ((ln = listNext(&li)) != NULL) {
        client *c = listNodeValue(ln);
        c->flags |= CLIENT_DIRTY_CAS;  // 标记 CAS 已脏
    }
}

// EXEC 时检查是否被标记为 DIRTY_CAS
void execCommand(client *c) {
    if (c->flags & CLIENT_DIRTY_CAS) {
        // 被监视的 key 已被修改，事务失败
        addReply(c, shared.nullmultibulk);  // 返回 nil
        discardTransaction(c);  // 丢弃事务队列
        return;
    }
    
    // 未被修改，执行事务中的所有命令
    // 逐条执行，不做回滚
    execClientCommand(c);
}
```

WATCH 的乐观锁语义：

```
客户端A: WATCH stock:SKU001    → 监视 stock:SKU001
客户端A: GET stock:SKU001      → 当前值 = 5
客户端A: MULTI

                                    客户端B: DECR stock:SKU001  → 值变为 4
                                    ↑ touchWatchedKey 触发
                                    ↑ 客户端A 被标记 CLIENT_DIRTY_CAS

客户端A: DECR stock:SKU001     → 入队
客户端A: EXEC                  → 检查 CLIENT_DIRTY_CAS → 已脏！
                                → 返回 nil（事务失败）
                                → 客户端A 需要重试
```

**⚠️ 常见坑/加分回答：**

- Redis 事务的"不回滚"是设计决策而非 bug。Antirez 的解释：Redis 命令可能在执行过程中出错（如类型错误），但此时部分命令已经执行，回滚会导致更复杂的状态。设计哲学是"如果命令有错误，在入队阶段就应该被发现"。
- 坑：`WATCH` 的监视范围是 key 级别，不是 field 级别。如果 WATCH 一个 Hash 的 key，任何对该 Hash 的修改（即使是不同的 field）都会导致事务失败。
- 加分回答：在 Redis 6.0+ 中，由于 IO 多线程的引入，事务的原子性仍然有保证（命令执行阶段是单线程的），但需要注意 `CLIENT PAUSE` 命令在多线程模式下的行为变化。

### 第30集：Redis的发布订阅（Pub/Sub）和Stream对比：为什么Stream更适合消息队列场景

**💡 核心回答：**

Redis 提供两种消息机制：Pub/Sub（发布订阅）和 Stream（Redis 5.0+）。

**Pub/Sub 的局限：**
- **不持久化**：消息发出后如果没有订阅者就丢弃
- **不存储**：消息不存磁盘，Redis 重启后丢失
- **不确认**：消费者没有 ACK 机制，消息可能丢失
- **不回放**：无法从某个时间点重新消费

**Stream 的优势：**
- **持久化**：消息存储在 Redis 中（支持 AOF/RDB）
- **消费者组（Consumer Group）**：类似 Kafka 的消费组
- **消息确认（ACK）**：消费者处理后显式确认
- **消息回放**：可以从任意位置重新消费
- **阻塞等待**：`XREAD BLOCK` 类似 Kafka 的长轮询

```bash
# Pub/Sub
PUBLISH channel:order "new_order_10001"     # 发布
SUBSCRIBE channel:order                     # 订阅

# Stream
XADD stream:order * productId "SKU001" qty 3    # 发送消息
XREAD COUNT 10 STREAMS stream:order 0           # 读取消息
XGROUP CREATE stream:order group1 0             # 创建消费者组
XREADGROUP GROUP group1 consumer1 COUNT 10 BLOCK 5000 STREAMS stream:order >  # 消费
XACK stream:order group1 1704067200000-0        # 确认消息
```


**📦 实际例子：**

悦茶平台最初使用 Pub/Sub 做订单状态变更通知：

```redis
# Pub/Sub 方案（已弃用）
PUBLISH order:status:changed "orderId:10001,status:PAID"
# 问题：如果消息推送时通知服务重启，消息就丢了
# 而且无法回溯哪些订单已经处理过
```

后来迁移到 Stream：

```redis
# Stream 方案（当前使用）
# 订单状态变更写入 Stream
XADD stream:order:changed * orderId "10001" oldStatus "UNPAID" newStatus "PAID" timestamp "1704067200"

# 通知服务从 Stream 消费（消费者组）
XGROUP CREATE stream:order:changed notify-group $  # 只处理新消息

# 通知服务消费者1
XREADGROUP GROUP notify-group notify-consumer-1 COUNT 10 BLOCK 5000 STREAMS stream:order:changed >

# 通知服务消费者2（负载均衡）
XREADGROUP GROUP notify-group notify-consumer-2 COUNT 10 BLOCK 5000 STREAMS stream:order:changed >

# 处理完成后确认
XACK stream:order:changed notify-group 1704067200000-0
```

**🔍 源码解析：**

Stream 的底层数据结构：

```c
// stream 的底层实现：Radix Tree + Listpack
// t_stream.c

// Stream 结构
typedef struct stream {
    rax *rax;              // Radix Tree：key 是消息 ID，value 是 listpack
    int64_t length;        // 消息总数
    streamID last_id;      // 最后一条消息的 ID
    rax *cgroups;          // 消费者组信息
} stream;

// 消息 ID 格式：timestamp-sequence（毫秒时间戳-序列号）
// 如 1704067200000-0 表示时间戳 1704067200000 的第 0 条消息

// 消费者组结构
typedef struct streamCG {
    streamID last_id;          // 最后分配的消息 ID
    rax *pel;                  // Pending Entries List（未确认消息）
    rax *consumers;            // 消费者信息
} streamCG;

// 消费者结构
typedef struct streamConsumer {
    char *name;
    streamID seen_time;        // 最后活跃时间
    rax *pel;                  // 该消费者未确认的消息
} streamConsumer;
```

XADD 的内部实现：

```c
// t_stream.c
void xaddCommand(client *c) {
    // 1. 生成消息 ID（如果客户端未指定）
    streamID id;
    if (use_auto_id) {
        id.ms = mstime();  // 当前毫秒时间戳
        id.seq = 0;
        if (id.ms == last_id.ms) id.seq = last_id.seq + 1;
    }
    
    // 2. 将消息内容序列化为 listpack
    unsigned char *lp = lpNew(0);
    for (int i = 0; i < fields_count; i++) {
        lp = lpAppend(lp, field[i], field_len[i]);
        lp = lpAppend(lp, value[i], value_len[i]);
    }
    
    // 3. 插入 Radix Tree（key = 消息ID，value = listpack）
    raxInsert(s->rax, (unsigned char*)&id, sizeof(id), lp, NULL);
    
    // 4. 更新消费者组的 pending 列表
    if (cgroups) {
        streamPropagateToGroups(s, id, lp);
    }
}
```

Radix Tree 的优势：消息 ID 是前缀递增的（时间戳），Radix Tree 对这种前缀共享的 key 有极高的压缩率。

**⚠️ 常见坑/加分回答：**

- Pub/Sub 并非一无是处。在实时通知（如聊天室、弹幕）等不需要持久化的场景中，Pub/Sub 的性能更好（不需要存储消息的开销）。
- 坑：Stream 消息不会自动删除，需要手动用 `XTRIM` 限制长度，否则会无限增长：
```redis
XTRIM stream:order:changed MAXLEN ~ 100000  # 保留最近 10 万条
```
- 加分回答：Stream 的消费者组有 Pending Entries List（PEL），记录了已分配但未 ACK 的消息。可以通过 `XPENDING` 查看未确认消息，实现"消息重投"功能。超时未确认的消息可以由 `XCLAIM` 转给其他消费者处理。
