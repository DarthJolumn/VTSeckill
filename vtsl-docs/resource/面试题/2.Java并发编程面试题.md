### 第1集：Thread、Runnable、Callable三种实现方式的区别

**💡 核心回答：**
严格来说，创建线程只有一种方式——`new Thread()`。但**提交任务**有三种方式：`Runnable`、`Callable`、以及继承 `Thread` 类。它们的核心区别：

| | Runnable | Callable | Thread |
|---|---|---|---|
| 返回值 | 无 | 有（Future） | 无 |
| 异常 | 不能抛checked异常 | 可以抛异常 | 不能抛checked异常 |
| 配合线程池 | ✅ 最适合 | ✅ 最适合 | ❌ 不推荐 |

**📦 实际例子：**
电商系统的**订单超时自动取消**功能：

```java
// 用Callable + FutureTask，可以拿到取消结果
Callable<Boolean> cancelTask = () -> {
    Thread.sleep(30 * 60 * 1000); // 等30分钟
    Order order = orderService.getById(orderId);
    if (order.getStatus() == OrderStatus.UNPAID) {
        orderService.cancel(orderId);
        return true; // 取消成功
    }
    return false;
};

FutureTask<Boolean> futureTask = new FutureTask<>(cancelTask);
new Thread(futureTask).start();

// 主线程可以拿到结果
Boolean cancelled = futureTask.get();
```

**🔍 源码解析：**
看 `Thread` 的 `run()` 方法，Runnable 和 Callable 最终都走了 `run()`：

```java
// Thread.java - 当你传Runnable时
public void run() {
    if (target != null) {
        target.run(); // target就是你的Runnable
    }
}

// FutureTask.java - Callable的包装
public void run() {
    callable = c;  // 你传的Callable
    if (c != null) {
        try {
            result = c.call();  // 调用call()，能拿到返回值
            set(result);        // 把结果存到state里
        } catch (Throwable ex) {
            setException(ex);   // 异常也能捕获
        }
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：实际开发中几乎不会直接 `new Thread()`，都用线程池。线程池的 `execute()` 接受 `Runnable`，`submit()` 接受 `Runnable` 和 `Callable`
- **坑**：继承 `Thread` 类就不能再继承其他类了，Java单继承限制。所以推荐实现接口的方式

### 第2集：线程的6种状态及转换

**💡 核心回答：**
Java线程有 **6种状态**，定义在 `Thread.State` 枚举中：

```
NEW → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED
```

| 状态 | 含义 |
|---|---|
| NEW | 创建了但还没start() |
| RUNNABLE | 就绪+运行中（JVM层面不区分） |
| BLOCKED | 等synchronized锁 |
| WAITING | 无限等待（wait/join/park） |
| TIMED_WAITING | 超时等待（sleep/带超时的wait） |
| TERMINATED | 执行完毕 |

**📦 实际例子：**
用户登录场景，模拟一个需要等待获取分布式锁的请求：

```java
public class LoginService {
    private final Object lock = new Object();
    
    public void login(String username) {
        // NEW: 线程刚创建
        // RUNNABLE: start()后进入就绪/运行
        
        synchronized (lock) {  // 如果没拿到锁 → BLOCKED
            // 拿到锁了 → 继续执行
            
            try {
                lock.wait();  // → WAITING（等别人notify）
            } catch (InterruptedException e) { ... }
            
            try {
                Thread.sleep(1000);  // → TIMED_WAITING（1秒后自动醒）
            } catch (InterruptedException e) { ... }
        }
        // 方法结束 → TERMINATED
    }
}
```

**🔍 源码解析：**
```java
// Thread.java
public enum State {
    NEW,
    RUNNABLE,
    BLOCKED,
    WAITING,
    TIMED_WAITING,
    TERMINATED;
}

// 关键：BLOCKED vs WAITING 的区别
// BLOCKED：等synchronized监视器锁，被动等待
// WAITING：主动调用wait()/join()/LockSupport.park()
```

**⚠️ 常见坑/加分回答：**
- **加分**：`RUNNABLE` 在JVM层面包含了OS的就绪和运行两种状态，面试时说出来很加分
- **加分**：BLOCKED只发生在 `synchronized` 关键字上，用 `ReentrantLock` 的线程等待状态是 `WAITING`，不是 `BLOCKED`
- **坑**：很多人说5种状态，是把 `WAITING` 和 `TIMED_WAITING` 合并了

### 第3集：sleep和wait的区别？

**💡 核心回答：**
| | sleep() | wait() |
|---|---|---|
| 所属类 | Thread（静态方法） | Object（实例方法） |
| 释放锁 | **不释放锁** | **释放锁** |
| 唤醒方式 | 时间到了自动醒 | notify()/notifyAll() 或超时 |
| 使用位置 | 任意位置 | 必须在synchronized块内 |
| 线程状态 | TIMED_WAITING | WAITING（无超时）/ TIMED_WAITING（有超时） |

**📦 实际例子：**
```java
// sleep —— 模拟延迟，不释放锁
synchronized (lock) {
    Thread.sleep(1000);  // 暂停1秒，但仍然持有lock锁
    // 其他线程在这1秒内拿不到lock
}

// wait —— 线程协作，释放锁
synchronized (lock) {
    while (!condition) {
        lock.wait();  // 释放lock锁，进入等待
        // 其他线程可以获取lock锁了！
    }
    // 被notify唤醒后，重新获取lock锁，继续执行
}
```

**🔍 源码解析：**
```java
// Thread.sleep() - native方法
public static native void sleep(long millis) throws InterruptedException;
// 底层调用OS的sleep，不操作Monitor，不释放锁

// Object.wait() - native方法
public final native void wait(long timeout) throws InterruptedException;
// 底层调用ObjectMonitor::wait()
// 核心操作：
// 1. 把当前线程从OwnerList移到WaitSet
// 2. 释放Monitor锁（monitorexit）
// 3. 调用park()挂起线程

// Object.notify() - native方法  
public final native void notify();
// 底层：
// 1. 从WaitSet取一个线程
// 2. 调用unpark()唤醒
// 3. 线程醒来后重新竞争Monitor锁
```

**⚠️ 常见坑/加分回答：**
- **加分**：`wait()` 放在while循环里而不是if里——防止**虚假唤醒**（spurious wakeup），JVM可能在某些平台上不通过notify就唤醒wait的线程
- **加分**：`wait(0)` 和 `wait()` 等价——都是无限等待。但 `sleep(0)` 有特殊含义——告诉调度器"我可以让出CPU了"
- **坑**：`Thread.sleep(0)` 不会释放锁！很多面试题考这个

### 第1集：synchronized的基本用法和原理

**💡 核心回答：**
| 用法 | 锁对象 |
|---|---|
| `synchronized` 实例方法 | 当前实例对象 `this` |
| `synchronized` 静态方法 | 当前类的Class对象 |
| `synchronized(obj)` 代码块 | 括号里的obj对象 |

**核心原理**：
- **同步代码块**：通过 `monitorenter` / `monitorexit` 字节码指令实现
- **同步方法**：通过方法的 `ACC_SYNCHRONIZED` 标志位实现
- **本质**：都是操作对象头中的 **Mark Word**

**📦 实际例子：**
秒杀扣库存——错误示范 vs 正确示范：

```java
public class SeckillService {
    
    // ❌ 错误：每个请求new一个SeckillService，锁不同对象，根本锁不住
    public synchronized void deductStock() {
        if (stock > 0) {
            stock--;
        }
    }
    
    // ✅ 正确：用静态方法，所有请求锁同一个Class对象
    public static synchronized void deductStockStatic() {
        if (stock > 0) {
            stock--;
        }
    }
    
    // ✅ 更好：代码块精确控制锁范围
    private static final Object LOCK = new Object();
    
    public void deductStockBetter() {
        // 查库存等不需要同步的操作...
        
        synchronized (LOCK) {
            if (stock > 0) {
                stock--;
            }
        }
        
        // 发通知等不需要同步的操作...
    }
}
```

**🔍 源码解析：**
对象头中 Mark Word 的结构（64位JVM）：

```
// Mark Word 结构（64位）
// ┌──────────────────────────────────────────────────┐
// │  62 bits: 哈希码/GC分代年龄/锁信息               │
// │   1 bit : 偏向锁标识                              │
// │   1 bit : 锁标志位                                │
// └──────────────────────────────────────────────────┘
// 
// 无锁状态:  [hashcode(31) | age(4) | biasable(1) | 01(2)]
// 偏向锁:   [threadId(54) | epoch(2) | age(4) | 1 | 01]
// 轻量级锁: [ptr_to_lock_record(62) | 00]
// 重量级锁: [ptr_to_heavyweight_monitor(62) | 10]
```

**⚠️ 常见坑/加分回答：**
- **加分**：锁的本质是修改对象头的 Mark Word，不是锁代码、不是锁方法
- **坑**：`synchronized` 加在 `private` 方法上不会报错，但子类可以绕过锁直接调父类私有方法
- **坑**：String常量做锁对象是大坑！`"abc"` 在常量池中是共享的，别的类也可能锁同一个对象

### 第2集：synchronized锁升级：偏向锁→轻量级锁→重量级锁

**💡 核心回答：**
锁升级是JDK 6引入的优化策略，目的是**减少锁的重量级操作带来的性能损耗**：

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁
（只能升级，不能降级）
```

- **偏向锁**：只有一个线程访问，Mark Word记录线程ID，下次直接进来
- **轻量级锁**：有第二个线程竞争，撤销偏向，自旋等待
- **重量级锁**：自旋失败超过阈值，膨胀为重量级锁，线程挂起（涉及OS互斥量）

**注意**：JDK 15开始，偏向锁默认关闭（`-XX:-UseBiasedLocking`），因为偏向锁的撤销需要等到安全点，开销太大。

**📦 实际例子：**
商品详情页读缓存——典型的"一写多读"场景：

```java
public class ProductCache {
    private final Object lock = new Object();
    private Map<Long, Product> cache = new HashMap<>();
    
    public Product getProduct(long id) {
        synchronized (lock) {  // 大多数情况只有一个线程访问同一件商品
            // 偏向锁：命中率高，几乎零开销
            return cache.get(id);
        }
    }
    
    public void refreshProduct(long id, Product product) {
        synchronized (lock) {  // 刷新缓存时多线程竞争少
            cache.put(id, product);
        }
    }
}
```

这种场景大部分时间只有一个线程操作同一把锁，偏向锁命中率极高。

**🔍 源码解析：**
锁升级的核心在 `ObjectMonitor` 和 Mark Word 的操作：

```java
// JDK源码 - ObjectMonitor::enter()（简化）
void ObjectMonitor::enter(Thread* Self) {
    // 1. 先尝试CAS设置owner字段
    if (cas_owner(null, Self)) {
        return;  // 轻量级锁，CAS成功直接拿到锁
    }
    
    // 2. CAS失败，说明有竞争
    // 检查是不是自己重入
    if (owner == Self) {
        _recursions++;  // 重入次数+1
        return;
    }
    
    // 3. 自旋等待
    for (int spin = 0; spin < PRE_SPIN_LIMIT; spin++) {
        if (owner == null && cas_owner(null, Self)) {
            return;
        }
    }
    
    // 4. 自旋失败 → 膨胀为重量级锁
    // 把当前线程加入EntryList（等待队列）
    // 调用操作系统 pthread_mutex_lock 或 Windows CriticalSection
    // 线程被挂起，等待被唤醒
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：说清楚锁升级是单向的——只能升级不能降级
- **加分**：JDK 15已经默认禁用偏向锁，原因是撤销偏向需要等安全点（SafePoint），代价大
- **坑**：`hashCode()` 调用会导致偏向锁失效！因为偏向锁的Mark Word存储了线程ID，而`hashCode`也需要存在Mark Word里，两者冲突

### 第3集：synchronized和ReentrantLock的区别

**💡 核心回答：**
| 对比项 | synchronized | ReentrantLock |
|---|---|---|
| 实现层面 | JVM关键字，字节码层面 | Java API，java.util.concurrent.locks |
| 锁释放 | JVM自动释放 | 必须手动unlock() |
| 可中断 | JDK 1.6前不行 | lockInterruptibly()可响应中断 |
| 超时获取 | 不行 | tryLock(timeout) |
| 公平锁 | 非公平 | 可选公平/非公平 |
| 条件变量 | 只有一个（wait/notify） | 多个Condition |
| 性能 | 锁升级后差不多 | 差不多 |

**📦 实际例子：**
订单超时取消——需要超时获取锁的场景：

```java
public class OrderService {
    private final ReentrantLock lock = new ReentrantLock();
    
    public void cancelOrder(String orderId) {
        // synchronized做不到"等3秒拿不到就放弃"
        if (lock.tryLock(3, TimeUnit.SECONDS)) {
            try {
                // 拿到锁了，执行取消逻辑
                orderRepository.updateStatus(orderId, CANCELLED);
            } finally {
                lock.unlock();  // 必须finally里释放！
            }
        } else {
            // 3秒没拿到锁，说明其他线程在处理，直接放弃
            log.warn("订单{}正在处理中，跳过", orderId);
        }
    }
}
```

**🔍 源码解析：**
ReentrantLock 的核心就是 **AQS**：

```java
// ReentrantLock.java - lock()
public void lock() {
    sync.lock();  // 委托给Sync（AQS的子类）
}

// ReentrantLock.java - tryLock() 支持超时
public boolean tryLock(long timeout, TimeUnit unit) {
    return sync.tryAcquireNanos(1, unit.toNanos(timeout));
}

// ReentrantLock.java - unlock()
public void unlock() {
    sync.release(1);  // state减1，减到0才真正释放
}

// 对比synchronized的字节码
// monitorenter → 获取锁（只能阻塞等待）
// monitorexit → 释放锁
// 没有"超时"和"中断"的机制，全靠JVM
```

**⚠️ 常见坑/加分回答：**
- **加分**：ReentrantLock底层就是AQS，synchronized底层是Monitor，两者实现完全不同但殊途同归
- **坑**：ReentrantLock必须在finally中unlock！如果try里抛异常没释放，其他线程永远等不到锁
- **加分**：`lockInterruptibly()` 可以让等待锁的线程响应中断，synchronized做不到这一点

### 第4集：公平锁和非公平锁的区别

**💡 核心回答：**
- **非公平锁**：新来的线程直接CAS抢锁，抢不到再排队。可能有人"插队"
- **公平锁**：严格按FIFO顺序，新来的线程先看队列里有没有人，有人就乖乖排队

**为什么默认非公平？** 公平锁每次获取锁都要判断队列，多了一次线程上下文切换，吞吐量明显低于非公平锁。实际场景中，"公平"带来的性能损失远大于收益。

**📦 实际例子：**
```java
// 非公平锁（默认）—— 性能好
ReentrantLock unfairLock = new ReentrantLock();

// 公平锁 —— 按顺序来
ReentrantLock fairLock = new ReentrantLock(true);

// 业务场景：VIP客户优先
// 非公平锁天然支持"先到先得"，VIP线程可以直接CAS抢
// 公平锁则必须等前面所有线程都拿到锁，VIP也要排队
```

**🔍 源码解析：**
```java
// 非公平锁的tryAcquire
final boolean nonfairTryAcquire(int acquires) {
    int c = getState();
    if (c == 0) {
        if (compareAndSetState(0, acquires)) {  // 直接CAS抢，不管队列
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    // ...
}

// 公平锁的tryAcquire —— 多了hasQueuedPredecessors()判断
protected final boolean tryAcquire(int acquires) {
    int c = getState();
    if (c == 0) {
        if (!hasQueuedPredecessors()  // 关键！先看队列里有没有人排队
            && compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    // ...
}

// hasQueuedPredecessors()的实现
public final boolean hasQueuedPredecessors() {
    Node h = head;
    if (h == null) return false;
    Node t = tail;
    Node s = h.next;
    // head的next不是自己（队列里有其他线程在等）
    // 或者当前线程不是队列第一个
    return s != h && s.thread != Thread.currentThread();
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：非公平锁的"插队"行为只发生在**刚来抢锁的时候**，一旦进入CLH队列就必须按顺序
- **加分**：`synchronized` 只能是非公平的，没有公平锁选项。这是ReentrantLock的额外能力
- **坑**：公平锁不等于响应时间更短！由于频繁的线程切换，平均响应时间可能更长

## 第三系列：内存模型·volatile与CAS

---

### 第1集：volatile关键字的作用和原理

**💡 核心回答：**
volatile 有两个作用：
1. **保证可见性**：写的时候立即刷回主内存，读的时候从主内存读
2. **禁止指令重排序**：通过内存屏障（Memory Barrier）实现

**不能保证原子性**！`i++` 这种操作不是原子的。

**📦 实际例子：**
经典的双检查锁定单例（DCL）——没有volatile会出大问题：

```java
public class Singleton {
    // 必须加volatile！
    private static volatile Singleton INSTANCE;
    
    public static Singleton getInstance() {
        if (INSTANCE == null) {                // 第一次检查
            synchronized (Singleton.class) {
                if (INSTANCE == null) {        // 第二次检查
                    INSTANCE = new Singleton(); // 这一行不是原子的！
                }
            }
        }
        return INSTANCE;
    }
}
```

**为什么必须volatile？** `new Singleton()` 实际上是3步：
```
1. 分配内存空间
2. 初始化对象
3. 把引用指向内存地址
```

没有volatile的话，步骤2和3可能重排序变成1→3→2。此时另一个线程看到INSTANCE不为null（步骤3已完成），但对象还没初始化（步骤2没做），直接使用就会NPE！

**🔍 源码解析：**
volatile在字节码层面就是一个修饰符，关键在JVM的实现：

```java
// 编译后的字节码
// volatile写：
//   在写操作前插入 StoreStore 屏障
//   在写操作后插入 StoreLoad 屏障（最关键！）
//
// volatile读：
//   在读操作前插入 LoadLoad 屏障  
//   在读操作后插入 LoadStore 屏障

// 内存屏障的作用（简化）：
// StoreStore屏障：确保写操作对其他CPU可见
// StoreLoad屏障：防止volatile写和后面的读重排序
// 这是4种屏障中最重的一个，相当于一个fence

// 对应到CPU指令层面：
// x86: lock前缀指令（lock addl $0,0(%rsp)）
// 作用：锁定总线/缓存行，让其他CPU核心缓存失效
```

**⚠️ 常见坑/加分回答：**
- **加分**：volatile的StoreLoad屏障是最昂贵的，频繁volatile写会影响性能
- **坑**：`volatile boolean running = true;` 做开关没问题，但 `volatile int count++` 绝对不安全
- **加分**：JMM（Java内存模型）中，volatile写-读建立了happens-before关系

### 第2集：volatile能保证原子性吗？

**💡 核心回答：**
**不能！** volatile只保证可见性和有序性，不保证原子性。

`count++` 实际上是3步操作：读→加→写。即使加了volatile，两个线程可能同时读到同一个值，各自加1后写回，结果只加了1。

**📦 实际例子：**
秒杀库存扣减——volatile的灾难现场：

```java
public class SeckillWrong {
    private volatile int stock = 100;
    
    // ❌ 看起来有volatile保护，实际会超卖！
    public void seckill() {
        if (stock > 0) {
            stock--;  // 读→减→写，不是原子操作！
            // 100个线程同时读到stock=100，各自减1写回99
            // 结果：卖了100次但stock=99，库存对不上
        }
    }
}

// ✅ 正确方案：用AtomicInteger
public class SeckillRight {
    private AtomicInteger stock = new AtomicInteger(100);
    
    public boolean seckill() {
        while (true) {
            int current = stock.get();
            if (current <= 0) return false;
            if (stock.compareAndSet(current, current - 1)) {
                return true;  // CAS成功
            }
            // CAS失败，重试
        }
    }
}
```

**🔍 源码解析：**
看 `i++` 的字节码就明白了：

```java
// count++ 编译后的字节码（不是原子的！）
// aload_0        // 读count字段到操作数栈
// dup            // 复制一份
// iconst_1       // 推入常量1
// iadd           // 栈顶两个值相加
// putfield       // 写回count字段

// 3个步骤：getfield → iadd → putfield
// volatile只保证getfield和putfield的可见性
// 但中间的iadd和整体不是原子的！
```

**⚠️ 常见坑/加分回答：**
- **加分**：要实现原子性，要么用 `synchronized`，要么用 `AtomicInteger`（CAS实现）
- **加分**：`AtomicInteger.incrementAndGet()` 底层用 `Unsafe.getAndAddInt()`，是CAS操作，保证原子性
- **坑**：`stock = stock + 1` 和 `stock++` 一样，都不是原子的

### 第3集：CAS是什么？有什么问题？

**💡 核心回答：**
**CAS = Compare And Swap**（比较并交换），是一种无锁算法。

三个操作数：**内存值V、预期值A、新值B**。只有当 V == A 时，才把V更新为B，否则不操作。

**CAS的3个问题**：
1. **ABA问题**：值从A变成B又变回A，CAS以为没变
2. **自旋开销**：长时间CAS失败会空转CPU
3. **只能保证一个变量的原子性**

**📦 实际例子：**
乐观锁更新商品库存——ABA问题的经典场景：

```java
// ABA问题：
// 线程1读到库存=10（A）
// 线程2把库存改成5（B），然后另一个线程又改回10（A）
// 线程1 CAS(10, 8)，成功了！但中间已经被改过了

// ✅ 用AtomicStampedReference解决ABA
AtomicStampedReference<Integer> stock = 
    new AtomicStampedReference<>(10, 0);  // 值=10，版本号=0

// 更新时带版本号
int stamp = stock.getStamp();          // 拿版本号
Integer value = stock.getReference();   // 拿值
stock.compareAndSet(value, value - 2, 
    stamp, stamp + 1);  // CAS时同时检查版本号

// 如果中间版本号变了，CAS失败，不会误更新
```

**🔍 源码解析：**
```java
// AtomicInteger.java - 核心incrementAndGet()
public final int incrementAndGet() {
    return unsafe.getAndAddInt(this, valueOffset, 1) + 1;
}

// Unsafe.java - CAS的核心实现（native方法）
// 直接操作内存地址，是一条CPU指令级别的原子操作
public final int getAndAddInt(Object var1, long var2, int var4) {
    int var5;
    do {
        var5 = this.getIntVolatile(var1, var2);  // 读当前值
    } while (!this.compareAndSwapInt(var1, var2, var5, var5 + var4));
    // compareAndSwapInt：比较var5和内存值，相等则写var5+var4
    // 这是CPU指令 xchg / cmpxchg 级别的原子操作
    return var5;
}

// 对应x86汇编：
// lock cmpxchg [mem], newValue
// lock前缀保证多核情况下的缓存一致性
```

**⚠️ 常见坑/加分回答：**
- **加分**：CAS的底层是CPU指令 `cmpxchg`，加上 `lock` 前缀后在多核环境下也保证原子性
- **加分**：`lock` 前缀会锁缓存行（不是锁总线），通过MESI协议保证缓存一致性
- **坑**：`AtomicStampedReference` 性能比 `AtomicReference` 差，只在确实有ABA风险时使用

## 第四系列：AQS原理·核心与源码

### 第1集：AQS是什么？核心原理？

**💡 核心回答：**
**AQS = AbstractQueuedSynchronizer**（抽象队列同步器），是Java并发包的基石。

核心就3样东西：
1. **state**：`volatile int` 类型的同步状态（锁计数）
2. **CLH队列**：双向链表，存放等待线程的Node
3. **模板方法**：子类实现 `tryAcquire()` / `tryRelease()` 来定义获取/释放锁的逻辑

**设计思想**：AQS把"怎么排队、怎么唤醒"都做好了，子类只需要关心"锁的状态怎么变"。

**📦 实际例子：**
不同工具类对AQS的不同用法：

```java
// ReentrantLock：独占锁
// state = 0 表示无锁，state = 1 表示被锁，> 1 表示重入
// tryAcquire：state从0变成1 → 拿到锁
// tryRelease：state从1变成0 → 释放锁

// Semaphore：共享锁
// state = 许可数，每acquire一次state减1，每release加1
// tryAcquire：state > 0 → state减1，拿到许可
// tryRelease：state加1

// CountDownLatch：计数器
// state = 倒计数值
// countDown()：state减1
// await()：state != 0 时阻塞，state = 0 时唤醒所有等待线程
```

**🔍 源码解析：**
```java
// AQS.java - 核心字段
public abstract class AbstractQueuedSynchronizer {
    // 同步状态——这是AQS最核心的字段
    private volatile int state;
    
    // CLH队列的头节点
    private transient volatile Node head;
    // CLH队列的尾节点
    private transient volatile Node tail;
    
    // 内部Node类——双向链表节点
    static final class Node {
        static final Node SHARED = new Node();   // 共享模式标记
        static final Node EXCLUSIVE = null;      // 独占模式标记
        
        static final int CANCELLED = 1;   // 线程取消
        static final int SIGNAL = -1;     // 后继节点需要唤醒
        static final int CONDITION = -2;  // 在条件队列中
        static final int PROPAGATE = -3;  // 共享模式下传播
        
        volatile int waitStatus;    // 等待状态
        volatile Node prev;         // 前驱节点
        volatile Node next;         // 后继节点
        volatile Thread thread;     // 绑定的线程
        Node nextWaiter;            // 下一个等待节点（条件队列用）
    }
    
    // 子类必须实现的方法——这就是模板方法模式
    protected boolean tryAcquire(int arg) {
        throw new UnsupportedOperationException();
    }
    protected boolean tryRelease(int arg) {
        throw new UnsupportedOperationException();
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：AQS用的是**模板方法模式**，`acquire()` 是模板方法，定义了排队、唤醒等通用逻辑，`tryAcquire()` 是子类实现的具体逻辑
- **加分**：CLH队列是**虚拟双向队列**——head和tail只是哨兵节点，真正的线程节点在后面
- **坑**：AQS的state用volatile修饰，保证可见性。但修改state时用的是CAS，不是synchronized

### 第2集：AQS的state和CLH队列是怎么协作的？

**💡 核心回答：**
一句话总结：**先用CAS争抢state，抢到了直接用，抢不到就进CLH队列排队等唤醒。**

具体流程：
1. 线程调用 `acquire()` 尝试获取锁
2. 调用子类的 `tryAcquire()` 用CAS修改state
3. 成功 → 拿到锁，直接返回
4. 失败 → 创建Node节点，加入CLH队列尾部
5. 入队后，检查前驱是不是head，如果是再尝试一次
6. 还不是 → `LockSupport.park()` 挂起自己
7. 前驱释放锁时，`unparkSuccessor()` 唤醒后继节点

**📦 实际例子：**
模拟秒杀场景中多个线程抢锁的过程：

```java
// 100个线程同时抢库存，ReentrantLock保护临界区
ReentrantLock lock = new ReentrantLock();
int stock = 5;  // 只有5个库存

for (int i = 0; i < 100; i++) {
    new Thread(() -> {
        lock.lock();  // 1个线程拿到锁（改state=1）
        try {          // 其他99个线程排队进CLH队列
            if (stock > 0) {
                stock--;
                System.out.println(Thread.currentThread().getName() + " 抢到库存");
            }
        } finally {
            lock.unlock();  // 释放锁（state=0），唤醒队列里下一个线程
        }
    }).start();
}
```

**🔍 源码解析：**
```java
// AQS.acquire() —— 获取锁的入口方法（模板方法）
public final void acquire(int arg) {
    // 1. 先tryAcquire()，子类实现。成功了直接返回
    // 2. 失败了 → 进入队列排队
    if (!tryAcquire(arg) && acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) {
        selfInterrupt();
    }
}

// AQS.addWaiter() —— 把当前线程包装成Node加入队列尾部
private Node addWaiter(Node mode) {
    Node node = new Node(Thread.currentThread(), mode);
    Node pred = tail;
    if (pred != null) {
        node.prev = pred;          // 双向链表，设置前驱
        if (compareAndSetTail(pred, node)) {  // CAS设置尾节点
            pred.next = node;      // 前驱的后继指向自己
            return node;
        }
    }
    enq(node);  // CAS失败则自旋入队
    return node;
}

// AQS.acquireQueued() —— 入队后的逻辑
final boolean acquireQueued(Node node, int arg) {
    for (;;) {
        final Node p = node.predecessor();
        // 如果前驱是head，再尝试一次
        if (p == head && tryAcquire(arg)) {
            setHead(node);  // 自己变成head
            p.next = null;  // 帮助GC
            return false;
        }
        // 前驱不是head或tryAcquire失败 → 挂起自己
        if (shouldParkAfterFailedAcquire(p, node) && parkAndCheckInterrupt())
            return true;  // 被中断了
    }
}

// 释放锁时（简化）
public final boolean release(int arg) {
    if (tryRelease(arg)) {  // state减1，减到0才算真正释放
        Node h = head;
        if (h != null && h.waitStatus != 0) {
            unparkSuccessor(h);  // 唤醒head后面的那个节点！
        }
        return true;
    }
    return false;
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：CLH队列里是**唤醒head的后继节点**，不是唤醒所有节点。这就是为什么ReentrantLock是非公平的原因之一——新来的线程可以直接CAS尝试抢锁
- **加分**：`shouldParkAfterFailedAcquire()` 会把前驱节点的waitStatus设为SIGNAL，意思是"我释放锁的时候会唤醒你"
- **坑**：AQS的park/unpark底层是 `LockSupport.park()` / `LockSupport.unpark()`，本质是对 `Unsafe` 的native调用

### 第3集：ReentrantLock的lock/unlock源码流程

**💡 核心回答：**
**加锁流程（非公平锁）**：
1. 如果state=0，CAS把state改成1，设置独占线程为自己，拿到锁
2. 如果state>0且当前线程就是持有者，state+1（可重入）
3. 如果state>0且是别的线程持有 → 加入CLH队列等待

**解锁流程**：
1. state减1
2. state=0 → 真正释放锁，唤醒队列中下一个线程
3. state>0 → 只是减少重入次数，还没释放

**📦 实际例子：**
分布式锁的本地模拟——同一个线程可以多次加锁：

```java
ReentrantLock lock = new ReentrantLock();

public void outerMethod() {
    lock.lock();  // state: 0 → 1
    try {
        innerMethod();  // 同一个线程再次加锁
    } finally {
        lock.unlock();  // state: 2 → 1，还没释放
    }
}

public void innerMethod() {
    lock.lock();  // state: 1 → 2（可重入！不用排队）
    try {
        // 执行业务逻辑
    } finally {
        lock.unlock();  // state: 2 → 1
    }
}
// outerMethod的unlock → state: 1 → 0，真正释放
```

**🔍 源码解析：**
```java
// Sync.nonfairTryAcquire() —— 非公平锁的核心
final boolean nonfairTryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();  // 读state
    
    if (c == 0) {  // 没被任何线程持有
        if (compareAndSetState(0, acquires)) {  // CAS: 0 → 1
            setExclusiveOwnerThread(current);   // 记录持有者
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        // 重入！当前线程已经持有锁
        int nextc = c + 1;  // state + 1
        if (nextc < 0) throw new Error("Maximum lock count exceeded");
        setState(nextc);    // 设置新state（这里不用CAS，因为当前线程独占）
        return true;
    }
    return false;  // 被别的线程持有，失败
}

// Sync.tryRelease() —— 解锁
protected final boolean tryRelease(int releases) {
    int c = getState() - releases;  // state - 1
    if (Thread.currentThread() != getExclusiveOwnerThread())
        throw new IllegalMonitorStateException();  // 只能自己解锁自己
    
    boolean free = false;
    if (c == 0) {  // state减到0，真正释放
        free = true;
        setExclusiveOwnerThread(null);  // 清除持有者
    }
    setState(c);  // 设置新state
    return free;  // 返回true时AQS会唤醒队列里的线程
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：重入时 `setState()` 不用CAS，因为当前线程独占锁，没有竞争
- **加分**：`setExclusiveOwnerThread()` 不需要volatile，因为修改state时已经通过volatile保证了可见性
- **坑**：如果持有锁的线程没有unlock就异常退出了，锁永远不释放，其他线程永远等待。所以一定要用try-finally！

```java
public ThreadPoolExecutor(
```

```java
ThreadPoolExecutor orderPool = new ThreadPoolExecutor(

            t.setName("order-pool-" + count.incrementAndGet());
```

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(0, 0));
// ctl 是int类型的原子变量，高3位存线程池状态，低29位存线程数量
// 一个变量存两个信息！

// 线程池的5种状态
private static final int RUNNING    = -1 << COUNT_BITS;  // 接受新任务+处理队列
private static final int SHUTDOWN   =  0 << COUNT_BITS;  // 不接受新任务，但处理队列
private static final int STOP       =  1 << COUNT_BITS;  // 不接受新任务，不处理队列，中断正在执行的
private static final int TIDYING    =  2 << COUNT_BITS;  // 所有任务终止，workerCount=0
private static final int TERMINATED =  3 << COUNT_BITS;  // terminated()执行完毕

// 7个参数的存储
private volatile int corePoolSize;       // 核心线程数
private volatile int maximumPoolSize;    // 最大线程数
```

- **坑**：`corePoolSize` 的线程默认没有keepAliveTime，即使空闲也不会回收。调用 `allowCoreThreadTimeOut(true)` 才会回收
- **坑**：阿里规约要求：**禁止使用Executors创建线程池**，必须通过ThreadPoolExecutor构造器创建

### 第2集：ThreadPoolExecutor的execute执行流程

**💡 核心回答：**
4步走，画出来最清晰：

```
提交任务
  │
  ▼
当前线程数 < corePoolSize？
  ├─ 是 → 创建核心线程执行
  └─ 否 ↓
工作队列满了吗？
  ├─ 没满 → 任务放入队列
  └─ 满了 ↓
当前线程数 < maximumPoolSize？
  ├─ 是 → 创建非核心线程执行
  └─ 否 ↓
执行拒绝策略
```

**📦 实际例子：**
大促秒杀系统的线程池策略：

```java
// 配置：核心5，最大20，队列100
ThreadPoolExecutor pool = new ThreadPoolExecutor(5, 20, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new ThreadPoolExecutor.AbortPolicy());

// 场景1：来了3个任务 → 创建3个核心线程（< 5）
// 场景2：来了10个任务 → 5个核心线程 + 5个放进队列
// 场景3：队列满了（100个在排队），又来新的 → 创建第6~20个线程
// 场景4：20个线程+100队列都满了 → AbortPolicy抛异常

// 实际业务中，推荐自定义拒绝策略：
pool.setRejectedExecutionHandler((r, executor) -> {
    // 记录到MQ，稍后重试，而不是直接丢弃
    messageQueue.send("order_retry", r.toString());
    log.warn("线程池满了，任务已发送到重试队列");
});
```

**🔍 源码解析：**
```java
// ThreadPoolExecutor.execute() —— 核心流程
public void execute(Runnable command) {
    int c = ctl.get();  // 获取线程数和状态
    
    // 第一步：当前线程数 < corePoolSize → 创建核心线程
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))  // true表示用corePoolSize判断
            return;
        c = ctl.get();  // 重新获取，因为可能并发变化
    }
    
    // 第二步：线程池RUNNING + 入队成功
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // 二次检查：如果线程池不是RUNNING了，移除任务并拒绝
        if (!isRunning(recheck) && remove(command))
            reject(command);
        // 如果线程数为0（比如核心线程都被回收了），补偿创建一个线程
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);
    }
    // 第三步：队列满了，尝试创建非核心线程
    else if (!addWorker(command, false))  // false表示用maximumPoolSize判断
        // 第四步：创建失败（超过maximumPoolSize），执行拒绝策略
        reject(command);
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：源码中有个"二次检查"（double check），因为 `isRunning()` 和 `offer()` 之间可能有其他线程修改了线程池状态
- **加分**：`addWorker(command, false)` 传false表示用 `maximumPoolSize` 做上限检查
- **坑**：如果用的是无界队列（如LinkedBlockingQueue不设容量），第二步永远不会到第三步，maximumPoolSize参数等于废了！

### 第3集：线程池为什么不建议用Executors创建？

**💡 核心回答：**
Executors提供的4种快捷方法都有坑：

| 方法 | 坑 | 后果 |
|---|---|---|
| `newFixedThreadPool` | 无界队列 LinkedBlockingQueue | OOM |
| `newSingleThreadExecutor` | 无界队列 LinkedBlockingQueue | OOM |
| `newCachedThreadPool` | 最大线程数 Integer.MAX_VALUE | OOM |
| `newScheduledThreadPool` | 最大线程数 Integer.MAX_VALUE | OOM |

**核心原因**：无界队列或无界线程数 → 内存耗尽 → OOM。

**📦 实际例子：**
```java
// ❌ 线上灾难：newFixedThreadPool
ExecutorService pool = Executors.newFixedThreadPool(10);
// 底层：new ThreadPoolExecutor(10, 10, 0, MILLISECONDS,
//     new LinkedBlockingQueue<>())  ← 队列容量Integer.MAX_VALUE！

// 大促时10万个订单任务涌入
// 10个线程在干活，99990个任务堆在队列里
// 每个任务对象占内存，很快OOM！

// ✅ 正确做法：手动指定参数
ExecutorService pool2 = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(10000)  // 明确队列上限
);
```

**🔍 源码解析：**
```java
// Executors.java - 源码一目了然

public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(
        nThreads, nThreads,
        0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>()  // ← 坑在这里！
        // LinkedBlockingQueue() 默认容量 = Integer.MAX_VALUE
    );
}

public static ExecutorService newCachedThreadPool() {
    return new ThreadPoolExecutor(
        0, Integer.MAX_VALUE,  // ← 坑在这里！最大线程数无限
        60L, TimeUnit.SECONDS,
        new SynchronousQueue<Runnable>()
    );
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：生产环境推荐使用 `ThreadPoolExecutor` 构造器或 `ThreadPoolTaskExecutor`（Spring），可以明确设置拒绝策略
- **加分**：JDK 21引入了虚拟线程（`Executors.newVirtualThreadPerTaskExecutor()`），这个是推荐的，因为虚拟线程非常轻量
- **坑**：`newScheduledThreadPool` 的延迟队列是 `DelayedWorkQueue`，也是无界的

### 第4集：如何合理配置线程池大小？

**💡 核心回答：**
根据任务类型决定：

**CPU密集型**（计算、加密、排序）：
```
线程数 = CPU核心数 + 1
```
多一个线程防止某线程缺页中断导致CPU空闲。

**IO密集型**（数据库查询、HTTP调用、文件读写）：
```
线程数 = CPU核心数 × 2 × (1 + 等待时间/计算时间)
```
或者更简单的：**CPU核心数 × 2 到 × 4**

**📦 实际例子：**
电商系统三种不同任务的线程池配置：

```java
int cpuCores = Runtime.getRuntime().availableProcessors(); // 假设8核

// 1. CPU密集型：图片压缩/加密
ThreadPoolExecutor cpuPool = new ThreadPoolExecutor(
    cpuCores + 1, cpuCores + 1, ...
);  // 9个线程就够了

// 2. IO密集型：查数据库+调外部接口
ThreadPoolExecutor ioPool = new ThreadPoolExecutor(
    cpuCores * 4, cpuCores * 4, ...
);  // 32个线程，因为大量时间在等IO

// 3. 混合型：先算价格再查库存再发短信
// 拆成两个子任务分别提交到不同线程池！
```

**🔍 源码解析：**
```java
// 获取CPU核心数
int cpuCores = Runtime.getRuntime().availableProcessors();

// 底层实现
public native int availableProcessors();
// JNI调用OS获取，Linux: sysconf(_SC_NPROCESSORS_ONLN)

// 实际上更科学的方式：
// 通过压测确定最佳线程数
// 用压测工具模拟真实流量，观察：
// - CPU利用率（目标70-80%）
// - 响应时间P99
// - 吞吐量QPS
// 逐步增加线程数，找到吞吐量拐点
```

**⚠️ 常见坑/加分回答：**
- **加分**：不要硬编码线程数！用 `Runtime.getRuntime().availableProcessors()` 动态获取，或者做成配置项
- **加分**：现代服务器超线程（HT）导致逻辑核数≠物理核数，可以用 `lscpu` 看物理核数
- **坑**：多个线程池之间会互相影响CPU资源。如果一个线程池占满了CPU，其他线程池的线程拿不到CPU时间片

### 第1集：ConcurrentHashMap的实现原理？1.7和1.8的区别？

**💡 核心回答：**
| | JDK 1.7 | JDK 1.8 |
|---|---|---|
| 数据结构 | Segment数组 + 链表 | Node数组 + 链表/红黑树 |
| 并发控制 | 分段锁（ReentrantLock） | CAS + synchronized |
| 锁粒度 | Segment级别（默认16个段） | 单个Node（桶）级别 |
| 哈希冲突 | 链表 | 链表（>8）→ 红黑树 |
| size计算 | 两次不加锁+一次全锁 | baseCount + CounterCell数组 |

**📦 实际例子：**
用户信息缓存——高并发读写场景：

```java
ConcurrentHashMap<Long, UserInfo> userCache = new ConcurrentHashMap<>();

// 并发读：无锁，极快
UserInfo user = userCache.get(userId);

// 并发写：只锁当前桶
userCache.put(userId, newUserInfo);

// 1.8的put操作：
// 1. 计算hash，定位到哪个桶
// 2. 如果桶为空，CAS直接放入（无锁！）
// 3. 如果桶不为空，synchronized锁住桶的头节点，再放入
// 锁的粒度从1.7的16分之一变成了1/桶数量，并发度大幅提升
```

**🔍 源码解析：**
```java
// JDK 1.7 - Segment分段锁
// ConcurrentHashMap本质上是一个Segment数组
// 每个Segment继承ReentrantLock，各自维护一个HashEntry数组
static class Segment<K,V> extends ReentrantLock implements Serializable {
    transient volatile HashEntry<K,V>[] table;  // 每个段有自己的哈希表
    transient int count;
}
// 默认16个Segment，最多支持16个线程并发写

// JDK 1.8 - Node数组 + CAS + synchronized
transient volatile Node<K,V>[] table;  // 哈希表
transient volatile Node<K,V>[] nextTable;  // 扩容用

// 节点结构
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    volatile V val;          // val是volatile的！保证可见性
    volatile Node<K,V> next; // next也是volatile的
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：1.8为什么不用ReentrantLock而用synchronized？因为JDK 6之后synchronized有了锁升级优化，性能已经不输ReentrantLock，而且synchronized是JVM级别的，可以做更细粒度的优化
- **加分**：链表长度>8且数组长度>=64时，链表转红黑树，查询从O(n)降到O(log n)
- **坑**：`size()` 方法在高并发下是不精确的！如果需要精确计数，用 `mappingCount()`（返回long）或者自己维护一个AtomicLong

### 第2集：ConcurrentHashMap的put源码流程（1.8）

**💡 核心回答：**
1. 计算key的hash值（高16位异或低16位，减少碰撞）
2. 如果table为空，先初始化（CAS）
3. 定位到桶位置：
   - 桶为空 → CAS直接放入
   - 桶不为空 → synchronized锁住头节点，链表或红黑树方式插入
4. 插入后如果链表长度≥8，尝试树化
5. 插入后检查是否需要扩容

**📦 实际例子：**
```java
ConcurrentHashMap<String, Integer> counterMap = new ConcurrentHashMap<>();

// 并发统计接口调用次数
counterMap.merge("api_call", 1, Integer::sum);
// merge方法：如果key不存在，put(1)；如果存在，value = old + 1
// 比 get + put 更安全，因为merge是原子操作
```

**🔍 源码解析：**
```java
// ConcurrentHashMap.putVal()（简化核心流程）
final V putVal(K key, V value, boolean onlyIfAbsent) {
    int hash = spread(key.hashCode());  // 扰动函数：hash ^ (hash >>> 16)
    int binCount = 0;
    
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();  // 初始化表格（CAS，保证只有一个线程初始化）
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            // 桶为空 → CAS直接放入（无锁！性能最高）
            if (casTabAt(tab, i, new Node<K,V>(hash, key, value, null)))
                break;
        }
        else if (fh == MOVED)
            tab = helpTransfer(tab, f);  // 正在扩容，帮忙搬数据
        else {
            // 桶不为空 → 加锁
            synchronized (f) {  // 锁住头节点！
                if (tabAt(tab, i) == f) {  // 二次检查
                    if (f instanceof TreeBin)
                        // 红黑树插入...
                    else {
                        // 链表插入
                        for (binCount = 1; ; ++binCount) {
                            Node<K,V> e = f.next;
                            if (e == null) {
                                f.next = new Node<K,V>(hash, key, value, null);
                                break;
                            }
                            if (e.hash == hash && key.equals(e.key)) {
                                // 相同key，覆盖值
                                break;
                            }
                            f = e;
                        }
                    }
                }
            }
            if (binCount >= 8)
                treeifyBin(tab, i);  // 链表长度≥8，尝试树化
        }
    }
    addCount(1L, binCount);  // 计数+1，检查是否需要扩容
    return null;
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：`spread()` 扰动函数让高16位也参与hash计算，减少碰撞，和HashMap的设计一样
- **加分**：扩容时，多个线程可以同时帮忙搬数据（`helpTransfer`），这是1.8的重大优化
- **坑**：ConcurrentHashMap不允许key或value为null！这是设计决策——在并发环境下，null有歧义（是没这个key还是value是null？）

### 第3集：CopyOnWriteArrayList的原理和适用场景

**💡 核心回答：**
**核心思想**：读操作不加锁，写操作时**复制整个数组**，在副本上修改，修改完后替换原数组引用。

- **读**：直接读原数组，无任何锁（极快）
- **写**：加 `ReentrantLock` → 复制数组 → 修改副本 → 替换引用 → 释放锁

**适用场景**：读多写少。如配置列表、白名单、黑名单。

**📦 实际例子：**
系统配置管理——运营后台改配置，线上服务读配置：

```java
// 运营后台的IP白名单，频繁读取，偶尔更新
CopyOnWriteArrayList<String> whitelist = new CopyOnWriteArrayList<>();

// 线上服务：大量读取（无锁，极快）
public boolean isAllowed(String ip) {
    return whitelist.contains(ip);  // 直接遍历数组，无锁
}

// 运营后台：偶尔更新（会复制整个数组）
public void updateWhitelist(List<String> newWhitelist) {
    whitelist.clear();
    whitelist.addAll(newWhitelist);  // 底层：lock → 复制 → 修改 → 替换
}
```

**🔍 源码解析：**
```java
// CopyOnWriteArrayList.java - add()
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();  // 加锁！写操作是互斥的
    try {
        Object[] elements = getArray();  // 拿到当前数组
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);  // 复制！
        newElements[len] = e;  // 在副本上修改
        setArray(newElements);  // 替换引用
        return true;
    } finally {
        lock.unlock();
    }
}

// get() —— 无锁，直接读
public E get(int index) {
    return get(getArray(), index);  // 直接读数组，没有任何锁
}

// setArray()
private void setArray(Object[] a) {
    array = a;  // volatile写，保证其他线程立即可见
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：CopyOnWriteArrayList只保证**最终一致性**，不能保证读到最新写入的数据（写入是替换引用，读的可能还是旧数组）
- **加分**：迭代器是"弱一致性"的——不会抛ConcurrentModificationException，但可能读到旧数据
- **坑**：写操作会复制整个数组，数据量大时内存占用翻倍，GC压力大。不适合大数据量或写频繁的场景

### 第4集：BlockingQueue的实现原理和使用场景

**💡 核心回答：**
BlockingQueue是**线程安全的队列**，核心特性：队列满时生产者阻塞，队列空时消费者阻塞。

| 实现类 | 结构 | 特点 |
|---|---|---|
| ArrayBlockingQueue | 数组 | 有界，公平/非公平锁 |
| LinkedBlockingQueue | 链表 | 可无界，读写分离锁 |
| PriorityBlockingQueue | 堆 | 优先级排序 |
| SynchronousQueue | 无缓冲 | 不存储，直接交付 |
| DelayQueue | 延时 | 到时间才能取出 |

**📦 实际例子：**
消息通知系统——生产者消费者模式：

```java
// 阻塞队列容量1000
BlockingQueue<Notification> queue = new LinkedBlockingQueue<>(1000);

// 生产者：订单服务产生通知
public void afterOrderCreated(Order order) {
    Notification notification = new Notification(order.getUserId(), 
        "订单创建成功");
    try {
        queue.put(notification);  // 队列满时阻塞等待
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}

// 消费者：通知发送线程
public void notificationWorker() {
    while (true) {
        try {
            Notification n = queue.take();  // 队列空时阻塞等待
            smsService.send(n.getUserId(), n.getMessage());
        } catch (InterruptedException e) {
            break;
        }
    }
}

// 用SynchronousQueue实现直接交付（不缓冲）
// 场景：任务必须被立即处理，不能排队
BlockingQueue<Task> directHandoff = new SynchronousQueue<>();
```

**🔍 源码解析：**
```java
// ArrayBlockingQueue - 核心字段
public class ArrayBlockingQueue<E> {
    final Object[] items;    // 数组存储
    int takeIndex;           // 消费位置
    int putIndex;            // 生产位置
    int count;               // 元素个数
    
    final ReentrantLock lock;
    private final Condition notEmpty;  // 消费条件：队列不为空
    private final Condition notFull;   // 生产条件：队列不满
}

// put() - 生产者
public void put(E e) throws InterruptedException {
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        while (count == items.length)  // 队列满了
            notFull.await();           // 生产者等待
        
        enqueue(e);                    // 放入数组
        if (++count == items.length)
            notFull.signal();          // 队列满了，不再唤醒生产者
        notEmpty.signal();             // 唤醒消费者
    } finally {
        lock.unlock();
    }
}

// take() - 消费者
public E take() throws InterruptedException {
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        while (count == 0)        // 队列空了
            notEmpty.await();     // 消费者等待
        
        E x = dequeue();          // 从数组取出
        if (count == 0)
            notEmpty.signal();    // 队列空了，不再唤醒消费者
        notFull.signal();         // 唤醒生产者
        return x;
    } finally {
        lock.unlock();
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：`LinkedBlockingQueue` 用了两把锁（`putLock` 和 `takeLock`），读写可以并发，性能比 `ArrayBlockingQueue` 高
- **加分**：`SynchronousQueue` 不存储任何元素，生产者put必须等到消费者take，适合做线程间直接交付
- **坑**：`LinkedBlockingQueue()` 默认容量是 `Integer.MAX_VALUE`，生产环境一定要设上限，否则可能OOM

## 第七系列：并发工具·CountDownLatch与Semaphore

### 第1集：CountDownLatch的使用场景和原理

**💡 核心回答：**
**CountDownLatch = 倒计数器**：初始化一个计数值，每次 `countDown()` 减1，`await()` 等到计数为0才放行。

**一次性工具**：计数到0后不能重置。需要重复使用用 `CyclicBarrier`。

**📦 实际例子：**
电商首页——需要同时拉取商品信息、用户信息、推荐信息：

```java
public HomePageVO getHomePage(Long userId) {
    CountDownLatch latch = new CountDownLatch(3);
    
    // 并行请求3个服务
    CompletableFuture.supplyAsync(() -> {
        try {
            return productService.getHotProducts();
        } finally {
            latch.countDown();  // 完成一个，计数-1
        }
    });
    
    CompletableFuture.supplyAsync(() -> {
        try {
            return userService.getUserInfo(userId);
        } finally {
            latch.countDown();
        }
    });
    
    CompletableFuture.supplyAsync(() -> {
        try {
            return recommendService.getRecommendations(userId);
        } finally {
            latch.countDown();
        }
    });
    
    try {
        latch.await(5, TimeUnit.SECONDS);  // 最多等5秒
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    
    // 3个服务都返回后，组装数据
    return assembleHomePage(productResult, userResult, recommendResult);
}
```

**🔍 源码解析：**
```java
// CountDownLatch内部就是AQS的一个共享锁实现
private static class Sync extends AbstractQueuedSynchronizer {
    Sync(int count) {
        setState(count);  // state就是计数值！
    }
    
    int getCount() { return getState(); }
    
    // 共享模式下获取锁——state不为0时阻塞
    protected int tryAcquireShared(int acquires) {
        return (getState() == 0) ? 1 : -1;  // state=0才成功
    }
    
    // 共享模式下释放锁——state减1
    protected boolean tryReleaseShared(int releases) {
        for (;;) {
            int c = getState();
            if (c == 0) return false;  // 已经是0了
            int nextc = c - 1;
            if (compareAndSetState(c, nextc))  // CAS减1
                return nextc == 0;  // 减到0时返回true，AQS会唤醒所有等待线程
        }
    }
}

// countDown()
public void countDown() {
    sync.releaseShared(1);  // state - 1
}

// await()
public void await() throws InterruptedException {
    sync.acquireSharedInterruptibly(1);  // state != 0 时阻塞
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：CountDownLatch底层就是AQS的**共享锁**模式——state到0时所有等待线程一起醒来
- **加分**：现代Java开发中，很多场景可以用 `CompletableFuture.allOf()` 替代，代码更优雅
- **坑**：一定要确保 `countDown()` 被执行到！放在finally块里，否则await可能永远等不到

### 第2集：CyclicBarrier和CountDownLatch的区别

**💡 核心回答：**
| | CountDownLatch | CyclicBarrier |
|---|---|---|
| 计数器 | 递减，不可重置 | 递减，可重置（Cyclic） |
| 等待方 | 一个或多个线程await | 所有参与方互相等待 |
| 回调 | 无 | 有barrierAction |
| 底层 | AQS共享锁 | ReentrantLock + Condition |
| 场景 | 主线程等子线程 | 多线程互相等到齐了一起干活 |

**📦 实际例子：**
游戏开发——等待所有玩家加载完毕后开始游戏：

```java
// 5个玩家必须全部加载完才开始游戏
CyclicBarrier barrier = new CyclicBarrier(5, () -> {
    System.out.println("所有玩家加载完毕，游戏开始！");
    gameService.startGame();
});

// 每个玩家客户端
public void playerJoin(String playerName) {
    try {
        // 加载资源...
        loadResources(playerName);
        
        System.out.println(playerName + " 加载完毕，等待其他玩家");
        barrier.await();  // 等所有玩家都到这里
        
        // 5个人同时从这里开始
        startPlaying(playerName);
    } catch (Exception e) {
        barrier.reset();  // 有人异常，重置屏障
    }
}
```

**🔍 源码解析：**
```java
// CyclicBarrier - 核心结构
public class CyclicBarrier {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition trip = lock.newCondition();  // 条件变量
    private final int parties;    // 参与方数量
    private int count;            // 当前剩余等待数
    private final Runnable barrierCommand;  // 到达屏障后的回调
    
    // 代（generation）——用于判断barrier是否被重置
    private Generation generation = new Generation();
    
    public int await() throws InterruptedException {
        final ReentrantLock lock = this.lock;
        lock.lock();
        try {
            int index = --count;  // 计数器减1
            if (index == 0) {     // 最后一个到达的线程
                boolean broken = false;
                try {
                    Runnable command = this.barrierCommand;
                    if (command != null)
                        command.run();    // 执行回调
                    tripped = true;
                    lock.unlock();
                    trip.signalAll();     // 唤醒所有等待线程
                    lock.lock();
                } finally { ... }
            } else {
                // 还没到齐，当前线程等待
                while (!tripped) {
                    trip.await();  // 等！
                }
            }
            return index;
        } finally {
            lock.unlock();
        }
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：CyclicBarrier底层用的不是AQS，而是 `ReentrantLock + Condition`。Condition的 `await/signalAll` 和 `wait/notifyAll` 类似但更灵活
- **加分**：`reset()` 方法可以重置barrier，但会抛 `BrokenBarrierException` 给正在等待的线程
- **坑**：如果parties设为5，但只有4个线程调用await，会永远死锁。生产环境建议设置超时：`barrier.await(10, TimeUnit.SECONDS)`

### 第3集：Semaphore的使用场景和原理

**💡 核心回答：**
**Semaphore = 信号量**，控制同时访问某个资源的线程数量。

- `acquire()` → 获取一个许可（state-1），没有许可就阻塞
- `release()` → 释放一个许可（state+1）
- 可以初始化多个许可 → 允许多个线程同时访问

**和ReentrantLock的区别**：ReentrantLock只允许1个线程（state只有0和1），Semaphore允许N个线程。

**📦 实际例子：**
限制数据库并发连接数：

```java
// 最多允许10个线程同时访问数据库
Semaphore dbSemaphore = new Semaphore(10);

public <T> T queryDatabase(String sql, Class<T> resultType) {
    try {
        dbSemaphore.acquire();  // 获取许可，没有就等
        try {
            Connection conn = dataSource.getConnection();
            // 执行查询...
            return executeQuery(conn, sql, resultType);
        } finally {
            dbSemaphore.release();  // 必须释放！
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RuntimeException("查询被中断");
    }
}

// 公平模式：按FIFO获取许可
Semaphore fairSemaphore = new Semaphore(10, true);

// 限流场景：限制API调用并发数
Semaphore apiSemaphore = new Semaphore(100);
```

**🔍 源码解析：**
```java
// Semaphore内部也是AQS！这次是共享模式

// 非公平模式
static final class NonfairSync extends Sync {
    protected int tryAcquireShared(int permits) {
        return nonfairTryAcquireShared(permits);
    }
}

// Sync基类
abstract static class Sync extends AbstractQueuedSynchronizer {
    Sync(int permits) {
        setState(permits);  // state = 许可数
    }
    
    final int nonfairTryAcquireShared(int acquires) {
        for (;;) {
            int available = getState();          // 当前许可数
            int remaining = available - acquires; // 剩余许可
            if (remaining < 0 ||                  // 不够了
                compareAndSetState(available, remaining))  // CAS扣减
                return remaining;
        }
    }
    
    protected final boolean tryReleaseShared(int releases) {
        for (;;) {
            int current = getState();
            int next = current + releases;  // 归还许可
            if (compareAndSetState(current, next))  // CAS归还
                return true;
        }
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：Semaphore底层也是AQS，state的含义从"锁计数"变成了"可用许可数"
- **加分**：`release()` 可以在没有 `acquire()` 的情况下调用——相当于增加了许可数
- **坑**：`acquire()` 和 `release()` 必须成对出现！和锁一样，要在finally中release

### 第1集：CompletableFuture异步编程怎么用？

**💡 核心回答：**
**Future的问题**：`get()` 会阻塞，想拿结果只能干等。

**CompletableFuture解决了**：
1. 链式调用（thenApply/thenAccept）
2. 组合多个异步任务（allOf/anyOf）
3. 异常处理（exceptionally/handle）
4. 不阻塞的回调

**📦 实际例子：**
电商商品详情页——并行查数据再组合：

```java
// 并行查询：商品详情、库存、评价
CompletableFuture<ProductDetail> productFuture = 
    CompletableFuture.supplyAsync(() -> productService.getDetail(id));

CompletableFuture<Integer> stockFuture = 
    CompletableFuture.supplyAsync(() -> stockService.getStock(id));

CompletableFuture<List<Review>> reviewFuture = 
    CompletableFuture.supplyAsync(() -> reviewService.getReviews(id));

// 三个都完成后组合结果
CompletableFuture<PageVO> pageFuture = 
    CompletableFuture.allOf(productFuture, stockFuture, reviewFuture)
        .thenApply(v -> {
            ProductDetail product = productFuture.join();
            Integer stock = stockFuture.join();
            List<Review> reviews = reviewFuture.join();
            return assemblePage(product, stock, reviews);
        });

// 非阻塞获取结果
pageFuture.thenAccept(page -> {
    // 数据准备好了，渲染页面
    render(page);
}).exceptionally(e -> {
    // 任何一步出错都会走这里
    log.error("加载详情页失败", e);
    return null;
});
```

**🔍 源码解析：**
```java
// CompletableFuture的核心——Completion链

    // 结果（volatile保证可见性）
    volatile Object result;  // 要么是结果值，要么是AltResult包装的异常

        return uniApplyStage(null, fn);
    }
    
    // allOf —— 等所有future完成
    public static CompletableFuture<Void> allOf(CompletableFuture<?>... cfs) {
        // 底层：每个cf都thenRun一个计数逻辑
        // 计数到0时，返回的future complete
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：`supplyAsync` 默认用 `ForkJoinPool.commonPool()`，生产环境建议传入自定义线程池，避免和其他异步任务抢线程
- **加分**：`join()` 会阻塞但不会抛checked异常，`get()` 会阻塞且抛 `InterruptedException`
- **坑**：`allOf` 中任何一个future异常，`allOf` 返回的future也会异常。每个future最好单独处理异常

### 第2集：ThreadLocal的原理是什么？为什么会内存泄漏？

**💡 核心回答：**
**原理**：每个Thread对象内部有一个 `ThreadLocalMap`，key是ThreadLocal对象本身（弱引用），value是存储的值。

**内存泄漏原因**：
1. `ThreadLocalMap` 的key是弱引用，key可以被GC回收
2. 但value是强引用，key被回收后value还在map里
3. 线程池场景下线程不销毁 → ThreadLocalMap一直存在 → value永远无法回收

**📦 实际例子：**
用户登录上下文传递：

```java
public class UserContext {
    private static final ThreadLocal<UserInfo> currentUser = new ThreadLocal<>();
    
    // 登录拦截器设置用户信息
    public static void setCurrentUser(UserInfo user) {
        currentUser.set(user);
    }
    
    // 业务代码随时获取
    public static UserInfo getCurrentUser() {
        return currentUser.get();
    }
    
    // ⚠️ 请求结束后必须清理！
    public static void clear() {
        currentUser.remove();
    }
}

// 拦截器
public class AuthInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest request, ...) {
        UserInfo user = parseToken(request);
        UserContext.setCurrentUser(user);  // 设置当前用户
        return true;
    }
    
    // 请求完成后必须清理
    public void afterCompletion(...) {
        UserContext.clear();  // ⚠️ 这行不写就会内存泄漏！
    }
}
```

**🔍 源码解析：**

**⚠️ 常见坑/加分回答：**
- **加分**：ThreadLocal的key用弱引用只是减少了key泄漏的可能，value泄漏的根源在于线程不销毁（线程池）+ 不调用remove()
- **加分**：解决内存泄漏的最佳实践：**永远在finally块中调用 `remove()`**
- **坑**：`InheritableThreadLocal` 可以让子线程继承父线程的值，但在**线程池**场景下会出问题——线程被复用，上一个任务设置的值会污染下一个任务

### 第3集：死锁是怎么产生的？怎么排查？

**💡 核心回答：**
**死锁4个必要条件**（缺一不可）：
1. **互斥**：资源同一时刻只能被一个线程持有
2. **持有并等待**：持有至少一个资源，同时等待获取其他资源
3. **不可抢占**：资源只能由持有者释放
4. **循环等待**：A等B，B等A（或者A→B→C→A）

**📦 实际例子：**
转账死锁——经典场景：

```java
public void transfer(Account from, Account to, BigDecimal amount) {
    synchronized (from) {          // 锁from账户
        synchronized (to) {        // 锁to账户
            from.debit(amount);
            to.credit(amount);
        }
    }
}

// 线程1: transfer(A, B, 100) → 锁A，等B
// 线程2: transfer(B, A, 200) → 锁B，等A
// 死锁！两个线程永远等下去

// ✅ 解决方案1：固定加锁顺序
public void transferSafe(Account from, Account to, BigDecimal amount) {
    Account first = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;
    
    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
// 两个线程都会先锁id小的账户，不会产生循环等待

// ✅ 解决方案2：tryLock超时
public void transferWithTimeout(Account from, Account to, BigDecimal amount) {
    if (fromLock.tryLock(5, TimeUnit.SECONDS)) {
        try {
            if (toLock.tryLock(5, TimeUnit.SECONDS)) {
                try {
                    // 转账
                } finally {
                    toLock.unlock();
                }
            }
        } finally {
            fromLock.unlock();
        }
    }
}
```

**🔍 源码解析：**
```bash
# 排查死锁的工具

# 方法1：jstack（最常用）
jstack <pid> > thread_dump.txt
# 输出中会直接提示：
# "Found one Java-level deadlock:"
# "Found 1 deadlock."

# 方法2：jconsole（可视化）
jconsole <pid>
# 检测→死锁 标签页会直接显示

    ThreadInfo[] infos = tmx.getThreadInfo(deadlockedIds, true, true);
    for (ThreadInfo info : infos) {
        System.out.println(info);  // 打印死锁线程信息
    }
}
```

**⚠️ 常见坑/加分回答：**
- **加分**：打破死锁只需要打破4个条件中的任意一个。最常用的是**打破循环等待**（固定加锁顺序）
- **加分**：`synchronized` 的锁不可中断，所以死锁后线程永远等待。用 `ReentrantLock.lockInterruptibly()` 至少可以响应中断
- **坑**：死锁不一定只发生在两个线程之间！A→B→C→A 三个线程也能死锁

### 第4集：什么是伪共享？怎么避免？

**💡 核心回答：**
**伪共享（False Sharing）**：两个线程修改不同变量，但因为这两个变量在同一个CPU缓存行（Cache Line，64字节）中，导致缓存频繁失效。

**原理**：CPU缓存以缓存行（64字节）为单位加载数据。线程A修改了变量x，线程B的缓存行也包含x（虽然B只修改y），B的缓存行也会失效。

**📦 实际例子：**
```java
// ❌ 伪共享示例
public class FalseSharing {
    public long a;  // 这两个变量很可能在同一个缓存行
    public long b;  // 因为long=8字节，64字节能放8个long
}

// 线程1改a，线程2改b
// 虽然改的是不同变量，但缓存行不断失效
// 性能比单线程还差！

// ✅ 解决方案1：填充（Padding）
public class TrueSharing {
    public long a;
    public long p1, p2, p3, p4, p5, p6, p7;  // 填充7个long（56字节）
    public long b;  // b和a不在同一个缓存行了！
}

// ✅ 解决方案2：JDK 8 @Contended注解
@sun.misc.Contended  // 告诉JVM自动填充
public volatile long a;

@sun.misc.Contended
public volatile long b;
// 注意：需要JVM参数 -XX:-RestrictContended
```

**🔍 源码解析：**
```java
// AQS中的CounterCell就避免了伪共享！
// jdk.internal.misc.Unsafe的缓存行大小
public static final int CACHE_LINE = 64;  // x86架构的缓存行大小

// Disruptor框架中的Sequence类（避免伪共享的经典案例）
public class Sequence {
    private volatile long value = INITIAL_CURSOR_VALUE;
    
    // 前后各填充7个long，确保value独占一个缓存行
    // padding before: p1-p7
    // 真正值: value
    // padding after: p8-p14
}

// LongAdder也是——每个Cell都用@Contended填充
// 这就是为什么LongAdder在高并发下比AtomicLong快得多
```

**⚠️ 常见坑/加分回答：**
- **加分**：`LongAdder` 比 `AtomicLong` 快的原因之一就是避免了伪共享——每个Cell独占一个缓存行
- **加分**：可以用 `-XX:+PrintCommandLineFlags` 查看JVM的缓存行配置
- **坑**：填充会浪费内存空间，是空间换时间的典型策略。不是所有场景都需要避免伪共享
