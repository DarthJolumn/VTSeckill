## 第一系列：Netty核心架构与线程模型

### 第1集：Netty的线程模型有几种？你的IM系统为什么选择主从多线程模型？

**💡 核心回答：**

Netty提供三种Reactor线程模型：

| 模型 | Boss线程 | Worker线程 | 适用场景 |
|------|---------|-----------|---------|
| 单线程 | 1个 | 复用同一个 | 低并发、简单场景 |
| 多线程 | 1个 | N个（线程池） | 中等并发 |
| 主从多线程 | M个 | N个（线程池） | 高并发长连接（IM首选） |

我们的IM系统支撑10万+长连接，选择**主从多线程模型**：
- **BossGroup**（通常1~2个线程）：专职处理客户端连接请求，不断轮询Accept事件
- **WorkerGroup**（通常CPU核数×2个线程）：处理已建立连接的IO读写和业务逻辑

**📦 实际例子：**

IM系统启动时创建主从多线程模型：

```java
public class ImServer {
    public void start(int port) {
        // Boss线程组：处理连接请求（Accept）
        // 10万连接下，1-2个Boss线程足够，因为Accept操作很轻量
        EventLoopGroup bossGroup = new NioEventLoopGroup(1);
        
        // Worker线程组：处理IO读写和业务逻辑
        // 默认CPU*2个线程，每个线程负责一批Channel的IO事件
        EventLoopGroup workerGroup = new NioEventLoopGroup();
        
        try {
            ServerBootstrap bootstrap = new ServerBootstrap();
            bootstrap.group(bossGroup, workerGroup)
                .channel(NioServerSocketChannel.class)
                // Boss线程的处理器：只处理Accept
                .handler(new LoggingHandler(LogLevel.INFO))
                // Worker线程的处理器：处理已连接Channel的IO
                .childHandler(new ImServerInitializer());
            
            // 绑定端口，同步等待绑定成功
            ChannelFuture future = bootstrap.bind(port).sync();
            System.out.println("IM Server started on port " + port);
            future.channel().closeFuture().sync();
        } finally {
            bossGroup.shutdownGracefully();
            workerGroup.shutdownGracefully();
        }
    }
}
```

**为什么Worker线程数设CPU×2？** 每个Worker线程通过epoll管理多个Channel，采用非阻塞IO。当某个Channel读不到数据（EAGAIN）时，线程立刻切换到下一个Channel。CPU×2是经验值，在大多数场景下能最大化CPU利用率。

**🔍 源码解析：**

`NioEventLoopGroup` 的构造函数最终走到 `MultithreadEventLoopGroup`：

```java
// MultithreadEventLoopGroup.java
public MultithreadEventLoopGroup(int nThreads, ThreadFactory threadFactory, Object... args) {
    // nThreads为0时，默认使用 CPU核数 * 2
    super(nThreads == 0 ? DEFAULT_EVENT_LOOP_THREADS : nThreads, 
          threadFactory, args);
}

// 在 StaticPropertyUtil 中定义
private static final int DEFAULT_EVENT_LOOP_THREADS = 
    Math.max(1, SystemPropertyUtil.getInt(
        "io.netty.eventLoopThreads", 
        NettyRuntime.availableProcessors() * 2));
```

`ServerBootstrap.bind()` 的调用链：

```java
// ServerBootstrap.java → AbstractBootstrap.java
public ChannelFuture bind(SocketAddress localAddress) {
    // 1. 校验参数
    validate();
    // 2. 实际调用 initAndRegister()
    return doBind(localAddress);
}

private ChannelFuture doBind(SocketAddress localAddress) {
    // 1. 初始化并注册ServerChannel到BossGroup
    final ChannelFuture regFuture = initAndRegister();
    final Channel channel = regFuture.channel();
    
    // 2. 等待注册完成
    // 3. 调用 channel.bind() → 最终触发 NioServerSocketChannel.doBind()
    //    → ServerSocketChannel.bind(localAddress, config.getBacklog())
    //    → 底层就是 Java NIO 的 ServerSocketChannel.bind()
    
    // 4. 绑定成功后，在Boss的EventLoop中注册Accept事件
    ch.eventLoop().execute(new Runnable() {
        @Override
        public void run() {
            if (channel.isActive()) {
                // 设置SelectionKey.OP_ACCEPT
                channel.pipeline().fireChannelActive();
            }
        }
    });
}
```

**⚠️ 常见坑/加分回答：**

- Boss线程数不需要太多，1~2个足够。Accept操作本身不涉及数据读写，只是将新连接包装成SocketChannel并注册到Worker的EventLoop上
- Worker线程数也不是越大越好。每个线程通过epoll管理上千个Channel，线程太多反而增加上下文切换开销
- 如果业务逻辑（如数据库查询、消息转发）比较重，建议将业务逻辑提交到单独的业务线程池，避免阻塞EventLoop线程。这是IM系统中非常常见的做法

### 第2集：EventLoop是什么？一个EventLoop管理多少个Channel？IM系统中如何选择EventLoop数量？

**💡 核心回答：**

`EventLoop` 是 Netty 的核心调度单元，一个 EventLoop = 一个线程 + 一个 Selector + 一组 Channel。它负责：
1. 监听注册Channel上的IO事件（读、写、Accept、Connect）
2. 执行Channel上的非IO任务（如业务逻辑提交）
3. 执行定时任务（如心跳检测）

一个 EventLoop 理论上可以管理**无上限**的 Channel（受限于文件描述符数量），实际中一个 EventLoop 管理数千到上万个 Channel 是常态。

**📦 实际例子：**

在IM系统中，10万个长连接大约需要：
- 假设每个EventLoop管理5000个Channel
- 需要 100000 / 5000 = 20 个 Worker EventLoop
- 这大致等于 10核CPU × 2 = 20，与默认值吻合

获取Channel对应的EventLoop：

```java
// 每个Channel在注册时会被分配一个EventLoop
Channel channel = ...; // 客户端连接
EventLoop eventLoop = channel.eventLoop();

// 在同一个EventLoop中提交任务（线程安全，无需加锁）
eventLoop.execute(() -> {
    // 这个任务会在该Channel所属的EventLoop线程中执行
    // 比如发送消息给该用户
    channel.writeAndFlush(message);
});

// 典型场景：将重任务提交到业务线程池，避免阻塞EventLoop
EventExecutorGroup businessGroup = new DefaultEventExecutorGroup(16);
pipeline.addLast(businessGroup, "businessHandler", new BusinessHandler());
```

**🔍 源码解析：**

EventLoop的注册过程——Channel是如何被分配给EventLoop的：

```java
// MultithreadEventExecutorGroup.java
private final EventExecutor[] children;
private int childIndex = 0;

// 使用轮询方式分配EventLoop给Channel
protected EventExecutor choose(EventExecutorChooserFactory.Chooser chooser) {
    return chooser.choose(children);
}

// PowerOfTwoEventExecutorChooser（当线程数为2的幂次时）
public EventExecutor choose(EventExecutor[] executors) {
    // 使用位运算替代取模，更高效
    return executors[childIndex.getAndIncrement() & executors.length - 1];
}
```

EventLoop的核心循环——`NioEventLoop.run()`：

```java
// NioEventLoop.java
@Override
protected void run() {
    for (;;) {
        try {
            // 1. 计算IO操作超时时间（有任务时取最近任务的等待时间）
            long time = nextScheduledTaskDeadlineNanos();
            long timeoutNanos = time == -1 ? 10_000_000L : 
                Math.max(0, time - deadlineNanos);
            
            // 2. 调用Selector.select()轮询IO事件
            //    底层：epoll_wait(epfd, events, MAX_EVENTS, timeout)
            select(wakenUp.compareAndSet(false, true));
            
            // 3. 处理IO事件
            processSelectedKeys();
            
            // 4. 处理非IO任务（普通任务、定时任务）
            runAllTasks(timeoutNanos);
            
        } catch (Throwable t) {
            handleLoopException(t);
        }
    }
}

// processSelectedKeys → processSelectedKeys0
private void processSelectedKeys() {
    if (selectedKeys != null) {
        // 使用自定义的SelectedSelectionKeySet（数组实现，比JDK的HashSet快）
        processSelectedKeysPlain(selectedKeys.flip());
    } else {
        processSelectedKeysPlain(selector.selectedKeys());
    }
}

// 处理每个SelectionKey
private void processSelectedKey(SelectionKey k, AbstractNioChannel ch) {
    if (k.isReadable()) {
        // 触发Channel的读事件
        ((AbstractNioChannel.AbstractNioUnsafe) ch.unsafe()).read();
    }
    if (k.isWritable()) {
        // 触发Channel的写事件
        ch.unsafe().forceFlush();
    }
}
```

**⚠️ 常见坑/加分回答：**

- **严禁在EventLoop中执行阻塞操作**（如数据库查询、HTTP调用）。IM系统中，消息持久化必须提交到业务线程池，否则会阻塞整个EventLoop上所有Channel的IO
- EventLoop的`select()`超时时间不是固定的：如果EventLoop中有定时任务（比如心跳检测），select超时时间会取到最近一个定时任务的到期时间，确保定时任务能被及时执行
- Netty对`selectedKeys`做了优化：用数组替代了JDK的HashSet，避免Iterator创建和GC开销。这个优化在10万连接场景下效果显著

### 第3集：Channel、Pipeline、Handler三者的关系是什么？在IM系统中如何组织Handler？

**💡 核心回答：**

- **Channel**：代表一个网络连接（一个客户端连接 = 一个Channel）
- **Pipeline**：Channel内部的处理器链（责任链模式），数据读写都会经过Pipeline
- **Handler**：Pipeline中的具体处理器节点，每个Handler负责一个职责

关系：一个Channel包含一个Pipeline，一个Pipeline包含多个Handler，数据按照Handler顺序（入站/出站）流动。

**📦 实际例子：**

IM服务端的Pipeline组织（按消息处理顺序）：

```java
public class ImServerInitializer extends ChannelInitializer<SocketChannel> {
    @Override
    protected void initChannel(SocketChannel ch) {
        ChannelPipeline pipeline = ch.pipeline();
        
        // ===== 入站Handler（Inbound）：从客户端读取数据 =====
        
        // 1. 空闲检测：60秒没收到任何数据→触发读空闲事件
        pipeline.addLast("idleStateHandler", 
            new IdleStateHandler(60, 30, 0, TimeUnit.SECONDS));
        
        // 2. 协议解码：处理粘包拆包，按消息长度拆帧
        pipeline.addLast("frameDecoder", 
            new LengthFieldBasedFrameDecoder(
                65535,    // 最大帧长度
                0,        // 长度字段偏移量
                4,        // 长度字段占4字节
                0,        // 长度修正值
                4         // 需要跳过的字节数（跳过长度字段本身）
            ));
        
        // 3. 协议反序列化：字节→IM消息对象
        pipeline.addLast("decoder", new ImMessageDecoder());
        
        // 4. 心跳处理器
        pipeline.addLast("heartbeatHandler", new HeartbeatHandler());
        
        // 5. 认证处理器
        pipeline.addLast("authHandler", new AuthHandler());
        
        // 6. 业务处理（提交到业务线程池）
        pipeline.addLast(businessGroup, "businessHandler", 
            new ImBusinessHandler());
        
        // ===== 出站Handler（Outbound）：向客户端写数据 =====
        
        // 7. 协议编码：消息对象→字节
        pipeline.addLast("encoder", new ImMessageEncoder());
    }
}
```

数据流方向：

```
客户端发送数据 →
  Inbound方向（从Head到Tail）：
    HeadContext → IdleStateHandler → FrameDecoder → ImMessageDecoder 
    → HeartbeatHandler → AuthHandler → BusinessHandler → TailContext

← 服务端响应数据
  Outbound方向（从Tail到Head）：
    TailContext → ImMessageEncoder → HeadContext → 网络
```

**🔍 源码解析：**

Pipeline中事件传播的核心机制：

```java
// DefaultChannelPipeline.java

// 入站事件传播（fireChannelRead）
public ChannelPipeline fireChannelRead(Object msg) {
    // 从HeadContext开始，沿入站方向传播
    AbstractChannelHandlerContext.invokeChannelRead(head, msg);
    return this;
}

static void invokeChannelRead(final AbstractChannelHandlerContext next, Object msg) {
    // 类型检查：判断下一个Handler是否实现了ChannelInboundHandler
    // 如果实现了，调用其channelRead方法
    // 如果没有实现，跳过该Handler，继续传播到下一个
    next.invokeChannelRead(msg);
}

// AbstractChannelHandlerContext.java
void invokeChannelRead(Object msg) {
    // 在EventLoop线程中执行，保证线程安全
    if (invokeNow()) {
        channelRead(msg);
    } else {
        execute(() -> channelRead(msg));
    }
}

// 具体Handler的channelRead实现
private void channelRead(Object msg) {
    // 获取当前context对应的Handler
    ChannelHandler handler = handler();
    // 判断handler是否实现了ChannelInboundHandler接口
    if (handler instanceof ChannelInboundHandler) {
        ((ChannelInboundHandler) handler).channelRead(this, (Object) msg);
    }
}

// 出站事件传播（writeAndFlush）
public ChannelFuture writeAndFlush(Object msg) {
    // 从TailContext开始，沿出站方向传播
    return tail.writeAndFlush(msg);
}
```

**⚠️ 常见坑/加分回答：**

- **Handler顺序很重要**：解码器必须在业务处理器之前，编码器必须在出站路径上。顺序放错会导致数据无法正确解析或发送
- `addLast`和`addFirst`的区别：addLast在链表尾部添加，addFirst在头部添加。通常用addLast保持直观顺序
- Pipeline是线程安全的，可以在运行时动态添加/移除Handler（比如认证成功后添加业务Handler、移除认证Handler），这在IM系统的登录流程中非常实用

## 第二系列：自定义协议与编解码

### 第4集：IM系统的自定义协议怎么设计？为什么不用HTTP？

**💡 核心回答：**

IM系统不使用HTTP而使用**TCP自定义协议**，原因：
1. **长连接需求**：HTTP是短连接（即使HTTP/1.1的Keep-Alive也不适合长连接场景），每次通信都要建立连接，延迟高
2. **协议开销**：HTTP头部字段冗长（几百字节到几KB），而IM消息头部通常只需要十几个字节
3. **双向通信**：HTTP是请求-响应模型，服务端无法主动推送消息给客户端。IM需要服务端主动推送
4. **心跳保活**：TCP长连接可以通过自定义心跳包维持连接，HTTP没有这个机制

**📦 实际例子：**

IM系统自定义协议设计（16字节定长头部 + 变长消息体）：

```
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────────┐
│ magic(4B)│ version  │ cmd(2B)  │ seqId(4B)│ bodyLen  │   body       │
│ 0xCAFEBABE│  (1B)   │ 消息类型  │ 消息序号  │  (4B)    │  (变长)      │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────────┘
  固定魔数    协议版本   1=登录     唯一标识    消息体长度   Protobuf序列化
                      2=聊天
                      3=心跳
                      4=ACK
                      5=已读回执
                      ...
```


**⚠️ 常见坑/加分回答：**

- 魔数的作用是**防止脏连接**：如果客户端用HTTP协议访问IM端口，魔数校验会直接拒绝，避免解析错误
- 协议版本号预留了升级空间：V1用Protobuf，V2可能换FlatBuffers，通过版本号选择不同解码器
- seqId用于消息去重和ACK确认：客户端发送时带上递增的seqId，服务端ACK回来同样的seqId，实现可靠传输

### 第5集：Netty中如何实现自定义协议的编解码器？

**💡 核心回答：**

Netty提供了多个解码器基类，最常用的是：
- `ByteToMessageDecoder`：字节→消息对象（入站解码）
- `MessageToByteEncoder`：消息对象→字节（出站编码）

对于我们的IM自定义协议，需要自己实现这两个类，按照协议格式进行读写。

**📦 实际例子：**

IM消息解码器：

```java
public class ImMessageDecoder extends ByteToMessageDecoder {
    
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        // 可读字节数不足一个完整头部，等待更多数据
        if (in.readableBytes() < ImProtocol.HEADER_LENGTH) {
            return;
        }
        
        // 标记当前读位置，用于回退
        in.markReaderIndex();
        
        // 1. 读取魔数
        int magic = in.readInt();
        if (magic != ImProtocol.MAGIC) {
            // 非法协议，关闭连接
            ctx.close();
            return;
        }
        
        // 2. 读取版本号
        byte version = in.readByte();
        
        // 3. 读取命令类型
        short cmd = in.readShort();
        
        // 4. 读取消息序号
        int seqId = in.readInt();
        
        // 5. 读取消息体长度
        int bodyLength = in.readInt();
        
        // 防御性校验：消息体不能太大（防止恶意攻击）
        if (bodyLength > 1024 * 1024) { // 最大1MB
            ctx.close();
            return;
        }
        
        // 可读字节数不足消息体，回退等待完整数据
        if (in.readableBytes() < bodyLength) {
            in.resetReaderIndex();
            return;
        }
        
        // 6. 读取消息体
        byte[] body = new byte[bodyLength];
        in.readBytes(body);
        
        // 7. 构建消息对象，传递给下一个Handler
        ImMessage message = new ImMessage();
        message.setMagic(magic);
        message.setVersion(version);
        message.setCmd(cmd);
        message.setSeqId(seqId);
        message.setBodyLength(bodyLength);
        message.setBody(body);
        
        out.add(message);
    }
}
```

IM消息编码器：


**🔍 源码解析：**

`ByteToMessageDecoder` 的工作机制——为什么需要 `cumulation` 缓冲区：

```java
// ByteToMessageDecoder.java
private ByteBuf cumulation;

@Override
public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
    if (msg instanceof ByteBuf) {
        // 核心：将接收到的数据追加到cumulation缓冲区
        // 因为TCP粘包/拆包，一次channelRead可能只收到半条消息
        ByteBuf data = (ByteBuf) msg;
        if (cumulation == null) {
            cumulation = data;
        } else {
            // 将新数据追加到已有数据后面
            cumulation = cumulation.writeBytes(data);
            data.release(); // 释放原始ByteBuf
        }
        
        // 调用子类的decode方法
        // decode中如果数据不够，直接return，不添加任何对象到out
        // 下次channelRead时，新数据会继续追加到cumulation
        callDecode(ctx, cumulation, out);
    }
}

// callDecode的核心逻辑
protected void callDecode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    while (in.isReadable()) {
        int outSize = out.size();
        int oldInputLength = in.readableBytes();
        
        // 调用我们实现的decode方法
        decodeRemovalReentryProtection(ctx, in, out);
        
        // 如果decode没有产出任何消息，说明数据不完整，等待下次
        if (outSize == out.size()) {
            if (oldInputLength == in.readableBytes()) {
                // 既没产出消息，也没消耗数据 → 数据不够，退出等待
                break;
            }
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

- `decode()` 方法中数据不够时**直接return即可**，不要抛出异常。ByteToMessageDecoder会自动累积数据，下次收到数据后再次调用decode
- 防御性校验非常重要：生产环境必须限制消息体大小，否则恶意客户端可以发送超大bodyLength耗尽服务器内存
- `in.readableBytes()` 和 `in.readIndex()` 的关系要搞清楚：readableBytes = writerIndex - readerIndex

### 第6集：什么是粘包拆包？IM系统中用LengthFieldBasedFrameDecoder怎么解决？

**💡 核心回答：**

TCP是**字节流协议**，没有消息边界的概念。发送端发出的两条消息，接收端可能收到：
- **粘包**：两条消息粘在一起变成一条
- **拆包**：一条消息被拆成多条接收

这是因为TCP的发送缓冲区、接收缓冲区、MSS（最大报文段长度）等因素造成的。

Netty提供了多种拆包方案：

| 方案 | 适用场景 |
|------|---------|
| FixedLengthFrameDecoder | 固定长度消息 |
| LineBasedFrameDecoder | 以换行符分隔（如文本协议） |
| DelimiterBasedFrameDecoder | 自定义分隔符（如XML的`</msg>`） |
| **LengthFieldBasedFrameDecoder** | **长度字段+消息体（IM最常用）** |

**📦 实际例子：**

IM系统使用LengthFieldBasedFrameDecoder：

```java
// 协议格式：
// ┌──────────┬──────────────┐
// │bodyLen(4B)│   body       │
// └──────────┴──────────────┘
// 注意：这里为了演示LengthFieldBasedFrameDecoder，简化为"长度+消息体"格式

pipeline.addLast(new LengthFieldBasedFrameDecoder(
    65535,   // maxFrameLength：最大帧长度，超过则关闭连接（防止OOM）
    0,       // lengthFieldOffset：长度字段在帧中的偏移量（第0字节开始）
    4,       // lengthFieldLength：长度字段占4字节
    0,       // lengthAdjustment：长度修正值（0表示bodyLen就是body的长度）
    4        // initialBytesToStrip：跳过帧开头的4字节（不把长度字段传给下游）
));
```

但我们的IM协议头部不止长度字段，还有magic、version、cmd、seqId，所以实际要用**自定义解码器**（第5集的做法），或者这样组合：

```java
// 方案：先用LengthFieldBasedFrameDecoder拆帧，再用自定义Handler解析帧头
pipeline.addLast(new LengthFieldBasedFrameDecoder(
    65535,           // maxFrameLength
    11,              // lengthFieldOffset：bodyLen在第11字节
                     // (magic=4 + version=1 + cmd=2 + seqId=4 = 11)
    4,               // lengthFieldLength：bodyLen占4字节
    0,               // lengthAdjustment：bodyLen后面就是body，不需要调整
    0                // initialBytesToStrip：不跳过，整个帧传给下游解析
));
pipeline.addLast(new ImProtocolParser()); // 解析帧头+body
```

**🔍 源码解析：**

`LengthFieldBasedFrameDecoder` 的核心拆帧逻辑：

```java
// LengthFieldBasedFrameDecoder.java → LengthFieldBasedFrameDecoder.decode()
protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
    // 1. 读取长度字段
    long frameLength = getUnadjustedFrameLength(in, actualOffset, lengthFieldLength, ...);
    
    // 2. 应用修正值
    frameLength += lengthAdjustment + lengthFieldEndOffset;
    
    // 3. 检查是否超过最大帧长度
    if (frameLength > maxFrameLength) {
        // 超过最大帧长度，抛异常（可配置为关闭连接）
        throw new TooLongFrameException(...);
    }
    
    // 4. 检查数据是否完整
    int frameLengthInt = (int) frameLength;
    if (in.readableBytes() < frameLengthInt) {
        // 数据不完整，返回null，等待下次decode
        return null;
    }
    
    // 5. 跳过指定字节数（initialBytesToStrip）
    if (initialBytesToStrip > 0) {
        in.skipBytes(initialBytesToStrip);
    }
    
    // 6. 提取帧数据（返回一个新的ByteBuf，不拷贝）
    int actualFrameLength = frameLengthInt - initialBytesToStrip;
    ByteBuf frame = in.readSlice(actualFrameLength);
    return frame;
}
```

**⚠️ 常见坑/加分回答：**

- `LengthFieldBasedFrameDecoder` 比手写解码器更安全，它内部已经处理了超长帧、数据不完整等边界情况
- `lengthAdjustment` 容易搞错：如果长度字段的值表示的是"从长度字段末尾到帧末尾的长度"，则adjustment=0；如果表示的是"整个帧的长度"，则需要减掉长度字段之前的字节数
- 生产环境一定要设置 `maxFrameLength`，这是防止内存溢出的最后一道防线

## 第三系列：ByteBuf与内存管理

### 第7集：Netty的ByteBuf和Java的ByteBuffer有什么区别？为什么Netty要自己设计？

**💡 核心回答：**

| 特性 | Java ByteBuffer | Netty ByteBuf |
|------|----------------|---------------|
| 读写分离 | 需要flip()切换读写模式 | 双指针（readerIndex/writerIndex），不需要flip |
| 动态扩容 | 固定大小，不能扩容 | 自动扩容（最大到maxCapacity） |
| 内存管理 | JVM GC管理 | **引用计数**手动管理 + 内存池化 |
| 零拷贝 | 不支持 | 支持（CompositeByteBuf、slice、fileRegion） |
| 性能 | 一般 | 高（池化+直接内存+复用） |

ByteBuf的核心设计——双指针模型：

```
          readerIndex              writerIndex
              │                        │
  ────────────┼────────────────────────┼────────────
              │    readable bytes      │
  discardable │    (可读区域)           │  writable
  bytes       │                        │  bytes
  ────────────┼────────────────────────┼────────────
              0                     capacity
```

- **readerIndex** 左侧：已读区域（可丢弃）
- **readerIndex ~ writerIndex**：可读区域
- **writerIndex** 右侧到capacity：可写区域

**📦 实际例子：**

在IM系统中使用ByteBuf：

```java
// 解码时使用ByteBuf
public void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    // 读取魔数
    int magic = in.readInt();     // readerIndex += 4
    
    // 检查是否有足够的可读字节
    if (in.readableBytes() < 11) {
        return; // 数据不够
    }
    
    // 标记当前读位置（用于回退）
    in.markReaderIndex();
    
    // 读取消息体
    int bodyLen = in.readInt();
    byte[] body = new byte[bodyLen];
    in.readBytes(body);           // readerIndex += bodyLen
    
    // 构建消息
    out.add(buildMessage(body));
}

// 编码时使用ByteBuf
public void encode(ChannelHandlerContext ctx, ImMessage msg, ByteBuf out) {
    out.writeInt(msg.getMagic());
    out.writeBytes(msg.getBody());
    // writerIndex自动增长
}
```

**🔍 源码解析：**

ByteBuf的自动扩容机制：

```java
// AbstractByteBuf.java
private void ensureCapacity0(int minNewCapacity) {
    // 当前容量不够，需要扩容
    int newCapacity = calculateNewCapacity(minNewCapacity, maxCapacity);
    capacity(newCapacity);  // 调用子类的扩容方法
}

private int calculateNewCapacity(int minNewCapacity, int maxCapacity) {
    // 扩容策略：当前容量 × 2，但不超过maxCapacity
    final int threshold = 4 * 1024 * 1024; // 4MB
    if (minNewCapacity == threshold) {
        return threshold;
    }
    
    // 如果大于4MB，按1MB对齐
    if (minNewCapacity > threshold) {
        int newCapacity = minNewCapacity / threshold * threshold;
        if (newCapacity > maxCapacity - threshold) {
            newCapacity = maxCapacity;
        } else {
            newCapacity += threshold;
        }
        return newCapacity;
    }
    
    // 小于4MB，按64字节对齐，从64开始不断×2
    int newCapacity = 64;
    while (newCapacity < minNewCapacity) {
        newCapacity <<= 1;  // × 2
    }
    return Math.min(newCapacity, maxCapacity);
}
```

**⚠️ 常见坑/加分回答：**

- ByteBuf最大的优势是**双指针不需要flip**，这在使用上比ByteBuffer简洁很多，而且避免了flip忘记调用导致的Bug
- ByteBuf的引用计数是Netty内存管理的核心：池化ByteBuf必须手动release()，否则内存泄漏。在IM系统中，10万连接高频消息下，泄漏会很快耗尽直接内存
- `readSlice()` 和 `readBytes()` 的区别：slice是共享底层内存（零拷贝），readBytes是拷贝一份新数据。IM转发消息时用slice性能更好

### 第8集：ByteBuf的引用计数是什么？IM系统中如何避免内存泄漏？

**💡 核心回答：**

ByteBuf使用**引用计数（Reference Counting）** 来管理内存，这是Netty内存管理的核心机制：
- 创建时：refCnt = 1
- retain()：refCnt++
- release()：refCnt--
- refCnt == 0：内存被回收（归还内存池或释放直接内存）

引用计数的目的是**延迟回收**：当ByteBuf被多个Handler共享时（如消息转发），不能随意释放，需要所有使用方都release后才能真正回收。

**📦 实际例子：**

IM系统中常见的内存泄漏场景和解决方案：

```java
// ✅ 正确做法1：在Handler中处理完消息后，Netty会自动release

@Override
protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    byte[] body = new byte[bodyLen];
    in.readBytes(body);    // 数据已经拷贝到body数组中
    out.add(new ImMessage(body));
    // in这个ByteBuf会被ByteToMessageDecoder自动release
}

// ✅ 正确做法2：消息转发时使用retain/release
public class MessageRouterHandler extends ChannelInboundHandlerAdapter {

    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        ImMessage message = (ImMessage) msg;
        
        // 转发给多个目标（如群聊场景）
        for (Channel targetChannel : targetChannels) {
            // 转发前必须retain，因为最后会release原始消息
            targetChannel.writeAndFlush(message.retain());
        }
        
        // 原始消息的引用：转发完后释放
        ReferenceCountUtil.release(message);

    // 内存泄漏！
}

// SimpleChannelInboundHandler会在channelRead0执行完后自动release消息

    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {

        // 方法结束后，msg会被自动release
        handleMessage(ctx, msg);
    }
```

**🔍 源码解析：**

引用计数的实现——`AbstractReferenceCountedByteBuf`：

```java
// AbstractReferenceCountedByteBuf.java
private volatile int refCnt = 1;  // volatile保证可见性

@Override
public int refCnt() {
    return refCnt;
}

@Override
public ByteBuf retain() {
    return retain0(1);
}

private ByteBuf retain0(int increment) {
    // CAS操作保证线程安全
    int oldRef = refCnt;
    if (oldRef == 0 || oldRef + increment < oldRef) {
        throw new IllegalReferenceCountException(oldRef, increment);
    }
    // 原子递增
    while (!REF_CNT_UPDATER.compareAndSet(this, oldRef, oldRef + increment)) {
        oldRef = refCnt;
    }
    return this;
}

@Override
public boolean release() {
    return release0(1);
}

private boolean release0(int decrement) {
    int oldRef = refCnt;
    if (oldRef == decrement) {
        // refCnt减到0，触发回收
        if (REF_CNT_UPDATER.compareAndSet(this, oldRef, 0)) {
            deallocate();  // 核心：归还内存
            return true;
        }
    }
    // CAS递减
    while (!REF_CNT_UPDATER.compareAndSet(this, oldRef, oldRef - decrement)) {
        oldRef = refCnt;
    }
    return false; // 还没减到0
}

// deallocate由子类实现
// PooledDirectByteBuf → 归还到内存池
// UnpooledDirectByteBuf → ByteBuffer.free()释放直接内存
```

**⚠️ 常见坑/加分回答：**

- **最常见的泄漏原因**：自定义Handler继承了`ChannelInboundHandlerAdapter`而不是`SimpleChannelInboundHandler`，后者会自动release
- 开发环境开启内存泄漏检测：`-Dio.netty.leakDetection.level=PARANOID`（生产环境用ADVANCED，性能影响小）
- 在IM系统中，群消息转发是最容易出泄漏的地方：消息要发给N个人，每个人都retain一次，最后原始消息要release一次。如果循环中某一步异常，要确保已retain的也能被释放

### 第9集：什么是ByteBuf的池化？PooledByteBufAllocator的原理是什么？

**💡 核心回答：**

ByteBuf的分配方式有两种：

| 类型 | 分配器 | 特点 |
|------|--------|------|
| 非池化 | UnpooledByteBufAllocator | 每次new，频繁创建销毁，GC压力大 |
| **池化** | **PooledByteBufAllocator** | **预分配大块内存，按需切分复用，GC压力小** |

池化的核心思想来自jemalloc（C语言内存分配器）：
1. **预分配**：启动时分配大块内存（Arena）
2. **分级管理**：按大小分Chunk → Arena → PoolSubpage → PoolChunk
3. **复用**：release后不真正释放内存，而是标记为可用，下次分配时直接复用

**📦 实际例子：**

IM系统中默认使用池化分配器：

```java
// Netty 4.x 默认使用池化分配器
// 可以通过系统属性配置
// -Dio.netty.allocator.type=pooled  （默认）
// -Dio.netty.allocator.type=unpooled

// 手动创建ByteBuf时，使用默认分配器
ByteBuf buf = PooledByteBufAllocator.DEFAULT.directBuffer(256);
// 从内存池中分配256字节的直接内存ByteBuf
// 实际可能分配更大的对齐块（最小分配单元是16字节，按2的幂次对齐）

// 直接内存 vs 堆内存
ByteBuf directBuf = PooledByteBufAllocator.DEFAULT.directBuffer(1024);
// 使用堆外内存（DirectByteBuffer），IO零拷贝时需要
ByteBuf heapBuf = PooledByteBufAllocator.DEFAULT.heapBuffer(1024);
// 使用JVM堆内存

// IM服务端推荐使用直接内存：
// 1. 减少一次堆内存→堆外内存的拷贝（Socket write时需要）
// 2. 不受JVM GC影响
```

**🔍 源码解析：**

PooledByteBufAllocator的核心数据结构：

```java
// PooledByteBufAllocator.java

// 内存层级结构：
// Allocator → Arena[] → PoolChunkList → PoolChunk → PoolSubpage

// 初始化时创建Arena数组
private final PoolArena<byte[]>[] heapArenas;     // 堆内存Arena数组
private final PoolArena<ByteBuffer>[] directArenas; // 直接内存Arena数组

// Arena数量 = min(CPU核数 * 2, globalArenas)
// 默认globalArenas = OS页大小 / Chunk大小，通常是CPU*2
static int defaultNumHeapArena() {
    return Math.max(0, SystemPropertyUtil.getInt(
        "io.netty.allocator.numHeapArenas",
        NettyRuntime.availableProcessors() * 2));
}

// PoolChunk：每个Chunk管理16MB内存
// 使用完全二叉树来管理内存分配（类似jemalloc的设计）
// 
// 16MB Chunk的树结构：
// Level 0: [                    16MB                    ]  → 分配16MB请求
// Level 1: [      8MB      ][          8MB            ]  → 分配8MB请求
// Level 2: [ 4MB ][ 4MB  ][ 4MB ][ 4MB ]               → 分配4MB请求
// Level 3: [2M][2M][2M][2M][2M][2M][2M][2M]            → 分配2MB请求
// ...
// Level 11: [16B×65536]                                  → 分配16B请求（最小单元）

// PoolSubpage：管理小于一个page（默认8KB）的微小内存分配
// 使用位图（bitmap）来标记哪些小块被分配/释放
// 比如一个8KB的page可以分成 8192/16 = 512 个16字节的小块
// 用512位的bitmap来管理

// 分配流程：
public ByteBuf allocate(int reqCapacity) {
    if (reqCapacity <= threadLocalCache.subpageOverflowThreshold) {
        // 小内存（<= 8KB）：走Subpage分配
        return allocateSubpage(reqCapacity);
    } else {
        // 大内存（> 8KB）：走Chunk分配
        int normCapacity = normalizeCapacity(reqCapacity);
        return allocateRun(normCapacity);
    }
}
```

**⚠️ 常见坑/加分回答：**

- 池化分配器的性能优势在高并发下非常明显：10万连接的IM系统，每秒可能分配/释放数百万个ByteBuf。池化避免了频繁的malloc/free，减少系统调用开销
- 池化ByteBuf的release()只是把内存标记为可复用，并不会真正释放给OS。这是Netty设计为引用计数的根本原因：需要精确知道什么时候内存可以归还给池
- 直接内存的大小不受JVM堆大小限制，但受OS限制。可以通过 `-Dio.netty.maxDirectMemory` 或 `-XX:MaxDirectMemorySize` 配置
- Arena之间通过线程绑定来避免锁竞争：每个EventLoop线程绑定一个Arena，分配/释放内存时不需要跨Arena竞争锁

### 第10集：Netty的零拷贝体现在哪里？IM系统中如何利用？

**💡 核心回答：**

Netty的"零拷贝"包含三个层面（不完全是OS级别的零拷贝）：

1. **CompositeByteBuf**：将多个ByteBuf逻辑组合成一个，避免内存拷贝
2. **slice/duplicate**：共享底层内存创建新ByteBuf，不拷贝数据
3. **FileRegion（DefaultFileRegion）**：封装OS的sendfile()系统调用，数据从文件直接到Socket，不经过用户态

**📦 实际例子：**

```java
// 场景1：IM发送图片消息——使用FileRegion零拷贝发送文件
// 客户端请求下载图片，服务端直接用零拷贝发送
public void sendImage(ChannelHandlerContext ctx, String imagePath) {
    File file = new File(imagePath);
    try (FileInputStream fis = new FileInputStream(file)) {
        FileRegion region = new DefaultFileRegion(
            fis.getChannel(), 0, file.length());
        ctx.writeAndFlush(region);
        // 底层调用 sendfile()，数据从文件→Socket
        // 不经过用户态缓冲区，不需要copy到ByteBuf
    } catch (IOException e) {
        e.printStackTrace();
    }
}

// 场景2：消息转发——使用slice共享内存，避免拷贝
public class MessageForwardHandler extends SimpleChannelInboundHandler<ImMessage> {

            // 注意：slice共享引用计数，只需要在原始buf上release
            member.writeAndFlush(shared.retain());

        originalBody.release();
    }
}
```

```java
    long count = this.count - position;
    if (count < 0 || position < 0) {
        throw new IllegalArgumentException(...);
    }
    
    // 底层调用 FileChannel.transferTo()
    // → Linux: sendfile(fd, s, offset, count)
    // → 数据直接从page cache→socket buffer
    // → 不需要拷贝到用户态
    long written = file.transferTo(this.position + position, count, target);
    
    if (written > 0) {
        transferred += written;
    }
    return written;
}

// 对比传统方式：
// 传统：read() 文件→用户缓冲区 → write() 用户缓冲区→socket
//        2次系统调用 + 2次数据拷贝
// sendfile：文件→socket
//           1次系统调用 + 0次用户态拷贝（DMA直接传输）
```

**⚠️ 常见坑/加分回答：**

- FileRegion只能用于文件传输，不能用于普通ByteBuf数据。如果是内存中的消息数据，还是需要通过ByteBuf发送
- CompositeByteBuf的component数量有上限（默认1024），超过会退化为拷贝。IM消息一般不会超过这个限制
- slice()创建的ByteBuf和原ByteBuf共享引用计数：在slice上调用retain/release会影响原ByteBuf的refCnt，使用时要小心
- sendfile在Windows上不可用（Windows使用TransmitFile），IM跨平台部署时需要注意

### 第11集：如何用Netty实现IM的用户登录鉴权流程？

**💡 核心回答：**

IM系统的登录鉴权流程：
1. 客户端建立TCP连接
2. 发送登录消息（包含Token/用户名+密码）
3. 服务端验证Token
4. 验证成功：绑定用户与Channel，返回成功
5. 验证失败：关闭连接

关键点：在Netty中，**未认证的连接不应该进入业务处理**，通过动态添加/移除Handler来控制。

**📦 实际例子：**

```java
// 认证Handler
public class AuthHandler extends SimpleChannelInboundHandler<ImMessage> {
    
    // 超时时间：连接建立后10秒内未认证成功，强制关闭
    private ScheduledFuture<?> authTimeoutFuture;
    
    @Override
    public void channelActive(ChannelHandlerContext ctx) {
        // 连接建立，启动认证超时定时器
        authTimeoutFuture = ctx.executor().schedule(() -> {
            if (!ctx.channel().hasAttr(AttributeKey.valueOf("userId"))) {
                // 10秒内未认证成功
                System.out.println("Auth timeout, closing connection");
                ctx.close();
            }
        }, 10, TimeUnit.SECONDS);
    }
    
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        if (msg.getCmd() == ImProtocol.CMD_LOGIN) {
            // 反序列化登录消息体
            LoginMessage login = LoginMessage.parseFrom(msg.getBody());
            
            // 验证Token（查Redis/数据库）
            String userId = TokenValidator.validate(login.getToken());
            
            if (userId != null) {
                // 认证成功
                ctx.channel().attr(AttributeKey.valueOf("userId")).set(userId);
                
                // 将用户ID绑定到Channel
                ChannelManager.getInstance().addChannel(userId, ctx.channel());
                
                // 动态修改Pipeline：移除认证Handler，添加业务Handler
                ctx.pipeline().remove(this); // 移除自己
                // 认证成功后的消息不再经过这里
                
                // 发送认证成功响应
                sendAuthResponse(ctx, msg.getSeqId(), true);
                
                // 取消超时定时器
                if (authTimeoutFuture != null) {
                    authTimeoutFuture.cancel(false);
                }
                
                System.out.println("User " + userId + " authenticated");
            } else {
                // 认证失败
                sendAuthResponse(ctx, msg.getSeqId(), false);
                ctx.close();
            }
        } else {
            // 未认证就发其他消息，非法行为
            ctx.close();
        }
    }
    
    @Override
    public void channelInactive(ChannelHandlerContext ctx) {
        // 连接断开，取消超时定时器
        if (authTimeoutFuture != null) {
            authTimeoutFuture.cancel(false);
        }
    }
}
```

### 第12集：IM的心跳保活机制怎么实现？IdleStateHandler的原理是什么？

**💡 核心回答：**

心跳保活是IM系统的核心机制，用于：
1. **检测死连接**：客户端崩溃、网络断开，TCP层面可能不会立刻感知
2. **维持连接**：中间网络设备（NAT/防火墙）会清理空闲TCP连接
3. **节省资源**：及时清理无效连接，释放服务器资源

IM系统采用**双向心跳**：
- **客户端→服务端**：客户端每隔30秒发心跳包
- **服务端→客户端**：服务端检测到60秒没收到客户端数据，主动断开

**📦 实际例子：**

```java
// 心跳Handler
public class HeartbeatHandler extends ChannelInboundHandlerAdapter {
    
    // 连续未收到客户端消息的次数
    private int readIdleTimes = 0;
    
    @Override
    public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
        if (evt instanceof IdleStateEvent) {
            IdleStateEvent event = (IdleStateEvent) evt;
            
            switch (event.state()) {
                case READER_IDLE:
                    // 读空闲：60秒没收到客户端任何数据
                    readIdleTimes++;
                    System.out.println("读空闲 #" + readIdleTimes + 
                        "，用户: " + ctx.channel().attr(USER_ID).get());
                    
                    if (readIdleTimes >= 3) {
                        // 连续3次读空闲（180秒），强制关闭
                        System.out.println("超过最大空闲次数，关闭连接");
                        ChannelManager.getInstance().removeChannel(
                            ctx.channel().attr(USER_ID).get());
                        ctx.close();
                    } else {
                        // 发送心跳请求给客户端（服务端主动探测）
                        ctx.writeAndFlush(buildHeartbeatMessage());
                    }
                    break;
                    
                case WRITER_IDLE:
                    // 写空闲：30秒没向客户端发送任何数据
                    // 主动发送心跳包维持连接
                    ctx.writeAndFlush(buildHeartbeatMessage());
                    break;
                    
                case ALL_IDLE:
                    // 读写都空闲
                    break;
            }
        } else {
            // 其他自定义事件，传递给下一个Handler
            ctx.fireUserEventTriggered(evt);
        }
    }
}
```

`IdleStateHandler` 的实现原理：

```java
// IdleStateHandler.java
public class IdleStateHandler extends ChannelDuplexHandler {
    
    private long readerIdleTimeNanos;  // 读空闲超时时间
    private long writerIdleTimeNanos;  // 写空闲超时时间
    private long allIdleTimeNanos;     // 读写空闲超时时间
    
    private ScheduledFuture<?> readerIdleTimeout;
    private ScheduledFuture<?> writerIdleTimeout;
    
    @Override
    public void channelActive(ChannelHandlerContext ctx) {
        // Channel激活时，初始化定时任务
        initialize(ctx);
        ctx.fireChannelActive();
    }
    
    private void initialize(ChannelHandlerContext ctx) {
        EventLoop loop = ctx.executor();
        
        if (readerIdleTimeNanos > 0) {
            // 调度读空闲检测定时任务
            readerIdleTimeout = loop.schedule(
                new ReaderIdleTimeoutTask(ctx),
                readerIdleTimeNanos, TimeUnit.NANOSECONDS);
        }
        
        if (writerIdleTimeNanos > 0) {
            writerIdleTimeout = loop.schedule(
                new WriterIdleTimeoutTask(ctx),
                writerIdleTimeNanos, TimeUnit.NANOSECONDS);
        }
    }
    
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        if (readerIdleTimeNanos > 0) {
            // 每次读到数据，重置读空闲计时
            readingInProgress.set(true);
            lastReadTime = ticksInNanos(); // 记录最后读取时间
        }
        ctx.fireChannelRead(msg);
    }
    
    // 读空闲定时任务
    private final class ReaderIdleTimeoutTask implements Runnable {
        @Override
        public void run(ChannelHandlerContext ctx) {
            long nextDelay = readerIdleTimeNanos;
            if (readingInProgress.compareAndSet(true, false)) {
                // 最近有读取过数据，重新计时
                lastReadTime = ticksInNanos();
                nextDelay = readerIdleTimeNanos - 
                    (ticksInNanos() - lastReadTime);
            }
            
            if (nextDelay <= 0) {
                // 真的超时了！触发读空闲事件
                // 通过fireUserEventTriggered传递给Pipeline中的Handler
                readerIdle(ctx);
                nextDelay = readerIdleTimeNanos;
            }
            
            // 重新调度下一次检测
            readerIdleTimeout = loop.schedule(this, nextDelay, ...);
        }
    }
    
    // 触发读空闲事件
    protected void readerIdle(ChannelHandlerContext ctx) {
        // 创建一个IdleStateEvent事件
        IdleStateEvent event = new IdleStateEvent(IdleState.READER_IDLE);
        // 通过Pipeline传播（fireUserEventTriggered）
        ctx.fireUserEventTriggered(event);
    }
}
```

**⚠️ 常见坑/加分回答：**

- IdleStateHandler的定时任务是绑定在EventLoop上的，如果EventLoop被阻塞（比如业务逻辑太重），定时任务无法及时执行，心跳检测会失效
- **不要混淆TCP层的KeepAlive和应用层心跳**：TCP KeepAlive默认2小时才发探测包，对IM来说太慢了。应用层心跳通常30秒，能更快检测到死连接
- 心跳包要尽量小：只包含协议头（15字节），不需要消息体，减少带宽消耗
- 在IM系统中，心跳还承载了"在线状态"的功能：用户心跳停止=用户下线

### 第13集：IM的单聊消息路由怎么实现？消息ACK怎么保证可靠传输？

**💡 核心回答：**

**单聊消息路由**的核心逻辑：
1. 发送方→服务端：消息包含fromUserId和toUserId
2. 服务端查在线状态：目标用户是否在线
3. 在线：直接通过目标用户的Channel推送
4. 离线：存入数据库，等目标用户上线后推送

**消息ACK（可靠传输）**：
1. 每条消息有唯一seqId
2. 发送方发消息后启动超时重传定时器
3. 接收方收到消息后发送ACK（携带seqId）
4. 发送方收到ACK后取消重传定时器

**📦 实际例子：**

消息路由Handler：

```java
public class MessageRouterHandler extends SimpleChannelInboundHandler<ImMessage> {
    
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        switch (msg.getCmd()) {
            case ImProtocol.CMD_CHAT:
                handleSingleChat(ctx, msg);
                break;
            case ImProtocol.CMD_GROUP_MSG:
                handleGroupChat(ctx, msg);
                break;
            case ImProtocol.CMD_ACK:
                handleAck(ctx, msg);
                break;
            case ImProtocol.CMD_READ_RECEIPT:
                handleReadReceipt(ctx, msg);
                break;
        }
    }
    
    private void handleSingleChat(ChannelHandlerContext ctx, ImMessage msg) {
        String fromUserId = ctx.channel().attr(USER_ID).get();
        
        // 解析消息体
        ChatMessage chatMsg = ChatMessage.parseFrom(msg.getBody());
        String toUserId = chatMsg.getToUserId();
        
        // 1. 消息持久化（异步提交到业务线程池）
        String msgId = messageStore.saveMessage(fromUserId, toUserId, chatMsg);
        
        // 2. 给发送方回复ACK
        sendAck(ctx, msg.getSeqId());
        
        // 3. 路由：查找目标用户的Channel
        Channel targetChannel = ChannelManager.getInstance().getChannel(toUserId);
        
        if (targetChannel != null && targetChannel.isActive()) {
            // 目标在线，直接推送
            ImMessage forwardMsg = buildForwardMessage(msg, fromUserId, msgId);
            targetChannel.writeAndFlush(forwardMsg);
            
            // 标记消息已送达
            messageStore.markDelivered(msgId);
        } else {
            // 目标离线，存入离线消息队列
            messageStore.saveOfflineMessage(toUserId, msgId, chatMsg);
            
            // 可选：触发离线推送（APNs/FCM）
            pushService.sendOfflinePush(toUserId, chatMsg);
        }
    }
    
    private void handleAck(ChannelHandlerContext ctx, ImMessage msg) {
        // 收到ACK，取消对应的重传定时器
        AckMessage ack = AckMessage.parseFrom(msg.getBody());
        int ackSeqId = ack.getSeqId();
        
        // 从待确认队列中移除
        PendingMessageManager.getInstance().removePending(ctx.channel(), ackSeqId);
    }
    
    private void sendAck(ChannelHandlerContext ctx, int seqId) {
        ImMessage ackMsg = new ImMessage();
        ackMsg.setCmd(ImProtocol.CMD_ACK);
        ackMsg.setSeqId(seqId);
        ackMsg.setBody(new AckMessage(seqId).toByteArray());
        ctx.writeAndFlush(ackMsg);
    }
}
```

发送方的超时重传机制：

```java
public class PendingMessageManager {
    // Channel → (seqId → PendingMessage)
    private final ConcurrentMap<Channel, ConcurrentMap<Integer, PendingMessage>> 
        pendingMessages = new ConcurrentHashMap<>();
    
    public void addPending(Channel channel, int seqId, ImMessage msg) {
        PendingMessage pending = new PendingMessage(seqId, msg);
        
        // 设置3秒超时重传
        pending.setTimeoutFuture(channel.eventLoop().schedule(() -> {
            // 超时未收到ACK，重传
            if (pending.getRetryCount() < 3) {
                pending.incrementRetry();
                channel.writeAndFlush(msg.retain());
                // 重新设置超时（指数退避：3s → 6s → 12s）
                long delay = 3L * (1 << pending.getRetryCount());
                pending.resetTimeoutFuture(channel.eventLoop().schedule(...));
            } else {
                // 超过最大重试次数，标记消息发送失败
                markFailed(seqId);
            }
        }, 3, TimeUnit.SECONDS));
        
        pendingMessages
            .computeIfAbsent(channel, k -> new ConcurrentHashMap<>())
            .put(seqId, pending);
    }
    
    public void removePending(Channel channel, int seqId) {
        ConcurrentMap<Integer, PendingMessage> map = pendingMessages.get(channel);
        if (map != null) {
            PendingMessage pending = map.remove(seqId);
            if (pending != null) {
                pending.cancelTimeout(); // 取消重传定时器
            }
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

- 消息ACK有两种模式：**服务端ACK**（消息到达服务器就回ACK）和**端到端ACK**（消息到达接收方才回ACK）。IM系统通常两者都有
- 已读回执和消息ACK不同：ACK是"消息到达"，已读回执是"用户看了消息"。微信已读回执只在企业微信中有
- 群消息广播不要循环单发，应该使用ChannelGroup的writeAndFlush，它会批量发送

### 第14集：IM的群聊消息广播怎么实现？ChannelGroup是什么？

**💡 核心回答：**

`ChannelGroup` 是 Netty 提供的 Channel 集合，核心特性：
1. 线程安全：内部使用 `ConcurrentSet`
2. 批量操作：`writeAndFlush()` 会遍历所有Channel逐个发送
3. 自动清理：Channel关闭时自动从Group中移除
4. 全局Group：使用 `GlobalEventExecutor` 的Group可以跨EventLoop

**📦 实际例子：**

```java
public class GroupChatManager {
    // groupId → ChannelGroup
    private final ConcurrentMap<String, ChannelGroup> groupChannels = 
        new ConcurrentHashMap<>();
    
    // 用户加入群聊
    public void joinGroup(String groupId, Channel channel) {
        ChannelGroup group = groupChannels.computeIfAbsent(groupId, 
            k -> new DefaultChannelGroup(groupId, GlobalEventExecutor.INSTANCE));
        group.add(channel);
        
        // 记录用户加入了哪些群（用于断开连接时清理）
        Set<String> userGroups = getUserGroups(channel);
        userGroups.add(groupId);
    }
    
    // 用户离开群聊
    public void leaveGroup(String groupId, Channel channel) {
        ChannelGroup group = groupChannels.get(groupId);
        if (group != null) {
            group.remove(channel);
        }
    }
    
    // 群消息广播
    public void broadcastGroupMessage(String groupId, ImMessage msg) {
        ChannelGroup group = groupChannels.get(groupId);
        if (group == null) return;
        
        // 群消息广播：遍历所有群成员
        // ChannelGroup.writeAndFlush() 会为每个Channel调用 writeAndFlush
        // 每个 writeAndFlush 是异步的，不会阻塞
        for (Channel memberChannel : group) {
            if (memberChannel.isActive()) {
                String userId = memberChannel.attr(USER_ID).get();
                String senderId = msg.getBody().getFromUserId();
                
                // 不发给发送者自己
                if (!userId.equals(senderId)) {
                    memberChannel.writeAndFlush(msg.retain());
                }
            }
        }
        // 最后释放原始消息
        ReferenceCountUtil.release(msg);
    }
    
    // 用户断开连接时，从所有群中移除
    public void onChannelClose(Channel channel) {
        Set<String> userGroups = getUserGroups(channel);
        for (String groupId : userGroups) {
            ChannelGroup group = groupChannels.get(groupId);
            if (group != null) {
                group.remove(channel);
            }
        }
    }
}
```

`DefaultChannelGroup` 的核心实现：

```java
// DefaultChannelGroup.java
public class DefaultChannelGroup implements ChannelGroup {
    
    // 内部使用 ConcurrentSet 存储 Channel
    // 基于 ConcurrentHashMap.newKeySet() 实现
    private final Set<Channel> serverChannels = 
        Collections.newSetFromMap(new ConcurrentHashMap<Channel, Boolean>());
    private final Set<Channel> childChannels = 
        Collections.newSetFromMap(new ConcurrentHashMap<Channel, Boolean>());
    
    @Override
    public ChannelGroupFuture writeAndFlush(Object message) {
        // 遍历所有Channel，逐个writeAndFlush
        Set<Channel> channels = channels();
        ChannelGroupFuture future = new DefaultChannelGroupFuture(channels, executor);
        
        for (Channel channel : channels) {
            if (channel.isActive()) {
                // 每个Channel的writeAndFlush是异步操作
                ChannelFuture f = channel.writeAndFlush(message);
                // 监听每个Channel的发送结果
                f.addListener(new ChannelGroupFutureListener(channel, future));
            }
        }
        return future;
    }
    
    @Override
    public boolean add(Channel channel) {
        // 添加到集合中
        // Channel关闭时，通过ChannelFutureListener自动移除
        boolean added = childChannels.add(channel);
        if (added) {
            channel.closeFuture().addListener(f -> remove(channel));
        }
        return added;
    }
}
```

**⚠️ 常见坑/加分回答：**

- `ChannelGroup.writeAndFlush()` 传入的消息对象，对每个Channel都会调用一次writeAndFlush。如果消息是ByteBuf，需要手动retain，否则第一个Channel消费后就release了，后面的Channel就报错了
- 大群广播（1000+成员）可能造成瞬间大量写操作。优化方案：分批发送、或者使用消息队列异步处理
- ChannelGroup是本地内存结构，不支持跨服务器。分布式IM需要结合Redis Pub/Sub或MQ来实现跨节点的群消息广播

### 第15集：离线消息怎么存储和推送？用户上线时如何拉取历史消息？

**💡 核心回答：**

离线消息的流程：
1. 消息发送时，如果接收方不在线，存入离线消息表
2. 用户上线时，服务端检查是否有离线消息
3. 有离线消息：按时间顺序批量推送给客户端
4. 客户端确认后，标记已读/已拉取

**📦 实际例子：**

用户上线时的离线消息推送：

```java
public class OnlineHandler extends SimpleChannelInboundHandler<ImMessage> {
    
    @Override
    public void channelActive(ChannelHandlerContext ctx) {
        // 连接建立后，在认证成功时触发离线消息推送
    }
    
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        if (msg.getCmd() == ImProtocol.CMD_LOGIN) {
            // 认证成功后的逻辑
            String userId = ctx.channel().attr(USER_ID).get();
            
            // 异步推送离线消息（不阻塞EventLoop）
            ctx.executor().execute(() -> {
                pushOfflineMessages(userId, ctx.channel());
            });
        }
    }
    
    private void pushOfflineMessages(String userId, Channel channel) {
        // 1. 查询离线消息（按时间排序）
        List<OfflineMessage> offlineMsgs = 
            messageStore.getOfflineMessages(userId);
        
        if (offlineMsgs.isEmpty()) {
            return;
        }
        
        System.out.println("推送 " + offlineMsgs.size() + 
            " 条离线消息给用户 " + userId);
        
        // 2. 批量推送（控制发送速率，避免瞬间冲垮连接）
        int batchSize = 50; // 每批50条
        for (int i = 0; i < offlineMsgs.size(); i += batchSize) {
            int end = Math.min(i + batchSize, offlineMsgs.size());
            List<OfflineMessage> batch = offlineMsgs.subList(i, end);
            
            for (OfflineMessage offlineMsg : batch) {
                ImMessage imMsg = buildMessage(offlineMsg);
                channel.write(imMsg); // 注意：先write，不flush
            }
            channel.flush(); // 一批flush一次，减少系统调用
            
            // 批次间加一点间隔（可选，防止对端缓冲区溢出）
        }
        
        // 3. 客户端确认收到后，删除离线消息
        // （通过ACK机制保证）
    }
}
```

### 第16集：Netty的EPOLL优化有哪些？EPOLLONESHOT和Edge Triggered是什么？

**💡 核心回答：**

Netty在Linux上提供了两种Epoll实现：
- `NioEventLoopGroup + NioServerSocketChannel`：基于JDK的Selector（跨平台）
- `EpollEventLoopGroup + EpollServerSocketChannel`：基于Linux原生epoll（Netty自己封装）

Netty的Epoll实现做了以下优化：

| 优化点 | JDK NIO | Netty Epoll |
|--------|---------|-------------|
| 触发模式 | Level Triggered (LT) | **Edge Triggered (ET)** |
| EPOLLONESHOT | 不支持 | **支持** |
| selectedKeys | JDK HashSet | **自定义数组（SelectedSelectionKeySet）** |
| JNI调用 | 通过JDK封装 | **直接JNI调用** |

**📦 实际例子：**

IM服务器使用Netty原生Epoll（Linux部署时）：

```java
public class ImServer {
    public void start(int port) {
        final EventLoopGroup bossGroup;
        final EventLoopGroup workerGroup;
        final Class<? extends ServerChannel> channelClass;
        
        // 检测是否支持Epoll（Linux环境）
        if (Epoll.isAvailable()) {
            bossGroup = new EpollEventLoopGroup(1);
            workerGroup = new EpollEventLoopGroup();
            channelClass = EpollServerSocketChannel.class;
            System.out.println("Using Netty native Epoll");
        } else {
            bossGroup = new NioEventLoopGroup(1);
            workerGroup = new NioEventLoopGroup();
            channelClass = NioServerSocketChannel.class;
            System.out.println("Using JDK NIO (Epoll not available)");
        }
        
        ServerBootstrap bootstrap = new ServerBootstrap();
        bootstrap.group(bossGroup, workerGroup)
            .channel(channelClass)
            // Epoll专属选项
            .option(EpollChannelOption.EPOLL_MODE, EpollMode.EDGE_TRIGGERED)
            // TCP优化
            .childOption(ChannelOption.SO_KEEPALIVE, true)
            .childOption(ChannelOption.TCP_NODELAY, true)
            .childOption(ChannelOption.SO_BACKLOG, 1024)
            .childHandler(new ImServerInitializer());
        
        bootstrap.bind(port).sync();
    }
}
```

**🔍 源码解析：**

Edge Triggered vs Level Triggered：

```
Level Triggered (LT) - JDK NIO默认：
  只要Socket缓冲区有数据，epoll_wait()就会一直返回该Channel的读事件
  → 需要一次性读完所有数据（while循环read直到返回-1/EAGAIN）
  → 简单但可能造成某个Channel独占EventLoop线程

Edge Triggered (ET) - Netty Epoll优化：
  只有Socket缓冲区状态发生变化（新数据到来）时，epoll_wait()才返回
  → 必须在一次通知中读完所有数据（或注册EPOLLOUT等下次再读）
  → 更高效：不会反复通知同一个Channel
  → 但编程复杂度高，需要配合非阻塞IO循环读取

EPOLLONESHOT：
  每个fd（Channel）在同一时刻只会被一个线程处理
  → 避免多个EventLoop线程同时处理同一个Channel
  → 减少锁竞争

// Netty Epoll的native方法调用
// EpollEventLoop.java
private int epollWait() {
    // 直接JNI调用Linux epoll_wait
    // int epoll_wait(int epfd, struct epoll_event *events, 
    //                int maxevents, int timeout);
    return Native.epollWait(epollFd, events, timerFd);
}
```

**⚠️ 常见坑/加分回答：**

- Netty的Epoll只在Linux上可用，Mac/Windows上回退到NIO。开发环境可能是Mac，生产环境是Linux，要注意兼容性代码
- `EpollMode.EDGE_TRIGGERED` 是Netty的默认值，不需要手动设置
- `SO_BACKLOG` 设置的是Accept队列大小。10万连接的IM系统建议设1024~2048，防止突发连接时队列溢出
- `TCP_NODELAY` 禁用Nagle算法：IM消息要求低延迟，不应该等待凑够一批再发送

### 第17集：Netty启动流程的源码是怎样的？从bind()到处理第一个请求经历了什么？

**💡 核心回答：**

Netty启动的核心流程：

```
1. 创建EventLoopGroup（Boss + Worker）
2. 创建ServerBootstrap并配置参数
3. bootstrap.bind(port)
   ├─ 3.1 反射创建NioServerSocketChannel
   ├─ 3.2 初始化Channel（设置参数、添加Handler）
   ├─ 3.3 将Channel注册到Boss的EventLoop
   │       └─ 底层：ServerSocketChannel.open() + selector.register()
   ├─ 3.4 绑定端口
   │       └─ 底层：ServerSocketChannel.bind()
   └─ 3.5 开始Accept循环
           └─ Boss的EventLoop开始epoll_wait()
4. 客户端连接到来
   ├─ Boss的EventLoop检测到OP_ACCEPT
   ├─ 调用ServerSocketChannel.accept()获取SocketChannel
   └─ 将SocketChannel注册到Worker的某个EventLoop
       └─ 底层：SocketChannel.register(workerSelector, OP_READ)
5. 客户端发送数据
   └─ Worker的EventLoop检测到OP_READ
       └─ 触发Pipeline的channelRead事件链
```

**🔍 源码解析：**

关键步骤的源码追踪：

```java
    for (SocketChannel channel : acceptedChannels) {

        pipeline.fireChannelRead(new NioSocketChannel(channel));

    pipeline.fireChannelReadComplete();
}
```

- `ServerBootstrapAcceptor` 是Netty自动添加的"桥梁Handler"，它的作用就是把Boss Accept到的新连接注册到Worker。理解这个Handler就能理解主从多线程模型的本质
- Channel的创建时机是在`bind()`时，不是`new ServerBootstrap()`时
- 注册是异步的：`channel.register(eventLoop)` 返回的是 `ChannelFuture`，注册可能在另一个线程中完成

### 第18集：ChannelPipeline中的事件传播机制是怎样的？异常如何处理？

**💡 核心回答：**

Pipeline中的事件传播分为两个方向：
- **入站（Inbound）**：从Head到Tail，处理读事件（channelRead）
- **出站（Outbound）**：从Tail到Head，处理写事件（write）

传播机制是**责任链模式**：每个Handler处理完自己的逻辑后，调用`ctx.fireChannelRead(msg)`将事件传递给下一个Handler。如果不调用，事件就到此为止（被消费了）。

**📦 实际例子：**

```java
// Pipeline中的事件传播示例
public class ImMessageDecoder extends ByteToMessageDecoder {
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        // ...解码逻辑...
        out.add(imMessage); // 添加到out，会自动fire到下一个Handler
    }
}

public class AuthHandler extends SimpleChannelInboundHandler<ImMessage> {
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        if (msg.getCmd() == ImProtocol.CMD_LOGIN) {
            // 处理登录
            handleLogin(ctx, msg);
            // 注意：channelRead0执行完后，消息会被自动release
            // 且不会传递给下一个Handler（因为SimpleChannelInboundHandler
            // 在channelRead中处理完后不调用fireChannelRead）
        }
    }
}

public class BusinessHandler extends SimpleChannelInboundHandler<ImMessage> {
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        switch (msg.getCmd()) {
            case ImProtocol.CMD_CHAT:
                handleChat(ctx, msg);
                break;
            case ImProtocol.CMD_GROUP_MSG:
                handleGroupMsg(ctx, msg);
                break;
        }
        // 消息到此为止，不会再传递给下一个Handler
    }
}

// 异常传播
public class ExceptionHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
        System.err.println("IM Server Error: " + cause.getMessage());
        cause.printStackTrace();
        
        // 记录异常信息（用户ID、Channel等）
        String userId = ctx.channel().attr(USER_ID).get();
        log.error("Error on channel for user: " + userId, cause);
        
        // 关闭连接（大部分异常都应该关闭连接，防止状态不一致）
        ctx.close();
    }
}
```

**🔍 源码解析：**

Pipeline事件传播的源码：

```java
// DefaultChannelPipeline.java

// 入站事件传播（以channelRead为例）
public ChannelPipeline fireChannelRead(Object msg) {
    // 从HeadContext开始传播
    AbstractChannelHandlerContext.invokeChannelRead(head, msg);
    return this;
}

// AbstractChannelHandlerContext.java
static void invokeChannelRead(final AbstractChannelHandlerContext next, Object msg) {
    final Object m = next.filterMsg(msg);
    
    // 获取next对应的EventLoop
    EventExecutor executor = next.executor();
    if (executor.inEventLoop()) {
        // 当前线程就是EventLoop线程，直接调用
        next.invokeChannelRead(m);
    } else {
        // 不在EventLoop线程，提交到EventLoop线程执行
        executor.execute(new Runnable() {
            public void run() {
                next.invokeChannelRead(m);
            }
        });
    }
}

private void invokeChannelRead(Object msg) {
    if (invokeHandler()) {
        // 获取Handler实例，调用其channelRead方法
        ChannelHandler handler = handler();
        if (handler instanceof ChannelInboundHandler) {
            ((ChannelInboundHandler) handler).channelRead(this, msg);
        }
    }
}

// Handler处理完后，调用ctx.fireChannelRead()传递给下一个
// ChannelInboundHandlerAdapter.java
public void channelRead(ChannelHandlerContext ctx, Object msg) {
    // 默认实现：直接传递给下一个Handler
    ctx.fireChannelRead(msg);
}

// 出站事件传播
public ChannelFuture write(Object msg) {
    // 从Tail开始，往Head方向传播
    return tail.write(msg);
}

// 异常传播
public ChannelPipeline fireExceptionCaught(Throwable cause) {
    // 异常事件从Head开始传播
    AbstractChannelHandlerContext.invokeExceptionCaught(head, cause);
    return this;
}

// 如果异常传播到Tail还没被处理，会打印日志
// TailContext.exceptionCaught()
public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) {
    // 没有Handler处理异常，打印警告
    onUnhandledInboundException(cause);
}
```

**⚠️ 常见坑/加分回答：**

- **异常必须被处理**：如果Pipeline中没有任何Handler重写了`exceptionCaught()`，异常会传播到Tail然后被丢弃（只打印日志），客户端可能一直等待响应
- `ctx.write()` vs `ctx.channel().write()` 的区别：ctx.write()从当前Handler开始往后传播，ctx.channel().write()从Tail开始传播。通常用ctx版本，跳过已经处理过的Handler
- `fireChannelRead()` 和 `ctx.write()` 的方向是相反的，记住：入站Head→Tail，出站Tail→Head

## 第六系列：IM系统进阶与性能优化

### 第19集：IM系统如何支持10万+长连接？Netty层面需要哪些优化？

**💡 核心回答：**

支撑10万+长连接的优化分为多个层面：

| 层面 | 优化措施 |
|------|---------|
| **操作系统** | 调大文件描述符限制、TCP参数调优、epoll优化 |
| **Netty** | 内存池化、EventLoop数量调优、ByteBuf直接内存、减少GC |
| **协议** | 精简协议头部、Protobuf序列化、压缩 |
| **架构** | 多节点部署、连接层与业务层分离 |

**📦 实际例子：**

IM服务器的完整优化配置：

```java
public class OptimizedImServer {
    public void start(int port) {
        EventLoopGroup bossGroup = new NioEventLoopGroup(1);
        
        // Worker线程数调优
        // 对于10万连接、消息处理较轻的场景，可以增大Worker线程数
        EventLoopGroup workerGroup = new NioEventLoopGroup(
            Math.min(Runtime.getRuntime().availableProcessors() * 2, 32));
        
        // 业务线程池（处理重逻辑：消息存储、转发）
        EventExecutorGroup businessGroup = new DefaultEventExecutorGroup(64);
        
        ServerBootstrap bootstrap = new ServerBootstrap();
        bootstrap.group(bossGroup, workerGroup)
            .channel(NioServerSocketChannel.class)
            
            // ===== 连接层优化 =====
            // Accept队列大小
            .option(ChannelOption.SO_BACKLOG, 2048)
            
            // ===== IO层优化 =====
            // 发送缓冲区（适当增大）
            .childOption(ChannelOption.SO_SNDBUF, 64 * 1024)
            // 接收缓冲区
            .childOption(ChannelOption.SO_RCVBUF, 64 * 1024)
            // 禁用Nagle算法（降低延迟）
            .childOption(ChannelOption.TCP_NODELAY, true)
            // TCP KeepAlive（OS层面的保活）
            .childOption(ChannelOption.SO_KEEPALIVE, true)
            // 允许端口重用
            .option(ChannelOption.SO_REUSEADDR, true)
            
            // ===== 内存优化 =====
            // 写缓冲区高水位线（超过后触发不可写事件）
            .childOption(ChannelOption.WRITE_BUFFER_WATER_MARK, 
                new WriteBufferWaterMark(32 * 1024, 64 * 1024))
            
            // ===== Pipeline配置 =====
            .childHandler(new ChannelInitializer<SocketChannel>() {
                @Override
                protected void initChannel(SocketChannel ch) {
                    ChannelPipeline pipeline = ch.pipeline();
                    
                    // 空闲检测（读60秒，写30秒）
                    pipeline.addLast(new IdleStateHandler(60, 30, 0, 
                        TimeUnit.SECONDS));
                    
                    // 协议解码
                    pipeline.addLast(new ImFrameDecoder());
                    pipeline.addLast(new ImMessageDecoder());
                    
                    // 协议编码
                    pipeline.addLast(new ImMessageEncoder());
                    
                    // 心跳处理
                    pipeline.addLast(new HeartbeatHandler());
                    
                    // 认证
                    pipeline.addLast(new AuthHandler());
                    
                    // 业务处理（使用独立线程池）
                    pipeline.addLast(businessGroup, "business", 
                        new ImBusinessHandler());
                    
                    // 异常处理
                    pipeline.addLast(new ImExceptionHandler());
                }
            });
        
        bootstrap.bind(port).sync();
    }
}
```

操作系统层面的优化（/etc/sysctl.conf）：

```bash
# 最大文件描述符（每个TCP连接占一个FD）
fs.file-max = 1000000
```

**⚠️ 常见坑/加分回答：**

- **文件描述符是10万连接的第一道坎**：Linux默认ulimit -n是1024，必须调到200000以上。每个TCP连接占一个FD，加上日志文件、数据库连接等，10万连接至少需要150000的FD限制
- 内存消耗估算：每个连接约消耗10~20KB（读缓冲区+写缓冲区+Channel对象），10万连接约1~2GB。加上JVM堆内存，建议服务器至少8GB内存
- **写缓冲区水位线**很重要：如果客户端网络差，消息堆积在写缓冲区，不及时清理会OOM。超过高水位线后，调用`channel.isWritable()`检查，不写或直接关闭连接

### 第20集：什么是写缓冲区水位线？IM系统中如何防止消息堆积导致OOM？

**💡 核心回答：**

Netty的写缓冲区水位线（WriteBufferWaterMark）是防止内存溢出的重要机制：

- **低水位线（lowWaterMark）**：写缓冲区字节数低于此值时，Channel变为可写（`isWritable()=true`）
- **高水位线（highWaterMark）**：写缓冲区字节数超过此值时，Channel变为不可写（`isWritable()=false`），触发`channelWritabilityChanged`事件

默认值：低32KB，高64KB。

**📦 实际例子：**

```java
// 发送消息前检查Channel是否可写
public void sendMessage(Channel channel, ImMessage msg) {
    if (!channel.isWritable()) {
        // 写缓冲区已满（超过高水位线），停止发送
        log.warn("Channel writability low, user: " + 
            channel.attr(USER_ID).get());
        
        // 可选策略：
        // 1. 丢弃消息（实时性要求高的场景）
        // 2. 存入队列等待（可靠性要求高的场景）
        // 3. 关闭连接（长时间不可写说明网络有问题）
        return;
    }
    
    channel.writeAndFlush(msg);
}

// 监听Channel可写性变化事件
public class WritabilityHandler extends ChannelInboundHandlerAdapter {
    @Override
    public void channelWritabilityChanged(ChannelHandlerContext ctx) {
        Channel channel = ctx.channel();
        boolean writable = channel.isWritable();
        
        if (!writable) {
            // Channel不可写：可能客户端网络差，消息堆积
            log.warn("Channel不可写: " + channel.attr(USER_ID).get());
            
            // 启动监控定时器：如果持续不可写超过30秒，关闭连接
            ctx.executor().schedule(() -> {
                if (!channel.isWritable() && channel.isActive()) {
                    log.error("Channel持续不可写，强制关闭");
                    channel.close();
                }
            }, 30, TimeUnit.SECONDS);
        } else {
            // Channel恢复可写：可以继续发送积压的消息
            log.info("Channel恢复可写: " + channel.attr(USER_ID).get());
        }
        
        // 传递给下一个Handler
        ctx.fireChannelWritabilityChanged();
    }
}
```

**🔍 源码解析：**

水位线的触发机制：

```java
// AbstractChannel.java
private volatile boolean autoRead = true;

// DefaultChannelPipeline.java
// 写操作时检查水位线
public ChannelFuture writeAndFlush(Object msg) {
    // ... 写操作 ...
    
    // 写完后检查缓冲区大小
    // ChannelOutboundBuffer.java
    public void addMessage(Object msg, ...) {
        // 更新总字节数
        totalPendingSize += msgSize;
        
        // 检查是否超过高水位线
        if (totalPendingSize >= highWaterMark) {
            // 标记为不可写
            channel.unsafe().doClose(); // 或触发channelWritabilityChanged
            // 实际上是通过Unsafe来设置 writability = false
        }
    }
    
    public void removeEntry(Entry entry) {
        totalPendingSize -= entry.pendingSize;
        
        // 检查是否降到低水位线以下
        if (totalPendingSize <= lowWaterMark) {
            // 恢复为可写
            // 触发 channelWritabilityChanged 事件
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

- 默认64KB高水位线对于IM系统可能太小：一条图片消息可能就有几百KB。建议根据实际消息大小调整，比如设为512KB~1MB
- 水位线只是**通知机制**，不会自动停止写入。必须自己检查`channel.isWritable()`并做出相应处理
- IM系统中的"慢客户端"问题：某个用户网络很差，消息发不过去，一直在写缓冲区堆积。如果不处理，不仅影响该用户，还可能影响整个EventLoop上的其他连接

### 第21集：Netty的线程安全模型是怎样的？为什么在Handler中不需要加锁？

**💡 核心回答：**

Netty的线程安全模型核心原则：**一个Channel的所有IO事件都在同一个EventLoop线程中处理**。

这意味着：
- 同一个Channel的`channelRead`、`channelActive`、`channelInactive`等方法都在同一个线程中调用
- Handler中操作Channel的属性（Attr）、Pipeline等都是线程安全的（因为只有一个线程在操作）
- 不需要加锁！这就是Netty的高性能设计

**📦 实际例子：**

```java
public class ImBusinessHandler extends SimpleChannelInboundHandler<ImMessage> {
    
    // 不需要volatile，不需要加锁
    // 因为所有方法都在同一个EventLoop线程中执行
    private int messageCount = 0;
    private long lastMessageTime = 0;
    
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        messageCount++;  // 线程安全！只有一个线程在调用
        lastMessageTime = System.currentTimeMillis();
        
        // 处理消息
        handleMessage(ctx, msg);
    }
    
    @Override
    public void channelInactive(ChannelHandlerContext ctx) {
        // 也是同一个线程，可以直接访问messageCount
        System.out.println("用户断开，共发送" + messageCount + "条消息");
    }
}
```

跨Channel操作才需要注意线程安全：

```java
// ❌ 错误：直接访问另一个Channel的属性（可能在另一个EventLoop线程中）
public void forwardMessage(Channel fromChannel, Channel toChannel, ImMessage msg) {
    // toChannel可能在另一个EventLoop线程中
    // 直接操作toChannel的属性可能线程不安全
    String userId = toChannel.attr(USER_ID).get(); // Attr本身是线程安全的
    toChannel.writeAndFlush(msg); // writeAndFlush本身是线程安全的
}

// ✅ 正确：通过EventLoop.execute()提交到目标Channel的线程
public void forwardMessageSafe(Channel toChannel, ImMessage msg) {
    EventLoop eventLoop = toChannel.eventLoop();
    if (eventLoop.inEventLoop()) {
        // 已经在同一个EventLoop线程中，直接操作
        toChannel.writeAndFlush(msg);
    } else {
        // 不在同一个线程，提交到目标EventLoop
        eventLoop.execute(() -> {
            toChannel.writeAndFlush(msg);
        });
    }
}

// 但实际上，channel.writeAndFlush() 内部已经做了线程安全处理
// 如果不在EventLoop线程中调用，会自动封装为Task提交到EventLoop
// 所以直接调用channel.writeAndFlush()也是安全的
```

**🔍 源码解析：**

`writeAndFlush` 的线程安全实现：

```java
// AbstractChannelHandlerContext.java
public ChannelFuture writeAndFlush(Object msg) {
    // 创建WriteAndFlushTask
    return writeAndFlush(msg, newPromise());
}

private ChannelFuture writeAndFlush(Object msg, ChannelPromise promise) {
    // 检查是否应该直接调用
    if (invokeNow()) {
        // invokeNow() = executor.inEventLoop() && !removed
        // 如果在EventLoop线程中，直接执行
        invokeWriteAndFlush(msg, promise);
    } else {
        // 不在EventLoop线程中，提交到EventLoop线程
        // 通过EventLoop.execute()确保在正确的线程中执行
        AbstractWriteTask task = WriteAndFlushTask.newInstance(this, msg, promise);
        executor().execute(task);
    }
}
```

**⚠️ 常见坑/加分回答：**

- "不需要加锁"仅限于**操作同一个Channel的内部状态**。如果要操作多个Channel共享的数据结构（如全局用户表），仍然需要线程安全
- `eventLoop.execute()` 和 `eventLoop.submit()` 的区别：execute没有返回值，submit返回Future。Netty内部更推荐用execute
- 业务Handler使用了独立的EventExecutorGroup时，该Handler的所有方法在**业务线程池**的某个线程中执行，而不是IO线程。这是IM系统将重逻辑从IO线程分离的关键

### 第22集：Netty中如何优雅地关闭连接？连接断开时要做哪些清理？

**💡 核心回答：**

优雅关闭连接的步骤：
1. 停止接收新消息（设置Channel为非可读）
2. 发送完缓冲区中的剩余消息
3. 发送关闭通知给对方
4. 等待对方确认或超时
5. 清理服务端资源（用户映射、群组、定时任务等）

**📦 实际例子：**

```java
public class ConnectionCleanupHandler extends ChannelInboundHandlerAdapter {
    
    @Override
    public void channelInactive(ChannelHandlerContext ctx) {
        Channel channel = ctx.channel();
        String userId = channel.attr(USER_ID).get();
        
        if (userId != null) {
            System.out.println("用户断开连接: " + userId);
            
            // 1. 从在线用户表中移除
            ChannelManager.getInstance().removeChannel(userId);
            
            // 2. 从所有群组中移除
            GroupChatManager.getInstance().onChannelClose(channel);
            
            // 3. 取消该用户的所有定时任务
            // （如果有的话）
            
            // 4. 通知好友/联系人（可选：发送下线通知）
            notifyContactsOffline(userId);
            
            // 5. 清理待发送队列
            PendingMessageManager.getInstance().clearPending(channel);
        }
        
        // 传递给下一个Handler
        ctx.fireChannelInactive();
    }
    
    // 优雅关闭连接（服务端主动关闭）
    public static void gracefulClose(Channel channel, String reason) {
        // 1. 发送关闭通知
        ImMessage closeMsg = buildCloseMessage(reason);
        
        // 2. 监听发送完成
        channel.writeAndFlush(closeMsg).addListener(future -> {
            if (future.isSuccess()) {
                // 3. 等待一小段时间确保数据发出
                channel.eventLoop().schedule(() -> {
                    // 4. 关闭连接
                    channel.close();
                }, 100, TimeUnit.MILLISECONDS);
            } else {
                // 发送失败，直接关闭
                channel.close();
            }
        });
    }
}
```

**⚠️ 常见坑/加分回答：**

- `channelInactive` 在连接**已经断开后**才被调用，不要在这里发送消息给客户端
- 客户端异常断开（如拔网线）时，服务端不会立刻感知，要等心跳超时或TCP KeepAlive超时才会触发`channelInactive`。这就是为什么心跳机制很重要
- 清理操作要放在`channelInactive`中而不是`exceptionCaught`中，因为正常关闭也会触发`channelInactive`，而`exceptionCaught`只在异常时触发

### 第23集：IM系统中如何实现消息的序列化？Protobuf和JSON怎么选？

**💡 核心回答：**

| 特性 | Protobuf | JSON |
|------|----------|------|
| 编码大小 | 小（二进制，通常1/3~1/5） | 大（文本） |
| 编码速度 | 快 | 慢 |
| 可读性 | 差（二进制） | 好（文本） |
| 跨语言 | 好（.proto定义） | 好 |
| 动态类型 | 差（需要预定义） | 好 |
| 调试难度 | 难 | 易 |

IM系统推荐**Protobuf**：
- 10万连接下，消息量大，Protobuf体积小可以节省带宽
- 编解码速度快，减少CPU消耗
- 强类型约束，减少序列化/反序列化错误

**📦 实际例子：**

Protobuf消息定义：

```protobuf

}
```

在Netty中使用Protobuf编解码：

```java
// 使用Netty内置的Protobuf编解码器
pipeline.addLast(new ProtobufVarint32FrameDecoder());
pipeline.addLast(new ProtobufDecoder(ImMessageProto.getDefaultInstance()));
pipeline.addLast(new ProtobufVarint32LengthFieldPrepender());
pipeline.addLast(new ProtobufEncoder());

// 或者自定义：先用自己的协议框架拆帧，再手动反序列化Protobuf
public class ImMessageDecoder extends ByteToMessageDecoder {
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) 
            throws Exception {
        // 1. 读取协议头（自定义格式）
        if (in.readableBytes() < ImProtocol.HEADER_LENGTH) return;
        
        in.markReaderIndex();
        int magic = in.readInt();
        byte version = in.readByte();
        short cmd = in.readShort();
        int seqId = in.readInt();
        int bodyLength = in.readInt();
        
        if (in.readableBytes() < bodyLength) {
            in.resetReaderIndex();
            return;
        }
        
        byte[] bodyBytes = new byte[bodyLength];
        in.readBytes(bodyBytes);
        
        // 2. 根据cmd类型反序列化不同的Protobuf消息
        Object body = null;
        switch (cmd) {
            case ImProtocol.CMD_LOGIN:
                body = LoginMessage.parseFrom(bodyBytes);
                break;
            case ImProtocol.CMD_CHAT:
                body = ChatMessage.parseFrom(bodyBytes);
                break;
            case ImProtocol.CMD_ACK:
                body = AckMessage.parseFrom(bodyBytes);
                break;
            case ImProtocol.CMD_HEARTBEAT:
                body = HeartbeatMessage.parseFrom(bodyBytes);
                break;
            case ImProtocol.CMD_READ_RECEIPT:
                body = ReadReceipt.parseFrom(bodyBytes);
                break;
        }
        
        // 3. 构建IM消息对象
        ImMessage message = new ImMessage();
        message.setMagic(magic);
        message.setVersion(version);
        message.setCmd(cmd);
        message.setSeqId(seqId);
        message.setBodyObject(body);
        
        out.add(message);
    }
}
```

- Protobuf的`bytes`类型在Java中对应`ByteString`，不是`byte[]`。注意转换
- Protobuf3移除了`required`关键字，所有字段默认optional。需要在业务层做非空校验
- 如果团队不熟悉Protobuf，可以先用JSON快速开发，后期再迁移。Netty的Pipeline设计使得替换编解码器非常方便

### 第24集：IM系统中如何处理粘包拆包？实际测试中会遇到什么？

**💡 核心回答：**

粘包拆包不是Bug，是TCP的正常行为。IM系统中必须正确处理，否则：
- 粘包：两条消息合并，解码失败
- 拆包：一条消息只收到一半，解码失败

处理方案就是前面提到的`LengthFieldBasedFrameDecoder`或自定义解码器。

**📦 实际例子：**

测试粘包拆包的模拟场景：

```java

    channel.writeAndFlush(encodeMessage(msg2));
    
    // 服务端可能一次read()收到两条消息的数据
    // 正确的解码器应该能拆分成两条消息
}

    channel.writeAndFlush(encodeMessage(bigMsg));

    // 正确的解码器应该等待第二次数据到达后再解码
```

自定义帧解码器（处理粘包拆包）：

```java
public class ImFrameDecoder extends ByteToMessageDecoder {
    
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        while (in.readableBytes() >= ImProtocol.HEADER_LENGTH) {
            // 标记当前位置
            in.markReaderIndex();
            
            // 读取头部
            int magic = in.readInt();
            in.readByte();    // version
            in.readShort();   // cmd
            in.readInt();     // seqId
            int bodyLength = in.readInt();
            
            // 回退到头部之前
            in.resetReaderIndex();
            
            // 计算完整帧长度
            int frameLength = ImProtocol.HEADER_LENGTH + bodyLength;
            
            // 检查数据是否完整
            if (in.readableBytes() < frameLength) {
                // 数据不完整，等待下次
                return;
            }
            
            // 数据完整，读取整个帧（不修改readerIndex）
            ByteBuf frame = in.readRetainedSlice(frameLength);
            out.add(frame);
            
            // 继续循环：可能还有下一条消息（粘包场景）
        }
    }
}
```

**⚠️ 常见坑/加分回答：**

- 粘包拆包在**局域网测试时可能不出现**（因为网络快，消息容易完整到达），到了**生产环境/弱网环境**才暴露。这是IM系统最常见的线上Bug之一
- 测试时可以用 `TrafficShapingHandler` 模拟弱网：

```java

    0,        // 写带宽限制（0=不限制）
    1024,     // 读带宽限制（1KB/s）
    100,      // 检查间隔（ms）
    500       // 最大延迟（ms）
));
```

### 第25集：Netty中的内存泄漏如何排查？IM系统的内存优化策略有哪些？

**💡 核心回答：**

Netty内存泄漏的常见原因：
1. ByteBuf没有release()
2. Handler链中消息传递中断（没调fireChannelRead也没release）
3. 群发时retain/release不匹配
4. 自定义Decoder中创建的ByteBuf没有释放

**📦 实际例子：**

排查内存泄漏的方法：

```java
// 1. 开启内存泄漏检测
// JVM启动参数：
// -Dio.netty.leakDetection.level=PARANOID  // 最严格，每次分配都追踪
// -Dio.netty.leakDetection.level=ADVANCED  // 生产推荐，采样追踪

// 2. 在代码中添加泄漏检测日志
// 开启后，Netty会在ByteBuf被GC回收时检查refCnt
// 如果refCnt != 0，说明内存泄漏，会打印分配时的调用栈

// 3. 手动追踪ByteBuf的生命周期
public class TrackedMessageHandler extends SimpleChannelInboundHandler<ImMessage> {
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        // SimpleChannelInboundHandler会自动release msg
        // 如果继承ChannelInboundHandlerAdapter，必须手动release
        
        processMessage(ctx, msg);
        // 方法结束后，msg.release()被自动调用
    }
}

public void processWithByteBuf(ChannelHandlerContext ctx, ByteBuf buf) {
    // 方式1：try-finally确保释放
    ByteBuf copy = buf.copy();
    try {
        // 使用copy
        processCopy(copy);
    } finally {
        copy.release(); // 确保释放
    }
    
    // 方式2：使用ReferenceCountUtil
    ReferenceCountUtil.release(buf);
}
```

IM系统的内存优化策略：

```java
// 1. 使用直接内存（减少堆内存→堆外内存拷贝）
ByteBuf directBuf = PooledByteBufAllocator.DEFAULT.directBuffer(256);

// 2. 消息转发使用slice零拷贝
public void forwardToMultiple(Channel[] channels, byte[] body) {
    ByteBuf shared = Unpooled.wrappedBuffer(body);
    for (Channel ch : channels) {
        ch.writeAndFlush(shared.retainedSlice()); // 零拷贝+引用安全
    }
    shared.release();
}

// 3. 复用ByteBuf（减少分配次数）
// ThreadLocal<ByteBuf> 复用编码缓冲区
private static final ThreadLocal<ByteBuf> ENCODE_BUFFER = 
    ThreadLocal.withInitial(() -> PooledByteBufAllocator.DEFAULT.heapBuffer(256));

public ByteBuf encodeWithReuse(ImMessage msg) {
    ByteBuf buf = ENCODE_BUFFER.get();
    buf.clear(); // 清空但保留内存
    // 编码...
    return buf; // 注意：返回后不能clear，需要调用方release或归还
}

// 4. 限制单连接最大缓存
// 通过WriteBufferWaterMark控制
pipeline.addLast(new WriteBufferWaterMarkHandler(32 * 1024, 256 * 1024));
```

**⚠️ 常见坑/加分回答：**

- PARANOID模式会严重影响性能（每次分配都记录调用栈），只在开发测试时使用
- 内存泄漏不一定是Netty ByteBuf的问题，也可能是业务代码中的对象泄漏（如ConcurrentHashMap中存储了大量不用的Channel）
- 使用JVM参数 `-Dio.netty.allocator.type=unpooled` 切换到非池化分配器可以帮助排查泄漏：非池化ByteBuf的泄漏更容易被JVM GC检测到

### 第26集：Netty的ChannelFuture是什么？异步编程模型在IM系统中如何应用？

**💡 核心回答：**

`ChannelFuture` 是 Netty 异步编程的核心：所有IO操作（connect、bind、write、close）都返回ChannelFuture，代表一个尚未完成的操作。

- `isDone()`：操作是否完成
- `isSuccess()`：操作是否成功
- `addListener()`：注册回调，操作完成时通知
- `sync()`：同步等待操作完成（阻塞当前线程）

**📦 实际例子：**

```java
// 1. 异步发送消息并监听结果
public void sendAndConfirm(Channel channel, ImMessage msg) {
    ChannelFuture future = channel.writeAndFlush(msg);
    
    future.addListener(f -> {
        if (f.isSuccess()) {
            log.debug("消息发送成功");
        } else {
            log.error("消息发送失败", f.cause());
            // 重试或存入离线队列
            retryOrOffline(msg);
        }
    });
}

// 2. 批量发送并等待全部完成
public void broadcastAndWait(List<Channel> channels, ImMessage msg) {
    // 使用ChannelGroupFuture等待所有Channel发送完成
    ChannelGroup group = new DefaultChannelGroup(GlobalEventExecutor.INSTANCE);
    channels.forEach(group::add);
    
    ChannelGroupFuture future = group.writeAndFlush(msg);
    future.addListener(f -> {
        // 所有Channel的发送都完成后回调
        int successCount = 0;
        for (ChannelFuture cf : f) {
            if (cf.isSuccess()) successCount++;
        }
        log.info("群发完成: {}/{} 成功", successCount, channels.size());
    });
}

// 3. 异步关闭连接
public void asyncClose(Channel channel) {
    channel.close().addListener(f -> {
        log.info("连接已关闭: " + channel.attr(USER_ID).get());
        // 关闭后的清理工作
    });
}
```

**⚠️ 常见坑/加分回答：**

- **严禁在EventLoop线程中调用sync()**：sync()会阻塞当前线程，如果当前线程是EventLoop线程，会造成死锁（EventLoop线程被阻塞，无法处理IO事件）
- `addListener()` 的回调在IO线程中执行，不要在回调中做耗时操作
- ChannelFuture是不可变的：一旦操作完成，结果不会改变

### 第27集：IM系统中如何实现断线重连？Netty客户端怎么配合？

**💡 核心回答：**

断线重连是IM客户端的核心功能。实现要点：
1. **指数退避重连**：重连间隔递增（1s→2s→4s→8s→...），避免服务端恢复时所有客户端同时重连
2. **心跳检测触发重连**：心跳超时认为连接断开
3. **重连后恢复状态**：拉取离线消息、恢复未确认消息
4. **限制最大重连次数**：避免无限重连

**📦 实际例子：**

```java
public class ImClient {
    private EventLoopGroup group;
    private Channel channel;
    private int retryCount = 0;
    private static final int MAX_RETRY = 12;
    private static final int BASE_DELAY = 1; // 秒
    
    public void connect(String host, int port) {
        group = new NioEventLoopGroup(1);
        Bootstrap bootstrap = new Bootstrap();
        bootstrap.group(group)
            .channel(NioSocketChannel.class)
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 5000)
            .handler(new ChannelInitializer<SocketChannel>() {
                @Override
                protected void initChannel(SocketChannel ch) {
                    ch.pipeline()
                        .addLast(new IdleStateHandler(0, 30, 0, TimeUnit.SECONDS))
                        .addLast(new ImFrameDecoder())
                        .addLast(new ImMessageDecoder())
                        .addLast(new ImMessageEncoder())
                        .addLast(new ImClientHandler(ImClient.this));
                }
            });
        
        doConnect(bootstrap, host, port);
    }
    
    private void doConnect(Bootstrap bootstrap, String host, int port) {
        ChannelFuture future = bootstrap.connect(host, port);
        
        future.addListener(f -> {
            if (f.isSuccess()) {
                channel = future.channel();
                retryCount = 0; // 重置重连计数
                System.out.println("连接成功");
                
                // 连接成功后发送登录消息
                sendLogin();
            } else {
                // 连接失败，触发重连
                scheduleReconnect(bootstrap, host, port);
            }
        });
    }
    
    private void scheduleReconnect(Bootstrap bootstrap, String host, int port) {
        if (retryCount >= MAX_RETRY) {
            System.out.println("超过最大重连次数，放弃重连");
            return;
        }
        
        retryCount++;
        // 指数退避：1s, 2s, 4s, 8s, 16s, 32s, 64s, 128s, 256s, 300s, 300s, 300s
        int delay = Math.min(BASE_DELAY * (1 << retryCount), 300);
        
        System.out.println("第" + retryCount + "次重连，" + delay + "秒后...");
        
        channel.eventLoop().schedule(() -> {
            doConnect(bootstrap, host, port);
        }, delay, TimeUnit.SECONDS);
    }
    
    // 连接断开时的处理
    public void onDisconnect() {
        System.out.println("连接断开，准备重连...");
        // 清理当前连接状态
        // 重连后需要重新登录、拉取离线消息
        scheduleReconnect(/* bootstrap, host, port */);
    }
}
```

**⚠️ 常见坑/加分回答：**

- 指数退避的最大值要封顶（如300秒），否则会无限增长
- 重连后必须重新认证（发送Login消息），不能直接发消息
- 重连后需要和服务端同步消息状态：哪些消息已收、哪些未收，避免消息丢失或重复

### 第28集：Netty中的ChannelOption有哪些？IM系统中常用的有哪些？

**💡 核心回答：**

| Option | 作用 | IM推荐值 |
|--------|------|---------|
| SO_BACKLOG | Accept队列大小 | 2048 |
| SO_KEEPALIVE | TCP KeepAlive | true |
| TCP_NODELAY | 禁用Nagle算法 | true |
| SO_REUSEADDR | 端口复用 | true |
| SO_SNDBUF | 发送缓冲区 | 64KB |
| SO_RCVBUF | 接收缓冲区 | 64KB |
| CONNECT_TIMEOUT_MILLIS | 连接超时 | 5000 |
| WRITE_BUFFER_WATER_MARK | 写缓冲水位线 | 32KB/256KB |
| ALLOCATOR | ByteBuf分配器 | Pooled |

**📦 实际例子：**

```java
ServerBootstrap bootstrap = new ServerBootstrap();
bootstrap
    // BossGroup的选项
    .option(ChannelOption.SO_BACKLOG, 2048)
    .option(ChannelOption.SO_REUSEADDR, true)
    
    // WorkerGroup/Channel的选项
    .childOption(ChannelOption.SO_KEEPALIVE, true)
    .childOption(ChannelOption.TCP_NODELAY, true)
    .childOption(ChannelOption.SO_SNDBUF, 64 * 1024)
    .childOption(ChannelOption.SO_RCVBUF, 64 * 1024)
    .childOption(ChannelOption.WRITE_BUFFER_WATER_MARK, 
        new WriteBufferWaterMark(32 * 1024, 256 * 1024))
    .childOption(ChannelOption.ALLOCATOR, PooledByteBufAllocator.DEFAULT);
```

**⚠️ 常见坑/加分回答：**

- `option()` 设置的是ServerSocketChannel（Boss）的参数
- `childOption()` 设置的是SocketChannel（Worker）的参数
- `SO_BACKLOG` 设置后要和OS的 `somaxconn` 配合，取两者的最小值
- `TCP_NODELAY=true` 对IM很重要：禁用Nagle算法后，小消息（如心跳包）不需要等待凑够MSS才发送，降低延迟

### 第29集：如何设计一个完整的Netty IM服务端？核心骨架代码是怎样的？

**💡 核心回答：**

完整的IM服务端包含以下核心模块：
1. **连接管理层**：Server启动、Pipeline配置、连接管理
2. **协议层**：自定义协议编解码、粘包拆包处理

```java
// ========================
// 1. 服务启动入口
// ========================
public class ImServerMain {
    
    private static final int PORT = 8888;
    
    public static void main(String[] args) throws Exception {
        // Boss线程组：处理连接
        EventLoopGroup bossGroup = new NioEventLoopGroup(1);
        // Worker线程组：处理IO
        EventLoopGroup workerGroup = new NioEventLoopGroup();
        // 业务线程组：处理重逻辑
        EventExecutorGroup businessGroup = new DefaultEventExecutorGroup(
            Runtime.getRuntime().availableProcessors() * 4);
        
        try {
            ServerBootstrap bootstrap = new ServerBootstrap();
            bootstrap.group(bossGroup, workerGroup)
                .channel(NioServerSocketChannel.class)
                .option(ChannelOption.SO_BACKLOG, 2048)
                .option(ChannelOption.SO_REUSEADDR, true)
                .childOption(ChannelOption.TCP_NODELAY, true)
                .childOption(ChannelOption.SO_KEEPALIVE, true)
                .childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
                    new WriteBufferWaterMark(32 * 1024, 256 * 1024))
                .childHandler(new ImServerInitializer(businessGroup));
            
            System.out.println("========== IM Server Starting ==========");
            ChannelFuture future = bootstrap.bind(PORT).sync();
            System.out.println("IM Server started on port " + PORT);
            
            // 注册JVM关闭钩子
            Runtime.getRuntime().addShutdownHook(new Thread(() -> {
                System.out.println("Shutting down IM Server...");
                bossGroup.shutdownGracefully();
                workerGroup.shutdownGracefully();
                businessGroup.shutdownGracefully();
            }));
            
            future.channel().closeFuture().sync();
        } finally {
            bossGroup.shutdownGracefully();
            workerGroup.shutdownGracefully();
            businessGroup.shutdownGracefully();
        }
    }
}

// 4. 业务处理
// ========================
public class ImBusinessHandler extends SimpleChannelInboundHandler<ImMessage> {
    
    @Override
    protected void channelRead0(ChannelHandlerContext ctx, ImMessage msg) {
        String userId = ctx.channel().attr(UserAttrKey.USER_ID).get();
        
        switch (msg.getCmd()) {
            case ImProtocol.CMD_CHAT:
                handleSingleChat(ctx, userId, msg);
                break;
            case ImProtocol.CMD_GROUP_MSG:
                handleGroupChat(ctx, userId, msg);
                break;
            case ImProtocol.CMD_ACK:
                handleAck(ctx, userId, msg);
                break;
            case ImProtocol.CMD_READ_RECEIPT:
                handleReadReceipt(ctx, userId, msg);
                break;
            default:
                log.warn("未知命令类型: " + msg.getCmd());
        }
    }
    
    private void handleSingleChat(ChannelHandlerContext ctx, String fromUserId, 
                                    ImMessage msg) {
        ChatMessage chat = ChatMessage.parseFrom(msg.getBody());
        String toUserId = chat.getToUserId();
        
        // 消息持久化
        String msgId = IdGenerator.nextId();
        MessageStore.getInstance().saveMessage(fromUserId, toUserId, msgId, chat);
        
        // 回复ACK给发送方
        sendAck(ctx, msg.getSeqId(), msgId);
        
        // 路由到目标用户
        Channel targetChannel = ChannelManager.getInstance().getChannel(toUserId);
        if (targetChannel != null && targetChannel.isActive() && targetChannel.isWritable()) {
            ImMessage forwardMsg = buildForwardMsg(msg, fromUserId, msgId);
            targetChannel.writeAndFlush(forwardMsg);
            MessageStore.getInstance().markDelivered(msgId);
        } else {
            // 离线消息存储
            MessageStore.getInstance().saveOfflineMessage(toUserId, msgId, chat);
        }
    }
    
    private void handleGroupChat(ChannelHandlerContext ctx, String fromUserId, 
                                   ImMessage msg) {
        ChatMessage chat = ChatMessage.parseFrom(msg.getBody());
        String groupId = chat.getToUserId(); // 群聊中toUserId存的是groupId
        
        // 群消息广播
        ChannelGroup group = GroupChatManager.getInstance().getGroup(groupId);
        if (group != null) {
            for (Channel member : group) {
                String memberId = member.attr(UserAttrKey.USER_ID).get();
                if (!memberId.equals(fromUserId) && member.isWritable()) {
                    member.writeAndFlush(msg.retain());
                }
            }
            ReferenceCountUtil.release(msg);
        }
    }
    
    private void sendAck(ChannelHandlerContext ctx, int seqId, String msgId) {
        ImMessage ack = new ImMessage();
        ack.setCmd(ImProtocol.CMD_ACK);
        ack.setSeqId(seqId);
        ack.setBody(new AckMessage.Builder()
            .seqId(seqId).msgId(msgId).status(1).build().toByteArray());
        ctx.writeAndFlush(ack);
    }
}
```
