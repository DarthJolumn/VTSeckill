## 第1章：Prometheus 监控体系全景

### 💡 核心概念：

**Prometheus 是什么：**

Prometheus 是 Cloud Native Computing Foundation（CNCF）的毕业项目，一个开源的系统监控和告警工具包。它的核心设计理念是"多维时间序列数据库 + 强大的查询语言 PromQL + 灵活的告警机制"。

**Pull 模型 vs Push 模型：**

Prometheus 默认采用 Pull（拉取）模式，主动从目标服务的 HTTP 端点拉取指标数据。这与传统 Push（推送）模式有本质区别：

```
┌─────────────────────────────────────────────────────────┐
│                    Pull 模型                             │
│                                                         │
│   Prometheus Server                                     │
│   ┌──────────┐    定时拉取    ┌──────────────────────┐  │
│   │  TSDB    │◄──────────────│  /metrics endpoint   │  │
│   │ (存储引擎)│    每15s      │  (应用暴露的指标端点)  │  │
│   └────┬─────┘              └──────────────────────┘  │
│        │                                                │
│        ▼                                                │
│   ┌──────────┐    push        ┌──────────────────────┐  │
│   │ Alertmgr │◄──────────────│  Pushgateway          │  │
│   └──────────┘               │  (短生命周期任务推送)   │  │
│                              └──────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

Pull 模型的优势：
- Prometheus 掌握采集节奏，便于控制资源消耗
- 目标服务挂了，Prometheus 能立刻感知（拉不到就是问题）
- 方便在本地调试（直接 curl /metrics 看数据）

Push 模型的场景：
- 定时任务（CronJob），执行完就退出，来不及被拉
- 解决方案：通过 Pushgateway 中转，任务执行完主动推送

**TSDB（时序数据库）：**

Prometheus 内部使用自定义的 TSDB 存储，核心特性：
- 本地磁盘存储，默认保留15天
- 数据按2小时分块（block），压缩后存储
- 通过 `remote_write` 支持长期存储（Thanos、VictoriaMetrics、M3DB）

**Service Discovery（服务发现）：**

Prometheus 支持多种服务发现机制，动态感知采集目标变化：
- Kubernetes SD：自动发现 K8s 集群中的 Pod/Service/Node
- Consul SD / Etcd SD：基于注册中心的服务发现
- File SD：基于文件的目标列表（适合静态配置）
- DNS SD：基于 DNS 记录的服务发现

### ⚠️ 常见问题与优化：

**1. Prometheus 内存暴涨问题**

生产环境中 Prometheus 内存消耗与时间序列数量直接相关。经验公式：

```
内存 ≈ 时间序列数 × 每序列内存（约 1.3KB ~ 3KB）
```

优化方案：
- 通过 `metric_relabel_configs` 丢弃无用指标
- 使用 `match_only` 减少 label 组合
- 调整 `scrape_interval` 降低采集频率（非核心指标从 15s 改为 60s）

```yaml
# 丢弃无用指标示例
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'go_gc_.*|go_memstats_.*'
    action: drop
  - source_labels: [__name__]
    regex: 'etcd_.*'
    action: drop
```

**2. 热加载配置**

不需要重启 Prometheus 即可重新加载配置：

```bash
# 方式1：发送 SIGHUP 信号
kill -HUP $(pidof prometheus)

# 方式2：HTTP API（需要启动参数 --web.enable-lifecycle）
curl -X POST http://localhost:9090/-/reload
```

## 第2章：Spring Boot 应用监控

### 💡 核心概念：

Spring Boot 应用监控的核心链路：

```
Spring Boot App
    │
    ├── Micrometer（指标门面层）
    │       │
    │       ├── Counter（计数器：请求总数、错误总数）
    │       ├── Gauge（瞬时值：内存使用、队列长度）
    │       ├── Timer（计时器：请求耗时、方法执行时间）
    │       └── DistributionSummary（分布统计：请求体大小、支付金额）
    │
    ├── Spring Boot Actuator（暴露端点）
    │       │
    │       ├── /actuator/health       健康检查
    │       ├── /actuator/info         应用信息
    │       ├── /actuator/metrics      指标列表
    │       └── /actuator/prometheus   Prometheus 格式输出
    │
    └── Prometheus（拉取采集）
            │
            └── GET /actuator/prometheus → 时序数据
```

Micrometer 是 Spring Boot 2.x+ 内置的指标门面（类似 SLF4J 之于日志），它屏蔽了底层监控系统的差异，同一套代码可以同时输出 Prometheus、Datadog、InfluxDB 等格式的指标。

**自定义业务指标代码：**

```java
// OrderMetrics.java - 订单业务指标
package com.yuecha.order.metrics;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import io.micrometer.core.instrument.DistributionSummary;
import org.springframework.stereotype.Component;

import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicLong;

@Component
public class OrderMetrics {

    private final Counter orderCreatedCounter;
```

**指标采集切面（自动统计方法耗时）：**

```java
// MetricAspect.java - AOP 自动采集方法指标
package com.yuecha.order.metrics;

import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class MetricAspect {

    private final MeterRegistry meterRegistry;

    public MetricAspect(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
    }

    @Around("@annotation(io.micrometer.core.annotation.Timed)")
    public Object timedMethod(ProceedingJoinPoint joinPoint) throws Throwable {
        String className = joinPoint.getTarget().getClass().getSimpleName();
        String methodName = joinPoint.getSignature().getName();
        String timerName = "yuecha.method." + className + "." + methodName;

        Timer timer = Timer.builder(timerName)
                .tag("class", className)
                .tag("method", methodName)
                .description("方法执行耗时")
                .publishPercentiles(0.5, 0.95, 0.99)
                .register(meterRegistry);

        return timer.recordCallable(joinPoint::proceed);
    }
}
```

### ⚠️ 常见问题与优化：

**1. 指标基数爆炸问题**

最常见的坑：HTTP 接口路径包含动态参数导致指标基数爆炸。

```
# 错误示例：/api/order/12345、/api/order/67890 每个都是独立的时间序列
http_server_requests_seconds_count{uri="/api/order/12345"}
http_server_requests_seconds_count{uri="/api/order/67890"}
```

解决方案：使用 WebMvcTagsProvider 将 URI 模板化：

```java
// UriTemplateTagProvider.java
import io.micrometer.core.instrument.Tag;
import io.micrometer.core.instrument.binder.http.DefaultWebMvcTagsProvider;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.stereotype.Component;

@Component
public class UriTemplateTagProvider extends DefaultWebMvcTagsProvider {
    @Override
    public Iterable<Tag> getTags(HttpServletRequest request,
                                  HttpServletResponse response,
                                  Object handler,
                                  Throwable exception) {
        // 将 /api/order/12345 转为 /api/order/{id}
        String uri = request.getRequestURI();
        if (uri.matches("/api/order/\\d+")) {
            uri = "/api/order/{id}";
        } else if (uri.matches("/api/product/\\d+")) {
            uri = "/api/product/{id}";
        }
        // 返回包含模板化 URI 的 tags
        return super.getTags(request, response, handler, exception);
    }
}
```

**2. Prometheus 采集 Spring Boot 指标返回 401/403**

Actuator 端点可能被 Spring Security 拦截，需要放行：

```java
// SecurityConfig.java
@Configuration
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/**").permitAll()  // 放行 actuator
            .anyRequest().authenticated()
        );
        return http.build();
    }
}
```

**3. 指标数据丢失**

Spring Boot 3.x 中，如果 `management.metrics.distribution.percentiles-histogram` 没开启，`histogram_quantile()` 函数无法工作，P95/P99 将不准。确保配置正确。

## 第3章：JVM 深度监控

### 💡 核心概念：

JVM 监控是 Java 应用监控的基石。悦茶平台运行着多个 Spring Boot 服务，每个服务都需要完善的 JVM 监控来确保稳定运行。

**JVM 关键指标体系：**

```
JVM 监控指标
├── 内存
│   ├── Heap Memory（堆内存）
│   │   ├── Eden Space
│   │   ├── Survivor Space (S0/S1)
│   │   └── Old Generation
│   ├── Non-Heap Memory（非堆内存）
│   │   ├── Metaspace
│   │   ├── Code Cache
│   │   └── Compressed Class Space
│   └── Direct Memory（堆外内存）
│
├── GC（垃圾回收）
│   ├── Young GC 次数 / 耗时
│   ├── Old GC（Full GC）次数 / 耗时
│   └── GC Pause Time（GC 停顿时间）
│
├── 线程
│   ├── 活跃线程数
│   ├── 守护线程数
│   ├── 线程状态分布（RUNNABLE/WAITING/BLOCKED/TIMED_WAITING）
│   └── 死锁检测
│
├── 类加载
│   ├── 已加载类数
│   └── 已卸载类数
│
└── 缓冲区
    └── NIO Buffer (Mapped/Direct)
```

**G1 GC vs ZGC 关键指标差异：**

| 指标 | G1 GC | ZGC |
|------|-------|-----|

### ⚠️ 常见问题与优化：

**线上 Full GC 排查完整流程：**

```
Step 1: 收到告警
    ↓ Full GC 频率 > 0.1/s 或 堆内存 > 85%
Step 2: 快速确认
    ↓ jstat -gcutil <PID> 1000
    ↓ 观察 O（Old 区）使用率、FGC（Full GC 次数）、FGCT（Full GC 耗时）
Step 3: 如果 O 持续接近 100%
    ↓ jmap -dump:live,format=b,file=/tmp/heap.hprof <PID>
    ↓ 注意：dump 会触发 Full GC，生产环境谨慎操作
    ↓ 替代方案：使用 -XX:+HeapDumpOnOutOfMemoryError 提前配置
Step 4: 分析 dump 文件
    ↓ 使用 MAT（Memory Analyzer Tool）或 VisualVM 分析
    ↓ 查看 Dominator Tree（支配树）找到大对象
    ↓ 查看 Leak Suspects（泄漏嫌疑）报告
Step 5: 定位代码
    ↓ 根据大对象的 GC Root 引用链，定位到代码位置
    ↓ 常见原因：
    │   ├── 本地缓存无上限（ConcurrentHashMap 无限增长）
    │   ├── ThreadLocal 未清理
    │   ├── 大对象（批量查询结果集未分页）
    │   └── 第三方库内存泄漏
Step 6: 修复验证
    ↓ 修复后灰度发布
    ↓ 观察 Grafana 的 JVM 面板确认堆内存趋势正常
```

**1. 阿里云 Tair vs 自建 Redis 监控差异：**

| 维度 | 阿里云 Tair（Redis 企业版） | 自建 Redis |
|------|---------------------------|------------|
| 监控接入 | 云监控 API / ARMS | redis_exporter |
| 大 Key 分析 | 控制台内置大 Key 分析 | 需要 `redis-cli --bigkeys` 或 SCAN |
| 热 Key 分析 | 控制台内置热 Key 分析 | 需要 `redis-cli --hotkeys`（需开启 LFU） |

| 告警 | 云监控 + 短信/电话 | Prometheus Alertmanager |
| 桥接方案 | 阿里云 Prometheus 托管版 → remote_write 到自建 Prometheus | 直接采集 |

**2. 大 Key 检测脚本：**

```bash
#!/bin/bash
# redis-bigkey-scan.sh - Redis 大 Key 扫描脚本
# 建议定期执行（如每天凌晨），将结果推送到监控平台

REDIS_HOST="redis-master"
REDIS_PORT=6379
REDIS_PASSWORD="${REDIS_PASSWORD}"

redis-cli -h $REDIS_HOST -p $REDIS_PORT -a $REDIS_PASSWORD --bigkeys

echo ""
echo "========== RDB 分析 =========="
# 使用 redis-rdb-tools 分析 RDB 文件
# pip install rdbtools
rdb --command json /var/lib/redis/dump.rdb | \
  python3 -c "
import json, sys
data = json.load(sys.stdin)
# 按大小排序，输出 Top 20 大 Key
sorted_data = sorted(data, key=lambda x: x.get('size_in_bytes', 0), reverse=True)
for item in sorted_data[:20]:
    print(f\"{item.get('key', 'N/A'):50s} {item.get('type', 'N/A'):10s} {item.get('size_in_bytes', 0) / 1024 / 1024:.2f} MB\")
```

**3. Redis 内存驱逐策略对监控的影响：**

当 Redis 内存达到 `maxmemory` 上限时，会根据配置的驱逐策略（`maxmemory-policy`）开始淘汰 Key。监控中需要关注 `redis_evicted_keys_total` 指标的变化：

- 如果该指标持续增长，说明内存不足，需要扩容或优化 Key 过期策略
- 常见驱逐策略：`allkeys-lru`（推荐）、`volatile-lru`、`noeviction`（不驱逐，写入报错）

悦茶平台推荐配置：`maxmemory-policy allkeys-lru`，并设置 `maxmemory` 为物理内存的 70%。

```bash
  python3 -c "import json,sys; print(int(json.load(sys.stdin)['data']['result'][0]['value'][1]))")

echo "当前堆积量: $CURRENT_LAG"

if [ "$CURRENT_LAG" -gt "$LAG_THRESHOLD" ]; then
    echo "堆积超过阈值，触发扩容..."

    # 方案1：K8s HPA 扩容消费者 Pod
    kubectl scale deployment order-notify-consumer --replicas=6 -n yuecha

    # 方案2：通过钉钉/飞书 Webhook 通知运维
    curl -X POST "https://oapi.dingtalk.com/robot/send?access_token=${DINGTALK_TOKEN}" \
      -H 'Content-Type: application/json' \
      -d "{
        \"msgtype\": \"text\",
        \"text\": {
            \"content\": \"【自动扩容】${TOPIC} 消费堆积 ${CURRENT_LAG}，已触发扩容至 6 实例\"
        }
    }"

    # 方案3：如果消费者数已达到分区数上限，需要增加分区
    PARTITION_COUNT=$(kafka-topics.sh --bootstrap-server kafka-1:9092 --describe --topic $TOPIC | grep -c "Partition:")
    CONSUMER_COUNT=$(kubectl get pods -l app=order-notify-consumer -n yuecha --no-headers | wc -l)

    if [ "$CONSUMER_COUNT" -ge "$PARTITION_COUNT" ]; then
        echo "消费者数已达分区数上限($PARTITION_COUNT)，需要增加分区"
        # kafka-topics.sh --alter --topic $TOPIC --partitions 12 --bootstrap-server kafka-1:9092
    fi
```

**告警 Webhook 适配器（钉钉通知）：**

```java
// SkyWalkingAlarmController.java
package com.yuecha.monitor.controller;

import com.fasterxml.jackson.annotation.JsonProperty;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.client.RestTemplate;

import java.util.List;
import java.util.Map;

@RestController
@RequestMapping("/skywalking")
public class SkyWalkingAlarmController {

    @Value("${dingtalk.webhook.url}")
    private String dingtalkWebhookUrl;

    private final RestTemplate restTemplate = new RestTemplate();

    @PostMapping("/callback")
    public ResponseEntity<String> handleAlarm(@RequestBody AlarmMessage alarm) {
        // 构建钉钉消息
        Map<String, Object> message = Map.of(
            "msgtype", "markdown",
            "markdown", Map.of(
                "title", "SkyWalking 告警",
                "text", buildAlarmMarkdown(alarm)
            )
        );

        // 发送钉钉通知
        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        HttpEntity<Map<String, Object>> request = new HttpEntity<>(message, headers);
        restTemplate.postForEntity(dingtalkWebhookUrl, request, String.class);

        return ResponseEntity.ok("OK");
    }

    private String buildAlarmMarkdown(AlarmMessage alarm) {
        StringBuilder sb = new StringBuilder();
        sb.append("### 🚨 SkyWalking APM 告警\n\n");
        sb.append("**告警名称:** ").append(alarm.getRuleName()).append("\n\n");
        sb.append("**告警消息:** ").append(alarm.getAlarmMessage()).append("\n\n");
        sb.append("**触发时间:** ").append(java.time.Instant.ofEpochMilli(alarm.getStartTime()))
          .toString();
        return sb.toString();
    }

    // SkyWalking 告警消息体
    public static class AlarmMessage {
        @JsonProperty("scopeId")
        private int scopeId;
        @JsonProperty("name")
        private String name;
        @JsonProperty("id0")
        private String id0;
        @JsonProperty("id1")
        private String id1;
        @JsonProperty("ruleName")
        private String ruleName;
        @JsonProperty("alarmMessage")
        private String alarmMessage;
        @JsonProperty("startTime")
        private long startTime;
        @JsonProperty("tags")
        private Map<String, String> tags;

        // getters/setters 省略
        public String getRuleName() { return ruleName; }
        public String getAlarmMessage() { return alarmMessage; }
        public long getStartTime() { return startTime; }
    }
}
```

### ⚠️ 常见问题与优化：

**1. Agent 性能影响优化：**

- 生产环境建议采样率设为 0.3~0.5（每3秒采集300~500条 Trace）
- 非核心服务可以设为 0.1 或更低
- 使用 `agent.ignore_url` 排除健康检查、metrics 端点
- 大响应体的 HTTP 接口，考虑设置 `plugin.http.include_http_headers` 只采集 Header

**2. OAP Server 存储优化：**

- ES 索引按天分片，定期清理历史数据
- 生产环境 ES 至少 3 节点，配置 `indexShardsNumber: 3`
- `bulkActions: 5000` 确保批量写入效率
- 对于 Trace 数据，可以使用 BanyanDB（SkyWalking 原生存储引擎），性能更优

**3. 跨线程 TraceId 传播：**

在异步场景（线程池、CompletableFuture）中，TraceId 默认不会传播。解决方案：

```java
// 使用 SkyWalking Toolkit 跨线程传播
import org.apache.skywalking.apm.toolkit.trace.RunnableWrapper;
import org.apache.skywalking.apm.toolkit.trace.CallableWrapper;

// 方式1：使用 RunnableWrapper
executorService.submit(RunnableWrapper.of(() -> {
    // 这里仍然在同一个 Trace 中
    orderService.processOrder(orderId);
}));

// 方式2：使用 @Trace 注解
@Trace(operationName = "asyncProcessOrder")
public void asyncProcessOrder(Long orderId) {
    // 自动创建子 Span
}
```

### ⚠️ 常见问题与优化：

**1. 阿里云 SLS vs 自建 ELK 对比：**

| 维度 | 阿里云 SLS | 自建 ELK/PLG |
|------|-----------|--------------|
| 部署 | 全托管 | 自建，运维成本高 |
| 存储成本 | 按量付费（较高） | 自有服务器（较低） |
| 查询性能 | 秒级响应 | 取决于 ES 配置 |
| 日志分析 | 内置 SQL 分析、机器学习 | 需要自建 |
| 告警 | 内置告警 + 对接云监控 | Grafana Alerting |
| 适用场景 | 小团队、快速启动 | 大规模、成本敏感 |

**2. Loki 标签设计原则：**

```
✅ 好的标签（低基数）：
   - {job="yuecha"}
   - {service="order-service"}
   - {level="ERROR"}
   - {host="app-server-01"}

❌ 坏的标签（高基数，会导致内存爆炸）：
   - {traceId="a1b2c3d4"}      ← 每个 Trace 一个值
   - {userId="12345"}           ← 用户数太多
   - {orderId="20260421001"}   ← 订单数太多

原则：Loki 标签用于过滤（类似 Prometheus），高基数的字段应该作为日志内容
      而非标签。查询时用 |= "traceId=a1b2c3d4" 行内过滤。
```

**3. Filebeat vs Promtail 资源占用对比：**

| 指标 | Filebeat | Promtail |
|------|----------|----------|
| 内存 | ~50-100MB | ~30-60MB |
| CPU | ~5% | ~2-3% |
| 部署 | 需要 JVM（Logstash）或独立 | 独立二进制 |
| 管道 | 支持复杂的 Grok/Mutate | Pipeline stages |
| 推荐 | ELK 栈 | PLG 栈 |

```yaml
# prometheus/http_error_rules.yml
groups:
  - name: http_error_alerts
    rules:
      # 5xx 错误率 > 1%（全局）
      - alert: Http5xxErrorRateHigh
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          /
          sum(rate(http_server_requests_seconds_count[5m]))
          > 0.01
        for: 3m
        labels:
          severity: critical
          team: backend
        annotations:
          summary: "HTTP 5xx 错误率超过 1%"
          description: "当前 5xx 错误率 {{ $value | humanizePercentage }}，持续 3 分钟"

      # 按服务维度的 5xx 告警
      - alert: Service5xxErrorRateHigh
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) by (application)
          /
          sum(rate(http_server_requests_seconds_count[5m])) by (application)
          > 0.05
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "服务 {{ $labels.application }} 5xx 错误率超过 5%"

      # 4xx 错误率 > 10%（可能是客户端问题）
      - alert: Http4xxErrorRateHigh
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"4.."}[5m]))
          /
          sum(rate(http_server_requests_seconds_count[5m]))
          > 0.10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "HTTP 4xx 错误率超过 10%"

      # 按接口维度的错误率（特定接口异常）
      - alert: EndpointErrorRateHigh
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) by (uri, application)
          /
          sum(rate(http_server_requests_seconds_count[5m])) by (uri, application)
          > 0.10
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "接口 {{ $labels.uri }} 错误率超过 10%"

      # 单个接口 5xx 绝对数量告警
      - alert: Endpoint5xxCountHigh
        expr: |
          sum(increase(http_server_requests_seconds_count{status=~"5.."}[5m])) by (uri, application) > 50
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "接口 {{ $labels.uri }} 5分钟内 5xx 超过 50 次"
```

**四、SLA/SLO/错误预算实现**

```yaml
# SLA/SLO 定义与监控
# 悦茶平台 SLA 目标：99.9%（月度不可用时间 < 43 分钟）

# prometheus/slo_rules.yml
groups:
  - name: slo_rules
    interval: 30s
    rules:
      # 记录规则：可用性指标
      - record: job:http_server_requests:availability_ratio_5m
        expr: |
          1 - (
            sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) by (job)
            /
            sum(rate(http_server_requests_seconds_count[5m])) by (job)
          )

      # 记录规则：30天滚动可用性
      - record: job:http_server_requests:availability_ratio_30d
        expr: |
          1 - (
            sum(rate(http_server_requests_seconds_count{status=~"5.."}[30d])) by (job)
            /
            sum(rate(http_server_requests_seconds_count[30d])) by (job)
          )

      # 记录规则：错误预算消耗速率
      - record: job:slo:error_budget_burn_rate_1h
        expr: |
          (1 - job:http_server_requests:availability_ratio_5m{job=~"yuecha-.*"})
          /
          (1 - 0.999)    # SLO = 99.9%，错误预算 = 0.1%

      # 告警：错误预算消耗过快（1小时燃尽速率 > 14.4x）
      # 含义：如果以当前速率消耗，错误预算将在 30天内耗尽
      - alert: SLOErrorBudgetBurnRateHigh
        expr: job:slo:error_budget_burn_rate_1h > 14.4
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "SLO 错误预算消耗过快（1h 燃尽速率 > 14.4x）"
          description: "{{ $labels.job }} 当前燃尽速率 {{ $value }}x，按此速率错误预算将在 {{ $value | humanizeDuration }} 内耗尽"

      # 告警：30天可用性低于 SLO
      - alert: SLOAvailabilityBelowTarget
        expr: job:http_server_requests:availability_ratio_30d < 0.999
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "30天滚动可用性低于 SLO 目标 99.9%"
          description: "{{ $labels.job }} 当前可用性 {{ $value | humanizePercentage }}"
```

### ⚠️ 常见问题与优化：

**1. 告警疲劳（Alert Fatigue）解决方案：**

- **分级明确**：P0 必须响应、P1 尽快响应、P2 工作日处理、P3 周报跟踪
- **收敛策略**：利用 Alertmanager 的 `group_by` 和 `inhibit_rules` 减少重复通知
- **定期复盘**：每月统计 Top 10 频繁告警，优化阈值或修复根因
- **值班激励**：On-call 补贴 + 故障复盘不追责（blameless）

**2. 监控盲区排查清单：**

| 检查项 | 方法 | 频率 |
|--------|------|------|
| Prometheus targets 是否全部 UP | `/targets` 页面检查 | 每日 |
| 告警规则是否覆盖所有核心指标 | 告警规则 Review | 每月 |
| Grafana Dashboard 数据是否完整 | 检查面板是否有"No Data" | 每周 |
| SkyWalking Agent 是否全部接入 | OAP 控制台查看服务列表 | 每周 |
| 日志采集是否覆盖所有应用 | Loki 查询 `{job=~".+"}` 检查 | 每月 |
| 告警演练 | 模拟故障验证告警是否触发 | 每季度 |
