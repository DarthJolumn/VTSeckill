# REDIS_SYNC 自适应流控改造方案（P99 + 非对称滞后 + 动态超时）

> 适用范围：`vtsl-seckill` 模块的 `REDIS_SYNC` 策略链路
> 涉及文件：`SlidingWindowStats` / `SyncDegradeController` / `KafkaOrderSender` / `RedisSyncStrategy` / `application.yml`
> 设计状态：**生产级可落地最终设计**（逻辑闭环，已通过 Code Review 修正）

---

## 1. 背景与问题

`REDIS_SYNC` 策略在扣减成功后，用 `KafkaTemplate.send().get(timeout)` **同步阻塞**等待 broker ack，
保证强一致。瓶颈在于：Broker 抖动时，固定超时要么误杀正常请求（503+回补），要么把请求线程挂太久拖垮线程池。

原实现（`SlidingWindowStats` + `SyncDegradeController`）已具备：
- 环形数组滑动窗口（最近 100 次发送耗时 / 超时率）
- 非对称降级（同步 → 异步受理）
- 探针恢复 + 防抖 + TTL 兜底

**但存在与简历描述不符、且统计不严谨的问题**，本次一次性修正：

| 维度 | 原实现 | 简历声称 | 本次修正 |
|------|--------|----------|----------|
| 降级阈值 | 均值 `avg > 500ms` | P99 超阈值 | **P99 超阈值** |
| 发送超时 | 固定 `3s` | P99 + k·σ 动态安全边界 | **动态超时 `clamp(P99 + 2.5σ, 100, 2000)`** |
| 恢复依据 | 探针连续成功计数 | 均值(Mean)为基准 | **Mean<200 && 超时率==0 持续达标** |

## 2. 两次 Code Review 修正的核心漏洞

### 2.1 幸存者偏差（Survivorship Bias）—— 最致命

> 原方案曾设想"超时样本不进 P99/σ"。

灾难推演：若 Kafka Broker 假死，所有请求在 `get(timeout)` 中等满才抛异常。
若剔除超时样本，窗口里只剩上一秒健康时的旧数据 → `P99 ≈ 80ms < 800ms` → 判定"网络健康，拒绝降级" →
系统继续 SYNC 死磕，每个请求挂 2s，虚拟/平台线程瞬间打满 → **雪崩**。

**修正**：超时样本**必须参与统计**，记录值 = 真实等待时长（如 2000ms）。
这些极大值天然排在数组尾部，瞬间推高 P99，极早触发降级。

### 2.2 非对称滞后状态机（Hysteresis）—— 防反复横跳

仅写 `if (p99 > 800) degrade()` 是**对称阈值**：P99 在 800ms 附近抖动时，
策略会在 SYNC/ASYNC 间疯狂横跳（Thrashing），引发大量上下文切换。

**修正**：显式定义非对称状态机
- **降级（灵敏）**：`P99 > 800ms` **或** `超时率 > 5%` → 立即切 ASYNC
- **恢复（迟钝）**：`Mean < 200ms` **且** `超时率 == 0`，并**持续 `recover-evals` 次**才切回 SYNC

相当于在降级/恢复之间加了一段"滞后缓冲区"，必须等网络环境**彻底、持续**恢复健康才回同步，
完美过滤毛刺误判，也正好把简历里"恢复以均值 Mean 为基准"真正落地。

## 3. 最终设计

### 3.1 `SlidingWindowStats`（全量统计）

```java
// 环形数组，所有样本（含超时）都进数组
public void record(long elapsedMs, boolean isTimeout);

// 全量（含超时）计算，单次拷贝排序
public ComputeStats computeStats();   // {count, mean, p99, stdDev}
public double timeoutRate();          // 基于 isTimeout 计数
public long averageMs();              // = mean（含超时）
public void reset();                  // 恢复瞬间清窗
```

- `record()`：O(1) 环形写，超时样本值 = 真实等待时长，`isTimeout` 仅用于超时率
- `computeStats()`：拷贝 `filled` 个样本到临时数组 → `Arrays.sort` 升序（N=100，亚微秒级）→
  `p99 = idx(ceil(0.99 * count) - 1)`，`σ = sqrt(meanSqDev)`；`count < 1` 返回空统计
- **不使用独立有序结构**（避免 O(N) 插入维护），按需拷贝排序 + O(1) 查找，符合约定

### 3.2 `SyncDegradeController`（状态机核心）

```java
// 状态（无锁读）
private final AtomicBoolean isDegraded = new AtomicBoolean(false);
private final AtomicInteger recoverCount = new AtomicInteger(0);

// 配置（全部走 application.yml，可调）
window-size=100, max-p99-ms=800, max-timeout-rate=0.05,
mean-recover-ms=200, recover-evals=50, timeout-k=2.5,
min-timeout-ms=100, max-timeout-ms=2000, cold-start-samples=30,
send-timeout-seconds=3, evaluate-interval-ms=100
```

- `record(elapsedMs, isTimeout)`：**仅** `window.record(...)`，热路径不做判定
- `evaluate()` → `@Scheduled(fixedDelay = evaluateIntervalMs)` **synchronized**：
  ```java
  ComputeStats s = window.computeStats();
  double rate = window.timeoutRate();
  if (!isDegraded.get() && (s.p99 > maxP99Ms || rate > maxTimeoutRate)) {
      isDegraded.set(true); recoverCount.set(0);                 // 灵敏降级
  } else if (isDegraded.get() && s.mean < meanRecoverMs && rate == 0) {
      if (recoverCount.incrementAndGet() >= recoverEvals) {      // 迟钝恢复
          isDegraded.set(false); recoverCount.set(0);
          window.reset();                                        // 清残留，干净起步
      }
  } else if (isDegraded.get()) {
      recoverCount.set(0);                                       // 毛刺重置
  }
  ```
- `isSyncMode()`：`return !isDegraded.get();`（无锁，供 `RedisSyncStrategy` 热路径）
- `safeTimeoutMs()`：热路径调用，**只锁窗口**不锁状态：
  ```java
  ComputeStats s = window.computeStats();
  if (s.count < coldStartSamples) return sendTimeoutSeconds * 1000;   // 冷启动兜底
  long boundary = (long) (s.p99 + timeoutK * s.stdDev);
  return Math.max(minTimeoutMs, Math.min(boundary, maxTimeoutMs));     // clamp(100, 2000)
  ```
- `printWindowStats`：增 p99 / σ / mean / safeTimeout / isDegraded（保留 2s 打印）
- **移除**原 `degrade-ttl-ms` / `ttlRecover`：定时 `evaluate` 已覆盖无流量场景
  （窗口残留超时样本使 mean/rate 不达标，不会误恢复）

### 3.3 `KafkaOrderSender`

```java
// 动态超时入参；真实耗时用 nanoTime 掐
public SendSyncResult sendSync(String msg, long timeoutMs) {
    long start = System.nanoTime();
    try {
        kafkaTemplate.send("seckill-order", msg).get(timeoutMs, TimeUnit.MILLISECONDS);
        return new SendSyncResult(SendOutcome.CONFIRMED, elapsedMs(start));
    } catch (TimeoutException e) {
        return new SendSyncResult(SendOutcome.TRANSIENT, elapsedMs(start)); // 真实等待
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return new SendSyncResult(SendOutcome.TRANSIENT, elapsedMs(start));
    } catch (ExecutionException e) {
        return new SendSyncResult(SendOutcome.FATAL, elapsedMs(start));
    }
}
```
- `sendAsyncReliable` 不变；`sendTimeoutSeconds` 作为冷启动兜底保留

### 3.4 `RedisSyncStrategy.createOrder`

```java
if (degrade.isSyncMode()) {
    long timeout = degrade.safeTimeoutMs();
    SendSyncResult r = sender.sendSync(msg, timeout);
    degrade.record(r.elapsedMs(), r.outcome() != SendOutcome.CONFIRMED);
    return r.outcome();
}
// 已降级：5% 探针仍走同步感知恢复，其余可靠异步受理
if (degrade.shouldSample()) {
    long timeout = degrade.safeTimeoutMs();
    SendSyncResult probe = sender.sendSync(msg, timeout);
    degrade.record(probe.elapsedMs(), probe.outcome() != SendOutcome.CONFIRMED);
    return sender.sendAsyncReliable(msg, orderNo);
}
return sender.sendAsyncReliable(msg, orderNo);
```

## 4. 工程落地打磨点（非漏洞，已采纳）

1. **恢复清窗**：状态 `DEGRADED → HEALTHY` 瞬间 `window.reset()`，清掉降级前的超时残留，
   避免"刚恢复下一轮 evaluate 又触发降级"
2. **真实耗时**：`sendSync` 用 `nanoTime()` 掐头去尾记录真实等待（含超时实际耗时），
   不用 `timeoutMs` 直接套，避免系统调度误差放大统计
3. **锁分离**：`record()` 走窗口内部锁（O(1) 环形写）；`evaluate()` 移到定时任务（100ms），
   不在每次发送时持有状态锁；`isDegraded` 用 `AtomicBoolean` 无锁读 → 高并发下无锁竞争瓶颈
4. **配置化**：阈值全部走 yml，第一版足够；后续可接 Nacos/Apollo 动态调整（含 σ 系数 k）

## 6. 面试话术（压轴题组织）

1. **先抛问题**："Kafka 同步发送的 `get()` 会阻塞线程，秒杀场景下 Broker 抖动时，固定超时要么误杀请求，要么拖垮线程池。"
2. **再讲方案**："滑动窗口统计最近 100 次发送耗时，**全量统计（含超时样本）**规避幸存者偏差——假死时超时样本的极大值会把 P99 瞬间推高，极早开启保护。"
3. **突出非对称滞后**："降级看 P99（灵敏），恢复看均值 + 持续达标（迟钝），中间形成滞后区间，防止状态机震荡（Thrashing）。"
4. **最后给机制**："动态超时 `P99 + kσ` 实现抖动自适应；非对称状态机实现流量自适应。这套机制上线后，极端场景下系统可用性显著提升。"

> 深挖防御："为什么超时样本不能剔除？" → 答幸存者偏差 + 雪崩推演。
> "怎么防反复横跳？" → 答非对称滞后：降级灵敏、恢复迟钝且需持续达标 + 恢复清窗。
